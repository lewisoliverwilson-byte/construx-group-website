Next.js ships with aggressive caching by default. That's mostly good. But when it caches things you didn't expect, or doesn't invalidate when you do, the defaults become a source of bugs. Here's the complete picture.

## The four caching layers

| Layer | What it caches | Scope | Invalidation |
|-------|---------------|-------|--------------|
| Request Memoization | `fetch()` responses | Single request | Automatic (per request) |
| Data Cache | `fetch()` responses | Cross-request | `revalidate`, `cache: 'no-store'` |
| Full Route Cache | Rendered page HTML/RSC | Build-time | `revalidateTag`, `revalidatePath` |
| Router Cache | Client-side page cache | Browser session | Navigation, `router.refresh()` |

## Request Memoization

Within a single render cycle, identical `fetch()` calls return the same result automatically:

```ts
// Both of these hit the network once, not twice
const user1 = await getUser(userId);  // fetch
const user2 = await getUser(userId);  // returns memoized result

async function getUser(id: string) {
  return fetch(`/api/users/${id}`).then(r => r.json());
}
```

This is automatic and non-configurable. It only applies within a single render — doesn't persist across requests.

## Data Cache: persistent across requests

The Data Cache persists between requests and even deployments. Opt in with `next`:

```ts
// Cached for 60 seconds (time-based revalidation)
const posts = await fetch('https://api.example.com/posts', {
  next: { revalidate: 60 },
});

// Cached indefinitely, invalidated by tag
const config = await fetch('https://api.example.com/config', {
  next: { tags: ['site-config'] },
});

// Never cached — always fresh
const livePrice = await fetch('https://api.example.com/price', {
  cache: 'no-store',
});
```

```ts
// Invalidate by tag — from a Server Action or Route Handler
import { revalidateTag } from 'next/cache';

export async function updateConfig(data: ConfigData) {
  await db.update(siteConfig).set(data);
  revalidateTag('site-config');  // purges all fetches tagged 'site-config'
}
```

In Next.js 15, `fetch()` defaults to `cache: 'no-store'` (uncached) — unlike Next.js 14. Set `revalidate` explicitly for the caching behavior you want.

## Redis for application-level caching

The Data Cache handles `fetch()`. For database queries, computed values, and shared state, use Redis:

```ts
// lib/cache.ts
import { Redis } from '@upstash/redis';

export const redis = Redis.fromEnv();  // UPSTASH_REDIS_REST_URL + TOKEN

export async function getCached<T>(
  key: string,
  fetcher: () => Promise<T>,
  ttl: number = 300,  // 5 minutes default
): Promise<T> {
  const cached = await redis.get<T>(key);
  if (cached !== null) return cached;

  const fresh = await fetcher();
  await redis.setex(key, ttl, JSON.stringify(fresh));
  return fresh;
}

export async function invalidate(...keys: string[]) {
  if (keys.length > 0) await redis.del(...keys);
}
```

```ts
// Usage — cache a slow query
const leaderboard = await getCached(
  'leaderboard:global',
  () => db.query.scores.findMany({ orderBy: [desc(scores.value)], limit: 100 }),
  60,  // cache for 60 seconds
);
```

## Cache key design

Scoped keys prevent collisions and make bulk invalidation easy:

```ts
export const cacheKeys = {
  user: (id: string) => `user:${id}`,
  userPosts: (id: string) => `user:${id}:posts`,
  post: (id: string) => `post:${id}`,
  globalLeaderboard: () => `leaderboard:global`,
  tenantData: (tenantId: string, resource: string) => `tenant:${tenantId}:${resource}`,
};

// Invalidate everything for a user
await invalidate(
  cacheKeys.user(userId),
  cacheKeys.userPosts(userId),
);
```

## Stale-while-revalidate at the edge

For public pages, serve the cached version instantly while revalidating in the background:

```ts
// app/api/trending/route.ts
export async function GET() {
  const posts = await getTrendingPosts();

  return Response.json(posts, {
    headers: {
      'Cache-Control': 'public, s-maxage=60, stale-while-revalidate=300',
      //                       ↑ fresh for 60s  ↑ serve stale for 5min while revalidating
    },
  });
}
```

At the CDN (Vercel Edge, Cloudflare), this means: serve instantly from cache for 5 minutes. After 60 seconds, trigger a background revalidation but still serve the stale response. Users never wait.

## On-demand revalidation via webhook

When upstream data changes, invalidate exactly what changed:

```ts
// app/api/webhooks/cms/route.ts
export async function POST(req: Request) {
  const { type, document } = await req.json();

  if (type === 'publish') {
    // Invalidate the specific page and any feeds that include it
    await Promise.all([
      revalidatePath(`/journal/${document.slug}`),
      revalidateTag('journal-feed'),
    ]);
  }

  return Response.json({ revalidated: true });
}
```

## Avoiding cache bugs

The most common caching mistakes:

**1. Not scoping cache keys by tenant**
```ts
// Bug: all tenants see the same cached data
const posts = await getCached('posts', fetchPosts);

// Fix: scope by tenant
const posts = await getCached(`posts:${tenantId}`, () => fetchPosts(tenantId));
```

**2. Caching user-specific data at the page level**
```ts
// Bug: first user's data gets cached, served to everyone
export const revalidate = 3600;  // don't do this on user-specific pages

// Fix: don't cache pages that depend on session
export const dynamic = 'force-dynamic';
```

**3. Forgetting to invalidate after mutations**
```ts
// Bug: cache serves stale data after update
async function updatePost(id: string, data: PostData) {
  await db.update(posts).set(data).where(eq(posts.id, id));
  // Missing: cache invalidation
}

// Fix: invalidate related cache entries
async function updatePost(id: string, data: PostData) {
  await db.update(posts).set(data).where(eq(posts.id, id));
  await Promise.all([
    invalidate(cacheKeys.post(id)),
    revalidateTag('journal-feed'),
    revalidatePath(`/journal/${data.slug}`),
  ]);
}
```

## Vercel KV vs Upstash

Both are Redis-compatible hosted services. Vercel KV is Upstash under the hood with Vercel-native integration. Use Vercel KV if you're on Vercel and want zero config. Use Upstash directly if you want the same cache to work across providers (Vercel, Railway, Fly, self-hosted).

The caching rule: cache aggressively, invalidate precisely. A stale cache hit is free. An unnecessary network call costs latency, money, and rate limit budget.
