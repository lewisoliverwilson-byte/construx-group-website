Content Security Policy is a browser security mechanism delivered via an HTTP header. It tells the browser which sources are allowed to load each type of resource. A script from an unexpected origin is blocked; an inline `<script>` without a nonce is blocked. The attacker's injected code doesn't run.

## The header

```http
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-{RANDOM}'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; font-src 'self'; connect-src 'self' https://api.construxgroup.io; frame-ancestors 'none';
```

Each directive controls a resource type:

**`default-src 'self'`**: the fallback for any directive not explicitly set. `'self'` means same origin only.

**`script-src`**: controls which JavaScript can run. The strictest target: no inline scripts, no `eval()`, scripts from self only, with a per-request nonce for any legitimate inline scripts.

**`style-src`**: controls CSS. `'unsafe-inline'` is often required because CSS-in-JS libraries inject inline styles. For Tailwind (class-based), you can often remove `'unsafe-inline'`.

**`img-src`**: controls image sources. `data:` allows base64 images. `https:` allows any HTTPS image URL — common for user-generated content.

**`connect-src`**: controls which URLs `fetch`, `XMLHttpRequest`, and WebSocket can connect to. List all API endpoints here.

**`frame-ancestors 'none'`**: prevents the page from being embedded in iframes — blocks clickjacking attacks. Equivalent to the older `X-Frame-Options: DENY`.

## Nonces for inline scripts

The fundamental problem with `'unsafe-inline'`: it allows any inline script, including injected ones. Nonces solve this: each response includes a randomly generated nonce, and only inline scripts with that nonce attribute are executed.

```http
Content-Security-Policy: script-src 'self' 'nonce-r4nd0m123'
```

```html
<script nonce="r4nd0m123">
  // This runs — nonce matches
</script>

<script>
  // This is blocked — no nonce
</script>
```

The nonce must be:
- Randomly generated per request (not per build or per session)
- At least 128 bits of entropy
- Base64-encoded

## Implementation in Next.js middleware

```ts
// middleware.ts
import { NextRequest, NextResponse } from 'next/server';

function generateNonce(): string {
  const array = new Uint8Array(16);
  crypto.getRandomValues(array);
  return Buffer.from(array).toString('base64');
}

export function middleware(req: NextRequest) {
  const nonce = generateNonce();

  const csp = [
    "default-src 'self'",
    `script-src 'self' 'nonce-${nonce}' 'strict-dynamic'`,
    "style-src 'self' 'unsafe-inline'",
    "img-src 'self' data: https:",
    "font-src 'self'",
    "connect-src 'self' https://api.construxgroup.io wss://api.construxgroup.io",
    "frame-ancestors 'none'",
    "base-uri 'self'",
    "form-action 'self'",
    "upgrade-insecure-requests",
  ].join('; ');

  const res = NextResponse.next();

  res.headers.set('Content-Security-Policy', csp);
  res.headers.set('x-nonce', nonce);  // pass nonce to the app

  return res;
}
```

```tsx
// app/layout.tsx — read nonce from headers
import { headers } from 'next/headers';

export default function RootLayout({ children }: { children: React.ReactNode }) {
  const nonce = headers().get('x-nonce') ?? '';

  return (
    <html>
      <head>
        <script nonce={nonce} dangerouslySetInnerHTML={{
          __html: `window.__NONCE__ = "${nonce}"`,
        }} />
      </head>
      <body>{children}</body>
    </html>
  );
}
```

## `'strict-dynamic'`

`'strict-dynamic'` is a key directive for Next.js: it allows dynamically-inserted scripts created by trusted scripts (those with a valid nonce). Next.js injects script tags at runtime to load page chunks — without `'strict-dynamic'`, these would be blocked.

With `'strict-dynamic'`:
- Scripts with a valid nonce can create child scripts
- Those child scripts are trusted automatically
- Source-list expressions (`'self'`, `https:`) are ignored — trust is propagated dynamically

This is the modern approach: trust the initial scripts via nonce, let them bootstrap the rest of the application.

## Report-Only mode

Start with `Content-Security-Policy-Report-Only` before enforcing:

```http
Content-Security-Policy-Report-Only: default-src 'self'; script-src 'self' 'nonce-{...}'; report-uri https://api.construxgroup.io/csp-report
```

The browser reports violations without blocking them. Collect reports for a week, fix legitimate violations (third-party scripts you forgot to whitelist), then switch to enforcement mode.

## The headers to set alongside CSP

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

These headers address adjacent concerns: HSTS prevents protocol downgrade, `nosniff` prevents MIME sniffing, `Referrer-Policy` limits referrer data in cross-origin requests.

A well-configured CSP combined with these headers covers the majority of the browser security surface without requiring changes to application logic.
