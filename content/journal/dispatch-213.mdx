The Hyve is a multi-tenant SaaS. Every workspace — every company using The Hyve — shares the same database schema. The messages, members, channels, and files for all workspaces live in the same tables.

The naive approach to multi-tenant isolation is application-level filtering: every query includes a `WHERE workspace_id = $workspaceId` clause, and the application code ensures the correct workspace ID is always used. This works until it doesn't — a missing `WHERE` clause, a copy-paste bug, or a refactor that drops the filter means workspace A can read workspace B's data.

Row-level security (RLS) is PostgreSQL's mechanism for enforcing access control at the database level, as a policy that applies to every query regardless of what the application sends.

## How RLS works

RLS policies are defined per table. When a policy is attached to a table, PostgreSQL automatically applies a filter to every `SELECT`, `INSERT`, `UPDATE`, and `DELETE` on that table. The filter is evaluated server-side, before the query results are returned to the application.

```sql
-- Enable RLS on the messages table
ALTER TABLE messages ENABLE ROW LEVEL SECURITY;
ALTER TABLE messages FORCE ROW LEVEL SECURITY;

-- Policy: users can only see messages from their workspace
CREATE POLICY messages_workspace_isolation ON messages
  FOR ALL
  USING (workspace_id = current_setting('app.current_workspace_id')::uuid);
```

`FORCE ROW LEVEL SECURITY` is important: it applies RLS even to the table owner. Without it, the database superuser can bypass RLS. In a production system, forcing RLS on all tenants prevents accidental bypass.

## Setting the workspace context

The policy uses `current_setting('app.current_workspace_id')` — a session-level configuration variable set at the start of each request.

```ts
// Middleware: set workspace context before every query
async function withWorkspaceContext<T>(
  workspaceId: string,
  fn: () => Promise<T>
): Promise<T> {
  await db.execute(
    sql`SELECT set_config('app.current_workspace_id', ${workspaceId}, true)`
  );
  return fn();
}
```

The third argument `true` to `set_config` scopes the setting to the current transaction — it's automatically reset when the transaction ends. This prevents the workspace context from leaking across requests.

## The problem with connection pooling

RLS + connection pooling has a subtle interaction. PgBouncer in transaction mode resets session settings between clients. But in session mode (which we don't use), a connection's session settings persist across requests from different users — meaning workspace A's request could leave the `app.current_workspace_id` set to workspace A's ID, and workspace B's subsequent request on the same connection would read the wrong data.

Using `set_config` with `true` (transaction-scoped) instead of `false` (session-scoped) prevents this: the setting is reset when the transaction ends, regardless of which connection pooling mode is in use.

```sql
-- Transaction-scoped (safe with connection pooling)
SELECT set_config('app.current_workspace_id', 'ws-123', true);

-- Session-scoped (unsafe with connection pooling — don't use this)
SELECT set_config('app.current_workspace_id', 'ws-123', false);
```

## Multiple policies

RLS allows multiple policies per table. We use separate policies for SELECT, INSERT, UPDATE, and DELETE when the rules differ.

```sql
-- Members can read all messages in their workspace
CREATE POLICY messages_select ON messages
  FOR SELECT
  USING (workspace_id = current_setting('app.current_workspace_id')::uuid);

-- Users can only delete their own messages
CREATE POLICY messages_delete ON messages
  FOR DELETE
  USING (
    workspace_id = current_setting('app.current_workspace_id')::uuid
    AND author_id = current_setting('app.current_user_id')::uuid
  );
```

This enforces both workspace isolation (no cross-workspace reads) and ownership rules (only the message author can delete their message) at the database level.

## Testing RLS policies

The critical test is verifying that the policies actually prevent access when the context isn't set correctly.

```ts
test('RLS prevents cross-workspace message access', async () => {
  const workspaceA = await createWorkspace();
  const workspaceB = await createWorkspace();
  const messageA = await createMessage({ workspaceId: workspaceA.id });

  // Set context to workspace B
  await db.execute(sql`SELECT set_config('app.current_workspace_id', ${workspaceB.id}, true)`);
  
  // Try to read workspace A's message — should return empty
  const result = await db.select().from(messages).where(eq(messages.id, messageA.id));
  expect(result).toHaveLength(0); // RLS filtered it out
});
```

We run this test against a real PostgreSQL instance (not a mock) because RLS is a database-level feature. A mocked database would give a false pass.

## What RLS doesn't cover

**Application-level logic:** RLS enforces data isolation but not business rules. "A user can only view channels they're a member of" requires application logic (or additional RLS policies) beyond basic workspace isolation.

**API keys and service accounts:** Service accounts that need to read across workspaces (for admin tooling, billing, analytics) need to bypass RLS. We use a separate database role for these with `BYPASSRLS` privilege, not the application role.

**Performance:** RLS adds overhead. Every query gets an additional filter. For simple equality checks on indexed columns (like `workspace_id`), the overhead is minimal. Complex policies with subqueries can have significant impact. We benchmark policy-heavy queries to ensure they stay within acceptable latency bounds.

## The defence-in-depth argument

We could rely on application-level filtering alone. Our code is correct; we review it carefully; the filters are always present. In practice, "the code is correct" is not a durable guarantee. RLS makes workspace isolation a constraint that applies regardless of application code correctness.

It's defence in depth: the application filters correctly, and the database enforces the same constraint. A bug that drops an application-level filter doesn't produce a data leak — it produces a permission error, which is surfaced in testing.

For a multi-tenant SaaS where workspace isolation is a core trust property, that extra layer is worth the operational complexity.
