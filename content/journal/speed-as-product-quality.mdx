Speed is underrated as a product quality dimension. Most product discussions focus on features, design, reliability, and pricing. Performance — how fast things happen — is usually treated as a technical concern rather than a product one.

This is a mistake. Speed is a feature. Users feel it. It affects perception, conversion, and retention in ways that are out of proportion to how difficult it is to achieve.

## The perception asymmetry

Slow products feel worse than they are. Fast products feel better than they are. This asymmetry is consistent across user research: latency directly affects perceived quality, even when quality is otherwise identical.

A product that scans a product page in 2 seconds feels dramatically more capable than one that scans the same page in 6 seconds. The result is identical. The experience is not.

For AI products specifically, this matters more than usual. AI inference is slow — much slower than database lookups or simple computations. The latency between a user's action and the AI's response is a constant reminder that something complex is happening. If that reminder is a 4-second blank screen, the user doubts the product. If it's a 1.2-second progressive response with visual feedback, the user trusts it.

## How we measure it

For each product, we track three latency metrics:

**Time to first byte (TTFB)**: how long from request to first server response. This is infrastructure — CDN, server location, caching strategy. We target under 200ms TTFB from anywhere in Europe.

**Time to interactive (TTI)**: how long until the user can do something useful. For AI products, this often means: how long until the first token of an AI response appears. We target under 1.5s for Scoutr scans, under 800ms for The Hyve's agent responses.

**Perceived completion time**: how long the user feels it takes, even if background processing continues. This is where UI design matters — progress indicators, streaming responses, and optimistic updates all reduce perceived completion time without changing actual completion time.

## Streaming responses

The single highest-impact change we made to The Hyve's AI agent: switching from buffered to streaming responses.

Before streaming: the user clicked "generate" and waited. The API call completed. The response appeared all at once, fully formed. The wait was 3-4 seconds of nothing.

After streaming: tokens appear as they're generated. The response begins in under 800ms. The user reads while the model writes. The total generation time is the same; the experience is fundamentally different.

Streaming responses change the user's cognitive state. Instead of waiting and wondering if something is happening, they're reading. Reading feels productive. Waiting feels passive. Same underlying process, opposite emotional response.

We implemented streaming across all three products wherever AI output is the primary response. It's one of the highest-return engineering decisions we've made.

## Optimistic updates

For operations that are fast but not instant, we use optimistic updates: the UI immediately shows the expected result, and corrects only if the actual result is different.

For The Marqet's listing management: when a user edits a listing description, the change appears immediately in the UI, before the server has confirmed the save. If the save fails (network error, validation problem), we roll back and show an error. But 99.8% of saves succeed, so 99.8% of the time, the user experiences zero latency on an action that actually takes 200-400ms.

The 0.2% failure case requires careful handling — the rollback has to be obvious and the error has to be actionable. But the 99.8% success case produces a product that feels instant.

## Caching AI responses

AI responses to identical queries can be cached. This is an obvious optimisation that many AI products miss.

For Scoutr: product pages don't change constantly. A scan of a product page today will produce nearly identical results to a scan tomorrow. We cache scan results for 24 hours. Users who re-scan a recently-scanned product get an instant result. The cache is invalidated if the product page URL changes or if 24 hours have passed.

Cache hit rate for Scoutr is around 23%. That's 23% of scan requests that complete in under 100ms instead of 3-4 seconds.

## Edge deployment

All three products are deployed via AWS Amplify with edge caching where appropriate. Static pages (documentation, marketing pages, the journal) are served from the CDN edge closest to the user — typically under 50ms globally.

For dynamic AI requests, we can't cache the response at the edge (each is unique). But we can serve the application shell from the edge and make the API call from a server that's geographically close to the AI provider. Reducing the API call latency by 200ms is the same as making the AI 200ms faster, from the user's perspective.

## The investment case

Performance engineering has a better return on investment at early stage than it does later. At early stage, a 2x improvement in perceived latency can double conversion. Later, when the product is established, users are more tolerant because they've already committed.

We've made performance a first-class concern from the start. Not premature optimisation — we don't optimise before we have a working product. But once something works, we ask: how fast does this feel? How fast could it feel?

The user's perception of your product's quality is partly determined by how fast it responds. Speed isn't a technical metric. It's a product quality metric.
