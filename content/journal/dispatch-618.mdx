Every Postgres connection spawns a backend process and uses roughly 5-10MB of RAM. A database with `max_connections = 100` runs out at 100 concurrent connections — after which new connections are rejected. For a serverless application that can spawn hundreds of concurrent function instances, each trying to open a connection, this is a critical constraint.

## The problem at scale

```
Without PgBouncer:
- 20 Lambda functions × 5 connections each = 100 connections
- Hit max_connections → connection refused

With PgBouncer:
- 20 Lambda functions × 5 connections → PgBouncer
- PgBouncer → 5 real Postgres connections
- 100 Lambda functions → still ~5 real Postgres connections
```

PgBouncer multiplexes application connections into real database connections.

## Pooling modes

**Session pooling**: one real connection per application session. The connection is returned to the pool when the session ends. Lowest overhead, least multiplexing. Not useful for serverless — each Lambda invocation is a session.

**Transaction pooling**: one real connection per transaction. The connection is returned to the pool when the transaction commits or rolls back. Highest multiplexing — the right mode for serverless and web applications.

**Statement pooling**: one real connection per statement. Maximum multiplexing, but incompatible with prepared statements and multi-statement transactions.

For most applications: **transaction pooling**.

## PgBouncer configuration

```ini
# pgbouncer.ini
[databases]
construx = host=localhost port=5432 dbname=construx

[pgbouncer]
listen_port        = 6432
listen_addr        = 0.0.0.0
auth_type          = scram-sha-256
auth_file          = /etc/pgbouncer/userlist.txt

pool_mode          = transaction
default_pool_size  = 10         ; 10 real Postgres connections
max_client_conn    = 500        ; accept up to 500 app connections
reserve_pool_size  = 5          ; extra connections for spikes
server_idle_timeout = 600

; Connection string from your app: postgres://user:pass@localhost:6432/construx
```

```
# userlist.txt (hashed passwords)
"construx_user" "SCRAM-SHA-256$4096:..."
```

## Transaction pooling limitations

When using transaction pooling, some Postgres features don't work:

- **Prepared statements**: the connection may be returned to the pool between the PREPARE and EXECUTE. Disable server-side prepared statements.
- **SET SESSION**: session-level settings reset when the connection is returned. Use `SET LOCAL` inside transactions instead.
- **Advisory locks**: session-scoped locks are meaningless when the session doesn't persist.
- **NOTIFY/LISTEN**: requires a dedicated connection outside the pool.

For Prisma, disable server-side prepared statements:

```
DATABASE_URL="postgresql://user:pass@pgbouncer:6432/construx?pgbouncer=true&connection_limit=1"
```

The `pgbouncer=true` query parameter disables Prisma's prepared statement caching. `connection_limit=1` prevents Prisma from opening multiple connections per instance (PgBouncer handles the pool).

## Serverless: Neon and Supabase connection poolers

Managed Postgres providers ship PgBouncer (or equivalent) as a built-in:

```
# Neon: separate pooler endpoint
DATABASE_URL="postgresql://user:pass@ep-cool-darkness-12345-pooler.us-east-2.aws.neon.tech/construx?sslmode=require"

# Supabase: port 6543 is the PgBouncer port
DATABASE_URL="postgresql://postgres:pass@db.xyz.supabase.co:6543/postgres"
```

Use the pooler URL for serverless functions and the direct URL for migrations and long-running processes (Prisma migrations need the direct connection to run DDL statements).

## Monitoring PgBouncer

```sql
-- Connect to PgBouncer's admin database
psql -h localhost -p 6432 -U pgbouncer pgbouncer

-- Show pool status
SHOW POOLS;
-- database | user | cl_active | cl_waiting | sv_active | sv_idle | sv_used | ...

-- Show client connections
SHOW CLIENTS;

-- Show server connections (real Postgres connections)
SHOW SERVERS;

-- Show stats
SHOW STATS;
-- avg_query_time | avg_wait_time | total_xact_count | ...
```

Watch `cl_waiting`: if clients are waiting for a server connection, `default_pool_size` is too small. Watch `sv_idle`: if all servers are idle, `default_pool_size` is too large.

## When not to use PgBouncer

Long-running transactions hold a real Postgres connection for their duration — during that time, other application connections may queue waiting for a connection. If your application uses long transactions (> a few seconds), PgBouncer transaction mode doesn't help.

For long-running batch processes, background jobs, or migrations: connect directly to Postgres, bypassing the pooler.

## Alternative: Prisma Accelerate

Prisma Accelerate is a managed connection pooler with edge caching:

```ts
// DATABASE_URL points to Accelerate, not Postgres directly
const prisma = new PrismaClient();

const posts = await prisma.post.findMany({
  cacheStrategy: {
    ttl: 60,        // cache for 60 seconds
    swr: 30,        // stale-while-revalidate for 30 seconds
  },
});
```

Accelerate sits in front of your database, pools connections, and caches query results at the edge. The trade-off: vendor lock-in and cost vs operational simplicity.
