Cloudflare Workers are serverless functions that run at the edge — at Cloudflare's network layer, before traffic ever reaches your origin server. The key differences from traditional serverless (Lambda, Cloud Run): V8 isolates instead of containers (cold start < 1ms vs 100ms+), and execution at the user's nearest Cloudflare PoP rather than a fixed region.

## The runtime

Workers run in the V8 JavaScript engine in a restricted environment:

- No `process`, no `fs`, no native Node.js modules
- `fetch()`, `Request`, `Response`, `URL`, `Headers` (Web APIs)
- `crypto.subtle` (Web Crypto API)
- `caches.default` (Cloudflare's HTTP cache API)
- `KV`, `D1`, `R2`, `Durable Objects` (Cloudflare's storage primitives)
- Execution limit: 30ms CPU time on the free plan, 30s on paid

## Basic structure

```ts
// worker.ts
export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const url = new URL(request.url);

    if (url.pathname === '/api/health') {
      return Response.json({ ok: true, region: request.cf?.region });
    }

    return fetch(request); // proxy to origin
  },
};

interface Env {
  KV: KVNamespace;
  API_KEY: string;  // environment variable
}
```

Workers intercept every request. You decide whether to respond directly, modify the request/response, or proxy to the origin.

## Routing and middleware

Workers are a natural place for routing and middleware:

```ts
export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const url  = new URL(request.url);
    const path = url.pathname;

    // Auth check before hitting origin
    if (path.startsWith('/api/')) {
      const token = request.headers.get('Authorization')?.replace('Bearer ', '');
      if (!token || !(await verifyToken(token, env.JWT_SECRET))) {
        return new Response('Unauthorized', { status: 401 });
      }
    }

    // Add custom headers before proxying
    const modified = new Request(request, {
      headers: {
        ...Object.fromEntries(request.headers),
        'X-Worker-Region': request.cf?.colo ?? 'unknown',
        'X-Forwarded-For': request.headers.get('CF-Connecting-IP') ?? '',
      },
    });

    return fetch(modified);
  },
};
```

## KV: global key-value storage

Workers KV is a globally distributed key-value store. Writes propagate to all edges within ~60 seconds; reads are served from the nearest PoP.

```ts
// Store a value
await env.KV.put('user:abc123', JSON.stringify(userData), {
  expirationTtl: 3600,  // expire in 1 hour
});

// Read a value
const raw = await env.KV.get('user:abc123');
const user = raw ? JSON.parse(raw) : null;

// Delete
await env.KV.delete('user:abc123');
```

KV is eventually consistent — ideal for caching, feature flags, and rate limit counters. Not suitable for data that requires strong consistency.

## D1: SQLite at the edge

D1 is Cloudflare's serverless SQLite database. Each Worker instance gets a SQLite connection:

```ts
// Query D1
const result = await env.DB.prepare(
  'SELECT * FROM posts WHERE author_id = ? ORDER BY created_at DESC LIMIT ?'
).bind(userId, 10).all();

const posts = result.results;

// Insert
await env.DB.prepare(
  'INSERT INTO posts (id, title, author_id) VALUES (?, ?, ?)'
).bind(id, title, authorId).run();
```

D1 runs SQLite at the edge. It replicates to multiple regions for reads (eventual consistency) with a primary write location. Good for read-heavy applications with global users.

## Caching responses

```ts
const cache = caches.default;

export default {
  async fetch(request: Request): Promise<Response> {
    // Check the cache
    const cached = await cache.match(request);
    if (cached) return cached;

    // Fetch from origin
    const response = await fetch(request);

    // Cache the response
    const cloned = response.clone();
    const toCache = new Response(cloned.body, {
      headers: {
        ...Object.fromEntries(response.headers),
        'Cache-Control': 'public, max-age=300',
      },
    });
    await cache.put(request, toCache);

    return response;
  },
};
```

`caches.default` is a shared cache across Worker invocations at the same PoP. `cache.match()` and `cache.put()` follow the standard HTTP Cache API.

## Wrangler: local development

```bash
npm install -D wrangler
npx wrangler dev     # local development with remote KV/D1 bindings
npx wrangler deploy  # deploy to Cloudflare's network
```

`wrangler dev` starts a local server that emulates the Worker runtime. The `--remote` flag connects to your actual KV/D1 instances during development.

## When Workers are the right choice

**Use Workers for**:
- Request routing and rewriting (A/B tests, geolocation redirects)
- Authentication middleware (JWT verification before hitting origin)
- Response caching (custom cache logic on top of Cloudflare's CDN)
- Edge APIs with global users (global low latency without regional complexity)
- Bot detection and rate limiting

**Don't use Workers for**:
- Long-running operations (30s CPU limit on paid, 10ms on free)
- Operations requiring Node.js ecosystem (native modules, `fs`, etc.)
- Compute-intensive work — the CPU time limit bites quickly

Workers complement your origin server; they don't replace it. The pattern: handle routing, auth, caching, and lightweight compute at the edge, pass everything else to the origin.
