Next.js App Router caches aggressively by default. The intention is good — fewer database hits, faster page loads — but the behaviour surprises developers who expect React's mental model: render when state changes. With caching in the picture, a Server Component re-renders on a schedule, not on data change, unless you tell it otherwise.

## The four caches

**Request Memoization** — deduplicated within a single request. If two Server Components call the same URL in the same render, the second call reuses the first's response. This is automatic and can't be disabled.

**Data Cache** — persisted across requests. `fetch()` responses are cached in a file-system store. By default, they live indefinitely until you revalidate.

**Full Route Cache** — the rendered HTML and RSC payload for static routes. Built at `next build` for routes without dynamic functions, or on first request for ISR routes.

**Router Cache** — client-side cache of RSC payloads. Cached in memory for the current browser session.

## Opting out of the Data Cache

```ts
// Per-request: no caching
const data = await fetch('https://api.example.com/products', {
  cache: 'no-store',
});

// Per-request: revalidate after 60 seconds
const data = await fetch('https://api.example.com/products', {
  next: { revalidate: 60 },
});
```

For database queries (not using `fetch`), use route segment config:

```ts
// app/dashboard/page.tsx
export const dynamic = 'force-dynamic';  // Never cache this route
export const revalidate = 60;            // Or: revalidate every 60 seconds

export default async function Dashboard() {
  const data = await db.query.scans.findMany({ ... });  // Always fresh
  return <ScanList scans={data} />;
}
```

## On-demand revalidation

The cleanest approach: cache aggressively, revalidate when the underlying data changes.

```ts
// After a mutation, invalidate the relevant cache tags
import { revalidateTag, revalidatePath } from 'next/cache';

// In a Server Action or Route Handler:
export async function updateProduct(id: string, data: Partial<Product>) {
  await db.update(products).set(data).where(eq(products.id, id));

  revalidateTag('products');        // Revalidates all fetches tagged 'products'
  revalidatePath('/products');      // Revalidates the /products page
  revalidatePath(`/products/${id}`); // Revalidates the specific product page
}
```

```ts
// Tag your fetches to enable targeted revalidation
const products = await fetch('/api/products', {
  next: { tags: ['products'] },
});

// Database queries (not fetch) — use unstable_cache:
import { unstable_cache } from 'next/cache';

const getCachedProducts = unstable_cache(
  async () => db.query.products.findMany({ where: eq(products.isActive, true) }),
  ['products-list'],
  { tags: ['products'], revalidate: 3600 },
);
```

## ISR — Incremental Static Regeneration

For pages where data changes infrequently, ISR generates static HTML and revalidates in the background:

```ts
// app/products/[id]/page.tsx
export const revalidate = 3600;  // Regenerate at most every hour

export async function generateStaticParams() {
  // Pre-render the top 100 products at build time
  const products = await db.query.products.findMany({ limit: 100 });
  return products.map((p) => ({ id: p.id }));
}

export default async function ProductPage({ params }: { params: { id: string } }) {
  const product = await db.query.products.findFirst({
    where: (p, { eq }) => eq(p.id, params.id),
  });

  // Remaining product pages: generated on first request, cached for 1 hour
  return <ProductDetail product={product} />;
}
```

The first visit to an uncached product generates and caches the page. Subsequent visits within the revalidation window get the static HTML. After the window expires, the next visit triggers a background regeneration — the current visitor still gets the stale page, the next visitor gets the fresh one.

## Dynamic vs static route detection

Next.js decides statically vs dynamically rendered at build time based on what you use in the route:

| Usage | Effect |
|---|---|
| `cookies()`, `headers()` | Forces dynamic rendering |
| `searchParams` | Forces dynamic rendering |
| `fetch({ cache: 'no-store' })` | Forces dynamic rendering |
| `export const dynamic = 'force-dynamic'` | Forces dynamic rendering |
| None of the above | Static: HTML generated at build |

## Router Cache expiry

The client-side Router Cache holds RSC payloads for navigation. Static routes are cached for 5 minutes; dynamic routes for 30 seconds. You can't clear it programmatically, but `router.refresh()` refetches the current page's data without a full navigation:

```tsx
'use client';

import { useRouter } from 'next/navigation';

function RefreshButton() {
  const router = useRouter();
  return (
    <button onClick={() => router.refresh()}>
      Refresh data
    </button>
  );
}
```

`router.refresh()` re-renders the current Server Components with fresh data while preserving client state (scroll position, focus, local `useState`). It's the right tool for "pull to refresh" patterns in dynamic dashboards.

## The practical heuristic

- **Marketing pages**: static, ISR with a long revalidation window
- **Dashboard pages with user-specific data**: `force-dynamic` or short revalidation
- **Shared data that changes on explicit actions**: cache with tags, revalidate on mutation
- **Real-time data**: skip caching entirely, consider WebSockets or SSE

Getting caching wrong in production means serving stale data silently. Getting it right means the database takes a fraction of the load. The cost of understanding the four cache layers pays back on the first high-traffic day.
