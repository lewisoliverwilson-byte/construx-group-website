title: "Bazel: reproducible, incremental builds for monorepos at scale"
date: "2033-06-24"
excerpt: "Bazel is a build system from Google designed for monorepos with many languages and many teams. The core property is reproducibility: every build target is defined by its inputs (source files, dependencies, toolchains), and the output is a deterministic function of those inputs — the same inputs always produce the same output. This enables correct incremental builds: Bazel tracks which targets are affected by a change and only rebuilds those targets, not the whole codebase. For a monorepo with 500 packages, changing one file rebuilds one package instead of everything. Bazel also supports remote caching and remote execution: build outputs are stored in a content-addressed cache, and builds are distributed across many machines in a remote execution cluster (RBE). Teams working on the same monorepo share cached build results — if a colleague already built the artifact with the same inputs, you get their cached output instantly."

## BUILD files and targets

```python
# BUILD file: defines targets and their dependencies
# Bazel uses Starlark (Python-like) for BUILD files

# WORKSPACE (root): declares external dependencies
# (or MODULE.bazel for Bzlmod)

# //backend/api/BUILD

load("@io_bazel_rules_go//go:def.bzl", "go_binary", "go_library", "go_test")
load("@rules_docker//go:image.bzl", "go_image")
load("@io_bazel_rules_docker//container:container.bzl", "container_push")

# Go library: the business logic
go_library(
    name = "api_lib",
    srcs = glob(["*.go"], exclude = ["*_test.go"]),
    importpath = "github.com/construx/construx/backend/api",
    deps = [
        "//backend/db:db_lib",
        "//backend/auth:auth_lib",
        "@com_github_go_chi_chi_v5//:chi",
        "@com_github_jackc_pgx_v5//:pgx",
    ],
    visibility = ["//visibility:public"],
)

# Go binary: the API server
go_binary(
    name = "api_server",
    embed = [":api_lib"],
    visibility = ["//visibility:public"],
)

# Go tests
go_test(
    name = "api_test",
    srcs = glob(["*_test.go"]),
    embed = [":api_lib"],
    deps = [
        "//backend/testutil:testutil_lib",
        "@com_github_stretchr_testify//assert",
    ],
)

# Docker image: built from the binary
go_image(
    name = "api_image",
    binary = ":api_server",
    base = "@distroless_base//image",
)

# Container push: push to registry
container_push(
    name = "push_api_image",
    image = ":api_image",
    format = "Docker",
    registry = "registry.construx.internal",
    repository = "construx/api",
    tag = "{BUILD_TIMESTAMP}",
)
```

## Remote caching and remote execution

```bash
# Build a specific target
bazel build //backend/api:api_server

# Run tests
bazel test //backend/api:api_test

# Build everything in the monorepo
bazel build //...

# Test everything
bazel test //...

# Build and push the Docker image
bazel run //backend/api:push_api_image

# Remote cache: share build outputs across the team
# .bazelrc:
# build --remote_cache=grpcs://cache.construx.internal:443
# build --remote_cache_header=x-build-team=construx

bazel build //backend/api:api_server
# INFO: Analyzed target //backend/api:api_server (0 packages loaded, 0 targets configured).
# INFO: Found 1 target...
# INFO: Elapsed time: 0.312s, Critical Path: 0.01s
# INFO: 12 processes: 12 remote cache hit.   ← colleague already built this exact output

# Remote execution: distribute build tasks across many machines
# .bazelrc:
# build --remote_executor=grpcs://rbe.construx.internal:443
# build --jobs=200   # 200 concurrent remote actions

bazel build //... --remote_executor=grpcs://rbe.construx.internal:443
# INFO: 1847 actions, 1831 cache hits, 16 remote executions, 0 local.
# INFO: Elapsed time: 34.2s, Critical Path: 8.1s

# Query: which targets are affected by a change?
git diff --name-only HEAD~1 HEAD | xargs bazel query 'rdeps(//..., set(...))'
# Shows exactly which targets need to be rebuilt — use in CI to only test affected targets
```

## Incremental builds in CI

```bash
# CI: affected-target test strategy
# Only build and test targets affected by this PR

# 1. Get changed files
CHANGED_FILES=$(git diff --name-only origin/main...HEAD | tr '\n' ' ')

# 2. Find all Bazel targets that depend on the changed files
CHANGED_TARGETS=$(bazel query "rdeps(//..., set($CHANGED_FILES))")

# 3. Build only affected targets
bazel build $CHANGED_TARGETS

# 4. Test only affected targets
bazel test $CHANGED_TARGETS

# Typical CI speedup on a 500-package monorepo:
# Full build: 45 minutes
# Affected-target build: 2-8 minutes (depending on what changed)
# With remote cache hits: often <60 seconds

# Bazel output base: where build outputs are stored
# By default: ~/.cache/bazel/
# For CI: use a shared remote cache instead

# Build event stream: structured log of all build events (for CI dashboards)
bazel test //... \
  --build_event_json_file=build_events.json \
  --bes_backend=grpcs://bes.construx.internal:443
```

Bazel vs Gradle vs Turborepo vs Nx vs Make: Make is simple but doesn't track dependencies correctly — incremental builds require manual dependency declaration and can silently give wrong results when deps change. Gradle (Java/Kotlin) and sbt (Scala) are build systems for JVM-centric monorepos — correct incremental builds but JVM-specific. Turborepo and Nx are JavaScript monorepo tools — faster than npm workspaces but limited to the JavaScript/TypeScript ecosystem. Bazel is language-agnostic (Go, Java, Python, TypeScript, Rust, C++, Docker) and has the strongest correctness guarantees of any build system — the sandboxed execution model catches undeclared dependencies that make builds non-reproducible. The cost: the learning curve for BUILD files and the initial investment in setting up rules for each language. For JavaScript-only repos, Turborepo or Nx are simpler. For large multi-language monorepos, Bazel's correctness and remote caching are worth it.
