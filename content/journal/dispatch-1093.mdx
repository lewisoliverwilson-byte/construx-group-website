title: "Grafana Mimir: horizontally scalable Prometheus-compatible TSDB — ingest, compaction, long-term storage"
date: "2033-12-06"
excerpt: "Grafana Mimir is a horizontally scalable, multi-tenant, long-term storage backend for Prometheus metrics. Where Thanos (dispatch-1064) adds long-term storage and global query to an existing Prometheus deployment via sidecars, Mimir is a full replacement for the Prometheus TSDB — it receives OTLP or Prometheus remote_write from agents, writes to object storage (S3/GCS) directly, and handles query fanout, compaction, and retention internally. Mimir's architecture decomposes Prometheus into independent, horizontally scalable microservices: the Distributor (receives ingest, hashes series to Ingestors), Ingester (in-memory write buffer, flushes to object storage as blocks), Querier (fetches blocks from object storage for range queries), Ruler (evaluates recording rules and alert rules), Compactor (merges and downsamples blocks for long-term retention), and Store-Gateway (caches block index data for fast query). Each component scales independently. A single Mimir cluster can ingest millions of active series from hundreds of Prometheus agents across all Kubernetes clusters and services. For multi-tenant SaaS, Mimir's tenant isolation means each customer's metrics are stored and queried independently — Grafana passes the tenant ID header to query a specific tenant's metrics without any cross-tenant data leakage."

## Mimir architecture and deployment

```yaml
# Mimir deployed in monolithic mode (small cluster) vs microservices mode (production)
# Helm chart: grafana/mimir-distributed

# values.yaml — microservices mode for production scale

mimir:
  structuredConfig:
    common:
      storage:
        backend: s3
        s3:
          bucket_name: construx-mimir-blocks
          endpoint: s3.eu-west-2.amazonaws.com
          region: eu-west-2

    limits:
      # Per-tenant ingestion limits
      ingestion_rate:                    150000   # series/s per tenant
      ingestion_burst_size:              250000
      max_global_series_per_user:        10000000  # 10M active series per tenant
      max_query_lookback:                "365d"
      compactor_blocks_retention_period: "365d"

    ingester:
      ring:
        replication_factor: 3   # write to 3 ingesters for durability

    store_gateway:
      sharding_ring:
        replication_factor: 3

distributor:
  replicas: 3
  resources:
    requests: { cpu: "1", memory: "2Gi" }

ingester:
  replicas: 6
  persistentVolume:
    enabled: true
    size: 50Gi           # WAL: write-ahead log for in-flight data

querier:
  replicas: 4
  resources:
    requests: { cpu: "2", memory: "4Gi" }

compactor:
  replicas: 1            # single compactor is sufficient; can scale to 2 with sharding
  persistentVolume:
    enabled: true
    size: 100Gi          # scratch space for compaction

store_gateway:
  replicas: 3            # index cache for fast block queries

ruler:
  enabled: true          # evaluates recording rules + alert rules
  replicas: 2
```

```yaml
# Grafana Agent (or Alloy) remote_write to Mimir
# Send metrics from all Kubernetes clusters to centralised Mimir

# Alloy config: scrape Prometheus targets and remote_write to Mimir
prometheus.scrape "construx_prod" {
  targets    = discovery.kubernetes.pods.targets
  job_name   = "construx-prod"
  forward_to = [prometheus.remote_write.mimir.receiver]
}

prometheus.remote_write "mimir" {
  endpoint {
    url = "https://mimir.construx.internal/api/v1/push"

    headers = {
      "X-Scope-OrgID" = "construx-prod",   # tenant ID
    }

    tls_config {
      ca_file   = "/etc/ssl/certs/ca.crt"
      cert_file = "/etc/ssl/certs/client.crt"
      key_file  = "/etc/ssl/certs/client.key"
    }

    queue_config {
      max_samples_per_send = 5000
      max_shards           = 30
      capacity             = 10000
    }
  }
}
```

# Query Mimir via Grafana (add Mimir as a Prometheus datasource in Grafana)

Grafana Mimir vs Thanos vs VictoriaMetrics vs Cortex: Cortex is Mimir's predecessor — Mimir is a fork by Grafana Labs that significantly simplifies Cortex's architecture and improves performance. They share the same storage format. Thanos (dispatch-1064) takes a different architectural approach: it keeps Prometheus instances intact and adds a sidecar that uploads blocks to object storage; Thanos Query fans out queries across multiple Prometheus instances. Mimir replaces Prometheus's TSDB entirely — agents remote_write directly to Mimir's Distributor. Thanos is easier to retrofit onto an existing Prometheus deployment; Mimir is easier to operate at large scale (no Prometheus instances to manage, no sidecar coordination). VictoriaMetrics is an independent high-performance TSDB with an extremely efficient compression algorithm — it often achieves 3-5x better storage efficiency than Prometheus or Mimir for the same dataset, and its single-binary mode is operationally very simple. The trade-off: VictoriaMetrics has less ecosystem integration than the Grafana stack (Mimir + Alloy + Grafana are deeply integrated). For multi-cluster, multi-tenant, global-query requirements with the Grafana observability stack, Mimir is the production choice.
