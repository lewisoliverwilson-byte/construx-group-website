Three live software products. Two founders. No full-time engineers beyond us. Here's what running this actually looks like.

## What "live" means for monitoring

Each venture runs on AWS Amplify. Amplify handles deployment, CDN, and basic uptime monitoring automatically. Beyond that, we've added:

**Uptime monitoring** via a third-party ping service. If a site returns a non-200 or doesn't respond within 30 seconds, we get a notification. This catches the obvious things — deployment failures, environment variable misconfigurations, regional AWS outages.

**Error alerting** is handled at the Next.js level. Unhandled errors get logged; the logging integration sends us a notification for novel errors (same error multiple times doesn't re-alert). Novel means something is wrong that we've not seen before.

**Cost alerting** on AWS. If the monthly bill starts trending significantly above forecast, we get an alert. AI inference costs are the variable we monitor most closely — a prompt loop or a high-traffic day can spike costs in a way that's worth knowing about immediately rather than at month end.

We don't have dashboards. No Grafana, no custom metrics infrastructure. The monitoring is deliberately minimal — the notifications we do have generate signal we actually act on, without noise that trains us to ignore it.

## Triaging issues

When something goes wrong, the triage process is:

1. Is it a deployment issue? Check Amplify's deployment log. Deployment failures are the most common source of brief outages and the easiest to diagnose.

2. Is it an environment variable issue? Missing or misconfigured env vars are the second most common source. Check the Amplify console.

3. Is it a runtime error? Check the error log for the first novel exception. Usually points directly to the failing code.

4. Is it an external dependency? The AI APIs (Anthropic's Claude API) have their own status. Before investigating our code, check if there's a platform outage upstream.

Most issues resolve within 15 minutes of identification. The rare ones that don't get triaged into one of two buckets: "fix now" (breaking the product for all users) or "fix next sprint" (degraded experience for a subset of users).

"Fix now" interrupts whatever we're working on. "Fix next sprint" gets a note and a slot in the next working session. We don't have a formal bug tracker — a simple running list in our project space is sufficient at current scale.

## Maintenance schedule

Across three ventures, maintenance falls into two categories:

**Reactive maintenance** is unscheduled — responding to issues, user feedback that reveals a bug, dependency updates with security implications. This happens when it happens.

**Proactive maintenance** happens on a loose weekly schedule. Once a week, we check:
- Dependency versions — are there any significant updates (major version bumps, security advisories)?
- Content freshness — The Marqet's listings need periodic review; AI content generation can drift in quality
- Fee data — Scoutr's Amazon and eBay fee tables need updating when platforms announce changes
- System prompt performance — do any products show signs of prompt drift based on recent outputs?

The proactive check takes about two hours across all three ventures. Most weeks, nothing needs action. Occasionally one thing needs attention. Rarely, multiple things need attention simultaneously.

## Deployments and rollbacks

All three ventures deploy via GitHub → Amplify. Push to the main branch, Amplify builds and deploys automatically.

We don't maintain staging environments. For significant changes, we use Amplify's branch preview feature — push to a branch, review the preview URL, merge to main when satisfied. For small changes, we ship directly to production. The risk tolerance is higher than a team of twenty would accept, and it's appropriate for our scale.

Rollbacks are handled by reverting the relevant commit and pushing. Amplify redeploys to the previous version. This works for code changes. For data changes (database migrations, content updates), we're more careful — we design for forward compatibility so rollbacks don't require data migrations in reverse.

The actual rollback rate is very low. Most deployments are straightforward because the changes are focused and we've tested them before shipping. The pre-ship checklist helps — a failure caught before deployment doesn't need a rollback.

## What a bad day looks like

A bad day is two things going wrong simultaneously in different ventures. One morning, Scoutr had a prompt returning malformed JSON on a specific category of product URLs (a corner case in the fee classification that we hadn't hit before), and The Marqet had a listing display issue caused by a dependency update that changed a date formatting function's output.

Both were diagnosed and fixed within a few hours. The first required a prompt adjustment and output validation update. The second required pinning the dependency version until we could properly update our date handling.

Nothing was down for more than a few minutes. Users who hit the issues during the window encountered error messages rather than incorrect data. Both were less bad than they could have been because we had explicit error handling and clear error messages.

This is the kind of operational problem you plan for without being able to predict the specifics. The plan is: triage fast, fix the immediate issue, log the root cause, prevent the category of problem recurring. Not: maintain a perfect operational record by never shipping quickly.

## The things we deliberately don't do

**We don't have on-call rotations.** We're two people. If something critical happens at 3am, it either waits until the morning or one of us handles it. So far, nothing has been critical enough to warrant a 3am response. Most incidents resolve within a business day without user-facing consequences.

**We don't maintain separate staging environments.** The overhead of keeping staging in sync with production, multiplied across three ventures, is not worth the benefit at our current scale.

**We don't do incident post-mortems with blameless retrospectives and five whys.** We fix the problem, note what caused it, adjust the process if needed, and move on. Formal post-mortem processes are valuable when you need institutional learning at scale. At two people, a five-minute conversation achieves the same thing.

**We don't monitor every metric.** Response time per route, error rate by endpoint, P99 latency — useful at scale, noise at ours. We monitor what tells us when something is broken, not what tells us how broken it is if it were broken.

## The honest answer to "how do you manage it?"

You manage it by building things that are simple to operate. Every complexity you add to a product is a complexity you have to maintain. Simpler architectures are easier to debug. Fewer dependencies are fewer things to update. Smaller codebases are faster to navigate when something breaks at an inconvenient time.

The operational load of three ventures is manageable not because we've built great operations infrastructure, but because we've built products that are straightforward to run. The infrastructure complexity is low. The failure modes are well-understood. The dependency surface is small.

This is a design constraint that applies from day one: will two people be able to operate this in six months? If the architecture can't answer yes, it's the wrong architecture.
