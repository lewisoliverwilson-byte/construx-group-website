Internationalisation (i18n) is one of those requirements that's worth doing well, worth doing at the right time, and very easy to over-engineer before you need it.

The Marqet launched UK-only: pricing in GBP, listings in English, sellers based in the UK. We've received enquiries from professional service buyers in Germany, France, and the Netherlands. The signal to consider expanding is there.

Here's how we've structured the codebase to make i18n possible without building it now.

## The current state

The Marqet has no i18n infrastructure. All text is English. All prices are GBP. The currency symbol is hardcoded. Date formats are UK-format.

This is intentional. Building i18n before you have non-English users is optimising for a problem you don't have. The classic premature abstraction.

## The preparation layer

What we have done is structure the code to make i18n straightforward to add when we need it. Specifically:

**Currency is always stored as a value + currency code pair, never as a formatted string.**

```ts
interface Price {
  amount: number;  // in minor units (pence for GBP, cents for EUR/USD)
  currency: string; // ISO 4217 currency code: 'GBP', 'EUR', 'USD'
}
```

We never store "£340". We store `{ amount: 34000, currency: 'GBP' }`. Formatting to a currency string happens at display time:

```ts
function formatCurrency(price: Price, locale = 'en-GB'): string {
  return new Intl.NumberFormat(locale, {
    style: 'currency',
    currency: price.currency,
  }).format(price.amount / 100);
}
```

The `Intl.NumberFormat` API handles the locale-specific formatting (symbol position, decimal separator, grouping separator) correctly for any currency/locale combination. When we add EUR support, `formatCurrency({ amount: 34000, currency: 'EUR' }, 'de-DE')` will produce "340,00 €" correctly.

**Dates are stored as UTC timestamps, displayed in user locale.**

All timestamps in the database are `timestamptz` (timestamp with time zone), stored as UTC. Display formatting uses `Intl.DateTimeFormat`:

```ts
function formatDate(date: Date | string, locale = 'en-GB'): string {
  return new Intl.DateTimeFormat(locale, {
    year: 'numeric',
    month: 'long',
    day: 'numeric',
  }).format(typeof date === 'string' ? new Date(date) : date);
}
```

**User-facing strings are not hardcoded inline.**

We don't have a full i18n string catalog. What we do have: UI text is in a single `translations/en.ts` file rather than scattered across components. If we add another language, we add another file.

```ts
// translations/en.ts
export const t = {
  'listing.enquiry.placeholder': 'Describe your project and requirements...',
  'listing.enquiry.cta': 'Send enquiry',
  'payment.escrow.notice': 'Payment is held securely until you confirm the work is complete.',
  // ...
};
```

This isn't a full i18n solution — it's not context-aware, doesn't handle plurals, and has no locale switching. But it means strings are in one place rather than 40 components, which makes a future migration substantially easier.

## What we'd build for real i18n

When we add a second market, the work is:

**1. Route-based locale prefix.** Next.js App Router has native support for i18n routing:

```ts
// next.config.ts
const nextConfig: NextConfig = {
  i18n: {
    locales: ['en-GB', 'de', 'fr', 'nl'],
    defaultLocale: 'en-GB',
  },
};
```

This adds `/de/`, `/fr/` prefixes to routes and makes the locale available in route handlers.

**2. Full string catalog per locale.** Extend the `translations/` folder with `de.ts`, `fr.ts`, etc. The catalog structure is already established.

**3. Locale detection and switching.** Accept-Language header → preferred locale → redirect to localised route.

**4. Legal compliance per region.** Terms of service, VAT handling, dispute resolution — these differ by region and are the hardest part of internationalisation. GDPR compliance is already in place (required for our UK users); local consumer protection laws require per-region legal review.

**5. Payment method localisation.** SEPA for European bank transfers, different card networks. This is a Stripe configuration change, largely handled by Stripe's payment element.

## The over-engineering risk

The temptation when anticipating i18n is to build the full system now: a robust message catalog, locale-aware routing, currency switching, regional pricing. This takes weeks and provides no value until you have non-English users.

Our principle: build for the current requirement with the future requirement in mind. The current requirement is a UK marketplace with GBP prices. The future requirement is European expansion. Building with this in mind means: don't hardcode currency symbols, don't hardcode locale assumptions, centralise strings — but don't build the full i18n infrastructure until there's a user segment that needs it.

The boundary is: doing the easy things now (data structure, string centralisation) while deferring the expensive things (full routing, legal review, payment localisation) until there's a clear business reason to do them.

The enquiries from European users are a signal. When we decide to expand, the codebase is ready. Until then, we have more impactful work to do.
