title: "Kata Containers: VM-isolated containers — hardware security boundaries with container ergonomics"
date: "2033-09-01"
excerpt: "Kata Containers runs each container (or pod) inside a lightweight virtual machine instead of using the host kernel's namespace and cgroup isolation. From the Kubernetes perspective, Kata pods look identical to regular pods — you schedule them with kubectl, they appear in kubectl get pods, they mount volumes, and they expose services. But underneath, each pod has its own VM kernel (a stripped-down KVM guest using QEMU or Cloud Hypervisor), its own virtual network interface, and its own memory space. This means a container escape — a kernel vulnerability that lets a process break out of namespace isolation — cannot reach the host kernel, because the container's kernel is a separate VM guest. The OCI runtime (kata-runtime) is registered with containerd alongside runc; Kata pods are selected via a RuntimeClass. Kata is used for multi-tenant container platforms (hosting untrusted code, SaaS sandboxing), CI workloads running arbitrary code (GitHub Actions runners), and compliance environments where hardware isolation is mandated."

VM-isolated containers. KVM guest kernel. RuntimeClass. OCI runtime. Hardware security boundary.

## Kata Containers setup on Kubernetes

```bash
# Install Kata Containers on a Kubernetes node
# Requires: hardware virtualisation support (Intel VT-x or AMD-V)

# Check virtualisation support
grep -E 'vmx|svm' /proc/cpuinfo | head -1
# flags: ... vmx ...   ← Intel VT-x present

# Install Kata runtime via binary tarball or package manager
# (Ubuntu example)
sudo apt-get install kata-containers

# Configure containerd to register kata-runtime alongside runc
# /etc/containerd/config.toml (add under plugins.cri.containerd.runtimes)
[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.kata]
  runtime_type = "io.containerd.kata.v2"
  privileged_without_host_devices = true
  [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.kata.options]
    ConfigPath = "/opt/kata/share/defaults/kata-containers/configuration.toml"

# Restart containerd
sudo systemctl restart containerd

# Verify Kata runtime is registered
ctr run --runtime io.containerd.kata.v2 --rm \
  docker.io/library/ubuntu:24.04 kata-test uname -r
# 6.1.38-kata   ← separate VM kernel, not the host kernel
```

## RuntimeClass and pod configuration

```yaml
# RuntimeClass: register Kata as an available runtime in Kubernetes
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: kata
handler: kata   # matches the runtimes key in containerd config
overhead:
  podFixed:
    cpu:    250m   # VM startup overhead per pod
    memory: 160Mi  # VM kernel + VMM overhead
scheduling:
  nodeSelector:
    kata.io/capable: "true"   # only schedule on nodes with Kata installed
---
# Pod using Kata isolation: identical to a regular pod except runtimeClassName
apiVersion: v1
kind: Pod
metadata:
  name: untrusted-workload
  namespace: sandboxed
spec:
  runtimeClassName: kata   # select Kata runtime
  containers:
    - name: workload
      image: registry.construx.internal/user-workload:latest
      resources:
        requests:
          cpu:    500m
          memory: 512Mi
        limits:
          cpu:    2
          memory: 1Gi
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem:   true
        runAsNonRoot:             true
        runAsUser:                1000
---
# Kata-specific configuration: /opt/kata/share/defaults/kata-containers/configuration.toml
[hypervisor.qemu]
path        = "/opt/kata/bin/qemu-system-x86_64"
kernel      = "/opt/kata/share/kata-containers/vmlinux.container"
image       = "/opt/kata/share/kata-containers/kata-containers.img"
machine_type = "q35"
enable_iommu = false

[runtime]
# Sandbox cgroup model: "sandbox" = shared cgroup for all containers in a pod
# matches Kubernetes pod-level resource limits
sandbox_cgroup_only = true
enable_cpu_memory_hotplug = true   # dynamically add vCPUs/RAM as container load grows
```

## Performance and tradeoffs

```bash
# Benchmark: pod startup time comparison
# runc (regular containers)
time kubectl run test-runc --image=ubuntu:24.04 --rm -it -- echo hello
# real 0m2.1s   ← fast: kernel namespaces, no VM boot

# kata-qemu (Kata with QEMU)
time kubectl run test-kata --image=ubuntu:24.04 \
  --overrides='{"spec":{"runtimeClassName":"kata"}}' --rm -it -- echo hello
# real 0m4.8s   ← slower: VM boot + kernel load

# kata-cloud-hypervisor (Kata with Cloud Hypervisor — faster VMM)
# real 0m2.9s   ← closer to runc startup

# Memory overhead per pod
kubectl top pod -n sandboxed
# NAME             CPU(cores)   MEMORY(bytes)
# untrusted-pod    48m          498Mi           ← 160Mi overhead + 338Mi app

# Verify isolation: container's kernel is not the host kernel
kubectl exec -n sandboxed untrusted-workload -- uname -r
# 6.1.38-kata   ← VM guest kernel

ssh node-01
uname -r
# 6.6.45-aws   ← host kernel — completely separate

# Kata metrics via Prometheus
# kata_agent_io_write_bytes_total    4821039
# kata_hypervisor_vcpu_time_seconds  12.34
# kata_startup_time_seconds{runtime="kata-qemu"} 4.82
```

Kata Containers vs gVisor vs Firecracker vs regular containers: Regular containers (runc) share the host kernel — a container escape reaches the host. gVisor (Google) runs a userspace kernel (Sentry) written in Go that intercepts syscalls — faster startup than Kata (no VM boot) but incomplete syscall coverage (some applications that use unusual kernel features don't work in gVisor). Firecracker (AWS Lambda/Fargate) is a minimal VMM purpose-built for serverless — 5ms VM boot, 128KB memory overhead, but requires Firecracker-specific tooling and is optimised for Lambda-style single-function workloads. Kata runs a full Linux kernel in the VM, so application compatibility is near-identical to regular containers — almost nothing breaks. The startup time (2.9-4.8s depending on VMM) is higher than runc (0.1-0.5s) but acceptable for long-running workloads. For platforms running untrusted multi-tenant code (SaaS where users upload and run arbitrary containers, CI/CD for public repositories), Kata's hardware isolation boundary is the appropriate security model.
