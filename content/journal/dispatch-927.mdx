date: "2032-07-26"
excerpt: "Debezium is a distributed platform for change data capture (CDC) — it reads the database write-ahead log (WAL) and emits every INSERT, UPDATE, and DELETE as an event stream to Kafka. This enables real-time replication, event sourcing from existing databases, cache invalidation, search index updates, and audit logging without polling. Debezium runs as a Kafka Connect connector: configure it with a JDBC connection and a list of tables, and it begins streaming the full table history followed by live changes. The event format includes before/after state for updates, table name, operation type, LSN position, and a full schema registry-compatible schema."

The WAL is a change log. Debezium reads it. Kafka stores it. Consumers react to it.

## PostgreSQL CDC setup

```bash
# Step 1: Enable logical replication in PostgreSQL
# postgresql.conf:
# wal_level = logical             (required for CDC)
# max_replication_slots = 10      (one slot per Debezium connector)
# max_wal_senders = 10

# Restart postgres to apply:
systemctl restart postgresql

# Step 2: Create a replication user
psql -U postgres << 'EOF'
CREATE USER debezium WITH REPLICATION LOGIN PASSWORD 'dz-secret';
GRANT SELECT ON ALL TABLES IN SCHEMA public TO debezium;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO debezium;
EOF

# Step 3: Create a replication slot (Debezium does this automatically, but you can verify)
SELECT * FROM pg_replication_slots;
# slot_name               | plugin   | slot_type | active
# construx_debezium_slot  | pgoutput | logical   | t
```

## Consumer patterns — cache invalidation, search sync

```python
# Python consumer: invalidate Redis cache on order updates
from confluent_kafka import Consumer
import json, redis

consumer = Consumer({
    'bootstrap.servers': 'kafka-bootstrap.construx.svc.cluster.local:9092',
    'group.id': 'cache-invalidator',
    'auto.offset.reset': 'earliest',
})
consumer.subscribe(['construx-db.public.orders'])

cache = redis.Redis(host='redis.construx.svc.cluster.local')

while True:
    msg = consumer.poll(timeout=1.0)
    if msg is None or msg.error():
        continue

    event = json.loads(msg.value())
    op = event.get('__op')
    order_id = event.get('order_id')

    if op in ('u', 'd'):   # Update or delete
        # Invalidate the cache entry
        cache.delete(f'order:{order_id}')
        cache.delete(f'customer-orders:{event.get("customer_id")}')
        print(f"Invalidated cache for order {order_id} (op={op})")

    elif op == 'c':
        # Pre-warm cache for new orders (optional)
        cache.setex(f'order:{order_id}', 3600, json.dumps(event))
```

```python
# Sync Meilisearch index from orders CDC stream
from meilisearch import Client

meili = Client('http://meilisearch.construx.svc.cluster.local:7700', 'MASTER_KEY')
index = meili.index('orders')

consumer.subscribe(['construx-db.public.orders'])

batch = []
BATCH_SIZE = 500

while True:
    msg = consumer.poll(timeout=0.1)
    if msg and not msg.error():
        event = json.loads(msg.value())
        op = event['__op']

        if op in ('c', 'u'):
            batch.append(event)
            if len(batch) >= BATCH_SIZE:
                index.add_documents(batch)
                batch.clear()

        elif op == 'd':
            index.delete_document(event['order_id'])

# Flush remaining
if batch:
    index.add_documents(batch)
```

## Monitoring and lag

```bash
# Kafka Connect REST API: connector status
curl http://kafka-connect.construx.svc.cluster.local:8083/connectors/construx-postgres-connector/status
# {
#   "name": "construx-postgres-connector",
#   "connector": {"state": "RUNNING", "worker_id": "connect-0:8083"},
#   "tasks": [{"id": 0, "state": "RUNNING", "worker_id": "connect-0:8083"}]
# }

# Check replication slot lag (WAL bytes not yet consumed by Debezium)
psql -U postgres -c "
  SELECT slot_name, active, pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn) AS lag_bytes
  FROM pg_replication_slots
  WHERE slot_name = 'construx_debezium_slot';
"
# construx_debezium_slot | t | 0      ← 0 bytes = fully caught up

# Kafka consumer group lag
kafka-consumer-groups.sh --bootstrap-server $BROKER \
  --describe --group cache-invalidator | grep "orders"
# cache-invalidator  construx-db.public.orders  0  38241  38241  0

# Alert: replication slot growing (Debezium stopped, WAL accumulating)
# This will eventually cause disk exhaustion — always monitor pg_replication_slots
```

Debezium vs polling vs application-level events: polling is the naive approach — query `WHERE updated_at > last_poll_time` every N seconds. It misses deletes, requires an `updated_at` column on every table, and creates load spikes. Application-level events (publishing to Kafka from your app code) are reliable but require every write path to produce events — easy to miss in edge cases (DB migrations, scripts, third-party tools). Debezium reads the WAL — the database's own change log — so it captures every change regardless of how it was made, including migrations, triggers, and direct SQL. The trade-off: Debezium requires `wal_level=logical`, uses a replication slot (which accumulates WAL if the consumer falls behind), and adds operational complexity. For greenfield systems, application-level events are simpler. For existing databases or systems where you can't control all write paths, CDC via Debezium is the correct foundation.
