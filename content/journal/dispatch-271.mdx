Early in building Scoutr, we logged everything. Every API call, every function entry, every state change. The result was a log stream so dense that finding the one line that mattered when something went wrong required filtering through hundreds of irrelevant entries.

The fix wasn't better tooling — it was being deliberate about what to log.

## The taxonomy

We categorise every log entry into one of four types:

**Operational events:** things that happened. A user signed up. A payment succeeded. A scan completed. These are facts about what the system did.

**Performance metrics:** how long things took. Scan duration. Database query time. AI API latency. These help you spot regressions and set performance budgets.

**Errors:** things that went wrong. Caught exceptions, failed external calls, validation failures. These should always be logged with full context.

**Debug traces:** temporary detailed logs added during development or incident investigation. These have a short lifespan and should be removed before shipping.

Production only contains the first three types. Debug traces are added locally or in staging, never committed.

## The format: structured JSON

Every log line is structured JSON, not a human-readable string.

```ts
// ✗ String log — impossible to query reliably
console.log(`Scan completed for ${asin} in ${duration}ms`);

// ✓ Structured log — queryable by any field
console.log(JSON.stringify({
  event: 'scan.completed',
  asin,
  duration_ms: duration,
  userId,
  workspaceId,
  confidence: result.confidence,
  margin: result.margin,
  ts: new Date().toISOString(),
}));
```

The string version is readable. The JSON version is filterable. When you need to answer "how many scans returned LOW confidence in the last 24 hours?", the JSON version makes this a query. The string version makes it a regex nightmare.

## The logger wrapper

We use a thin wrapper around `console.log` that adds consistent fields and redacts sensitive data:

```ts
// lib/logger.ts
const REDACT_KEYS = new Set(['password', 'token', 'secret', 'apiKey', 'authorization']);

function redact(obj: Record<string, unknown>): Record<string, unknown> {
  return Object.fromEntries(
    Object.entries(obj).map(([k, v]) => [
      k,
      REDACT_KEYS.has(k.toLowerCase()) ? '[REDACTED]' : v,
    ])
  );
}

interface LogPayload {
  event: string;
  [key: string]: unknown;
}

export const logger = {
  info: (payload: LogPayload) => {
    console.log(JSON.stringify({
      level: 'info',
      ts: new Date().toISOString(),
      env: process.env.NODE_ENV,
      ...redact(payload),
    }));
  },

  error: (payload: LogPayload & { error: unknown }) => {
    const err = payload.error;
    console.error(JSON.stringify({
      level: 'error',
      ts: new Date().toISOString(),
      env: process.env.NODE_ENV,
      ...redact(payload),
      error: {
        message: err instanceof Error ? err.message : String(err),
        stack: err instanceof Error ? err.stack : undefined,
      },
    }));
  },

  perf: (event: string, duration_ms: number, meta?: Record<string, unknown>) => {
    console.log(JSON.stringify({
      level: 'perf',
      event,
      duration_ms,
      ts: new Date().toISOString(),
      ...meta,
    }));
  },
};
```

The redaction is imperfect — it's key-name based, not content-aware — but it prevents the most common accidental secret exposures.

## Performance timing with wrapping

Rather than manually recording timestamps, we wrap async functions:

```ts
async function withTiming<T>(
  label: string,
  fn: () => Promise<T>,
  meta?: Record<string, unknown>,
): Promise<T> {
  const start = performance.now();
  try {
    const result = await fn();
    logger.perf(label, Math.round(performance.now() - start), meta);
    return result;
  } catch (err) {
    logger.error({ event: `${label}.error`, error: err, ...meta });
    throw err;
  }
}

// Usage
const result = await withTiming(
  'scan.execute',
  () => runScan(asin),
  { asin, userId },
);
```

Every call to `runScan` now records its duration in a structured log entry. Querying for p95 latency across all scans in a day is a log query, not an instrumentation change.

## Where logs go

AWS Amplify routes console output to CloudWatch Logs. We query CloudWatch Insights for structured JSON:

```
fields @timestamp, event, duration_ms, userId, asin
| filter event = 'scan.execute'
| stats avg(duration_ms), p95(duration_ms), count() by bin(1h)
| sort @timestamp desc
| limit 24
```

This gives a 24-hour view of scan latency by hour. An anomaly (p95 suddenly doubles) shows up immediately.

For errors, we use a CloudWatch Alarm that triggers when the error rate exceeds a threshold — it's just a metric filter on `level = 'error'` with a count threshold.

## The rule on what to log

Log at the boundary of your system: when something enters, when something exits, when something external is called, when something fails.

Don't log internal state changes, intermediate computations, or values that are derivable from other logs. Log the event, the context, the duration, and the outcome. Everything else is noise.

Noise doesn't just make logs less useful — it makes them actively misleading. When every log entry looks the same, the signal entries don't stand out.
