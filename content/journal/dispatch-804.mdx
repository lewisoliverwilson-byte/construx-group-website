Five fields. Six with seconds. The edge cases that bite.

## Field structure

```
# ┌──────────── minute        (0–59)
# │ ┌────────── hour          (0–23)
# │ │ ┌──────── day of month  (1–31)
# │ │ │ ┌────── month         (1–12 or JAN–DEC)
# │ │ │ │ ┌──── day of week   (0–7 or SUN–SAT, 0 and 7 are both Sunday)
# │ │ │ │ │
# * * * * *
```

## Common patterns

```bash
# Every minute
* * * * *

# Every 5 minutes
*/5 * * * *

# Every hour at :30
30 * * * *

# Daily at 2am UTC
0 2 * * *

# Monday at 9am UTC
0 9 * * 1

# Weekdays at 8am UTC
0 8 * * 1-5

# 1st of every month at midnight
0 0 1 * *

# Every 15 minutes during business hours (weekdays 9am–5pm UTC)
*/15 9-17 * * 1-5

# Twice daily: 8am and 8pm UTC
0 8,20 * * *

# Every quarter: Jan, Apr, Jul, Oct at midnight
0 0 1 1,4,7,10 *

# Last day of month workaround — runs on 28th (always exists)
0 0 28 * *
```

## Six-field format (with seconds)

```bash
# Used in: AWS EventBridge, some GitHub Actions, Trigger.dev
# ┌────────── second  (0–59)
# │ ┌──────── minute  (0–59)
# │ │ ┌────── hour    (0–23)
# │ │ │ ┌──── dom     (1–31)
# │ │ │ │ ┌── month   (1–12)
# │ │ │ │ │ ┌ dow     (1–7, 1=Monday in EventBridge)
# │ │ │ │ │ │
# 0 */5 * * ? *    # Every 5 minutes (EventBridge: ? means "no specific value")
```

## GitHub Actions

```yaml
on:
  schedule:
    - cron: '0 4 * * *'   # 4am UTC daily
    - cron: '0 */6 * * *' # Every 6 hours
```

GitHub Actions uses UTC and the standard 5-field format. Minimum interval is every 5 minutes. Scheduled workflows may run up to 15 minutes late during high load.

## systemd timer OnCalendar

```ini
# systemd uses its own syntax — not cron
OnCalendar=*-*-* 02:00:00   # 2am every day
OnCalendar=Mon *-*-* 09:00  # Every Monday at 9am
OnCalendar=*-*-01 00:00     # 1st of month
OnCalendar=weekly            # Monday 00:00:00
OnCalendar=daily             # *-*-* 00:00:00
OnCalendar=hourly            # *-*-* *:00:00
```

```bash
# Verify a timer expression
systemd-analyze calendar "Mon *-*-* 09:00"
# → Next elapse: Mon 2031-07-21 09:00:00 UTC
#   From now: 2d 14h
```

## Edge cases

**Day of month vs day of week**: If both are set, most implementations fire when EITHER matches (OR logic), not AND. This surprises everyone once.

```bash
# Fires on the 1st OR on Monday — not just Monday the 1st
0 0 1 * 1

# Workaround: use a script check
0 0 1 * 1 [ "$(date +\%d)" = "01" ] && /path/to/script
```

**February 31st**: `0 0 31 2 *` never fires — February has no 31st day. Use `28` for a guaranteed monthly job.

**DST clock changes**: Cron uses wall clock time. Jobs scheduled at 2am during spring-forward may not fire (clock jumps from 1:59 to 3:00). Use UTC everywhere and avoid scheduling at 2am.

**Missed jobs**: If the server is down when a job is scheduled, standard cron skips it. systemd timers with `Persistent=true` run the missed job on next boot.

```ini
[Timer]
Persistent=true  # Run missed executions on boot
```

Cron expression tester: https://crontab.guru for visual validation. Always use UTC for production schedules.
