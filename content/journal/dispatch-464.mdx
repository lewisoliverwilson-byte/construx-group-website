Context is widely misunderstood. It's often used as a global state store — putting everything from user data to UI state into a single context. This causes every context consumer to re-render whenever anything in the context changes. The right mental model: context is for values that are stable or change infrequently.

## What context is good for

- **Theming**: dark/light mode, colour scheme
- **Authentication**: current user, session data
- **Locale**: current language, currency, timezone
- **Feature flags**: values that are set once and don't change
- **Dependency injection**: providing instances of services/clients

## What context is not good for

- Frequently-updating values (UI state, form state, real-time data)
- State that only a subtree of components needs (lift it up, don't inject down)
- Replacing proper state management for complex state machines

## Basic context pattern

```tsx
// contexts/AuthContext.tsx
'use client';

import { createContext, useContext, useEffect, useState, type ReactNode } from 'react';

interface User {
  id: string;
  email: string;
  name: string;
  role: 'admin' | 'user';
}

interface AuthContextValue {
  user: User | null;
  isLoading: boolean;
  signOut: () => Promise<void>;
}

const AuthContext = createContext<AuthContextValue | null>(null);

export function AuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<User | null>(null);
  const [isLoading, setIsLoading] = useState(true);

  useEffect(() => {
    fetch('/api/auth/me')
      .then((r) => r.ok ? r.json() : null)
      .then((data) => {
        setUser(data?.user ?? null);
        setIsLoading(false);
      })
      .catch(() => setIsLoading(false));
  }, []);

  const signOut = async () => {
    await fetch('/api/auth/sign-out', { method: 'POST' });
    setUser(null);
  };

  return (
    <AuthContext.Provider value={{ user, isLoading, signOut }}>
      {children}
    </AuthContext.Provider>
  );
}

// Custom hook — forces proper error handling
export function useAuth(): AuthContextValue {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error('useAuth must be used within AuthProvider');
  return ctx;
}
```

## Splitting contexts by update frequency

```tsx
// Bad: everything in one context — all consumers re-render on any change
const AppContext = createContext({
  user: null,
  theme: 'dark',
  notifications: [],  // Updates frequently
  modalOpen: false,   // Updates frequently
});

// Good: separate stable and dynamic values
const UserContext = createContext<User | null>(null);      // Stable
const ThemeContext = createContext<'dark' | 'light'>('dark');  // Rare changes
// notifications → TanStack Query or Zustand
// modalOpen → local useState in the component that needs it
```

## Context with a reducer

For complex context state (multiple related values), a reducer is cleaner than multiple `useState` calls:

```tsx
'use client';

import { createContext, useContext, useReducer, type Dispatch, type ReactNode } from 'react';

interface Toast {
  id: string;
  message: string;
  type: 'success' | 'error' | 'info';
}

type ToastAction =
  | { type: 'ADD'; toast: Omit<Toast, 'id'> }
  | { type: 'REMOVE'; id: string };

function toastReducer(state: Toast[], action: ToastAction): Toast[] {
  switch (action.type) {
    case 'ADD':
      return [...state, { ...action.toast, id: crypto.randomUUID() }];
    case 'REMOVE':
      return state.filter((t) => t.id !== action.id);
    default:
      return state;
  }
}

const ToastContext = createContext<Toast[]>([]);
const ToastDispatchContext = createContext<Dispatch<ToastAction>>(() => {});

export function ToastProvider({ children }: { children: ReactNode }) {
  const [toasts, dispatch] = useReducer(toastReducer, []);

  return (
    <ToastContext.Provider value={toasts}>
      <ToastDispatchContext.Provider value={dispatch}>
        {children}
      </ToastDispatchContext.Provider>
    </ToastContext.Provider>
  );
}

// Separate contexts for state and dispatch prevents re-renders in dispatch-only consumers
export const useToasts = () => useContext(ToastContext);
export const useToastDispatch = () => useContext(ToastDispatchContext);

// Convenience hook
export function useToast() {
  const dispatch = useToastDispatch();
  return {
    success: (message: string) => dispatch({ type: 'ADD', toast: { message, type: 'success' } }),
    error: (message: string) => dispatch({ type: 'ADD', toast: { message, type: 'error' } }),
    remove: (id: string) => dispatch({ type: 'REMOVE', id }),
  };
}
```

## Separating state from dispatch

The pattern `const ToastContext` and `const ToastDispatchContext` avoids a performance trap. Components that only dispatch actions (buttons that trigger toasts) don't re-render when the toast list changes — they only consume `ToastDispatchContext`, which never changes.

Without this separation, every button that uses `useToast()` re-renders when any toast is added or removed. For most apps this doesn't matter. For complex UIs with many consumers, it does.

## When context starts to hurt

Signs that context is the wrong tool:
- You're memoising the context value with `useMemo` to prevent re-renders
- You're using multiple `useRef` hacks to avoid re-renders
- The same value needs to be in multiple contexts
- You're context-wrapping at the component level, not the app level

When context feels painful, switch to Zustand for shared global state. Zustand has selector-based subscriptions — components only re-render when the specific slice of state they access changes.

```ts
// Zustand equivalent — components only re-render when their selected slice changes
import { create } from 'zustand';

interface Store {
  user: User | null;
  setUser: (user: User | null) => void;
}

const useStore = create<Store>((set) => ({
  user: null,
  setUser: (user) => set({ user }),
}));

// This component only re-renders when user.name changes — not when anything else in the store changes
function UserName() {
  const name = useStore((state) => state.user?.name);
  return <span>{name}</span>;
}
```

Context and Zustand are complementary. Context for stable, injected values. Zustand for shared mutable state that changes frequently.
