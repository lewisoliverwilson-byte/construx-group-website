Notifications look simple until you start building them. A naive implementation — poll the database every few seconds, show new rows — works for a prototype and collapses under load. The production pattern is a fanout queue with a persistent log.

## The data model

Start with a notification log: every notification that should ever be shown to a user, persisted in a table.

```sql
CREATE TABLE notifications (
  id          TEXT PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id     TEXT NOT NULL REFERENCES users(id),
  type        TEXT NOT NULL,          -- 'comment', 'mention', 'system', etc.
  title       TEXT NOT NULL,
  body        TEXT,
  action_url  TEXT,
  read_at     TIMESTAMPTZ,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  metadata    JSONB DEFAULT '{}'
);

CREATE INDEX notifications_user_unread ON notifications (user_id, created_at DESC)
  WHERE read_at IS NULL;
```

The `metadata` column stores typed payload per notification type — the comment ID, the mentioner's user ID, whatever the client needs to render the notification richly without extra fetches.

## The producer: creating notifications

Notifications are created by domain events. Don't call a notification function directly from business logic — emit an event and let a handler create the notification.

```ts
// lib/events.ts
export type DomainEvent =
  | { type: 'comment.created'; commentId: string; postId: string; authorId: string; recipientId: string }
  | { type: 'user.mentioned'; mentionerId: string; mentionedId: string; context: string }
  | { type: 'task.assigned'; taskId: string; assigneeId: string; assignerId: string };

// lib/notification-handler.ts
import { db } from './db';
import { queue } from './queue';

export async function handleDomainEvent(event: DomainEvent) {
  switch (event.type) {
    case 'comment.created':
      await db.notifications.create({
        data: {
          userId:    event.recipientId,
          type:      'comment',
          title:     'New comment on your post',
          actionUrl: `/posts/${event.postId}#comment-${event.commentId}`,
          metadata:  { commentId: event.commentId, authorId: event.authorId },
        },
      });
      // Queue delivery (email, push) separately
      await queue.add('notification.deliver', {
        userId: event.recipientId,
        type:   'comment',
      });
      break;
  }
}
```

## Real-time delivery with Server-Sent Events

For in-app notifications, Server-Sent Events are simpler than WebSockets. The client opens a long-lived HTTP connection; the server pushes events down when notifications arrive.

```ts
// app/api/notifications/stream/route.ts
import { db } from '@/lib/db';
import { notificationEmitter } from '@/lib/notification-emitter';

export async function GET(req: Request) {
  const userId = await getUserId(req);
  if (!userId) return new Response('Unauthorized', { status: 401 });

  const stream = new ReadableStream({
    start(controller) {
      const encoder = new TextEncoder();

      const send = (data: object) => {
        controller.enqueue(encoder.encode(`data: ${JSON.stringify(data)}\n\n`));
      };

      // Send unread count on connect
      db.notifications
        .count({ where: { userId, readAt: null } })
        .then((count) => send({ type: 'init', unreadCount: count }));

      // Listen for new notifications
      const cleanup = notificationEmitter.on(`notification:${userId}`, (notification) => {
        send({ type: 'notification', notification });
      });

      req.signal.addEventListener('abort', cleanup);
    },
  });

  return new Response(stream, {
    headers: {
      'Content-Type':  'text/event-stream',
      'Cache-Control': 'no-cache',
      'Connection':    'keep-alive',
    },
  });
}
```

```ts
// The emitter — in-process pub/sub, replace with Redis pub/sub for multi-instance
// lib/notification-emitter.ts
import { EventEmitter } from 'events';
export const notificationEmitter = new EventEmitter();
```

After creating a notification in the database, emit to the channel:

```ts
notificationEmitter.emit(`notification:${userId}`, notification);
```

For multiple server instances (common in production), replace the in-process EventEmitter with Redis pub/sub so events from any instance reach the right client connection.

## The client

```ts
// hooks/useNotifications.ts
'use client';
import { useEffect, useState } from 'react';

export function useNotifications() {
  const [unreadCount, setUnreadCount] = useState(0);
  const [notifications, setNotifications] = useState<Notification[]>([]);

  useEffect(() => {
    const es = new EventSource('/api/notifications/stream');

    es.onmessage = (e) => {
      const data = JSON.parse(e.data);
      if (data.type === 'init') {
        setUnreadCount(data.unreadCount);
      }
      if (data.type === 'notification') {
        setNotifications((prev) => [data.notification, ...prev]);
        setUnreadCount((c) => c + 1);
      }
    };

    return () => es.close();
  }, []);

  return { unreadCount, notifications };
}
```

## Email and push delivery via queue

Real-time in-app delivery is just one channel. Email and push notifications need to be queued and processed asynchronously — you don't want to block notification creation on a Resend API call.

```ts
// workers/notification-deliver.ts
import { Worker } from 'bullmq';
import { resend } from '@/lib/resend';
import { db } from '@/lib/db';

const worker = new Worker('notifications', async (job) => {
  const { userId, type } = job.data;

  const user = await db.users.findUnique({ where: { id: userId } });
  if (!user?.emailNotifications) return;

  if (type === 'comment') {
    await resend.emails.send({
      from:    'Construx <notifications@construxgroup.io>',
      to:      user.email,
      subject: 'New comment on your post',
      react:   <CommentNotificationEmail user={user} />,
    });
  }
}, { connection: redis });
```

## Mark as read

```ts
// app/api/notifications/read/route.ts
import { revalidatePath } from 'next/cache';

export async function POST(req: Request) {
  const { ids } = await req.json();
  const userId = await getUserId(req);

  await db.notifications.updateMany({
    where: { id: { in: ids }, userId },
    data:  { readAt: new Date() },
  });

  return Response.json({ ok: true });
}
```

## What we use for The Hyve

The Hyve uses SSE for real-time delivery (the target users have the app open all day — WebSockets felt like over-engineering for the use case). Redis pub/sub fans events to the correct SSE connection across instances. Email delivery goes through BullMQ → Resend.

The notification log keeps 90 days of history per user. Older notifications are archived to cold storage (S3), not deleted — the metadata is valuable for understanding engagement patterns.

The pattern that surprised us: SSE reconnects automatically in the browser when a server restarts. WebSockets require explicit reconnect logic on the client. For a notification stream that doesn't need bidirectional communication, SSE is less work.
