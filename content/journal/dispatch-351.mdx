The gap between "AI-powered" and "AI-first" is the architecture. Most products use an LLM as a better search box or a fancier autocomplete. AI-first products use the LLM as the decision-making layer — the thing that reads context, selects actions, and produces structured output that the rest of the system can act on.

Here's how that architecture works in practice.

## The key insight: structured output over free text

The first mistake is treating LLM output as free text that your UI renders. The output should be structured data that your system acts on. The rendering is secondary.

```ts
import Anthropic from '@anthropic-ai/sdk';

const client = new Anthropic();

// Wrong: generate free text and render it
const completion = await client.messages.create({
  model: 'claude-opus-4-8',
  messages: [{ role: 'user', content: prompt }],
  max_tokens: 1024,
});
const text = completion.content[0].text;
// Now you have a string — what do you do with it?

// Right: generate structured data
const completion = await client.messages.create({
  model: 'claude-opus-4-8',
  messages: [{ role: 'user', content: prompt }],
  max_tokens: 2048,
  tools: [{
    name: 'create_product_recommendations',
    description: 'Generate structured product recommendations based on user criteria',
    input_schema: {
      type: 'object' as const,
      properties: {
        recommendations: {
          type: 'array',
          items: {
            type: 'object',
            properties: {
              productId: { type: 'string' },
              score: { type: 'number', minimum: 0, maximum: 100 },
              reason: { type: 'string' },
              priceRange: { type: 'string', enum: ['budget', 'mid', 'premium'] },
            },
            required: ['productId', 'score', 'reason', 'priceRange'],
          },
        },
        searchTerms: { type: 'array', items: { type: 'string' } },
      },
      required: ['recommendations', 'searchTerms'],
    },
  }],
  tool_choice: { type: 'tool', name: 'create_product_recommendations' },
});

// Now you have typed structured data
const toolUse = completion.content.find((b) => b.type === 'tool_use');
if (toolUse?.type === 'tool_use') {
  const data = toolUse.input as ProductRecommendations;
  // Use data.recommendations, data.searchTerms
}
```

`tool_choice: { type: 'tool', name: '...' }` forces Claude to use the tool — you always get structured output, never a text response you need to parse.

## Streaming for responsiveness

AI inference is slow. Stream the output so users see progress:

```ts
import { streamText } from 'ai';  // Vercel AI SDK
import { anthropic } from '@ai-sdk/anthropic';

// app/api/chat/route.ts
export async function POST(req: Request) {
  const { messages } = await req.json();

  const result = streamText({
    model: anthropic('claude-opus-4-8'),
    system: 'You are a product research assistant. Be concise and specific.',
    messages,
    maxTokens: 1024,
    onFinish: async ({ text, usage }) => {
      // Log usage for billing/monitoring after stream completes
      await logAIUsage({ text, usage, sessionId });
    },
  });

  return result.toDataStreamResponse();
}
```

```tsx
// Client component
```

## Context management

Claude has a context window limit. For product use cases, you need to be deliberate about what goes in the context:

```ts
interface Message {
  role: 'user' | 'assistant';
  content: string;
}

function buildContext(
  userQuery: string,
  history: Message[],
  relevantData: unknown[],
  systemContext: string,
): Message[] {
  // 1. Most recent conversation history (keeps conversational context)
  const recentHistory = history.slice(-6);  // last 3 exchanges

  // 2. Relevant data retrieved for this query (RAG pattern)
  const dataContext = relevantData.length > 0
    ? [{
        role: 'user' as const,
        content: `Here is relevant data for this query:\n${JSON.stringify(relevantData, null, 2)}`,
      }]
    : [];

  // 3. Current user query
  const currentQuery = [{ role: 'user' as const, content: userQuery }];

  return [...recentHistory, ...dataContext, ...currentQuery];
}
```

Don't stuff everything into context hoping Claude figures it out. Be selective — the quality of the context is more important than the quantity.

## The system prompt is the product

The system prompt is where your product's behavior lives:

```ts
const SCOUTR_SYSTEM_PROMPT = `You are Scoutr's price analysis engine. Your job is to analyze product listings and identify arbitrage opportunities.

CAPABILITIES:
- Compare prices across multiple marketplaces
- Identify profitable resale opportunities (minimum 20% margin after fees)
- Flag suspicious pricing patterns
- Estimate selling velocity

OUTPUT FORMAT:
Always use the analyze_products tool. Never respond in plain text.

CONSTRAINTS:
- Only analyze products with sufficient price data (minimum 3 sources)
- Apply platform-specific fee structures (Amazon: 15%, eBay: 13%, Etsy: 9%)
- Flag any product where margin calculation is uncertain

PRICING MODEL:
- Source price includes all fees and shipping to buyer
- Selling price uses the platform's current median for that ASIN/listing
- Profit margin = (selling price - source price - platform fees) / selling price`;
```

The system prompt should specify what the AI can and cannot do, the format of outputs, and the domain-specific rules. It's the contract between your product and the model.

## Model selection by use case

Don't use the most capable model for everything:

```ts
const models = {
  // Simple classification, tagging, summarization
  fast: 'claude-haiku-4-5-20251001',
  
  // Complex reasoning, code generation, analysis
  balanced: 'claude-sonnet-4-6',
  
  // Maximum capability — strategic decisions, complex multi-step
  max: 'claude-opus-4-8',
};

// Route based on complexity
function selectModel(taskType: string, complexity: 'low' | 'medium' | 'high'): string {
  if (taskType === 'classification' || complexity === 'low') return models.fast;
  if (complexity === 'high') return models.max;
  return models.balanced;
}
```

Haiku is 10-20x cheaper than Opus. If a task doesn't need Opus's reasoning depth, use Haiku.

## Error handling and fallbacks

AI calls fail. Handle them gracefully:

```ts
async function callWithFallback<T>(
  primary: () => Promise<T>,
  fallback: () => Promise<T>,
  fallbackConditions: (e: Error) => boolean = () => true,
): Promise<T> {
  try {
    return await primary();
  } catch (error) {
    if (error instanceof Error && fallbackConditions(error)) {
      console.error('AI call failed, using fallback:', error.message);
      return await fallback();
    }
    throw error;
  }
}

// Usage
const recommendations = await callWithFallback(
  () => getAIRecommendations(query),
  () => getKeywordRecommendations(query),  // rule-based fallback
  (e) => e.message.includes('overloaded') || e.message.includes('timeout'),
);
```

A rule-based fallback keeps the product functional when AI is unavailable. Users notice "something went wrong" much less than they notice "nothing happened."

## Caching AI responses

AI responses are expensive and deterministic for the same input. Cache aggressively:

```ts
import { kv } from '@vercel/kv';
import crypto from 'crypto';

async function getCachedAIResponse<T>(
  prompt: string,
  fn: () => Promise<T>,
  ttl: number = 3600,
): Promise<T> {
  const key = `ai:${crypto.createHash('sha256').update(prompt).digest('hex').slice(0, 16)}`;
  
  const cached = await kv.get<T>(key);
  if (cached) return cached;

  const result = await fn();
  await kv.setex(key, ttl, result);
  return result;
}
```

For product recommendation engines, summaries, or any content that doesn't need to be unique per request — cache it.
