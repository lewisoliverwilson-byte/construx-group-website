date: "2033-11-09"
excerpt: "Pixie is a Kubernetes observability platform that uses eBPF to capture telemetry at the Linux kernel level without requiring any code instrumentation, sidecar injection, or application restarts. When you install Pixie on a Kubernetes cluster, the Pixie Edge Module (PEM) DaemonSet runs one pod per node; each PEM uses eBPF probes to intercept system calls and capture HTTP/1.1, HTTP/2, gRPC, PostgreSQL, MySQL, Redis, Cassandra, Kafka, and DNS traffic automatically. This means you get request/response latency, error rates, and throughput for every service in your cluster — including services you don't own and can't modify — within minutes of installation. Pixie uses in-cluster data storage (not sending raw traffic data to the cloud): telemetry is stored on node memory (configurable, typically 1-2GB per node) with a rolling 24-hour window. Queries run directly against this in-cluster store using PxL (Pixie Language, a Python-based query language). Pixie integrates with Grafana (as a data source), with OpenTelemetry export, and with the Pixie web UI (accessed via the Pixie Cloud or self-hosted). The net result: any service running on the cluster gets baseline RED metrics (Rate, Errors, Duration) for free."

```python
# PxL script: custom query in Python-like Pixie Language
# Find the slowest SQL queries hitting PostgreSQL (no Postgres instrumentation needed)

import px

def sql_stats(start_time: str, threshold_ms: int):
    df = px.DataFrame(table='conn_stats', start_time=start_time)

    # Filter to PostgreSQL connections (port 5432)
    df = df[df.remote_port == 5432]

    # Parse the SQL query from the request body (captured by eBPF)
    df.query = df.req_body.str[:200]

    # Aggregate: count requests and compute latency stats
    df = df.groupby(['query']).agg(
        count       = ('query',      px.count),
        p50_ms      = ('latency',    px.quantiles(0.5)),
        p99_ms      = ('latency',    px.quantiles(0.99)),
        error_count = ('resp_status', lambda x: px.sum(x == '500')),
    )

    # Filter to slow queries only
    df = df[df.p99_ms > threshold_ms * 1e6]   # nanoseconds
    df = df.sort('p99_ms', ascending=False)
    return df

px.display(sql_stats('-30m', 100), 'slow_sql_queries')
# QUERY                                      COUNT  P50_MS  P99_MS  ERRORS
# SELECT * FROM orders WHERE tenant_id = $1  18421  4.2ms   142ms   0
# UPDATE tenants SET last_seen = NOW()        4821   2.1ms   31ms    0
```

Pixie vs Datadog APM vs Jaeger/OTel vs Prometheus vs traditional APM: Traditional APM (Datadog, New Relic, Dynatrace) requires either a language-specific agent installed in every service or SDK instrumentation in the application code. Rolling out APM to 50 services means 50 deployment changes. Jaeger and OpenTelemetry require even more work — SDK integration, context propagation, trace sampling configuration. Pixie requires none of this: install once at the cluster level, get baseline observability for everything immediately. The trade-off: Pixie captures at the kernel level, so it sees HTTP/SQL/Redis traffic but not application-specific business events (a user purchase, a specific workflow step). For custom business metrics, OpenTelemetry instrumentation is still necessary. Pixie's 24-hour in-cluster data window is a limitation for historical analysis — it's for real-time debugging, not long-term trend analysis. The right pattern is Pixie for instant, no-friction baseline observability (RED metrics, HTTP request logs, SQL queries) and Prometheus + OTel for deeper, application-specific metrics with longer retention.
