Feature flags (also called feature toggles) let you deploy code to production that isn't visible or active for all users. The flag controls whether the feature is on or off for a given user, cohort, or percentage of traffic.

The core benefit: you can deploy code without releasing features. Deployment and launch become independent events.

## When flags are worth the overhead

Feature flags add complexity. Every flag is an additional code path, a state to manage, and a cleanup task when the flag is eventually removed. At our scale, we use flags selectively — only when the benefit outweighs the overhead.

Worth using:
- **Risky new features**: a major change to Scoutr's scan algorithm that might have edge cases we haven't found. Deploy to 10% of users, watch error rates and feedback, expand.
- **A/B testing**: two versions of an onboarding flow. 50% see version A, 50% see version B. Compare activation rates.
- **Staged rollouts**: new features that touch shared infrastructure. Roll out to internal users first, then 10%, then 100%.
- **Beta access**: early access features for specific users who've opted in.

Not worth using:
- **Small, low-risk changes**: a copy change, a layout adjustment, a performance improvement. Just deploy it.
- **Bug fixes**: a bug fix should go to 100% of users immediately, not be flagged.
- **Infrastructure changes**: flags are for application features, not infrastructure. An infrastructure change should be validated and deployed to all users, not flagged.

## PostHog feature flags: the implementation

We use PostHog for feature flags. It's already in the stack for analytics, so there's no additional service to manage.

Defining a flag in PostHog: create a flag with a key (e.g., `scoutr-new-scan-ui`), set the rollout conditions (all users, specific user IDs, percentage, or property-based targeting), and enable/disable.

In the application:

```typescript
// Server component (Next.js App Router)
import { PostHog } from 'posthog-node';

const posthog = new PostHog(process.env.POSTHOG_API_KEY!, {
  host: 'https://eu.i.posthog.com',
});

const newScanUiEnabled = await posthog.isFeatureEnabled(
  'scoutr-new-scan-ui',
  userId,
);

// Render different UI based on flag
```

For client-side flags (rendering different UI in client components):

```tsx
'use client';
import { useFeatureFlagEnabled } from 'posthog-js/react';

function ScanInterface() {
  const newUiEnabled = useFeatureFlagEnabled('scoutr-new-scan-ui');
  
  if (newUiEnabled) {
    return <NewScanInterface />;
  }
  return <CurrentScanInterface />;
}
```

## The flag lifecycle

Every flag has a lifecycle:

1. **Created**: flag is off for all users
2. **Internal**: flag is on for internal users (us), off for everyone else
3. **Limited rollout**: flag is on for 10-20% of users
4. **Full rollout**: flag is on for 100% of users
5. **Cleaned up**: flag is removed, code paths for the disabled state are deleted

The cleanup step is critical and often skipped. Flags that are permanently at 100% and never cleaned up accumulate. The codebase fills with dead `if (!flagEnabled)` branches that no longer serve any purpose. We try to clean up flags within 2 weeks of reaching 100% rollout.

## The A/B test case

A/B testing with feature flags: we deployed two versions of Scoutr's scan results page (the layout that shows fee breakdowns). Half of users saw the original tabular layout; half saw a new card-based layout.

After 3 weeks of data:
- Card layout: 18% higher time-on-page after scan completion
- Card layout: 22% higher click-through to scan more products
- Card layout: no significant difference in trial-to-paid conversion

Decision: roll out the card layout to 100%. The engagement metrics clearly favoured it.

The PostHog funnel comparison between the two flag cohorts gave us the data. The flag made it possible to collect this data safely without committing the full UI change before we had evidence.

## Flag hygiene

Three rules we try to follow:

**Name flags clearly**: `scoutr-new-scan-results-cards`, not `scan-v2`. The name should indicate what the flag controls and for which product.

**Document the expected lifecycle**: when we create a flag, we note the target rollout date and what the cleanup trigger is ("clean up when 100% for 2 weeks").

**Don't gate stable features indefinitely**: a feature that's been at 100% for more than a month isn't a flag anymore, it's a permanent feature. Remove the flag.

Flags are a temporary control mechanism, not a permanent feature toggle system. If a feature needs to be togglable permanently (for billing reasons, for user preferences), that's a different system — application configuration or user settings, not a deployment flag.
