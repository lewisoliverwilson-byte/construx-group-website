date: "2032-09-15"
excerpt: "grype is a vulnerability scanner from Anchore that matches packages in a container image or filesystem against the Grype DB — a merged vulnerability database drawn from NVD, GitHub Advisory Database, Alpine SecDB, Debian Security Tracker, and others. It is SBOM-aware: pipe in a syft SBOM and grype skips the package discovery phase entirely, scanning against the already-computed package inventory. The `--fail-on` flag makes it a CI gate: exit non-zero if any vulnerability at or above the specified severity is found. grype understands language packages (Go modules, npm, PyPI, Cargo) and OS packages (deb, rpm, apk) in the same scan, and shows the fixed-in version alongside each CVE."
author: "Lewis Wilson"

Scan the image. Gate on `--fail-on high`. Feed it a syft SBOM. Check the Grype DB daily.

## Scanning container images

```bash
# grype: scan a container image — pulls layers, discovers packages, matches CVEs
grype construx/api:1.4.2

# Output:
# ✔ Vulnerability DB  [2032-09-14T08:00:00Z]  558,241 known vulns
# ✔ Loaded image       construx/api:1.4.2
# ✔ Parsed image       241 packages across 12 layers
#
# NAME              INSTALLED   FIXED-IN    TYPE    VULNERABILITY   SEVERITY
# openssl           3.1.3       3.1.5       deb     CVE-2024-0727   Critical
# libcurl4          8.4.0       8.6.0       deb     CVE-2024-2398   High
# golang.org/x/net  0.21.0      0.23.0      go-mod  CVE-2024-27304  High
# libgnutls30       3.8.1       3.8.4       deb     CVE-2024-28835  Medium

# --scope AllLayers: scan all image layers (not just final layer)
# Catches vulnerabilities in intermediate layers that weren't cleaned up
grype construx/api:1.4.2 --scope AllLayers

# --fail-on: exit non-zero if any vuln at this severity or higher is found
# Use in CI to block image pushes with known critical/high CVEs
grype construx/api:1.4.2 --fail-on high
# exit code 1 if any High or Critical CVE is found

# Output formats
grype construx/api:1.4.2 --output json > vulns.json
grype construx/api:1.4.2 --output table   # default
grype construx/api:1.4.2 --output cyclonedx-json > vulns-cdx.json
grype construx/api:1.4.2 --output sarif > vulns.sarif   # GitHub Security tab format

# Scan by digest (immutable — tag can change)
grype construx/api@sha256:abc123def456...

# Scan a local tarball
docker save construx/api:1.4.2 | grype
```

## Filesystem and directory scans

```bash
# Scan the current directory (reads go.mod, package.json, requirements.txt, etc.)
grype dir:.

# Scan with --fail-on in CI (before building the image)
grype dir:. --fail-on high
# Runs before `docker build` — fails fast on known-bad dependencies

# Scan only specific package types
grype dir:. --add-cpes-if-none

# Scan a specific file (tar archive, SBOM)
grype construx-api-1.4.2.tar.gz

# Exclude paths from scanning
grype dir:. --exclude ./vendor --exclude ./testdata

# Update the Grype DB before scanning
grype db update
# Updated vulnerability database to 2032-09-15T06:00:00Z
# 558,847 known vulnerabilities

# Check which DB version is in use
grype db status
# Status:         valid
# Built:          2032-09-14 08:00:00 +0000 UTC
# Schema:         5
# Location:       ~/.cache/grype/db/5
# Checksum:       sha256:abc123...
```

## SBOM-aware scanning with syft

```bash
# syft: generate an SBOM (Software Bill of Materials) from an image
# grype can then scan the SBOM without pulling the image again
syft construx/api:1.4.2 -o spdx-json > sbom-1.4.2.json

# Scan the SBOM (skips image pull and layer parsing)
grype sbom:sbom-1.4.2.json

# This pattern is useful in CI:
# 1. Build image and extract SBOM (once)
# 2. Scan SBOM (fast — no image pull)
# 3. Attach SBOM to the image as an OCI artifact

# Attach SBOM to image (OCI artifact)
syft construx/api:1.4.2 -o spdx-json | \
  oras attach construx/api:1.4.2 --artifact-type application/spdx+json -

# Generate CycloneDX SBOM (alternative format)
syft construx/api:1.4.2 -o cyclonedx-json > sbom-cdx.json
grype sbom:sbom-cdx.json

# Diff SBOMs between versions (find new packages introduced)
syft construx/api:1.4.1 -o spdx-json > sbom-1.4.1.json
syft construx/api:1.4.2 -o spdx-json > sbom-1.4.2.json
# Compare with: grype sbom:sbom-1.4.2.json vs sbom-1.4.1.json (manual diff)
```

## CI integration and suppression

```bash
# .grype.yaml: project-level configuration
# Suppress false positives or accepted risks with vulnerability IDs
cat .grype.yaml

# ignore:
#   # CVE-2023-45853: zlib vulnerability with no fix yet — tracked, accepted risk
#   - vulnerability: CVE-2023-45853
#     reason: "No fix available; mitigated by network policy"
#   # Only suppress in non-OS packages
#   - vulnerability: CVE-2023-52425
#     package:
#       type: go-module   # ignore only in Go packages, not deb
#
# fail-on-severity: high
# output: table
# scope: AllLayers

# GitHub Actions: scan image and upload SARIF to Security tab
# - name: Scan image with Grype
#   run: |
#     grype ${{ env.IMAGE }} --output sarif > grype.sarif
#   continue-on-error: true
# - name: Upload SARIF
#   uses: github/codeql-action/upload-sarif@v3
#   with:
#     sarif_file: grype.sarif

# Check if any critical vulnerabilities have a fix available
grype construx/api:1.4.2 --output json | \
  jq '[.matches[] | select(.vulnerability.severity == "Critical" and .vulnerability.fix.versions != [])] | length'
# 1  ← 1 critical vuln with a fix available → must upgrade
```

grype vs trivy vs snyk: trivy is the most commonly used scanner — it handles containers, IaC, and git repos in one tool, and has first-class Kubernetes and GitHub integration. grype is more focused: excellent SBOM integration (the syft+grype combination is purpose-built), faster scans on pre-generated SBOMs, and a clean Go API for custom tooling. Snyk is commercial with a SaaS dashboard, which adds fix PR automation and developer-focused output — better for organizations that want a managed experience. The practical setup: use syft to generate SBOMs at build time (attach to OCI), use grype for fast SBOM-based scans in CI, and use `--fail-on high` as the gate that blocks image promotion from staging to prod. A scanner that doesn't gate the pipeline is just noise.
