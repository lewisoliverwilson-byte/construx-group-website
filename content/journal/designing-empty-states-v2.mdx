The empty state is the first thing a user sees after creating an account. It appears at the moment when the user has the highest motivation to engage and the least context about how to proceed. It's the most important screen in the product and the one that's most commonly an afterthought.

Here's how we think about and design empty states across our products.

## Why empty states fail

The most common empty state: a blank screen with a button. "No scans yet. Click here to start your first scan."

This is technically correct and practically useless. It tells the user what to do but not why. It doesn't show the user what the product will look like when it's populated. It doesn't demonstrate the value they're about to get. It's an instruction, not an experience.

The second most common: a large illustration with a friendly message. "Your journey starts here! Explore the possibilities." This is worse — it adds visual noise without adding information and feels patronising.

## What good empty states do

An effective empty state does four things:

1. **Tells the user what this space is for** (orient)
2. **Shows what it will look like when populated** (demonstrate)
3. **Tells the user exactly what to do next** (direct)
4. **Shows why that action is worth taking** (motivate)

For Scoutr's scan interface, the empty state is designed around these principles:
- A visual preview of what a completed scan looks like (a simplified example with product names, fees, and profit margins visible)
- Microcopy that explains what populating it requires: "Paste a product URL from Amazon, eBay, or any retail site"
- A pre-populated input field with an example URL already in it (the most impactful single change we made)
- The explanation of what happens next: "Scoutr scans the page, calculates fees and profit margins, and ranks products by potential return"

The visual preview matters most. Seeing a populated scan result tells the user: "this is what you'll get, and it looks useful." The instruction alone ("paste a URL") doesn't convey value; the preview does.

## The example-first principle

Wherever possible, we pre-populate the empty state with an example rather than leaving it empty.

Scoutr: the scan input has an example URL pre-populated. Click "Scan" and you immediately see results for a real product — no setup required.

The Marqet: new users are shown a curated selection of listings relevant to their professional role (selected during onboarding). The browse interface is never empty.

The Hyve: new workspaces have a pre-configured "Getting Started" channel with the AI agent's first message already there. The channel isn't empty; it's started.

Pre-population converts the empty state from a decision point ("what do I do?") to a demonstration ("here's what this does"). The cognitive load drops dramatically.

## Empty states as product demos

The best empty states double as product demos. A user who hasn't completed setup sees a working example of what they'd see if they had.

This principle applies beyond the first-use empty state. Every time a user encounters a feature they haven't activated yet, they should see what it would look like if they had. Not a placeholder. Not an illustration. A representative example.

For The Marqet's wishlist feature (listings the user has saved), an empty wishlist doesn't say "no saved listings yet" — it shows 3 example listings that have been popular with users in their professional category, with a prompt to save any they find interesting.

The empty wishlist is a low-stakes entry point for the feature. Seeing relevant examples is more likely to prompt engagement than a blank state with a call to action.

## Handling recurring empty states

Some empty states recur: a filtered view that returns no results, a search with no matches, a date range with no data. These are different from first-use empty states — the user knows the product and has deliberately narrowed their view to something that has no content.

For recurring empty states:
- Acknowledge the specific action that produced the empty state ("No scan results matching 'kettle'")
- Offer a path forward ("Try a shorter search term" or "Scan all products on this page instead")
- Don't apologise or be overly cheerful — keep it functional

The tone of a recurring empty state should be neutral and helpful. First-use empty states can be more encouraging; recurring ones should be efficient.

## The metric for empty state quality

The activation metric (time from signup to first meaningful action) is directly influenced by empty state design. Better empty states reduce time-to-activation.

After adding the pre-populated example URL to Scoutr's empty scan interface, time-to-activation dropped from an average of 3.4 minutes to 1.1 minutes. The change took two hours to implement. This is a better return than any feature we've shipped.
