Playbooks are idempotent: running them twice leaves the server in the same state as running them once. For teams that need to manage multiple servers consistently without a full Kubernetes setup, Ansible is the right level of automation."

SSH. YAML. Idempotent. No agent to install.

## Basic playbook

```yaml
# playbooks/deploy.yml
- name: Deploy Construx API
  hosts: api_servers
  become: true
  vars:
    app_version: "{{ lookup('env', 'APP_VERSION') }}"
    image:       "ghcr.io/construx/api:{{ app_version }}"

  tasks:
    - name: Pull latest Docker image
      community.docker.docker_image:
        name:   "{{ image }}"
        source: pull
        force_source: true

    - name: Copy systemd unit file
      template:
        src:   templates/construx-api.service.j2
        dest:  /etc/systemd/system/construx-api.service
        owner: root
        mode:  '0644'
      notify: Reload systemd

    - name: Start and enable service
      systemd:
        name:    construx-api
        state:   started
        enabled: true
        daemon_reload: true

    - name: Wait for health endpoint
      uri:
        url:                 http://localhost:3001/health
        return_content:      true
        status_code:         200
      retries: 10
      delay:   3

  handlers:
    - name: Reload systemd
      systemd:
        daemon_reload: true
```

## Roles — reusable components

```
roles/
  construx.api/
    tasks/main.yml     # Task list
    templates/         # Jinja2 templates
    vars/main.yml      # Role variables
    defaults/main.yml  # Default values (overridable)
    handlers/main.yml  # Handlers
```

```yaml
# site.yml — assembles roles into a full playbook
- hosts: api_servers
  roles:
    - role: construx.api
      vars:
        app_version: "{{ lookup('env', 'APP_VERSION') }}"

- hosts: monitoring
  roles:
    - role: prometheus
    - role: grafana
```

## Templates — Jinja2

```jinja
{# templates/construx-api.service.j2 #}
[Unit]
Description=Construx API Server
After=network.target

[Service]
ExecStart=/usr/bin/docker run \
  --name construx-api \
  -p 3001:3001 \
  -e DATABASE_URL={{ database_url }} \
  -e NODE_ENV=production \
  {{ image }}
Restart=on-failure
RestartSec=5s

[Install]
WantedBy=multi-user.target
```

## Vault — encrypted secrets

```bash
# Encrypt a secrets file
ansible-vault encrypt vars/secrets.yml

# Run playbook with vault password
ansible-playbook site.yml --ask-vault-pass

# Or use a password file (for CI)
ansible-playbook site.yml --vault-password-file ~/.vault-pass
```

```yaml
# vars/secrets.yml — stored encrypted in git
database_url: !vault |
  $ANSIBLE_VAULT;1.1;AES256
  61626364...
```

## Run

```bash
# Run full site playbook
ansible-playbook -i inventory/prod site.yml

# Limit to specific hosts
ansible-playbook -i inventory/prod site.yml --limit vps-fra01

# Dry run (check mode)
ansible-playbook -i inventory/prod site.yml --check --diff

# Run specific tags only
ansible-playbook -i inventory/prod site.yml --tags deploy
```

Ansible vs Terraform vs Docker Compose: Terraform manages infrastructure (cloud resources, DNS). Ansible manages server configuration (packages, files, services). Docker Compose manages container composition locally. They serve different layers — you might use all three. The Construx default: Terraform for cloud resource provisioning; Ansible for server configuration; Docker Compose for local development.
