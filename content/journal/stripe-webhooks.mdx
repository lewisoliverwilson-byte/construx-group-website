Stripe webhooks are the event notification system that connects Stripe's payment processing to your application. When a customer pays, subscribes, or cancels, Stripe sends an HTTP POST to your webhook endpoint. Your application processes the event and updates its state accordingly.

Getting webhooks wrong causes real problems: payments recorded as failed when they succeeded, subscriptions that don't activate, refunds that aren't processed. Here's the correct implementation.

## The webhook endpoint

The webhook endpoint receives POST requests from Stripe. The critical requirement: you must verify that the request came from Stripe, not from someone else who discovered your webhook URL.

```typescript
// app/api/stripe/webhook/route.ts
import { headers } from 'next/headers';
import Stripe from 'stripe';

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY!);
const webhookSecret = process.env.STRIPE_WEBHOOK_SECRET!;

export async function POST(request: Request) {
  const body = await request.text();
  const headersList = await headers();
  const sig = headersList.get('stripe-signature');
  
  if (!sig) {
    return new Response('Missing stripe-signature header', { status: 400 });
  }

  let event: Stripe.Event;
  try {
    event = stripe.webhooks.constructEvent(body, sig, webhookSecret);
  } catch (err) {
    return new Response(`Webhook signature verification failed: ${err}`, { status: 400 });
  }
  
  // Process the event
  await handleStripeEvent(event);
  
  return new Response('OK', { status: 200 });
}
```

The `constructEvent` call verifies the signature using the webhook secret. If the signature doesn't match, the request is rejected. This prevents anyone from sending fake Stripe events to your endpoint.

## The critical mistake: reading the body as JSON

The body must be read as **raw text** before signature verification, not as JSON. If you use `request.json()`, the body is parsed and then re-serialised, which changes the byte representation and invalidates the signature.

This is a common mistake that produces a `signature verification failed` error that's confusing to debug. The fix: `request.text()`, then pass the raw text string to `constructEvent`.

## Event handling: the idempotency requirement

Stripe may send the same event multiple times (if your endpoint returns a 5xx, Stripe retries). Your event handler must be idempotent — processing the same event twice must produce the same result as processing it once.

The standard pattern: check whether you've already processed this event before acting.

```typescript
async function handleStripeEvent(event: Stripe.Event) {
  // Check if we've already processed this event
  const existing = await db.query(
    'SELECT id FROM processed_stripe_events WHERE event_id = $1',
    [event.id]
  );
  if (existing.rows.length > 0) return; // Already processed

  // Record the event as processed first
  await db.query(
    'INSERT INTO processed_stripe_events (event_id, event_type, created_at) VALUES ($1, $2, NOW())',
    [event.id, event.type]
  );
  
  // Now handle the event
  switch (event.type) {
    case 'payment_intent.succeeded':
      await handlePaymentSucceeded(event.data.object as Stripe.PaymentIntent);
      break;
    case 'customer.subscription.deleted':
      await handleSubscriptionCancelled(event.data.object as Stripe.Subscription);
      break;
    // ... other events
  }
}
```

## The events we handle

For Scoutr's subscription model:

**`checkout.session.completed`**: a new subscriber has completed checkout. Create their account, activate their subscription, send the welcome email.

**`customer.subscription.updated`**: a subscription changed (upgraded, downgraded, renewal). Update the user's tier in the database.

**`customer.subscription.deleted`**: a subscription was cancelled or failed to renew. Downgrade the user to the free tier (rather than immediately blocking access).

**`invoice.payment_failed`**: a subscription renewal payment failed. Flag the account and send a payment failure notification.

For The Marqet's transactional model:

**`payment_intent.succeeded`**: a listing purchase was completed. Unlock the purchased listing for the buyer.

**`charge.refunded`**: a refund was processed. Revoke access to the refunded listing.

## Testing webhooks locally

The Stripe CLI enables local webhook testing:

```bash
stripe listen --forward-to localhost:3000/api/stripe/webhook
```

This starts a local proxy that forwards Stripe webhook events to your local development server. The CLI also provides a `STRIPE_WEBHOOK_SECRET` for local testing (different from the production secret) that you add to your `.env.local`.

We test every event type in the local environment before deploying. Stripe's test mode provides trigger commands:

```bash
stripe trigger payment_intent.succeeded
stripe trigger customer.subscription.deleted
```

These fire real (test mode) webhook events that exercise your handler code.

## The response timing requirement

Stripe expects a 2xx response from your webhook within 30 seconds. For webhooks that trigger slow processing (sending emails, updating multiple database tables), return 200 immediately and process asynchronously:

```typescript
// Return 200 immediately
const responsePromise = new Response('OK', { status: 200 });

// Process asynchronously (don't await)
processEventAsync(event).catch(console.error);

return responsePromise;
```

This prevents Stripe from timing out and retrying due to slow processing. The risk: if async processing fails, you won't know to retry. We log all failed async webhook processing to monitoring (PostHog errors) and manually review daily.
