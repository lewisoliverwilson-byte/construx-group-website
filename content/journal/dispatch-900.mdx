date: "2032-05-06"
excerpt: "Crossplane extends Kubernetes to manage external infrastructure — AWS RDS instances, S3 buckets, GCP Cloud SQL, Azure resource groups — using the same Kubernetes CRD and control loop model used for application resources. You define a claim (e.g., a PostgreSQLInstance with storage: 100Gi, tier: production), and Crossplane's provider controller provisions the actual cloud resource and returns connection secrets. The big idea: the Kubernetes control plane becomes the infrastructure plane — one API, one GitOps flow, one set of RBAC rules for both applications and the infrastructure they depend on."

Define infrastructure as a claim. Crossplane provisions it. GitOps manages the lifecycle.

## Installing Crossplane and cloud providers

```bash
# Install Crossplane via Helm
helm repo add crossplane-stable https://charts.crossplane.io/stable
helm install crossplane crossplane-stable/crossplane \
  --namespace crossplane-system \
  --create-namespace

# Install the AWS provider
kubectl apply -f - <<EOF
apiVersion: pkg.crossplane.io/v1
kind: Provider
metadata:
  name: provider-aws-rds
spec:
  package: xpkg.upbound.io/upbound/provider-aws-rds:v1.12.0
EOF

# Create provider credentials
kubectl create secret generic aws-credentials \
  --namespace crossplane-system \
  --from-literal=credentials="[default]
aws_access_key_id = AKIAXXXXXXXXXXXXXXXX
aws_secret_access_key = xxxxxxxxxxxxxxxxxxxxxxxx"

# Configure the provider to use the credentials
kubectl apply -f - <<EOF
apiVersion: aws.upbound.io/v1beta1
kind: ProviderConfig
metadata:
  name: default
spec:
  credentials:
    source: Secret
    secretRef:
      name: aws-credentials
      namespace: crossplane-system
      key: credentials
EOF
```

## Managed resources — direct cloud resource provisioning

```yaml
# RDSInstance: provision an AWS RDS PostgreSQL instance directly
apiVersion: rds.aws.upbound.io/v1beta1
kind: Instance
metadata:
  name: construx-postgres-prod
  annotations:
    crossplane.io/external-name: construx-postgres-prod   # AWS resource name
spec:
  forProvider:
    region: us-east-1
    engine: postgres
    engineVersion: "16.1"
    instanceClass: db.t3.medium
    allocatedStorage: 100
    storageType: gp3
    dbName: construx
    username: construx_admin
    multiAz: true                    # HA: primary + standby in different AZs
    deletionProtection: true
    backupRetentionPeriod: 7
    storageEncrypted: true
    vpcSecurityGroupIdSelector:
      matchLabels:
        app: construx-rds-sg
    dbSubnetGroupNameSelector:
      matchLabels:
        app: construx-db-subnet-group

  writeConnectionSecretToRef:
    name: construx-postgres-connection    # Connection secret written to this K8s secret
    namespace: construx

  providerConfigRef:
    name: default

# After Crossplane provisions the RDS instance:
# kubectl get secret construx-postgres-connection -n construx
# Data keys: endpoint, port, username, password, database
```

## Composite resources — abstract infrastructure API

```yaml
# CompositeResourceDefinition (XRD): define your own infrastructure API
# Developers request a "PostgreSQLInstance", not a specific cloud resource

apiVersion: apiextensions.crossplane.io/v1
kind: CompositeResourceDefinition
metadata:
  name: xpostgresqlinstances.construx.io
spec:
  group: construx.io
  names:
    kind: XPostgreSQLInstance
    plural: xpostgresqlinstances
  claimNames:
    kind: PostgreSQLInstance
    plural: postgresqlinstances

  # Schema for the claim (what developers specify)
  versions:
    - name: v1alpha1
      served: true
      referenceable: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                parameters:
                  type: object
                  required: [storageGB, tier]
                  properties:
                    storageGB:
                      type: integer
                      minimum: 20
                    tier:
                      type: string
                      enum: [dev, staging, production]

---
# Composition: maps claim parameters to actual cloud resources
apiVersion: apiextensions.crossplane.io/v1
kind: Composition
metadata:
  name: postgresql-aws
spec:
  compositeTypeRef:
    apiVersion: construx.io/v1alpha1
    kind: XPostgreSQLInstance

  resources:
    - name: rds-instance
      base:
        apiVersion: rds.aws.upbound.io/v1beta1
        kind: Instance
        spec:
          forProvider:
            region: us-east-1
            engine: postgres
            engineVersion: "16.1"
      patches:
        # Map storageGB claim field to RDS allocatedStorage
        - type: FromCompositeFieldPath
          fromFieldPath: spec.parameters.storageGB
          toFieldPath: spec.forProvider.allocatedStorage

        # Map tier to instance class
        - type: FromCompositeFieldPath
          fromFieldPath: spec.parameters.tier
          toFieldPath: spec.forProvider.instanceClass
          transforms:
            - type: map
              map:
                dev:        db.t3.micro
                staging:    db.t3.medium
                production: db.r7g.large

---
# Developer claim: request a database without knowing about AWS internals
apiVersion: construx.io/v1alpha1
kind: PostgreSQLInstance
metadata:
  name: billing-db
  namespace: construx
spec:
  parameters:
    storageGB: 100
    tier: production
  writeConnectionSecretToRef:
    name: billing-db-connection
```

Crossplane vs Terraform: Both provision cloud infrastructure as code, but they differ fundamentally in model. Terraform is a CLI-driven, plan-apply workflow with state stored in a backend — it's imperative (you run terraform apply). Crossplane is a Kubernetes controller — infrastructure is defined as CRDs and reconciled continuously by a controller (if someone manually deletes the RDS instance, Crossplane re-creates it). For teams already running Kubernetes with GitOps, Crossplane is compelling: one API server, one GitOps workflow, consistent RBAC for both apps and infrastructure. For teams managing infrastructure outside Kubernetes or with complex module sharing, Terraform remains the better choice.
