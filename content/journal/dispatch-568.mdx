DNS is the distributed database that maps domain names to resources. When you type `construxgroup.io`, DNS resolves it to an IP address. When you send email to `@construxgroup.io`, DNS tells your mail server where to deliver it. When you add a domain to a CDN, you're creating DNS records.

Each record type has a specific job. Understanding them prevents the "why isn't this working" debugging session when you misconfigure one.

## A and AAAA

`A` maps a hostname to an IPv4 address. `AAAA` maps it to an IPv6 address.

```
construxgroup.io.  299  IN  A     76.223.108.40
construxgroup.io.  299  IN  A     99.83.190.102
construxgroup.io.  299  IN  AAAA  2600:9000:a61e:d28::1
```

Multiple `A` records for the same hostname enable basic load balancing — DNS returns all records, and the client picks one (usually the first). Most CDNs (Cloudflare, AWS CloudFront) assign two or more IPs per domain for redundancy.

The `299` is the TTL in seconds — how long resolvers are allowed to cache this record. Shorter TTL means faster propagation of changes; longer TTL reduces DNS query load.

## CNAME

`CNAME` maps a hostname to another hostname. It's an alias.

```
www.construxgroup.io.  3599  IN  CNAME  construxgroup.io.
app.construxgroup.io.  3599  IN  CNAME  d3dpr3doar5fjy.cloudfront.net.
```

You cannot set a CNAME on the root of a domain (`construxgroup.io.`). This is a fundamental DNS limitation — the root must have A/AAAA records (or use a non-standard ALIAS/ANAME record that some DNS providers offer). You can set a CNAME on any subdomain.

CNAME chains work (a CNAME pointing to a CNAME) but add latency and create brittle dependencies. Keep chains short.

## MX

`MX` records specify which mail servers handle email for the domain. The number is a priority — lower is preferred.

```
construxgroup.io.  3599  IN  MX  10 inbound-smtp.eu-west-1.amazonaws.com.
```

Multiple MX records with different priorities create failover: if priority 10 is unavailable, the sender tries priority 20. Email senders (other mail servers) perform the MX lookup when delivering. If you have no MX record, email for your domain is undeliverable.

## TXT

`TXT` records store arbitrary text strings. In practice they're used for three things:

**SPF (Sender Policy Framework)**: specifies which servers are allowed to send email as your domain.

```
"v=spf1 include:amazonses.com ~all"
```

`include:` adds another domain's allowed senders to yours. `~all` means "softfail" — mail from other sources is suspicious but not rejected. `-all` is a hard fail.

**DKIM**: TXT records store the public key used to verify email signatures. The key is published at `selector._domainkey.domain.`:

```
dkim._domainkey.construxgroup.io.  TXT  "v=DKIM1; k=rsa; p=MIIBIjANB..."
```

**DMARC**: specifies what to do when SPF or DKIM fails.

```
_dmarc.construxgroup.io.  TXT  "v=DMARC1; p=quarantine; rua=mailto:dmarc@construxgroup.io"
```

`p=quarantine` puts suspicious email in spam. `p=reject` blocks it entirely. `rua=` is where to send aggregate DMARC reports.

**Domain verification**: most third-party services (Google Search Console, Stripe, etc.) ask you to add a TXT record to prove domain ownership.

## NS

`NS` records identify the authoritative nameservers for the domain — the servers that hold the canonical DNS records for that zone.

```
construxgroup.io.  3599  IN  NS  ns-1536.awsdns-00.co.uk.
construxgroup.io.  3599  IN  NS  ns-820.awsdns-38.net.
```

These are set by your domain registrar. When you point a domain to Route 53, Cloudflare, or another DNS provider, you update the NS records at the registrar to point to that provider's nameservers.

## SOA

`SOA` (Start of Authority) is a single record that defines the zone's metadata: primary nameserver, responsible email address, serial number (version), and timing parameters for secondary nameserver refresh.

```
construxgroup.io.  21599  IN  SOA  ns-1536.awsdns-00.co.uk. hostmaster.awsdns.com. 1 7200 900 1209600 86400
```

The serial number increments when the zone changes, signaling to secondary nameservers that they should refresh. You rarely need to manage this manually — DNS providers handle it.

## TTL: the caching mechanism

Every record has a TTL. Resolvers cache records for their TTL duration. This means:

- Lowering a TTL takes effect gradually — resolvers that already cached the old value wait until their TTL expires
- Before a migration (changing A records to a new IP), lower the TTL to 60 seconds and wait for the old TTL to expire, then make the change. Propagation will be faster.
- After the migration is confirmed, raise the TTL back to a normal value

DNS propagation is often cited as "up to 48 hours" — in practice it's TTL-dependent. With a 300-second TTL, propagation is done in 5 minutes.

## Debugging

```bash
dig construxgroup.io A +short          # Just the A records
dig construxgroup.io MX               # MX records
dig construxgroup.io TXT              # TXT records
dig @8.8.8.8 construxgroup.io A      # Force a specific resolver

nslookup construxgroup.io             # Windows-friendly alternative
```

`dig` is the most reliable tool. The `@` flag lets you query a specific resolver directly — useful for checking if changes have propagated to a specific DNS server.
