The choice between WebSockets, Server-Sent Events (SSE), and polling is a transport decision. Pick the wrong one and you have unnecessary complexity or a feature that doesn't work at all.

## Polling

HTTP requests on an interval. Simple to implement. Works everywhere. Wasted bandwidth when nothing changes.

```ts
// Client — poll every 5 seconds
function usePolledData<T>(endpoint: string, interval = 5000) {
  const [data, setData] = useState<T | null>(null);

  useEffect(() => {
    const fetch = async () => {
      const res = await fetch(endpoint);
      if (res.ok) setData(await res.json());
    };

    fetch();  // immediate
    const id = setInterval(fetch, interval);
    return () => clearInterval(id);
  }, [endpoint, interval]);

  return data;
}

// Usage
const notifications = usePolledData<Notification[]>('/api/notifications');
```

**Use when:** data changes infrequently (status checks, heartbeats), and sub-second latency doesn't matter. Works fine for "last updated X minutes ago" style UIs.

**Don't use when:** updates are frequent or time-sensitive. Polling at 1s interval with 1000 users = 1000 req/s minimum.

## Server-Sent Events (SSE)

A persistent HTTP connection from server to client. Server pushes events. Client cannot send data over the same connection. Automatic reconnection built in. Works through HTTP proxies.

```ts
// app/api/notifications/stream/route.ts
export async function GET(req: Request) {
  const session = await auth();
  if (!session) return Response.json({ error: 'Unauthorized' }, { status: 401 });

  let controller: ReadableStreamDefaultController;
  const userId = session.user.id;

  const stream = new ReadableStream({
    start(c) {
      controller = c;

      // Send initial connection event
      controller.enqueue(`event: connected\ndata: ${JSON.stringify({ userId })}\n\n`);

      // Subscribe to events for this user
      const unsubscribe = eventBus.subscribe(userId, (event) => {
        controller.enqueue(`event: ${event.type}\ndata: ${JSON.stringify(event.data)}\n\n`);
      });

      // Cleanup on close
      req.signal.addEventListener('abort', () => {
        unsubscribe();
        controller.close();
      });
    },
  });

  return new Response(stream, {
    headers: {
      'Content-Type': 'text/event-stream',
      'Cache-Control': 'no-cache, no-transform',
      'Connection': 'keep-alive',
      'X-Accel-Buffering': 'no',  // disable Nginx buffering
    },
  });
}
```

```ts
// Client
function useSSE(url: string) {
  const [events, setEvents] = useState<Event[]>([]);

  useEffect(() => {
    const source = new EventSource(url, { withCredentials: true });

    source.addEventListener('notification', (e) => {
      setEvents((prev) => [...prev, JSON.parse(e.data)]);
    });

    source.onerror = () => {
      // EventSource auto-reconnects — no manual handling needed
      console.log('SSE connection lost, reconnecting...');
    };

    return () => source.close();
  }, [url]);

  return events;
}
```

**Use when:** server needs to push updates to the client (notifications, live feeds, AI streaming responses, progress updates). The client only consumes.

**Don't use when:** you need bidirectional communication (collaborative editing, multiplayer, chat).

## WebSockets

Full-duplex persistent connection. Both sides can send at any time. No HTTP overhead per message. More complex to operate (sticky sessions, load balancer config).

```ts
// Using Ably or Pusher handles the hard parts
// (connection management, auth, reconnection, scaling)
import Ably from 'ably';

const client = new Ably.Realtime({ authUrl: '/api/ably/token' });
const channel = client.channels.get('room:abc123');

// Send
channel.publish('message', { text: 'hello' });

// Receive
channel.subscribe('message', (message) => {
  setMessages((prev) => [...prev, message.data]);
});
```

For self-hosted WebSockets with Next.js, you need a separate server (Next.js doesn't support WebSocket upgrade in App Router handlers):

```ts
// server/ws.ts — separate Node.js process
import { WebSocketServer } from 'ws';
import { createServer } from 'http';

const server = createServer();
const wss = new WebSocketServer({ server });

wss.on('connection', (ws, req) => {
  const userId = authenticateRequest(req);
  if (!userId) return ws.close(1008, 'Unauthorized');

  ws.on('message', (data) => {
    const message = JSON.parse(data.toString());
    // Handle message
    broadcastToRoom(message.roomId, message);
  });

  ws.on('close', () => {
    cleanupUser(userId);
  });
});

server.listen(3001);
```

**Use when:** bidirectional real-time (chat, collaborative editing, multiplayer, live cursor positions). If you're already using Ably or Pusher, this is handled for you.

## Streaming AI responses

SSE is the right choice for streaming LLM responses. The Vercel AI SDK abstracts this:

```ts
// app/api/chat/route.ts
import { streamText } from 'ai';
import { anthropic } from '@ai-sdk/anthropic';

export async function POST(req: Request) {
  const { messages } = await req.json();

  const result = await streamText({
    model: anthropic('claude-opus-4-8'),
    messages,
  });

  return result.toDataStreamResponse();  // SSE response
}
```

```tsx
// Client — useChat handles SSE internally
import { useChat } from 'ai/react';

function ChatInterface() {
  const { messages, input, handleSubmit, handleInputChange, isLoading } = useChat({
    api: '/api/chat',
  });

  return (
    <div>
      {messages.map((m) => <p key={m.id}>{m.content}</p>)}
      <form onSubmit={handleSubmit}>
        <input value={input} onChange={handleInputChange} />
        <button disabled={isLoading}>Send</button>
      </form>
    </div>
  );
}
```

## Decision matrix

| Need | Transport |
|---|---|
| Data changes rarely (< 1/min) | Polling |
| Server pushes updates (notifications, feeds) | SSE |
| AI response streaming | SSE |
| Bidirectional (chat, collaborative) | WebSockets (via Ably/Pusher) |
| Presence (who's online) | WebSockets (via Ably/Pusher) |
| Multiplayer / live cursors | WebSockets (via Ably/Pusher) |

The pattern: default to SSE for server-to-client streaming, WebSocket providers (not raw WebSockets) for bidirectional use cases, polling only when you can afford the latency.
