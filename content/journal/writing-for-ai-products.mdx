Writing for AI products is a distinct craft from writing for conventional software. The challenges are different: you're describing a capability that users can't fully predict, a system that produces variable output, and a technology that most people don't understand from first principles.

Get it wrong in one direction and you overpromise — "AI that knows everything, does anything." Get it wrong in the other and you underpromise — "AI-assisted tool that helps with some tasks." Neither is honest or useful.

Here's how we think about it.

## The anthropomorphism trap

The temptation when writing about AI is to use human language that implies sentience: "Claude understands your business," "the AI knows what you need," "your AI colleague reads every decision."

Some of this is fine as shorthand. "Reads and remembers" is a useful way to describe vector memory retrieval. "Understands" is a reasonable approximation of semantic processing. Language that helps users build a correct mental model of how the system works is useful even if it's not literally precise.

The trap is when the language implies properties the system doesn't have:

**Certainty.** "The AI knows the right answer" implies deterministic correctness. AI systems produce probabilistic output — sometimes correct, sometimes plausible-but-wrong. Copy that implies certainty sets up a trust failure when the output is wrong.

**Memory across sessions.** Phrases like "remembers your preferences" are sometimes used to describe session-scoped context, not persistent memory. If the AI doesn't actually remember between sessions, this is misleading.

**Independent judgment.** "The AI decides what to prioritise" implies agency the system doesn't have. The AI produces ranked output based on the instructions it was given. The framing as "decision" suggests a process that's closer to human judgment than it is.

The standard we hold ourselves to: if a user read the copy, formed a belief about how the system works, and that belief would consistently lead them to incorrect expectations — the copy is wrong.

## What Scoutr's copy has to do

Scoutr's core feature is a profit estimate. The copy problem is explaining what that estimate is — and is not.

Early Scoutr copy said things like: "Find profitable products instantly." This was technically accurate but created an expectation that the profit estimate was definitive. "This product is profitable" as a conclusion, rather than "here is your best estimate of profitability based on current fees and available product data."

The revised framing: "See projected margins after all fees — estimated from the product data available." This is longer, less punchy. It's also honest about what the number is: a projection, from available data, that should be treated as an input to a decision rather than as the decision itself.

We then worked to make the caveats useful rather than just defensive. "Estimated from available data" is more useful than a generic disclaimer if we also show users what data was used (extracted vs estimated dimensions, confirmed vs inferred category). The transparency makes the caveat actionable: a user who sees "category: estimated" knows to double-check before committing to a large inventory purchase.

## What The Marqet's copy has to do

The Marqet sells AI configurations — system prompts, prompt packs, workflow templates — for Claude Projects. The copy challenge is explaining what buying a configuration does without implying magic.

The honest framing: "A professional configuration tells Claude exactly what role to play, what constraints to apply, and what format to use. You get the benefit of someone else having figured out the right way to ask."

The too-short version: "Unlock Claude's full potential." This is meaningless marketing copy. It implies Claude has hidden capabilities that the configuration unlocks, which is wrong.

The too-long version: a technical explanation of system prompt mechanics. Accurate but not useful for someone who just wants to know if it works.

The right copy sits at the level of "here is the job this configuration does and here is why it does it better than asking Claude without it." Technical accuracy where technical accuracy matters. Plain language where the technical detail is noise.

## Variable output and how to write about it

AI output varies. Two users asking the same question get different answers. The same user asking the same question twice gets different answers. Most AI product copy ignores this.

Ignoring it creates a category of user disappointment that's hard to address after the fact: "It worked great the first time, but now it does something different." This is expected AI behavior experienced as a product bug.

The copy approach that works: acknowledge variability as a feature, not a limitation. The AI produces different outputs because it reasons from the specific context you provide — change the context, change the output. This is correct and useful behavior; the copy should set the expectation that users have a role in shaping the output.

This shifts the user model from "press button, receive answer" to "provide context, shape output, refine as needed." The second model is accurate. It also increases engagement — users who understand that their input shapes the output are more likely to iterate and find value than users who expected a one-shot magic solution.

## Confidence calibration in copy

A related problem: AI systems often express high confidence in outputs that are uncertain. The system says "the fee for this product is £4.73" when the honest answer is "the fee is approximately £4.50-£5.00, depending on dimensions we estimated."

If the product copy implies precision that the system can't deliver, the user doesn't know to apply appropriate skepticism. This is a trust problem downstream.

The solution is copy that accurately conveys the system's confidence level without requiring users to understand probability distributions. "Approximately," "estimated based on available data," "typical for this category" — these are useful hedges that help users calibrate their own confidence in the output.

What doesn't work: generic disclaimers at the bottom of the page that users skip. Confidence calibration only works when it's presented in context — next to the number it applies to, not in a footer legal statement.

## The summary principle

AI product copy should give users an accurate mental model of how the system works — not a complete technical explanation, but an accurate simplified version of what's happening. A user who forms the right mental model will:

1. Have appropriate expectations
2. Know how to use the product effectively
3. Trust it in the right situations and apply skepticism in the right situations
4. Not blame the product for failures that are within expected operating parameters

The goal is not to make the AI sound impressive. An accurate mental model will make the AI impressive — if it's genuinely impressive. If the copy has to do the work of making it sound impressive, that's a signal the product itself has a problem the copy can't solve.
