Strings for cache. Sorted sets for leaderboards. Streams for events. Pipelines for bulk ops.

## Core data structures

```bash
# String — the simplest type: SET, GET, INCR, EXPIRE
redis-cli SET order:a3f9b2c1 '{"status":"shipped","total":4999}' EX 3600
redis-cli GET order:a3f9b2c1
redis-cli TTL order:a3f9b2c1   # Remaining TTL in seconds

# INCR: atomic counter (rate limiting, metrics)
redis-cli INCR api:requests:2032-06-05:14
# 1, 2, 3, ... (atomic — no race conditions)

# Hash — field-value pairs (like a JSON object, but field-level operations)
redis-cli HSET order:a3f9b2c1 status shipped tracking DHL-1Z999AA
redis-cli HGET order:a3f9b2c1 status
redis-cli HMGET order:a3f9b2c1 status tracking
redis-cli HGETALL order:a3f9b2c1

# List — ordered, push/pop from either end (queue, stack)
redis-cli RPUSH job:queue '{"type":"send_email","order_id":"a3f9b2c1"}'
redis-cli LPOP job:queue          # Pop from front (FIFO queue)
redis-cli BLPOP job:queue 0       # Blocking pop — wait until a job arrives

# Set — unordered, unique members (tag systems, unique visitors)
redis-cli SADD customer:cust-001:tags premium verified
redis-cli SMEMBERS customer:cust-001:tags
redis-cli SISMEMBER customer:cust-001:tags premium   # 1 = present
redis-cli SINTER customer:cust-001:tags customer:cust-002:tags   # Intersection
```

## Sorted set — leaderboards and range queries

```bash
# ZADD: add member with score (score = sort key)
redis-cli ZADD leaderboard:revenue 142876.9 "cust-001"
redis-cli ZADD leaderboard:revenue 138421.3 "cust-002"
redis-cli ZADD leaderboard:revenue 119204.7 "cust-003"

# Top 10 by revenue (highest first — REV reverses order)
redis-cli ZRANGE leaderboard:revenue 0 9 REV WITHSCORES
# cust-001  142876.9
# cust-002  138421.3
# cust-003  119204.7

# Rank of a specific member (0-indexed)
redis-cli ZREVRANK leaderboard:revenue cust-001   # 0 (first place)

# Score of a member
redis-cli ZSCORE leaderboard:revenue cust-001     # 142876.9

# Range by score (customers with revenue > 100k)
redis-cli ZRANGEBYSCORE leaderboard:revenue 100000 +inf WITHSCORES

# Use sorted sets for time-series with timestamp as score
redis-cli ZADD requests:api:2032-06-05 1748592727.0 "req:a3f9b2c1"
redis-cli ZRANGEBYSCORE requests:api:2032-06-05 1748592000 1748592999   # Range by time

# Sliding window rate limiter using sorted sets
RATE_KEY="ratelimit:cust-001:api"
NOW=$(date +%s%N | cut -c1-13)   # Milliseconds
WINDOW=$((NOW - 60000))           # 1 minute window

redis-cli MULTI
redis-cli ZADD $RATE_KEY $NOW $NOW
redis-cli ZREMRANGEBYSCORE $RATE_KEY 0 $WINDOW
redis-cli ZCARD $RATE_KEY
redis-cli EXPIRE $RATE_KEY 120
redis-cli EXEC
# Count > 100 = rate limit exceeded
```

## Streams — persistent pub/sub with consumer groups

```bash
# Streams: like Kafka topics but simpler — append-only, persistent, consumer groups
# XADD: append an event (auto-generate ID with *)
redis-cli XADD orders '*' order_id a3f9b2c1 status shipped customer_id cust-001
# 1748592727000-0   ← message ID: timestamp-sequence

# Read the last 5 events
redis-cli XREVRANGE orders + - COUNT 5

# Consumer groups: distribute events across workers (like Kafka consumer groups)
redis-cli XGROUP CREATE orders order-processor $ MKSTREAM
# Register the consumer group starting from now ($) — use 0 for all history

# Worker reads up to 10 events (blocking, 5s timeout)
redis-cli XREADGROUP GROUP order-processor worker-1 COUNT 10 BLOCK 5000 STREAMS orders '>'

# Acknowledge processed events (mark as done)
redis-cli XACK orders order-processor 1748592727000-0

# Check pending (unacknowledged) messages
redis-cli XPENDING orders order-processor - + 10
# 1748592727000-0  worker-1  3412ms  1   ← pending 3.4s, 1 delivery attempt

# Claim stale messages from dead workers (auto-rebalancing)
redis-cli XAUTOCLAIM orders order-processor worker-2 60000 0-0 COUNT 10
# Reclaims messages pending > 60s from any worker
```

## Pipelines and Lua scripting

```python
# Python with redis-py: pipeline multiple commands in one round trip
import redis

r = redis.Redis(host='redis.construx.svc.cluster.local', decode_responses=True)

# Without pipeline: 1000 commands = 1000 round trips
for order_id in order_ids:
    r.setex(f'order:{order_id}', 3600, json.dumps(orders[order_id]))
# This takes 1000 * RTT (e.g. 1000 * 0.5ms = 500ms)

# With pipeline: 1000 commands = 1 round trip
with r.pipeline() as pipe:
    for order_id in order_ids:
        pipe.setex(f'order:{order_id}', 3600, json.dumps(orders[order_id]))
    pipe.execute()
# All 1000 commands sent in one TCP write, responses in one read

# Lua script: atomic multi-key operation (runs atomically in Redis)
rate_limit_script = r.register_script("""
local key = KEYS[1]
local window = tonumber(ARGV[1])
local limit = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

redis.call('ZADD', key, now, now)
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
redis.call('EXPIRE', key, window / 1000 + 1)
local count = redis.call('ZCARD', key)
return count
""")

# Atomically check and record a request
count = rate_limit_script(
    keys=[f'ratelimit:{customer_id}:api'],
    args=[60000, 100, int(time.time() * 1000)]
)
if count > 100:
    raise RateLimitError("Too many requests")
```

Redis vs Memcached vs local in-process cache: Memcached is pure string cache — fast, simple, no persistence, no data structures. Redis is a data structure server with optional persistence (RDB snapshots or AOF log), replication, clustering, and rich data types. A local in-process cache (Python dict, Go sync.Map) has zero latency but doesn't survive restarts and doesn't share state across instances. The practical rule: use Redis when you need shared state across multiple instances (caching, session storage, rate limiting, queues, pub/sub). Use Memcached when you need the absolute minimum cache surface with no persistence. Use in-process caching for single-instance services where sub-millisecond latency matters more than sharing state — often combined with Redis as the backing store.
