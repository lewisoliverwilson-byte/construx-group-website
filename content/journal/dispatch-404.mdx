Environment variables are the standard mechanism for runtime configuration — database URLs, API keys, feature flags. The key distinction in Next.js: some variables are server-only, some are exposed to the browser.

## The Next.js model

**`NEXT_PUBLIC_*`** — exposed to the browser. Baked into the JavaScript bundle at build time. Never put secrets here.

**Everything else** — server-only. Available to Route Handlers, Server Components, middleware, and API routes. Not accessible in Client Components.

```ts
// Safe — public values
process.env.NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY  // public key, fine in browser
process.env.NEXT_PUBLIC_SITE_URL                 // not a secret

// Server-only — never access from client code
process.env.DATABASE_URL           // connection string
process.env.STRIPE_SECRET_KEY      // secret key
process.env.ANTHROPIC_API_KEY      // AI API key
process.env.JWT_SECRET             // session signing key
```

## Validation with Zod at startup

Fail fast when environment variables are misconfigured. Catching a missing `DATABASE_URL` at startup is better than a cryptic error at runtime:

```ts
// lib/env.ts
import { z } from 'zod';

const serverEnvSchema = z.object({
  // Database
  DATABASE_URL: z.string().url(),

  // Auth
  JWT_SECRET: z.string().min(32, 'JWT_SECRET must be at least 32 characters'),
  NEXTAUTH_URL: z.string().url().optional(),

  // Stripe
  STRIPE_SECRET_KEY: z.string().startsWith('sk_'),
  STRIPE_WEBHOOK_SECRET: z.string().startsWith('whsec_'),

  // AI
  ANTHROPIC_API_KEY: z.string().startsWith('sk-ant-'),

  // Email
  RESEND_API_KEY: z.string().startsWith('re_'),

  // Redis (optional)
  UPSTASH_REDIS_REST_URL: z.string().url().optional(),
  UPSTASH_REDIS_REST_TOKEN: z.string().optional(),

  NODE_ENV: z.enum(['development', 'test', 'production']).default('development'),
});

const clientEnvSchema = z.object({
  NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY: z.string().startsWith('pk_'),
  NEXT_PUBLIC_SITE_URL: z.string().url(),
  NEXT_PUBLIC_PUSHER_KEY: z.string().optional(),
});

// Validate at module import time — fails at startup if misconfigured
export const serverEnv = serverEnvSchema.parse(process.env);
export const clientEnv = clientEnvSchema.parse({
  NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY: process.env.NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY,
  NEXT_PUBLIC_SITE_URL: process.env.NEXT_PUBLIC_SITE_URL,
  NEXT_PUBLIC_PUSHER_KEY: process.env.NEXT_PUBLIC_PUSHER_KEY,
});
```

```ts
// Use typed env instead of process.env directly
import { serverEnv } from '@/lib/env';

const stripe = new Stripe(serverEnv.STRIPE_SECRET_KEY);
```

This gives you TypeScript types on every variable and catches missing/malformed values before a request ever fails.

## .env files

```bash
# .env.local — local development, not committed to git
DATABASE_URL="postgresql://localhost:5432/construx_dev"
STRIPE_SECRET_KEY="sk_test_..."

# .env.example — committed to git, documents required variables
DATABASE_URL="postgresql://..."
STRIPE_SECRET_KEY="sk_..."

# .env.production — committed, but only contains non-secret defaults
NEXT_PUBLIC_SITE_URL="https://construxgroup.io"
NODE_ENV="production"
```

`.env.local` is gitignored. `.env.example` is a template that documents every required variable with placeholder values.

## AWS Secrets Manager for production

For production secrets, avoid relying on environment variables in the deployment platform. Use a secrets manager:

```ts
// lib/secrets.ts
import {
  SecretsManagerClient,
  GetSecretValueCommand,
} from '@aws-sdk/client-secrets-manager';

const client = new SecretsManagerClient({ region: process.env.AWS_REGION! });

export async function getSecret(secretId: string): Promise<Record<string, string>> {
  const command = new GetSecretValueCommand({ SecretId: secretId });
  const response = await client.send(command);

  if (!response.SecretString) throw new Error(`Secret ${secretId} has no string value`);
  return JSON.parse(response.SecretString);
}
```

```ts
// At startup — fetch secrets and populate process.env
const secrets = await getSecret('construx/production/app');
Object.assign(process.env, secrets);
```

## Rotation

Secrets should rotate. The pattern: use Secret Manager, set a rotation schedule, update the secret without downtime by supporting both old and new values during the transition window.

```ts
// Graceful rotation — try new key, fall back to old
async function verifyWebhookSignature(body: string, sig: string) {
  const secrets = await getSecret('construx/stripe/webhooks');

  for (const secret of [secrets.current, secrets.previous].filter(Boolean)) {
    try {
      return stripe.webhooks.constructEvent(body, sig, secret);
    } catch { /* try next */ }
  }

  throw new Error('Webhook signature verification failed');
}
```

## Never log secrets

```ts
// Don't do this
logger.info('Database connected', { url: process.env.DATABASE_URL });

// Do this
logger.info('Database connected', { host: new URL(process.env.DATABASE_URL!).hostname });
```

Secrets in logs are secrets in your log aggregator, which is often less secured than your secrets manager. Extract only what you need for debugging — hostnames, config names, version numbers — not the values.
