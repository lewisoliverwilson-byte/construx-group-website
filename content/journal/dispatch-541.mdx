TypeScript with `strict: false` is a type-annotated JavaScript that doesn't enforce much. With `strict: true`, the compiler catches an entire class of runtime bugs at compile time. Enable it on every project from the start — retrofitting is painful.

## What strict mode enables

`strict: true` in `tsconfig.json` is shorthand for:

```json
{
  "compilerOptions": {
    "strict": true
  }
}
```

Which expands to:

```json
{
  "strictNullChecks": true,
  "strictFunctionTypes": true,
  "strictBindCallApply": true,
  "strictPropertyInitialization": true,
  "noImplicitAny": true,
  "noImplicitThis": true,
  "alwaysStrict": true,
  "useUnknownInCatchVariables": true
}
```

Each one catches a distinct category of bug.

## strictNullChecks

The most important one. Without it, `null` and `undefined` are assignable to every type. With it, `null | undefined` must be handled explicitly.

```ts
// Without strictNullChecks — compiles, crashes at runtime
function getUser(id: string): User {
  return db.users.find(u => u.id === id); // returns User | undefined
}
getUser('missing').name; // TypeError: Cannot read property 'name' of undefined

// With strictNullChecks — caught at compile time
function getUser(id: string): User | undefined {
  return db.users.find(u => u.id === id);
}
getUser('missing').name; // Error: Object is possibly 'undefined'

// Fix:
const user = getUser('missing');
if (user) {
  user.name; // safe
}
```

The number of production `Cannot read property of undefined` errors this catches is substantial.

## noImplicitAny

Prevents variables and parameters from silently falling back to `any` when TypeScript can't infer a type.

```ts
// Without noImplicitAny — silently types as any
function process(data) {           // data: any — no error
  return data.whatever.you.want;   // no type checking at all
}

// With noImplicitAny — must annotate
function process(data: unknown) {  // explicit, forces handling
  if (typeof data === 'object' && data !== null && 'value' in data) {
    return (data as { value: string }).value;
  }
}
```

Functions that process external data (API responses, form inputs, event handlers) are where implicit any causes the most damage.

## useUnknownInCatchVariables

Before TypeScript 4.4, caught errors were typed as `any`. With this flag, they're `unknown` — which forces you to actually check what you caught before using it.

```ts
// Old behavior — error is any, this compiles but may crash
try {
  await fetchData();
} catch (error) {
  console.log(error.message); // error is any, no safety
}

// With useUnknownInCatchVariables — error is unknown
try {
  await fetchData();
} catch (error) {
  if (error instanceof Error) {
    console.log(error.message); // safe
  } else {
    console.log(String(error));
  }
}
```

Libraries throw strings, numbers, objects, and `Error` instances. The `unknown` type forces you to handle all of them.

## strictPropertyInitialization

Class properties must be initialized in the constructor or marked as definitely assigned.

```ts
class UserService {
  private db: Database;   // Error: not definitely assigned in constructor

  // Fix 1: initialize in constructor
  constructor(db: Database) {
    this.db = db;
  }

  // Fix 2: definite assignment assertion (use sparingly)
  private db!: Database;  // tell the compiler "I'll handle this"
}
```

This catches the common pattern of declaring class properties without initializing them, which leads to `undefined` at runtime.

## Additional flags worth enabling beyond strict

```json
{
  "noUncheckedIndexedAccess": true,
  "noImplicitReturns": true,
  "exactOptionalPropertyTypes": true,
  "noFallthroughCasesInSwitch": true
}
```

**noUncheckedIndexedAccess** is the most impactful additional flag. Array access and object index access return `T | undefined` instead of `T`:

```ts
const items = ['a', 'b', 'c'];
const first = items[0];  // string | undefined with noUncheckedIndexedAccess
first.toUpperCase();     // Error: possibly undefined
```

This one is not in `strict` because it's a breaking change for most codebases. Enable it on new projects.

**noImplicitReturns** ensures every code path in a function returns a value:

```ts
function getLabel(status: string): string {
  if (status === 'active') return 'Active';
  if (status === 'pending') return 'Pending';
  // Error: not all code paths return a value
}
```

## Enabling strict on an existing codebase

If you're adding strict to an existing project, the suppressions will be extensive. Two approaches:

**Option 1:** Enable strict and use `// @ts-expect-error` to suppress specific errors, then fix them incrementally.

**Option 2:** Use `ts-migrate` to automatically add type assertions and suppression comments across the codebase. You end up with `as any` everywhere but at least strict is on — then clean up over time.

For new files in an existing codebase, you can create a `tsconfig.strict.json` that extends the base config with strict mode, and apply it per-file using path mappings. Clunky but effective for gradual adoption.

## Our setup

Every Construx project starts with:

```json
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noImplicitReturns": true,
    "exactOptionalPropertyTypes": true
  }
}
```

The friction at development time is worth it. Every `undefined` error the compiler catches is one that doesn't reach a user.
