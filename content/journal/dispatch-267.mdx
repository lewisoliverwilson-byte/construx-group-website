Every product in the portfolio uses images: product photos in Scoutr, listing thumbnails in The Marqet, user avatars in The Hyve. Handling them badly means slow pages and layout shift. Handling them well is mostly configuration, not code.

Here's the full picture of how we handle images.

## The Next.js Image component is the right default

`<Image>` from `next/image` gives you:

- Lazy loading by default (images below the fold don't load until needed)
- Automatic WebP/AVIF conversion (smaller file sizes without quality loss)
- Responsive sizing via `srcset` (the browser loads the right size for the screen)
- Cumulative Layout Shift prevention (the browser reserves space for the image before it loads)

These are not trivial to implement correctly from scratch. Use `<Image>` unless you have a specific reason not to.

The reasons not to:
- SVGs (already vector, no format conversion needed, use `<img>`)
- Images where dimensions are unknown at render time and layout shift is acceptable
- Dynamically constructed external URLs that the Next.js image CDN can't optimise

## Configuring external domains

By default, Next.js refuses to optimise images from external domains — a security measure to prevent your image CDN from being used as a free proxy for arbitrary images.

For each external image source, add it to `next.config.ts`:

```ts
const nextConfig: NextConfig = {
  images: {
    remotePatterns: [
      {
        protocol: 'https',
        hostname: 'images-na.ssl-images-amazon.com',
        pathname: '/**',
      },
      {
        protocol: 'https',
        hostname: 'm.media-amazon.com',
        pathname: '/images/**',
      },
      {
        protocol: 'https',
        hostname: '*.ebayimg.com',
        pathname: '/**',
      },
      {
        protocol: 'https',
        hostname: 'storage.construxgroup.io',  // Our S3-backed storage
        pathname: '/**',
      },
    ],
    formats: ['image/avif', 'image/webp'],
    deviceSizes: [640, 750, 828, 1080, 1200, 1920],
    imageSizes: [16, 32, 48, 64, 96, 128, 256, 384],
  },
};
```

The `formats` array controls which formats Next.js generates. AVIF is smaller than WebP but takes longer to encode — for product images that are fetched once and cached, AVIF is a good choice. For avatars that change frequently, WebP is faster.

`deviceSizes` and `imageSizes` control the `srcset` breakpoints. The defaults are reasonable; we add `1920` for full-width hero images.

## The sizes prop

The `sizes` prop is the most commonly omitted `<Image>` attribute, and missing it causes the browser to load images at full screen width even for small thumbnails.

`sizes` is a CSS-like hint to the browser about how wide the image will actually be rendered:

```tsx
{/* Correct — tells the browser this is always a 64px square */}
<Image
  src={user.avatarUrl}
  alt={user.name}
  width={64}
  height={64}
  sizes="64px"
/>

{/* Correct — tells the browser this is full width on mobile, 
    half width on large screens */}
<Image
  src={listing.imageUrl}
  alt={listing.title}
  fill
  sizes="(max-width: 768px) 100vw, 50vw"
/>

{/* Missing sizes — browser loads the image at full viewport width 
    even though it renders at 64px */}
<Image
  src={user.avatarUrl}
  alt={user.name}
  fill  {/* fill requires sizes to be effective */}
/>
```

The `fill` layout mode is for images that should fill their container. It requires the parent to have `position: relative`. Without `sizes`, `fill` images default to viewport width for every breakpoint — loading a 1920px image for what renders as a 64px avatar.

## Blur placeholders for large images

For large above-the-fold images, the `placeholder="blur"` prop shows a blurred low-res version while the full image loads:

```tsx
{/* For local images — Next.js generates the blur automatically */}
import heroImage from '@/public/hero.jpg';

<Image
  src={heroImage}
  alt="Hero"
  placeholder="blur"
  priority
/>
```

```tsx
{/* For remote images — you supply the blurDataURL */}
<Image
  src={listing.imageUrl}
  alt={listing.title}
  placeholder="blur"
  blurDataURL={listing.blurHash}  // Pre-computed and stored in DB
  width={400}
  height={300}
  sizes="(max-width: 768px) 100vw, 400px"
/>
```

We pre-compute blur hashes for listing images when they're scraped and store them in the database. The `blurhash` library generates a compact representation (~30 chars) that can be decoded into a small blurred placeholder on the client.

## Priority loading for above-the-fold images

The browser defers loading images that aren't visible. For the main hero image or the first product image in a list, this causes unnecessary delay — the image is above the fold and the user sees it immediately.

`priority` disables lazy loading for that specific image:

```tsx
<Image
  src={hero}
  alt="Product hero"
  fill
  priority  {/* Loads immediately, not lazily */}
  sizes="100vw"
/>
```

One `priority` image per page — the most important image above the fold. Using it on multiple images defeats the purpose.

## What we measure

Core Web Vitals for images:

- **Largest Contentful Paint (LCP):** how long until the largest visible element loads. For image-heavy pages, this is usually the hero image. Target: under 2.5 seconds.
- **Cumulative Layout Shift (CLS):** unexpected layout movement as images load. Target: under 0.1. The `width`/`height` props on `<Image>` prevent this by reserving space.

We check these in Lighthouse during development and via real-user monitoring in PostHog. An LCP regression from a new image component is usually a missing `priority` or a `sizes` misconfiguration.
