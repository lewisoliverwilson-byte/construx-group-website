React Server Components (RSC) change where components run. Before RSC, all components ran in the browser — the server just sent HTML for the initial render, then React took over. With RSC, some components run exclusively on the server and never reach the browser.

The practical consequence: Server Components can do things that only the server can do.

## What Server Components can do

```tsx
// app/dashboard/page.tsx — a Server Component (default in Next.js App Router)
import { db } from '@/lib/db';
import { getServerSession } from 'next-auth';

export default async function DashboardPage() {
  const session = await getServerSession();
  const posts = await db.post.findMany({
    where: { authorId: session?.user?.id },
    orderBy: { createdAt: 'desc' },
    take: 10,
  });

  return (
    <main>
      {posts.map((post) => (
        <PostCard key={post.id} post={post} />
      ))}
    </main>
  );
}
```

This component queries Postgres directly — no API route needed. The database credentials never leave the server. The component never ships to the client. Zero JavaScript added to the bundle for this component.

## What Server Components can't do

Server Components can't use anything that's only available in the browser:

- `useState`, `useEffect`, or any other React hook that requires a component instance
- Browser APIs (`window`, `document`, `localStorage`)
- Event handlers (`onClick`, `onChange`)
- `useContext` (at the component level)

If you try to use `useState` in a Server Component, you get a build error.

## The 'use client' boundary

`'use client'` marks a component as a Client Component. It runs in the browser.

```tsx
'use client';

import { useState } from 'react';

export function LikeButton({ postId }: { postId: string }) {
  const [liked, setLiked] = useState(false);

  async function handleLike() {
    setLiked(true);
    await fetch(`/api/posts/${postId}/like`, { method: 'POST' });
  }

  return (
    <button onClick={handleLike}>
      {liked ? '♥' : '♡'} Like
    </button>
  );
}
```

`'use client'` is a module-level directive. It's not per-component — every component in the module and every component imported into it becomes a Client Component too.

## The composition pattern

Server Components can render Client Components. Client Components can't render Server Components (directly), but can render Server Components as `children`.

```tsx
// Server Component — queries data, renders Client Component
async function PostPage({ postId }: { postId: string }) {
  const post = await db.post.findUnique({ where: { id: postId } });

  return (
    <article>
      <h1>{post.title}</h1>
      <PostContent content={post.content} />
      <LikeButton postId={postId} />  {/* Client Component */}
    </article>
  );
}
```

```tsx
'use client';

// Client Component — can accept Server Component children
export function Sidebar({ children }: { children: React.ReactNode }) {
  const [open, setOpen] = useState(false);
  return (
    <aside>
      <button onClick={() => setOpen(!open)}>Toggle</button>
      {open && children}  {/* children can be Server Components */}
    </aside>
  );
}
```

The pattern: push the `'use client'` boundary as deep as possible. The more of your component tree that runs on the server, the less JavaScript ships to the client.

## What this replaces

In the Pages Router, the pattern for fetching data was `getServerSideProps` or `getStaticProps` — functions that run on the server and pass data to the page component as props. The page itself ran on both server and client.

In the App Router with RSC, you just `await` the data directly in the component. No special functions, no prop drilling from the data-fetching layer to the UI layer. The component is the data-fetching layer.

```tsx
// Pages Router — old pattern
export async function getServerSideProps() {
  const posts = await fetchPosts();
  return { props: { posts } };
}
export default function Page({ posts }) { ... }

// App Router — new pattern
export default async function Page() {
  const posts = await fetchPosts(); // directly in the component
  return ...;
}
```

## Caching in Server Components

Next.js caches `fetch()` calls in Server Components by default. Two components that `fetch()` the same URL get the same cached response within a request.

```tsx
async function UserAvatar({ userId }: { userId: string }) {
  const user = await fetch(`/api/users/${userId}`).then(r => r.json());
  return <img src={user.avatar} />;
}

async function UserName({ userId }: { userId: string }) {
  const user = await fetch(`/api/users/${userId}`).then(r => r.json());
  return <span>{user.name}</span>;
}
```

Both components request the same URL. Next.js deduplicates the request — one HTTP call, shared result. No need to lift state or pass the user object as a prop.

## The mental model

Server Components handle data access and layout. Client Components handle interactivity.

The boundary between them should be at the leaf of the component tree — individual buttons, inputs, charts — not at the page level. If the entire page is a Client Component, you've replicated the Pages Router pattern and gained nothing.

The goal: static structure and data-driven content rendered on the server with zero client JavaScript, interactive islands (forms, dropdowns, modals) rendered as Client Components only where necessary.
