title: "KEDA: Kubernetes event-driven autoscaling from Kafka lag to scale-to-zero"
date: "2033-04-10"
excerpt: "KEDA (Kubernetes Event-driven Autoscaling) extends the Kubernetes HPA to scale workloads based on external event sources — Kafka consumer group lag, Redis queue depth, Prometheus metrics, RabbitMQ queue length, HTTP request rate, cron schedules, and dozens more. The key capability KEDA adds over the standard HPA is scale-to-zero: a deployment can drop to zero replicas when there is nothing to process, and wake on the first incoming event. For event-driven workloads (Kafka consumers, queue workers, batch processors), this eliminates the baseline compute cost of keeping a minimum number of replicas alive. The scaling decision happens in the KEDA ScaledObject controller, which reads from the scaler backend, computes the desired replica count, and updates the HPA target — standard Kubernetes scaling machinery handles the actual pod creation."

## ScaledObject and TriggerAuthentication

```yaml
# ScaledObject: binds a Kubernetes Deployment to KEDA triggers
# KEDA reads the trigger metrics, computes replicas, updates the HPA

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: construx-api-scaler
  namespace: construx-prod
spec:
  scaleTargetRef:
    name: construx-api        # the Deployment to scale
  minReplicaCount: 0          # scale to zero when no events
  maxReplicaCount: 20
  pollingInterval: 15         # check trigger every 15s
  cooldownPeriod:  30         # wait 30s before scaling down

  triggers:
    # Trigger 1: scale on Kafka consumer group lag
    - type: kafka
      metadata:
        bootstrapServers: redpanda.messaging.svc:9092
        consumerGroup: benthos-event-processor
        topic: construx.events
        lagThreshold: "1000"    # 1 replica per 1000 messages of lag
        offsetResetPolicy: latest
      authenticationRef:
        name: kafka-trigger-auth

    # Trigger 2: scale on Prometheus metric
    - type: prometheus
      metadata:
        serverAddress: http://thanos-query.monitoring.svc:9090
        metricName: http_requests_per_second
        threshold: "50"         # 1 replica per 50 req/s
        query: sum(rate(http_requests_total{namespace="construx-prod",service="construx-api"}[1m]))

---
# TriggerAuthentication: credentials for the trigger backend
# Keeps auth config out of the ScaledObject (can be shared across scalers)

apiVersion: keda.sh/v1alpha1
kind: TriggerAuthentication
metadata:
  name: kafka-trigger-auth
  namespace: construx-prod
spec:
  secretTargetRef:
    - parameter: sasl.username
      name: redpanda-credentials   # Kubernetes Secret
      key: username
    - parameter: sasl.password
      name: redpanda-credentials
      key: password
    - parameter: tls.ca
      name: redpanda-tls
      key: ca.crt
```

## Scale-to-zero: queue workers

```yaml
# Scale-to-zero: the email sender drops to 0 replicas when the queue is empty
# KEDA polls the queue depth; when a message arrives, it wakes the deployment

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: email-sender-scaler
  namespace: construx-prod
spec:
  scaleTargetRef:
    name: email-sender
  minReplicaCount: 0        # true zero — no pods running when idle
  maxReplicaCount: 5
  pollingInterval: 10
  cooldownPeriod: 60        # stay up 60s after queue empties (batching window)

  triggers:
    - type: rabbitmq
      metadata:
        protocol: amqp
        queueName: construx.email-queue
        mode: QueueLength
        value: "1"          # 1 replica per message (burst-capable)
        host: amqp://rabbitmq.messaging.svc:5672/
      authenticationRef:
        name: rabbitmq-auth

---
# Cold start concern: email-sender takes ~2.1s to start
# Mitigation: set cooldownPeriod to keep replicas up for at least 60s
# after the last message — avoids thrashing if messages arrive in bursts

# Observe scaling decisions
# kubectl get hpa -n construx-prod
# NAME                            REFERENCE              TARGETS           MINPODS  MAXPODS  REPLICAS
# keda-hpa-email-sender-scaler    Deployment/email-sender   0/1 (avg)     1        5        0
# keda-hpa-construx-api-scaler    Deployment/construx-api   4218/1000     1        20       8

kubectl get scaledobject -n construx-prod
# NAME                    SCALETARGETKIND    SCALETARGETNAME   MIN  MAX  TRIGGERS     READY
# construx-api-scaler     apps/Deployment    construx-api      0    20   kafka,prom   True
# email-sender-scaler     apps/Deployment    email-sender      0    5    rabbitmq     True
```

## Cron and Redis triggers

```yaml
# Cron trigger: scale up at known busy periods regardless of queue depth
# Use with a Kafka trigger: whichever gives higher replica count wins

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: worker-scaler
  namespace: construx-prod
spec:
  scaleTargetRef:
    name: construx-worker
  minReplicaCount: 1
  maxReplicaCount: 50

  triggers:
    # Redis: scale on list length (job queue)
    - type: redis
      metadata:
        address: dragonfly.cache.svc:6379
        listName: construx:job-queue
        listLength: "10"    # 1 replica per 10 queued jobs
      authenticationRef:
        name: redis-trigger-auth

    # Cron: pre-scale for predictable load spikes
    # Scale to 10 replicas Mon-Fri 08:00-10:00 UTC regardless of queue
    - type: cron
      metadata:
        timezone: Europe/London
        start: "0 8 * * 1-5"    # 08:00 Mon-Fri
        end:   "0 10 * * 1-5"   # 10:00 Mon-Fri
        desiredReplicas: "10"

---
# ScaledJob: for batch workloads — create a new Job per event batch
# Useful when each message should be processed by its own Job pod

apiVersion: keda.sh/v1alpha1
kind: ScaledJob
metadata:
  name: report-generator
  namespace: construx-prod
spec:
  jobTargetRef:
    template:
      spec:
        containers:
          - name: report-gen
            image: construx/report-generator:latest
            args: ["--mode=batch"]
        restartPolicy: Never
  triggers:
    - type: kafka
      metadata:
        bootstrapServers: redpanda.messaging.svc:9092
        consumerGroup: report-generator
        topic: construx.report-requests
        lagThreshold: "1"   # 1 Job per message
```

KEDA vs HPA vs KEDA + HPA vs VPA: The standard HPA scales on CPU/memory — which correlates poorly with event-driven workloads (a Kafka consumer at 0% CPU might have 50k messages of lag). KEDA adds external metric sources to the HPA, making lag/queue-depth the primary scaling signal. VPA (Vertical Pod Autoscaler) adjusts resource requests per pod rather than replica count — it's orthogonal to KEDA and can be used together. The scale-to-zero capability is the headline feature: a standard HPA has a minimum of 1 replica, which means idle queue workers still consume cluster capacity. KEDA removes that floor, making event-driven architectures genuinely cost-proportional to load.
