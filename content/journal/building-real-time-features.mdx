The Hyve's core feature is real-time team channels — a shared workspace where messages appear instantly, AI responses stream in, and documents update live as collaborators edit them. Building this requires handling state that changes unpredictably, from multiple sources, at unknown intervals.

The naive approach is "add WebSockets to everything real-time." This works but overengineers most of it. Here's what we found actually requires WebSockets and what doesn't.

## What WebSockets are for

WebSockets provide a persistent bidirectional connection between client and server. The server can push data to the client at any time without the client having to request it. This is the critical property.

You need WebSockets when:
- The server needs to push updates to the client without a preceding request
- Updates are frequent enough that polling would create unacceptable latency or load
- Bidirectionality matters (client and server both initiate messages)

You don't need WebSockets when:
- Updates are infrequent (occasional poll is simpler and cheaper)
- The server only ever responds to client requests
- You can tolerate seconds of latency

The Hyve has a mix. Not everything that looks real-time requires WebSockets.

## Channel messages: WebSockets are the right call

The core team channels — where messages are sent and received instantly — genuinely require WebSockets. When a user sends a message, everyone in the channel needs to see it within a fraction of a second. Polling with 1-second intervals would feel broken. Polling with 100ms intervals would generate enormous load for marginal improvement.

The implementation: a persistent WebSocket connection per channel session. When a user joins a channel, a connection is established. Messages are broadcast to all connections in the channel immediately.

Connection management is the hard part. WebSocket connections drop — on mobile, when tabs go to background, on network changes. Every client needs to:
1. Detect disconnection
2. Queue any messages sent while disconnected
3. Reconnect automatically
4. Reconcile the local state with server state after reconnection

The reconnection and reconciliation logic is non-trivial. Most real-time systems that feel buggy are failing at step 3 or 4 — they reconnect but don't correctly replay what happened while the connection was down.

## AI response streaming: Server-Sent Events, not WebSockets

When the AI team member responds to a message in a Hyve channel, the response streams in token by token — like watching Claude type in real time. This creates the impression of a fast, alive AI rather than a spinner followed by a wall of text.

The implementation is Server-Sent Events (SSE), not WebSockets. SSE is a one-directional stream from server to client over a standard HTTP connection. The client connects to an endpoint and the server keeps the connection open, pushing tokens as they arrive from the Claude API.

Why SSE instead of WebSockets for streaming?

1. **Simpler implementation.** SSE is standard HTTP. No upgrade negotiation, no WebSocket protocol handling. The browser has native support for EventSource.

2. **Right shape for the problem.** AI streaming is unidirectional: server pushes tokens to client. WebSockets allow bidirectionality that we don't need for streaming responses.

3. **Better infrastructure compatibility.** SSE works through standard HTTP infrastructure without special configuration. WebSockets require WebSocket-aware proxies and load balancers.

The Claude API returns a streaming response when you set `stream: true`. We pipe that stream to the SSE connection, transforming each token event into an SSE message. The client appends each token to the display.

## Document collaboration: polling with optimistic updates

The Hyve's shared documents are collaborative — multiple users can edit the same document. This sounds like it requires WebSockets (Google Docs-style live cursors and simultaneous editing). For our initial implementation, it doesn't.

We use optimistic updates with polling:

1. When a user edits a document, the change is applied locally immediately (optimistic update).
2. The change is sent to the server via a standard HTTP PATCH request.
3. Every 3 seconds, the client polls for changes from other users.
4. If a server-side change conflicts with a local change, the server version wins.

At the team sizes The Hyve targets, simultaneous document edits are rare enough that polling works. The 3-second poll interval is usually imperceptible — the last person to edit "wins" without users noticing the mechanism.

The optimistic update is what makes this feel responsive. The user's own changes appear instantly because they're applied before the server confirms receipt. This is correct behavior 99% of the time; the 1% where the server rejects the change is handled with a gentle error indicator.

We'll move to a proper CRDT-based real-time collaboration when actual usage shows that 3-second polling is causing friction. That hasn't happened yet.

## Kanban boards: event-driven with WebSockets

The kanban boards — task tracking, status updates, board membership — use WebSockets but with a different pattern than the channels. Rather than broadcasting every state change to everyone, the kanban system broadcasts only events:

- "Task X moved to column Y by user Z"
- "Task X assigned to user Z"
- "New task created: [task]"

The client maintains local state and applies events as they arrive. This is more efficient than broadcasting full state on every change — at scale, the difference between broadcasting events and broadcasting state matters.

This event-driven pattern also makes it easier to build the activity log (a chronological list of everything that happened to a board), since events are naturally a log.

## What we chose not to build

The most obvious missing feature in real-time collaboration is live cursors — seeing where other users are currently editing in a document. We chose not to implement this.

Live cursors require transmitting cursor position updates at very high frequency (every mouse move), which is bandwidth-intensive. They add significant complexity to the client state management. And in practice, for documents rather than code editors, knowing where someone else's cursor is is rarely useful.

"I can see Dan is editing the introduction" is useful information. "Dan's cursor is at line 17, column 43" is not, unless you're building a code editor.

Same with presence indicators — real-time dots showing who's actively online. We show whether someone was active recently (within the last 15 minutes), updated when they send a message or join a channel. Not a continuous heartbeat that tracks whether a tab is in the foreground.

## The operational reality

Real-time features have higher operational complexity than standard request-response endpoints. Persistent connections need to be monitored — connection count, connection lifetime, message throughput. WebSocket infrastructure doesn't degrade gracefully the way stateless HTTP does.

At The Hyve's current scale, this is manageable. At 10x current scale, dedicated WebSocket infrastructure with proper horizontal scaling becomes necessary. We've designed for this (stateless message routing, external message broker rather than in-process state) without prematurely building it.

The lesson from building this: start with the simplest thing that produces the right user experience. SSE where streaming is needed. Polling where latency tolerance allows. WebSockets only where you genuinely need the server to initiate communication. Don't add complexity you haven't earned.
