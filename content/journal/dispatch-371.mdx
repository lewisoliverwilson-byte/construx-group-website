Some work shouldn't happen in a request-response cycle. Sending emails, generating PDFs, processing uploads, syncing data from external APIs, running ML inference — these either take too long, need retries on failure, or need to run on a schedule. That's background jobs.

## The options in Next.js

| Option | Best for | Infra required |
|--------|----------|----------------|
| Trigger.dev | Durable multi-step workflows, human-in-the-loop | None (managed) |
| Inngest | Event-driven jobs, fan-out patterns | None (managed) |
| BullMQ | High-throughput queues, priority jobs | Redis |
| Vercel Cron | Simple scheduled jobs, no complex logic | None |

## Trigger.dev: durable workflows

Trigger.dev runs long tasks reliably — the task can wait for external events, pause and resume, and retry individual steps:

```ts
// trigger/send-welcome-sequence.ts
import { task, wait, retry } from "@trigger.dev/sdk/v3";
import { sendEmail } from "@/lib/email";
import { db } from "@/db";

export const welcomeSequence = task({
  id: "welcome-sequence",
  run: async (payload: { userId: string }) => {
    const user = await db.query.users.findFirst({
      where: eq(users.id, payload.userId),
    });

    // Day 0: welcome email
    await sendEmail({ to: user!.email, template: "welcome", data: { name: user!.name } });

    // Wait 3 days, then send a follow-up
    await wait.for({ days: 3 });

    // Day 3: onboarding tips
    await sendEmail({ to: user!.email, template: "tips", data: { name: user!.name } });

    // Wait 4 more days
    await wait.for({ days: 4 });

    // Day 7: check if they've activated
    const activated = await db.query.users.findFirst({
      where: and(eq(users.id, payload.userId), isNotNull(users.activatedAt)),
    });

    if (!activated) {
      await sendEmail({ to: user!.email, template: "activation-nudge", data: {} });
    }
  },
});
```

```ts
// Trigger from an API route or Server Action
import { welcomeSequence } from "@/trigger/send-welcome-sequence";

await welcomeSequence.trigger({ userId: newUser.id });
```

The `wait.for` call actually pauses execution — no polling, no cron job to manage. Trigger.dev resumes the function exactly when the wait completes.

## Inngest: event-driven jobs

Inngest models work as functions that respond to events:

```ts
// inngest/functions.ts
import { inngest } from "@/lib/inngest";

export const processUpload = inngest.createFunction(
  {
    id: "process-upload",
    retries: 3,
    throttle: {
      limit: 10,
      period: "1m",  // max 10 uploads per minute
    },
  },
  { event: "upload/completed" },
  async ({ event, step }) => {
    const { fileKey, userId } = event.data;

    // Each step is retried independently on failure
    const metadata = await step.run("extract-metadata", async () => {
      return extractFileMetadata(fileKey);
    });

    await step.run("generate-thumbnail", async () => {
      return generateThumbnail(fileKey, metadata.dimensions);
    });

    await step.run("update-database", async () => {
      return db.update(uploads)
        .set({ status: "processed", metadata })
        .where(eq(uploads.fileKey, fileKey));
    });

    await step.run("notify-user", async () => {
      return sendNotification(userId, "Your upload is ready");
    });
  }
);
```

```ts
// lib/inngest.ts
import { Inngest } from "inngest";
export const inngest = new Inngest({ id: "construx-app" });
```

```ts
// app/api/inngest/route.ts — the Inngest serving endpoint
import { serve } from "inngest/next";
import { inngest } from "@/lib/inngest";
import { processUpload } from "@/inngest/functions";

export const { GET, POST, PUT } = serve({ client: inngest, functions: [processUpload] });
```

```ts
// Emit an event from anywhere
await inngest.send({
  name: "upload/completed",
  data: { fileKey: "uploads/user-123/file.pdf", userId: "user-123" },
});
```

## BullMQ: Redis-backed queues

For high-throughput work where you control the infrastructure:

```ts
// lib/queue.ts
import { Queue, Worker } from "bullmq";
import IORedis from "ioredis";

const connection = new IORedis(process.env.REDIS_URL!, { maxRetriesPerRequest: null });

export const emailQueue = new Queue("emails", { connection });

// Worker (runs in a separate process, not a serverless function)
export const emailWorker = new Worker(
  "emails",
  async (job) => {
    const { to, template, data } = job.data;
    await sendEmail({ to, template, data });
  },
  {
    connection,
    concurrency: 5,  // process 5 jobs simultaneously
  }
);

emailWorker.on("failed", (job, err) => {
  console.error(`Email job ${job?.id} failed:`, err);
});
```

```ts
// Add jobs to the queue
await emailQueue.add(
  "welcome",
  { to: "user@example.com", template: "welcome", data: { name: "Alice" } },
  {
    attempts: 3,
    backoff: { type: "exponential", delay: 1000 },
    delay: 0,
  }
);

// Scheduled job: runs in 24 hours
await emailQueue.add(
  "follow-up",
  { to: "user@example.com", template: "day-1", data: {} },
  { delay: 24 * 60 * 60 * 1000 }
);
```

BullMQ requires a long-running worker process — it doesn't fit serverless. Run it as a separate service alongside your Next.js app.

## Vercel Cron: scheduled jobs

For simple, predictable scheduled work:

```ts
// app/api/cron/sync-metrics/route.ts
import { NextRequest } from "next/server";

export async function GET(req: NextRequest) {
  // Verify the request is from Vercel
  const authHeader = req.headers.get("authorization");
  if (authHeader !== `Bearer ${process.env.CRON_SECRET}`) {
    return new Response("Unauthorized", { status: 401 });
  }

  await syncMetricsFromAnalytics();
  await updateLeaderboard();

  return Response.json({ ok: true, timestamp: new Date().toISOString() });
}
```

```json
// vercel.json
{
  "crons": [
    {
      "path": "/api/cron/sync-metrics",
      "schedule": "0 * * * *"
    }
  ]
}
```

Always authenticate Vercel Cron requests — the endpoint is publicly accessible without the check.

## Idempotency: the non-negotiable rule

Every background job must be safe to run multiple times with the same input. Networks fail, servers restart, queues redeliver:

```ts
export const processInvoice = inngest.createFunction(
  { id: "process-invoice" },
  { event: "invoice/created" },
  async ({ event, step }) => {
    const { invoiceId } = event.data;

    await step.run("mark-processing", async () => {
      // Use upsert — safe to run twice
      await db.insert(invoiceJobs)
        .values({ invoiceId, status: "processing", startedAt: new Date() })
        .onConflictDoUpdate({
          target: invoiceJobs.invoiceId,
          set: { status: "processing", startedAt: new Date() },
        });
    });

    await step.run("charge-customer", async () => {
      // Check if already charged before charging
      const existing = await stripe.paymentIntents.search({
        query: `metadata["invoiceId"]:"${invoiceId}"`,
      });
      if (existing.data.length > 0) return existing.data[0];  // already done

      return stripe.paymentIntents.create({
        amount: invoice.amountCents,
        currency: "gbp",
        metadata: { invoiceId },
      });
    });
  }
);
```

## When to use each

- **Trigger.dev**: multi-step workflows with waits (email sequences, approval flows, anything that spans days)
- **Inngest**: event-driven fan-out, upload processing, anything webhook-triggered
- **BullMQ**: high-throughput, priority queues, jobs that must run in order
- **Vercel Cron**: data sync, cache warming, anything that runs on a schedule and is stateless
