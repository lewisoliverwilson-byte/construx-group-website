Stripe's webhook system is reliable but assumes your endpoint can fail. If your handler returns a non-2xx status, Stripe retries the webhook with exponential backoff over 72 hours. This makes your handler's idempotency correctness critical — a flaky endpoint that processes events twice causes duplicate subscriptions, double-charges, or corrupted state.

## The basic handler structure

```ts
// app/api/webhooks/stripe/route.ts
import Stripe from 'stripe';
import { headers } from 'next/headers';

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY!);

export async function POST(req: Request) {
  const body      = await req.text();
  const signature = headers().get('stripe-signature') ?? '';

  let event: Stripe.Event;
  try {
    event = stripe.webhooks.constructEvent(
      body,
      signature,
      process.env.STRIPE_WEBHOOK_SECRET!,
    );
  } catch (err) {
    return Response.json({ error: 'Invalid signature' }, { status: 400 });
  }

  await handleEvent(event);
  return Response.json({ received: true });
}
```

Always verify the webhook signature. A POST to your webhook endpoint without a valid signature should be rejected. Never skip this step.

## Idempotency via event ID tracking

Track processed event IDs to make your handler idempotent:

```sql
CREATE TABLE stripe_events (
  id         TEXT PRIMARY KEY,              -- Stripe event ID
  type       TEXT NOT NULL,
  processed_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

```ts
async function handleEvent(event: Stripe.Event) {
  // Idempotency check
  const existing = await db.query.stripeEvents.findFirst({
    where: eq(stripeEvents.id, event.id),
  });
  if (existing) return; // already processed, skip

  // Process the event
  await processEvent(event);

  // Mark as processed
  await db.insert(stripeEvents).values({ id: event.id, type: event.type });
}
```

The check-then-insert is not atomic in a basic implementation — two concurrent webhook deliveries of the same event could both pass the check before either inserts. Fix with an upsert or a database constraint:

```ts
// Upsert with conflict handling
try {
  await db.insert(stripeEvents).values({ id: event.id, type: event.type });
} catch (err) {
  if (isUniqueViolation(err)) return; // already processed
  throw err;
}

// Then process the event
await processEvent(event);
```

Insert first, process second. If the insert conflicts, it was already processed. If the insert succeeds but processing fails, Stripe will retry — the insert record will be there on retry, causing it to be skipped. This is acceptable for most events; for events that must not be dropped, remove the record on failure and let Stripe retry.

## Event routing

```ts
async function processEvent(event: Stripe.Event) {
  switch (event.type) {
    case 'checkout.session.completed':
      await handleCheckoutCompleted(event.data.object as Stripe.Checkout.Session);
      break;

    case 'customer.subscription.created':
      await handleSubscriptionCreated(event.data.object as Stripe.Subscription);
      break;

    case 'customer.subscription.deleted':
      await handleSubscriptionDeleted(event.data.object as Stripe.Subscription);
      break;

    case 'invoice.payment_failed':
      await handlePaymentFailed(event.data.object as Stripe.Invoice);
      break;

    default:
      // Unhandled event types — log and ignore
      console.log(`Unhandled event type: ${event.type}`);
  }
}
```

## Handling subscription state correctly

```ts
async function handleSubscriptionCreated(subscription: Stripe.Subscription) {
  const customerId = subscription.customer as string;
  const customer   = await stripe.customers.retrieve(customerId);

  if (customer.deleted) return;

  const userId = customer.metadata.userId;
  if (!userId) throw new Error(`No userId in customer metadata: ${customerId}`);

  const plan  = subscription.items.data[0]?.price?.lookup_key ?? 'unknown';
  const until = new Date(subscription.current_period_end * 1000);

  await db.update(users)
    .set({ plan, subscriptionId: subscription.id, subscriptionUntil: until })
    .where(eq(users.id, userId));
}

async function handleSubscriptionDeleted(subscription: Stripe.Subscription) {
  await db.update(users)
    .set({ plan: 'free', subscriptionId: null, subscriptionUntil: null })
    .where(eq(users.subscriptionId, subscription.id));
}
```

Store the `userId` in Stripe customer metadata when creating the customer. This lets you look up the right user in your database without needing a mapping table.

```ts
// When creating a Stripe customer:
const customer = await stripe.customers.create({
  email:    user.email,
  metadata: { userId: user.id },
});
```

## Timeout and async processing

Your webhook handler must respond within 30 seconds. For events that trigger long-running operations (sending emails, generating reports, updating many records), process the event asynchronously:

```ts
case 'checkout.session.completed': {
  const session = event.data.object as Stripe.Checkout.Session;
  // Enqueue for async processing — respond 200 immediately
  await queue.add('stripe.checkout.completed', { sessionId: session.id });
  break;
}
```

The queue worker does the heavy lifting. The webhook handler just validates, records, and enqueues — it always returns 200 within milliseconds.

## What we run

Construx's products use the same pattern: idempotency table, upsert-first, async queue for slow operations. The webhook endpoint has responded 200 to every Stripe event since launch — no retries needed, no duplicate state.

The one edge case: Stripe sends `invoice.payment_succeeded` and `customer.subscription.updated` together when a subscription renews. Both handlers update the `subscriptionUntil` date. With idempotent upserts and the last-write-wins pattern, this is safe — whichever lands second writes the same value.
