The serverless constraint is a feature, not a bug: no process management, no scaling concerns, cost proportional to usage. But it comes with a hard limit: requests time out. Vercel's maximum is 300 seconds. Amplify's Lambda functions default to 30 seconds.

Any operation that can't complete in that window needs a different model.

## The patterns

**Fire-and-forget with a queue.** The API route enqueues a job and returns immediately. A worker processes the job asynchronously. Correct for: sending emails, generating reports, running AI batch jobs.

**Scheduled crons.** A cron triggers a job on a schedule, independently of user requests. Correct for: daily digest emails, cleanup jobs, syncing external data, building precomputed indexes.

**Chunked processing.** A large job is split into smaller jobs, each small enough to fit within the timeout. Correct for: batch processing large datasets, generating many AI completions in parallel.

## Queue-based jobs

For queue-based background work without a dedicated queue service, the database is sufficient for small to medium scale:

```sql
CREATE TABLE job_queue (
  id          BIGSERIAL PRIMARY KEY,
  type        TEXT NOT NULL,
  payload     JSONB NOT NULL,
  status      TEXT NOT NULL DEFAULT 'pending',
  attempts    INT NOT NULL DEFAULT 0,
  max_attempts INT NOT NULL DEFAULT 3,
  scheduled_for TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  started_at  TIMESTAMPTZ,
  completed_at TIMESTAMPTZ,
  failed_at   TIMESTAMPTZ,
  error       TEXT,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_job_queue_pending
  ON job_queue (scheduled_for, status)
  WHERE status = 'pending';
```

The enqueue function:

```ts
// lib/jobs.ts
export async function enqueue<T extends Record<string, unknown>>(
  type: string,
  payload: T,
  options?: { delayMs?: number },
): Promise<void> {
  const scheduledFor = options?.delayMs
    ? new Date(Date.now() + options.delayMs)
    : new Date();

  await db.insert(jobQueue).values({ type, payload, scheduledFor });
}
```

Usage from a route handler:

```ts
// app/api/scan/route.ts
export async function POST(req: Request) {
  const session = await getSession();
  const { asin } = await req.json();

  // Run the fast part synchronously
  const scanResult = await runScan(asin);

  // Enqueue the slow AI enrichment
  await enqueue('ai-enrich-scan', {
    scanId: scanResult.id,
    asin,
    userId: session.userId,
  });

  // Return immediately — don't wait for enrichment
  return Response.json({ ...scanResult, enrichmentPending: true });
}
```

The worker polls the queue on a cron:

```ts
// app/api/cron/process-jobs/route.ts
export async function GET(req: Request) {
  const authHeader = req.headers.get('authorization');
  if (authHeader !== `Bearer ${process.env.CRON_SECRET}`) {
    return new Response('Unauthorized', { status: 401 });
  }

  // Claim up to 10 pending jobs atomically
  const jobs = await db.execute(sql`
    UPDATE job_queue
    SET status = 'running', started_at = NOW(), attempts = attempts + 1
    WHERE id IN (
      SELECT id FROM job_queue
      WHERE status = 'pending'
        AND scheduled_for <= NOW()
        AND attempts < max_attempts
      ORDER BY scheduled_for
      LIMIT 10
      FOR UPDATE SKIP LOCKED
    )
    RETURNING *
  `);

  for (const job of jobs.rows) {
    try {
      await processJob(job);
      await db.execute(sql`
        UPDATE job_queue SET status = 'completed', completed_at = NOW()
        WHERE id = ${job.id}
      `);
    } catch (err) {
      const failed = job.attempts >= job.max_attempts;
      await db.execute(sql`
        UPDATE job_queue
        SET status = ${failed ? 'failed' : 'pending'},
            failed_at = ${failed ? sql`NOW()` : null},
            error = ${err instanceof Error ? err.message : 'Unknown error'}
        WHERE id = ${job.id}
      `);
    }
  }

  return Response.json({ processed: jobs.rows.length });
}
```

The `FOR UPDATE SKIP LOCKED` is the key: multiple worker invocations can run safely in parallel without double-processing a job.

## Scheduled crons on Amplify

AWS Amplify Gen 2 supports scheduled functions via CDK constructs:

```ts
// amplify/backend.ts
import { defineBackend } from '@aws-amplify/backend';
import { Function, Schedule } from 'aws-cdk-lib/aws-lambda';
import { Rule } from 'aws-cdk-lib/aws-events';
import { LambdaFunction } from 'aws-cdk-lib/aws-events-targets';

const backend = defineBackend({});

// Create a scheduled rule that hits our cron endpoint every minute
const cronRule = new Rule(backend.stack, 'ProcessJobsCron', {
  schedule: Schedule.rate(Duration.minutes(1)),
});

cronRule.addTarget(
  new HttpsEndpointTarget({
    url: `${process.env.NEXT_PUBLIC_SITE_URL}/api/cron/process-jobs`,
    headers: {
      Authorization: `Bearer ${process.env.CRON_SECRET}`,
    },
  })
);
```

On Vercel, `vercel.json` supports cron configuration:

```json
{
  "crons": [
    {
      "path": "/api/cron/process-jobs",
      "schedule": "* * * * *"
    }
  ]
}
```

## Chunked processing for large datasets

When a job is genuinely too large for one invocation, chunk it. A "start batch" job creates individual item jobs; the worker processes items independently:

```ts
async function processJob(job: JobRecord) {
  if (job.type === 'portfolio-margin-refresh') {
    // This job creates sub-jobs for each portfolio item
    const items = await db.select().from(portfolioItems)
      .where(eq(portfolioItems.userId, job.payload.userId));

    for (const item of items) {
      await enqueue('refresh-single-item-margin', {
        itemId: item.id,
        asin: item.asin,
      });
    }
    return;
  }

  if (job.type === 'refresh-single-item-margin') {
    const scan = await runScan(job.payload.asin);
    await db.update(portfolioItems)
      .set({ margin: scan.margin, lastRefreshedAt: new Date() })
      .where(eq(portfolioItems.id, job.payload.itemId));
    return;
  }

  throw new Error(`Unknown job type: ${job.type}`);
}
```

Each individual item scan completes in well under the timeout. The entire portfolio refreshes across many parallel invocations.

## When to use a dedicated queue service

The database queue approach works until it doesn't. The signals to move to a dedicated queue (SQS, BullMQ, Inngest):

- **High job volume**: polling a database every minute for jobs adds load. At thousands of jobs per hour, a purpose-built queue is more efficient.
- **Retry semantics**: the database queue has basic retry logic. Inngest and BullMQ give you exponential backoff, dead-letter queues, and fan-out patterns without writing the infrastructure.
- **Real-time processing**: database polling has up to a 60-second lag. SQS triggers Lambda on message arrival — no polling delay.

For early products, the database queue is the right call. It's one less dependency, it uses infrastructure you already have, and it's easy to inspect (it's just a table).
