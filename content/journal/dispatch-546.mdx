Rate limiting is easy to add and easy to get wrong. A fixed-window counter (100 requests per minute) can be burst-abused: 100 requests at 00:59, 100 more at 01:01 — 200 requests in two seconds, neither window triggers the limit. The sliding window algorithm fixes this.

## Sliding window with Redis

```ts
// lib/rate-limit.ts
import { Redis } from '@upstash/redis';

const redis = Redis.fromEnv();

export interface RateLimitResult {
  success:   boolean;
  limit:     number;
  remaining: number;
  reset:     number; // Unix timestamp ms
}

export async function rateLimit(
  identifier: string,
  { limit = 60, window = 60 }: { limit?: number; window?: number } = {},
): Promise<RateLimitResult> {
  const now      = Date.now();
  const key      = `rl:${identifier}`;
  const windowMs = window * 1000;

  const [count] = await redis
    .pipeline()
    .zremrangebyscore(key, 0, now - windowMs)   // remove expired entries
    .zadd(key, { score: now, member: `${now}-${Math.random()}` })
    .zcard(key)
    .expire(key, window + 1)
    .exec<[number, number, number, number]>();

  const current  = count ?? 0;
  const success  = current <= limit;
  const reset    = now + windowMs;

  return {
    success,
    limit,
    remaining: Math.max(0, limit - current),
    reset,
  };
}
```

The sliding window uses a Redis sorted set where each request is a member with a score of the current timestamp. On each request, we remove entries older than the window, add the new entry, and count. The count tells us how many requests have happened in the last N seconds — a true sliding window.

## Applying rate limits in Next.js middleware

```ts
// middleware.ts
import { rateLimit } from '@/lib/rate-limit';
import { NextRequest, NextResponse } from 'next/server';

const LIMITS: Record<string, { limit: number; window: number }> = {
  '/api/contact':  { limit: 5,   window: 3600 }, // 5 per hour (contact form)
  '/api/auth':     { limit: 20,  window: 900  }, // 20 per 15min (login)
  '/api/search':   { limit: 100, window: 60   }, // 100 per minute (search)
  'default':       { limit: 300, window: 60   }, // 300 per minute (everything else)
};

export async function middleware(req: NextRequest) {
  if (!req.nextUrl.pathname.startsWith('/api')) {
    return NextResponse.next();
  }

  const ip        = req.ip ?? req.headers.get('x-forwarded-for') ?? 'unknown';
  const path      = req.nextUrl.pathname;
  const config    = LIMITS[path] ?? LIMITS.default;
  const identifier = `${ip}:${path}`;

  const result = await rateLimit(identifier, config);

  const res = result.success
    ? NextResponse.next()
    : NextResponse.json(
        { error: 'Too many requests', retryAfter: Math.ceil((result.reset - Date.now()) / 1000) },
        { status: 429 },
      );

  res.headers.set('X-RateLimit-Limit',     String(result.limit));
  res.headers.set('X-RateLimit-Remaining', String(result.remaining));
  res.headers.set('X-RateLimit-Reset',     String(result.reset));
  if (!result.success) {
    res.headers.set('Retry-After', String(Math.ceil((result.reset - Date.now()) / 1000)));
  }

  return res;
}

export const config = {
  matcher: '/api/:path*',
};
```

The middleware runs at the edge (no cold start), Redis is co-located regionally (Upstash), and the rate limit check adds ~2ms latency.

## Identifier strategies

Identifying the requester correctly is as important as the limit itself.

**IP address**: Default. Works for unauthenticated endpoints. Fails for shared IPs (offices, NAT, IPv6 ranges).

**User ID**: Better for authenticated endpoints. A legitimate user with many IPs counts as one.

**API key**: For developer APIs. Rate limit per key, not per IP.

**Composite**: For sensitive endpoints, combine user ID + IP. A compromised account abused from a new IP is easier to detect.

```ts
// For authenticated API routes
const userId   = await getAuthUserId(req);
const ip       = req.ip ?? 'unknown';
const identifier = userId
  ? `user:${userId}:${path}`           // authenticated: per user
  : `ip:${ip}:${path}`;                // unauthenticated: per IP
```

## Graduated response

A binary block (pass/reject) is coarse. A graduated response — warn before blocking — improves the experience for legitimate users who hit limits.

```ts
const result = await rateLimit(identifier, config);

if (!result.success) {
  return NextResponse.json({ error: 'Rate limit exceeded' }, { status: 429 });
}

// Warn if approaching limit (within 10%)
if (result.remaining < config.limit * 0.1) {
  res.headers.set('X-RateLimit-Warning', 'approaching-limit');
}
```

The client reads `X-RateLimit-Warning` and can surface a message to the user before they hit the wall.

## The contact form case

Scoutr's contact endpoint is rate-limited to 5 requests per hour per IP. The implementation includes a secondary limit per email address — even if someone rotates IPs, the same email address can't spam the endpoint.

```ts
const ipIdentifier    = `contact:ip:${ip}`;
const emailIdentifier = `contact:email:${email.toLowerCase()}`;

const [ipResult, emailResult] = await Promise.all([
  rateLimit(ipIdentifier,    { limit: 5, window: 3600 }),
  rateLimit(emailIdentifier, { limit: 3, window: 86400 }), // 3 per day per email
]);

if (!ipResult.success || !emailResult.success) {
  return { error: 'Too many requests', status: 429 };
}
```

## Upstash vs self-hosted Redis

Upstash is the practical choice for serverless/edge deployments: no persistent connection required, HTTP-based SDK, global replication, and free tier covers most apps. Self-hosted Redis (via Docker or Railway) makes sense if you're already running Redis for queues and want to consolidate.

The Upstash SDK handles the atomic operations correctly. If you implement sliding window yourself against a plain Redis client, use Lua scripts to make the pipeline atomic — a race condition in the rate limiter defeats its purpose.
