excerpt: "Velero is the de facto Kubernetes backup tool: it snapshots cluster state (all Kubernetes objects in a namespace or cluster) and persistent volumes (via CSI volume snapshots or Restic), stores them in S3-compatible object storage, and supports restore to the same or a different cluster. It runs on a schedule (cron-style) and integrates with cloud provider snapshot APIs. Velero is the practical answer to 'what happens if we lose the cluster' — it enables DR runbooks, namespace cloning for staging, and production data exports."

Cluster state plus volume snapshots to S3. Restore to any cluster.

## Installation and storage configuration

```bash
# Install Velero CLI
brew install velero

# Install Velero on the cluster — AWS S3 backend
velero install \
  --provider aws \
  --plugins velero/velero-plugin-for-aws:v1.10.0 \
  --bucket construx-velero-backups \
  --backup-location-config region=us-east-1 \
  --snapshot-location-config region=us-east-1 \
  --secret-file ./velero-credentials   # AWS credentials file

# velero-credentials format:
# [default]
# aws_access_key_id=AKIAXXXXXXXXXXXXXXXX
# aws_secret_access_key=xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

# Use IAM roles for service accounts (IRSA) in EKS instead of static credentials
# velero-serviceaccount annotation:
# eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/velero-role

# Verify installation
velero version
# Client:
#         Version: v1.14.1
# Server:
#         Version: v1.14.1

kubectl get pods -n velero
# velero-6d9f5c4b8-xk2pq   1/1   Running   0   5m
```

## Backup configuration and schedules

```bash
# On-demand backup — snapshot a specific namespace
velero backup create construx-manual-20320325 \
  --include-namespaces construx \
  --snapshot-volumes=true \    # Include PVC snapshots (requires CSI driver)
  --storage-location default

# Monitor backup progress
velero backup describe construx-manual-20320325
# Phase: Completed
# Started:    2032-03-25 10:14:05Z
# Completed:  2032-03-25 10:16:48Z
#
# Namespaces:
#   Included:   construx
#   Excluded:   <none>
#
# Resources:
#   Included:   *
#   Excluded:   <none>
#
# Persistent Volumes:
#   postgres-data-postgres-0:  snap-0a1b2c3d4e (aws)  Completed
#   redis-data-redis-0:        snap-0f9e8d7c6b (aws)  Completed

# Scheduled daily backup — 02:00 UTC with 10-day retention
velero schedule create construx-daily \
  --schedule="0 2 * * *" \
  --include-namespaces construx,construx-monitoring \
  --ttl 240h \                 # 240 hours = 10 days retention
  --snapshot-volumes=true

# Weekly backup with longer retention (30 days)
velero schedule create construx-weekly \
  --schedule="0 3 * * 0" \    # Every Sunday at 03:00
  --include-namespaces construx \
  --ttl 2160h \               # 90 days
  --snapshot-volumes=true

# List all backups with status
velero backup get
# NAME                          STATUS      ERRORS  CREATED                EXPIRES
# construx-daily-20320325-0200  Completed   0       2032-03-25 02:00:23Z   9d
# construx-daily-20320324-0200  Completed   0       2032-03-24 02:00:21Z   8d
```

## Restore operations — DR testing and migration

```bash
# Restore to same namespace (overwrite existing resources)
velero restore create --from-backup construx-daily-20320325-0200

# Restore to a different namespace — creates a staging copy of production
velero restore create staging-copy \
  --from-backup construx-daily-20320325-0200 \
  --namespace-mappings construx:construx-staging \
  --restore-volumes=true     # Also restore PVC snapshots

# Monitor restore
velero restore describe staging-copy --details

# Restore only specific resource types (e.g., just ConfigMaps and Secrets)
velero restore create config-restore \
  --from-backup construx-daily-20320325-0200 \
  --include-resources configmaps,secrets

# Cross-cluster restore (disaster recovery scenario):
# 1. Install Velero on the new cluster pointing to the same S3 bucket
velero install --provider aws --bucket construx-velero-backups ...

# 2. Velero automatically discovers existing backups from S3
velero backup get   # Shows backups from the original cluster

# 3. Restore to new cluster
velero restore create --from-backup construx-daily-20320325-0200

# DR drill checklist:
# [ ] Take a backup of production
# [ ] Provision a new cluster in a different region
# [ ] Install Velero pointing to the same S3 bucket
# [ ] Restore and verify the application starts
# [ ] Measure RTO: target <30 minutes from cluster provision to app healthy
```

## Backup hooks — application-consistent snapshots

```yaml
# Backup hooks: run commands inside pods before/after snapshot
# Use case: flush PostgreSQL WAL before snapshotting the PVC

apiVersion: velero.io/v1
kind: Backup
metadata:
  name: construx-consistent-backup
spec:
  includedNamespaces:
    - construx
  snapshotVolumes: true
  hooks:
    resources:
      - name: postgres-checkpoint
        includedNamespaces:
          - construx
        labelSelector:
          matchLabels:
            app: postgres
        pre:
          - exec:
              container: postgres
              command:
                - /bin/bash
                - -c
                - psql -c "CHECKPOINT;" -U postgres   # Force WAL flush before snapshot
              timeout: 60s
              onError: Fail
        post:
          - exec:
              container: postgres
              command: ["/bin/bash", "-c", "echo backup complete"]
              timeout: 10s
```

Velero vs etcd backup: The Kubernetes API server stores all cluster state in etcd. Backing up etcd directly (via `etcdctl snapshot save`) captures everything including cluster configuration, but it's difficult to restore to a different Kubernetes version, and it doesn't capture PVC data. Velero works at the Kubernetes API level — it exports objects as YAML and uses CSI snapshots for volumes — making it version-agnostic and easier to restore to different clusters. For self-managed clusters, use both: etcd snapshots for cluster-level recovery, Velero for namespace-level backup and migration.
