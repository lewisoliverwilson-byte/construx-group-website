A slow query usually has one of three causes: wrong index (or no index), bad cardinality estimate (planner chose a bad plan), or genuinely too much data to process. EXPLAIN ANALYZE tells you which it is.

## Running EXPLAIN ANALYZE

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT) 
SELECT p.id, p.title, u.email
FROM posts p
JOIN users u ON u.id = p.author_id
WHERE p.status = 'published'
ORDER BY p.created_at DESC
LIMIT 10;
```

Always use `ANALYZE` (executes the query), `BUFFERS` (shows cache hit/miss stats), and run on production data or a realistic sample.

## Reading the output

```
Limit (cost=0.43..31.14 rows=10 width=88) (actual time=0.082..0.194 rows=10 loops=1)
  ->  Nested Loop (cost=0.43..1247.82 rows=400 width=88) (actual time=0.080..0.190 rows=10 loops=1)
        ->  Index Scan using posts_created_at_idx on posts p
              (cost=0.29..48.14 rows=400 width=56)
              (actual time=0.062..0.148 rows=10 loops=1)
              Index Cond: (status = 'published')
              Filter: (status = 'published')
              Rows Removed by Filter: 0
        ->  Index Scan using users_pkey on users u
              (cost=0.14..2.99 rows=1 width=32)
              (actual time=0.003..0.003 rows=1 loops=10)
              Index Cond: (id = p.author_id)
Planning Time: 0.412 ms
Execution Time: 0.231 ms
```

Key numbers:
- `cost=0.29..48.14` — estimated startup and total cost (in planner's arbitrary units)
- `actual time=0.062..0.148` — actual startup and total milliseconds
- `rows=400` vs `actual rows=10` — planner estimated 400, got 10. Bad estimate = bad plan risk.
- `loops=10` — this node executed 10 times

## Bad plan: sequential scan instead of index

```sql
EXPLAIN ANALYZE SELECT * FROM posts WHERE content ILIKE '%nix%';
```

```
Seq Scan on posts  (cost=0.00..4821.00 rows=1 width=...) (actual time=0.041..882.14 rows=127 loops=1)
  Filter: ((content)::text ~~* '%nix%')
  Rows Removed by Filter: 98241
Planning Time: 0.118 ms
Execution Time: 882.182 ms
```

The problem: `ILIKE '%nix%'` with a leading wildcard can't use a B-tree index. The fix: use full-text search (tsvector) or a trigram index (pg_trgm).

```sql
-- Trigram index for LIKE/ILIKE with wildcards
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX posts_content_trgm_idx ON posts USING gin (content gin_trgm_ops);

-- Now re-run the query:
-- Bitmap Heap Scan on posts (actual time=4.12..5.88 rows=127 loops=1)
--   Recheck Cond: (content ~~* '%nix%')
-- Planning Time: 1.241 ms
-- Execution Time: 6.002 ms
```

882ms → 6ms.

## Bad cardinality estimate

```sql
-- Planner estimates 10 rows, actually returns 50000
EXPLAIN ANALYZE
SELECT * FROM events WHERE user_id = 42 AND type = 'click';
```

If the planner underestimates rows, it may choose nested loop over hash join — expensive when the actual row count is large.

```sql
-- Fix: update statistics
ANALYZE events;

-- Or: increase statistics target for skewed columns
ALTER TABLE events ALTER COLUMN user_id SET STATISTICS 500;
ANALYZE events;
```

After `ANALYZE`, the planner has better data and may choose a better join strategy.

## The most common fixes

```sql
-- Missing index on WHERE clause column
CREATE INDEX posts_status_created_idx ON posts (status, created_at DESC);

-- Missing index on foreign key (JOIN column)
CREATE INDEX posts_author_id_idx ON posts (author_id);

-- Partial index for frequent filtered queries
CREATE INDEX posts_published_idx ON posts (created_at DESC) WHERE status = 'published';

-- Expression index for function-based filters
CREATE INDEX users_lower_email_idx ON users (lower(email));
-- Allows: WHERE lower(email) = lower($1)
```

A partial index for `status = 'published'` is much smaller than a full index on `(status, created_at)` — it only indexes the rows you query.

## pg_stat_statements: find slow queries in production

```sql
-- Enable the extension
CREATE EXTENSION pg_stat_statements;

-- Find the 10 slowest queries by total time
SELECT
  round(total_exec_time::numeric, 2) AS total_ms,
  round(mean_exec_time::numeric, 2)  AS avg_ms,
  calls,
  round(rows / calls::numeric, 1)    AS rows_per_call,
  left(query, 100)                   AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

This shows which queries are consuming the most total time in production — the starting point for any database performance investigation.

## EXPLAIN with auto_explain

```sql
-- In postgresql.conf:
shared_preload_libraries = 'auto_explain'
auto_explain.log_min_duration = 100   -- log plans for queries > 100ms
auto_explain.log_analyze = true
auto_explain.log_buffers = true
```

`auto_explain` logs the execution plan of slow queries automatically. You don't need to identify the slow query first — it logs itself.
