PostHog is our analytics layer across all three products. We chose it for the standard reasons: self-hostable for GDPR compliance, feature flags without a separate service, session recordings for qualitative understanding.

What we didn't expect: AI products require different analytics thinking from conventional products, and PostHog's event-based model is well-suited to it.

## The conventional analytics failure mode

Conventional analytics tells you who visits your site, where they drop off, and how long they stay. For a landing page or a e-commerce flow, this is the relevant information.

For an AI feature, "how long did the user spend on the output page" tells you very little. Did they spend a long time reading the output because it was valuable and they were making decisions from it? Or because it was confusing and they were trying to figure out what it meant? The session duration is the same; the experience is opposite.

The question that matters for AI products: did the user find the output useful enough to act on it? And the signals for that are different from session duration.

## The events we track

For Scoutr, the core events:

**`scan_initiated`**: a user started a scan. Properties: URL domain (not the full URL — we don't need or want the specific product URLs), session context.

**`scan_completed`**: a scan finished successfully. Properties: number of products returned, time to complete.

**`scan_product_engaged`**: a user clicked on or expanded a specific product result. Properties: product rank in the list (did they engage with the top result or one further down?), projected margin range.

**`scan_product_link_clicked`**: a user clicked through to the product page from the Scoutr result. This is the action signal — they found the result useful enough to investigate further.

**`scan_error`**: a scan failed. Properties: error type (parse failure, API timeout, rate limit), URL pattern.

The ratio of `scan_product_link_clicked` to `scan_product_engaged` tells us whether users trust the output enough to act on it. A low click-through rate from engaged products suggests either the output isn't accurate enough to trust, or the next step (the product link) isn't clear enough.

## Funnel analysis for AI features

The standard funnel for a web product is visit → sign up → activate → retain. The AI product funnel has an additional step: find value.

Finding value for an AI product means the output was useful enough to inform a decision or take an action. For Scoutr: a user scanned, found a product with a good margin, and clicked through to investigate.

We track this as a multi-step funnel in PostHog:
1. `scan_initiated`
2. `scan_completed` (did the scan succeed?)
3. `scan_product_engaged` (did they engage with results?)
4. `scan_product_link_clicked` (did they act on the results?)

The drop-off at each step tells us where the experience breaks down. If step 2 → 3 drop-off is high, users are completing scans but not engaging with results — perhaps the output format is confusing or the results aren't what they expected. If step 3 → 4 drop-off is high, users are reading results but not acting on them — perhaps the confidence in the output isn't high enough.

## The AI quality signal

For AI products, there's an event type that conventional products don't have: the quality feedback event.

We don't ask for star ratings. Instead, we track implicit signals:

**Regeneration**: a user requesting a new output from the same input. This is a negative signal — they didn't like the first output. We track regeneration rate per feature and per user segment.

**Copy**: a user copying the AI output. This is a positive signal — they found it useful enough to use elsewhere.

**Edit after generation**: for features that produce editable content (The Hyve's AI draft documents), a user editing the draft before using it. The extent of editing tells us something about output quality — light editing suggests the output was mostly correct; heavy editing suggests it was a rough starting point.

These implicit signals give us a quality signal without requiring explicit user ratings that most users don't provide.

## Session recordings for AI features

Session recordings (screen + interaction captures) are more valuable for AI products than for conventional products because they capture the user's reaction to the output in real time.

The specific thing we look for: the pause after an AI output appears. A user who reads the output, then looks around the screen, then closes the tab is probably confused or disappointed. A user who reads the output, then immediately acts on it (clicks a link, starts typing) is probably satisfied.

This is qualitative signal that event analytics can't capture. The combination of event analytics (what happened) and session recordings (how it happened) gives a more complete picture of user experience than either alone.

## Privacy considerations

AI product analytics requires extra care about what you log. AI features often process sensitive user inputs — product URLs in Scoutr, project discussions in The Hyve, professional documents in The Marqet.

Our approach: log the event type and outcome, not the content. `scan_completed` with properties about the scan result, not the actual products found. `message_sent` with properties about the message length and response time, not the message content.

PostHog's self-hosted option means analytics data stays on infrastructure we control. This matters for GDPR compliance and for user trust — we can accurately tell users their data isn't sent to third-party analytics services.

The tradeoff: we have less content data for debugging than we'd like. When a user reports that a specific output was wrong, we can find the session and understand the sequence of events, but we can't replay the exact AI call with the exact input. This is the right tradeoff for products that handle user inputs they might consider sensitive.
