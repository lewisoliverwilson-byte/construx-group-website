The case for Docker in development: environment parity. The Node version on your machine, the one your colleague uses, and the one on CI are all different. Docker eliminates that drift. Every developer runs the same container, the same Node version, the same OS-level dependencies.

The case against: Docker adds complexity and can make the edit-refresh cycle feel slow if set up badly. Set up well, it's transparent.

## The Dockerfile

Multi-stage builds keep the development and production images separate while sharing the base configuration:

```dockerfile
# Dockerfile
FROM node:22-alpine AS base
WORKDIR /app

# Install dependencies in a separate stage to cache them
FROM base AS deps
COPY package.json package-lock.json ./
RUN npm ci

# Development stage
FROM base AS development
COPY --from=deps /app/node_modules ./node_modules
COPY . .
EXPOSE 3000
CMD ["npm", "run", "dev"]

# Builder stage for production
FROM base AS builder
COPY --from=deps /app/node_modules ./node_modules
COPY . .
ENV NEXT_TELEMETRY_DISABLED=1
RUN npm run build

# Production stage — minimal image
FROM base AS production
ENV NODE_ENV=production
ENV NEXT_TELEMETRY_DISABLED=1

RUN addgroup --system --gid 1001 nodejs
RUN adduser --system --uid 1001 nextjs

COPY --from=builder /app/public ./public
COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./
COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/static

USER nextjs
EXPOSE 3000
CMD ["node", "server.js"]
```

The production stage uses Next.js's standalone output — a minimal Node server without node_modules. Enable it in `next.config.ts`:

```ts
const nextConfig: NextConfig = {
  output: 'standalone',
};
```

## Docker Compose for development

```yaml
# docker-compose.yml
services:
  app:
    build:
      context: .
      target: development
    ports:
      - "3000:3000"
    volumes:
      - .:/app                          # mount source for hot reload
      - /app/node_modules               # don't overwrite container node_modules
      - /app/.next                      # don't overwrite build cache
    environment:
      - NODE_ENV=development
      - DATABASE_URL=postgresql://postgres:password@db:5432/construx
      - NEXTAUTH_URL=http://localhost:3000
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: password
      POSTGRES_DB: construx
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 5s
      retries: 5

volumes:
  postgres_data:
```

Start everything with `docker compose up`. The app hot-reloads on file changes because the source directory is volume-mounted.

## The node_modules problem

The anonymous volume trick (`- /app/node_modules`) prevents the host's `node_modules` from overwriting the container's. Without it, your Mac's native binaries (like the `@next/swc-darwin-arm64` package) would clobber the Linux ones inside the container.

The same applies to `.next` — you don't want the container's build cache overwritten by anything on the host.

## Watch mode with compose watch (Docker 2.22+)

Docker Compose watch is a better alternative to bind mounts for some workflows:

```yaml
services:
  app:
    build:
      context: .
      target: development
    ports:
      - "3000:3000"
    develop:
      watch:
        - action: sync
          path: ./app
          target: /app/app
        - action: sync
          path: ./components
          target: /app/components
        - action: sync
          path: ./lib
          target: /app/lib
        - action: rebuild
          path: package.json
```

`sync` copies files into the running container without a restart. `rebuild` triggers a full image rebuild when dependencies change. This is faster than a full volume mount and more explicit about what triggers what.

Run with `docker compose watch` instead of `docker compose up`.

## .dockerignore

Essential for keeping images fast and small:

```
node_modules
.next
.git
*.md
.env*.local
.DS_Store
coverage
.nyc_output
```

Without `.dockerignore`, `COPY . .` copies `node_modules` (hundreds of MB) into the build context before Docker even starts.

## Running one-off commands

```bash
# Run database migrations
docker compose exec app npx drizzle-kit migrate

# Open a shell in the container
docker compose exec app sh

# Run tests inside the container
docker compose exec app npm test

# Check logs
docker compose logs -f app
```

## Environment variables

Don't bake secrets into the image. Use a `.env.docker` file for development:

```bash
# .env.docker (not committed)
DATABASE_URL=postgresql://postgres:password@db:5432/construx
NEXTAUTH_SECRET=dev-secret-not-for-production
OPENAI_API_KEY=sk-...
```

```yaml
services:
  app:
    env_file:
      - .env.docker
```

Production secrets come from your platform (Amplify, Vercel, ECS) — never from committed files.

## When to use Docker in development

Use it when: the team has more than two people; you use OS-specific native dependencies (sharp, sqlite, imagemagick); you're targeting Linux in production and developing on Mac; or you want CI and local environments to be identical.

Skip it when: you're a solo developer, your toolchain is pure JS with no native modules, and you're happy managing Node versions with nvm or fnm.
