For server-side use, SQLite is appropriate for read-heavy workloads, edge functions, and applications where the simplicity of a single file outweighs the need for concurrent writes. One file. No server. Full SQL. WAL mode makes it concurrent enough for most read workloads.

## Basic operations and WAL mode

```bash
# Open a SQLite database (creates it if it doesn't exist)
sqlite3 construx.db

# Enable WAL mode (Write-Ahead Log) — allows concurrent readers during writes
PRAGMA journal_mode=WAL;
# wal

# Essential pragmas for production use
PRAGMA synchronous=NORMAL;      # Faster writes; safe with WAL (not FULL mode)
PRAGMA cache_size=-64000;       # 64MB page cache (negative = KB)
PRAGMA temp_store=MEMORY;       # Temp tables in RAM
PRAGMA mmap_size=268435456;     # 256MB memory-mapped I/O
PRAGMA foreign_keys=ON;         # Enforce FK constraints (off by default!)
PRAGMA busy_timeout=5000;       # Wait 5s before "database is locked" error

# Create a table with proper types
CREATE TABLE orders (
  id          TEXT PRIMARY KEY DEFAULT (lower(hex(randomblob(8)))),
  customer_id TEXT NOT NULL,
  status      TEXT NOT NULL CHECK(status IN ('pending','shipped','cancelled')),
  total_cents INTEGER NOT NULL,
  created_at  TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ','now')),
  metadata    TEXT                        -- JSON stored as TEXT
);

CREATE INDEX idx_orders_customer ON orders(customer_id);
CREATE INDEX idx_orders_status   ON orders(status, created_at DESC);

# Insert with RETURNING (SQLite 3.35+)
INSERT INTO orders (customer_id, status, total_cents, metadata)
VALUES ('cust-001', 'pending', 4999, '{"source":"web","promo":"SUMMER10"}')
RETURNING id, created_at;
-- a3f9b2c1  2032-05-21T14:32:07Z
```

## JSON functions and full-text search

```bash
# json_extract: query JSON stored in TEXT columns
SELECT
  id,
  json_extract(metadata, '$.source') AS source,
  json_extract(metadata, '$.promo')  AS promo
FROM orders
WHERE json_extract(metadata, '$.promo') IS NOT NULL;
-- a3f9b2c1  web  SUMMER10

# json_each: iterate over JSON arrays
SELECT o.id, j.value AS tag
FROM orders o, json_each(json_extract(o.metadata, '$.tags')) j
WHERE o.status = 'shipped';

# FTS5: full-text search (built-in)
CREATE VIRTUAL TABLE dispatches_fts USING fts5(
  title, content, tokenize='porter unicode61'
);

INSERT INTO dispatches_fts(title, content)
  SELECT title, body FROM dispatches;

-- Search with ranking
SELECT title, rank
FROM dispatches_fts
WHERE dispatches_fts MATCH 'kubernetes OR ebpf'
ORDER BY rank
LIMIT 10;
-- Cilium: eBPF-native networking...  -2.841
-- Falco: runtime security...          -2.213

# BM25 rank access
SELECT title, bm25(dispatches_fts) AS score
FROM dispatches_fts
WHERE dispatches_fts MATCH 'postgres replication'
ORDER BY score;
```

## WAL mode concurrency and ATTACH DATABASE

```bash
# WAL mode: readers never block writers, one writer at a time
# This is enough for most server workloads (many reads, few writes)

# Check WAL file size
ls -lh construx.db-wal
# -rw-r--r-- 1 construx construx 3.2M construx.db-wal

# Manual checkpoint: merge WAL into main database file
PRAGMA wal_checkpoint(FULL);
-- 0  1024  1024   (mode, pages_written, pages_moved)

# Auto-checkpoint threshold (default: 1000 pages = 4MB)
PRAGMA wal_autocheckpoint=2000;

# ATTACH DATABASE: query multiple SQLite files in one session
ATTACH DATABASE '/var/db/construx-archive.db' AS archive;

-- Query across attached databases
SELECT 'live' AS source, id, status FROM orders
UNION ALL
SELECT 'archive', id, status FROM archive.orders
WHERE created_at < '2032-01-01T00:00:00Z';

-- Cross-database join
SELECT o.id, c.name
FROM orders o
JOIN archive.customers c ON o.customer_id = c.id;

DETACH DATABASE archive;
```

## Performance and production patterns

```bash
# Explain query plan — check index usage
EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE customer_id = 'cust-001' AND status = 'shipped'
ORDER BY created_at DESC LIMIT 10;
-- SEARCH orders USING INDEX idx_orders_customer (customer_id=?)
-- ← good: using index, not full table scan

# Covering index: include all needed columns so the query never touches the main table
CREATE INDEX idx_orders_cov ON orders(status, created_at DESC, total_cents, id);
EXPLAIN QUERY PLAN SELECT id, total_cents, created_at FROM orders WHERE status='shipped';
-- SEARCH orders USING COVERING INDEX idx_orders_cov (status=?)  ← no table lookup

# VACUUM: reclaim space after deletes (creates a new database file, so needs free space)
VACUUM;

# Online backup (safe while database is in use)
sqlite3 construx.db ".backup /var/backup/construx-$(date +%Y%m%d).db"

# Litestream: continuous replication to S3 (streaming WAL changes)
# litestream replicate construx.db s3://construx-backups/construx.db
# litestream restore -o construx.db s3://construx-backups/construx.db

# Connection pooling in Go (single writer, multiple readers)
# SQLite allows multiple readers with WAL mode — use separate read/write connections
# Write DB: max 1 connection (prevents "database is locked")
# Read DB: max N connections (WAL readers are concurrent)
db, _ := sql.Open("sqlite3", "file:construx.db?mode=ro&_journal_mode=WAL")
db.SetMaxOpenConns(10)   # Read pool

writeDB, _ := sql.Open("sqlite3", "file:construx.db?_journal_mode=WAL")
writeDB.SetMaxOpenConns(1)   # Single writer
```

SQLite vs PostgreSQL for server applications: PostgreSQL handles concurrent writes natively (MVCC), supports multiple application servers, and scales to terabytes. SQLite has one writer at a time and lives in a single file on a single machine. The inflection point: if your application has more than one server process writing to the database, use PostgreSQL. If you have one process (or many readers and rare writes), SQLite is simpler, faster for local reads, and eliminates operational complexity — no server to manage, backup is a file copy, and the database follows the application binary. Litestream changes the calculus further: streaming replication to S3 makes SQLite a reasonable choice for production single-node deployments where the simplicity is worth the write serialisation constraint.
