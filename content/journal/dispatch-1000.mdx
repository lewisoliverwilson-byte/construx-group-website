## The compounding argument

```
Dispatch 1   → "we're learning this"
Dispatch 100 → "we know this area"
Dispatch 500 → "we have a point of view"
Dispatch 1000 → "this is what we do"

The shift isn't subjective. It's structural.

At 100 dispatches:
- You have a topic range but not depth
- Search finds you on long-tail queries
- Readers sample a post or two
- Duration signal: 10 months

At 1000 dispatches:
- You have depth on dozens of topics
- Search finds you on short-tail queries you've covered repeatedly
- Readers have years of posts to read through
- Duration signal: 3 years

The gap between 100 and 1000 isn't 10x more work.
It's 10x different work. The 900 entries after 100
aren't adding to what existed — they're converting a
collection into a corpus.

A corpus has properties a collection doesn't:
- Internal cross-linking becomes meaningful
- Patterns across entries become visible
- The reader can find the arc, not just the point
```

## What we learned from writing 1000 build logs

```bash
# 1. The tool matters less than the discipline
#    We've used: Terraform, Pulumi, CDK, raw CloudFormation
#    We've used: Prometheus, VictoriaMetrics, Datadog, CloudWatch
#    We've used: Kubernetes, Nomad, ECS, plain Docker
#    The pattern across all of them: the tool is the easy part.
#    The hard part is the same every time: knowing when to use it.

# 2. The comparison is the value
#    Almost every dispatch ends with:
#    "Tool X vs Tool Y vs Tool Z — when to use each"
#    These comparisons are what we come back to most.
#    They're also the hardest to write — you have to understand
#    all three tools at production depth to write one paragraph
#    that's genuinely useful.

# 3. The code is the argument
#    A paragraph saying "Consul handles service discovery well"
#    is not useful. A 60-line bash transcript showing exactly
#    what consul catalog services returns and how DNS SRV records
#    look is useful. The code is the argument.
#    You can quote a paragraph. You can't refute working code.

# 4. Three days is the right interval
#    Weekly felt too slow — a week between entries is enough time
#    for momentum to dissipate. Daily felt too fast — the quality
#    dropped because we were writing about things we'd just learned
#    rather than things we'd understood.
#    Three days gives you time to actually run the thing, hit the
#    edge cases, and write about what you found rather than what
#    you expected to find.

# 5. Publication date doesn't matter
#    Dispatch 1 gets as many readers as it ever will in the first
#    48 hours. Then it gets more, steadily, as the corpus grows
#    and search indexes it. The total lifetime readership of a
#    dispatch is determined mostly by how searchable the topic is,
#    not when it was published. Write for the corpus, not the feed.
```

Dispatch 1000 isn't a destination. It's a data point that proves the model works. The model is: publish consistently at a cadence that allows quality, on topics you're actually building with, with enough depth to be useful rather than merely present.
