Vercel and Cloudflare Workers are designed for stateless request/response. Fly.io is designed for stateful apps that need to run continuously — databases, WebSocket servers, background workers, game servers. You get the global deployment benefit of edge without the stateless constraint.

## Setup

```bash
# Install flyctl
curl -L https://fly.io/install.sh | sh

# Login
fly auth login

# Create a new app from a Dockerfile
fly launch
```

## fly.toml

```toml
app = "construx-api"
primary_region = "lhr"  # London

[build]
  dockerfile = "Dockerfile"

[env]
  NODE_ENV    = "production"
  PORT        = "3000"

[http_service]
  internal_port        = 3000
  force_https          = true
  auto_stop_machines   = "stop"
  auto_start_machines  = true
  min_machines_running = 1

  [http_service.concurrency]
    type      = "requests"
    hard_limit = 200
    soft_limit = 100

[[vm]]
  size = "shared-cpu-1x"

[[mounts]]
  source      = "construx_data"
  destination = "/data"

[checks]
  [checks.health]
    grace_period = "10s"
    interval     = "15s"
    method       = "GET"
    path         = "/api/health"
    timeout      = "2s"
```

## Deploying

```bash
# Deploy
fly deploy

# Deploy without downtime
fly deploy --strategy rolling

# Scale horizontally
fly scale count 3

# Scale to specific regions
fly scale count 2 --region lhr
fly scale count 1 --region sin
fly scale count 1 --region sea

# Check status
fly status
fly logs
```

## Persistent volumes (LiteFS, SQLite)

```bash
# Create a volume
fly volumes create construx_data --size 10 --region lhr

# LiteFS: distributed SQLite across Fly regions
# fly.toml for LiteFS
[mounts]
  source      = "litefs"
  destination = "/var/lib/litefs"
```

```yaml
# litefs.yml
fuse:
  dir: /var/lib/litefs

data:
  dir: /var/lib/litefs/data

exec:
  - cmd: node /app/server.js

lease:
  type: consul
  advertise-url: "http://${HOSTNAME}.vm.${FLY_APP_NAME}.internal:20202"

consul:
  url: "${FLY_CONSUL_URL}"
  advertise-url: "http://${HOSTNAME}.vm.${FLY_APP_NAME}.internal:20202"
```

LiteFS replicates SQLite writes to all VMs. Each region reads locally, writes forward to the primary. Zero-latency reads everywhere.

## Environment secrets

```bash
# Set secrets (encrypted, never in logs)
fly secrets set \
  DATABASE_URL="postgres://..." \
  STRIPE_SECRET_KEY="sk_live_..." \
  NEXTAUTH_SECRET="$(openssl rand -base64 32)"

# List secret names (not values)
fly secrets list

# Unset
fly secrets unset STRIPE_SECRET_KEY
```

## Fly Postgres

```bash
# Attach a managed Postgres cluster
fly postgres create --name construx-db --region lhr
fly postgres attach --app construx-api construx-db

# This sets DATABASE_URL automatically in the app's environment
```

## SSH into a VM

```bash
# Open a shell on a running VM
fly ssh console

# Run a command
fly ssh console -C "node -e 'console.log(process.env.NODE_ENV)'"

# Proxy a port locally
fly proxy 5432:5432 --app construx-db
# Now psql -h localhost -p 5432 construxgroup works
```

## Fly.io vs Railway vs Render vs AWS ECS

Fly.io: global deployment, micro-VMs, LiteFS for SQLite at the edge, lowest latency for global apps. Railway: simpler UX, fewer regions, great for MVPs. Render: managed PaaS, good Postgres and Redis integration, single region by default. AWS ECS: full control, complex setup, integrates with the entire AWS ecosystem. For apps that need global presence and persistent state (WebSockets, stateful workers, LiteFS SQLite), Fly.io is the best choice outside AWS.
