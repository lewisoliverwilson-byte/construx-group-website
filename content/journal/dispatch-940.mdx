excerpt: "systemd-analyze is the diagnostic companion to systemd — it profiles boot time, graphs unit dependencies, verifies unit file syntax, and scores unit security with a detailed breakdown of which capabilities and syscall filters are or aren't in place. `systemd-analyze blame` shows which units consumed the most boot time; `systemd-analyze critical-chain` traces the critical path through the dependency graph; `systemd-analyze dot` generates a Graphviz dot file of the full dependency graph. The security subcommand scores each unit on a 0-10 scale based on sandboxing (PrivateTmp, ProtectSystem, NoNewPrivileges, SeccompFilter, CapabilityBoundingSet) — useful for hardening long-running services."

`blame` for boot. `critical-chain` for the bottleneck. `security` for hardening scores.

## Boot time analysis

```bash
# systemd-analyze: total boot time breakdown
systemd-analyze
# Startup finished in 1.823s (kernel) + 3.412s (initrd) + 8.241s (userspace) = 13.477s
# graphical.target reached after 8.124s in userspace

# blame: show units sorted by activation time (slowest first)
systemd-analyze blame
# 4.821s postgresql.service        ← database needs index warm-up
# 2.183s construx-api.service      ← JVM/app startup
# 1.847s NetworkManager.service
# 1.204s docker.service
#   841ms containerd.service
#   621ms systemd-udev-settle.service
#   384ms dev-sda1.device
#   ...

# Filter to just your services
systemd-analyze blame | grep construx
# 2.183s construx-api.service
#   312ms construx-worker.service
#   187ms construx-metrics.service

# critical-chain: the dependency path that determined boot time
# (units on the critical path, with timing)
systemd-analyze critical-chain
# The time unit is 1ms
# graphical.target @8124ms
# └─multi-user.target @8124ms
#   └─construx-api.service @5941ms +2183ms   ← bottleneck
#     └─postgresql.service @1120ms +4821ms
#       └─network.target @1098ms
#         └─NetworkManager.service @251ms +847ms

# critical-chain for a specific unit
systemd-analyze critical-chain construx-api.service
```

## Dependency graph and unit verification

```bash
# dot: generate Graphviz dependency graph (all units)
systemd-analyze dot | dot -Tsvg > boot-graph.svg

# Filter to specific units and their dependencies
systemd-analyze dot 'construx-*.service' 'postgresql.service' | dot -Tpng > construx-deps.png

# dot output is readable directly:
systemd-analyze dot construx-api.service
# // Dependencies for construx-api.service
# digraph systemd {
#   "construx-api.service" -> "postgresql.service" [color="green"];
#   "construx-api.service" -> "network.target" [color="blue"];
#   "construx-api.service" -> "construx-worker.service" [color="black", style="dashed"];
# }

# verify: check unit file syntax without reloading
systemd-analyze verify /etc/systemd/system/construx-api.service
# No errors found.

# Verify multiple units at once
systemd-analyze verify /etc/systemd/system/*.service

# cat: show the effective unit file (including overrides)
systemctl cat construx-api.service

# show: display all unit properties
systemctl show construx-api.service | grep -E "^(Type|Restart|ExecStart|MemoryLimit|CPUQuota)"
# Type=notify
# Restart=on-failure
# ExecStart=/usr/local/bin/construx-api serve --config /etc/construx/config.yaml
# MemoryLimit=2147483648
# CPUQuota=200%
```

## Security scoring

```bash
# systemd-analyze security: score a unit's sandboxing
systemd-analyze security construx-api.service

# NAME                                                        DESCRIPTION                              EXPOSURE
# ✗ PrivateNetwork=                                           Service has access to the host network   0.5
# ✗ User=/DynamicUser=                                        Service runs as root user                0.4
# ✓ NoNewPrivileges=                                          Service cannot gain new privileges        -
# ✗ CapabilityBoundingSet=~CAP_(SYS_ADMIN|SYS_TIME|...)      Capabilities not restricted              0.3
# ✗ SeccompFilter=                                            Syscall filter not set                   0.2
# ✓ PrivateTmp=                                               Service has private /tmp                  -
# ✗ ProtectKernelTunables=                                    Kernel variables accessible               0.2
# ✗ ProtectSystem=                                            Host filesystem accessible                0.3
#
# Overall exposure level for construx-api.service: 3.2 OK

# Harden the unit to reduce exposure:
# /etc/systemd/system/construx-api.service
[Service]
User=construx
Group=construx
NoNewPrivileges=true
PrivateTmp=true
PrivateDevices=true
ProtectSystem=strict
ProtectHome=true
ProtectKernelTunables=true
ProtectKernelModules=true
ProtectControlGroups=true
ReadWritePaths=/var/lib/construx /var/log/construx
CapabilityBoundingSet=
AmbientCapabilities=
SystemCallFilter=@system-service
SystemCallErrorNumber=EPERM

# After adding these, re-score:
systemctl daemon-reload
systemd-analyze security construx-api.service
# Overall exposure level: 0.8 SAFE
```

## Calendar expressions and timer analysis

```bash
# systemd-analyze calendar: validate and expand systemd calendar expressions
# (used in OnCalendar= directives for timer units)

# Daily at 3am UTC
systemd-analyze calendar "03:00 UTC"
#   Original form: 03:00 UTC
# Normalized form: *-*-* 03:00:00 UTC
#     Next elapse: Wed 2032-09-04 03:00:00 UTC
#            From: Tue 2032-09-03 14:22:07 UTC
#        Distance: 12h 37min 53s

# Every 15 minutes
systemd-analyze calendar "*:0/15"
# Normalized form: *-*-* *:00/15:00
#     Next elapse: Tue 2032-09-03 14:30:00 UTC

# First day of every month
systemd-analyze calendar "*-*-01 00:00:00"

# List active timers
systemctl list-timers --all
# NEXT                          LEFT    LAST                          PASSED  UNIT
# Wed 2032-09-04 03:00:00 UTC   12h     Tue 2032-09-03 03:00:01 UTC  11h     restic-backup.timer
# Wed 2032-09-04 04:00:00 UTC   13h     Tue 2032-09-03 04:00:02 UTC  10h     logrotate.timer

# timespan: convert human-readable duration to seconds
systemd-analyze timespan 1h 30min
# Original: 1h 30min
# μs:       5400000000
# s:        5400
```

systemd-analyze vs journalctl for diagnostics: journalctl answers "what happened" — log events after the fact. systemd-analyze answers "why is this slow to start" and "is this unit properly sandboxed" — structural and timing questions. The security subcommand is particularly useful as a checklist: it identifies missing `PrivateTmp`, missing `ProtectSystem`, and missing syscall filters before a security team does. The practical workflow for new services: write the unit, run `systemd-analyze security` to find sandboxing gaps, add the directives incrementally (testing after each), and re-score until the exposure level is below 2. Scoring below 1 requires `DynamicUser=yes` or careful `User=` + `CapabilityBoundingSet=` configuration.
