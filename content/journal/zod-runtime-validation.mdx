TypeScript's type system is compile-time only. The types you write don't exist at runtime — they're erased during compilation. This means that any data coming from outside your TypeScript codebase (API responses, user input, environment variables, database query results) is untyped at runtime.

Zod bridges this gap. It provides runtime schema validation that produces TypeScript types from the same definition.

## The problem Zod solves

Consider an API endpoint that returns product data:

```typescript
// Your TypeScript type
interface Product {
  id: string;
  title: string;
  price: number;
  category: string;
}

const response = await fetch('/api/products');
const product = await response.json() as Product;
// "as Product" is a lie — it tells TypeScript to treat this as Product
// but at runtime, the actual shape is whatever the API returned
```

If the API changes its response shape, or returns an error object instead of a product, TypeScript won't catch this at runtime. Your code will crash, or worse, silently use unexpected values.

## The Zod approach

```typescript
import { z } from 'zod';

const ProductSchema = z.object({
  id: z.string(),
  title: z.string(),
  price: z.number().positive(),
  category: z.string(),
});

type Product = z.infer<typeof ProductSchema>;
// TypeScript type is inferred from the schema — no duplication

const response = await fetch('/api/products');
const data = await response.json();

// This throws a ZodError with a detailed message if the data doesn't match
const product = ProductSchema.parse(data);
```

If the API returns unexpected data, `parse` throws with a detailed error explaining exactly which fields are wrong and why. This converts a silent runtime bug into an explicit, diagnosable error.

## Where we use Zod

**API route input validation.** Every Next.js API route that accepts request body data validates it with Zod:

```typescript
const ScanRequestSchema = z.object({
  url: z.string().url('Must be a valid URL'),
  marketplace: z.enum(['amazon', 'ebay', 'both']).default('both'),
});

export async function POST(request: Request) {
  const body = await request.json();
  const result = ScanRequestSchema.safeParse(body);
  
  if (!result.success) {
    return NextResponse.json(
      { error: 'Invalid request', details: result.error.issues },
      { status: 400 }
    );
  }
  
  const { url, marketplace } = result.data;
  // url and marketplace are now fully typed and validated
}
```

The `safeParse` method returns a result object instead of throwing, which is better for user-facing validation where you want to return a helpful error message rather than throw.

**LLM output validation.** Claude's JSON output is validated against a schema before being used in application code:

```typescript
const ScanResultSchema = z.object({
  products: z.array(z.object({
    title: z.string(),
    asin: z.string().optional(),
    referral_fee_pct: z.number().min(0).max(1),
    fba_fee: z.number().nonnegative(),
    estimated_margin: z.number(),
    confidence: z.enum(['LOW', 'MEDIUM', 'HIGH']),
  })),
  scan_duration_ms: z.number(),
});

const rawOutput = JSON.parse(claudeResponse);
const result = ScanResultSchema.parse(rawOutput);
```

This ensures that if Claude returns malformed output, we catch it explicitly rather than passing bad data through the application.

**Environment variable validation.** We validate required environment variables at startup:

```typescript
const EnvSchema = z.object({
  DATABASE_URL: z.string().url(),
  STRIPE_SECRET_KEY: z.string().startsWith('sk_'),
  ANTHROPIC_API_KEY: z.string().startsWith('sk-ant-'),
  NEXT_PUBLIC_POSTHOG_KEY: z.string(),
});

// In app/api route or server component startup
const env = EnvSchema.parse(process.env);
```

A missing or malformed environment variable throws immediately at startup with a clear error, rather than causing a confusing runtime error when the variable is first used.

## The transformations

Zod schemas can include transformations — modifying values during validation:

```typescript
const ProductUrlSchema = z.string()
  .url()
  .transform(url => {
    // Normalise Amazon URLs to remove affiliate tracking parameters
    const parsed = new URL(url);
    parsed.searchParams.delete('tag');
    parsed.searchParams.delete('ref');
    return parsed.toString();
  });
```

This combines validation and normalisation in a single step. The URL is validated, then cleaned of tracking parameters before being used.

## The performance consideration

Zod validation adds a small overhead — typically 0.1-0.5ms for a simple schema. This is negligible for API endpoints that handle network I/O. For tight inner loops or very high-throughput scenarios, the overhead matters more.

We use Zod at the boundary (input validation, LLM output validation) and not inside tight loops. For hot paths that need schema validation, we consider `valibot` or `arktype` which have lower overhead, but Zod's ergonomics and ecosystem support make it the right default for most use cases.

## Zod with Stripe webhooks

The webhook event data from Stripe is validated using Zod before processing. The Stripe SDK provides TypeScript types, but Zod adds runtime confidence:

```typescript
const PaymentSucceededSchema = z.object({
  id: z.string(),
  amount: z.number().positive(),
  currency: z.string().length(3),
  metadata: z.record(z.string()),
  status: z.literal('succeeded'),
});
```

This ensures that critical payment data has the expected shape before we act on it.
