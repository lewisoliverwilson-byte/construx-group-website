The most common Redis mistake is using it only as a key-value cache. The other data structures are what make Redis uniquely suited to certain problems.

## Setup (ioredis)

```bash
npm install ioredis
npm install -D @types/ioredis
```

```ts
// lib/redis.ts
import Redis from 'ioredis';

export const redis = new Redis(process.env.REDIS_URL!, {
  maxRetriesPerRequest: 3,
  enableReadyCheck:     true,
  lazyConnect:          true,
});
```

## Sorted sets: leaderboards

```ts
// Add or update a score (O(log N))
await redis.zadd('leaderboard:monthly', score, userId);

// Increment score atomically
await redis.zincrby('leaderboard:monthly', 10, userId);

// Top 10 with scores (descending)
const top10 = await redis.zrevrangebyscore(
  'leaderboard:monthly',
  '+inf', '-inf',
  'WITHSCORES',
  'LIMIT', 0, 10,
);

// Rank of a specific user (0-indexed)
const rank = await redis.zrevrank('leaderboard:monthly', userId);

// Score of a specific user
const score = await redis.zscore('leaderboard:monthly', userId);
```

## Sorted sets: priority queue

```ts
// Add tasks with priority (lower score = higher priority)
await redis.zadd('tasks:pending', priority, JSON.stringify({ id, type, payload }));

// Pop the highest-priority task atomically
const [[taskStr]] = await redis.bzpopmin('tasks:pending', 0);  // 0 = block forever
const task = JSON.parse(taskStr);
```

## Pub/Sub: real-time notifications

```ts
// Publisher (any server process)
const publisher = new Redis(process.env.REDIS_URL!);

await publisher.publish('channel:notifications', JSON.stringify({
  type:    'post.published',
  postId:  'abc',
  userId:  'u1',
}));

// Subscriber (separate connection — pub/sub connections are stateful)
const subscriber = new Redis(process.env.REDIS_URL!);

await subscriber.subscribe('channel:notifications');

subscriber.on('message', (channel: string, message: string) => {
  const event = JSON.parse(message);
  console.log(`[${channel}]`, event.type, event.postId);
  // Forward to WebSocket clients, trigger webhook, etc.
});

// Pattern subscription
await subscriber.psubscribe('channel:*');
subscriber.on('pmessage', (pattern, channel, message) => {
  // handles all channel:* channels
});
```

## Streams: persistent event log

```ts
// Write to a stream (generates a unique ID)
const id = await redis.xadd('events:posts', '*', {
  type:      'post.viewed',
  postId:    'abc',
  userId:    'u1',
  timestamp: Date.now().toString(),
});
console.log(id);  // e.g. "1722882441000-0"

// Read from a consumer group (at-least-once delivery)
await redis.xgroup('CREATE', 'events:posts', 'analytics-workers', '$', 'MKSTREAM');

// Consumer reads pending messages
const messages = await redis.xreadgroup(
  'GROUP', 'analytics-workers', 'worker-1',
  'COUNT', 10,
  'BLOCK', 2000,  // block 2 seconds if no messages
  'STREAMS', 'events:posts', '>',
);

if (messages) {
  for (const [stream, entries] of messages) {
    for (const [msgId, fields] of entries) {
      const event = Object.fromEntries(
        fields.reduce((acc, _, i) => i % 2 === 0 ? [...acc, [fields[i], fields[i+1]]] : acc, [] as [string,string][]),
      );
      await processEvent(event);
      await redis.xack('events:posts', 'analytics-workers', msgId);
    }
  }
}
```

## Rate limiting with sliding window

```ts
async function rateLimit(
  identifier: string,
  limit: number,
  windowSeconds: number,
): Promise<{ allowed: boolean; remaining: number; resetIn: number }> {
  const now    = Date.now();
  const window = now - windowSeconds * 1000;
  const key    = `ratelimit:${identifier}`;

  const pipeline = redis.pipeline();
  pipeline.zremrangebyscore(key, 0, window);  // remove old entries
  pipeline.zadd(key, now, now.toString());    // add current request
  pipeline.zcard(key);                         // count in window
  pipeline.expire(key, windowSeconds);

  const results = await pipeline.exec();
  const count   = results![2][1] as number;
  const allowed = count <= limit;

  return {
    allowed,
    remaining: Math.max(0, limit - count),
    resetIn:   windowSeconds,
  };
}
```

## Redis vs Kafka vs RabbitMQ

Redis Streams: simple setup, lower throughput, good for internal event logs, persistence optional. Kafka: high throughput, durable, consumer groups, replay — for production event pipelines at scale. RabbitMQ: routing, dead-letter queues, AMQP protocol — for complex routing requirements. Use Redis when you are already running it and need messaging without adding another service. Add Kafka when message volume exceeds ~10K/sec or durability guarantees become critical.
