Multi-tenancy solves the economics of SaaS: you run one system, many customers use it. The isolation problem is: how do you ensure customer A can't see customer B's data? There are three main approaches, each with different trade-offs.

## 1. Shared tables with tenant column (row-level isolation)

The simplest approach: add a `tenant_id` column to every table and filter every query.

```ts
// db/schema.ts
export const posts = pgTable('posts', {
  id:       text('id').primaryKey(),
  tenantId: text('tenant_id').notNull(),
  title:    text('title').notNull(),
  body:     text('body').notNull(),
});

// All indexes include tenant_id
// CREATE INDEX posts_tenant_idx ON posts (tenant_id, created_at DESC);
```

```ts
// Every query must filter by tenant
async function getPosts(tenantId: string) {
  return db
    .select()
    .from(posts)
    .where(eq(posts.tenantId, tenantId))
    .orderBy(desc(posts.createdAt));
}
```

**The risk:** a missing `WHERE tenant_id = ?` clause leaks all tenants' data. Mitigate with Postgres row-level security:

```sql
-- Enable RLS on the table
ALTER TABLE posts ENABLE ROW LEVEL SECURITY;

-- Policy: users can only see rows matching their tenant_id
CREATE POLICY tenant_isolation ON posts
  USING (tenant_id = current_setting('app.tenant_id'));

-- Set in every session:
SET app.tenant_id = 'tenant_123';
```

With RLS enabled, Postgres rejects queries that would cross tenant boundaries, even if the application code forgets the filter.

```ts
// lib/db.ts — set tenant context on every request
export async function withTenant<T>(tenantId: string, fn: () => Promise<T>): Promise<T> {
  await db.execute(sql`SET LOCAL app.tenant_id = ${tenantId}`);
  return fn();
}
```

**Best for:** cost-sensitive products, early-stage SaaS, single-region deployments. All tenants share compute and storage.

## 2. Separate schemas per tenant

Postgres schemas let you namespace tables — `tenant_abc.posts`, `tenant_xyz.posts`. Each tenant gets their own set of tables in the same database cluster.

```sql
-- Create a schema for each new tenant
CREATE SCHEMA tenant_abc;
CREATE TABLE tenant_abc.posts (LIKE posts INCLUDING ALL);
```

```ts
// lib/db.ts — set schema for each request
export async function getDbForTenant(tenantId: string) {
  const schemaName = `tenant_${tenantId.replace(/-/g, '_')}`;
  await db.execute(sql`SET search_path = ${sql.identifier(schemaName)}, public`);
  return db;
}
```

**Best for:** mid-market SaaS where tenants need isolated backup/restore, stronger logical isolation, or per-tenant schema migrations.

**Limitations:** schema-per-tenant hits Postgres limits around 10k tenants. Migration management (running `ALTER TABLE` across all schemas) requires tooling.

## 3. Separate database per tenant

Each tenant gets their own Postgres cluster. Full isolation: independent backup, scaling, and data residency. Neon and PlanetScale make this practical at scale via branching.

```ts
// lib/tenant-db.ts — route to tenant's database
const TENANT_DB_URLS: Record<string, string> = {
  'enterprise-acme': process.env.DB_ACME!,
  'enterprise-corp':  process.env.DB_CORP!,
};

export function getDbUrl(tenantId: string): string {
  return TENANT_DB_URLS[tenantId] ?? process.env.DATABASE_URL!;
}
```

**Best for:** enterprise SaaS with data residency requirements (GDPR: European data must stay in Europe), tenants with SOC 2 Type II requirements for logical separation, or when individual tenants generate enough load to justify dedicated compute.

## What we use

Scoutr uses shared tables + RLS — it's developer-focused tooling with hundreds of small tenants. The cost economics of separate databases don't apply at that scale.

The Marqet's partner API uses separate schemas for large partners with dedicated SLAs and custom data requirements. Standard users are on shared tables.

Future The Hyve enterprise tier will use separate databases — team workspaces have data that customers explicitly want isolated ("our Slack conversations should not share hardware with a competitor").

## The migration problem

Starting with shared tables and migrating to per-schema or per-database later is expensive. The schemas approach is the most practical starting point if you expect enterprise customers: it provides strong isolation without the operational overhead of separate clusters, and migration paths to per-database exist.
