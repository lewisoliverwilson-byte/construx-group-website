excerpt: "Nomad is HashiCorp's workload scheduler — it runs containers, binaries, JVM processes, batch jobs, and system daemons across a cluster without requiring every service to be containerized. The killer feature versus Kubernetes: Nomad can schedule any task driver (Docker, containerd, exec, Java, QEMU), meaning you can run a mix of containerized microservices, legacy Java apps, and raw binaries under one scheduler. The job file is simpler than a Kubernetes manifest — one HCL file describes the job, its task groups, resource requests, and update strategy. Nomad handles placement, health checking, rescheduling on failure, and rolling deploys natively. Consul integration gives services automatic DNS-based discovery without sidecar injection. Single scheduler for containers, binaries, and JVM. HCL job files. Consul + Vault native integration.

## Nomad job file anatomy

```hcl
# construx-api.nomad — a typical web service job

job "construx-api" {
  datacenters = ["eu-west-1"]
  type        = "service"  # long-running service (vs batch or system)

  # Update strategy: rolling deploy, no downtime
  update {
    max_parallel      = 1
    min_healthy_time  = "30s"
    healthy_deadline  = "5m"
    auto_revert       = true   # roll back if health checks fail
    canary            = 1      # deploy one canary first
  }

  group "api" {
    count = 3  # 3 instances

    # Placement constraints
    constraint {
      attribute = "${attr.kernel.name}"
      value     = "linux"
    }

    # Spread across distinct hosts
    spread {
      attribute = "${node.unique.id}"
    }

    # Consul service registration (automatic from the job file)
    service {
      name = "construx-api"
      port = "http"
      tags = ["v2", "primary"]

      check {
        type     = "http"
        path     = "/healthz"
        interval = "10s"
        timeout  = "3s"
      }
    }

    network {
      port "http" { to = 8080 }  # dynamic host port mapped to container port 8080
    }

    task "api" {
      driver = "docker"  # or exec, java, containerd, qemu, etc.

      config {
        image = "registry.construx.io/construx/api:v2.1.4"
        ports = ["http"]
      }

      # Resource limits
      resources {
        cpu    = 500   # MHz
        memory = 512   # MB
      }

      # Environment variables from Vault (dynamic secrets)
      template {
        data = <<EOT
{{ with secret "database/creds/construx-api" }}
DATABASE_URL=postgres://{{ .Data.username }}:{{ .Data.password }}@postgres.service.consul:5432/construx
{{ end }}
{{ with secret "secret/construx/api" }}
JWT_SECRET={{ .Data.jwt_secret }}
{{ end }}
EOT
        destination = "secrets/env"
        env         = true  # expose as environment variables
        change_mode = "restart"
      }
    }
  }
}
```

## Running and managing jobs

```bash
# Install Nomad
brew install nomad

# Validate a job file before submitting
nomad job validate construx-api.nomad
# Job validation successful

# Plan: show what Nomad will do (like terraform plan)
nomad job plan construx-api.nomad
# + Job: "construx-api"
# + Task Group: "api" (3 create)
#   + Task: "api" (forces create)
# Scheduler dry-run:
#   - All tasks successfully allocated.

# Submit the job
nomad job run construx-api.nomad
# ==> Monitoring evaluation "abc123"
#     Evaluation triggered by job "construx-api"
#     Allocation "def456" created: node "node-1", group "api"
#     Allocation "ghi789" created: node "node-2", group "api"
#     Allocation "jkl012" created: node "node-3", group "api"
#     Evaluation "abc123" finished with status "complete"

# Status
nomad job status construx-api
# ID          = construx-api
# Type        = service
# Status      = running
# Datacenters = eu-west-1
#
# Allocations
# ID        Node ID   Task Group  Version  Desired  Status   Created
# def456    node-1    api         2        run      running  2033-01-31T09:12:00Z
# ghi789    node-2    api         2        run      running  2033-01-31T09:12:01Z
# jkl012    node-3    api         2        run      running  2033-01-31T09:12:02Z

# Logs from an allocation
nomad alloc logs def456
# {"level":"info","msg":"construx-api v2.1.4 started","port":8080}

# Exec into a running allocation
nomad alloc exec -task api def456 /bin/sh
# (opens a shell inside the running container)

# Scale a job
nomad job scale construx-api api 5
# Successfully scaled job "construx-api" task group "api" to count 3→5

# Stop a job (without deleting it)
nomad job stop construx-api

# Stop and purge (removes job history)
nomad job stop -purge construx-api
```

## Batch jobs and parameterized jobs

```bash
# Batch job: runs to completion, not continuously
cat > reindex.nomad <<'EOF'
job "reindex" {
  type = "batch"

  group "reindex" {
    count = 1

    task "reindex" {
      driver = "exec"   # run a binary directly, no container

      config {
        command = "/usr/local/bin/construx-reindex"
        args    = ["--index", "products", "--full"]
      }

      resources {
        cpu    = 2000
        memory = 2048
      }
    }
  }
}
EOF

nomad job run reindex.nomad
# Job runs once, Nomad tracks its completion status

# Parameterized job: a job template that takes arguments at dispatch time
cat > report-generator.nomad <<'EOF'
job "report-generator" {
  type = "batch"

  parameterized {
    meta_required = ["report_type", "date_range"]
    meta_optional = ["format"]
  }

  group "generate" {
    task "generate" {
      driver = "docker"

      config {
        image = "registry.construx.io/construx/reporter:latest"
        args  = [
          "--type",  "${NOMAD_META_report_type}",
          "--range", "${NOMAD_META_date_range}",
          "--format","${NOMAD_META_format}",
        ]
      }
    }
  }
}
EOF

nomad job run report-generator.nomad  # registers the template

# Dispatch instances with different parameters
nomad job dispatch -meta report_type=sales -meta date_range=2033-01 report-generator
nomad job dispatch -meta report_type=traffic -meta date_range=2033-01 -meta format=json report-generator
```

## System jobs and multi-driver clusters

```bash
# System job: runs exactly one allocation per node
# Useful for log shippers, monitoring agents, node-level daemons

cat > vector.nomad <<'EOF'
job "vector" {
  type = "system"

  group "vector" {
    task "vector" {
      driver = "docker"
      config {
        image   = "timberio/vector:latest-alpine"
        volumes = [
          "/var/log:/var/log:ro",
          "/var/run/docker.sock:/var/run/docker.sock:ro",
        ]
      }
      resources {
        cpu    = 200
        memory = 128
      }
    }
  }
}
EOF

nomad job run vector.nomad
# Deploys one Vector instance to every node automatically
# New nodes get Vector as they join the cluster

# Mixed-driver cluster: containers + binaries + JVM on the same Nomad cluster
# Java service with exec driver (no Docker)
task "legacy-billing" {
  driver = "java"
  config {
    jar_path    = "local/billing-1.4.7.jar"
    jvm_options = ["-Xmx512m", "-Xms128m"]
    args        = ["--config", "secrets/billing.properties"]
  }
  artifact {
    source = "s3://construx-artifacts/billing-1.4.7.jar"
  }
}

# Everything — containers, JARs, raw binaries — is scheduled by the same
# Nomad server cluster with the same job syntax and monitoring
```

Nomad vs Kubernetes: Kubernetes is the industry standard for containerized workloads but requires everything to be a container and has substantial operational complexity. Nomad's advantage is the multi-driver model — one scheduler for containers, JARs, and binaries, with less infrastructure overhead. The HashiCorp stack (Nomad + Consul + Vault) is a coherent alternative to Kubernetes + service mesh + secrets manager, but with more manual orchestration of features Kubernetes handles natively (StatefulSets, PersistentVolumeClaims, Operators). For teams with mixed workloads (containers + legacy Java) or small clusters where Kubernetes overhead is disproportionate, Nomad is the pragmatic choice.
