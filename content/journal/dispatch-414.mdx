Internationalization (i18n) is one of those features that's easy to add in an MVP and becomes a full-time job if you bolt it on later. The right time to set it up is when you first add more than one locale — even if that's just `en-US` and `en-GB` with different date formats.

## Route structure

The two approaches in Next.js:

**Prefix routing** — locale in the URL path: `/en/about`, `/fr/about`. Clear, cacheable, shareable links. The standard.

**Domain routing** — locale from the hostname: `example.com` vs `example.fr`. More setup. Better for brand reasons.

Prefix routing with next-intl:

```bash
npm install next-intl
```

```
app/
  [locale]/
    layout.tsx
    page.tsx
    about/
      page.tsx
  not-found.tsx   # locale-independent fallback
middleware.ts
```

## Middleware for locale detection

```ts
// middleware.ts
import createMiddleware from 'next-intl/middleware';

export default createMiddleware({
  locales: ['en', 'fr', 'de', 'ja'],
  defaultLocale: 'en',
  localePrefix: 'as-needed',  // skip /en prefix, add /fr, /de, /ja
});

export const config = {
  matcher: ['/((?!api|_next|_vercel|.*\\..*).*)'],
};
```

## Layout and provider

```tsx
// app/[locale]/layout.tsx
import { NextIntlClientProvider } from 'next-intl';
import { getMessages } from 'next-intl/server';
import { notFound } from 'next/navigation';

const locales = ['en', 'fr', 'de', 'ja'] as const;
type Locale = (typeof locales)[number];

export default async function LocaleLayout({
  children,
  params,
}: {
  children: React.ReactNode;
  params: { locale: string };
}) {
  const { locale } = await params;

  if (!locales.includes(locale as Locale)) {
    notFound();
  }

  const messages = await getMessages();

  return (
    <html lang={locale} dir={locale === 'ar' || locale === 'he' ? 'rtl' : 'ltr'}>
      <body>
        <NextIntlClientProvider messages={messages}>
          {children}
        </NextIntlClientProvider>
      </body>
    </html>
  );
}
```

## Using translations

In Server Components:

```tsx
// app/[locale]/ventures/page.tsx
import { useTranslations } from 'next-intl';

export default function VenturesPage() {
  const t = useTranslations('ventures');

  return (
    <div>
      <h1>{t('title')}</h1>
      <p>{t('subtitle')}</p>
      <p>{t('count', { count: ventures.length })}</p>
    </div>
  );
}
```

In Client Components:

```tsx
'use client';

import { useTranslations } from 'next-intl';

export function NavLink({ href, messageKey }: { href: string; messageKey: string }) {
  const t = useTranslations('nav');
  return <a href={href}>{t(messageKey)}</a>;
}
```

## Dates, numbers, and currencies

next-intl wraps the Intl API:

```tsx
import { useFormatter } from 'next-intl';

function PostDate({ date }: { date: Date }) {
  const format = useFormatter();

  return (
    <time dateTime={date.toISOString()}>
      {format.dateTime(date, { dateStyle: 'long' })}
    </time>
  );
}

// en: "January 15, 2028"
// fr: "15 janvier 2028"
// de: "15. Januar 2028"
// ja: "2028年1月15日"
```

```tsx
function Price({ amount, currency }: { amount: number; currency: string }) {
  const format = useFormatter();

  return (
    <span>
      {format.number(amount, { style: 'currency', currency })}
    </span>
  );
}

// en-US: "$1,234.56"
// fr: "1 234,56 €"
// de: "1.234,56 €"
```

## Locale-aware routing

next-intl provides locale-aware `Link` and `useRouter`:

```tsx
import { Link } from '@/i18n/routing';  // generated by next-intl

// Always links to the correct locale prefix
<Link href="/ventures">Ventures</Link>
// en: /ventures
// fr: /fr/ventures
```

```ts
// i18n/routing.ts
import { createNavigation } from 'next-intl/navigation';

export const { Link, redirect, usePathname, useRouter } = createNavigation({
  locales: ['en', 'fr', 'de', 'ja'],
  defaultLocale: 'en',
});
```

## Type safety for message keys

```bash
npx next-intl generate-types
```

This generates TypeScript types from your message files. `t('ventures.titl')` — a typo — becomes a compile error.

## SEO: hreflang tags

```tsx
// app/[locale]/layout.tsx
export async function generateMetadata({ params }: { params: { locale: string } }) {
  const { locale } = await params;
  const locales = ['en', 'fr', 'de', 'ja'];

  return {
    alternates: {
      canonical: `https://construxgroup.io/${locale}`,
      languages: Object.fromEntries(
        locales.map((l) => [l, `https://construxgroup.io/${l}`]),
      ),
    },
  };
}
```

The pattern: locale in the URL path, messages in JSON files per locale, format dates and numbers via the Intl API (not manual string manipulation), type-check message keys. Adding a locale later is a new JSON file and a middleware config line — everything else scales automatically.
