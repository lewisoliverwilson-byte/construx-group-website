The Hyve is built around a central promise: an AI team member that behaves like a colleague, not a chatbot. A colleague who reads everything written in the workspace, remembers decisions, and can be asked weeks later what the team decided about a given problem.

This is a different technical problem than a general-purpose AI assistant. A general assistant has no memory of your specific project. It can only work with what you put in front of it in the current conversation. Building a team member that holds context across months of project history requires a specific architecture.

## The problem with context windows

The naive approach: stuff the entire project history into Claude's context window with every message. Modern frontier models have large context windows — 200k tokens is available on current Claude versions — so this seems viable.

It's not, for three reasons.

**Cost at scale.** A workspace with 6 months of active use accumulates hundreds of thousands of words of messages, decisions, documents, and threads. Sending all of this with every message is expensive and gets more expensive as the project grows.

**Quality degradation.** Even within a large context window, Claude's attention is imperfect on very long contexts. The "lost in the middle" problem is real: information buried in a long context is reliably recalled less well than information at the beginning or end.

**Latency.** Processing 200k tokens of context takes time. For an AI team member that people actually use in conversation, the response latency matters.

## The vector memory architecture

The solution is a vector database as memory. Every message, document, and thread in The Hyve gets embedded and stored in a vector index at the time it's created. When the AI is asked something, a semantic search retrieves the most relevant content from the entire history, and that retrieved content — not the full history — goes into the context.

The result: the AI has access to the entire project history semantically, without processing all of it on every message. A message like "what did we decide about the auth flow?" triggers a semantic search that finds the specific messages and documents about auth decisions, retrieves them, and passes them to Claude as context.

We use a hybrid retrieval approach: semantic search via embedding similarity plus keyword matching for specific technical terms. The combination catches both conceptually similar content and exact terminology.

## What gets embedded

The embedding architecture matters. In The Hyve, everything is embedded:

**Messages** — every message in every channel, with metadata about who sent it and when. This creates a searchable history of all team communication.

**Documents** — the full text of every document created in the workspace. When someone asks about a design decision, the AI can surface the relevant document section.

**Decision records** — The Hyve has a specific `Decision` content type where teams record important choices with context. These are embedded separately with a boosted weight, so documented decisions surface reliably even when asked about them indirectly.

**Thread summaries** — long discussions get periodically summarised. The summary is embedded alongside the original messages, giving the AI a compressed view of long threads.

## The prompt architecture

The retrieval gets the right content in front of Claude. The prompt architecture makes sure Claude uses it correctly.

The system prompt for The Hyve's AI team member is significantly more complex than Scoutr's. It tells Claude:

- You have access to retrieved context from a project workspace. Treat this as genuine memory of what the team has discussed and decided.
- When citing a past decision or conversation, reference it specifically (channel, approximate date, or document name) so the team can verify.
- If the retrieved context doesn't answer the question, say so clearly. Don't hallucinate content from the project that wasn't retrieved.
- You are a team member, not an assistant. Communicate peer-to-peer, not as a subordinate.

That last point matters more than it sounds. The tone and positioning of the AI's responses shapes how teams use it. An AI that answers in assistant-style deference gets treated as a search interface. An AI that responds peer-to-peer gets pulled into actual decisions.

## What didn't work

**Real-time embedding with blocking calls.** Our first version embedded content synchronously when it was created. This added latency to every message send. We moved to async embedding: content is stored immediately and embedded in the background. There's a short window where very recent content isn't yet searchable, but it's never longer than a few seconds and users don't notice it.

**Embedding everything equally.** Not all content is equally relevant for memory. A quick "sounds good" message carries different informational weight than a document explaining an architectural decision. We added content-type weighting to the retrieval ranking — decisions and documents rank higher than casual messages for retrieval quality.

**Over-retrieval.** Early versions retrieved too much context: high recall but low precision. The AI had trouble synthesising a meaningful response from 40 retrieved items. We tuned down to a smaller, higher-precision retrieval set (typically 10-15 items) and saw quality improve significantly.

## The result

In production, the AI team member can accurately answer questions about project history going back months. It references specific decisions by channel and approximate date. It distinguishes between things the team discussed and decided versus things that were considered but rejected.

The experience is genuinely different from a general AI assistant. Teams report that the AI's responses feel like it was in the room — because, in a meaningful sense, it was. It read every message. It knows the context.

This architecture is now the foundation for every AI-native product feature we build across Construx. The vector memory pattern is a core competency we've developed that has direct application to any product where context accumulation over time matters.
