REST is the right default for most APIs. GraphQL is worth the overhead when: multiple client types (web, mobile, third-party) each need different shapes of data; you have a deep graph of related entities that callers need to traverse in arbitrary ways; or you need a self-documenting API that client teams can explore without back-end changes for every new data shape.

If none of those apply, REST is simpler.

## Setting up a GraphQL server with Pothos

Pothos is a code-first GraphQL schema builder for TypeScript. You define your schema in TypeScript, Pothos generates the SDL, and type safety flows through.

```bash
npm install @pothos/core graphql graphql-yoga
npm install -D @graphql-codegen/cli @graphql-codegen/typescript @graphql-codegen/typescript-resolvers
```

```ts
// lib/graphql/builder.ts
import SchemaBuilder from '@pothos/core';

interface Types {
  Scalars: {
    Date: { Input: Date; Output: Date };
  };
}

export const builder = new SchemaBuilder<Types>({});

builder.addScalarType('Date', {
  serialize: (value) => (value as Date).toISOString(),
  parseValue: (value) => new Date(value as string),
});
```

```ts
// lib/graphql/schema/post.ts
import { builder } from '../builder';
import { db } from '@/db';
import { posts, users } from '@/db/schema';
import { eq, desc } from 'drizzle-orm';

const PostType = builder.objectType('Post', {
  fields: (t) => ({
    id: t.exposeString('id'),
    title: t.exposeString('title'),
    body: t.exposeString('body'),
    publishedAt: t.expose('publishedAt', { type: 'Date', nullable: true }),
    author: t.field({
      type: 'User',
      resolve: async (post) => {
        const [author] = await db.select()
          .from(users)
          .where(eq(users.id, post.authorId));
        return author;
      },
    }),
  }),
});

const UserType = builder.objectType('User', {
  fields: (t) => ({
    id: t.exposeString('id'),
    name: t.exposeString('name'),
    email: t.exposeString('email'),
    posts: t.field({
      type: [PostType],
      resolve: async (user) => {
        return db.query.posts.findMany({
          where: eq(posts.authorId, user.id),
          orderBy: [desc(posts.publishedAt)],
        });
      },
    }),
  }),
});

builder.queryType({
  fields: (t) => ({
    posts: t.field({
      type: [PostType],
      resolve: () => db.query.posts.findMany({
        where: eq(posts.published, true),
        orderBy: [desc(posts.publishedAt)],
        limit: 20,
      }),
    }),
    post: t.field({
      type: PostType,
      nullable: true,
      args: { id: t.arg.string({ required: true }) },
      resolve: (_, { id }) => db.query.posts.findFirst({ where: eq(posts.id, id) }),
    }),
  }),
});

export const schema = builder.toSchema();
```

## Route handler with graphql-yoga

```ts
// app/api/graphql/route.ts
import { createYoga } from 'graphql-yoga';
import { schema } from '@/lib/graphql/schema';

const { handleRequest } = createYoga({
  schema,
  graphqlEndpoint: '/api/graphql',
  fetchAPI: { Response, Request },
});

export const GET = handleRequest;
export const POST = handleRequest;
```

Navigate to `/api/graphql` in development and you get GraphiQL — the built-in playground.

## DataLoader for N+1 prevention

The N+1 problem: if you fetch 20 posts and each post resolver hits the database to fetch its author, you make 21 database queries. DataLoader batches and deduplicates these:

```ts
// lib/graphql/loaders.ts
import DataLoader from 'dataloader';
import { db } from '@/db';
import { users } from '@/db/schema';
import { inArray } from 'drizzle-orm';

export function createLoaders() {
  return {
    userById: new DataLoader<string, typeof users.$inferSelect>(
      async (ids) => {
        const rows = await db.select()
          .from(users)
          .where(inArray(users.id, [...ids]));

        const map = new Map(rows.map((u) => [u.id, u]));
        return ids.map((id) => map.get(id) ?? new Error(`User ${id} not found`));
      }
    ),
  };
}
```

```ts
// In the Post type author resolver — use the loader instead of a direct query
author: t.field({
  type: 'User',
  resolve: async (post, _, ctx) => {
    return ctx.loaders.userById.load(post.authorId);
  },
}),
```

20 posts → 1 batched user query instead of 20.

## Client-side querying with urql

```bash
npm install urql graphql
```

```tsx
// providers/UrqlProvider.tsx
'use client';

import { createClient, cacheExchange, fetchExchange, Provider } from 'urql';

const client = createClient({
  url: '/api/graphql',
  exchanges: [cacheExchange, fetchExchange],
});

export function UrqlProvider({ children }: { children: React.ReactNode }) {
  return <Provider value={client}>{children}</Provider>;
}
```

```tsx
// components/PostList.tsx
'use client';

import { useQuery } from 'urql';

const POSTS_QUERY = `
  query Posts {
    posts {
      id
      title
      publishedAt
      author {
        name
      }
    }
  }
`;

export function PostList() {
  const [{ data, fetching, error }] = useQuery({ query: POSTS_QUERY });

  if (fetching) return <p>Loading…</p>;
  if (error) return <p>Error: {error.message}</p>;

  return (
    <ul>
      {data.posts.map((post: { id: string; title: string; author: { name: string } }) => (
        <li key={post.id}>
          {post.title} — {post.author.name}
        </li>
      ))}
    </ul>
  );
}
```

## Code generation for type safety

```yaml
# codegen.yml
schema: http://localhost:3000/api/graphql
generates:
  lib/graphql/__generated__/types.ts:
    plugins:
      - typescript
      - typescript-resolvers
```

```bash
npx graphql-codegen
```

Now your resolver types and query result types are generated from the schema — no manual type maintenance.

## When to stick with REST

GraphQL adds: a schema to maintain, a resolver layer, DataLoader complexity, and client-side query management. That overhead is justified when clients genuinely have divergent data needs. If your API serves a single web app with consistent data requirements, REST with typed route handlers and Zod validation is simpler, faster to develop, and easier to cache.

The question to ask: are clients repeatedly waiting for new API endpoints to get slightly different data shapes? That's the signal GraphQL is worth the cost.
