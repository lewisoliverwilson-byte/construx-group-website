Most writing about AI-first companies focuses on the revenue opportunity. Less is written about the cost structure. Here's an honest account of what it costs to run three live SaaS products with two founders and no external funding.

## The cost categories

**API costs.** The Claude API is our largest variable cost. Every scan in Scoutr, every listing generated for The Marqet, every AI response in The Hyve — all of these are API calls with input and output costs.

The cost per user interaction varies significantly by product. Scoutr scans are high-input (the product page content sent to Claude) and moderate-output (structured product analysis). The Hyve conversations are lower-input but higher in frequency. The Marqet's listing generation is batch-oriented — we generate during setup, not in real time for each user session.

As a rule: API costs are the most important variable to monitor and optimise. They scale directly with usage, unlike infrastructure costs which have a large fixed component.

**Hosting.** AWS Amplify for all three product frontends and the Construx Group site. Railway for The Hyve's real-time backend. The Amplify costs are modest at our current scale — the pricing model (build minutes + bandwidth + requests) keeps costs low for low-to-moderate traffic. Railway scales with the WebSocket connection count and background job volume.

**Database.** PostgreSQL instances for The Hyve. Managed Postgres on Railway is straightforward to provision and maintain. The pgvector extension adds storage overhead (vectors are large) but doesn't require a separate service.

**Email.** Resend for transactional email. Low volume, low cost.

**Analytics.** PostHog's open-source tier covers our analytics needs. No external cost.

**Tooling.** Linear (issue tracking), Figma (design when needed), various development tools. These are stable fixed costs.

## The AI cost trajectory

The most significant financial observation about running AI products: API costs are falling and have been falling consistently.

The cost per token for Claude's models has decreased substantially since we started building. Products that were marginal at early API pricing are comfortably profitable at current pricing. Products that might be marginal today will improve in economics as pricing continues to fall.

This trajectory matters for how you should think about AI product economics. Pricing based on today's API costs builds in margin improvement as costs fall. Pricing based on optimistic future cost projections is risky.

Our approach: use current API costs to model unit economics, treat cost decreases as upside rather than baseline assumptions. The products are viable at current costs; cost decreases improve the margin.

## The portfolio cost advantage

Running three products has a portfolio effect on costs that isn't obvious until you're doing it.

Some costs are shared:
- **Tooling and subscriptions** are team-level fixed costs, not per-product costs. Linear, Figma, GitHub — one subscription serves three products.
- **AWS infrastructure** has some shared economies. Shared monitoring, shared deployment practices, shared knowledge of how to configure things correctly.
- **Operational knowledge** compounds across products. The process we developed for Scoutr (monitoring API costs, response quality sampling, deployment workflow) applied to The Marqet and The Hyve with minimal adaptation.

Some costs don't scale with product count as much as you'd expect:
- The marginal cost of running a second product is lower than the cost of running the first, for costs that are fixed at the team level.
- The learning about what matters (reliable error monitoring, consistent deployment processes) doesn't have to be relearned per product.

## What we've learned about cost control

**Monitoring API costs daily.** API costs can spike unexpectedly — a new feature with inefficient prompting, an unusual usage pattern, an unexpected volume increase. Catching this daily rather than monthly makes the response time much faster.

**Caching aggressively.** Claude caches repeated prompt prefixes. Well-structured prompts with static content at the top and dynamic content at the end take advantage of this. The cache hit rate matters financially.

**Model selection by task.** Not all tasks need the most capable model. Routine classification tasks (identifying product categories in Scoutr) run on lighter models. Complex reasoning tasks (understanding a nuanced user question in The Hyve) use the full capability.

**Setting hard limits on API spend.** We have budget limits per product. If an unexpected spike hits a limit, it triggers an alert rather than an uncapped cost increase. We've never hit a limit in production, but the guardrail is there.

## The honest picture

Two founders, three live products, no external funding. The portfolio is profitable on current revenue. API and infrastructure costs are real but manageable.

What makes this possible: the tools available to small teams today are qualitatively better than they were five years ago. Claude's API is both cheap enough and capable enough to build real products on. Amplify makes deployment trivial. The modern JavaScript stack is productive for small teams.

What we've preserved by not taking funding: control over priorities, product design, and timeline. We don't answer to investors who want faster growth at the expense of product quality. We build things we believe in at the pace that produces good work.

The portfolio model has another advantage: diversification. Three products with different user bases and use cases means a problem with one product (a competitor, a market shift, a technical issue) doesn't stop the business. The others continue.

We didn't plan the portfolio as a financial strategy. It emerged from wanting to build multiple things and having the capacity to do so. The financial advantage was a discovery, not a plan.
