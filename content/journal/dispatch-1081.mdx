date: "2033-10-31"
excerpt: "Crossplane (introduced in dispatch-1040 for basic provider setup) becomes significantly more powerful with Compositions. A Composition maps a custom Composite Resource Definition (XRD) to one or more managed resources. You define an XRD that represents a high-level concept — a construx.io/v1alpha1 Database — and a Composition that specifies how to realise that Database from underlying provider resources (an AWS RDSInstance, a SecurityGroup, a SubnetGroup, a parameter group Secret). A platform team owns the Composition; application teams create Database claims without knowing anything about RDS. This is the infrastructure abstraction layer: the same Database claim works across AWS (using the AWS provider) and Azure (using the Azure provider) because the Composition maps to provider-specific resources behind the scenes. Composition functions (available since Crossplane v1.14) allow writing the mapping logic in Go, Python (via Crossplane Functions), or Starlark — enabling conditions, loops, and dynamic resource generation that pure YAML Patches cannot express. The rendered managed resources are fully observable via kubectl, Prometheus, and the standard Kubernetes event system."

## CompositeResourceDefinition and Composition

```yaml
# XRD: defines the API that application teams interact with
# This is a "Database" abstraction — teams request a database, not an RDS instance

apiVersion: apiextensions.crossplane.io/v1
kind: CompositeResourceDefinition
metadata:
  name: xdatabases.construx.io
spec:
  group: construx.io
  names:
    kind:     XDatabase
    plural:   xdatabases
  claimNames:
    kind:   Database     # namespace-scoped claim — what app teams create
    plural: databases
  versions:
    - name: v1alpha1
      served:       true
      referenceable: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                parameters:
                  type: object
                  properties:
                    storageGB:
                      type:    integer
                      default: 20
                    instanceClass:
                      type:    string
                      default: db.t4g.medium
                    engine:
                      type: string
                      enum: [postgres, mysql]
                      default: postgres
                    multiAZ:
                      type:    boolean
                      default: false
              required: [parameters]
---
# Composition: maps XDatabase to AWS RDS resources
apiVersion: apiextensions.crossplane.io/v1
kind: Composition
metadata:
  name: xdatabases-aws-rds
  labels:
    provider: aws
    environment: prod
spec:
  compositeTypeRef:
    apiVersion: construx.io/v1alpha1
    kind:       XDatabase

  resources:
    # Resource 1: RDS subnet group
    - name: subnet-group
      base:
        apiVersion: rds.aws.upbound.io/v1beta1
        kind:       SubnetGroup
        spec:
          forProvider:
            region:           eu-west-2
            subnetIdSelector:
              matchLabels:
                access: private

    # Resource 2: RDS instance
    - name: rds-instance
      base:
        apiVersion: rds.aws.upbound.io/v1beta1
        kind:       Instance
        spec:
          forProvider:
            region:            eu-west-2
            engine:            postgres
            engineVersion:     "16"
            skipFinalSnapshot: false
            storageType:       gp3
            dbSubnetGroupNameSelector:
              matchControllerRef: true
      patches:
        # Map XDatabase.spec.parameters.storageGB → RDS allocatedStorage
        - type:          FromCompositeFieldPath
          fromFieldPath: spec.parameters.storageGB
          toFieldPath:   spec.forProvider.allocatedStorage
        - type:          FromCompositeFieldPath
          fromFieldPath: spec.parameters.instanceClass
          toFieldPath:   spec.forProvider.instanceClass
        - type:          FromCompositeFieldPath
          fromFieldPath: spec.parameters.multiAZ
          toFieldPath:   spec.forProvider.multiAz
```

## Application team workflow and composition functions

```yaml
# Application team creates a Database claim — no knowledge of RDS required
apiVersion: construx.io/v1alpha1
kind: Database
metadata:
  name:      construx-prod-db
  namespace: construx-prod
spec:
  compositionSelector:
    matchLabels:
      provider:     aws
      environment:  prod
  parameters:
    storageGB:     100
    instanceClass: db.r7g.large
    engine:        postgres
    multiAZ:       true
  # Crossplane writes the connection details to this Secret
  writeConnectionSecretToRef:
    name: construx-prod-db-credentials
```

```bash
# Observe the claim and composite resource lifecycle

# Application team view: just the Database claim
kubectl get database -n construx-prod
# NAME                SYNCED  READY   CONNECTION-SECRET       AGE
# construx-prod-db    True    True    construx-prod-db-creds  4d

# Platform team view: the composite resource and its managed resources
kubectl get xdatabase
# NAME                         SYNCED  READY  COMPOSITION              AGE
# construx-prod-construx-prod  True    True   xdatabases-aws-rds       4d

kubectl get managed | grep construx-prod
# NAME                           SYNCED  READY  EXTERNAL-NAME       AGE
# subnetgroup/construx-prod-xk2  True    True   construx-prod-xk2   4d

# Composition Function: Python function for dynamic resource generation
```

Crossplane Compositions vs Terraform modules vs Pulumi components vs Helm charts for infrastructure abstraction: Terraform modules are the standard infrastructure abstraction — parameterised HCL that provisions cloud resources. The key difference from Crossplane is the execution model: Terraform state is external (S3 backend, Terraform Cloud), and applying a change requires running a pipeline. Crossplane runs the reconciliation loop continuously inside the cluster — drift from out-of-band changes is detected and corrected automatically, the same way Kubernetes corrects pod drift. Pulumi components use general-purpose languages (TypeScript, Go, Python) for infrastructure composition — more expressive than YAML Compositions, but still pipeline-driven. Helm charts can template Kubernetes objects but have no native cloud resource provisioning. Crossplane is the right choice when your platform already runs Kubernetes and you want to expose infrastructure (databases, message queues, S3 buckets) as Kubernetes-native APIs that application teams consume via kubectl and GitOps — no separate toolchain, no separate state backend, just Kubernetes CRDs all the way down.
