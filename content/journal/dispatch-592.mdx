A database index is a separate data structure that lets Postgres find rows without scanning every row in the table. Without an index on a filter column, Postgres reads every row (sequential scan). With an index, it reads only the matching rows (index scan). The tradeoff: indexes make reads faster at the cost of slower writes (every write must update all relevant indexes) and storage.

## B-tree: the default

B-tree (balanced tree) is the default index type for `CREATE INDEX`. It handles:
- Equality: `WHERE id = 'abc'`
- Range: `WHERE created_at > '2029-01-01'`
- Prefix matching: `WHERE slug LIKE 'react-%'`
- Sorting: `ORDER BY created_at DESC`
- `IS NULL` / `IS NOT NULL`

```sql
CREATE INDEX idx_posts_author_id ON posts (author_id);
CREATE INDEX idx_posts_created_at ON posts (created_at DESC);
```

Most indexes in a typical web application are B-trees. They're the right default.

## Composite indexes

A composite index covers multiple columns. It's useful when queries filter on multiple columns together:

```sql
CREATE INDEX idx_posts_author_status ON posts (author_id, status);
```

A query `WHERE author_id = 'x' AND status = 'published'` can use this index fully. A query `WHERE author_id = 'x'` can also use it (the leftmost prefix). A query `WHERE status = 'published'` alone cannot — it would need a separate index on `status`.

The rule: the leftmost columns of a composite index must appear in the query's WHERE clause for the index to be useful.

**Column ordering in composite indexes**: put the most selective column first (the one with the most distinct values). An index on `(author_id, status)` is better than `(status, author_id)` if there are few statuses but many authors.

## Partial indexes

A partial index only indexes rows matching a condition. Much smaller, faster to scan:

```sql
-- Only index published posts
CREATE INDEX idx_posts_published ON posts (created_at DESC)
WHERE status = 'published';

-- Only index unprocessed jobs
CREATE INDEX idx_jobs_pending ON jobs (created_at)
WHERE processed = false;
```

The partial index is only used for queries that include the same WHERE condition. Smaller index = faster lookups and less memory pressure on the buffer cache.

## Hash indexes

Hash indexes store a hash of the column value. They're faster than B-tree for equality lookups, but they can't handle ranges, sorting, or prefix matching.

```sql
CREATE INDEX idx_sessions_token ON sessions USING HASH (token);
```

Only use hash indexes when:
- The column is only ever queried with `=`
- The column has high cardinality (many distinct values)
- Range queries on this column are never needed

Session tokens are a classic case: always queried with equality, never sorted or ranged.

## GIN: arrays, JSONB, and full-text search

GIN (Generalized Inverted Index) handles complex types where a single row can match multiple queries.

**Full-text search**:

```sql
-- Add a tsvector column
ALTER TABLE posts ADD COLUMN search_vector tsvector
  GENERATED ALWAYS AS (
    to_tsvector('english', coalesce(title, '') || ' ' || coalesce(content, ''))
  ) STORED;

CREATE INDEX idx_posts_search ON posts USING GIN (search_vector);

-- Query
SELECT * FROM posts WHERE search_vector @@ to_tsquery('english', 'react & typescript');
```

**JSONB containment**:

```sql
CREATE INDEX idx_events_metadata ON events USING GIN (metadata);

-- Uses the GIN index
SELECT * FROM events WHERE metadata @> '{"type": "click", "source": "homepage"}';
```

**Array containment**:

```sql
CREATE INDEX idx_posts_tags ON posts USING GIN (tags);

-- Find posts with all these tags
SELECT * FROM posts WHERE tags @> ARRAY['react', 'typescript'];
```

## CONCURRENTLY: safe index creation in production

`CREATE INDEX` locks the table for writes while building. `CREATE INDEX CONCURRENTLY` builds the index without locking — slower, but doesn't block your application:

```sql
CREATE INDEX CONCURRENTLY idx_posts_author_id ON posts (author_id);
```

Always use `CONCURRENTLY` on production tables with traffic. The downside: it can't run inside a transaction.

## When not to index

- **Small tables** (under a few thousand rows): a sequential scan is often faster. Postgres ignores indexes when the table is small enough that the overhead of the index lookup exceeds the cost of the scan.
- **Write-heavy columns**: every write must update all indexes. A table that gets millions of inserts per second shouldn't have excessive indexes.
- **Low-selectivity columns**: a boolean column with 90% true values — an index on it is nearly useless, since Postgres would rather scan than fetch 90% of the table through an index.

Use `EXPLAIN ANALYZE` to verify that an index is being used after creating it. Postgres may choose not to use it if it estimates a sequential scan is faster.
