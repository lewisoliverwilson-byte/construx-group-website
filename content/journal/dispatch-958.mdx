title: "Linkerd: lightweight service mesh with automatic mTLS and golden metrics"
date: "2032-10-27"
excerpt: "Linkerd is a CNCF service mesh for Kubernetes that adds automatic mTLS encryption between services, Prometheus-compatible golden metrics (success rate, request rate, latency percentiles) per route, and traffic management (weighted routing, retries, timeouts) — without requiring any application code changes. Unlike Istio (which uses Envoy as the data plane), Linkerd uses its own Rust-based micro-proxy (linkerd2-proxy) with a significantly smaller footprint: ~100MB per pod vs Envoy's ~500MB. The control plane issues mTLS certificates to every pod's proxy automatically via the trust anchor. Linkerd's diagnostic CLI (`linkerd check`, `linkerd viz top`, `linkerd stat`) surfaces per-service health in real time."

Auto mTLS between every pod. Golden metrics per route. Rust proxy. No Envoy, no YAML marathon.

## Installation and verification

```bash
# Install Linkerd CLI
curl --proto '=https' --tlsv1.2 -sSfL https://run.linkerd.io/install | sh
export PATH=$PATH:$HOME/.linkerd2/bin

# Pre-install checks (cluster readiness)
linkerd check --pre
# kubernetes-api: can initialize the client ✓
# kubernetes-version: is running the minimum version ✓
# pre-kubernetes-cluster-setup: control plane namespace does not already exist ✓

# Install the control plane
linkerd install --crds | kubectl apply -f -
linkerd install | kubectl apply -f -

# Verify installation
linkerd check
# linkerd-config: control plane Namespace exists ✓
# linkerd-existence: control plane pods are ready ✓
# linkerd-proxy-injector: proxy-injector pod is running ✓
# control-plane-ca: certificate is valid for at least 60 days ✓

# Install the Viz extension (metrics dashboard)
linkerd viz install | kubectl apply -f -
linkerd check

# Open the dashboard
linkerd viz dashboard
# Linkerd dashboard available at: http://localhost:50750/namespaces/construx
```

## Injecting the proxy

```bash
# Linkerd injects its micro-proxy as a sidecar — annotation-based
# Two methods: manual inject or namespace-level auto-injection

# Auto-inject: annotate the namespace
kubectl annotate namespace construx linkerd.io/inject=enabled

# All new pods in the namespace get the sidecar automatically
kubectl rollout restart deployment -n construx

# Or inject manually into a specific deployment
kubectl get deployment construx-api -n construx -o yaml | \
  linkerd inject - | \
  kubectl apply -f -

# Verify injection
linkerd check --proxy -n construx
linkerd viz stat deploy -n construx
# NAME            MESHED   SUCCESS   RPS     LATENCY_P50  LATENCY_P95  LATENCY_P99
# construx-api    3/3      100.00%   142.1   8.4ms        32.1ms       84.2ms
# construx-worker 2/2       99.84%    18.4   12.1ms       41.3ms       98.4ms
# postgres        1/1      100.00%     8.2   4.1ms         9.2ms       14.8ms
```

## Golden metrics and traffic observing

```bash
# linkerd viz top: live per-route traffic (like top for HTTP)
linkerd viz top deploy/construx-api -n construx

# SOURCE          DESTINATION   METHOD  PATH             COUNT   BEST   WORST  LAST   SUCCESS
# construx-web    construx-api  GET     /v1/orders        48.2    8ms   142ms   12ms   100.00%
# construx-worker construx-api  POST    /v1/orders/status  8.1   12ms    84ms   18ms    99.84%
# prometheus      construx-api  GET     /metrics           0.1    4ms     8ms    5ms   100.00%

# linkerd viz tap: stream live request/response headers
linkerd viz tap deploy/construx-api -n construx --namespace construx
# req id=0:1 proxy=in  src=10.0.1.100:42810 dst=10.0.2.200:8080 :method=GET :path=/v1/orders :authority=construx-api:8080
# rsp id=0:1 proxy=in  src=10.0.1.100:42810 dst=10.0.2.200:8080 :status=200 latency=12841µs

# Filter tap to a specific route
linkerd viz tap deploy/construx-api -n construx \
  --method GET \
  --path /v1/orders \
  --to deploy/construx-api

# linkerd viz routes: per-route metrics (requires ServiceProfile)
linkerd viz routes deploy/construx-api -n construx

# Edges: show mTLS status between services
linkerd viz edges deploy -n construx
# SRC            DST            SRC-NS    DST-NS    SECURED
# construx-web   construx-api   construx  construx  √ (mTLS)
# construx-api   postgres       construx  construx  √ (mTLS)
```

## Traffic management with ServiceProfiles

```yaml
# ServiceProfile: per-route configuration for retries, timeouts, and metrics
apiVersion: linkerd.io/v1alpha2
kind: ServiceProfile
metadata:
  name: construx-api.construx.svc.cluster.local
  namespace: construx
spec:
  routes:
    - name: GET /v1/orders
      condition:
        method: GET
        pathRegex: /v1/orders(/.*)?
      responseClasses:
        - condition:
            status:
              min: 500
              max: 599
          isFailure: true   # 5xx counts as failure for success rate
      timeout: 30s

    - name: POST /v1/orders
      condition:
        method: POST
        pathRegex: /v1/orders
      isRetryable: true        # retry on failure (idempotency required)
      timeout: 60s
```

```bash
# Apply ServiceProfile
kubectl apply -f service-profile.yaml

# Now per-route metrics appear in linkerd viz routes
linkerd viz routes deploy/construx-api -n construx
# ROUTE                    SUCCESS   EFFECTIVE-RPS   ACTUAL-RPS   LATENCY_P99
# GET /v1/orders           100.00%         48.2          48.2        84.2ms
# POST /v1/orders           99.84%          8.1           8.3        98.4ms  ← retries add ~0.2 RPS
# [DEFAULT]                 100.00%          2.1           2.1        12.4ms

# Weighted routing: traffic split between two deployments (canary)
kubectl apply -f - <<EOF
apiVersion: split.smi-spec.io/v1alpha2
kind: TrafficSplit
metadata:
  name: construx-api-split
  namespace: construx
spec:
  service: construx-api
  backends:
    - service: construx-api-stable
      weight: 900m   # 90%
    - service: construx-api-canary
      weight: 100m   # 10%
EOF
```

Linkerd vs Istio: Istio is the most feature-rich service mesh — advanced traffic management (circuit breaking, fault injection, external auth), a larger community, and first-class integration with the full Envoy ecosystem. Linkerd is simpler and lighter — mTLS, golden metrics, and basic traffic management work out of the box with less configuration. The Rust proxy is ~5× smaller than Envoy, which matters in large clusters where sidecars run on every pod. The practical choice: start with Linkerd if you need mTLS and observability without the Istio complexity tax. Move to Istio if you need advanced traffic policies (JWT authentication, WebAssembly extensions, egress control), or if you're already heavily invested in Envoy.
