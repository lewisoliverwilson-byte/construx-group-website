Static Site Generation (SSG) and Incremental Static Regeneration (ISR) are two points on the same spectrum: how much staleness can the page tolerate? SSG is zero-latency, infinitely cacheable, and always stale. ISR is zero-latency for most visitors, regenerates on a schedule, and is sometimes slightly stale.

The decision is almost never about performance — both are fast. It's about correctness: would a user seeing data that's 10 minutes old be a problem?

## The options in Next.js 15

**Static (SSG):** The page builds at deploy time. Content is frozen until the next deploy. Correct for content that changes only when you deploy — marketing pages, the manifesto, static content like `/uses`.

```ts
// No fetch = static by default in Next.js 15
export default async function ManifestoPage() {
  return <div>...</div>;
}
```

**ISR:** The page builds at deploy time, then rebuilds on a schedule (or on demand). Correct for content that changes independently of deploys — journal indexes, product listings, public dashboards.

```ts
// app/journal/page.tsx
export const revalidate = 3600; // Rebuild at most every hour

export default async function JournalPage() {
  const posts = await getPosts(); // Will rerun on ISR rebuild
  return <div>...</div>;
}
```

**Dynamic (SSR):** The page renders on every request. Correct for personalised content, auth-gated pages, anything that requires the current session.

```ts
// app/dashboard/page.tsx
export const dynamic = 'force-dynamic';

export default async function DashboardPage() {
  const session = await getSession();
  const data = await getUserData(session.userId);
  return <div>...</div>;
}
```

## The decision tree

**Is the page auth-gated or personalised?**
→ Yes: dynamic. No static content for authenticated state.
→ No: continue.

**Does the content change more than once per deploy?**
→ No: SSG. The journal entry itself, the manifesto, the about page.
→ Yes: continue.

**Can the page tolerate being 5-60 minutes stale?**
→ Yes: ISR with `revalidate = 300` (5 minutes) to `revalidate = 3600` (1 hour).
→ No: dynamic, or ISR with a very short revalidate (60 seconds).

## ISR on Next.js + Amplify

On AWS Amplify with Next.js 15, ISR is supported via Lambda function URLs and an S3-backed cache. The setup is handled automatically when you deploy a Next.js project — Amplify detects the `revalidate` exports and configures the cache infrastructure.

The one gotcha: `revalidate = 0` is treated as `dynamic = 'force-dynamic'` in Next.js 15. If you want short-interval ISR, use a positive number:

```ts
export const revalidate = 30; // Minimum 30 seconds, not 0
```

## On-demand revalidation

For content that should update immediately when something changes (a new post published, a product price updated), on-demand revalidation is more precise than a polling interval:

```ts
// app/api/revalidate/route.ts
import { revalidatePath, revalidateTag } from 'next/cache';

export async function POST(req: Request) {
  const authHeader = req.headers.get('authorization');
  if (authHeader !== `Bearer ${process.env.REVALIDATION_SECRET}`) {
    return new Response('Unauthorized', { status: 401 });
  }

  const { path, tag } = await req.json();

  if (path) {
    revalidatePath(path);
  }

  if (tag) {
    revalidateTag(tag);
  }

  return Response.json({ revalidated: true });
}
```

Then from your CMS webhook or admin action:

```ts
await fetch('/api/revalidate', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'Authorization': `Bearer ${process.env.REVALIDATION_SECRET}`,
  },
  body: JSON.stringify({ path: '/journal' }),
});
```

## Tagging fetch calls for selective invalidation

Next.js 15's `fetch` supports cache tags. Tag a fetch, and you can invalidate all pages that used that data without touching others:

```ts
// In a data-fetching function
const posts = await fetch('/api/posts', {
  next: { tags: ['posts'] },
}).then((r) => r.json());

// To invalidate all pages that fetched with tag 'posts':
revalidateTag('posts');
```

This is the most precise tool: a new post is published → `revalidateTag('posts')` → the journal index and homepage rebuild, but nothing else.

## What we use on construx-group-website

The site is mostly SSG — journal entries, ventures, the manifesto, founders page — because the content changes only at deploy time. The journal index uses `revalidate = 3600` because it reflects new posts, but an hour of staleness is fine. The stats and now pages are SSG with static values computed at build time, updated on each deploy.

Nothing on the site needs SSR. The dashboard products (Scoutr, The Marqet) are dynamic because they're auth-gated, but the public-facing pages are all static or ISR.

The pattern: start with SSG, add ISR when content changes faster than your deploy frequency, add SSR only when you can't avoid it.
