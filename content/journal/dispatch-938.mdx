excerpt: "hyperfine is a command-line benchmarking tool written in Rust that treats measurement as a statistics problem, not just timing. It runs warmup iterations to prime caches, then runs the target command N times, reporting mean, standard deviation, min, and max. When comparing two commands it runs a Welch t-test and reports the speedup with a p-value. The --parameter-list flag sweeps a variable across a list of values — useful for benchmarking across input sizes or config flags. --export-json writes machine-readable results for CI regression tracking. hyperfine handles shell expansion, environment variable setup, and command caching via --prepare, making it the right tool for any benchmark where 'time' isn't repeatable enough."

Warmup. Statistical significance. Parameter sweeps. Export to JSON for regression CI.

## Basic benchmarking

```bash
# hyperfine: run a command N times and report statistics
hyperfine 'construx-api --dry-run'
# Benchmark: construx-api --dry-run
#   Time (mean ± σ):     142.3 ms ± 4.8 ms  [User: 118.2 ms, System: 24.1 ms]
#   Range (min … max):   136.1 ms … 154.7 ms   10 runs

# --warmup: run N times before measuring (prime CPU caches, JIT, OS page cache)
hyperfine 'construx-api --dry-run' --warmup 3

# --runs: control the sample count (more = more accurate stddev, slower total time)
hyperfine 'go test ./...' --warmup 1 --runs 5

# --min-runs / --max-runs: let hyperfine decide based on time budget
hyperfine 'pg-query --plan' --min-runs 10 --max-runs 100

# --shell: specify which shell to use (or 'none' to skip shell entirely)
hyperfine --shell=none '/usr/local/bin/construx-api --dry-run'  # avoids shell startup overhead

# --prepare: run a command before each benchmark run (cache invalidation, state reset)
hyperfine 'cat /var/lib/construx/state.db | wc -l' \
  --prepare 'sync; echo 3 > /proc/sys/vm/drop_caches'   # clear page cache before each run
```

## Comparing commands

```bash
# Compare two commands — hyperfine interleaves runs for fairness
hyperfine \
  'construx-api --engine=v1' \
  'construx-api --engine=v2' \
  --warmup 5 --runs 20

# Benchmark 1: construx-api --engine=v1
#   Time (mean ± σ): 183.4 ms ± 7.2 ms
# Benchmark 2: construx-api --engine=v2
#   Time (mean ± σ): 142.3 ms ± 4.8 ms
# Summary: engine=v2 is 1.29× faster (p < 0.001)

# p-value interpretation:
# p < 0.001 → very strong evidence the difference is real
# p < 0.05  → statistically significant
# p ≥ 0.05  → difference could be noise — run more iterations

# Name benchmarks for clarity
hyperfine \
  --command-name 'v1 (sync resolver)' 'construx-api --engine=v1' \
  --command-name 'v2 (async resolver)' 'construx-api --engine=v2'

# Compare jq vs gojq for JSON processing
hyperfine \
  'jq ".results[] | .latency" data.json' \
  'gojq ".results[] | .latency" data.json' \
  --warmup 3
```

## Parameter sweeps

```bash
# --parameter-list: sweep a variable across values
# {size} is substituted into the command string
hyperfine \
  --parameter-list size 1k,10k,100k,1m \
  'jq . data-{size}.json' \
  --warmup 2

# jq . data-1k.json:      5.4 ms ±  0.3 ms
# jq . data-10k.json:    41.2 ms ±  1.8 ms
# jq . data-100k.json:  318.7 ms ± 11.4 ms
# jq . data-1m.json:   2847.1 ms ± 38.2 ms  ← linear scaling confirmed

# --parameter-scan: sweep a numeric range (start, end, step)
hyperfine \
  --parameter-scan workers 1 8 \
  'construx-worker --threads={workers} --bench'

# workers=1:  842 ms  ← baseline
# workers=2:  431 ms  ← ~2× speedup (near linear)
# workers=4:  221 ms  ← ~3.8× (diminishing returns)
# workers=8:  148 ms  ← ~5.7× (IO-bound portion limits scaling)

# Shell expansion in parameter list
hyperfine \
  --parameter-list compression 'none,gzip,zstd,lz4' \
  'construx-pack --compression={compression} payload.bin'
```

## Export and CI integration

```bash
# --export-json: machine-readable output for regression tracking
hyperfine 'construx-api --dry-run' \
  --warmup 3 --runs 50 \
  --export-json "bench-$(git rev-parse --short HEAD).json"

# JSON schema:
# {
#   "results": [{
#     "command": "construx-api --dry-run",
#     "mean": 0.1423,
#     "stddev": 0.0048,
#     "median": 0.1419,
#     "user": 0.1182,
#     "system": 0.0241,
#     "min": 0.1361,
#     "max": 0.1547,
#     "times": [0.1388, 0.1412, ...]
#   }]
# }

# CI regression check: fail if mean > threshold
MEAN=$(hyperfine 'construx-api --dry-run' --runs 20 --export-json /tmp/bench.json \
  --warmup 3 -q && jq '.results[0].mean' /tmp/bench.json)
THRESHOLD=0.200   # 200ms
awk "BEGIN { exit ($MEAN > $THRESHOLD) }" && echo "PASS: ${MEAN}s" || echo "FAIL: ${MEAN}s > ${THRESHOLD}s"

# --export-markdown: table for PR comments
hyperfine \
  'construx-api --engine=v1' \
  'construx-api --engine=v2' \
  --export-markdown bench.md

# --export-csv: for spreadsheet analysis
hyperfine \
  --parameter-list workers 1,2,4,8 \
  'construx-worker --threads={workers}' \
  --export-csv scaling.csv
```

hyperfine vs time vs wrk: `time` gives you one sample — no warmup, no statistics, subject to OS scheduling jitter. `wrk` is for HTTP load testing (throughput, latency percentiles under concurrency). hyperfine is for benchmarking individual commands: it treats the problem statistically, handles warmup, and produces reproducible numbers you can compare across commits. The right mental model: use hyperfine when the question is "is this change faster?" and you need a defensible answer. One `time` run is not a defensible answer. hyperfine with 20+ runs and a p-value is.
