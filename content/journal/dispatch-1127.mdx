title: "OpenTelemetry Collector: receiver → processor → exporter pipelines, sampling, tail-based sampling"
date: "2034-03-18"
excerpt: "The OpenTelemetry Collector is a vendor-agnostic telemetry processing pipeline that receives traces, metrics, and logs from instrumented services, transforms them, and exports them to any backend (Tempo, Prometheus, Loki, Jaeger, Datadog, Elasticsearch, and dozens of others). It runs as a sidecar (per-pod) or as a centrally deployed gateway (per-cluster), sitting between instrumented services and observability backends. The collector's pipeline model is receiver → processor → exporter: receivers accept telemetry in any format (OTLP, Jaeger, Zipkin, Prometheus scrape, StatsD, Kafka); processors transform, filter, sample, and enrich the data; exporters send to backends in their native format. Tail-based sampling is one of the collector's most powerful features: instead of making sampling decisions at the application level (where you don't know if a trace will be interesting until it's complete), the tail sampling processor waits until all spans for a trace arrive, then applies rules — keep 100% of error traces, keep 1% of successful traces, keep 100% of traces slower than 2 seconds. This gives representative sampling without losing important traces. The collector's resource detection processor automatically enriches telemetry with cloud metadata (AWS region, instance type, Kubernetes pod name, namespace, cluster) by querying the local metadata API, so developers don't have to manually add this information to every service."

## OTel Collector config: full pipeline

```yaml
# otelcol-config.yaml: full collector pipeline configuration
# Deployed as DaemonSet (one per node) collecting from all pods on that node

receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

  prometheus:
    config:
      scrape_configs:
        - job_name: "kubernetes-pods"
          kubernetes_sd_configs:
            - role: pod
          relabel_configs:
            - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
              action: keep
              regex: "true"
            - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_port]
              action: replace
              target_label: __address__
              regex: (.+)
              replacement: $${1}

  k8s_events:
    namespaces: [construx-prod, construx-staging]

  kubeletstats:
    collection_interval: 30s
    auth_type: serviceAccount
    endpoint: "${K8S_NODE_NAME}:10250"
    insecure_skip_verify: true
    metric_groups: [node, pod, container]

processors:
  batch:
    send_batch_size: 512
    timeout: 200ms
    send_batch_max_size: 1024

  memory_limiter:
    check_interval: 1s
    limit_mib: 512
    spike_limit_mib: 128

  resource_detection:
    detectors: [env, eks, ec2]    # auto-enrich with cloud metadata
    timeout: 5s
    override: false

  # Kubernetes attributes: add pod/namespace/deployment labels from k8s API
  k8sattributes:
    auth_type: serviceAccount
    passthrough: false
    extract:
      metadata:
        - k8s.pod.name
        - k8s.pod.uid
        - k8s.deployment.name
        - k8s.namespace.name
        - k8s.node.name
        - k8s.pod.start_time
      labels:
        - tag_name: app.label
          key: app.kubernetes.io/name
          from: pod

  # Tail-based sampling: make sampling decisions after trace is complete
  tail_sampling:
    decision_wait: 30s            # wait up to 30s for all spans to arrive
    num_traces: 100000            # max traces in memory buffer
    policies:
      - name: error-traces
        type: status_code
        status_code: {status_codes: [ERROR]}   # 100% of error traces
      - name: slow-traces
        type: latency
        latency: {threshold_ms: 2000}          # 100% of traces > 2s
      - name: sample-all-services
        type: probabilistic
        probabilistic: {sampling_percentage: 1}  # 1% of all other traces

  # Transform: add custom attributes, rename fields
  transform:
    trace_statements:
      - context: span
        statements:
          - set(attributes["construx.env"], "prod")
          - set(attributes["construx.version"], "${SERVICE_VERSION}")

exporters:
  otlp/tempo:
    endpoint: tempo-distributor.construx-monitoring.svc.cluster.local:4317
    tls:
      insecure: true

  prometheusremotewrite:
    endpoint: http://mimir-nginx.construx-monitoring.svc.cluster.local/api/v1/push
    tls:
      insecure: true

  loki:
    endpoint: http://loki-gateway.construx-monitoring.svc.cluster.local/loki/api/v1/push

extensions:
  health_check:
    endpoint: 0.0.0.0:13133
  pprof:
    endpoint: 0.0.0.0:1777
  zpages:
    endpoint: 0.0.0.0:55679

service:
  extensions: [health_check, pprof, zpages]
  pipelines:
    traces/prod:
      receivers:  [otlp]
      processors: [memory_limiter, k8sattributes, resource_detection, tail_sampling, batch]
      exporters:  [otlp/tempo]

    metrics/prod:
      receivers:  [otlp, prometheus, kubeletstats]
      processors: [memory_limiter, k8sattributes, resource_detection, batch]
      exporters:  [prometheusremotewrite]

    logs/prod:
      receivers:  [otlp, k8s_events]
      processors: [memory_limiter, k8sattributes, resource_detection, batch]
      exporters:  [loki]
```

```bash
# OTel Collector: operational commands and debugging

# Check collector health (liveness probe endpoint)
curl -s http://otelcol:13133/

# zpages: live diagnostic pages (no external tools needed)
# Shows pipeline stats, span samples, service info
curl -s http://otelcol:55679/debug/tracez | head -50

# pprof: CPU and memory profiling of the collector itself
go tool pprof http://otelcol:1777/debug/pprof/heap

# Prometheus metrics: collector's own telemetry
curl -s http://otelcol:8888/metrics | grep -E "otelcol_receiver_accepted|otelcol_exporter_sent|otelcol_processor_refused"

# otelcol validate: check config file syntax before deploying
otelcol validate --config=otelcol-config.yaml

# Generate test telemetry for collector debugging
# (telemetrygen tool from OTel contrib)
telemetrygen traces --otlp-endpoint otelcol:4317 \
  --traces 1000 --rate 10 \
  --service orders-api

telemetrygen metrics --otlp-endpoint otelcol:4317 \
  --metrics 100 --rate 10
```

OTel Collector vs Fluent Bit vs Logstash vs Vector vs direct SDK export: Direct SDK export (service sends traces directly to Tempo, metrics directly to Prometheus) eliminates the collector hop but requires every service to know every backend — changing backends requires updating all services. The collector decouples services from backends: services always send to the collector's OTLP endpoint; the collector routes to whatever backends are configured. Fluent Bit is the canonical log shipping sidecar — extremely efficient for log collection, but not designed for traces or metrics. Logstash is the ELK stack's processing pipeline — powerful for log enrichment but heavy (JVM), and not the right tool for traces or metrics. Vector (by Datadog) is a modern, Rust-based observability pipeline with excellent performance and a growing connector ecosystem — a strong alternative to the OTel Collector for logs specifically, but with less native trace support. The OTel Collector's advantage is standardisation: it is the official CNCF telemetry pipeline, with hundreds of community-maintained receivers and exporters. If your observability backends are OTel-native (Tempo, Mimir, Loki) and your services use OTel SDKs, the collector is the natural integration point with minimal configuration.
