title: "Boundary: zero-trust infrastructure access with Vault credential injection"
date: "2033-01-10"
excerpt: "HashiCorp Boundary brokers connections to infrastructure (SSH, databases, Kubernetes, RDP) based on identity — authenticated via OIDC, LDAP, or Okta — without distributing static SSH keys or VPN access. Every session is authorized individually, proxied through Boundary workers, and fully audited. The Vault integration injects ephemeral credentials at session start: Vault's SSH certificate engine signs a short-lived cert (30m TTL), or Vault's database engine creates a dynamic Postgres user that expires when the session ends. Users never see the credentials. The result: zero shared SSH keys, least-privilege per-session access, and a compliance-ready audit trail of every infrastructure connection."
author: "Lewis Wilson"
tag: "Build Log"

OIDC authentication. Vault credential injection. No shared keys. Full session audit.

## Architecture and components

```
Boundary components:
┌─────────────────────────────────────────────────────────┐
│  User (developer, DBA)                                  │
│  boundary CLI or Boundary Desktop                       │
└─────────────────────┬───────────────────────────────────┘
                      │ 1. Authenticate (OIDC → Okta)
                      ▼
┌─────────────────────────────────────────────────────────┐
│  Boundary Controller                                    │
│  - Identity and policy engine                           │
│  - Session database (PostgreSQL)                        │
│  - API (gRPC + REST)                                    │
│  - HCP Boundary or self-hosted                          │
└─────────────────────┬───────────────────────────────────┘
                      │ 2. Authorize session → fetch creds from Vault
                      ▼
┌─────────────────────────────────────────────────────────┐
│  Vault                                                  │
│  - SSH CA (signs short-lived certs)                     │
│  - Database engine (dynamic Postgres/MySQL users)        │
│  - Ephemeral credentials (30m–24h TTL)                  │
└─────────────────────┬───────────────────────────────────┘
                      │ 3. Proxy the connection
                      ▼
┌─────────────────────────────────────────────────────────┐
│  Boundary Worker (placed close to targets)              │
│  - TCP proxy (SSH, database, HTTP)                      │
│  - Injects credentials transparently                    │
│  - Logs session metadata (bytes, duration)              │
└─────────────────────┬───────────────────────────────────┘
                      │ 4. Reach the target
                      ▼
┌─────────────────────────────────────────────────────────┐
│  Target (SSH host, Postgres, Redis, Kubernetes API)     │
│  - No inbound ports exposed to the internet             │
│  - No shared passwords or SSH keys                      │
└─────────────────────────────────────────────────────────┘
```

## CLI workflow

```bash
# Install Boundary CLI
brew tap hashicorp/tap
brew install hashicorp/tap/boundary
boundary version
# Boundary v0.17.1

# Configure the controller address
export BOUNDARY_ADDR=https://d1234567890.boundary.hashicorp.cloud

# Authenticate via OIDC (Okta, GitHub, Azure AD)
boundary authenticate oidc \
  --auth-method-id amoidc_1234567890
# → Opens browser → completes OIDC flow → issues a Boundary token
# Token is stored in ~/.boundary/token (or the OS keychain)

# List targets you're authorized to reach
boundary targets list -scope-id global -recursive
# ID              NAME              TYPE  SCOPE
# tssh_abc123     api-01-ssh        SSH   construx-prod
# tssh_def456     bastion-eu        SSH   construx-prod
# ttcp_ghi789     postgres-primary  TCP   construx-prod  (5432)
# ttcp_jkl012     redis-cluster     TCP   construx-prod  (6379)

# Connect to SSH target
boundary connect ssh --target-id tssh_abc123 -- -l ubuntu -p 22
# Boundary fetches SSH cert from Vault (30m TTL)
# Proxies through the Boundary worker
# You get a shell on the target server

# Connect to Postgres (Boundary brokers the TCP connection)
boundary connect postgres \
  --target-id ttcp_ghi789 \
  --dbname construx_prod
# Boundary fetches dynamic credentials from Vault database engine
# Opens psql session with an ephemeral user (expires when session ends)
# construx_prod=# SELECT version();

# Generic TCP proxy (for any TCP target)
boundary connect \
  --target-id ttcp_jkl012 \
  --listen-port 6379
# Opens local port 6379 → Boundary worker → Redis
# redis-cli -p 6379 PING
```

## Terraform configuration

```hcl
# targets.tf — define what Boundary can broker

# Scope: organizational unit
resource "boundary_scope" "construx_prod" {
  name                     = "construx-prod"
  scope_id                 = "global"
  auto_create_admin_role   = true
  auto_create_default_role = true
}

# Static host catalog
resource "boundary_host_catalog_static" "prod" {
  name        = "prod-hosts"
  scope_id    = boundary_scope.construx_prod.id
}

resource "boundary_host_static" "api_01" {
  name            = "api-01"
  host_catalog_id = boundary_host_catalog_static.prod.id
  address         = "10.0.1.10"
}

# SSH target with Vault-injected certificates
resource "boundary_target" "api_ssh" {
  type                = "ssh"
  name                = "api-01-ssh"
  scope_id            = boundary_scope.construx_prod.id
  session_max_seconds = 3600   # 1 hour max
  session_connection_limit = 1

  host_source_ids = [boundary_host_set_static.api_servers.id]

  injected_application_credential_source_ids = [
    boundary_credential_library_vault_ssh_certificate.api.id,
  ]
}

# Vault credential library: SSH certificate
resource "boundary_credential_library_vault_ssh_certificate" "api" {
  name                = "api-ssh-cert"
  credential_store_id = boundary_credential_store_vault.construx.id
  path                = "ssh/sign/construx-api-role"
  username            = "ubuntu"
  key_type            = "ed25519"
  ttl                 = "30m"
  critical_options    = {}
  extensions          = { permit-pty = "" }
}

# Postgres target with dynamic credentials
resource "boundary_target" "postgres" {
  type                = "tcp"
  name                = "postgres-primary"
  scope_id            = boundary_scope.construx_prod.id
  default_port        = 5432
  session_max_seconds = 1800   # 30 min max

  host_source_ids = [boundary_host_set_static.databases.id]

  brokered_credential_source_ids = [
    boundary_credential_library_vault.postgres_readonly.id,
  ]
}

# Vault credential library: dynamic Postgres credentials
resource "boundary_credential_library_vault" "postgres_readonly" {
  name                = "postgres-readonly"
  credential_store_id = boundary_credential_store_vault.construx.id
  path                = "database/creds/construx-readonly-role"
  credential_type     = "username_password"
}
```

## Session audit

```bash
# Every session is recorded with full metadata
boundary sessions list -scope-id global -recursive

# Session record:
# ID               TARGET             USER               STATUS       DURATION
# s_abc123...     api-01-ssh (SSH)   lewis@construx.io  terminated   14m22s
# s_def456...     postgres (TCP)     data@construx.io   active       2m11s

# Detailed session info
boundary sessions read -id s_abc123
# ID:               s_abc123
# Target ID:        tssh_abc123
# Target Name:      api-01-ssh
# User ID:          u_xyz789
# User Email:       lewis.wilson@construx.io
# Auth Token ID:    at_okta_...
# Endpoint:         10.0.1.10:22
# Worker:           worker-prod-eu-01
# Status:           terminated
# Created:          2033-01-10T09:00:00Z
# Terminated:       2033-01-10T09:14:22Z
# Duration:         14m22s
# Bytes Up:         42KB
# Bytes Down:       1.2MB
# Credentials used: Vault SSH cert (path: ssh/sign/construx-api-role, ttl: 30m)

# This audit trail answers compliance questions:
# - Who accessed which server, when, for how long?
# - What credentials were used?
# - Was the access authorized by policy?
```

Boundary vs bastion hosts vs VPN: a bastion host gives SSH access to a subnet — once you SSH through the bastion, you can laterally move to any host. VPN is similar: once connected, broad network access. Boundary enforces per-session, per-target authorization. A developer can connect to `api-01` but not `postgres-primary` unless they have that grant. Credentials are ephemeral (Vault injection), so there are no shared SSH keys to rotate. The audit trail records every connection, not just authentication. The tradeoff: Boundary adds operational complexity (controller + workers + Vault integration) that VPN doesn't have.
