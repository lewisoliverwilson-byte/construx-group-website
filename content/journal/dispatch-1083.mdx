date: "2033-11-06"
excerpt: "KEDA (Kubernetes Event Driven Autoscaler) extends Kubernetes HPA to scale workloads based on external event sources — message queue depth, Kafka consumer group lag, Prometheus metric values, Redis list length, AWS SQS queue size, scheduled cron expressions, and dozens of other scalers. Unlike the standard HPA, which only scales on CPU and memory, KEDA understands the semantics of your application's workload: if an SQS queue has 1000 messages and each worker processes 10 per second, KEDA can calculate that you need 100 workers. KEDA can also scale to zero replicas when the queue is empty — no messages, no workers, no cost. KEDA implements two Kubernetes CRDs: ScaledObject (for Deployments and StatefulSets) and ScaledJob (for Jobs — creates a new Job per batch of events). It integrates with HPA under the hood but exposes a higher-level API. The KEDA operator queries each configured trigger on a polling interval (typically 30s), computes the desired replica count, and updates the underlying HPA. Multiple triggers on the same ScaledObject use an OR model by default — scale out if any trigger threshold is exceeded."

## ScaledObject configuration

```yaml
# ScaledObject: scale a Deployment based on Kafka consumer lag
# If construx-order-processor falls behind, KEDA adds more pods

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name:      construx-order-processor
  namespace: construx-prod
spec:
  scaleTargetRef:
    name: construx-order-processor   # the Deployment to scale
  pollingInterval:  30    # check triggers every 30 seconds
  cooldownPeriod:   300   # wait 300s before scaling down after event drain
  minReplicaCount:  0     # scale to zero when no messages
  maxReplicaCount:  50

  triggers:
    # Trigger 1: Kafka consumer group lag
    - type: kafka
      metadata:
        bootstrapServers: kafka.construx.internal:9092
        consumerGroup:    construx-order-processor
        topic:            persistent://construx/events/order-placed
        lagThreshold:     "100"    # target: 100 messages lag per pod
        # lagThreshold=100, current lag=1000 → KEDA targets 10 pods
        activationLagThreshold: "10"  # scale from 0 to 1 when lag > 10

    # Trigger 2: SQS dead-letter queue — emergency scale-up if DLQ fills
    - type: aws-sqs-queue
      metadata:
        queueURL:         https://sqs.eu-west-2.amazonaws.com/123456789012/order-dlq
        queueLength:      "5"      # alert if more than 5 messages in DLQ
        awsRegion:        eu-west-2
        identityOwner:    operator  # use KEDA's IRSA role
      metricType: AverageValue
---
# ScaledObject: Prometheus-metric-based scaling
# Scale construx-api based on requests per second from Prometheus

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name:      construx-api-rps
  namespace: construx-prod
spec:
  scaleTargetRef:
    name: construx-api
  minReplicaCount: 2    # minimum 2 for HA (don't scale to zero for API)
  maxReplicaCount: 30
  triggers:
    - type: prometheus
      metadata:
        serverAddress: http://prometheus.monitoring.svc.cluster.local:9090
        metricName:    http_requests_per_second
        threshold:     "100"   # target 100 RPS per pod
        query: |
          sum(rate(http_requests_total{namespace="construx-prod",app="construx-api"}[2m]))
---
# ScaledObject: cron-based scaling (pre-scale before known traffic spikes)
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name:      construx-api-cron
  namespace: construx-prod
spec:
  scaleTargetRef:
    name: construx-api
  triggers:
    - type: cron
      metadata:
        timezone:    Europe/London
        start:       "0 8 * * 1-5"    # scale up at 08:00 weekdays
        end:         "0 20 * * 1-5"   # scale down at 20:00 weekdays
        desiredReplicas: "10"          # maintain at least 10 replicas during business hours
```

## ScaledJob and monitoring

```yaml
# ScaledJob: create one Job per batch of events
# Better than a long-running Deployment for batch workloads

apiVersion: keda.sh/v1alpha1
kind: ScaledJob
metadata:
  name:      construx-report-generator
  namespace: construx-prod
spec:
  jobTargetRef:
    template:
      spec:
        containers:
          - name:  report-generator
            image: registry.construx.internal/report-generator:latest
            env:
              - name:  BATCH_SIZE
                value: "50"
        restartPolicy: OnFailure
  pollingInterval: 30
  maxReplicaCount: 10
  triggers:
    - type: aws-sqs-queue
      metadata:
        queueURL:    https://sqs.eu-west-2.amazonaws.com/123456789012/report-requests
        queueLength: "50"     # 50 messages per Job instance
        awsRegion:   eu-west-2
  scalingStrategy:
    strategy: accurate   # create exactly ceil(queue_length / batch_size) Jobs
```

KEDA vs HPA vs VPA vs Knative KPA vs manual scaling: HPA scales Deployments based on CPU/memory — it can't scale to zero and doesn't understand business-domain metrics (queue depth, active WebSocket connections, external event rates). VPA (Vertical Pod Autoscaler) adjusts resource requests per pod rather than replica count — complementary to HPA/KEDA, not a substitute. Knative KPA (covered in dispatch-1070) is concurrency-based and specific to Knative Serving — excellent for HTTP-triggered serverless workloads but not for queue consumers. KEDA bridges the gap: it brings event-driven scaling to standard Kubernetes Deployments and Jobs, with 60+ built-in scalers covering every common event source. The scale-to-zero capability is particularly valuable for batch workloads — a report generator that processes an overnight batch runs 0 pods for 22 hours and 10 pods for 2 hours, costing 1/11th of running continuously. For teams with Kafka consumers, SQS workers, or any queue-backed service, KEDA is the standard autoscaling answer.
