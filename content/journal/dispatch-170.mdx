Observability in a large engineering organisation is a full discipline: distributed tracing, structured logging at scale, complex alerting trees, SLO burn rates. For a two-person team, most of this is overhead that produces noise without signal.

Here's what we actually monitor, and why we chose each.

## The monitoring stack

**PostHog:** Product analytics — user events, funnel analysis, session recordings, feature flag management. Covers the product behaviour layer.

**Supabase dashboard:** Database query performance, connection counts, table sizes, slow query log. Covers the data layer.

**Amplify console:** Build status, deploy history, function invocation counts, error rates. Covers the infrastructure layer.

**Custom uptime checker:** HTTP status checks every 60 seconds for all three products. Alerts on Slack. Covers availability.

**Stripe dashboard:** Revenue metrics, payment failure rates, dispute rates. Covers the business layer.

What we don't have: APM (Application Performance Monitoring), distributed tracing, or a dedicated logging platform. At our scale and stack (serverless on Amplify, Supabase), these add complexity without proportional benefit.

## What we alert on

Alerts are the subset of monitoring that wakes you up. Alerting on too much produces alert fatigue; alerting on too little produces blind spots.

We alert on:

**HTTP health check failure:** Any product returning non-200 for two consecutive checks (2 minutes). Immediate Slack notification.

**Database connection count > 70%:** Early warning before connection exhaustion (which caused our 47-minute incident in October).

**Query duration p95 > 500ms:** Indicates a slow query that may become a problem under load.

**Build failure:** Any failed Amplify build. Deployments are blocked until fixed.

**Payment failure rate > 5% (30-minute window):** Indicates a Stripe issue or a payment flow bug.

**Dispute opened:** Immediate notification. Each dispute requires manual review.

That's seven alert types. We can respond to seven types of alerts. We couldn't respond coherently to 70.

## What we don't alert on (and why)

**Error rates for known, benign errors:** `404 Not Found` for missing resources is expected and non-actionable. Rate-limited requests are expected. We filter these from alert conditions.

**Individual function invocations:** Serverless function calls are logged but not individually monitored. The aggregate (error rate, duration) matters; individual invocations don't.

**Traffic spikes:** A spike in traffic is good. We don't alert on it. If a spike causes a problem (connection exhaustion, slow queries), the downstream alerts will fire.

**Business metrics below threshold:** We track revenue and user metrics but don't alert on them. A slow day in signups is information, not an emergency.

## Logging

Every API route logs structured JSON to stdout. Amplify captures this and makes it searchable in CloudWatch. The log format:

```ts
function log(level: 'info' | 'error' | 'warn', message: string, data?: object) {
  console.log(JSON.stringify({
    level,
    message,
    timestamp: new Date().toISOString(),
    env: process.env.NODE_ENV,
    ...data,
  }));
}
```

We log:
- Every API request (method, path, status, duration)
- Every database query that exceeds 100ms
- Every error (with stack trace)
- Every payment event
- Every AI API call (model, tokens, duration)

We don't log:
- Individual user actions within the product (PostHog handles this)
- Successful cache hits (noise)
- Health check requests

## The PostHog implementation

PostHog provides the product analytics layer. Key events we track:

**Scoutr:** `scan_initiated`, `scan_completed`, `subscription_started`, `subscription_cancelled`

**The Marqet:** `listing_viewed`, `enquiry_sent`, `payment_initiated`, `payment_completed`, `dispute_opened`

**The Hyve:** `workspace_created`, `message_sent`, `ai_agent_mentioned`, `channel_created`

Each event includes properties: `userId`, `workspaceId` or `listingId`, and context-specific properties.

Session recordings are enabled for onboarding flows (the first 3 sessions for a new user). This is how we identify UX friction during onboarding — watching recordings is faster than analysing click data for identifying where users get stuck.

## The key insight about observability

More monitoring doesn't produce more insight. It produces more data, which requires more time to interpret.

At our scale, the goal of observability is: know when something is wrong fast enough to fix it before users notice, and have enough information to diagnose the cause quickly. Everything beyond this goal is overhead.

The monitoring stack we have hits this goal. A down event produces an alert within 2 minutes. A slow query alert fires before connection pools are exhausted. Build failures block bad deploys before they reach production.

The things we'd add if we had a dedicated site-reliability engineer: distributed tracing across service boundaries, structured log aggregation with better query capabilities, SLO tracking. These would be genuine improvements. They'd also require a person to maintain them and interpret the output.

For now: seven alert types, a simple log format, and a team small enough to respond to anything that fires. It works.
