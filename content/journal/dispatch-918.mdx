title: "Prometheus recording rules: pre-computing expensive queries for dashboard speed"
date: "2032-06-29"
excerpt: "Prometheus recording rules evaluate PromQL expressions on a schedule and write the result back as a new time series. This pre-computes expensive aggregations — sum across thousands of pods, rate calculations across large label cardinalities — so dashboards load instantly instead of running costly fan-out queries at render time. Recording rules also enable the federation pattern: a high-level Prometheus scrapes recording rules from per-cluster Prometheus instances rather than forwarding millions of raw time series. Well-structured recording rules follow the naming convention level:metric:operation and are organized into rule groups with independent evaluation intervals."

Pre-compute at write time. Read instantly at query time. Name your rules `level:metric:op`.

## Recording rule basics

```yaml
# /etc/prometheus/rules/construx-api.yml

groups:
  - name: construx_api_aggregations
    interval: 30s   # Evaluate every 30s (default: same as global scrape_interval)
    rules:

      # Request rate per service (pre-computed instead of calculating at dashboard time)
      - record: job:http_requests:rate5m
        expr: sum by (job, status_code) (rate(http_requests_total[5m]))

      # Error ratio per job (bad/total)
      - record: job:http_errors:ratio_rate5m
        expr: |
          sum by (job) (rate(http_requests_total{status_code=~"5.."}[5m]))
          /
          sum by (job) (rate(http_requests_total[5m]))

      # P99 latency — expensive histogram_quantile pre-computed per job
      - record: job:http_request_duration_seconds:p99_rate5m
        expr: |
          histogram_quantile(0.99,
            sum by (job, le) (rate(http_request_duration_seconds_bucket[5m]))
          )

      # P50 latency
      - record: job:http_request_duration_seconds:p50_rate5m
        expr: |
          histogram_quantile(0.50,
            sum by (job, le) (rate(http_request_duration_seconds_bucket[5m]))
          )

      # Active database connections (useful for connection pool saturation alerts)
      - record: job:db_connections:utilisation
        expr: |
          pg_stat_activity_count{state="active"}
          /
          pg_settings_max_connections
```

## Naming convention: `level:metric:operation`

```yaml
# The Prometheus naming convention for recording rules is:
#   level      — the aggregation level (job, instance, cluster, region)
#   metric     — the base metric name (http_requests, db_connections, memory_bytes)
#   operation  — the aggregation function (rate5m, ratio, p99, avg, sum)

# Examples following the convention:
groups:
  - name: construx_node_rules
    rules:
      # CPU utilisation per instance (1 - idle)
      - record: instance:cpu_utilisation:ratio
        expr: 1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m]))

      # Memory pressure (ratio of used to total)
      - record: instance:memory_used:ratio
        expr: |
          1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)

      # Network throughput per instance
      - record: instance:network_transmit_bytes:rate5m
        expr: sum by (instance) (rate(node_network_transmit_bytes_total[5m]))

      # Disk I/O saturation (avg queue depth > 1 = saturated)
      - record: instance:disk_io_saturation:ratio
        expr: avg by (instance, device) (rate(node_disk_io_time_weighted_seconds_total[5m]))

  - name: construx_kube_rules
    rules:
      # Pod CPU by namespace (pre-aggregated for namespace dashboards)
      - record: namespace:pod_cpu:rate5m
        expr: |
          sum by (namespace) (
            rate(container_cpu_usage_seconds_total{container!=""}[5m])
          )

      # Memory by namespace
      - record: namespace:pod_memory:bytes
        expr: |
          sum by (namespace) (
            container_memory_working_set_bytes{container!=""}
          )
```

## Alert rules alongside recording rules

```yaml
groups:
  - name: construx_alerts
    rules:
      # Alert using the pre-computed recording rule (fast — single series lookup)
      - alert: HighErrorRate
        expr: job:http_errors:ratio_rate5m > 0.01
        for: 5m
        labels:
          severity: critical
          team: platform
        annotations:
          summary: "High error rate on {{ $labels.job }}"
          description: "Error ratio is {{ $value | humanizePercentage }} (threshold: 1%)"
          runbook: "https://runbooks.construx.io/high-error-rate"

      - alert: SlowP99Latency
        expr: job:http_request_duration_seconds:p99_rate5m > 1.0
        for: 3m
        labels:
          severity: warning
        annotations:
          summary: "P99 latency > 1s on {{ $labels.job }}"
          description: "P99 is {{ $value | humanizeDuration }}"

      # Dead man's switch — alert if Prometheus stops evaluating rules
      - alert: PrometheusRuleEvaluationFailures
        expr: increase(prometheus_rule_evaluation_failures_total[5m]) > 0
        for: 0m
        labels:
          severity: critical

  - name: construx_slo_rules
    interval: 60s
    rules:
      # SLO burn rate (multi-window alerting — Google SRE Workbook pattern)
      # 1-hour burn rate window (fast burn = immediate alert)
      - record: job:slo_error:ratio_rate1h
        expr: |
          sum by (job) (rate(http_requests_total{status_code=~"5.."}[1h]))
          /
          sum by (job) (rate(http_requests_total[1h]))

      # 6-hour burn rate (slow burn = warning)
      - record: job:slo_error:ratio_rate6h
        expr: |
          sum by (job) (rate(http_requests_total{status_code=~"5.."}[6h]))
          /
          sum by (job) (rate(http_requests_total[6h]))

      # Alert: fast burn (14.4x) in 1h window + 6h window (page immediately)
      - alert: SLOBurnRateFast
        expr: |
          job:slo_error:ratio_rate1h > (14.4 * 0.001)   # 14.4x burn, 0.1% budget
          and
          job:slo_error:ratio_rate6h > (6 * 0.001)
        for: 2m
        labels:
          severity: page
```

## Thanos ruler for global recording rules

```yaml
# In a multi-cluster setup (Thanos), use Thanos Ruler to evaluate rules
# across all cluster data — not just one Prometheus instance

# thanos-ruler.yml
type: THANOS   # query across all Prometheus instances via Thanos Query

# Thanos ruler evaluates these rules against the global Thanos Query endpoint
# Results are stored back in object storage (S3) as new time series

# Global error ratio across all clusters:
- record: global:job:http_errors:ratio_rate5m
  expr: |
    sum by (job, cluster) (rate(http_requests_total{status_code=~"5.."}[5m]))
    /
    sum by (job, cluster) (rate(http_requests_total[5m]))
```

Recording rules vs instant queries in dashboards: every Grafana panel that uses a raw PromQL query with `rate(metric[5m])` fans out to Prometheus at render time — if you have 20 panels and each scans 60+ pods, dashboard load can take 10-30 seconds. Recording rules pre-compute those expressions every 30 seconds and write a single aggregated series. The dashboard then queries one series instead of fanning out across thousands of time series. The storage cost is minimal — a recording rule that produces 10 label combinations adds 10 series, consuming ~10KB/day. The query cost saving can be orders of magnitude. As a rule of thumb: any PromQL expression used in a dashboard panel should be a recording rule candidate if it's expensive (histogram_quantile across many buckets, sum across many pods) or accessed frequently.
