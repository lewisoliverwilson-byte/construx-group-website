title: "External Secrets Operator: SecretStore, ClusterSecretStore, ExternalSecret sync"
date: "2034-02-04"
excerpt: "External Secrets Operator (ESO) is a Kubernetes operator that synchronises secrets from external secret stores (AWS Secrets Manager, HashiCorp Vault, GCP Secret Manager, Azure Key Vault, 1Password, Doppler, and others) into Kubernetes Secrets. Without ESO, teams either bake secrets into Helm values (insecure), manually create Kubernetes Secrets (fragile, not GitOps-compatible), or use Vault Agent sidecar injection (operationally complex). ESO introduces two custom resources: SecretStore (namespaced) and ClusterSecretStore (cluster-wide), which define how to authenticate to the external provider; and ExternalSecret, which specifies which secret values to sync, how to map them into a Kubernetes Secret, and how frequently to resync. ESO supports push (write to external store) as well as pull, field-level templating (compose multiple secret values into a single Kubernetes Secret), and generator resources (UUID, Fake, Password) for use in GitOps pipelines. The synchronisation model is eventually consistent: ESO polls the external store on a configurable interval, so changes to the external secret propagate to Kubernetes within seconds to minutes. Combined with Reloader (stakater/Reloader), which watches for Secret/ConfigMap changes and rolls deployments that reference them, ESO enables fully automated secret rotation with zero manual intervention."

## ESO config: Vault + AWS Secrets Manager

```yaml
# ClusterSecretStore: authenticates to Vault using Kubernetes auth
# Applied cluster-wide — all namespaces can reference this store

apiVersion: external-secrets.io/v1beta1
kind: ClusterSecretStore
metadata:
  name: vault-construx
spec:
  provider:
    vault:
      server: https://vault.construx.internal
      path: secret
      version: v2
      auth:
        kubernetes:
          mountPath: kubernetes
          role: external-secrets-operator
          serviceAccountRef:
            name: external-secrets
            namespace: external-secrets

---
# SecretStore: authenticates to AWS Secrets Manager (region-scoped)

apiVersion: external-secrets.io/v1beta1
kind: SecretStore
metadata:
  name: aws-secrets
  namespace: construx-prod
spec:
  provider:
    aws:
      service: SecretsManager
      region: eu-west-2
      auth:
        jwt:
          serviceAccountRef:
            name: external-secrets-sa   # IRSA: pod identity → IAM role
```

```yaml
# ExternalSecret: sync Vault secret → Kubernetes Secret
# Vault path: secret/data/construx-prod/payments-api
# Result: Kubernetes Secret "payments-api-secrets" in construx-prod namespace

apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: payments-api-secrets
  namespace: construx-prod
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-construx
    kind: ClusterSecretStore
  target:
    name: payments-api-secrets
    creationPolicy: Owner    # ESO owns this Secret; it deletes it if ExternalSecret is deleted
    template:
      type: Opaque
      data:
        # Compose multiple Vault fields into a connection string
        DATABASE_URL: "postgresql://{{ .db_user }}:{{ .db_password }}@postgres-0.construx-prod.svc.cluster.local:5432/payments"
        STRIPE_API_KEY: "{{ .stripe_api_key }}"
        JWT_SIGNING_KEY: "{{ .jwt_signing_key }}"
  data:
    - secretKey: db_user
      remoteRef:
        key: secret/construx-prod/payments-api
        property: db_user
    - secretKey: db_password
      remoteRef:
        key: secret/construx-prod/payments-api
        property: db_password
    - secretKey: stripe_api_key
      remoteRef:
        key: secret/construx-prod/payments-api
        property: stripe_api_key
    - secretKey: jwt_signing_key
      remoteRef:
        key: secret/construx-prod/payments-api
        property: jwt_signing_key

---
# ExternalSecret: bulk sync entire Vault path as dataFrom
# Pulls all key-value pairs from a Vault secret into a Kubernetes Secret

apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: orders-api-all-secrets
  namespace: construx-prod
spec:
  refreshInterval: 30m
  secretStoreRef:
    name: vault-construx
    kind: ClusterSecretStore
  target:
    name: orders-api-secrets
    creationPolicy: Owner
  dataFrom:
    - extract:
        key: secret/construx-prod/orders-api
```

```yaml
# PushSecret: write to Vault from a Kubernetes Secret
# Useful for secrets generated by cert-manager or Kubernetes job outputs

apiVersion: external-secrets.io/v1alpha1
kind: PushSecret
metadata:
  name: push-generated-api-key
  namespace: construx-prod
spec:
  refreshInterval: 10s
  secretStoreRefs:
    - name: vault-construx
      kind: ClusterSecretStore
  selector:
    secret:
      name: generated-api-key   # Kubernetes Secret to push
  data:
    - match:
        secretKey: api_key
        remoteRef:
          remoteKey: secret/construx-prod/generated-keys
          property: api_key

---
# Generator: Password generator — creates random secrets in GitOps pipelines
# No hardcoded values in Git; each cluster gets a unique generated secret

apiVersion: generators.external-secrets.io/v1alpha1
kind: Password
metadata:
  name: db-password-gen
  namespace: construx-prod
spec:
  length: 32
  digits: 5
  symbols: 3
  symbolCharacters: "!@#$%"
  noUpper: false
  allowRepeat: false
```

ESO vs Vault Agent Sidecar vs Sealed Secrets vs SOPS vs Doppler: Vault Agent Sidecar injects secrets as files into pod filesystems — it works, but every pod needs a sidecar container, which adds resource overhead and operational complexity. ESO is simpler: one operator manages all secret synchronisation cluster-wide, and Pods consume ordinary Kubernetes Secrets. Sealed Secrets (Bitnami) encrypts Kubernetes Secrets with a cluster-specific key before storing them in Git — the encrypted SealedSecret is safe to commit, and the controller decrypts it in the cluster. This is GitOps-clean but requires re-sealing every time a secret rotates. SOPS (Secrets OPerationS) encrypts secret files with KMS or PGP before committing to Git, decrypting at deploy time — popular in Flux workflows via sops-decrypt. Doppler is a cloud-hosted secrets platform with native Kubernetes sync — excellent developer UX but introduces a SaaS dependency in the critical path. ESO's advantage is provider-agnostic design: you can sync from Vault in production and from AWS Secrets Manager in staging without changing application code, just by changing the SecretStore reference.
