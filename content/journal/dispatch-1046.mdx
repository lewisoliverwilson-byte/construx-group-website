date: "2033-07-18"
excerpt: "dbt (data build tool) is a transformation layer that sits between your raw data (from ETL tools, CDC pipelines, or S3 ingestion) and your analytics tables. You write SELECT statements — called models — and dbt compiles them into the correct DDL for your data warehouse (BigQuery, Snowflake, Redshift, DuckDB, Trino, Spark). dbt handles incremental materialisation (append only new rows since the last run), dependency management (models reference other models with ref()), schema tests (assert column uniqueness, non-null constraints, accepted values, referential integrity), documentation (auto-generated lineage DAG), and source freshness checks. The workflow: define sources (raw tables from your ingestion layer), write models as SELECT statements, add tests to the schema.yml, run dbt build — dbt computes the DAG, runs models in dependency order, and fails the build if any test fails. The result is a tested, documented analytics layer that is version-controlled and reproducible."

## Models and ref()

```sql
-- models/staging/stg_orders.sql
-- Source: raw orders from Debezium CDC → S3 → external table

{{ config(materialized='view') }}   -- jinja2 config block

SELECT
    id                                              AS order_id,
    tenant_id,
    status,
    total_pence,
    CAST(created_at AS TIMESTAMP)                  AS created_at,
    CAST(fulfilled_at AS TIMESTAMP)                AS fulfilled_at,
    _cdc_op                                         AS cdc_operation,   -- c/u/d from Debezium
    _cdc_ts                                         AS ingested_at
FROM {{ source('raw', 'orders') }}   -- references sources.yml → raw.orders
WHERE _cdc_op != 'd'                 -- exclude deleted rows
---
-- models/marts/orders_daily.sql
-- Incremental model: only process new rows since last run

{{ config(
    materialized='incremental',
    unique_key='order_date || \'_\' || tenant_id',
    on_schema_change='sync_all_columns',
    incremental_strategy='merge',
) }}

WITH base AS (
    SELECT
        DATE_TRUNC('day', created_at)  AS order_date,
        tenant_id,
        status,
        total_pence
    FROM {{ ref('stg_orders') }}    -- ref() = dependency on stg_orders model
    WHERE status = 'completed'
    {% if is_incremental() %}
        AND created_at > (SELECT MAX(order_date) FROM {{ this }})
    {% endif %}
)

SELECT
    order_date,
    tenant_id,
    COUNT(*)                       AS order_count,
    SUM(total_pence) / 100.0      AS revenue_gbp,
    AVG(total_pence) / 100.0      AS avg_order_gbp
FROM base
GROUP BY order_date, tenant_id
---
-- models/marts/tenant_summary.sql
-- Fan-out: depends on multiple models

{{ config(materialized='table') }}

SELECT
    t.tenant_id,
    t.name                         AS tenant_name,
    t.plan_tier,
    d.order_count                  AS orders_last_30d,
    d.revenue_gbp                  AS revenue_last_30d_gbp,
    p.active_product_count
FROM {{ ref('stg_tenants') }}          AS t
LEFT JOIN {{ ref('orders_daily') }}    AS d
    ON t.tenant_id = d.tenant_id
    AND d.order_date >= CURRENT_DATE - INTERVAL '30 days'
LEFT JOIN {{ ref('product_stats') }}   AS p
    ON t.tenant_id = p.tenant_id
```

## Schema tests and sources

```yaml
# models/staging/schema.yml
# dbt tests: run automatically on dbt build

version: 2

sources:
  - name: raw
    database: construx_prod
    schema: raw
    freshness:
      warn_after: {count: 6,  period: hour}
      error_after: {count: 24, period: hour}
    loaded_at_field: _cdc_ts
    tables:
      - name: orders
        description: "Raw orders from Debezium CDC pipeline"
      - name: tenants
      - name: products

models:
  - name: stg_orders
    description: "Staged orders: cleaned, typed, deletes excluded"
    columns:
      - name: order_id
        description: "Primary key"
        tests:
          - unique
          - not_null
      - name: tenant_id
        tests:
          - not_null
          - relationships:
              to: ref('stg_tenants')
              field: tenant_id
      - name: status
        tests:
          - not_null
          - accepted_values:
              values: [pending, confirmed, shipped, completed, cancelled]
      - name: total_pence
        tests:
          - not_null
          - dbt_expectations.expect_column_values_to_be_between:
              min_value: 1
              max_value: 10000000   # sanity: < £100k per order

  - name: orders_daily
    columns:
      - name: order_date
        tests: [not_null]
      - name: revenue_gbp
        tests:
          - not_null
          - dbt_expectations.expect_column_values_to_be_between:
              min_value: 0
```

## CLI and CI integration

```bash
# dbt CLI

# Run all models
dbt run

# Run a specific model and its downstream dependencies
dbt run --select orders_daily+

# Run tests
dbt test

# Build: run + test in dependency order (recommended for CI)
dbt build

# Check source freshness
dbt source freshness
# Found 3 sources:
# raw.orders           OK freshness (last loaded 0:04:12 ago)
# raw.tenants          OK freshness (last loaded 0:08:41 ago)
# raw.products         WARN freshness (last loaded 5:22:10 ago)

# Generate docs and lineage DAG
dbt docs generate
dbt docs serve   # http://localhost:8080 — interactive lineage graph

# Compile Jinja SQL to inspect final SQL
dbt compile --select orders_daily
# Compiled SQL written to: target/compiled/construx/models/marts/orders_daily.sql

# Incremental run: process only new rows
dbt run --select orders_daily --full-refresh   # force full rebuild when schema changes

# CI pipeline: GitHub Actions
# - dbt build --target=ci (ci profile uses separate schema: construx_ci)
# - dbt test --store-failures   # persist failed test rows for investigation
```

dbt vs raw SQL scripts vs Airflow PythonOperators vs Spark jobs: Raw SQL scripts in a cron job or Airflow bash operator have no dependency tracking, no tests, no lineage, and no incremental logic — they run everything every time. Airflow PythonOperators that run pandas transforms are expressive but slow (data lands in Python memory), hard to test, and invisible to the data catalog. Spark jobs are powerful for huge datasets but require JVM infrastructure, are verbose for simple SELECT-level transforms, and don't integrate with a SQL data warehouse natively. dbt's value is that your analytics logic stays in SQL (the language every analyst already knows), runs inside the warehouse (no data movement, uses its compute and storage), is tested (schema assertions catch regressions before they reach dashboards), and has a documented dependency DAG. The constraint: dbt is a transform layer, not an ingestion layer — you still need something upstream (Fivetran, Airbyte, Debezium, custom pipelines) to get raw data into the warehouse. dbt then handles everything from raw → clean → modelled.
