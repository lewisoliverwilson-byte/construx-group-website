excerpt: "Backstage is an open-source developer portal built by Spotify and donated to the CNCF. It provides a centralised interface for everything a developer needs to discover, understand, and create services: a software catalog (a queryable inventory of every service, library, API, dataset, and resource across the organisation), TechDocs (documentation-as-code rendered from Markdown stored next to the service code), a scaffolding system (create-a-new-service templates that provision git repos, CI pipelines, and cloud resources in one click), and a plugin system for integrating third-party tools (PagerDuty alerts, Datadog dashboards, ArgoCD deploy status, SonarQube code quality — all surfaced in the service's Backstage page). The catalog is populated via YAML descriptor files (catalog-info.yaml) committed to each service's repo. Backstage reads these descriptors (via GitHub integration or direct file import) and builds a graph of ownership, dependencies, and API contracts. The result: a developer can navigate from a service to its owners, its API spec, its deploy status, its on-call rotation, and its runbook — all in one place, without knowing where each tool lives."

## Catalog descriptor and TechDocs configuration

```yaml
# catalog-info.yaml: committed at the root of every service repo
# Backstage reads this file to populate the catalog

apiVersion: backstage.io/v1alpha1
kind: Component
metadata:
  name:        construx-api
  title:       "Construx API"
  description: "Core API service — tenant management, billing, order processing"
  annotations:
    # GitHub Actions CI link
    github.com/project-slug: construx-group/construx-api
    # ArgoCD deployment link
    argocd/app-name: construx-api-prod
    # PagerDuty on-call service
    pagerduty.com/service-id: P4ABC12
    # Datadog dashboard
    datadoghq.com/dashboard-url: https://app.datadoghq.com/dashboard/xyz
    # TechDocs: mkdocs-based docs in /docs/ directory
    backstage.io/techdocs-ref: dir:.
spec:
  type:      service
  lifecycle:  production
  owner:      team-platform       # references a Group entity in the catalog
  system:     construx-core        # references a System entity
  providesApis:
    - construx-rest-api           # references an API entity
  consumesApis:
    - stripe-payments-api
    - sendgrid-email-api
  dependsOn:
    - resource:construx-postgres
    - resource:construx-redis
---
# API entity: OpenAPI spec stored in the catalog
apiVersion: backstage.io/v1alpha1
kind: API
metadata:
  name:  construx-rest-api
  title: "Construx REST API"
  annotations:
    backstage.io/techdocs-ref: dir:.
spec:
  type:       openapi
  lifecycle:  production
  owner:      team-platform
  definition: |
    openapi: 3.1.0
    info:
      title:   Construx API
      version: "1.42.0"
    paths:
      /api/v1/orders:
        get:
          summary: List orders
          ...
---
# Group entity: team ownership — maps to GitHub team
apiVersion: backstage.io/v1alpha1
kind: Group
metadata:
  name:  team-platform
  title: "Platform Engineering"
spec:
  type:    team
  profile:
    displayName: "Platform Engineering"
    email:        platform@construx.io
  parent: engineering   # parent group
  members:
    - lewis-wilson
    - james-harper
```

## Scaffolding templates and plugin integration

```yaml
# Software Template: "create a new microservice" in one click
# scaffolding creates the git repo, CI pipeline, Kubernetes manifests, and catalog entry

apiVersion: scaffolder.backstage.io/v1beta3
kind: Template
metadata:
  name:  create-service
  title: "Create a new microservice"
  tags:  [service, kubernetes, recommended]
spec:
  owner: team-platform
  type:  service
  parameters:
    - title: Service details
      properties:
        name:         { type: string, title: "Service name" }
        owner:        { type: string, title: "Owning team" }
        language:     { type: string, enum: [typescript, go, python] }
        description:  { type: string, title: "What does this service do?" }
  steps:
    # Step 1: create git repository from template
    - id:     create-repo
      name:   "Create GitHub repository"
      action: publish:github
      input:
        repoUrl:  github.com?repo={{parameters.name}}&owner=construx-group
        description: "{{parameters.description}}"

    # Step 2: scaffold code from a skeleton
    - id:     render-skeleton
      name:   "Render service skeleton"
      action: fetch:template
      input:
        url:    ./skeletons/{{parameters.language}}-service
        values: { name: "{{parameters.name}}", owner: "{{parameters.owner}}" }

    # Step 3: create Kubernetes manifests in the k8s-manifests repo
    - id:     create-k8s-manifests
      name:   "Create Kubernetes manifests"
      action: publish:github:pull-request
      input:
        repoUrl:       github.com?repo=k8s-manifests&owner=construx-group
        branchName:    "feat/add-{{parameters.name}}"
        title:         "feat: scaffold {{parameters.name}} manifests"

    # Step 4: register the new service in the catalog
    - id:     register-catalog
      name:   "Register in catalog"
      action: catalog:register
      input:
        repoContentsUrl: "{{steps['create-repo'].output.repoContentsUrl}}"
        catalogInfoPath: /catalog-info.yaml
```

# Backstage local development
yarn create @backstage/app   # scaffold a new Backstage instance
cd backstage
yarn dev                      # starts frontend on :3000 and backend on :7007

# Production: deploy via Helm
helm repo add backstage https://backstage.github.io/charts

  --namespace backstage \
  --values values.yaml \
  --version 1.9.6

# Query the catalog API programmatically
curl https://backstage.construx.internal/api/catalog/entities?filter=kind=Component | \
  jq '[.[] | {name: .metadata.name, owner: .spec.owner, lifecycle: .spec.lifecycle}]'

Backstage vs Confluence + Jira vs custom internal tooling vs no portal: Most engineering organisations start with the Confluence + Jira combination for documentation and tickets, then bolt on separate tools for service ownership (a spreadsheet), API docs (Swagger UI), and deployment status (a CI dashboard). The result is a high-context-switching environment where finding basic information ("who owns this service? where is its runbook? is it deployed?") requires knowing which tool to look in. Backstage's value is aggregation — it doesn't replace the tools, it surfaces their data in one place behind a consistent model (the entity catalog). The investment is the initial catalog-info.yaml rollout across all repos and the plugin configuration for each tool (PagerDuty, ArgoCD, Datadog integration). At small scale (< 20 services), Backstage's overhead is hard to justify. At scale (> 50 services, multiple teams), the cognitive load of undiscoverable services and unknown ownership becomes a real operational cost that Backstage amortises. For growing engineering organisations who have passed the "everyone knows everything" inflection point, Backstage is the standard platform engineering investment.
