Next.js Route Handlers have a 30-second execution limit on Vercel (or similar serverless platforms). Anything longer — processing uploads, sending batched emails, running AI pipelines, syncing external data — needs a background job system.

## Option 1: Trigger.dev (managed, developer-friendly)

Trigger.dev is a background job platform built for TypeScript. Define jobs as code, run them durably, get real-time logging in a dashboard:

```ts
// trigger/process-upload.ts
import { task } from '@trigger.dev/sdk/v3';
import { processUpload } from '@/lib/processing';

export const processUploadTask = task({
  id: 'process-upload',
  maxDuration: 300, // 5 minutes
  run: async (payload: { fileUrl: string; userId: string }) => {
    const { fileUrl, userId } = payload;

    // Runs outside serverless limits
    const result = await processUpload(fileUrl);
    await notifyUser(userId, result);

    return { processed: true, fileId: result.id };
  },
});
```

Trigger from an API route:

```ts
// app/api/upload/route.ts
import { processUploadTask } from '@/trigger/process-upload';

export async function POST(req: Request) {
  const { fileUrl, userId } = await req.json();

  // Returns immediately — job runs in background
  const handle = await processUploadTask.trigger({ fileUrl, userId });

  return Response.json({ jobId: handle.id });
}
```

Good for: long-running tasks, AI pipelines, anything that benefits from real-time logging and automatic retries.

## Option 2: QStash (serverless message queue)

QStash from Upstash is a serverless HTTP-based queue — no persistent connections, pay per message:

```ts
// lib/queue.ts
import { Client } from '@upstash/qstash';

export const qstash = new Client({ token: process.env.QSTASH_TOKEN! });

export async function enqueueJob(
  endpoint: string,
  payload: unknown,
  options?: { delay?: number; retries?: number },
) {
  return qstash.publishJSON({
    url: `${process.env.NEXT_PUBLIC_SITE_URL}/api/jobs/${endpoint}`,
    body: payload,
    delay: options?.delay,
    retries: options?.retries ?? 3,
  });
}
```

Job handler:

```ts
// app/api/jobs/send-newsletter/route.ts
import { verifySignatureAppRouter } from '@upstash/qstash/nextjs';

async function handler(req: Request) {
  const { postId } = await req.json();
  const post = await getPost(postId);
  const subscribers = await getSubscribers();

  // Send in batches of 100
  for (let i = 0; i < subscribers.length; i += 100) {
    const batch = subscribers.slice(i, i + 100);
    await sendBatch(post, batch);
  }

  return Response.json({ sent: subscribers.length });
}

export const POST = verifySignatureAppRouter(handler);
```

Good for: webhooks, scheduled jobs, fan-out patterns. Doesn't require a persistent worker.

## Option 3: Database-backed queue (zero dependencies)

For simple use cases, a database queue is good enough and requires no additional services:

```sql
-- migrations/create_job_queue.sql
CREATE TABLE job_queue (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  type       TEXT NOT NULL,
  payload    JSONB NOT NULL DEFAULT '{}',
  status     TEXT NOT NULL DEFAULT 'pending',  -- pending, running, done, failed
  attempts   INT NOT NULL DEFAULT 0,
  max_attempts INT NOT NULL DEFAULT 3,
  run_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
  started_at TIMESTAMPTZ,
  completed_at TIMESTAMPTZ,
  error      TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX job_queue_status_run_at ON job_queue (status, run_at)
  WHERE status IN ('pending', 'failed');
```

Worker:

```ts
// lib/worker.ts
import { db } from '@/db';
import { sql } from 'drizzle-orm';

async function processJob(job: Job) {
  switch (job.type) {
    case 'send-email':
      await sendEmail(job.payload as EmailPayload);
      break;
    case 'sync-inventory':
      await syncInventory(job.payload as SyncPayload);
      break;
    default:
      throw new Error(`Unknown job type: ${job.type}`);
  }
}

export async function runWorker() {
  while (true) {
    // Atomic claim with pessimistic locking
    const [job] = await db.execute(sql`
      UPDATE job_queue
      SET status = 'running', started_at = now(), attempts = attempts + 1
      WHERE id = (
        SELECT id FROM job_queue
        WHERE status IN ('pending', 'failed')
          AND attempts < max_attempts
          AND run_at <= now()
        ORDER BY run_at ASC
        FOR UPDATE SKIP LOCKED
        LIMIT 1
      )
      RETURNING *
    `);

    if (!job) {
      await new Promise((r) => setTimeout(r, 2000));
      continue;
    }

    try {
      await processJob(job);
      await db.execute(sql`
        UPDATE job_queue SET status = 'done', completed_at = now() WHERE id = ${job.id}
      `);
    } catch (err) {
      const error = err instanceof Error ? err.message : String(err);
      await db.execute(sql`
        UPDATE job_queue
        SET status = CASE WHEN attempts >= max_attempts THEN 'failed' ELSE 'pending' END,
            error = ${error},
            run_at = now() + interval '1 minute' * attempts
        WHERE id = ${job.id}
      `);
    }
  }
}
```

Enqueue from anywhere:

```ts
await db.execute(sql`
  INSERT INTO job_queue (type, payload, run_at)
  VALUES ('send-email', ${JSON.stringify({ to: email, template: 'welcome' })}, ${new Date()})
`);
```

`FOR UPDATE SKIP LOCKED` is the key — it's an atomic claim that prevents two workers from picking the same job. Exponential backoff on failure: retried after `n minutes * attempts`.

Good for: simple jobs, small volume (< 10k/day), teams who want zero additional services.

## Choosing

| Option | Best for | Ceiling |
|---|---|---|
| Trigger.dev | AI pipelines, long tasks, observability | Unlimited |
| QStash | Serverless, scheduled, fan-out | Millions/day |
| DB queue | Simple jobs, low volume | ~10k/day |

Start with the database queue. Move to QStash when you need schedule-based jobs or high volume. Move to Trigger.dev when you need real-time observability or jobs longer than 15 minutes.
