Real-time communication in web apps uses one of two transport mechanisms: WebSockets or Server-Sent Events (SSE). The choice depends on whether you need the client to send data to the server on the same connection.

## WebSockets: full-duplex

WebSockets upgrade an HTTP connection to a persistent, bidirectional channel. Both sides can send messages at any time without a new request.

```ts
// Server (with ws library)
import { WebSocketServer } from 'ws';

const wss = new WebSocketServer({ port: 8080 });

wss.on('connection', (ws) => {
  ws.on('message', (data) => {
    const msg = JSON.parse(data.toString());
    console.log('Received:', msg);

    // Echo back
    ws.send(JSON.stringify({ type: 'echo', data: msg }));
  });

  // Broadcast to all clients
  wss.clients.forEach((client) => {
    if (client.readyState === ws.OPEN) {
      client.send(JSON.stringify({ type: 'user_joined' }));
    }
  });
});
```

```ts
// Client
const ws = new WebSocket('wss://api.construxgroup.io/ws');

ws.onopen    = () => ws.send(JSON.stringify({ type: 'subscribe', channel: 'updates' }));
ws.onmessage = (event) => console.log(JSON.parse(event.data));
ws.onclose   = () => reconnect();
ws.onerror   = (err) => console.error(err);
```

**The deployment problem**: WebSockets are stateful connections that must be routed to the same server instance. Behind a load balancer, you need sticky sessions or a message broker (Redis Pub/Sub) to broadcast to clients on different servers. This is the main operational complexity.

## Server-Sent Events: one-way, simpler

SSE is a one-way channel from server to client over a regular HTTP connection. The client can't send messages over the SSE connection — it uses normal fetch requests for that.

```ts
// Next.js Route Handler — SSE
export async function GET(req: Request) {
  const encoder = new TextEncoder();

  const stream = new ReadableStream({
    start(controller) {
      const send = (data: unknown) => {
        controller.enqueue(encoder.encode(`data: ${JSON.stringify(data)}\n\n`));
      };

      // Send initial state
      send({ type: 'connected' });

      // Subscribe to updates (Redis, DB, etc.)
      const unsubscribe = subscribe('user-updates', (event) => {
        send(event);
      });

      req.signal.addEventListener('abort', () => {
        unsubscribe();
        controller.close();
      });
    },
  });

  return new Response(stream, {
    headers: {
      'Content-Type':  'text/event-stream',
      'Cache-Control': 'no-cache',
      'Connection':    'keep-alive',
    },
  });
}
```

```ts
// Client — SSE
const es = new EventSource('/api/events');
es.onmessage = (event) => {
  const data = JSON.parse(event.data);
  console.log(data);
};
es.onerror = () => es.close();
```

`EventSource` handles reconnection automatically. If the connection drops, the browser retries after a configurable delay. It sends the `Last-Event-ID` header so the server can resume from where it left off.

## The SSE format

SSE is a plain text protocol:

```
data: {"type":"update","id":42}\n\n
```

Each event is separated by a blank line (`\n\n`). The format supports:
- `data:` — the event payload
- `id:` — event ID (used for reconnection)
- `event:` — custom event type
- `retry:` — reconnection interval in milliseconds

```
event: notification
id: 1001
data: {"message":"Your export is ready"}

```

## For LLM streaming output

SSE is the standard for streaming LLM responses. OpenAI's API, Anthropic's API, and most LLM providers use SSE for streaming.

```ts
// Route Handler that streams Claude output via SSE
export async function POST(req: Request) {
  const { prompt } = await req.json();

  const stream = client.messages.stream({
    model:     'claude-opus-4-8',
    max_tokens: 1024,
    messages:  [{ role: 'user', content: prompt }],
  });

  const encoder = new TextEncoder();
  const readable = new ReadableStream({
    async start(controller) {
      for await (const event of stream) {
        if (event.type === 'content_block_delta' && event.delta.type === 'text_delta') {
          controller.enqueue(
            encoder.encode(`data: ${JSON.stringify({ text: event.delta.text })}\n\n`)
          );
        }
      }
      controller.enqueue(encoder.encode('data: [DONE]\n\n'));
      controller.close();
    },
  });

  return new Response(readable, {
    headers: {
      'Content-Type':  'text/event-stream',
      'Cache-Control': 'no-cache',
    },
  });
}
```

## When to choose each

**Use WebSockets when**:
- The client needs to send data to the server on the same persistent connection
- Building a chat app, multiplayer game, or collaborative editing
- You need sub-100ms latency in both directions

**Use SSE when**:
- You need server-to-client streaming (notifications, live updates, LLM output)
- You want simpler deployment (works through standard HTTP proxies)
- You're on a platform that doesn't support WebSocket upgrades (some edge runtimes)
- You want the browser's built-in reconnection handling

For most applications — dashboards with live data, notifications, AI streaming — SSE is sufficient and significantly simpler to operate. WebSockets are the right choice only when you genuinely need bidirectional low-latency communication on a single connection.
