The database migration that looks like a one-liner in your migration file can lock a 10-million-row table for 30 seconds. In a production system with active connections, that 30 seconds is 30 seconds of downtime — or a cascade of timeouts that takes the app with it.

The root problem: migrations that run synchronously at deploy time are coupled to your application's live traffic. The database doesn't distinguish between "maintenance migration" and "user-facing query." It just locks.

Here's the risk model and the sequencing that avoids it.

## What causes lock contention

Adding a NOT NULL column with a default:

```sql
-- ✗ Locks the entire table while rewriting every row
ALTER TABLE scans ADD COLUMN source TEXT NOT NULL DEFAULT 'manual';
```

In PostgreSQL, prior to version 11, this rewrites every row to include the new column with its default value. On a large table, this holds an `ACCESS EXCLUSIVE` lock for the entire rewrite duration. Every read and write to that table blocks.

PostgreSQL 11+ handles constant defaults faster, but non-constant defaults (sequences, functions, subqueries) still require the rewrite. And adding a constraint — like `CHECK` or `UNIQUE` — still requires a full table scan to validate existing rows.

## The three-phase pattern

The safe approach: separate the migration into phases that can each be deployed independently.

**Phase 1: Add column nullable, no constraint.**

```sql
-- Instant. No lock held beyond a brief metadata change.
ALTER TABLE scans ADD COLUMN source TEXT;
```

**Phase 2: Backfill existing rows in batches.**

```ts
// Run as a background job, not a migration
async function backfillScanSource() {
  const BATCH = 1000;
  let lastId = 0;

  while (true) {
    const rows = await db.execute(sql`
      UPDATE scans
      SET source = 'manual'
      WHERE source IS NULL
        AND id > ${lastId}
      ORDER BY id
      LIMIT ${BATCH}
      RETURNING id
    `);

    if (rows.length === 0) break;
    lastId = rows[rows.length - 1].id;

    // Brief pause between batches — don't saturate the database
    await new Promise(r => setTimeout(r, 50));
  }
}
```

Batched updates hold short-lived row locks on small chunks. They don't block reads. They can be cancelled without leaving the table in a partial state.

**Phase 3: Add the constraint once the backfill is complete.**

```sql
-- Only after backfill confirms source IS NOT NULL for all rows
ALTER TABLE scans ALTER COLUMN source SET NOT NULL;
```

This validates the constraint. If the backfill is complete, the validation is fast. Some databases support `NOT VALID` + `VALIDATE CONSTRAINT` to separate the validation further.

## Renaming a column

Column renames are particularly risky because they break running app instances immediately. The app in production is still querying `old_column`, and a migration that renames it to `new_column` breaks every query in flight.

Safe pattern:

```sql
-- Phase 1: Add new column
ALTER TABLE scans ADD COLUMN scan_source TEXT;

-- Phase 2: Backfill + write dual columns in the app
-- (App writes to both old_column and scan_source, reads from old_column)
UPDATE scans SET scan_source = source WHERE scan_source IS NULL;

-- Phase 3: Deploy app reading from scan_source
-- (App reads from scan_source, writes to both)

-- Phase 4: Stop writing to source
-- (App reads and writes scan_source only)

-- Phase 5: Drop old column
ALTER TABLE scans DROP COLUMN source;
```

Five deploys. Not one. This is the cost of zero downtime on a live system. The alternative — rename it in one migration — is a gamble on how fast your deploy completes versus how long your app holds open connections.

## Index creation

Adding an index to a large table without `CONCURRENTLY`:

```sql
-- ✗ Locks writes for the duration of index build
CREATE INDEX idx_scans_asin ON scans(asin);
```

With `CONCURRENTLY`:

```sql
-- ✓ No write lock — slower to build, but live traffic continues
CREATE INDEX CONCURRENTLY idx_scans_asin ON scans(asin);
```

`CONCURRENTLY` takes longer and uses more resources, but it does not block writes. The trade-off is always worth it on tables with active traffic.

Note: `CREATE INDEX CONCURRENTLY` cannot run inside a transaction. If your migration framework wraps all migrations in transactions, you'll need to opt out for this migration specifically:

```ts
// In Drizzle — disable transaction for this migration
export async function up(db: NodePgDatabase) {
  await db.execute(sql`
    CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_scans_asin ON scans(asin)
  `);
}
```

## What we track

Every migration gets a risk label before it ships:

- **SAFE** — metadata-only change, no row rewrite, no full-table lock
- **BACKFILL REQUIRED** — requires phased approach with background job
- **CONCURRENTLY REQUIRED** — index creation must use `CONCURRENTLY`
- **MULTI-DEPLOY** — rename or type change that requires overlapping app versions

The label goes in the migration file as a comment. It forces the decision to be made before deploy, not during an incident.

```sql
-- Risk: BACKFILL REQUIRED
-- Phase: 1 of 3
-- Backfill job: scripts/backfill-scan-source.ts
ALTER TABLE scans ADD COLUMN source TEXT;
```

Three years ago, a column rename broke a production system for 11 minutes because the migration and deploy were coupled. The fix was a four-deploy process over two days. The lesson: migrations are a deployment concern, not just a database concern.
