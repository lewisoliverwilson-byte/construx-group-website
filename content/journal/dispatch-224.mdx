Drizzle is not a traditional ORM in the active-record sense. It doesn't have models with methods. It doesn't abstract away SQL. It's a query builder that generates typed SQL, with a migration system that uses your TypeScript schema as the source of truth.

This makes it significantly different from Prisma or TypeORM, and better suited to how we want to work with the database.

## The schema definition

```ts
// schema.ts
import { pgTable, uuid, text, boolean, timestamp, integer } from 'drizzle-orm/pg-core';

export const workspaces = pgTable('workspaces', {
  id: uuid('id').primaryKey().defaultRandom(),
  name: text('name').notNull(),
  slug: text('slug').notNull().unique(),
  createdAt: timestamp('created_at', { withTimezone: true }).defaultNow().notNull(),
});

export const members = pgTable('members', {
  id: uuid('id').primaryKey().defaultRandom(),
  workspaceId: uuid('workspace_id').notNull().references(() => workspaces.id, { onDelete: 'cascade' }),
  userId: text('user_id').notNull(), // Clerk user ID
  role: text('role').notNull().default('member'), // 'owner' | 'admin' | 'member'
  joinedAt: timestamp('joined_at', { withTimezone: true }).defaultNow().notNull(),
});

export const messages = pgTable('messages', {
  id: uuid('id').primaryKey().defaultRandom(),
  channelId: uuid('channel_id').notNull(),
  authorId: text('author_id').notNull(),
  content: text('content').notNull(),
  pinned: boolean('pinned').default(false),
  createdAt: timestamp('created_at', { withTimezone: true }).defaultNow().notNull(),
});
```

The schema is TypeScript. Drizzle infers the types automatically — `db.select().from(messages)` returns `typeof messages.$inferSelect[]` without explicit type annotation.

## Querying with relations

Drizzle has a `relations()` API for defining foreign key relationships and a `.query` API that uses those relations for eager loading:

```ts
// Define relations
export const workspacesRelations = relations(workspaces, ({ many }) => ({
  members: many(members),
}));

export const membersRelations = relations(members, ({ one }) => ({
  workspace: one(workspaces, {
    fields: [members.workspaceId],
    references: [workspaces.id],
  }),
}));

// Query with related data
const workspace = await db.query.workspaces.findFirst({
  where: eq(workspaces.slug, slug),
  with: {
    members: {
      where: eq(members.role, 'owner'),
      limit: 5,
    },
  },
});
// workspace.members is typed as Member[]
```

This generates a single query using JOINs rather than N+1 queries. The type system ensures that `workspace.members` is properly typed — if `members` is included in `with`, TypeScript knows it exists; if not, accessing it is a type error.

## The query builder for complex queries

The `.query` API is convenient for simple fetch-with-relations patterns. For more complex queries, the query builder provides explicit control:

```ts
// Complex aggregation query
const stats = await db
  .select({
    channelId: messages.channelId,
    messageCount: count(messages.id),
    lastMessageAt: max(messages.createdAt),
  })
  .from(messages)
  .where(
    and(
      eq(messages.workspaceId, workspaceId),
      gte(messages.createdAt, sevenDaysAgo),
    )
  )
  .groupBy(messages.channelId)
  .orderBy(desc(count(messages.id)))
  .limit(10);
```

The SQL generated by this is exactly what you'd write by hand. The Drizzle layer adds type safety: `stats[0].messageCount` is typed as `number`, `stats[0].lastMessageAt` is typed as `Date | null`.

## When we write raw SQL

Some queries don't fit cleanly into the query builder. We reach for raw SQL when:

**CTEs (Common Table Expressions):** Complex reporting queries that need multiple WITH clauses.

```ts
const result = await db.execute(sql`
  WITH active_users AS (
    SELECT DISTINCT author_id
    FROM messages
    WHERE workspace_id = ${workspaceId}
      AND created_at > now() - interval '7 days'
  ),
  user_stats AS (
    SELECT author_id, COUNT(*) as message_count
    FROM messages
    WHERE workspace_id = ${workspaceId}
    GROUP BY author_id
  )
  SELECT au.author_id, us.message_count
  FROM active_users au
  JOIN user_stats us USING (author_id)
  ORDER BY us.message_count DESC
  LIMIT 10
`);
```

**Window functions:** Ranking, running totals, lead/lag operations.

**Full-text search:** PostgreSQL's `tsvector` / `tsquery` syntax isn't abstracted by Drizzle.

**RLS configuration:** `SELECT set_config(...)` for row-level security context.

The `sql` tagged template literal properly parameterises values — no SQL injection risk even when building raw queries.

## Migration management

Drizzle Kit generates migrations from the schema diff:

```bash
npx drizzle-kit generate  # Generate migration SQL
npx drizzle-kit push      # Apply migrations to database
```

Generated migrations are SQL files committed to the repository. We review them before running — a migration that Drizzle generates automatically can still be dangerous on a large table.

```sql
-- 0023_add_pinned_column.sql (generated by drizzle-kit)
ALTER TABLE "messages" ADD COLUMN "pinned" boolean DEFAULT false;
```

For our cases requiring `CONCURRENTLY` or batched backfills, we write the migration SQL manually and commit it to the migration directory.

## What Drizzle doesn't have

**Model methods.** No `user.save()`, no `message.destroy()`. All operations go through `db.insert()`, `db.update()`, `db.delete()`. This is by design — it keeps database operations explicit.

**Lifecycle hooks.** No `beforeSave()`, `afterCreate()`. Side effects on database writes are handled in the service layer above Drizzle.

**Soft deletes.** No built-in `paranoid` mode. We implement soft deletes with a `deleted_at` column and filter in queries.

These absences are not bugs — they're the Drizzle philosophy. Keep the ORM close to SQL. Don't abstract things that SQL handles well.

## The comparison to Prisma

Prisma is the more popular alternative. The key difference: Prisma generates its own Prisma Client from a schema file, while Drizzle uses TypeScript directly. Prisma's type inference is excellent; Drizzle's is arguably more transparent because the types are derived from standard TypeScript table definitions you can read and reason about.

We chose Drizzle because it stays closer to SQL, makes it easier to write custom queries, and doesn't require a separate schema language or client generation step.

For a team comfortable with SQL (which we are), Drizzle's philosophy matches how we think about data access. If you want more ORM magic and less SQL exposure, Prisma is the better choice.
