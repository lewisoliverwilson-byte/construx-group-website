The strangler fig tree grows around an existing tree, eventually replacing it while the host continues to support it. The pattern — named by Martin Fowler — describes a migration approach: wrap the old system with a new one, move functionality piece by piece, retire the old system when nothing remains.

## Why rewrites fail

The big bang rewrite is the default impulse when a codebase becomes painful: "Let's start fresh, build it properly." It fails for predictable reasons:

- The new system must reach feature parity before it can replace the old one
- During the rewrite, the old system continues to need maintenance and new features
- The rewrite takes 2-3x longer than estimated, during which nothing ships to users
- Edge cases in the old system were never documented and appear only in production
- At the end, you replace one problem codebase with a new one nobody fully understands yet

The strangler fig pattern avoids all of these by making migration incremental and reversible.

## The implementation

The central mechanism is a routing proxy. All traffic enters the proxy; the proxy sends requests to either the old or the new system based on which route has been migrated.

```
Client → Proxy (nginx / Cloudflare / Next.js middleware) → Old System
                                                          → New System
```

```nginx
# nginx routing: migrated routes go to new system
location /api/v2/products {
  proxy_pass http://new-system:3001;
}

location /api/v2/users/auth {
  proxy_pass http://new-system:3001;
}

# Everything else goes to old system
location / {
  proxy_pass http://old-system:3000;
}
```

As each route is migrated to the new system, you add a line to the proxy config. The old system shrinks; the new system grows. At the end, the old system has no routes left — it's been strangled.

## Migration order

Migrate routes in order of their value and complexity:

1. **New features**: build exclusively on the new system from day one. No legacy code. Validates the new architecture before migration starts.

2. **Leaf routes**: routes with no dependencies on other old-system functionality. API endpoints that read a database table and return JSON — simple, self-contained.

3. **Connected routes**: routes that depend on shared state (auth sessions, shared database tables). Requires careful data synchronisation.

4. **Core flows**: checkout, authentication, critical paths. Migrate last, when the new system is proven.

## Data migration

The hardest part of the strangler fig pattern is shared data. During migration, both systems need to read and write the same records.

**Strategy 1: Shared database**: both old and new system point at the same Postgres instance. Simple but means your database schema must satisfy both systems — no schema changes that would break the old system.

**Strategy 2: Dual-write**: new system writes to its own database; also writes to the old database for compatibility. The old system continues to function. When migration is complete, remove the dual-write.

**Strategy 3: Read from both**: the new system reads from its database for its own data, queries the old system's API for data it hasn't migrated yet. Decoupled, but adds latency and dependencies.

The right strategy depends on your situation. Shared database is the most common for SQL-based systems.

## Feature flags for gradual rollout

Route migration doesn't have to be all-or-nothing. Use a feature flag to route a percentage of traffic to the new system:

```ts
// middleware.ts
export function middleware(req: NextRequest) {
  const newSystemRollout = 0.1; // 10% to new system

  if (req.nextUrl.pathname.startsWith('/api/products')) {
    if (Math.random() < newSystemRollout) {
      return NextResponse.rewrite(new URL('/new/api/products', req.url));
    }
  }
  return NextResponse.next();
}
```

Start at 1%, monitor error rates and latency, increase to 10%, 50%, 100%. Roll back by setting the flag to 0.

## The reverse strangler: extracting a service

The pattern works in reverse too — extracting a specific service from a monolith into its own deployment:

1. Identify the service boundary (e.g., the email sending subsystem)
2. Route all email requests through a thin internal API
3. Move the implementation behind that API to a separate service
4. The monolith calls the service; nothing else changes

The API is the strangler vine. Once everything routes through it, you can move the implementation anywhere.

## Our approach for The Hyve

The Hyve started as a monolith with auth, workspace management, messaging, and file storage all in one Next.js application. The AI context pipeline needed to be separated — it had different scaling characteristics (CPU-intensive, long-running) and blocked deployment of other features.

We extracted it using the strangler fig: all AI context requests went through a thin internal `/api/context` endpoint. We moved the implementation to a separate Node.js service, updated the endpoint to proxy to that service, and deployed them independently. The main application had no idea anything changed.

Total migration time: three weeks, with normal feature shipping throughout.
