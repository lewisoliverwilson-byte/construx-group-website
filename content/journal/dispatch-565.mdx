HTTP caching headers are the mechanism browsers and CDNs use to avoid re-fetching content they already have. They're also the source of most "the page isn't updating" bugs. Understanding the model takes 20 minutes; it removes hours of debugging.

## Cache-Control

`Cache-Control` is the primary caching directive. It's set by the server, read by browsers and CDNs.

```http
Cache-Control: max-age=3600, stale-while-revalidate=60
```

Key directives:

**`max-age=N`**: Cache the response for N seconds. After that, the cached copy is considered stale.

**`s-maxage=N`**: Like `max-age` but for shared caches (CDNs). Overrides `max-age` for CDNs, leaving browser behaviour unchanged.

**`no-cache`**: Misleadingly named. The response can be cached, but the browser must revalidate it on every request (using ETag or Last-Modified). Not the same as "don't cache."

**`no-store`**: Actually "don't cache" — the response is never stored. Use for sensitive data (session tokens, user-specific pages).

**`must-revalidate`**: Once the response is stale (past `max-age`), the browser must revalidate before serving it from cache. Prevents serving stale content even when the origin is unreachable.

**`stale-while-revalidate=N`**: Serve the stale response immediately while revalidating in the background. The user sees no latency; the cache becomes fresh after the background request completes.

**`immutable`**: Tells the browser the response will never change. Used with content-addressed assets (hashed filenames). The browser won't revalidate even when the user does a hard refresh. Combined with a long `max-age`:

```http
Cache-Control: max-age=31536000, immutable
```

## ETag and conditional requests

`ETag` is a version identifier for the response — typically a hash of the content or a version string.

```http
ETag: "abc123def456"
```

When the browser has a cached response with an ETag, it sends a conditional request:

```http
GET /api/data HTTP/1.1
If-None-Match: "abc123def456"
```

If the content hasn't changed, the server responds with `304 Not Modified` — no body, just headers. The browser uses its cached copy. If the content changed, the server responds with `200 OK` and the new content (and a new ETag).

This pattern is efficient: the browser pays the latency cost of an HTTP request but avoids the transfer cost when content is unchanged.

## Last-Modified

Older than ETag, works on the same principle. The server returns a timestamp:

```http
Last-Modified: Tue, 01 Aug 2029 12:00:00 GMT
```

The browser sends:

```http
GET /api/data HTTP/1.1
If-Modified-Since: Tue, 01 Aug 2029 12:00:00 GMT
```

Server responds `304` if unchanged, `200` with new content if changed. ETag is preferred — it handles cases where content is regenerated with the same effective value, or where byte-identical content is produced at different times.

## The caching decision tree

For most Next.js apps:

```
Static assets (JS, CSS, images with hashed names)
  → Cache-Control: max-age=31536000, immutable

HTML pages (SSR or SSG)
  → Cache-Control: no-cache (revalidate every request, but serve from cache instantly if ETag matches)
  or
  → Cache-Control: max-age=60, stale-while-revalidate=300 (serve stale for 5 minutes while revalidating)

API responses (user-specific data)
  → Cache-Control: private, no-store

API responses (shared, can be cached)
  → Cache-Control: public, max-age=30, s-maxage=60, stale-while-revalidate=120
```

## Setting headers in Next.js

In `next.config.js`:

```js
/** @type {import('next').NextConfig} */
const nextConfig = {
  headers: async () => [
    {
      source: '/_next/static/:path*',
      headers: [{ key: 'Cache-Control', value: 'public, max-age=31536000, immutable' }],
    },
    {
      source: '/api/:path*',
      headers: [{ key: 'Cache-Control', value: 'no-store' }],
    },
  ],
};
```

In a Route Handler:

```ts
export async function GET() {
  const data = await fetchData();
  return Response.json(data, {
    headers: {
      'Cache-Control': 'public, max-age=60, stale-while-revalidate=300',
    },
  });
}
```

In a Server Component with Next.js fetch:

```ts
const data = await fetch('https://api.example.com/data', {
  next: { revalidate: 60 },
});
```

This sets a 60-second revalidation window on the Next.js data cache — separate from the HTTP cache, but the concept is the same.

## The "why isn't this updating" checklist

When a change isn't showing up:

1. **Check the response headers** — what `Cache-Control` does the server actually return? Open DevTools Network tab, click the request, look at response headers.

2. **Check if it's a CDN** — your browser might be fine but a CDN has cached the old response. Purge the CDN cache or test with `curl -H "Cache-Control: no-cache"`.

3. **Check `max-age`** — if it's set to 3600 and the page updated 30 minutes ago, users won't see it for another 30 minutes unless you force revalidation.

4. **For hashed assets** — if your build output has hashed filenames, the problem is usually that the HTML referencing the old hashes is cached. Fix the HTML caching, not the asset caching.

5. **`no-cache` vs `no-store`** — if you set `no-store` on a page you expected to cache-and-revalidate, it won't be cached at all. Check your directive.

Most "caching is broken" bugs are actually "I set the wrong directive" bugs.
