Drizzle Kit compares your TypeScript schema to the last applied migration snapshot and generates the SQL diff. The generated SQL is the source of truth — you review it, run it, and it's in the migration history forever. Getting the workflow right matters because production schema changes can lock tables and cause downtime.

## The basic workflow

```bash
# Generate a migration from schema changes
npx drizzle-kit generate

# Review the generated SQL in drizzle/migrations/
# Then apply:
npx drizzle-kit migrate

# Or apply programmatically at startup:
import { migrate } from 'drizzle-orm/postgres-js/migrator';
await migrate(db, { migrationsFolder: './drizzle/migrations' });
```

The migration files are plain SQL:

```sql
-- drizzle/migrations/0004_add_subscription_tier.sql
ALTER TABLE "users" ADD COLUMN "subscription_tier" text NOT NULL DEFAULT 'free';
ALTER TABLE "users" ADD COLUMN "stripe_customer_id" text;
CREATE INDEX "users_stripe_customer_id_idx" ON "users" ("stripe_customer_id");
```

Review every generated migration before applying. Drizzle Kit is usually right, but it can't know your intent — it only knows the diff.

## Safe migrations: backward-compatible first

The critical rule: **never make a breaking schema change in a single deployment**. Instead, expand then contract:

**Step 1 — deploy: add the new column, keep the old one**

```sql
ALTER TABLE "orders" ADD COLUMN "total_pence" integer;
```

**Step 2 — deploy: backfill data**

```sql
UPDATE "orders" SET "total_pence" = ROUND("total_amount" * 100)
WHERE "total_pence" IS NULL;
```

**Step 3 — deploy: make the new column required, use it in code**

```sql
ALTER TABLE "orders" ALTER COLUMN "total_pence" SET NOT NULL;
```

**Step 4 — deploy: drop the old column**

```sql
ALTER TABLE "orders" DROP COLUMN "total_amount";
```

Each step is backward-compatible with the previous deploy. If step 3 fails, you roll back to step 2 code — the column still exists, nothing breaks.

## Adding a NOT NULL column safely

The most common footgun: adding a NOT NULL column to a large table requires a full table scan and a lock.

```sql
-- ❌ Locks the table for the duration — can be minutes on a large table
ALTER TABLE "products" ADD COLUMN "slug" text NOT NULL;

-- ✅ Three-step approach:
-- Step 1: add nullable
ALTER TABLE "products" ADD COLUMN "slug" text;

-- Step 2: backfill (can run while the app is live)
UPDATE "products" SET "slug" = lower(replace(name, ' ', '-'))
WHERE "slug" IS NULL;

-- Step 3: add the NOT NULL constraint (fast — data is already populated)
ALTER TABLE "products" ALTER COLUMN "slug" SET NOT NULL;
```

Postgres 12+ has `NOT VALID` for adding foreign key constraints without a full table scan:

```sql
-- Add constraint without validating existing rows (fast)
ALTER TABLE "orders" ADD CONSTRAINT "orders_user_id_fk"
  FOREIGN KEY ("user_id") REFERENCES "users" ("id") NOT VALID;

-- Validate in a separate transaction (doesn't hold an exclusive lock)
ALTER TABLE "orders" VALIDATE CONSTRAINT "orders_user_id_fk";
```

## Index creation without locking

Standard `CREATE INDEX` takes a `SHARE` lock, blocking writes:

```sql
-- ❌ Blocks writes during index build
CREATE INDEX ON "products" ("category");

-- ✅ CONCURRENTLY — no lock on writes, table stays readable and writable
CREATE INDEX CONCURRENTLY ON "products" ("category");
```

`CONCURRENTLY` takes longer but doesn't block the application. Use it for large tables in production.

## Rollback plan

Every migration should have a rollback. Drizzle Kit doesn't generate rollback SQL, so write it manually:

```sql
-- 0004_rollback.sql (keep alongside the migration, don't apply automatically)
ALTER TABLE "users" DROP COLUMN IF EXISTS "subscription_tier";
ALTER TABLE "users" DROP COLUMN IF EXISTS "stripe_customer_id";
DROP INDEX IF EXISTS "users_stripe_customer_id_idx";
```

If a migration causes problems in production, having the rollback SQL ready means you can apply it in 30 seconds rather than scrambling.

## Drizzle push for development

In development, skip the migration file and push schema changes directly:

```bash
npx drizzle-kit push
```

`push` applies the schema diff to your dev database without creating a migration file. Useful for rapid iteration. Never use it on production.
