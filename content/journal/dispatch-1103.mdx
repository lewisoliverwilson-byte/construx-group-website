excerpt: "Knative Eventing provides the infrastructure for event-driven microservices on Kubernetes. While Knative Serving (dispatch-1070) handles HTTP request-driven scale-to-zero, Knative Eventing handles asynchronous event flows. The core abstractions are: Source (emits CloudEvents from an external system — Kafka, GitHub webhooks, cron, PubSub), Broker (a durable event bus that receives CloudEvents and dispatches them to matching subscribers), Trigger (a subscription to a Broker with an optional filter — e.g., only events of type orders.created from source construx.orders), and Channel (a lightweight pub/sub channel backed by Kafka, Redis, or in-memory). CloudEvents is the CNCF specification for event envelope format — a JSON structure with mandatory fields (type, source, id, specversion) plus optional extensions and an arbitrary data payload. Knative Eventing's trigger-based routing means new consumers can subscribe to existing events without changing the producer — the producer publishes to a Broker, and any number of Triggers can independently receive and filter those events. At Construx, Knative Eventing drives the real-time pipeline: order created events fan out to the billing service (via Trigger), the analytics service (via Trigger), and the notification service (via Trigger), all from a single order-service Broker publish."

## Broker, Trigger, and Source configuration

```yaml
# MSB (Multi-tenant Simple Broker backed by Kafka)
apiVersion: eventing.knative.dev/v1
kind: Broker
metadata:
  name: construx-events
  namespace: construx-prod
  annotations:
    eventing.knative.dev/broker.class: Kafka
spec:
  config:
    apiVersion: v1
    kind: ConfigMap
    name: kafka-broker-config
    namespace: knative-eventing
  delivery:
    deadLetterSink:
      ref:
        apiVersion: v1
        kind: Service
        name: events-dlq-handler   # dead letter queue for failed deliveries
    backoffPolicy: exponential
    backoffDelay: "PT2S"
    timeout: "PT10S"
    retry: 3

---
# ApiServerSource: emit a CloudEvent for every Kubernetes Event in construx-prod
apiVersion: sources.knative.dev/v1
kind: ApiServerSource
metadata:
  name: k8s-events-source
  namespace: construx-prod
spec:
  serviceAccountName: api-server-source
  mode: Resource
  resources:
    - apiVersion: v1
      kind: Event
  sink:
    ref:
      apiVersion: eventing.knative.dev/v1
      kind: Broker
      name: construx-events

---
# KafkaSource: consume from an existing Kafka topic and emit as CloudEvents
apiVersion: sources.knative.dev/v1beta1
kind: KafkaSource
metadata:
  name: orders-kafka-source
  namespace: construx-prod
spec:
  bootstrapServers:
    - kafka.construx-infra.svc.cluster.local:9092
  topics:
    - construx.orders.created
  consumerGroup: knative-eventing-orders-source
  sink:
    ref:
      apiVersion: eventing.knative.dev/v1
      kind: Broker
      name: construx-events

---
# Trigger: billing-service subscribes to orders.created events
apiVersion: eventing.knative.dev/v1
kind: Trigger
metadata:
  name: billing-service-trigger
  namespace: construx-prod
spec:
  broker: construx-events
  filter:
    attributes:
      type:   orders.created
      source: construx/orders-api
  subscriber:
    ref:
      apiVersion: serving.knative.dev/v1
      kind: Service
      name: billing-service   # Knative Service — auto scales to handle load

---
# Trigger: analytics-service subscribes to ALL events (no filter)
apiVersion: eventing.knative.dev/v1
kind: Trigger
metadata:
  name: analytics-service-trigger
  namespace: construx-prod
spec:
  broker: construx-events
  subscriber:
    ref:
      apiVersion: v1
      kind: Service
      name: analytics-service   # standard k8s Service
    uri: /events/ingest
```

```go
// CloudEvents receiver: Knative Eventing delivers via HTTP POST to the subscriber
// The SDK handles envelope parsing, type routing, and response codes

package main

import (
    "context"
    "fmt"
    "log"

    cloudevents "github.com/cloudevents/sdk-go/v2"
)

type OrderCreated struct {
    TenantID string  `json:"tenant_id"`
    OrderID  string  `json:"order_id"`
    Amount   float64 `json:"amount"`
}

func handleOrderCreated(ctx context.Context, event cloudevents.Event) error {
    var order OrderCreated
    if err := event.DataAs(&order); err != nil {
        return fmt.Errorf("failed to parse order: %w", err)
    }
    fmt.Printf("billing: processing order %s for tenant %s amount=%.2f\n",
        order.OrderID, order.TenantID, order.Amount)
    // ... billing logic
    return nil
}

func main() {
    c, _ := cloudevents.NewDefaultClient()
    // Return 2xx → event acked
    // Return 4xx → event dropped (do not retry)
    // Return 5xx / timeout → event retried with backoff
    log.Fatal(c.StartReceiver(context.Background(), handleOrderCreated))
}
```

Knative Eventing vs Kafka direct integration vs NATS JetStream vs AWS EventBridge vs Apache Camel: Direct Kafka integration requires each service to implement a Kafka consumer — correct for high-throughput stream processing but adds Kafka client dependency to every service and couples services to Kafka's offset management model. NATS JetStream (dispatch-1090) provides similar event fan-out with lower operational overhead and a built-in KV store, but without the CloudEvents envelope standard or the Kubernetes-native Trigger/Broker model. AWS EventBridge is the managed alternative — excellent for AWS-native event routing across services and accounts, but vendor-locked and limited for in-cluster service-to-service eventing. Apache Camel K provides >300 connectors for external systems to Kubernetes, complementing Knative Eventing for source integration. Knative Eventing's key advantage is the trigger-based subscription model: producers are completely decoupled from consumers — a new consumer subscribes to a Broker via a Trigger without any producer change. Combined with Knative Serving's scale-to-zero, event consumers start cold and scale with event rate — you don't run idle consumers for low-frequency events.
