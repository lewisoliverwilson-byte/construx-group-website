date: "2034-02-01"
excerpt: "Grafana Tempo is a high-scale distributed tracing backend that stores traces in object storage (S3, GCS, Azure Blob) with no per-trace indexing — unlike Jaeger or Zipkin, which require a search index over trace metadata, Tempo stores traces as blobs keyed by trace ID and retrieves them directly. The trade-off: Tempo requires an external system (Loki, Prometheus, or the Tempo metrics generator) to produce trace IDs worth looking up. The typical flow is: a Prometheus alert fires, you jump to an exemplar attached to the metric (exemplars embed trace IDs in Prometheus time series), Grafana uses the trace ID to fetch the full trace from Tempo. TraceQL is Tempo's query language — it can search traces by service name, duration, span attributes, and status code, and supports structural queries like 'find all traces where a database span followed by a network error'. The Tempo metrics generator derives service graph metrics and span metrics from the trace stream itself, producing RED metrics (Rate, Error, Duration) for every service-to-service edge without requiring Prometheus instrumentation on each service. Tempo is deployed in Construx as a distributed component (distributor, ingester, querier, compactor) backed by S3, replacing Jaeger after trace volume exceeded 50GB/day."

## Tempo TraceQL queries and config

```traceql
# TraceQL: structural and attribute-based trace queries

# All traces with a span that errored in the payments-api service
{ resource.service.name = "payments-api" && status = error }

# Traces where total duration exceeded 5 seconds (slow requests)
{ duration > 5s }

# Traces where a database span was followed by an HTTP 500 span
# (structural query: ordering matters)
{ span.db.system = "postgresql" } >> { http.status_code = 500 }

# Find traces with high db query count (N+1 query detection)
{ span.db.system = "postgresql" } | count() > 20

# Traces affecting a specific tenant
{ span.tenant_id = "acme" && status = error && duration > 2s }

# Aggregate: p99 duration grouped by service
{ resource.service.name =~ ".*" } | rate() by (resource.service.name)
```

```yaml
# Grafana Tempo: distributed deployment config (Helm)
# grafana/tempo-distributed

tempo:
  reportingEnabled: false

  storage:
    trace:
      backend: s3
      s3:
        bucket: construx-tempo-traces
        region: eu-west-2
        endpoint: s3.eu-west-2.amazonaws.com

  global_overrides:
    max_traces_per_user: 10000000
    ingestion_rate_limit_bytes: 50000000   # 50 MB/s per tenant
    ingestion_burst_size_bytes: 100000000
    max_bytes_per_trace: 5000000           # 5 MB max trace size

  # Metrics generator: derive service graph + RED metrics from traces
  metricsGenerator:
    enabled: true
    remoteWrite:
      - url: http://mimir.construx-monitoring.svc.cluster.local/api/v1/push

  # Compactor: merge small blocks in S3 into larger ones
  compactor:
    compaction:
      block_retention: 720h   # 30 days
      compacted_block_retention: 1h

distributor:
  replicas: 3
  receivers:
    otlp:
      protocols:
        grpc:
          endpoint: 0.0.0.0:4317
        http:
          endpoint: 0.0.0.0:4318
    jaeger:
      protocols:
        thrift_compact:
          endpoint: 0.0.0.0:6831
        grpc:
          endpoint: 0.0.0.0:14250

ingester:
  replicas: 5
  config:
    max_block_duration: 5m     # flush to S3 every 5 minutes

querier:
  replicas: 3

compactor:
  replicas: 1
```

```yaml
# Grafana datasource: Tempo with exemplar linkage to Prometheus
# Exemplars bridge metrics → traces: a Prometheus time series embeds trace IDs
# at high-latency points, giving you a direct link from alert → trace

datasources:
  - name: Tempo
    type: tempo
    url: http://tempo-query-frontend.construx-monitoring.svc.cluster.local:3100
    jsonData:
      tracesToLogsV2:
        datasourceUid: loki
        spanStartTimeShift: "-1m"
        spanEndTimeShift: "1m"
        filterByTraceID: true
        filterBySpanID: true
      serviceMap:
        datasourceUid: prometheus
      search:
        hide: false
      nodeGraph:
        enabled: true   # render service dependency graph from trace data

  - name: Prometheus
    type: prometheus
    url: http://mimir.construx-monitoring.svc.cluster.local/prometheus
    jsonData:
      exemplarTraceIdDestinations:
        - name: trace_id
          datasourceUid: tempo    # click exemplar → jump to Tempo trace
```

Tempo vs Jaeger vs Zipkin vs Datadog APM vs AWS X-Ray: Jaeger was the reference open-source distributed tracing system for years — excellent UI, Cassandra or Elasticsearch backend, robust sampling. At high trace volume (50GB+/day), Jaeger's Elasticsearch backend becomes expensive and operationally complex. Zipkin is simpler but older and less actively developed. Datadog APM provides excellent correlation between traces, logs, and metrics with minimal setup — but per-host pricing makes it expensive at scale. AWS X-Ray is tightly integrated with AWS services (Lambda, API Gateway, ECS) but has a weaker query model and limited support for non-AWS workloads. Tempo's core insight is that object storage (S3) is 50x cheaper than Elasticsearch per GB — and distributed tracing is inherently write-heavy with infrequent random reads. By removing the search index and requiring trace IDs (obtained via exemplars, Loki log links, or TraceQL attribute search), Tempo achieves dramatically lower storage costs. TraceQL's structural query model (sequences of spans, aggregations over spans) is more expressive than Jaeger's tag-based search for diagnosing complex distributed failures.
