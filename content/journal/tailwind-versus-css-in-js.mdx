All three Construx products use Tailwind CSS. We chose it before the first line of product code was written and haven't reconsidered it.

Here's the full picture of that choice — including where it's worked well and where it falls short.

## Why Tailwind

The core argument for Tailwind in a multi-product small-team context is build speed. Styling with utility classes removes the overhead of naming things (what is this component called?), deciding where to put the styles (component file? global stylesheet? module?), and maintaining the relationship between class names and the elements they style.

With Tailwind, the styles are on the element. You don't need to navigate between files to understand how a component is styled. You read the JSX and the styles are there.

For a team of two building three products, this removed a category of cognitive overhead that accumulated at every small decision. We don't debate naming conventions. We don't refactor CSS that's no longer needed. We don't manage the specificity hierarchy.

## Tailwind's actual weaknesses

**Verbose JSX for complex components.** A card with hover states, dark backgrounds, border variations, and multiple responsive breakpoints produces a `className` string that spans multiple lines. This is ugly and harder to read than well-structured CSS.

We handle this by extracting complex class combinations into variables:

```tsx
const cardBase = [
  'px-5 py-4',
  'bg-[rgba(5,5,18,0.5)]',
  'border border-[rgba(255,255,255,0.06)]',
  'rounded-[3px]',
  'transition-colors hover:border-[rgba(255,255,255,0.1)]',
].join(' ');
```

This is still Tailwind, but the class string is structured. The component reads cleanly because the visual presentation is named implicitly by the variable.

**Arbitrary values for non-standard design tokens.** The Construx design system uses specific values — `rgba(249,115,22,0.1)` for the orange background tint, `rgba(240,239,255,0.7)` for the primary text color — that don't fit cleanly into Tailwind's default palette.

Tailwind supports arbitrary values via square bracket syntax: `bg-[rgba(249,115,22,0.1)]`. This works but produces class strings that are harder to read and don't carry semantic meaning.

Our fix: extend `tailwind.config.js` with semantic tokens for the values we use repeatedly. `text-text-base`, `text-text-muted`, `text-construx` — these map to the design system values and read clearly in JSX.

**CSS keyframe animations.** Tailwind doesn't have arbitrary keyframe animations. We write these in `globals.css` and reference them via custom Tailwind classes or inline `animation` properties.

This is the one area where we consistently fall out of Tailwind into standard CSS. The tradeoff is acceptable — animations are defined once, referenced by class, and the class names are clear (`log-entry`, `histogram-bar`).

## Where CSS-in-JS wins

The strongest argument for CSS-in-JS (Styled Components, Emotion, vanilla-extract) is the dynamic styling case — styles that depend on runtime values, component state, or theme variables.

For dynamic styles, Tailwind requires either conditional class concatenation or inline styles. Neither is as clean as a CSS-in-JS expression that computes the style value directly:

```tsx
// Tailwind: conditional class concatenation
className={`${isActive ? 'bg-orange-500' : 'bg-transparent'}`}

// CSS-in-JS
css={{ backgroundColor: isActive ? theme.orange : 'transparent' }}
```

For most cases, the Tailwind version is fine. For complex conditional styling with many variants, CSS-in-JS produces cleaner code.

We handle this in practice by using inline styles for dynamic values and Tailwind for everything else:

```tsx
<div
  className="px-5 py-4 border-l-2"
  style={{ borderColor: palette.rowBorder }}
>
```

The `borderColor` is dynamic (it changes per item based on the item's tag); the structural styles are Tailwind. This hybrid approach lets us use Tailwind for the 90% case while reaching for inline styles for the 10% that requires dynamic values.

## The configuration overhead

A common complaint about Tailwind is the configuration overhead — the `tailwind.config.js` file, the PostCSS integration, the `globals.css` boilerplate.

This is real but one-time. Across three products, the Tailwind configuration is nearly identical. The setup cost has been paid once; subsequent products reuse the same configuration with minor adjustments.

For a new project, this overhead would be maybe 30 minutes. It's front-loaded and then gone.

## Our actual verdict

Tailwind is the right choice for our context: small team, multiple products, Next.js, TypeScript-first. The productivity gain from not managing a CSS architecture outweighs the weaknesses.

The weaknesses are real — verbose class strings for complex components, arbitrary value syntax for custom design tokens, falling out to `globals.css` for animations. We've developed patterns to handle each one.

If we were building a product with a complex, highly dynamic UI (a design tool, a rich text editor), we'd re-evaluate. For content-adjacent SaaS products with relatively stable layouts, Tailwind has been the right call.
