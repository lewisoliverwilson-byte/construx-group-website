Every Construx project has `strict: true` in its `tsconfig.json`. We've never turned it off. Here's why, and what it means in practice.

## What strict mode enables

`strict: true` is a shorthand for several compiler flags:

- **`strictNullChecks`**: `null` and `undefined` are not assignable to other types without explicit union. `string | null` and `string` are different types.
- **`strictFunctionTypes`**: function parameter types are checked contravariantly.
- **`strictBindCallApply`**: the types of `bind`, `call`, and `apply` are checked.
- **`strictPropertyInitialization`**: class properties must be initialised in the constructor or marked as definitely assigned.
- **`noImplicitAny`**: variables without an inferred type must be explicitly typed; implicit `any` is an error.
- **`noImplicitThis`**: `this` in functions must be explicitly typed.

The most impactful in practice are `strictNullChecks` and `noImplicitAny`. These two flags catch the majority of runtime errors that TypeScript non-strict would silently allow.

## The strictNullChecks difference

Without `strictNullChecks`:

```ts
function getUserName(userId: string): string {
  const user = db.users.findById(userId); // returns User | null
  return user.name; // no error — but user might be null
}
```

This compiles cleanly without strict mode. At runtime, if `findById` returns `null`, this throws `Cannot read properties of null (reading 'name')`.

With `strictNullChecks`:

```ts
function getUserName(userId: string): string {
  const user = db.users.findById(userId); // returns User | null
  return user.name; // Error: Object is possibly 'null'
}
```

You're forced to handle the null case:

```ts
function getUserName(userId: string): string {
  const user = db.users.findById(userId);
  if (!user) throw new Error(`User not found: ${userId}`);
  return user.name;
}
```

Or return `string | null` and propagate the nullability up the call chain. Either way, the possibility of null is made explicit and handled deliberately.

The null-handling code is not extra overhead — it's the code you should have written anyway. Strict mode makes it required rather than optional.

## The noImplicitAny difference

Without `noImplicitAny`:

```ts
function processResults(results) { // results: any (implicit)
  return results.map(r => r.value); // no type checking on any of this
}
```

`results` is implicitly `any`, which means TypeScript stops checking inside this function. You could access `.nonexistentProperty` on `r` and TypeScript wouldn't complain.

With `noImplicitAny`:

```ts
function processResults(results) { // Error: Parameter 'results' implicitly has an 'any' type
```

You must explicitly type the parameter:

```ts
function processResults(results: ProductResult[]): number[] {
  return results.map(r => r.value); // TypeScript now checks that value is a property of ProductResult
}
```

Once typed, TypeScript can verify that `value` exists on `ProductResult`, flag typos (`r.vale` would be an error), and infer the return type correctly.

## The "it's more work" objection

Adding types is work. Handling nulls explicitly is work. Strict mode is genuinely more friction than no strict mode, especially when migrating an existing codebase.

The counterargument: the work is frontloaded, not eliminated. Every type annotation and null check you write at development time is a bug you don't investigate and fix in production. The total work is lower.

For new projects (which all three Construx products were), the strict mode overhead is minimal. You write types from the start; there's no migration cost.

For existing codebases, enabling strict mode gradually via `strictNullChecks` first (then the other flags) is a manageable path. The TypeScript compiler tells you exactly what needs to be fixed.

## The real-world prevention examples

Three specific bugs that strict mode caught in development across our products:

**Scoutr:** An eBay API response field was documented as always-present but was actually optional for certain listing types. Without `strictNullChecks`, we would have accessed it without a null check. With it, TypeScript forced us to handle the optional field, which would have been a runtime crash for that listing type subset.

**The Marqet:** A route handler returned `user | undefined` in one code path. Without strict mode, a later function that passed this user to another function would have silently passed `undefined`. With strict mode, every function in the chain had to declare and handle the possible undefined.

**The Hyve:** A class property was conditionally set in the constructor based on a config flag. Without `strictPropertyInitialization`, this compiled fine. With it, we had to use the definite assignment assertion or change the design to always set the property — which revealed that the conditional initialisation was actually a design problem.

In each case, the strict mode error caught a real bug. Not a hypothetical one — a bug that would have appeared in production under specific conditions.

## The `npx tsc --noEmit` gate

We run `npx tsc --noEmit` as part of every CI build and as a pre-commit check locally. If the TypeScript compiler reports errors, the build fails.

This means we can't ship code with type errors. The type check is a hard gate, not advisory.

The habit from this: we run `npx tsc --noEmit` manually during development whenever we make significant changes, not just at commit time. Finding a type error early is much cheaper than finding it at the CI gate. This has become automatic — it's just part of the development rhythm.
