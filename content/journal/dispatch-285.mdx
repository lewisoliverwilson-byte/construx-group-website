Content Security Policy is a browser security mechanism that tells the browser which sources it's allowed to load scripts, styles, images, and other resources from. A well-configured CSP makes XSS attacks significantly harder — even if an attacker manages to inject a `<script>` tag, the browser won't execute it unless it comes from an approved source.

Most production applications don't have one. It's one of those things that's easy to skip and rarely comes up until something goes wrong.

## The basics

CSP is delivered as an HTTP response header:

```
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-abc123'; style-src 'self' 'unsafe-inline'
```

The directives are a whitelist. `default-src 'self'` means "by default, only load resources from the same origin." `script-src 'self' 'nonce-abc123'` means "only execute scripts from this origin, or scripts with this specific nonce."

The nonce approach is the right one for Next.js: generate a random nonce per request, pass it to your inline scripts (and `next/script`), and the browser executes only nonce-tagged scripts.

## Setting headers in Next.js

The cleanest place to set headers is `next.config.ts`:

```ts
// next.config.ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  headers: async () => [
    {
      source: '/(.*)',
      headers: [
        {
          key: 'X-Frame-Options',
          value: 'DENY',
        },
        {
          key: 'X-Content-Type-Options',
          value: 'nosniff',
        },
        {
          key: 'Referrer-Policy',
          value: 'strict-origin-when-cross-origin',
        },
        {
          key: 'Permissions-Policy',
          value: 'camera=(), microphone=(), geolocation=()',
        },
      ],
    },
  ],
};

export default nextConfig;
```

`X-Frame-Options: DENY` prevents clickjacking. `X-Content-Type-Options: nosniff` prevents MIME-sniffing attacks. These are static headers — set them for every route and move on.

CSP is more nuanced because inline scripts need nonces, and nonces must be random per request.

## Nonce-based CSP via middleware

```ts
// middleware.ts
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';
import { getSession } from '@/lib/auth';

export async function middleware(req: NextRequest) {
  // Generate a cryptographically random nonce
  const nonce = Buffer.from(crypto.randomUUID()).toString('base64');

  const csp = [
    "default-src 'self'",
    // Scripts: only from self, plus nonce-tagged inline scripts
    // 'strict-dynamic' propagates trust to scripts loaded by trusted scripts
    `script-src 'self' 'nonce-${nonce}' 'strict-dynamic'`,
    // Styles: self + inline (inline styles are hard to avoid in Next.js)
    "style-src 'self' 'unsafe-inline'",
    // Images: self + data URIs (for inline SVGs/icons)
    "img-src 'self' data: blob:",
    // Fonts: self only
    "font-src 'self'",
    // Connect: self + your API domains
    "connect-src 'self' https://api.construx.group",
    // No plugins, no embeds
    "object-src 'none'",
    // Base tag restrictions
    "base-uri 'self'",
    // Form submissions: self only
    "form-action 'self'",
    // Upgrade insecure requests in production
    ...(process.env.NODE_ENV === 'production' ? ["upgrade-insecure-requests"] : []),
  ].join('; ');

  const res = NextResponse.next({
    request: {
      headers: new Headers({
        ...Object.fromEntries(req.headers.entries()),
        'x-nonce': nonce,
      }),
    },
  });

  res.headers.set('Content-Security-Policy', csp);

  // Auth guard — redirect to login if not authenticated
  const session = await getSession();
  const isProtected = req.nextUrl.pathname.startsWith('/dashboard');
  if (isProtected && !session) {
    return NextResponse.redirect(new URL('/login', req.url));
  }

  return res;
}

export const config = {
  matcher: [
    '/((?!_next/static|_next/image|favicon.ico).*)',
  ],
};
```

The nonce is set as a request header (`x-nonce`) so server components and layouts can read it.

## Reading the nonce in layout

```tsx
// app/layout.tsx
import { headers } from 'next/headers';

export default async function RootLayout({ children }: { children: React.ReactNode }) {
  const nonce = (await headers()).get('x-nonce') ?? '';

  return (
    <html lang="en">
      <head>
        {/* Any inline scripts here need the nonce */}
      </head>
      <body>
        {children}
        {/* Analytics or other inline scripts */}
        <script
          nonce={nonce}
          dangerouslySetInnerHTML={{
            __html: `window.__NONCE__ = "${nonce}";`,
          }}
        />
      </body>
    </html>
  );
}
```

```tsx
// Using next/script with nonce
import Script from 'next/script';
import { headers } from 'next/headers';

export async function AnalyticsScript() {
  const nonce = (await headers()).get('x-nonce') ?? '';

  return (
    <Script
      src="https://analytics.example.com/script.js"
      nonce={nonce}
      strategy="afterInteractive"
    />
  );
}
```

## Common breakage and how to fix it

**Inline event handlers.** `onclick="..."` attributes in HTML are blocked by a nonce-based CSP. Replace them with `addEventListener` in a nonce-tagged `<script>` block. If you're using React, event handlers in JSX are fine — they compile to `addEventListener` calls.

**Third-party scripts.** If you embed a third-party script (Intercom, Stripe.js, etc.), you need to add their domain to `script-src`. Check their documentation for the exact domains — most third-party scripts load additional scripts from subdomains:

```
script-src 'self' 'nonce-${nonce}' 'strict-dynamic'
  https://js.stripe.com
  https://widget.intercom.io
```

**Stripe iframe.** Stripe's payment elements load in an iframe. You need `frame-src https://js.stripe.com https://hooks.stripe.com` or Stripe's elements will silently fail.

**Inline styles from component libraries.** Some libraries inject inline styles at runtime (Radix UI, Framer Motion). These are blocked by a CSP without `unsafe-inline` in `style-src`. `unsafe-inline` is a weak allowance for styles (it doesn't enable script execution), so it's generally acceptable.

## Testing your CSP

Set the header as `Content-Security-Policy-Report-Only` first. This reports violations to the browser console without enforcing them — you can see what would break before enabling enforcement:

```ts
res.headers.set('Content-Security-Policy-Report-Only', csp);
```

Check the browser console for CSP violation messages. Fix each one by adding the relevant domain to the appropriate directive. When the console is clean, switch to `Content-Security-Policy`.

The Security headers tool at securityheaders.com grades your header configuration and shows what each directive does. An A rating means you haven't missed anything obvious.

## What CSP doesn't protect against

CSP is not a substitute for input sanitisation. If your server reflects unsanitised user input into HTML, an attacker can inject markup that doesn't rely on scripts. CSP also doesn't protect against server-side vulnerabilities — SQL injection, SSRF, insecure direct object references. It's one layer of a defence-in-depth strategy, not the whole strategy.

The value of CSP is in reducing the impact of any XSS that does get through. Combined with `HttpOnly` cookies (which CSP can't steal even if XSS is present), the damage surface for a successful XSS drops significantly.
