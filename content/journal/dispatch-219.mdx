The testing pyramid — lots of unit tests, fewer integration tests, even fewer end-to-end tests — is the standard advice. It's also advice designed for large teams with large codebases where the cost of each test type matters significantly.

For a two-person team building three products, the trade-offs are different. Here's how we actually allocate testing effort.

## What we test rigorously

**Business logic with complex rules.** The Scoutr confidence score algorithm, The Marqet's escrow state machine, The Hyve's membership permission checks. These are the functions where a bug has direct financial or trust consequences.

The confidence score algorithm has 15 unit tests covering edge cases: products with no sales history, products where margin data is unavailable, products with anomalous velocity spikes. Each test is fast (no network calls, no database) and tests a specific algorithmic property.

```ts
describe('confidenceScore', () => {
  it('returns 0 for a product with no sales data', () => {
    const result = confidenceScore({ soldItems: 0, totalListings: 50, margin: 0 });
    expect(result).toBe(0);
  });

  it('weights margin at 35% of the total score', () => {
    const highMargin = confidenceScore({ margin: 1.0, velocity: 0, competition: 0, availability: 0, stability: 0 });
    const lowMargin  = confidenceScore({ margin: 0.0, velocity: 0, competition: 0, availability: 0, stability: 0 });
    expect(highMargin - lowMargin).toBeCloseTo(35); // 35-point difference for full margin range
  });

  it('caps the maximum confidence score at 100', () => {
    const result = confidenceScore({ margin: 1, velocity: 1, competition: 1, availability: 1, stability: 1 });
    expect(result).toBeLessThanOrEqual(100);
  });
});
```

**Authentication and authorisation.** Who can do what. These tests run against a real test database (not a mock) because auth logic interacts with the actual schema, RLS policies, and session state.

**Database migrations.** We test that every migration produces the expected schema state and is reversible. This catches the case where a migration generates correct SQL but the SQL does something unexpected with actual data.

**Webhook signature verification.** Cryptographic functions are easy to get subtly wrong. We test that our signature generation and verification functions are consistent and that tampered payloads are rejected.

## What we test lightly

**API routes.** We have integration tests for the key API endpoints (scan, list, send message) that hit a real test database. These tests are slower than unit tests but faster than Playwright end-to-end tests. They catch the most common class of API bug: a validation rule that's too strict, a query that returns the wrong shape.

We don't test every API route. We test the high-traffic routes and the routes with complex logic. Simple CRUD routes are covered by TypeScript's type checking more than by explicit tests.

**React components.** We test components that have complex interactive states (the DispatchCalendar, the contact form validation) but not components that are primarily layout (the footer, the hero sections). Layout testing is expensive and fragile; visual inspection catches layout bugs faster.

## What we don't test at all

**Simple transformations.** A function that takes a string and formats it as a date doesn't need a unit test. TypeScript's type checking plus visual inspection in development covers it.

**Third-party integrations.** We don't test that the eBay API returns data — that's eBay's problem. We test that our code correctly handles what the eBay API returns, including error responses.

**UI flows in CI.** We don't run Playwright end-to-end tests in CI. Playwright tests are slow, brittle (flaky on timing), and expensive to maintain. We run them manually before major releases. This is a known gap — for a larger team with more stability requirements, e2e tests in CI would be worth the investment.

## The testing infrastructure

All tests use Vitest (not Jest). Vitest is significantly faster than Jest for TypeScript projects because it uses esbuild for transformation rather than Babel. The configuration is simpler and the runtime faster.

```ts
// vitest.config.ts
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    environment: 'node',
    globals: true,
    setupFiles: ['./test/setup.ts'],
  },
});
```

Database tests use a dedicated test database that's reset between test runs. We use `pg_dump` to snapshot the initial state and `psql` to restore it before each test suite.

## The honest gap

Our UI isn't well tested. The components work correctly (TypeScript + our own use catches regressions), but we have no automated protection against visual regressions. If we accidentally change the journal page to orange text on orange background, no test catches it.

For a product at our scale and with our team size, this is an acceptable gap. The cost of comprehensive visual regression testing (screenshot comparison, CI infrastructure, maintenance) exceeds the benefit given our current release velocity.

As products stabilise and release velocity slows, the trade-off will shift. More tests make sense when the feature set is stable enough that tests don't need constant updates.

## The principle

Test the things that are expensive to debug in production. Don't test the things that TypeScript, linting, and visual inspection cover adequately.

A 500-test suite that covers every function is expensive to maintain and gives false confidence. A 50-test suite focused on business-critical logic is faster to run, cheaper to maintain, and catches the bugs that actually matter.
