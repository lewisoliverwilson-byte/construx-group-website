Cold start is init phase. Warm invoke is microseconds. Memory buys CPU.

## Lambda execution model — phases and lifecycle

```python
# Lambda handler — Python 3.12 runtime
# File: handler.py

import json
import boto3
import os

# INIT PHASE: code at module level runs once when the environment starts
# This is where you should create clients, open connections, load configs
# Cold start = the init phase plus container download/start (~100ms-2s total)

dynamodb = boto3.resource('dynamodb')        # Connection pool: created once
table = dynamodb.Table(os.environ['TABLE_NAME'])

order_cache = {}                              # In-memory cache: survives across invocations
                                              # until the environment is recycled (~15min idle)

# INVOKE PHASE: handler() is called for every request
# A warm invocation takes 1-5ms (just the handler code)
def handler(event, context):
    order_id = event['pathParameters']['orderId']

    # Cache hit: no DynamoDB call
    if order_id in order_cache:
        return {
            'statusCode': 200,
            'body': json.dumps(order_cache[order_id]),
            'headers': {'X-Cache': 'HIT'}
        }

    # Cache miss: DynamoDB read
    response = table.get_item(Key={'order_id': order_id})
    item = response.get('Item')

    if not item:
        return {'statusCode': 404, 'body': '{"error": "not found"}'}

    order_cache[order_id] = item
    return {
        'statusCode': 200,
        'body': json.dumps(item, default=str),
        'headers': {'X-Cache': 'MISS'}
    }

# SHUTDOWN PHASE (optional): Lambda sends a SIGTERM ~2s before recycle
# Register a handler for graceful shutdown (flush buffers, close connections)
import signal

def shutdown_handler(signum, frame):
    # Flush any buffered logs, close DB connections, etc.
    pass

signal.signal(signal.SIGTERM, shutdown_handler)
```

## Cold starts — measuring and reducing them

```bash
# Measure cold start frequency and duration
aws logs filter-log-events \
  --log-group-name /aws/lambda/construx-order-handler \
  --filter-pattern "Init Duration" \
  --query 'events[*].message' \
  --output text

# Output: REPORT Init Duration: 842.32 ms Duration: 3.21 ms Billed Duration: 850 ms
# The Init Duration is the cold start — the handler itself was only 3ms

# Cold start causes:
# 1. First invocation to a function (no warm environments)
# 2. Scaling: burst of concurrent requests spins up new environments
# 3. Deployment: new version = new environments (old ones drain)
# 4. VPC functions: ENI attachment adds 1-10s to cold start

# Reduce cold start duration:
# 1. Choose the right runtime — Rust/Go have <5ms init; Python ~100ms; JVM ~500ms-2s
# 2. Minimize package size — smaller zip = faster download and init
# 3. Move init code to module level (not inside handler) — already in warm pool
# 4. Avoid VPC if you don't need it — VPC adds ENI attachment time

# Provisioned concurrency: pre-warms N execution environments
aws lambda put-provisioned-concurrency-config \
  --function-name construx-order-handler \
  --qualifier production        \  # Alias, not $LATEST
  --provisioned-concurrent-executions 10

# Now 10 environments are always warm — cold start for first 10 concurrent requests is 0ms
# Cost: you pay for provisioned concurrency even when idle (~$0.015/GB-hour)
```

## Lambda Power Tuning — find the optimal memory setting

```bash
# Lambda memory setting (128MB-10240MB) also controls proportional CPU allocation
# More memory = more CPU = faster execution = lower duration cost
# Optimal point: diminishing returns on CPU vs linear cost of memory

# Deploy the AWS Lambda Power Tuning tool (SAR application)
aws serverlessrepo create-cloud-formation-change-set \
  --application-id arn:aws:serverlessrepo:us-east-1:451282441545:applications/aws-lambda-power-tuning \
  --stack-name lambda-power-tuning \
  --capabilities CAPABILITY_IAM

# Run the state machine with your function
aws stepfunctions start-execution \
  --state-machine-arn arn:aws:states:us-east-1:123456789012:stateMachine:powerTuningStateMachine \
  --input '{
    "lambdaARN": "arn:aws:lambda:us-east-1:123456789012:function:construx-order-handler",
    "powerValues": [128, 256, 512, 1024, 1769, 3008],
    "num": 20,
    "payload": {"pathParameters": {"orderId": "order-a3f9"}},
    "parallelInvocation": true,
    "strategy": "cost"    # Optimise for cost vs "speed" for latency
  }'

# Results (typical for a I/O-bound Python function):
# Memory  | Avg Duration | Cost/1M invocations
# 128 MB  | 842 ms       | $1.75
# 256 MB  | 421 ms       | $1.75  ← same cost, 2x faster
# 512 MB  | 218 ms       | $1.81
# 1024 MB | 112 ms       | $1.87
# 1769 MB | 108 ms       | $3.11  ← full vCPU, no improvement (I/O bound)
#
# Optimal: 256 MB — half the duration, same cost as 128 MB
# (I/O-bound functions plateau early — extra CPU doesn't help)

# Apply the optimal setting
aws lambda update-function-configuration \
  --function-name construx-order-handler \
  --memory-size 256
```

Lambda vs ECS/Fargate: Lambda is cheaper and operationally simpler for sporadic, short-duration workloads — event-driven processing, API handlers with under 15 min max duration, webhook receivers. Fargate is better for long-running processes, sustained high traffic (warm Lambda concurrency gets expensive at scale), or workloads needing persistent connections. The pricing crossover point varies: at ~1M requests/month with under 200ms duration, Lambda is usually cheaper; at 10M requests/month with sustained load, a small Fargate task running continuously is often cheaper than the equivalent Lambda concurrency. Measure both.
