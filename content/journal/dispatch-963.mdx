title: "Cilium: eBPF-native networking, network policy, and observability for Kubernetes"
date: "2032-11-11"
excerpt: "Cilium is a Kubernetes CNI plugin that replaces iptables with eBPF programs loaded directly into the Linux kernel. Instead of the O(n) iptables rule chains that traditional CNIs generate, Cilium uses BPF maps (hash tables in kernel space) for O(1) policy lookups. Network policies in Cilium are L3/L4/L7-aware: you can allow traffic only to a specific HTTP path and method, not just a port. Hubble is Cilium's observability layer — it captures every network flow in the cluster and exposes them via a gRPC API, a CLI, and a UI. The combination eliminates the need for a service mesh for most observability and policy requirements while reducing latency by removing the iptables conntrack overhead."
author: "Lewis Wilson"

eBPF replaces iptables. L7 network policy. Hubble flow observability. Zero-overhead service identity.

## Installation and cluster connectivity

```bash
# Install Cilium CNI (helm)
helm repo add cilium https://helm.cilium.io/
helm install cilium cilium/cilium \
  --version 1.16.3 \
  --namespace kube-system \
  --set kubeProxyReplacement=true \
  --set k8sServiceHost=<API_SERVER_IP> \
  --set k8sServicePort=6443 \
  --set hubble.enabled=true \
  --set hubble.relay.enabled=true \
  --set hubble.ui.enabled=true

# Validate installation
cilium status
# ✅ Cilium:           OK
# ✅ Operator:         OK
# ✅ Hubble Relay:     OK
# ✅ ClusterMesh:      disabled
# KubeProxyReplacement: True (eBPF, no iptables)

# Connectivity test (end-to-end pod networking check)
cilium connectivity test
# ✅ [connectivity-check] 42/42 tests passed

# Check BPF programs loaded by Cilium
bpftool prog list | grep -i cilium | head -10
# 12: sched_cls  name handle_xgress  tag abc123  gpl
# 13: sched_cls  name cil_from_netdev  tag def456  gpl
```

## Network policy — L3/L4/L7

```yaml
# Standard Kubernetes NetworkPolicy: L3/L4 only
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-api-to-db
  namespace: construx-prod
spec:
  podSelector:
    matchLabels:
      app: postgres
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: api
      ports:
        - protocol: TCP
          port: 5432
---
# CiliumNetworkPolicy: L7-aware (HTTP, gRPC, Kafka)
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: api-http-policy
  namespace: construx-prod
spec:
  endpointSelector:
    matchLabels:
      app: orders-service
  ingress:
    - fromEndpoints:
        - matchLabels:
            app: api-gateway
      toPorts:
        - ports:
            - port: "8080"
              protocol: TCP
          rules:
            http:
              # Only allow GET /orders and POST /orders — block everything else
              - method: GET
                path: /orders.*
              - method: POST
                path: /orders
  egress:
    - toEndpoints:
        - matchLabels:
            app: postgres
      toPorts:
        - ports:
            - port: "5432"
              protocol: TCP
    # Allow DNS
    - toEndpoints:
        - matchLabels:
            k8s-app: kube-dns
      toPorts:
        - ports:
            - port: "53"
              protocol: UDP
          rules:
            dns:
              - matchPattern: "*.construx.internal"
```

## Hubble — flow observability

```bash
# Install Hubble CLI
cilium hubble enable
export HUBBLE_VERSION=1.16.3
curl -L "https://github.com/cilium/hubble/releases/download/v${HUBBLE_VERSION}/hubble-linux-amd64.tar.gz" | tar xz
mv hubble /usr/local/bin/

# Port-forward the Hubble relay
cilium hubble port-forward &

# Watch live network flows
hubble observe --follow

# Example output:
# Nov  8 09:00:01.234 construx-prod/api-7f9b → construx-prod/postgres-0:5432 postgres FORWARDED
# Nov  8 09:00:01.235 construx-prod/api-7f9b → construx-prod/redis-0:6379 tcp FORWARDED
# Nov  8 09:00:01.410 internet → construx-prod/api-7f9b:8080 http GET /orders FORWARDED
# Nov  8 09:00:01.412 construx-prod/scraper → construx-prod/orders-service:8080 http POST /admin DROP

# Filter by namespace, pod, or verdict
hubble observe \
  --namespace construx-prod \
  --verdict DROPPED \
  --follow

# Filter by L7 protocol and path
hubble observe \
  --http-method POST \
  --http-path /orders \
  --follow

# Flow statistics
hubble observe \
  --namespace construx-prod \
  --output json \
  | jq -r '.flow | select(.verdict == "DROPPED") | .source.workloads[0].name' \
  | sort | uniq -c | sort -rn
# 142 scraper
#  31 external-probe
#   7 legacy-cron

# Hubble UI (port-forward then open browser)
cilium hubble ui &
# Opens http://localhost:12000 — service dependency graph with flow counts
```

## Service map and policy visibility

```bash
# Show all endpoints Cilium manages
cilium endpoint list
# ENDPOINT  POLICY  IDENTITY  LABELS                          STATUS
# 1234      yes     12345     app=api,namespace=construx-prod ready
# 1235      yes     12346     app=postgres,namespace=...      ready

# Show BPF policy for an endpoint
cilium endpoint get 1234 | jq '.spec.policy'

# Inspect BPF maps (low-level: what eBPF actually enforces)
cilium bpf policy get 1234

# Trace policy decision for a specific flow (useful for debugging drops)
cilium policy trace \
  --src-endpoint 1234 \
  --dst-endpoint 1235 \
  --dport 5432
# ✅ ALLOW — matched rule: ingress from app=api to port 5432

# Monitor BPF events in real time (packet-level)
cilium monitor \
  --type drop \
  --from-source construx-prod/scraper
# xx drop (Policy denied) flow 0x12345678: scraper → orders-service:8080 tcp SYN

# ClusterMesh: connect multiple clusters (cross-cluster service discovery)
cilium clustermesh enable \
  --service-type LoadBalancer
cilium clustermesh connect \
  --destination-context k8s-cluster-eu
# Enables cross-cluster service discovery and network policy
```

## Replacing kube-proxy with eBPF

```bash
# Cilium's kube-proxy replacement uses BPF maps instead of iptables NAT rules
# Traditional kube-proxy: O(n) iptables chain walk for n services
# Cilium eBPF:            O(1) BPF map lookup regardless of service count

# Verify kube-proxy is replaced
cilium status | grep KubeProxy
# KubeProxyReplacement: True (socket-based LB, DSR, eBPF NodePort)

# DSR (Direct Server Return): for NodePort traffic, response goes directly
# from the backend pod to the client — bypasses the node that received the request
# --set loadBalancer.mode=dsr

# Maglev consistent hashing: consistent backend assignment for flows
# (same 5-tuple always goes to same backend — improves connection affinity)
# --set loadBalancer.algorithm=maglev

# Check BPF LB table
cilium bpf lb list | head -20
# SERVICE ADDRESS           BACKEND ADDRESS        STATUS
# 10.96.0.1:443             10.0.1.5:6443          active
# 10.96.100.10:80           10.0.2.10:8080         active
# 10.96.100.10:80           10.0.2.11:8080         active

# XDP acceleration: process packets at the NIC driver level (before the kernel)
# Requires driver support (Intel i40e, Mellanox mlx5, etc.)
# --set loadBalancer.acceleration=native
```

Cilium vs Calico vs Flannel: Flannel is a simple VXLAN overlay — it handles pod networking but no policy. Calico is iptables-based L3/L4 policy with BGP routing, solid and widely deployed. Cilium uses eBPF to implement everything in the kernel without iptables — the result is L7 policy enforcement (HTTP, gRPC, Kafka), O(1) service load balancing, and flow-level observability with Hubble, all without a sidecar proxy. The cost: Cilium requires a recent kernel (5.10+ for full features) and is more complex to debug. The value: for clusters where you'd otherwise run a service mesh for observability and policy, Cilium often eliminates that requirement entirely and reduces per-connection latency by removing the iptables conntrack path.
