excerpt: "Falco is a cloud-native runtime security tool that detects unexpected behaviour in containers and Kubernetes at runtime. It works by intercepting Linux system calls via an eBPF probe (or a kernel module) — every syscall made by any process on the node passes through Falco's rule engine. Falco rules define what behaviour is unexpected: a shell spawned inside a container, a write to a sensitive path (/etc, /proc), a container trying to read /etc/shadow, a process making a network connection that wasn't expected, a container running with --privileged making a sensitive syscall. When a rule matches, Falco generates an alert with full context: the container name, pod name, namespace, process name, parent process, syscall arguments. Falco ships with a large library of default rules covering common attack vectors (container escapes, credential theft, lateral movement). Custom rules cover application-specific security requirements. Falco alert outputs can route to stdout, file, syslog, gRPC, webhook, or Falcosidekick (which fans out to Slack, PagerDuty, Elasticsearch, Loki, or dozens of other destinations). At Construx, Falco provides the real-time alert layer on top of static scanning (Trivy, Grype for image CVEs, OPA/Kyverno for policy) — it detects active exploitation attempts that bypass static controls."

## Falco rules and custom policy

```yaml
# Falco rules: default + custom rules for construx security policy
# /etc/falco/construx_rules.yaml

# Custom list: approved shells in containers
- list: allowed_shells
  items: [bash, sh, ash, dash]

# Custom macro: reusable conditions
- macro: container_entrypoint
  condition: >
    (proc.vpid = 1 and container)

- macro: spawned_process
  condition: >
    (evt.type = execve and evt.dir = <)

- macro: sensitive_dir
  condition: >
    (fd.name startswith /etc or
     fd.name startswith /root or
     fd.name startswith /proc/1)

# Rule: alert on any shell spawned in a production container
# (indicates someone exec'd into a pod — should be audited)
- rule: Shell Spawned in Container
  desc: A shell was spawned inside a production container
  condition: >
    spawned_process and
    container and
    container.image.repository != "construx/debug-toolkit" and
    proc.name in (allowed_shells) and
    not container_entrypoint
  output: >
    Shell spawned (pod=%k8s.pod.name ns=%k8s.ns.name image=%container.image.repository
    cmd=%proc.cmdline user=%user.name)
  priority: WARNING
  tags: [container, shell, construx]

# Rule: write to /etc in a running container (potential container escape)
- rule: Write to Sensitive Directory
  desc: A container wrote to a sensitive host path
  condition: >
    open_write and
    container and
    sensitive_dir and
    not proc.name in (construx_allowed_writers)
  output: >
    File written in sensitive dir (pod=%k8s.pod.name file=%fd.name
    proc=%proc.name image=%container.image.repository)
  priority: CRITICAL
  tags: [container, filesystem, construx]

# Rule: unexpected outbound connection from database pod
# Database pods should only accept inbound, not initiate outbound
- rule: Database Pod Outbound Connection
  desc: A database pod initiated an unexpected outbound network connection
  condition: >
    evt.type = connect and
    evt.dir = < and
    container and
    k8s.deployment.name in (postgres, clickhouse, redis) and
    not fd.sip in (allowed_db_egress_ips)
  output: >
    Database pod outbound connection (pod=%k8s.pod.name dest=%fd.rip:%fd.rport
    proc=%proc.name)
  priority: HIGH
  tags: [network, database, construx]

# Rule: detect crypto mining (high CPU + network to known mining pools)
- rule: Cryptocurrency Mining Process
  desc: A known cryptocurrency miner binary was executed
  condition: >
    spawned_process and
    proc.name in (xmrig, minergate, cryptonight, minerd, cpuminer)
  output: >
    Crypto miner detected (pod=%k8s.pod.name proc=%proc.cmdline
    image=%container.image.repository)
  priority: CRITICAL
  tags: [cryptomining, malware, construx]
```

Falco vs AppArmor/seccomp vs Tetragon vs Sysdig vs traditional SIEM: AppArmor and seccomp are Linux kernel security mechanisms — they restrict what syscalls and capabilities a container can use, acting as preventative controls. If a process tries a blocked syscall, the kernel denies it without generating a Falco-visible event (unless AppArmor is configured to audit). AppArmor/seccomp complement Falco — preventative restriction reduces attack surface; Falco detects what gets through. Tetragon (from Cilium) also uses eBPF to intercept syscalls and process lifecycle events, with the ability to enforce (kill processes) rather than just alert — it is more powerful than Falco for enforcement but has a smaller rule library and is less mature for complex policy. Traditional SIEM solutions (Splunk, QRadar, Azure Sentinel) ingest logs and alerts but don't have the real-time process-level visibility that eBPF provides. Sysdig is the commercial product that Falco originated from — Falco is its open-source engine. For Kubernetes runtime security where you want real-time alerts on unexpected behaviour (not just static policy checks that run at admission time), Falco provides the best combination of coverage, performance, and ecosystem integration.
