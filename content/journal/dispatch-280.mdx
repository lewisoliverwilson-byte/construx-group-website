The default choice for "real-time" is WebSockets, but WebSockets are bidirectional by design. When you only need the server to push updates to the client — live notifications, feed updates, streaming AI responses — you're paying the overhead of a full-duplex connection for something that only needs simplex.

Server-Sent Events (SSE) exist for this use case. They're HTTP, they work through standard proxies, they reconnect automatically, and they require far less infrastructure.

## Server-Sent Events: the underused primitive

SSE is a browser native API over HTTP. The server sends a stream of text/event-stream events; the client receives them through an `EventSource`:

```ts
// app/api/notifications/stream/route.ts
export const runtime = 'nodejs';  // required for streaming

export async function GET(req: Request) {
  const session = await getSession();
  if (!session) return new Response('Unauthorized', { status: 401 });

  const encoder = new TextEncoder();

  const stream = new ReadableStream({
    async start(controller) {
      const send = (event: string, data: unknown) => {
        controller.enqueue(
          encoder.encode(`event: ${event}\ndata: ${JSON.stringify(data)}\n\n`)
        );
      };

      // Send an initial connected event
      send('connected', { userId: session.userId });

      // Subscribe to notifications for this user
      const unsubscribe = notificationBus.subscribe(session.userId, (notification) => {
        send('notification', notification);
      });

      // Clean up when the connection closes
      req.signal.addEventListener('abort', () => {
        unsubscribe();
        controller.close();
      });
    },
  });

  return new Response(stream, {
    headers: {
      'Content-Type': 'text/event-stream',
      'Cache-Control': 'no-cache',
      'Connection': 'keep-alive',
    },
  });
}
```

```ts
// Client: EventSource with automatic reconnection
function useNotifications(userId: string) {
  useEffect(() => {
    const es = new EventSource('/api/notifications/stream');

    es.addEventListener('notification', (e) => {
      const notification = JSON.parse(e.data);
      // handle the notification
    });

    es.addEventListener('error', () => {
      // EventSource reconnects automatically after a delay
      // This fires on connection loss, not necessarily a fatal error
    });

    return () => es.close();
  }, [userId]);
}
```

The browser reconnects SSE automatically. No client-side reconnection logic required.

## When SSE works and when it doesn't

SSE is the right choice when:
- The data flow is one-directional: server → client
- Events are relatively infrequent (not high-frequency tick data)
- You want built-in reconnection without client-side implementation
- Your infrastructure runs through HTTP/2 (SSE multiplexes over a single connection)

SSE doesn't work when:
- You need the client to send data beyond HTTP requests (bidirectional messaging)
- You need binary data (SSE is text-only)
- The server cannot hold open connections (some serverless environments)

## Streaming AI responses with SSE

SSE is the natural format for streaming AI responses — the model generates tokens incrementally, and you want to display them as they arrive:

```ts
// app/api/ai/stream/route.ts
import Anthropic from '@anthropic-ai/sdk';

const client = new Anthropic();

export async function POST(req: Request) {
  const { prompt, systemPrompt } = await req.json();

  const encoder = new TextEncoder();

  const stream = new ReadableStream({
    async start(controller) {
      const send = (event: string, data: unknown) => {
        controller.enqueue(
          encoder.encode(`event: ${event}\ndata: ${JSON.stringify(data)}\n\n`)
        );
      };

      const claudeStream = client.messages.stream({
        model: 'claude-sonnet-4-6',
        max_tokens: 1024,
        system: systemPrompt,
        messages: [{ role: 'user', content: prompt }],
      });

      for await (const event of claudeStream) {
        if (event.type === 'content_block_delta' && event.delta.type === 'text_delta') {
          send('token', { text: event.delta.text });
        }
        if (event.type === 'message_stop') {
          send('done', {});
          controller.close();
        }
      }
    },
  });

  return new Response(stream, {
    headers: {
      'Content-Type': 'text/event-stream',
      'Cache-Control': 'no-cache',
    },
  });
}
```

## WebSockets: when you actually need them

WebSockets are right when the client needs to send data over the same persistent connection — chat, collaborative editing, multiplayer, realtime presence.

For The Hyve, we use WebSockets because the client sends typing indicators, message drafts, and read receipts over the same connection it receives messages on:

```ts
// server/ws.ts (Node.js WebSocket server, hosted on Railway)
import { WebSocketServer, WebSocket } from 'ws';

const wss = new WebSocketServer({ port: 3001 });

const workspaceConnections = new Map<string, Set<WebSocket>>();

wss.on('connection', (ws, req) => {
  const workspaceId = extractWorkspaceId(req);

  // Register connection
  if (!workspaceConnections.has(workspaceId)) {
    workspaceConnections.set(workspaceId, new Set());
  }
  workspaceConnections.get(workspaceId)!.add(ws);

  ws.on('message', (data) => {
    const msg = JSON.parse(String(data));

    if (msg.type === 'message.send') {
      // Broadcast to all connections in the same workspace
      const conns = workspaceConnections.get(workspaceId);
      conns?.forEach((conn) => {
        if (conn !== ws && conn.readyState === WebSocket.OPEN) {
          conn.send(JSON.stringify({ type: 'message.new', payload: msg.payload }));
        }
      });
    }

    if (msg.type === 'typing.start') {
      // Broadcast typing indicator — ephemeral, no persistence
      const conns = workspaceConnections.get(workspaceId);
      conns?.forEach((conn) => {
        if (conn !== ws && conn.readyState === WebSocket.OPEN) {
          conn.send(JSON.stringify({ type: 'typing', userId: msg.userId }));
        }
      });
    }
  });

  ws.on('close', () => {
    workspaceConnections.get(workspaceId)?.delete(ws);
  });
});
```

WebSockets require stateful server processes. They can't run on standard serverless functions — the connection needs to persist. For The Hyve's WebSocket server, we use Railway (persistent Node.js process) rather than Amplify (serverless functions).

## The architecture decision

If the data flows one way and it's text — SSE.
If it's bidirectional or binary — WebSocket.
If it's occasional push events (like notifications) and you don't need a persistent connection — HTTP polling with a 5-30s interval is often more robust and easier to operate than either.

The simplest solution that works is usually the right one.
