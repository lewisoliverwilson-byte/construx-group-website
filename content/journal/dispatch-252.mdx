Zod is the validation layer that sits between the outside world and our application code. Every API route, every form submission, every webhook payload goes through a Zod schema before we touch it.

After using it across three products with different API shapes, some patterns have become standard.

## The colocate-or-share question

Should schemas live next to the routes that use them, or in a shared `lib/schemas.ts`?

Both. We use two tiers:

**Shared schemas** for types that cross multiple contexts. The `UserSchema` is the same whether you're in an API route, a server component, or a client form. These live in `lib/schemas/`:

```ts
// lib/schemas/user.ts
export const UserSchema = z.object({
  id: z.string().uuid(),
  email: z.string().email(),
  name: z.string().min(1).max(100),
  role: z.enum(['admin', 'member', 'guest']),
  createdAt: z.coerce.date(),
});

export type User = z.infer<typeof UserSchema>;
```

**Route-local schemas** for one-off request bodies. The `CreateListingBody` schema is only used in `POST /api/listings` — it lives in that file:

```ts
// app/api/listings/route.ts
const CreateListingBodySchema = z.object({
  title: z.string().min(2).max(120),
  price: z.number().positive().multipleOf(0.01),
  category: z.enum(['electronics', 'fashion', 'home', 'toys']),
  images: z.array(z.string().url()).min(1).max(8),
  description: z.string().max(2000).optional(),
});
```

Keeping these local means you can change the endpoint's interface without touching shared code.

## The parse-don't-validate pattern

Zod's `safeParse` returns `{ success: boolean, data?: T, error?: ZodError }`. We almost never call `parse` directly (which throws on failure). The `safeParse` pattern gives you explicit error handling:

```ts
export async function POST(req: Request) {
  const body = await req.json();
  const result = CreateListingBodySchema.safeParse(body);

  if (!result.success) {
    return Response.json(
      { error: 'Invalid request', issues: result.error.flatten().fieldErrors },
      { status: 400 }
    );
  }

  const { title, price, category, images, description } = result.data;
  // From here, everything is typed and validated
}
```

`result.error.flatten().fieldErrors` gives a `{ fieldName: string[] }` structure that maps directly to form error display. The client gets actionable error messages without custom serialisation.

## Transforming on parse

Zod schemas aren't just validators — they're transformers. We use this to normalise data at the boundary:

```ts
const SearchQuerySchema = z.object({
  q: z.string().trim().min(1),
  page: z.coerce.number().int().positive().default(1),
  limit: z.coerce.number().int().min(1).max(100).default(20),
  tag: z.string().optional().transform((v) => v?.toLowerCase()),
});
```

- `z.string().trim()` removes leading/trailing whitespace from the search query — the caller shouldn't have to clean this
- `z.coerce.number()` converts `"42"` (string from URL params) to `42` (number) — URL params are always strings
- `.default(1)` means missing `page` param becomes `1`, not `undefined`
- `.transform((v) => v?.toLowerCase())` normalises the tag to lowercase before it hits the database

The data that comes out of `safeParse` is already in the shape the rest of the code expects. No additional normalisation step.

## Nested objects and discriminated unions

Scoutr's scan result schema uses a discriminated union because successful and error responses have different shapes:

```ts
const ScanResultSchema = z.discriminatedUnion('status', [
  z.object({
    status: z.literal('success'),
    asin: z.string().length(10),
    title: z.string(),
    buyPrice: z.number().positive(),
    sellPrice: z.number().positive(),
    margin: z.number(),
    confidence: z.enum(['STRONG', 'GOOD', 'MODERATE', 'LOW']),
    freshAt: z.coerce.date(),
  }),
  z.object({
    status: z.literal('error'),
    code: z.enum(['ASIN_NOT_FOUND', 'NO_DATA', 'RATE_LIMITED', 'INVALID_URL']),
    message: z.string(),
  }),
]);
```

`discriminatedUnion` requires a literal discriminant field (`status`). TypeScript narrows the type correctly after a status check:

```ts
const result = ScanResultSchema.parse(data);

if (result.status === 'success') {
  console.log(result.margin); // TypeScript knows this exists
}
// result.margin would be a type error outside the branch
```

Without discriminated union, you'd need `if ('margin' in result)` checks, which are less readable.

## Webhook validation

Clerk, Stripe, and other webhooks arrive as arbitrary JSON. We validate their shape before processing:

```ts
const ClerkUserCreatedSchema = z.object({
  type: z.literal('user.created'),
  data: z.object({
    id: z.string(),
    email_addresses: z.array(z.object({
      email_address: z.string().email(),
      id: z.string(),
    })).min(1),
    first_name: z.string().nullable(),
    last_name: z.string().nullable(),
    image_url: z.string().url().optional(),
  }),
});
```

If Clerk changes their webhook payload format, the schema fails immediately and the error is caught by our logging — rather than silently processing malformed data.

## Schema versioning

The Marqet's public API (used by partner integrations) needs schema stability. We version schemas explicitly:

```ts
// lib/schemas/api/v1/listing.ts — stable, never break
export const ListingV1Schema = z.object({ ... });

// lib/schemas/api/v2/listing.ts — extends v1 with new fields
export const ListingV2Schema = ListingV1Schema.extend({
  variants: z.array(VariantSchema).optional(),
});
```

Internal schemas evolve freely. Public API schemas only get additive changes within a version.

## What Zod doesn't give you

Zod validates shape and type. It doesn't validate:

- Business rules: "this discount must be less than the current price" — that's application code
- Cross-field constraints that require database lookups: "this username must be unique" — that's a database constraint
- File contents: Zod can validate that a field is a string with `contentType: image/jpeg`, but not that the file actually is a JPEG

For business rules we write explicit checks after `safeParse`. For database uniqueness we rely on `UNIQUE` constraints and catch the specific Postgres error code. For file validation we do server-side magic number checking after the upload confirms.

Zod is the first gate. It's not the only gate.
