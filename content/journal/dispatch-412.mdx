Every schema change is a migration. Every migration has to run on live data. The question is whether you do it thoughtfully or by accident.

## The Drizzle migration workflow

```bash
# 1. Edit your schema
# 2. Generate migration SQL
npx drizzle-kit generate

# 3. Review the generated SQL (always)
# 4. Apply to dev
npx drizzle-kit migrate

# 5. Apply to production (CI/CD step)
```

```ts
// drizzle.config.ts
import { defineConfig } from 'drizzle-kit';

export default defineConfig({
  schema: './db/schema.ts',
  out: './db/migrations',
  dialect: 'postgresql',
  dbCredentials: {
    url: process.env.DATABASE_URL!,
  },
  verbose: true,
  strict: true,  // fail if migration would cause data loss
});
```

## Migration files

Generated migrations live in `db/migrations/`. Each is a `.sql` file with a timestamp prefix:

```
db/migrations/
  0001_initial_schema.sql
  0002_add_users_role.sql
  0003_add_posts_published_at.sql
  meta/
    _journal.json  # tracks which migrations have run
```

Never edit a migration that has already run in production. Create a new one instead.

## Running migrations programmatically

```ts
// lib/migrate.ts — run at app startup or in a deploy step
import { drizzle } from 'drizzle-orm/postgres-js';
import { migrate } from 'drizzle-orm/postgres-js/migrator';
import postgres from 'postgres';

export async function runMigrations() {
  const sql = postgres(process.env.DATABASE_URL!, { max: 1 });
  const db = drizzle(sql);

  await migrate(db, { migrationsFolder: './db/migrations' });
  await sql.end();
}
```

```ts
// scripts/migrate.ts — called in CI before deploying
import { runMigrations } from '@/lib/migrate';

await runMigrations();
console.log('Migrations complete');
process.exit(0);
```

In your CI/CD pipeline:
```yaml
- name: Run migrations
  run: npx tsx scripts/migrate.ts
  env:
    DATABASE_URL: ${{ secrets.DATABASE_URL }}

- name: Deploy app
  run: # deploy command
```

Migrations before deploy — always.

## Zero-downtime column additions

Adding a nullable column is safe. Adding a NOT NULL column without a default is not — the query will fail for any existing rows:

```ts
// Safe — nullable with default
export const posts = pgTable('posts', {
  // ...existing columns
  viewCount: integer('view_count').notNull().default(0),  // safe: has default
  publishedAt: timestamp('published_at'),  // safe: nullable
  archivedAt: timestamp('archived_at'),    // safe: nullable
});
```

For a NOT NULL column on an existing table with data:

```sql
-- Step 1: Add as nullable
ALTER TABLE posts ADD COLUMN slug TEXT;

-- Step 2: Backfill (can run while app is live)
UPDATE posts SET slug = regexp_replace(lower(title), '\W+', '-', 'g')
WHERE slug IS NULL;

-- Step 3: Add NOT NULL constraint (after backfill is complete)
ALTER TABLE posts ALTER COLUMN slug SET NOT NULL;

-- Step 4: Add unique index
CREATE UNIQUE INDEX CONCURRENTLY idx_posts_slug ON posts (slug);
```

`CONCURRENTLY` is critical — it builds the index without locking the table.

## Column renames

Drizzle detects renames as drop+add, which loses data:

```bash
# Drizzle will generate:
ALTER TABLE posts DROP COLUMN body;
ALTER TABLE posts ADD COLUMN content TEXT;
# ⚠️ This deletes your data
```

Do this manually instead:

```sql
-- Migration: rename body to content
ALTER TABLE posts RENAME COLUMN body TO content;
```

Then update the Drizzle schema to match:

```ts
export const posts = pgTable('posts', {
  content: text('content').notNull(),  // was 'body'
});
```

## Backfills

Large backfills (millions of rows) should run in batches to avoid locking:

```ts
// scripts/backfill-slugs.ts
import { db } from '@/lib/db';
import { posts } from '@/db/schema';
import { isNull, sql } from 'drizzle-orm';

const BATCH_SIZE = 500;
let processed = 0;

while (true) {
  const batch = await db
    .select({ id: posts.id, title: posts.title })
    .from(posts)
    .where(isNull(posts.slug))
    .limit(BATCH_SIZE);

  if (batch.length === 0) break;

  for (const post of batch) {
    const slug = post.title.toLowerCase().replace(/\W+/g, '-');
    await db.update(posts)
      .set({ slug })
      .where(sql`${posts.id} = ${post.id}`);
  }

  processed += batch.length;
  console.log(`Processed ${processed} rows`);

  // Small delay to avoid overwhelming the DB
  await new Promise((r) => setTimeout(r, 50));
}

console.log(`Done: ${processed} rows backfilled`);
```

Run this as a one-off script, not inside a migration. It can be interrupted and resumed.

## Rollbacks

Drizzle doesn't have automatic rollback. The safe approach: write down migrations and keep the ability to run a reverse migration manually.

```sql
-- 0003_add_posts_published_at.sql (up)
ALTER TABLE posts ADD COLUMN published_at TIMESTAMP;

-- 0003_add_posts_published_at.down.sql (down, manual)
ALTER TABLE posts DROP COLUMN published_at;
```

For genuinely irreversible migrations (data deletions, constraint drops), make that explicit: test in staging, have a database backup before applying to production.

The pattern: generate, review, run migrations before deploy. Batch backfills separately. Never drop or rename a column in a single step — always add first, migrate data, then remove.
