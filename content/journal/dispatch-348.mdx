Serverless functions have a hard wall on execution time. Everything that might hit that wall — sending ten emails, generating a PDF, running an AI pipeline on user-uploaded content, processing a batch import — needs to move off the request path.

The pattern: accept the request immediately, enqueue the work, return `202 Accepted`, process asynchronously.

## Trigger.dev: background jobs in TypeScript

Trigger.dev lets you write background jobs in TypeScript that run outside the serverless function lifecycle. Jobs have automatic retries, real-time progress, and a dashboard for monitoring.

```bash
npm install @trigger.dev/sdk
npx trigger.dev@latest init
```

### Define a job

```ts
// trigger/jobs/send-welcome-email.ts
import { client } from '@/trigger';
import { eventTrigger } from '@trigger.dev/sdk';
import { z } from 'zod';
import { sendEmail } from '@/lib/email';

client.defineJob({
  id: 'send-welcome-email',
  name: 'Send Welcome Email',
  version: '1.0.0',
  trigger: eventTrigger({
    name: 'user.created',
    schema: z.object({
      userId: z.string(),
      email: z.string().email(),
      name: z.string(),
    }),
  }),
  run: async (payload, io, ctx) => {
    await io.logger.info('Sending welcome email', { userId: payload.userId });

    await io.runTask('send-email', async () => {
      await sendEmail({
        to: payload.email,
        subject: 'Welcome to Construx',
        template: 'welcome',
        variables: { name: payload.name },
      });
    });

    await io.logger.info('Welcome email sent');
  },
});
```

### Trigger from a route handler

```ts
// app/api/users/route.ts
import { client } from '@/trigger';

export async function POST(req: Request) {
  const { email, name } = await req.json();

  const user = await db.insert(users).values({ email, name }).returning();

  // Fire and forget — returns immediately
  await client.sendEvent({
    name: 'user.created',
    payload: {
      userId: user[0].id,
      email,
      name,
    },
  });

  return Response.json({ user: user[0] }, { status: 201 });
}
```

The API route returns before the email sends. Trigger.dev handles retries, logging, and failure alerting.

## Inngest: event-driven functions

Inngest is similar to Trigger.dev but uses a different model — functions subscribe to events and can be deployed anywhere without a separate queue infrastructure.

```bash
npm install inngest
```

```ts
// inngest/client.ts
import { Inngest } from 'inngest';
export const inngest = new Inngest({ id: 'construx-group' });
```

```ts
// inngest/functions/process-upload.ts
import { inngest } from '../client';

export const processUpload = inngest.createFunction(
  { id: 'process-upload', retries: 3 },
  { event: 'upload/completed' },
  async ({ event, step }) => {
    const { fileUrl, userId } = event.data;

    // step.run() wraps work in retryable units
    const analysis = await step.run('analyze-content', async () => {
      return await analyzeWithAI(fileUrl);
    });

    await step.run('save-results', async () => {
      await db.update(uploads)
        .set({ analysis, status: 'complete' })
        .where(eq(uploads.fileUrl, fileUrl));
    });

    await step.run('notify-user', async () => {
      await sendNotification(userId, 'Your file has been processed');
    });
  },
);
```

Each `step.run()` is independently retried. If the AI call succeeds but saving fails, only the save step retries — the AI call doesn't re-run.

## Scheduled tasks with Vercel Cron

For recurring work — daily reports, weekly digests, cleanup jobs — Vercel Cron triggers an API route on a schedule:

```json
// vercel.json
{
  "crons": [
    {
      "path": "/api/cron/daily-digest",
      "schedule": "0 8 * * *"
    },
    {
      "path": "/api/cron/cleanup-expired-sessions",
      "schedule": "0 * * * *"
    }
  ]
}
```

```ts
// app/api/cron/daily-digest/route.ts
export async function GET(req: Request) {
  // Verify the request comes from Vercel Cron
  const authHeader = req.headers.get('authorization');
  if (authHeader !== `Bearer ${process.env.CRON_SECRET}`) {
    return Response.json({ error: 'Unauthorized' }, { status: 401 });
  }

  // Enqueue the actual work (don't do it in the cron handler)
  await client.sendEvent({ name: 'digest.send', payload: { date: new Date().toISOString() } });

  return Response.json({ ok: true });
}
```

The cron handler enqueues work rather than doing it inline — the cron itself just needs to return before timing out.

## QStash: HTTP-based queue

For simple queue needs without a full background job service, Upstash QStash sends HTTP requests to your API routes on a delay or schedule:

```ts
import { Client } from '@upstash/qstash';

const qstash = new Client({ token: process.env.QSTASH_TOKEN! });

// Queue a message to be processed in 5 minutes
await qstash.publishJSON({
  url: 'https://construxgroup.io/api/jobs/process-upload',
  body: { fileId: 'file_123', userId: 'user_456' },
  delay: 300,  // seconds
  retries: 3,
});
```

QStash delivers the message via HTTP POST and retries on failure. No infrastructure to run, no worker process to maintain.

## Choosing between them

- **Trigger.dev**: full observability, TypeScript-native, great for complex multi-step jobs with branching
- **Inngest**: event-driven, step functions, good for workflows where steps have dependencies
- **Vercel Cron**: schedule only, no queue, for simple recurring tasks
- **QStash**: HTTP-based queue, great for simple delay/retry without a background job service

All four work with Vercel and Amplify deployments. The deciding factor is usually how much visibility you need into job execution — Trigger.dev and Inngest both have dashboards; QStash and Vercel Cron are more opaque.

For most projects: start with Vercel Cron for scheduled work and QStash for deferred jobs. Graduate to Trigger.dev or Inngest when you need step functions, retry observability, or complex workflows.
