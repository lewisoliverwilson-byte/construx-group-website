excerpt: "Apache Flink is a distributed stateful stream processing framework. Unlike Spark Streaming (micro-batch) or Kafka Streams (single JVM), Flink processes data as a true continuous stream with per-event processing semantics. The key abstractions are: DataStream (a potentially infinite stream of typed records), Operators (map, filter, keyBy, window, join — applied to streams), State (per-key state stored in RocksDB, fault-tolerant via checkpoints), and Watermarks (monotonically increasing timestamps that track progress through event time, enabling late-data handling). Flink's Table API provides a SQL-like abstraction over streams and bounded datasets — unified batch and stream processing with the same SQL syntax. Flink checkpointing is the fault-tolerance mechanism: the Flink coordinator periodically injects checkpoint barriers into all input streams; when a barrier passes through all operators, each operator snapshots its state to object storage (S3). On recovery from a node failure, Flink restores from the last completed checkpoint and replays the input stream from that offset. At Construx, Flink processes the real-time product event stream: enriching raw events with product metadata (joining stream with a slowly-changing database snapshot), computing 5-minute sliding window aggregations for the live dashboard, and detecting anomalous purchase patterns for fraud scoring."

## DataStream API: event enrichment and windowed aggregation

```java
// Flink DataStream API: enrich product events and compute sliding window metrics
// Deployed on Flink Kubernetes Operator (flink-kubernetes-operator)

StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();
env.setParallelism(8);

// Checkpoint configuration: fault tolerance
env.enableCheckpointing(60_000L);   // checkpoint every 60 seconds
env.getCheckpointConfig().setCheckpointStorage("s3://construx-flink-checkpoints/prod/");
env.getCheckpointConfig().setTolerableCheckpointFailureNumber(3);

// Kafka source: product events
KafkaSource<ProductEvent> kafkaSource = KafkaSource.<ProductEvent>builder()
    .setBootstrapServers("kafka.construx-infra.svc.cluster.local:9092")
    .setTopics("construx.product-events")
    .setGroupId("flink-product-enrichment")
    .setStartingOffsets(OffsetsInitializer.committedOffsets(OffsetResetStrategy.LATEST))
    .setValueOnlyDeserializer(new ProductEventDeserializer())
    .build();

DataStreamSource<ProductEvent> rawEvents = env.fromSource(
    kafkaSource,
    WatermarkStrategy.<ProductEvent>forBoundedOutOfOrderness(Duration.ofSeconds(10))
        .withTimestampAssigner((event, ts) -> event.getTimestampMs()),
    "kafka-product-events"
);

// Async enrichment: join with product catalog (RocksDB state or async I/O)
SingleOutputStreamOperator<EnrichedEvent> enriched = AsyncDataStream
    .unorderedWait(
        rawEvents,
        new ProductCatalogEnricher(redisClient),   // async Redis lookup
        5, TimeUnit.SECONDS,
        100   // max async requests in flight
    );

// KeyBy tenant → sliding window → aggregate
DataStream<TenantMetrics> metrics = enriched
    .keyBy(EnrichedEvent::getTenantId)
    .window(SlidingEventTimeWindows.of(
        Time.minutes(5),    // window size
        Time.minutes(1)     // slide interval — new result every minute
    ))
    .aggregate(new TenantMetricsAggregator());

// Kafka sink: publish aggregated metrics to downstream dashboard topic
KafkaSink<TenantMetrics> kafkaSink = KafkaSink.<TenantMetrics>builder()
    .setBootstrapServers("kafka.construx-infra.svc.cluster.local:9092")
    .setRecordSerializer(KafkaRecordSerializationSchema.builder()
        .setTopic("construx.tenant-metrics")
        .setValueSerializationSchema(new TenantMetricsSerializer())
        .build()
    )
    .setDeliveryGuarantee(DeliveryGuarantee.AT_LEAST_ONCE)
    .build();

metrics.sinkTo(kafkaSink);
env.execute("construx-product-event-enrichment");
```

Flink vs Kafka Streams vs Spark Streaming vs Storm vs Beam: Kafka Streams is a library (not a separate cluster) that runs inside your application JVM — perfect for simple per-event transformations and stateful aggregations where the input and output are Kafka topics, and you don't want a separate processing cluster. Spark Streaming processes data in micro-batches — the batch size is the minimum latency, typically 200ms-5s — it is not a true stream processor. Apache Storm is a legacy stream processing system — superseded by Flink for most use cases. Apache Beam is an abstraction layer over multiple execution engines (Flink, Spark, Dataflow) — useful for code portability across processing backends. Flink's advantage is its combination of true event-time processing (watermarks handle late-arriving events correctly), exactly-once state management (checkpoint-based, not relying on idempotent sinks), and the unified batch+stream API (the same DataStream or Table API code runs over bounded historical data or an unbounded stream). For complex event-time operations (windowed joins across two streams, session windows, late data handling) and large stateful applications (petabytes of RocksDB state per operator), Flink is the production choice.
