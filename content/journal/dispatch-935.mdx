excerpt: "htop is the classic interactive process monitor — a colorful ncurses interface over /proc that shows per-CPU bar graphs, memory/swap usage, and a sortable process tree with mouse support. btop is the modern successor: a richer TUI with GPU support, per-process network I/O, a collapsible process tree, and configurable color themes. Both run without root; both are read-only views into the kernel's process accounting data. The key metrics: %CPU (user + sys time over the last sample interval), %MEM (RSS as a fraction of total RAM), VIRT (virtual address space including shared libs and mmap'd files — nearly always larger than RES), and RES (resident set size — pages currently in RAM). Combine with pidstat for disk I/O and perf stat for hardware counters."

Sort by CPU. Watch the top process. Press `t` for tree view. `F5` to refresh.

## htop — interactive process inspector

```bash
# htop: interactive, colorful, sortable — reads /proc for everything
htop

# Key bindings:
# F2         → setup (columns, colors, meters)
# F3 / /     → search by process name
# F4         → filter (show only matching processes)
# F5         → tree view (parent/child relationships)
# F6         → sort column (CPU%, MEM%, PID, TIME+, etc.)
# F9 / k     → send signal to selected process
# F10 / q    → quit
# Space      → tag process (for bulk signal)
# u          → filter by user
# H          → hide user threads
# K          → hide kernel threads

# Non-interactive: output snapshot (useful in scripts)
htop --no-color -d 10 --sort-key PERCENT_CPU | head -20

# What the columns mean:
# PID        process ID (assigned by kernel at fork)
# USER       owner (effective UID)
# PRI / NI  priority / nice value (-20 = high priority, 19 = low)
# VIRT       virtual memory = code + data + shared libs + mmap = always large
# RES        resident set size = pages actually in RAM right now
# SHR        shared memory (shared libs, mmap'd files shared between processes)
# S          state: R=running, S=sleeping, D=uninterruptible I/O, Z=zombie
# CPU%       user+sys CPU time since last sample (can exceed 100% with multiple cores)
# MEM%       RES / total RAM
# TIME+      total CPU time consumed since process start
# Command    argv[0] — or full command line with F2 → Display → Show full paths
```

## btop — modern TUI process monitor

```bash
# btop: successor to bashtop and bpytop — written in C++, zero dependencies
btop

# Key bindings:
# q          → quit
# ESC / m    → menu
# F2 / o    → options
# 1-9        → select CPU, MEM, NET, PROC, or GPU panels
# p          → sort order (CPU, MEM, PID, Name, etc.)
# e          → show/hide process tree
# f          → filter
# +/-        → expand/collapse process tree node
# k          → send signal
# Delete     → kill selected process (sends SIGTERM)

# btop config: ~/.config/btop/btop.conf
# color_theme: Default / Dracula / TTY / night-owl
# vim_keys:    True   (j/k navigation)
# proc_tree:   True   (tree view by default)
# update_ms:   1000   (refresh rate — default 1000ms = 1Hz)

# btop with specific update rate and color theme
btop --utf-force --update-ms 500

# What btop adds over htop:
# Per-process network send/receive (bytes/s) — visible in the PROC panel
# GPU utilisation panel (NVIDIA/AMD via nvml/rocm)
# Disk I/O panel (read/write MB/s per device)
# Network panel (total and per-interface throughput)
# Collapsible process tree with aggregated child CPU/MEM
```

## Reading the CPU bar

```bash
# htop CPU bar segments (left to right):
# Blue   → low priority (nice > 0) user processes
# Green  → normal user processes
# Red    → kernel (sys) time
# Orange → IRQ/softirq time
# The bar spans 0-100% per core

# btop CPU bar:
# Shows per-core utilisation in a compact grid
# Color indicates mix of user/sys/io-wait
# Steal time shown separately (relevant in VMs)

# What "100% CPU" actually means:
# One CPU core at full utilisation for that sample interval
# A process can use >100% on multi-core (e.g. 380% = ~4 cores busy)
# htop shows aggregate unless you press F2 → Display → Show detailed CPU time

# Load average (top-left in htop / header in btop):
# 1-min  5-min  15-min average runnable+uninterruptible processes
# Load = 1.0 per core is "fully loaded" — on 8-core: overloaded if > 8.0
# Load > nCPU = processes waiting for CPU time (or I/O D-state)

# Check load vs core count:
nproc
# 8
uptime
# 14:22:07 up 12 days, 4:31, 2 users, load average: 4.12, 3.87, 3.91
# Load 4.12 on 8 cores = 51% utilised — healthy
```

## Process states and what they mean

```bash
# S column values:
# R  Running or runnable (on CPU or in run queue)
# S  Sleeping (interruptible — waiting for event, e.g. I/O, timer, lock)
# D  Uninterruptible sleep (I/O wait — can't be killed, must wait for I/O)
# T  Stopped (SIGSTOP or traced by debugger)
# Z  Zombie (exited but parent hasn't called wait() yet)
# I  Idle kernel thread

# D-state processes are dangerous: they can't be killed with SIGKILL
# They block shutdown and can accumulate if disk/NFS is hung
# Find them:
ps aux | awk '$8 == "D" {print}'

# Zombie processes: harmless unless there are thousands
# They hold a PID and a slot in the process table — that's it
# Fix: find the parent (ppid) and kill it, or wait for it to call wait()
ps -el | awk '$2 == "Z" {print $4, $5}'   # zombie PID + PPID

# Thread count per process:
ps -eLf | awk '{print $1, $2}' | sort | uniq -c | sort -rn | head -10
# or in htop: F2 → Display → Show threads in a different color
```

## Combining htop data with other tools

```bash
# pidstat: per-process CPU + I/O (1-second samples, 5 iterations)
pidstat -u -d 1 5 -p $(pgrep construx-api)
# Linux 5.15  (prod-01)
# Time     UID    PID   %usr %system  %wait   %CPU  Command
# 14:22:08   0   1847  36.00    2.00   0.00  38.00  construx-api
# Time     UID    PID  kB_rd/s  kB_wr/s  kB_ccwr/s  Command
# 14:22:08   0   1847     8.40    14.20       0.00  construx-api

# perf stat: hardware performance counters for a running process
perf stat -p $(pgrep construx-api) sleep 5
# Performance counter stats for process '1847':
#      5,003,412,813  cycles
#      4,871,234,001  instructions              #    0.97  insn per cycle
#        124,381,922  cache-misses              #    3.14% of all cache refs
#         38,241,219  branch-misses

# strace: what system calls is the process making?
strace -p $(pgrep construx-api) -e trace=network,file -f -c
# ... runs for a few seconds, then summary:
# % time     seconds  usecs/call     calls    errors syscall
# 38.42    0.002241          12       187           epoll_wait
# 24.18    0.001410          18        78           read
# 19.87    0.001159          22        53           write

# lsof: open files and network connections
lsof -p $(pgrep construx-api) | grep -E "REG|IPv"
# construx 1847 construx  txt REG  /usr/local/bin/construx-api
# construx 1847 construx   12 IPv4 TCP prod-01:41821->postgres:5432 (ESTABLISHED)
# construx 1847 construx   18 IPv4 TCP *:8080 (LISTEN)
```

htop vs btop vs top: `top` is on every Linux system — know it for emergencies, but the output is dense and dated. htop adds color, mouse support, tree view, and easy sorting — it's the default interactive choice. btop is the richest: GPU panels, per-process network I/O, and a better visual layout — worth installing on any workstation or long-lived server. For scripting and one-liners, skip all three and use `ps aux --sort=-%cpu | head`, `pidstat`, or `/proc/<pid>/stat` directly — they're scriptable and don't need a terminal.
