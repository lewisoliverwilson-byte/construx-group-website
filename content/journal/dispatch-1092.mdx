date: "2033-12-03"
excerpt: "kube-state-metrics (KSM) and node-exporter are the two foundational Prometheus exporters for Kubernetes observability. kube-state-metrics watches the Kubernetes API and generates Prometheus metrics from Kubernetes object state: kube_pod_status_phase (is a pod running/pending/failed?), kube_deployment_status_replicas_unavailable (how many pods in a Deployment are not ready?), kube_job_status_failed, kube_node_status_condition, kube_resourcequota_used (how close is a namespace to its resource quota?), and dozens more. These are state-derived metrics — not timeseries from the node OS but Kubernetes API objects translated to metric labels. node-exporter runs as a DaemonSet and scrapes the node operating system: CPU, memory, disk I/O, network interface stats, filesystem usage, load average, interrupts. Together they cover the full cluster picture: KSM tells you what Kubernetes thinks is happening (object state, deployment progress, quota utilisation), node-exporter tells you what the underlying Linux kernel is actually doing (CPU steal, memory pressure, disk saturation). The kube-prometheus-stack Helm chart bundles KSM, node-exporter, Alertmanager, Grafana, and a pre-built dashboard library (Kubernetes / USE dashboards) as a single installation."

## Key metrics and alert expressions

```promql
# kube-state-metrics: Kubernetes object state

# Pods not running in production namespace
count by (namespace, pod, phase) (
  kube_pod_status_phase{namespace="construx-prod", phase!="Running", phase!="Succeeded"} == 1
)

# Deployment unavailable replicas (rollout progress / pod crash)
sum by (namespace, deployment) (
  kube_deployment_status_replicas_unavailable{namespace="construx-prod"} > 0
)

# Resource quota utilisation: CPU requests close to namespace limit
(
  sum by (namespace) (kube_resourcequota_used{resource="requests.cpu", namespace="construx-prod"})
  /
  sum by (namespace) (kube_resourcequota_hard{resource="requests.cpu", namespace="construx-prod"})
) > 0.85

# OOMKilled pods in last 10m — memory limit too low
increase(kube_pod_container_status_restarts_total{namespace="construx-prod"}[10m]) > 2

# PersistentVolumeClaim not bound
kube_persistentvolumeclaim_status_phase{phase!="Bound"} == 1

# Node NotReady
kube_node_status_condition{condition="Ready", status="true"} == 0

# Jobs that have been running for more than 2 hours (likely stuck)
(
  time() - kube_job_status_start_time{namespace="construx-prod"}
  > 7200
) and kube_job_status_active == 1
```

```promql
# node-exporter: Linux kernel saturation metrics (USE method)

# CPU utilisation per node (idle = complement of utilisation)
1 - avg by (node) (
  rate(node_cpu_seconds_total{mode="idle"}[5m])
)

# CPU steal (virtualised environments — competing for host CPU time)
avg by (node) (
  rate(node_cpu_seconds_total{mode="steal"}[5m])
) > 0.05   # alert if >5% steal

# Memory pressure: available / total
(
  node_memory_MemAvailable_bytes
  / node_memory_MemTotal_bytes
) < 0.15   # alert if less than 15% available

# Disk saturation: I/O utilisation (time disk is busy)
rate(node_disk_io_time_seconds_total{device!~"loop.*"}[5m]) > 0.8

# Disk fill rate prediction — will fill in <4 hours
predict_linear(node_filesystem_avail_bytes{mountpoint="/"}[1h], 4 * 3600) < 0

# Network receive saturation
rate(node_network_receive_bytes_total{device!="lo"}[5m]) > 900e6   # >900 MB/s

# File descriptor exhaustion
(
  node_filefd_allocated / node_filefd_maximum
) > 0.8
```

# values.yaml
kubeStateMetrics:
  enabled: true

  enabled: true
  tolerations:
    - effect: NoSchedule        # run on GPU nodes and tainted nodes too
      operator: Exists

  enabled: true

  prometheusSpec:
    retention: 15d
    storageSpec:
      volumeClaimTemplate:
        spec:
          storageClassName: longhorn   # use Longhorn for replicated storage

  enabled: true
  defaultDashboardsEnabled: true   # Kubernetes / USE / CoreDNS dashboards pre-loaded
  adminPassword: "${GRAFANA_ADMIN_PASSWORD}"

  dashboardProviders:

          options:
            path: /var/lib/grafana/dashboards/construx

  dashboardsConfigMaps:
    construx-custom: construx-grafana-dashboards

  config:
    route:
      group_by: ['alertname', 'namespace']

      - name: 'pagerduty-construx'

kube-state-metrics vs metrics-server vs cAdvisor vs Prometheus node-exporter: metrics-server is the in-cluster API aggregation layer that powers `kubectl top` — it scrapes cAdvisor on each node for real-time CPU/memory usage but intentionally short-circuits to avoid scaling issues: no long-term storage, no query API, no Prometheus integration. cAdvisor is the per-node container metrics daemon (bundled in kubelet) — it exposes per-container CPU/memory/network metrics, which are scraped by Prometheus directly from the kubelet metrics endpoint. kube-state-metrics is entirely different: it watches the Kubernetes API server (not the nodes) and translates object state into metrics — Deployment replica counts, Pod phase, Job completion status, ResourceQuota utilisation. node-exporter covers the host OS layer below containers — raw CPU, memory, disk, and network from the Linux kernel. The correct monitoring stack uses all four: cAdvisor for container resource utilisation, KSM for Kubernetes object state, node-exporter for node saturation (USE method), and metrics-server only for `kubectl top` and Horizontal Pod Autoscaler inputs.
