date: "2033-04-28"
excerpt: "RisingWave is a streaming database that maintains SQL views over streaming data (Kafka, Kinesis, S3) with a PostgreSQL-compatible interface and durable, cloud-native state storage. Unlike Materialize (which stores state in memory) or Flink (which requires S3/RocksDB checkpoint configuration), RisingWave separates compute from storage: processing nodes are stateless, and state is stored in a cloud object store (S3) via a shared-state architecture borrowed from cloud-native OLAP systems. The query interface is PostgreSQL: you can query results from psql or any Postgres client, create indexes, and use standard SQL joins and window functions. RisingWave is designed for cases where you want sub-second freshness over streaming data, don't want to size memory for the full state, and want to deliver results to PostgreSQL-native tools like Grafana or Metabase."

PostgreSQL-compatible. Cloud-native state. Kafka source. Persistent materialized views. Sub-second freshness.

## Sources and materialized views

```sql
-- RisingWave: connect via standard Postgres client
-- psql -h risingwave.streaming.svc -p 4566 -U risingwave

-- Source: Kafka topic in JSON format
CREATE SOURCE construx_events (
  user_id     VARCHAR,
  event_type  VARCHAR,
  occurred_at TIMESTAMPTZ,
  payload     JSONB,
  session_id  VARCHAR
)
WITH (
  connector    = 'kafka',
  topic        = 'construx.events',
  properties.bootstrap.server = 'redpanda.messaging.svc:9092',
  scan.startup.mode = 'latest'
)
FORMAT PLAIN ENCODE JSON;

-- Source: Debezium CDC from PostgreSQL (upstream OLTP DB)
CREATE SOURCE construx_orders_cdc
WITH (
  connector    = 'kafka',
  topic        = 'construx.orders',
  properties.bootstrap.server = 'redpanda.messaging.svc:9092'
)
FORMAT DEBEZIUM ENCODE AVRO (
  schema.registry = 'http://schema-registry.messaging.svc:8081'
);

-- Materialized view: incremental aggregation — always fresh
CREATE MATERIALIZED VIEW mv_hourly_events AS
  SELECT
    date_trunc('hour', occurred_at) AS hour,
    event_type,
    count(*)                        AS event_count,
    count(DISTINCT user_id)         AS unique_users
  FROM construx_events
  GROUP BY 1, 2;

-- Index: accelerate point queries on the materialized view
CREATE INDEX ON mv_hourly_events (event_type, hour DESC);

-- Materialized view: join streaming events with a CDC table
CREATE MATERIALIZED VIEW mv_user_event_summary AS
  SELECT
    o.user_id,
    o.plan_tier,
    count(e.event_type)                                           AS total_events,
    count(e.event_type) FILTER (WHERE e.event_type = 'purchase') AS purchase_count,
    max(e.occurred_at)                                            AS last_seen
  FROM construx_orders_cdc o
  LEFT JOIN construx_events e ON e.user_id = o.user_id
  WHERE e.occurred_at > now() - INTERVAL '7 days'
  GROUP BY o.user_id, o.plan_tier;
```

## Sinks and PostgreSQL tooling integration

```sql
-- Sink: write materialized view results to Kafka
CREATE SINK mv_hourly_events_sink
FROM mv_hourly_events
WITH (
  connector = 'kafka',
  properties.bootstrap.server = 'redpanda.messaging.svc:9092',
  topic = 'construx.analytics.hourly-events'
)
FORMAT PLAIN ENCODE JSON (force_append_only = true);

-- Sink: write to an external PostgreSQL for BI tools that need PG access
CREATE SINK mv_event_summary_pg_sink
FROM mv_user_event_summary
WITH (
  connector = 'jdbc',
  jdbc.url  = 'jdbc:postgresql://postgres.construx.svc:5432/analytics',
  table.name = 'user_event_summary',
  type = 'upsert',
  primary_key = 'user_id'
);

-- Query materialized views with standard SQL — results are always fresh
SELECT event_type, sum(event_count), sum(unique_users)
FROM mv_hourly_events
WHERE hour > now() - INTERVAL '24 hours'
GROUP BY event_type
ORDER BY sum(event_count) DESC;
-- Returns in <5ms — reads from incrementally maintained state, not re-scanning Kafka

-- Grafana: connect directly via PostgreSQL data source

-- Database: risingwave
-- SELECT hour, event_count FROM mv_hourly_events WHERE event_type = '$event_type'
-- Grafana reads live streaming results like a normal database query
```

RisingWave vs Materialize vs Flink SQL vs ksqlDB: Materialize keeps all state in memory (fast reads, memory-constrained), RisingWave uses cloud object storage (state scales independently of compute, slightly higher read latency). Flink SQL is more mature and handles exactly-once semantics with complex stateful operations, but requires JVM and a Flink cluster. ksqlDB (Confluent) has limited SQL expressiveness and is tightly coupled to Confluent Platform. RisingWave is the right choice when you want PostgreSQL compatibility for downstream tools (Grafana, Metabase, dbt), need state that outlives the memory of a single machine, and want a managed cloud deployment model. The PostgreSQL wire compatibility is the headline feature: no new query language, no new client library — just psql.
