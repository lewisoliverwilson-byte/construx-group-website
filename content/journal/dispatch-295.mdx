Search is the feature most products need first and get wrong longest. The usual path: build a basic filter, realise it misses obvious cases, add more filters, still miss obvious cases, and eventually wonder why users aren't finding things that are clearly there.

The problem is almost always that text search doesn't understand meaning — it matches characters, not concepts. "Show me affordable electronics" won't match a $50 pair of earbuds tagged "Budget Audio".

There are three tiers of search implementation, each meaningfully better than the last.

## Tier 1: SQL ILIKE — enough for early products

For small datasets where users know what they're looking for, a case-insensitive LIKE query is fast and sufficient:

```ts
// lib/search.ts
import { db } from '@/lib/db';
import { products } from '@/lib/schema';
import { ilike, or } from 'drizzle-orm';

export async function searchProducts(query: string) {
  if (!query.trim()) return [];

  const term = `%${query.trim()}%`;

  return db.select().from(products)
    .where(
      or(
        ilike(products.title, term),
        ilike(products.description, term),
        ilike(products.category, term),
      )
    )
    .limit(50);
}
```

This breaks on:
- Typos (`"earbuds"` vs `"earbudd"`)
- Synonyms (`"cheap"` vs `"budget"` vs `"affordable"`)
- Partial matches at word boundaries (`"audio"` won't match `"audiobook"`)

Acceptable for internal tools and admin panels. Not good enough for user-facing search.

## Tier 2: Postgres full-text search — much better, still free

Postgres has a built-in full-text search engine. It handles stemming (running → run), stop words (the, a, is), and ranked results:

```sql
-- Add a search vector column
ALTER TABLE products ADD COLUMN search_vector tsvector;

-- Create a GIN index for fast search
CREATE INDEX products_search_idx ON products USING GIN(search_vector);

-- Populate the vector (run after adding column, and on inserts/updates)
UPDATE products SET search_vector =
  setweight(to_tsvector('english', coalesce(title, '')), 'A') ||
  setweight(to_tsvector('english', coalesce(description, '')), 'B') ||
  setweight(to_tsvector('english', coalesce(category, '')), 'C');

-- Keep it up to date with a trigger
CREATE OR REPLACE FUNCTION update_product_search_vector()
RETURNS trigger AS $$
BEGIN
  NEW.search_vector :=
    setweight(to_tsvector('english', coalesce(NEW.title, '')), 'A') ||
    setweight(to_tsvector('english', coalesce(NEW.description, '')), 'B') ||
    setweight(to_tsvector('english', coalesce(NEW.category, '')), 'C');
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER products_search_vector_update
  BEFORE INSERT OR UPDATE ON products
  FOR EACH ROW EXECUTE FUNCTION update_product_search_vector();
```

The `setweight` assigns priority: title matches (A) rank higher than description matches (B) which rank higher than category (C).

Querying with ranking:

```ts
import { sql } from 'drizzle-orm';

export async function searchProductsFTS(query: string) {
  if (!query.trim()) return [];

  // ts_query converts search terms to a query object
  // plainto_tsquery handles plain text input safely
  const results = await db.execute(sql`
    SELECT
      id,
      title,
      description,
      category,
      ts_rank(search_vector, plainto_tsquery('english', ${query})) as rank
    FROM products
    WHERE search_vector @@ plainto_tsquery('english', ${query})
    ORDER BY rank DESC
    LIMIT 50
  `);

  return results.rows;
}
```

This handles stemming and stop words, ranks by relevance, and is fast with a GIN index. Good for most products. Doesn't handle semantic similarity.

## Tier 3: pgvector — semantic search

pgvector adds vector operations to Postgres. You store embeddings alongside your data, and search finds semantically similar records even when the exact words don't match.

```sql
-- Install the extension (available on Supabase, Neon, and self-hosted Postgres 14+)
CREATE EXTENSION IF NOT EXISTS vector;

-- Add an embedding column
ALTER TABLE products ADD COLUMN embedding vector(1536);

-- Index for approximate nearest-neighbour search (much faster than exact)
CREATE INDEX products_embedding_idx ON products
  USING ivfflat (embedding vector_cosine_ops)
  WITH (lists = 100);
```

Generate embeddings with OpenAI's text-embedding-3-small (or Anthropic's when available):

```ts
// lib/embeddings.ts
import OpenAI from 'openai';

const openai = new OpenAI();

export async function getEmbedding(text: string): Promise<number[]> {
  const response = await openai.embeddings.create({
    model: 'text-embedding-3-small',
    input: text.slice(0, 8192), // Max input length
  });
  return response.data[0].embedding;
}

// lib/search.ts
export async function searchProductsSemantic(query: string) {
  const queryEmbedding = await getEmbedding(query);

  const results = await db.execute(sql`
    SELECT
      id,
      title,
      description,
      category,
      1 - (embedding <=> ${JSON.stringify(queryEmbedding)}::vector) as similarity
    FROM products
    WHERE embedding IS NOT NULL
    ORDER BY embedding <=> ${JSON.stringify(queryEmbedding)}::vector
    LIMIT 20
  `);

  return results.rows;
}
```

The `<=>` operator is cosine distance. `1 - distance` is similarity. Results are ordered by semantic relevance.

## Hybrid search: combining FTS and vector

The best results combine both approaches — keyword relevance plus semantic similarity:

```ts
export async function searchProductsHybrid(query: string) {
  const queryEmbedding = await getEmbedding(query);

  const results = await db.execute(sql`
    SELECT
      id,
      title,
      description,
      -- Reciprocal rank fusion of FTS rank and vector similarity
      (
        COALESCE(ts_rank(search_vector, plainto_tsquery('english', ${query})), 0) * 0.3
        + (1 - (embedding <=> ${JSON.stringify(queryEmbedding)}::vector)) * 0.7
      ) as combined_score
    FROM products
    WHERE
      search_vector @@ plainto_tsquery('english', ${query})
      OR embedding IS NOT NULL
    ORDER BY combined_score DESC
    LIMIT 20
  `);

  return results.rows;
}
```

The weights (0.3 FTS / 0.7 vector) are tunable based on what your users need. For intent-heavy searches ("I want to grow my Amazon business"), weight vector higher. For specific product searches ("Echo Dot Gen 5"), weight FTS higher.

## Keeping embeddings up to date

Embeddings need to be generated for new and updated records:

```ts
// In the background job queue
async function generateProductEmbedding(productId: string) {
  const [product] = await db.select()
    .from(products)
    .where(eq(products.id, productId));

  if (!product) return;

  const text = `${product.title}. ${product.description}. Category: ${product.category}.`;
  const embedding = await getEmbedding(text);

  await db.update(products)
    .set({ embedding: JSON.stringify(embedding) })
    .where(eq(products.id, productId));
}
```

Enqueue `generate-product-embedding` on insert or significant update. Don't regenerate on every minor change — embeddings are expensive and stable for the same content.
