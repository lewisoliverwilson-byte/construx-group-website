eBay's category system is a tree with over 15,000 leaf nodes. Each category has its own:

- **Final value fee rate** (8-15% depending on category and seller tier)
- **Minimum final value fee** (some categories have a floor)
- **Listing requirements** (what item specifics are mandatory)
- **Allowed condition values** (New, Used, Refurbished, and variants specific to the category)
- **International site multipliers** (fees vary by eBay site)

When Scoutr calculates a margin, it needs the correct fee for the specific category of the item being scanned. Getting this wrong produces incorrect margin calculations. Getting it right requires understanding the taxonomy.

## Building the category database

The eBay Taxonomy API returns the full category tree. We download it periodically (it changes infrequently — eBay updates major structure a few times a year) and store it in a flat table:

```sql
CREATE TABLE ebay_categories (
  category_id      TEXT PRIMARY KEY,
  category_name    TEXT NOT NULL,
  parent_id        TEXT REFERENCES ebay_categories(category_id),
  leaf             BOOLEAN NOT NULL DEFAULT false,
  depth            INTEGER NOT NULL,
  full_path        TEXT NOT NULL,  -- e.g., "Electronics > Mobile Phones > Smartphones"
  fvf_rate         NUMERIC(5,4),   -- final value fee as decimal (0.12 = 12%)
  fvf_min_usd      NUMERIC(8,2),   -- minimum fee in USD
  fvf_cap_usd      NUMERIC(8,2),   -- maximum fee cap (some categories)
  updated_at       TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX ON ebay_categories (parent_id);
CREATE INDEX ON ebay_categories (leaf);
-- Full-text search for category lookup by name
CREATE INDEX ON ebay_categories USING GIN (to_tsvector('english', full_path));
```

The `full_path` column stores the human-readable path from root to leaf. This is expensive to compute but makes category lookup by description trivial.

## The fee schedule problem

The fee schedule isn't in the Taxonomy API — it's in eBay's documentation and changes independently of the taxonomy. We maintain a separate `ebay_fee_schedule` table that maps category groups to fee rates:

```sql
CREATE TABLE ebay_fee_schedule (
  schedule_id      TEXT PRIMARY KEY,
  category_ids     TEXT[],  -- categories this schedule applies to
  rate_standard    NUMERIC(5,4) NOT NULL,
  rate_above_threshold NUMERIC(5,4),  -- lower rate above a transaction threshold
  threshold_usd    NUMERIC(8,2),
  min_fee_usd      NUMERIC(8,2),
  cap_fee_usd      NUMERIC(8,2),
  effective_from   DATE NOT NULL,
  effective_to     DATE,  -- null = current
  site             TEXT NOT NULL DEFAULT 'EBAY_US'
);
```

The category→schedule mapping is many-to-one: many categories share the same fee schedule. We maintain this mapping by hand (eBay doesn't provide it programmatically) and update it when eBay publishes fee changes.

## Category inference at scan time

When a user scans a source URL, we don't always have an explicit eBay category. We infer it from the product title and description using two approaches:

**Approach 1: eBay's own categorisation.** The eBay Browse API, given a search query, returns item results with their category assignments. We use the category of the top result as a signal:

```ts
async function inferCategoryFromTitle(title: string): Promise<string | null> {
  const results = await ebayBrowseSearch({ q: title, limit: 5 });
  if (!results.itemSummaries?.length) return null;
  
  // Find the most common category among top results
  const categoryCounts = new Map<string, number>();
  for (const item of results.itemSummaries) {
    const cat = item.categories?.[0]?.categoryId;
    if (cat) categoryCounts.set(cat, (categoryCounts.get(cat) ?? 0) + 1);
  }
  
  let topCategory: string | null = null;
  let topCount = 0;
  for (const [cat, count] of categoryCounts) {
    if (count > topCount) { topCategory = cat; topCount = count; }
  }
  
  return topCategory;
}
```

**Approach 2: Embedding-based lookup.** For product types that don't have strong eBay search signals, we embed the product description and find the closest category in our database by cosine similarity against pre-embedded category `full_path` strings:

```ts
async function inferCategoryByEmbedding(description: string): Promise<string | null> {
  const embedding = await generateEmbedding(description);
  const result = await db.execute(sql`
    SELECT category_id, full_path,
           1 - (embedding <=> ${JSON.stringify(embedding)}::vector) AS similarity
    FROM ebay_categories
    WHERE leaf = true
    ORDER BY embedding <=> ${JSON.stringify(embedding)}::vector
    LIMIT 1
  `);
  return result.rows[0]?.category_id ?? null;
}
```

We use approach 1 when the product has good eBay search coverage, and approach 2 as a fallback. In practice, approach 1 is more accurate for well-known product categories; approach 2 handles niche categories that don't have strong search signal.

## The fee calculation

Once we have a category, fee calculation is straightforward:

```ts
async function calculateEbayFee(categoryId: string, salePrice: number): Promise<number> {
  const schedule = await getFeeScheduleForCategory(categoryId);
  
  if (!schedule) {
    // Fallback to eBay's standard rate (currently 13.25% for most categories)
    return salePrice * 0.1325;
  }
  
  let fee: number;
  if (schedule.threshold_usd && salePrice > schedule.threshold_usd) {
    const belowThreshold = schedule.threshold_usd * schedule.rate_standard;
    const aboveThreshold = (salePrice - schedule.threshold_usd) * schedule.rate_above_threshold!;
    fee = belowThreshold + aboveThreshold;
  } else {
    fee = salePrice * schedule.rate_standard;
  }
  
  // Apply floor and cap
  if (schedule.min_fee_usd) fee = Math.max(fee, schedule.min_fee_usd);
  if (schedule.cap_fee_usd) fee = Math.min(fee, schedule.cap_fee_usd);
  
  return fee;
}
```

## The data freshness problem

Fee schedules change. eBay announces fee changes with 30-60 days notice, but we must update our schedule table before the effective date or Scoutr will report incorrect margins.

We handle this with:
1. A calendar reminder 30 days before any known `effective_from` date with a future value
2. A monitoring check that compares our calculated fees against eBay's published fee calculator for 10 spot-check products weekly
3. A flag in the UI if the fee schedule for a category hasn't been verified within 90 days

The monitoring check catches quiet updates that aren't announced prominently. The UI flag tells users when to treat a margin calculation with lower confidence.

The eBay taxonomy problem isn't glamorous — it's data management and mapping maintenance. But getting it wrong means every margin Scoutr reports is wrong. We've invested proportionally.
