The Hyve is the most technically complex of the three Construx products. It requires real-time multi-user communication, persistent AI memory that spans sessions, and an AI agent that participates in channels alongside humans. Here's how the architecture handles each of these.

## The top-level structure

The Hyve is a Next.js 15 App Router application with three main layers:

**Real-time layer**: WebSocket connections (via Supabase Realtime) for live channel updates. When a user sends a message, all other users in the same workspace see it appear in real-time without refreshing.

**Persistence layer**: Postgres (via Supabase) for all data — workspaces, channels, messages, tasks, documents, AI agent run history.

**AI layer**: the AI agent pipeline — Claude API calls, context retrieval (pgvector), message processing, and response streaming.

These three layers need to be coordinated: when the AI agent processes a message and produces a response, that response needs to be persisted and broadcast in real-time to all channel members.

## Real-time: how messages flow

When a user sends a message in a channel:

1. Client sends the message via an API route (`POST /api/channels/{id}/messages`)
2. The API route persists the message to Postgres
3. Supabase Realtime detects the new database row (via Postgres logical replication) and broadcasts an event to all connected clients subscribed to that channel
4. Connected clients receive the event and append the message to their local channel state

The AI agent participates in the same flow. When a message is sent, the API route checks if it should trigger an AI response (based on whether the message mentions the AI agent or is addressed to it). If yes, it enqueues an AI processing job.

The AI processing job:
1. Retrieves relevant context from pgvector
2. Constructs the prompt
3. Calls Claude with streaming enabled
4. Streams the response — each chunk is sent to the channel as a partial message update via Supabase Realtime
5. When complete, persists the full response to Postgres

The streaming approach means users see the AI response appearing word by word, the same way they see typing indicators from human team members.

## AI memory: the vector pipeline

Every message sent in a channel is processed asynchronously:
1. The message is chunked (for long messages, split at sentence boundaries)
2. Each chunk is embedded using Claude Embeddings
3. The embedding is stored in a `message_embeddings` table with a `vector(1536)` column

When the AI agent processes a new message, it queries the vector store:

```sql
SELECT m.content, m.created_at, m.channel_id,
       me.embedding <=> $1 AS distance
FROM messages m
JOIN message_embeddings me ON m.id = me.message_id
WHERE m.workspace_id = $2
  AND me.embedding <=> $1 < 0.4
ORDER BY me.embedding <=> $1
LIMIT 8;
```

This retrieves the 8 most semantically similar past messages from anywhere in the workspace, filtered by a minimum similarity threshold. The retrieved messages are included in the AI agent's context as relevant background.

The effect: the AI agent can reference a decision made three months ago in a different channel if it's relevant to the current conversation. Users frequently notice this and it's one of the features that most differentiates The Hyve from a simple AI chatbot.

## The agent invocation design

The AI agent participates in channels, but doesn't respond to every message. The invocation rules:

**Always responds**: messages that explicitly mention the agent by name (`@AI`)

**Responds if configured**: some channels have "AI active" mode, where the agent evaluates each message and responds when it has something useful to add. The system prompt is tuned to be conservative — respond when there's something specific and useful to contribute, not just to demonstrate presence.

**Never responds**: to its own previous responses, to system notifications, or to human-to-human exchanges it's not been invited into.

## Multi-tenancy

Every table includes a `workspace_id` column. Row-level security in Postgres enforces workspace isolation at the database layer:

```sql
ALTER TABLE messages ENABLE ROW LEVEL SECURITY;

CREATE POLICY messages_workspace_isolation ON messages
  USING (workspace_id = current_setting('app.workspace_id')::uuid);
```

The application sets `app.workspace_id` on the database session before querying. A bug in the application code that omits the workspace filter is caught at the database layer. RLS is the safety net that makes multi-tenancy trustworthy.

## The scaling limit

The current architecture has one limit that will require addressing at higher traffic: AI processing is synchronous within each request. When many messages arrive simultaneously, the AI processing jobs queue up and responses arrive with increasing delay.

The solution is a proper job queue (Inngest, or a simple Postgres-backed queue) that processes AI jobs asynchronously and independently of the request lifecycle. This is the next infrastructure investment for The Hyve.

At current user count, the synchronous approach is fine. At 10x, it wouldn't be. We'll build the queue when the metric demands it.
