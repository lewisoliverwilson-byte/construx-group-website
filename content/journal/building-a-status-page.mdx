A status page is one of those things that feels premature until the moment you don't have one. Then it feels embarrassing.

Here's what happened when Scoutr went down for 40 minutes during a Vercel edge network issue: three users emailed us. Two tweeted. One opened a support ticket asking if we'd been hacked. We had no status page. We had no way to communicate to users that we were aware of the issue and working on it. We looked like we didn't know our own product was broken.

We built the status page that day.

## What a status page actually does

The immediate function is obvious: it tells users whether the product is working. But the actual value is more nuanced.

**It reduces support noise during incidents.** When users can self-serve the answer to "is it broken or is it me?", they don't email. During the next Scoutr incident (a database connection pool issue, 22 minutes of degraded performance), we received zero support emails. We'd posted a status update 4 minutes after detection. Users read it and waited.

**It demonstrates operational maturity.** A public status page says: we take uptime seriously, we have monitoring, and we're not trying to hide problems. That's a trust signal for professional users evaluating whether to depend on your product.

**It forces reliability thinking.** To run a status page, you need to know your components. To know your components, you need to instrument them. The act of setting up the status page forced us to define what "working" means for each product — which components, which metrics, what thresholds.

## What we built

We didn't build a custom status page platform. We use Betteruptime, which offers a hosted status page tied to monitoring. The monthly cost per product is less than a coffee.

Each product has a status page at `status.[product-domain]`. The components we monitor:

**Scoutr:**
- API (health check endpoint responding under 2s)
- eBay data fetching (latency of eBay API calls)
- AI analysis (Claude API reachability)
- Database (connection pool availability)

**The Marqet:**
- API
- Search (vector similarity endpoint)
- Embeddings service (Claude embedding API)
- Stripe webhooks (webhook delivery success rate)
- Database

**The Hyve:**
- API
- AI agent (Claude API)
- WebSocket connections
- Supabase (database + realtime)
- Storage

## The monitoring setup

Each health check endpoint is a Next.js API route at `/api/health`:

```ts
export async function GET() {
  const checks = await Promise.allSettled([
    checkDatabase(),
    checkRedis(),
    checkExternalAPI(),
  ]);

  const healthy = checks.every(c => c.status === 'fulfilled');
  
  return Response.json(
    {
      status: healthy ? 'ok' : 'degraded',
      timestamp: new Date().toISOString(),
      checks: checks.map((c, i) => ({
        name: ['database', 'redis', 'external'][i],
        status: c.status === 'fulfilled' ? 'ok' : 'error',
      })),
    },
    { status: healthy ? 200 : 503 }
  );
}
```

Betteruptime polls this endpoint every 30 seconds. If it returns non-200 three times in a row, it opens an incident and sends us an alert. We get Slack and SMS notifications within 90 seconds of a real outage.

## The incident communication protocol

When an incident opens:

1. **Within 5 minutes**: post an initial update on the status page. Even if the update is "we're investigating" — the critical thing is that users can see we know.
2. **Every 15 minutes**: post an update until the incident is resolved. Even if the update is "still investigating."
3. **On resolution**: post a resolved update with a brief explanation of the cause.
4. **Within 24 hours**: post a postmortem if the incident lasted more than 30 minutes or affected more than 10 users.

The protocol sounds demanding for a two-person team, but in practice it takes 90 seconds to post a status update. The investment is tiny relative to the trust cost of silence.

## The postmortem format

We keep postmortems short. They live on the status page and are public:

- **Duration:** When it started, when it ended, total time.
- **Impact:** What was affected, how many users experienced it.
- **Root cause:** One paragraph, no jargon, no blame.
- **What we changed:** Specific actions taken to prevent recurrence.

The public postmortem has an unexpected side effect: it signals that we take reliability seriously enough to be transparent about failures. Some users have specifically mentioned the postmortem culture as a reason they trust our products.

## The argument against "we're too small"

The most common objection to status pages at the small-company stage is that they're an enterprise concern — something for companies with SLAs and enterprise customers. We disagree.

The cost of not having a status page is fully realised the first time you have an incident. That might happen in week one. The cost of setting one up is two hours.

We had fewer than 50 users when we set up status pages for all three products. It was one of the best two-hour investments we've made.
