excerpt: "fio (Flexible I/O Tester) is the standard tool for measuring storage performance. It simulates different workloads — sequential reads and writes, random I/O at 4K blocks, mixed read/write — and reports throughput (MB/s), IOPS, and latency percentiles. The latency percentiles matter more than averages: p99 latency is what a slow request experiences; p99.9 latency is what the slowest 1-in-1000 request experiences."

Average latency is a lie. Measure p99. Measure p99.9.

## Basic benchmark — sequential read/write

```bash
# Sequential read — 1 thread, 128K blocks, 32 queued IOs
fio \
  --name=seq-read \
  --filename=/dev/nvme0n1 \
  --rw=read \
  --bs=128k \
  --ioengine=libaio \
  --iodepth=32 \
  --numjobs=1 \
  --time_based \
  --runtime=30s \
  --group_reporting

# Output excerpt:
# READ: bw=1843MiB/s (1932MB/s), bw=1843MiB/s (1932MB/s), iops=14.4k, run=30001-30001msec
# lat (usec): min=48, max=2104, avg=68.2, stdev=12.4
# lat (usec) percentiles:
#   |  50th=65, 75th=78, 95th=88, 99th=104, 99.9th=188
```

## Random 4K — what databases care about

```bash
# Random 4K read — the workload that kills spinning disks
fio \
  --name=rand-read-4k \
  --filename=/dev/nvme0n1 \
  --rw=randread \
  --bs=4k \
  --ioengine=libaio \
  --iodepth=32 \
  --numjobs=4 \
  --time_based \
  --runtime=60s \
  --group_reporting

# Random 4K write
fio \
  --name=rand-write-4k \
  --filename=/dev/nvme0n1 \
  --rw=randwrite \
  --bs=4k \
  --ioengine=libaio \
  --iodepth=32 \
  --numjobs=4 \
  --time_based \
  --runtime=60s \
  --group_reporting
```

## fio job file — run multiple tests at once

```ini
; benchmarks.fio
[global]
filename   = /dev/nvme0n1
ioengine   = libaio
iodepth    = 32
numjobs    = 4
time_based = 1
runtime    = 30s
group_reporting = 1

[seq-read]
rw = read
bs = 128k

[seq-write]
rw = write
bs = 128k

[rand-read-4k]
rw = randread
bs = 4k

[rand-write-4k]
rw = randwrite
bs = 4k

[rand-mixed-4k]
rw     = randrw
rwmixread = 70
bs     = 4k
```

```bash
fio benchmarks.fio --output-format=json > results.json
```

## Interpreting results

```bash
# Parse JSON output with jq
cat results.json | jq '[.jobs[] | {
  name:     .jobname,
  iops:     .read.iops + .write.iops,
  bw_mbs:   ((.read.bw + .write.bw) / 1024 | floor),
  lat_avg:  .read.lat_ns.mean // .write.lat_ns.mean | . / 1000 | floor,
  lat_p99:  .read.lat_ns.percentile["99.000000"] // .write.lat_ns.percentile["99.000000"] | . / 1000 | floor,
  lat_p999: .read.lat_ns.percentile["99.900000"] // .write.lat_ns.percentile["99.900000"] | . / 1000 | floor
}]'
```

## Benchmark context — what the numbers mean

| Workload | NVMe SSD | SATA SSD | Cloud EBS gp3 | Cloud EBS io2 |
|----------|----------|----------|---------------|---------------|
| Seq read | 1.8 GB/s | 550 MB/s | 250 MB/s      | 4 GB/s        |
| Rand 4K read IOPS | 45k | 90k | 16k | 256k |
| Rand 4K write IOPS | 38k | 80k | 16k | 256k |
| p99 lat (µs) | 104 | 80 | 2,000 | 500 |

Cloud EBS gp3 has 16k IOPS at base. PostgreSQL with random 4K writes will saturate this at ~16 concurrent writes. For write-heavy databases on AWS, io2 is the correct choice — not gp3.

## PostgreSQL-specific benchmark

```bash
# pgbench — PostgreSQL's built-in OLTP benchmark
pgbench -i -s 100 construx  # Initialize with scale factor 100 (~1.5GB)

# Run for 60 seconds with 10 clients
pgbench -c 10 -j 2 -T 60 construx

# Output:
# tps = 1842.34 (without initial connection time)
# latency average = 5.43 ms
```

The Construx default: benchmark every VPS before deploying a database. NVMe-backed instances (Hetzner EX, OVH Advance) give 40-50k random IOPS; standard cloud VMs give 3-16k. The difference determines whether your PostgreSQL p99 is 2ms or 20ms.
