date: "2032-03-13"
excerpt: "ZFS is a combined filesystem and volume manager with copy-on-write (CoW) semantics: every write creates a new block rather than overwriting an existing one. This enables atomic snapshots (taken in O(1) time, no matter the filesystem size), rollbacks, and incremental replication via `zfs send/receive`. ZFS also manages RAID internally (RAID-Z1/Z2/Z3, mirroring, striping), replacing hardware RAID controllers with software that understands the filesystem layout. Used in production by FreeBSD, Proxmox, TrueNAS, Oracle Solaris, and increasingly Linux (OpenZFS)."

Every write is a new block. Snapshots are free. RAID lives in software.

## Pool creation — RAID topologies

```bash
# ZFS pool: combines physical disks into a logical storage unit

# Mirror (RAID-1): 2 disks, 1 can fail
zpool create tank mirror /dev/sdb /dev/sdc

# RAID-Z1 (RAID-5 equivalent): 3+ disks, 1 can fail
zpool create tank raidz1 /dev/sdb /dev/sdc /dev/sdd

# RAID-Z2 (RAID-6 equivalent): 4+ disks, 2 can fail
zpool create tank raidz2 /dev/sdb /dev/sdc /dev/sdd /dev/sde

# Striped mirrors (RAID-10): 2 mirrors striped — highest performance
zpool create tank \
  mirror /dev/sdb /dev/sdc \
  mirror /dev/sdd /dev/sde

# Pool status — health and error counts
zpool status tank
# NAME        STATE     READ WRITE CKSUM
# tank        ONLINE       0     0     0
#   raidz2-0  ONLINE       0     0     0
#     sdb     ONLINE       0     0     0
#     sdc     ONLINE       0     0     0
#     sdd     ONLINE       0     0     0
#     sde     ONLINE       0     0     0
# errors: No known data errors

# Pool I/O stats
zpool iostat tank 1
# capacity     operations     bandwidth
# alloc  free  read  write  read   write
# 1.21T  8.79T  842   1,204  6.54G  9.37G
```

## Datasets — filesystems within a pool

```bash
# Create datasets (sub-filesystems with independent properties)
zfs create tank/postgres
zfs create tank/postgres/data
zfs create tank/postgres/wal      # Separate dataset for WAL (different compression)
zfs create tank/backups

# Set properties on datasets
zfs set compression=zstd   tank/postgres
zfs set compression=lz4    tank/postgres/wal    # Faster, less compression for WAL
zfs set atime=off          tank/postgres        # No access-time updates (perf)
zfs set recordsize=8k      tank/postgres/data   # Match PostgreSQL block size
zfs set recordsize=128k    tank/backups         # Larger blocks for sequential reads

# Mount the dataset
zfs set mountpoint=/var/lib/postgresql/data tank/postgres/data

# Show dataset properties
zfs get all tank/postgres/data
# NAME                    PROPERTY     VALUE         SOURCE
# tank/postgres/data      type         filesystem    -
# tank/postgres/data      creation     Mon Mar 10    -
# tank/postgres/data      used         142G          -
# tank/postgres/data      available    8.58T         -
# tank/postgres/data      compression  zstd          local
# tank/postgres/data      compressratio 2.41x         -   ← 2.4x compression
```

## Snapshots — O(1) point-in-time copies

```bash
# Take a snapshot (instant — no data is copied)
zfs snapshot tank/postgres/data@2032-03-10T02:00

# List snapshots
zfs list -t snapshot -o name,creation,used
# NAME                                    CREATION      USED
# tank/postgres/data@2032-03-09T02:00    Mon Mar 09    1.23G  ← diff from previous
# tank/postgres/data@2032-03-10T02:00    Tue Mar 10    841M

# Rollback to a snapshot (destroys all data written after the snapshot)
zfs rollback tank/postgres/data@2032-03-10T02:00

# Clone a snapshot (writable, CoW — shares blocks with the snapshot)
zfs clone tank/postgres/data@2032-03-10T02:00 tank/postgres/data-clone
# mount as read-write copy — only diffs use new blocks

# Automated hourly snapshots via cron
echo '0 * * * * root zfs snapshot tank/postgres/data@$(date +%Y-%m-%dT%H:00)' >> /etc/crontab

# Prune snapshots older than 7 days
zfs list -t snapshot -o name,creation -H | \
  awk '{print $1, $2}' | \
  while read name date; do
    age_days=$(( ($(date +%s) - $(date -d "$date" +%s)) / 86400 ))
    [ $age_days -gt 7 ] && zfs destroy "$name"
  done
```

## zfs send/receive — incremental replication

```bash
# Full send: replicate a dataset to another host
# First replication: send the full snapshot
zfs send tank/postgres/data@2032-03-10T02:00 | \
  ssh backup-01 "zfs receive backup/postgres/data"

# Incremental: only send the diff between two snapshots
# Use -i for delta (compressed wire transfer)
zfs send -i \
  tank/postgres/data@2032-03-10T02:00 \
  tank/postgres/data@2032-03-11T02:00 \
  | ssh backup-01 "zfs receive backup/postgres/data"

# With compression and verbose output
zfs send -Rv tank/postgres/data@2032-03-11T02:00 | \
  mbuffer -s 128k -m 1G | \       # Buffer for network bursts
  ssh backup-01 "mbuffer -s 128k -m 1G | zfs receive -F backup/postgres/data"

# Encrypted send (ZFS native encryption)
zfs create -o encryption=aes-256-gcm -o keylocation=prompt -o keyformat=passphrase \
  tank/secrets
zfs send -R --raw tank/secrets@backup | \  # --raw: send encrypted, don't decrypt
  ssh backup-01 "zfs receive backup/secrets"
```

## ZFS scrub — background data integrity verification

```bash
# Scrub: reads every block and verifies checksums against the RAID parity
# ZFS checksums every block (unlike ext4/XFS which have no checksums)
zpool scrub tank

# Monitor progress
zpool status tank | grep -A 5 scrub
# scan: scrub in progress since Mon Mar 10 02:00:00 2032
#     450.12G scanned at 1.50G/s, 128.32G issued at 427M/s, 1.21T total
#     0 repaired, 2.91% done, no estimated completion time

# After scrub completes:
# scrub repaired 0B in 00:14:32 with 0 errors on Mon Mar 10 02:14:32 2032

# If errors are found: ZFS automatically repairs them using parity (RAID-Z) or mirror
# This is impossible with software RAID (md) + ext4: no checksums, no self-healing
```

ZFS vs ext4/XFS: ext4 and XFS are traditional filesystems — they write in-place, have no checksums (silent corruption goes undetected), and snapshots require LVM underneath. ZFS checksums every block, self-heals from RAID-Z parity, and snapshots are free. The cost: ZFS requires more RAM (ARC cache: ideally 1GB RAM per 1TB storage), uses more CPU for RAID-Z parity, and the in-kernel Linux module (OpenZFS) lags the FreeBSD port by a few months. For PostgreSQL or any database workload where silent data corruption is catastrophic, ZFS's per-block checksums are worth every megabyte of RAM.
