date: "2033-06-06"
excerpt: "Velero is a Kubernetes backup tool that snapshots cluster state — all resources in a namespace (Deployments, Services, ConfigMaps, Secrets, CRDs) plus persistent volumes — and stores them in object storage (S3, GCS, Azure Blob). A Velero backup is a point-in-time snapshot that can be restored to the same cluster (for recovery from accidental deletion) or a different cluster (for cluster migration or disaster recovery). Velero uses volume plugins (Restic, Kopia) to back up PVC data at the file system level, independent of the storage provider — so you can back up an NFS PV and restore it into a different CSI driver. Scheduled backups run as CronJobs defined in VolumeSnapshotLocations, and TTLs automatically expire old backups. The workflow is: schedule → backup → store in S3 → test restore in staging."

Namespace backup. PVC snapshot. S3 backend. Scheduled backup. Restore. Disaster recovery.

## Installation and backup location

```bash
# Install Velero with S3 backend (AWS)
velero install \
  --provider aws \
  --plugins velero/velero-plugin-for-aws:v1.10.0 \
  --bucket construx-velero-backups \
  --backup-location-config region=eu-west-1 \
  --snapshot-location-config region=eu-west-1 \
  --secret-file ./credentials-velero \
  --use-node-agent \   # enables file-system level PV backup via Kopia
  --use-volume-snapshots=true

# credentials-velero:
# [default]
# aws_access_key_id=AKIA...
# aws_secret_access_key=...
# (or use IRSA — IAM Role for Service Account — no static keys)

# Verify installation
velero backup-location get
# NAME    PROVIDER  BUCKET/PREFIX                    PHASE
# default  aws      construx-velero-backups/velero   Available

# Snapshot location
velero snapshot-location get
# NAME    PROVIDER
# default  aws
```

## Backups and schedules

```bash
# One-off backup: all resources in construx-prod namespace + PVCs
velero backup create construx-prod-backup-manual \
  --include-namespaces construx-prod \
  --include-cluster-resources=true \
  --wait

# Watch backup progress
velero backup describe construx-prod-backup-manual --details
# Phase:  Completed
# Namespaces:
#   Included:  construx-prod
# Resources:
#   Included: *
#   Cluster-scoped: auto
# Label selector: <none>
# TTL: 720h0m0s   ← expires in 30 days
# Hooks: <none>
# Backup Item Operations:
#   Status: Completed
# Backup Volumes:
#   Restic/Kopia Backups:
#     Completed:
#       construx-prod/postgres-pvc-0 (2.4 GB)
#       construx-prod/redis-pvc-0    (0.1 GB)

# Schedule: daily backup at 02:00 UTC with 30-day TTL
velero schedule create construx-prod-daily \
  --schedule "0 2 * * *" \
  --include-namespaces construx-prod \
  --ttl 720h0m0s

# Weekly full cluster backup (includes cluster-scoped resources: CRDs, ClusterRoles)
velero schedule create full-cluster-weekly \
  --schedule "0 3 * * 0" \
  --include-namespaces "*" \
  --include-cluster-resources=true \
  --ttl 2160h0m0s   # 90 days

# List all backups
velero backup get
# NAME                            STATUS     ERRORS  WARNINGS  CREATED                TTL
# construx-prod-daily-20330606    Completed  0       0         2033-06-06 02:00:00    720h0m0s
# construx-prod-daily-20330605    Completed  0       0         2033-06-05 02:00:00    720h0m0s
# full-cluster-weekly-20330602    Completed  0       0         2033-06-02 03:00:00    2160h0m0s
```

## Restore and disaster recovery

```bash
# Restore a namespace from the latest backup
# (to a new namespace for testing — or same namespace after accidental deletion)
velero restore create \
  --from-backup construx-prod-daily-20330606 \
  --include-namespaces construx-prod \
  --namespace-mappings construx-prod:construx-prod-restore \
  --wait

# Restore to a completely different cluster (disaster recovery)
# 1. Install Velero on the new cluster with the same S3 bucket
# 2. All backups are automatically discovered
velero backup get   # shows backups from S3

# Restore the full namespace with PVCs
velero restore create \
  --from-backup construx-prod-daily-20330606 \
  --include-namespaces construx-prod \
  --restore-volumes=true \
  --wait

velero restore describe construx-prod-daily-20330606-20330606120000
# Phase: Completed
# Warnings: 0
# Errors: 0
# Included namespaces: construx-prod
# Resource List:
#   apps/Deployment: 4
#   v1/Service: 4
#   v1/ConfigMap: 8
#   v1/Secret: 6
#   v1/PersistentVolumeClaim: 2

# Backup hooks: run a command before/after backup for database consistency
# (e.g., flush postgres WAL, snapshot at a clean checkpoint)
# Add annotation to the pod:
kubectl annotate pod postgres-0 \
  pre.hook.backup.velero.io/command='["/bin/bash", "-c", "pg_dump -U postgres construx > /tmp/pre-backup.sql"]' \
  pre.hook.backup.velero.io/timeout=5m
```

Velero vs etcd snapshot vs cloud-native snapshots vs Kasten: etcd snapshot captures raw cluster state but not persistent volume data — useless for restoring application data. Cloud-native snapshots (AWS EBS snapshot, GCP PD snapshot) back up PVs but not Kubernetes resource metadata — you'd need to recreate all the Deployments, Services, and ConfigMaps manually. Kasten K10 (Veeam) is a full Kubernetes backup platform with a web UI, application-aware backup policies, and compliance reporting — commercial and feature-complete but adds cost. Velero is open source, S3-compatible, and covers the main use cases: namespace-level backup and restore, cluster migration, and disaster recovery. The combination of resource backup (namespace state as YAML) plus PVC backup (file system data via Kopia) makes Velero the standard open-source choice for Kubernetes backup.
