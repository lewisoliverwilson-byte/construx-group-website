`next/image` is one of the most impactful features in the Next.js framework for production performance. It's also frequently used incorrectly — usually by cargo-culting `<Image>` everywhere without understanding what's actually happening.

Here's what it does, how we use it, and when it's wrong.

## What next/image actually does

**Format negotiation.** The component serves WebP to browsers that support it and falls back to the original format for those that don't. WebP is typically 25-35% smaller than JPEG at equivalent quality. For Amplify deployments (which we use), this negotiation happens at the CDN edge.

**Responsive sizing.** The `sizes` prop, combined with the `srcSet` generated by Next.js, serves the appropriately sized image for the viewport width. A 2000px hero image served to a 375px mobile viewport wastes bandwidth and parsing time. `next/image` eliminates this by generating multiple size variants.

**Lazy loading.** Images outside the viewport are not loaded until they approach the visible area. This is the native browser `loading="lazy"` attribute plus an IntersectionObserver polyfill for older browsers. The default for `next/image`.

**CLS prevention.** When you provide explicit `width` and `height` props (or use `fill` layout), the browser knows the image dimensions before it loads. This prevents layout shifts when the image loads — a Core Web Vitals signal.

**On-demand optimisation.** Next.js doesn't pre-generate all image variants at build time. It generates them on first request and caches them. This keeps build times fast but means the first request for each size/format variant hits the origin.

## How we configure it

In `next.config.ts`:

```ts
const nextConfig: NextConfig = {
  images: {
    formats: ['image/avif', 'image/webp'],
    deviceSizes: [390, 640, 828, 1080, 1200, 1920],
    imageSizes: [16, 32, 48, 64, 96, 128, 256],
    minimumCacheTTL: 86400,
    remotePatterns: [
      {
        protocol: 'https',
        hostname: '**.supabase.co',
        port: '',
        pathname: '/storage/v1/object/public/**',
      },
    ],
  },
};
```

We add AVIF as the preferred format — it's 20-40% smaller than WebP at equivalent quality, with good browser support (Chrome 85+, Firefox 93+, Safari 16+). We fall back to WebP for older browsers.

## The sizes prop: the most important thing to get right

The `sizes` prop tells the browser (and Next.js's `srcSet`) which image width to download at each viewport width. Getting this wrong is the most common `next/image` mistake:

```tsx
// Wrong: tells browser image is always full viewport width (100vw)
// This downloads a 1920px image on desktop even if the image is 600px wide
<Image src={src} alt={alt} width={600} height={400} />

// Correct: tells browser the actual rendered width at each breakpoint
<Image
  src={src}
  alt={alt}
  width={600}
  height={400}
  sizes="(max-width: 640px) 100vw, (max-width: 1024px) 50vw, 600px"
/>
```

The `sizes` value should match the CSS layout. If the image is full-width on mobile, half-width on tablet, and fixed 600px on desktop, say so exactly.

## The Marqet listing images

Listing portfolio images are the most image-heavy part of the platform. Each listing can have up to 8 images; they appear in search results as thumbnails and in listing detail as full-width images.

```tsx
// Listing card thumbnail
<Image
  src={imageUrl}
  alt={`${sellerName} portfolio example`}
  fill
  className="object-cover"
  sizes="(max-width: 640px) 50vw, (max-width: 1024px) 33vw, 25vw"
/>

// Listing detail hero
<Image
  src={imageUrl}
  alt={alt}
  width={800}
  height={600}
  priority={index === 0}
  sizes="(max-width: 768px) 100vw, 800px"
/>
```

The `priority` prop on the first image skips lazy loading and hints to the browser to preload it. For the above-fold hero image, this is correct — it's the LCP element and should load as fast as possible.

## When we bypass next/image

**SVG icons and illustrations.** SVG doesn't benefit from format conversion or size optimisation — it's already a vector format. We use `<img>` for SVGs.

**The solar system.** The homepage Three.js scene has no `<Image>` components — it's pure WebGL with Three.js textures loaded via `TextureLoader`. `next/image` doesn't apply to WebGL texture loading.

**Dynamically constructed image URLs.** Some Supabase storage URLs include transformation parameters (width, quality). Double-optimising — Next.js + Supabase transforms — can degrade quality. For these, we use `<img>` with the Supabase transformation parameters directly.

**Open Graph images.** OG images in `opengraph-image.tsx` use Next.js's ImageResponse API, not the Image component. These are rendered server-side and served as static images.

## The result

After implementing proper `sizes` props and AVIF format priority, the Marqet's listing pages went from an average LCP of 2.8s (on a 4G connection) to 1.6s. The change was entirely image optimisation — no code changes to the component logic.

The lesson: `next/image` with correct configuration is significant performance work that's free. The only cost is understanding it well enough to use it correctly.
