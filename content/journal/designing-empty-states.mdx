Empty states are easy to deprioritise. They're only visible to users who haven't yet done anything — and once users do something, the empty state disappears. It's tempting to treat them as an afterthought.

For AI products specifically, the empty state is one of the most consequential screens in the product. It's where the user forms their first impression of what the product can do, and whether they can use it.

## Why AI empty states are different

Traditional products handle empty states with a call-to-action: "Add your first project" or "Import your data." The action is simple, the outcome is clear.

AI products are harder. The value proposition depends on what the AI can do — which depends on what context the user provides — which the user doesn't know how to provide yet.

The empty state for an AI product isn't just "there's nothing here yet." It's "you haven't told me enough to help you yet." That's a fundamentally different kind of emptiness, and it requires a different design approach.

## The failure mode: blank chat input

The worst empty state for an AI product is a blank chat interface with no context. "Ask me anything" sounds capable but communicates nothing specific.

Users don't know what to ask. They don't know what the AI knows. They don't know what kind of questions produce good answers versus bad ones. They type something vague, get a vague answer, and leave unconvinced.

We made this mistake on The Hyve's first version. The AI agent's default state was an empty message input with the placeholder "What do you need?" After watching user sessions: almost everyone typed something generic, got a generic answer, and didn't return.

## The fix: opinionated empty states

The revision: we gave the empty state strong opinions. Instead of "ask me anything," we showed:

"I'm your AI team member. Here's where I can help right now: [bullet list of 4 specific things the agent can do given the current workspace state]"

The bullets weren't generic capabilities. They were specific to what the workspace contained. If the workspace had a product spec document, one bullet said: "Review the spec in [document name] for gaps and ambiguities." If there were recent messages in a channel, one said: "Summarise the decision we made yesterday about [topic]."

The result: users clicked the specific bullets rather than typing their own queries. The first interaction was productive. The return rate improved.

## Showing capability through examples

The second technique: show examples, not descriptions. Instead of "I can analyse your product data," show an example of what that looks like.

For Scoutr's empty state when no products have been scanned: we show a sample scan result for a fictional product. Not real data, but a realistic demonstration of what a scan output looks like — the fee breakdown, the margin estimate, the confidence indicators.

This does three things: it sets accurate expectations for what a scan looks like, it shows the level of detail the user will get, and it makes the "scan your first product" CTA immediately compelling because the user can see exactly what they'll get.

## Progressive disclosure of capability

Another approach: reveal capability progressively as the user provides context.

The Hyve's agent shows different suggested actions based on what's in the workspace. An empty workspace gets generic setup suggestions. A workspace with a product spec gets review-oriented suggestions. A workspace mid-sprint gets progress-tracking suggestions.

This prevents the empty state from feeling overwhelming. The user doesn't need to understand every capability on first load — they need to understand the one thing that's most useful right now.

## Handling the zero-data state for analytics features

For The Marqet's analytics features (click rates on listings, sales performance): the zero-data empty state shows a projected version of what the chart will look like after 30 days of data, with all values zeroed or estimated.

This does something important: it commits to what the feature will look like, before the user has done anything. The user understands what they're signing up for, which reduces the anxiety of "will this work for my situation."

## The ghost interface

A technique borrowed from native app design that works well for AI products: the ghost interface. Show a dimmed, skeleton version of the full product state, with real-seeming (but clearly example) data.

For Scoutr, the dashboard shows a ghost of what a populated scan history looks like — lists of products, margin estimates, trend lines — all in low-opacity, blurred-out form that makes clear it's sample data. The "scan your first product" button sits in the middle of this ghost.

Users consistently describe this as making the product feel more concrete. They can see what they're working toward.

## The principle

AI empty states should answer the question the user is really asking: "is this product going to be useful to me?" They don't know yet. The empty state's job is to give them enough evidence to believe the answer is yes, and enough specific direction to take a productive first action.

A blank interface says "figure it out yourself." An opinionated empty state says "here's exactly where to start."
