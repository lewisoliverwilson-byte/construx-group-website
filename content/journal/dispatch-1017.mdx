excerpt: "CockroachDB is a distributed SQL database that gives you PostgreSQL-compatible SQL with serializable isolation across multiple nodes and regions. The core property: every transaction is ACID, every write is replicated via Raft before it acknowledges, and every read sees a consistent snapshot — regardless of which node you talk to. This is the thing most distributed databases give up: DynamoDB, Cassandra, and most NewSQL databases allow eventual consistency or weaker isolation to achieve their throughput. CockroachDB keeps serializable isolation by using a hybrid logical clock (HLC) to order transactions across nodes and MVCC to handle concurrent reads and writes. The tradeoff is latency: a write that touches data in multiple regions incurs the round-trip to reach quorum. For globally distributed applications that need both SQL and strong consistency, CockroachDB is the primary option."

Distributed SQL. Raft replication. Serializable isolation. Geo-partitioning. MVCC.

## Schema and table creation

```sql
-- CockroachDB is PostgreSQL-wire-compatible
-- Connect with: cockroach sql --url "postgresql://construx@cockroach.storage.svc:26257/construx?sslmode=require"

-- Create the database
CREATE DATABASE IF NOT EXISTS construx;
USE construx;

-- Standard SQL table — same syntax as PostgreSQL
CREATE TABLE orders (
  id          UUID          DEFAULT gen_random_uuid() PRIMARY KEY,
  user_id     UUID          NOT NULL,
  status      VARCHAR(32)   NOT NULL DEFAULT 'pending',
  total_pence INT           NOT NULL CHECK (total_pence > 0),
  currency    CHAR(3)       NOT NULL DEFAULT 'GBP',
  created_at  TIMESTAMPTZ   NOT NULL DEFAULT now(),
  updated_at  TIMESTAMPTZ   NOT NULL DEFAULT now()
);

-- Index for common query pattern
CREATE INDEX idx_orders_user_status ON orders (user_id, status, created_at DESC);

-- Table with geo-partitioning: store EU orders on EU nodes, US orders on US nodes
-- Requires a region column in the primary key
CREATE TABLE orders_global (
  region      CRDB_INTERNAL_REGION AS (
                CASE
                  WHEN country_code IN ('GB','DE','FR','NL') THEN 'eu-west'
                  WHEN country_code IN ('US','CA')           THEN 'us-east'
                  ELSE 'eu-west'
                END
              ) STORED,
  id          UUID DEFAULT gen_random_uuid(),
  user_id     UUID NOT NULL,
  country_code CHAR(2) NOT NULL,
  total_pence INT NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (region, id)
) LOCALITY REGIONAL BY ROW;
-- LOCALITY REGIONAL BY ROW: each row is pinned to the region determined by `region` column
-- Reads from EU nodes for EU orders are local — no cross-region latency
```

## Transactions and serializable isolation

```python
import psycopg2
from psycopg2 import sql
import os

conn = psycopg2.connect(
    host='cockroach.storage.svc',
    port=26257,
    dbname='construx',
    user='construx_api',
    password=os.environ['COCKROACH_PASSWORD'],
    sslmode='require',
)

# CockroachDB transactions: serializable by default
# Retry on 40001 (serialization failure) — CockroachDB can abort transactions
# that conflict with concurrent writers

def execute_with_retry(conn, fn, max_retries=3):
    for attempt in range(max_retries):
        try:
            with conn.cursor() as cur:
                cur.execute("BEGIN")
                result = fn(cur)
                cur.execute("COMMIT")
                return result
        except psycopg2.errors.SerializationFailure:
            conn.rollback()
            if attempt == max_retries - 1:
                raise
        except Exception:
            conn.rollback()
            raise

def create_order(cur, user_id, items):
    # Insert the order
    cur.execute("""
        INSERT INTO orders (user_id, status, total_pence)
        VALUES (%s, 'pending', %s)
        RETURNING id
    """, (user_id, sum(i['price_pence'] for i in items)))
    order_id = cur.fetchone()[0]

    # Insert order items (same transaction — atomically consistent)
    for item in items:
        cur.execute("""
            INSERT INTO order_items (order_id, product_id, quantity, unit_price_pence)
            VALUES (%s, %s, %s, %s)
        """, (order_id, item['product_id'], item['quantity'], item['price_pence']))

    return order_id

order_id = execute_with_retry(conn, lambda cur: create_order(cur, user_id, items))

# Follower reads: read from the nearest replica (slightly stale — AS OF SYSTEM TIME)
# Useful for analytics queries that don't need real-time data
cur.execute("""
    SELECT count(*), sum(total_pence)
    FROM orders
    AS OF SYSTEM TIME follower_read_timestamp()
    WHERE status = 'completed'
      AND created_at > now() - INTERVAL '7 days'
""")
```

CockroachDB vs PostgreSQL vs PlanetScale vs Spanner: PostgreSQL on a single node is simpler, cheaper, and faster for workloads that fit on one machine — no distributed coordination overhead. PlanetScale (MySQL-compatible) shards horizontally but uses eventual consistency for cross-shard transactions. Spanner is Google's internal distributed SQL (available externally as Cloud Spanner) — similar guarantees to CockroachDB but tightly coupled to GCP. CockroachDB is the right choice when you need: SQL (not key-value), serializable isolation across nodes, horizontal scaling beyond a single machine, and cloud-neutral deployment. The operational cost is real — Raft replication, range splits, and distributed transaction coordination add complexity that PostgreSQL doesn't have. Only reach for CockroachDB when you've actually outgrown a single-node PostgreSQL.
