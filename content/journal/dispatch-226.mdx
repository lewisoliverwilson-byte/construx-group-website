All three Construx products use Next.js with the App Router. We started building after the App Router was stable (Next.js 14+) so we didn't have to migrate from the Pages Router. That said, the App Router introduced enough architectural changes that even starting fresh required deliberate adjustment.

Here's what required the most rethinking.

## The Server Components mental model

The biggest shift is the default rendering model. In the Pages Router, components were client-side React by default — they ran in the browser. In the App Router, components are Server Components by default — they run on the server at request time (or at build time for static pages).

Server Components:
- Can't use `useState`, `useEffect`, or browser APIs
- Can access the filesystem, databases, and environment variables directly
- Are never shipped to the client as JavaScript
- Are rendered to HTML on the server

Client Components (`'use client'`):
- Are standard React components — hooks work, browser APIs work
- Are hydrated in the browser
- Can't access server-side resources directly

The mistake we made early: thinking of `'use client'` as a file-level thing. In reality, adding `'use client'` to a component makes that component and all its children Client Components. If you put `'use client'` on a layout component, everything inside it becomes client-side.

The correct approach: keep the client boundary as low as possible. The outer layout is a Server Component. Only the interactive leaf nodes (the button that opens a modal, the form with state) are Client Components.

```tsx
// app/journal/page.tsx — Server Component
// Fetches data on the server, no JavaScript shipped
export default async function JournalPage() {
  const posts = getAllPostMeta(); // Runs on the server
  return <JournalList posts={posts} />;
}

// components/JournalList.tsx — Server Component
// Renders HTML, ships no JS for the list itself
export default function JournalList({ posts }: { posts: PostMeta[] }) {
  return (
    <div>
      {posts.map((post) => (
        <JournalItem key={post.slug} post={post} />
      ))}
    </div>
  );
}

// components/TagFilter.tsx — Client Component
'use client';
// This component needs state (active tag) and event handlers
export default function TagFilter() {
  const [activeTag, setActiveTag] = useState('all');
  // ...
}
```

## Layouts and nested layouts

The App Router's file-based routing includes layout files. A `layout.tsx` at any directory level wraps all routes in that directory.

```
app/
  layout.tsx          <- Wraps everything (html, body, nav, footer)
  journal/
    layout.tsx        <- Wraps all journal routes
    page.tsx          <- /journal
    [slug]/
      page.tsx        <- /journal/[slug]
```

The nested layout model means you can have a journal-specific layout (with the table of contents, reading progress bar, ByFlyline) without those components appearing on other pages. We use this for the journal slug page — components that should only appear on article pages live in `app/journal/[slug]/layout.tsx` (or are included directly in the page).

## Data fetching: async/await in components

In the App Router, Server Components can be `async`. Data fetching happens directly in the component function, without `useEffect` or lifecycle methods:

```tsx
// Pages Router — data fetching via getStaticProps
export async function getStaticProps({ params }) {
  const post = await getPost(params.slug);
  return { props: { post } };
}

export default function JournalPost({ post }) {
  return <article>{post.content}</article>;
}

// App Router — data fetching inline
export default async function JournalPostPage({ params }) {
  const { slug } = await params;
  const post = await getPost(slug);
  return <article>{post.content}</article>;
}
```

The async component pattern is cleaner. No separate data-fetching functions, no `props` threading. The component owns its data fetching directly.

## Static generation and `generateStaticParams`

For statically generated pages with dynamic routes (`/journal/[slug]`), the Pages Router used `getStaticPaths`. The App Router uses `generateStaticParams`:

```tsx
// Pages Router
export async function getStaticPaths() {
  const posts = getAllPostMeta();
  return {
    paths: posts.map((p) => ({ params: { slug: p.slug } })),
    fallback: false,
  };
}

// App Router
export async function generateStaticParams() {
  return getAllPostMeta().map((p) => ({ slug: p.slug }));
}
```

The App Router version is simpler — just return the params objects, no `paths` wrapper, no `fallback` configuration.

## The `params` Promise

In Next.js 15, `params` in page components is a `Promise`. This was a breaking change from Next.js 14 and required updates:

```tsx
// Next.js 14 — params was a plain object
export default function Page({ params }: { params: { slug: string } }) {
  const { slug } = params;
}

// Next.js 15 — params is a Promise
export default async function Page({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;
}
```

This tripped us up when upgrading. TypeScript caught the mismatch, which saved us from silent runtime bugs.

## What still feels awkward

**Client-server data passing.** When you need data in a Client Component that was fetched server-side, you have to pass it through props. No built-in streaming from server to client without SSE or similar.

**useSearchParams in Server Components.** Search params (`?tag=Build Log`) aren't available in Server Components at build time — only at request time. Pages that use search params can't be fully statically generated; they must be server-rendered.

**Error boundaries across the boundary.** Errors in Server Components and errors in Client Components are handled differently. Getting the error UX right requires understanding where in the rendering tree the error occurs.

The App Router is clearly the right direction for Next.js — Server Components are a genuine improvement for performance and bundle size. The adjustment period is real, and the mental model takes time to internalise. Three products in, it's become second nature.
