Most production applications eventually need work that happens outside a request-response cycle. Sending emails, processing uploads, running scheduled reports, retrying failed operations. Next.js doesn't have a first-class answer to this, which means you have to build or buy one.

Here's what we've converged on after trying multiple approaches.

## What "background job" means in practice

There are actually three distinct problems usually called "background jobs":

**Fire-and-forget:** start something that doesn't need to complete before the response. Send an analytics event, increment a counter, log something. Low stakes, tolerable data loss.

**Reliable processing:** work that must eventually happen, must not happen more than once, and requires retry on failure. User signup provisioning, payment reconciliation, email dispatch after a purchase.

**Scheduled work:** things that run on a clock. Daily digest emails, cache warming, stale data cleanup.

These three have different solutions.

## Fire-and-forget: `waitUntil`

For low-stakes async work in route handlers and Server Actions, Next.js 15 exposes `after()`:

```ts
import { after } from 'next/server';

export async function POST(req: Request) {
  const body = await req.json();
  const result = await processRequest(body);
  
  // Runs after the response is sent
  after(async () => {
    await logToAnalytics({ event: 'scan_completed', userId: body.userId });
    await updateUserStats(body.userId);
  });
  
  return Response.json(result);
}
```

`after()` runs after the response is sent, in the same process lifetime. Not durable — if the process dies, the work doesn't happen. Fine for analytics and cache updates. Not fine for billing or user provisioning.

## Reliable processing: database-backed queue

For work that must complete, we use the pattern from dispatch-262: a `webhook_events` style table that acts as a queue.

The same pattern generalises to any reliable processing:

```sql
CREATE TABLE job_queue (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  type        TEXT NOT NULL,         -- 'provision_workspace', 'send_email'
  payload     JSONB NOT NULL,
  scheduled_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  processed_at TIMESTAMPTZ,
  status      TEXT NOT NULL DEFAULT 'pending',
  attempts    INTEGER NOT NULL DEFAULT 0,
  max_attempts INTEGER NOT NULL DEFAULT 3,
  error       TEXT
);

CREATE INDEX ON job_queue (status, scheduled_at) 
  WHERE status IN ('pending', 'failed');
```

Jobs are inserted transactionally with the business operation:

```ts
// In a transaction: create the user AND queue their welcome email
await db.transaction(async (tx) => {
  const [user] = await tx.insert(users).values({ email, name }).returning();
  
  await tx.insert(jobQueue).values({
    type: 'send_welcome_email',
    payload: { userId: user.id, email, name },
  });
});
```

The transactional insertion is the key pattern: either both the user and the job exist, or neither does. No user without a queued email, no job without a user.

## The processor: Vercel Cron

Vercel (and by extension Amplify) supports cron jobs via a `vercel.json` configuration. We run a processor every minute:

```json
{
  "crons": [
    {
      "path": "/api/jobs/process",
      "schedule": "* * * * *"
    }
  ]
}
```

The `/api/jobs/process` route picks up pending jobs:

```ts
export async function GET(req: Request) {
  // Verify this is an internal cron call, not a public request
  const authHeader = req.headers.get('authorization');
  if (authHeader !== `Bearer ${process.env.CRON_SECRET}`) {
    return new Response('Unauthorized', { status: 401 });
  }

  const jobs = await db
    .select()
    .from(jobQueue)
    .where(
      and(
        eq(jobQueue.status, 'pending'),
        lt(jobQueue.attempts, jobQueue.maxAttempts),
        lte(jobQueue.scheduledAt, new Date()),
      )
    )
    .limit(20)
    .for('update', { skipLocked: true });

  const results = await Promise.allSettled(
    jobs.map((job) => processJob(job))
  );

  return Response.json({ processed: jobs.length });
}
```

## Scheduled work: also Vercel Cron

Scheduled tasks use the same mechanism but with appropriate cron expressions:

```json
{
  "crons": [
    { "path": "/api/cron/daily-digest",    "schedule": "0 8 * * *" },
    { "path": "/api/cron/warm-cache",      "schedule": "*/15 * * * *" },
    { "path": "/api/cron/cleanup-expired", "schedule": "0 0 * * *" }
  ]
}
```

Each cron route is a standard route handler, authenticated with `CRON_SECRET`, doing whatever the scheduled work requires.

## What we don't use

**BullMQ / Redis queues:** More operationally complex than a Postgres table for our current job volume. A Postgres queue handles tens of thousands of jobs per minute — we're nowhere near that limit.

**Inngest / Trigger.dev / Quirrel:** Purpose-built job queue services with better observability and retry UI. Evaluated Inngest — liked it, but the marginal complexity of a third-party dependency wasn't worth it at our volume. We'll reconsider when we have more job types and higher throughput.

**Serverless background functions:** AWS Lambda invocations, Vercel Edge Functions with streaming. More operational overhead than cron + Postgres.

The decision framework: a database-backed queue with a cron processor handles 95% of background job needs without adding operational dependencies. The codebase stays simpler, the job history is queryable alongside everything else, and the failure surface is smaller.

When we need sub-minute latency on job processing, or job throughput that saturates a cron-per-minute cycle, we'll graduate to a proper queue service. That threshold is higher than most two-person teams expect.
