date: "2033-12-27"
excerpt: "Cluster API (CAPI) is a Kubernetes project that brings the Kubernetes declarative API model to cluster lifecycle management — provisioning, upgrading, and deleting Kubernetes clusters using the same kubectl and GitOps workflows you use to manage workloads. You define a Cluster, a ControlPlane, MachineDeployments, and MachineTemplatse as Kubernetes CRDs in a management cluster; CAPI reconciles those objects against the actual cluster state by calling out to infrastructure providers (AWS, Azure, GCP, vSphere, OpenStack, Talos via CAPT) via provider-specific CRDs. The management cluster runs the CAPI controllers and provider controllers; workload clusters are the clusters being managed. CAPI handles the full lifecycle: bootstrap (generating kubeadm configs or Talos machine configs), infrastructure provisioning (VMs, load balancers, security groups), joining worker nodes, and rolling upgrades (new MachineDeployment rolling update replaces each node with a new one running the target Kubernetes version). At Construx, CAPI manages all Kubernetes cluster infrastructure as GitOps-controlled YAML in a dedicated management cluster — adding a new workload cluster is a git commit, and all clusters upgrade on the same rolling schedule controlled by a single PR."

## Cluster API manifests and cluster provisioning

```yaml
# CAPI cluster definition: AWS provider (CAPA — Cluster API Provider AWS)
# Applied to the management cluster — CAPI controllers reconcile and provision

# AWSCluster: infrastructure layer (VPC, subnets, load balancer, security groups)
apiVersion: infrastructure.cluster.x-k8s.io/v1beta2
kind: AWSCluster
metadata:
  name: construx-prod-eu-west-2
  namespace: capi-clusters
spec:
  region: eu-west-2
  sshKeyName: construx-k8s-nodes
  network:
    vpc:
      cidrBlock: 10.0.0.0/16
    subnets:
      - availabilityZone: eu-west-2a
        cidrBlock:        10.0.1.0/24
        isPublic:         false
      - availabilityZone: eu-west-2b
        cidrBlock:        10.0.2.0/24
        isPublic:         false
      - availabilityZone: eu-west-2c
        cidrBlock:        10.0.3.0/24
        isPublic:         false
  controlPlaneLoadBalancer:
    scheme: internet-facing

---
# Cluster: logical cluster (references AWSCluster and KubeadmControlPlane)
apiVersion: cluster.x-k8s.io/v1beta1
kind: Cluster
metadata:
  name: construx-prod-eu-west-2
  namespace: capi-clusters
spec:
  clusterNetwork:
    pods:
      cidrBlocks: ["10.244.0.0/16"]
    services:
      cidrBlocks: ["10.96.0.0/12"]
  controlPlaneRef:
    apiVersion: controlplane.cluster.x-k8s.io/v1beta1
    kind: KubeadmControlPlane
    name: construx-prod-eu-west-2-cp
  infrastructureRef:
    apiVersion: infrastructure.cluster.x-k8s.io/v1beta2
    kind: AWSCluster
    name: construx-prod-eu-west-2

---
# KubeadmControlPlane: 3 control plane nodes with HA
apiVersion: controlplane.cluster.x-k8s.io/v1beta1
kind: KubeadmControlPlane
metadata:
  name: construx-prod-eu-west-2-cp
  namespace: capi-clusters
spec:
  replicas: 3
  version: v1.31.2
  machineTemplate:
    infrastructureRef:
      apiVersion: infrastructure.cluster.x-k8s.io/v1beta2
      kind: AWSMachineTemplate
      name: construx-prod-eu-west-2-cp-template
  kubeadmConfigSpec:
    initConfiguration:
      nodeRegistration:
        kubeletExtraArgs:
          cloud-provider: external
    clusterConfiguration:
      apiServer:
        extraArgs:
          oidc-issuer-url: https://dex.construx.internal
          oidc-client-id: kubernetes
    joinConfiguration:
      nodeRegistration:
        kubeletExtraArgs:
          cloud-provider: external
  rolloutStrategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1

---
# MachineDeployment: worker node pool
apiVersion: cluster.x-k8s.io/v1beta1
kind: MachineDeployment
metadata:
  name: construx-prod-eu-west-2-workers
  namespace: capi-clusters
spec:
  clusterName: construx-prod-eu-west-2
  replicas: 6
  template:
    spec:
      version: v1.31.2
      clusterName: construx-prod-eu-west-2
      bootstrap:
        configRef:
          apiVersion: bootstrap.cluster.x-k8s.io/v1beta1
          kind: KubeadmConfigTemplate
          name: construx-prod-eu-west-2-workers
      infrastructureRef:
        apiVersion: infrastructure.cluster.x-k8s.io/v1beta2
        kind: AWSMachineTemplate
        name: construx-prod-eu-west-2-worker-template
  strategy:
    rollingUpdate:
      maxSurge: 1          # one extra node created before deleting old one
      maxUnavailable: 0    # zero unavailable during rolling upgrade

---
# AWSMachineTemplate: EC2 instance specification for workers
apiVersion: infrastructure.cluster.x-k8s.io/v1beta2
kind: AWSMachineTemplate
metadata:
  name: construx-prod-eu-west-2-worker-template
  namespace: capi-clusters
spec:
  template:
    spec:
      instanceType:    m6i.2xlarge
      iamInstanceProfile: nodes.cluster-api-provider-aws.sigs.k8s.io
      sshKeyName:      construx-k8s-nodes
      rootVolume:
        size: 100
        type: gp3
      ami:
        id: ami-0a1b2c3d4e5f6a7b8   # Ubuntu 22.04 EKS-optimised AMI
```

```bash
# clusterctl: CAPI management CLI

# Initialise management cluster with AWS provider
clusterctl init --infrastructure aws

# Get cluster status
kubectl get cluster -n capi-clusters
# NAME                         PHASE         AGE  VERSION
# construx-prod-eu-west-2      Provisioned   14d  v1.31.2

# Get machine health
kubectl get machines -n capi-clusters
# NAME                                CLUSTER                      NODENAME            PHASE    VERSION
# construx-prod-eu-west-2-cp-0        construx-prod-eu-west-2      ip-10-0-1-42        Running  v1.31.2
# construx-prod-eu-west-2-cp-1        construx-prod-eu-west-2      ip-10-0-2-18        Running  v1.31.2
# construx-prod-eu-west-2-cp-2        construx-prod-eu-west-2      ip-10-0-3-29        Running  v1.31.2
# construx-prod-eu-west-2-workers-x7  construx-prod-eu-west-2      ip-10-0-1-77        Running  v1.31.2

# Upgrade a cluster: bump version in KubeadmControlPlane and MachineDeployment
kubectl patch kubeadmcontrolplane construx-prod-eu-west-2-cp \
  -n capi-clusters \
  --type merge \
  --patch '{"spec":{"version":"v1.32.0"}}'
# CAPI begins rolling control plane upgrade automatically

# Retrieve kubeconfig for workload cluster
clusterctl get kubeconfig construx-prod-eu-west-2 -n capi-clusters > kubeconfig-prod.yaml
```

CAPI vs EKS managed nodegroups vs Rancher vs plain Terraform for clusters: Terraform + AWS provider can provision EKS clusters and node groups, but Terraform is not a continuous reconciliation loop — if someone manually modifies a node group outside Terraform, the drift is not corrected until the next `terraform apply`. CAPI runs a controller that continuously reconciles declared state vs actual state, just like every other Kubernetes controller. EKS managed node groups handle OS patching and node replacement automatically but are AWS-specific and have less flexibility for network/OS configuration than self-managed CAPI clusters. Rancher provides a multi-cluster management UI with its own provisioning engine (RKE2 or K3s based) — easier to get started with for teams not already using GitOps, but less native to the Kubernetes ecosystem. CAPI's advantage is its pure Kubernetes-native API: cluster definitions are YAML, cluster management uses kubectl and GitOps, and the same RBAC and policy tooling (Kyverno, OPA) applies to cluster management as to workload management. For organisations managing more than five clusters with strict GitOps requirements, CAPI is the architecture.
