Open-source dependencies are the infrastructure of modern software. Every npm install pulls in dozens of packages, each with its own security posture, maintenance status, and breaking change history. Managing this at scale is a discipline; most small teams do it reactively, which means the first sign of a problem is a security vulnerability or a broken build.

Here's our approach.

## The dependency philosophy

We treat dependencies as infrastructure, not resources. A dependency that's insecure, unmaintained, or abandoned is a liability, not a free feature.

The principles:

**Prefer well-maintained packages.** Before adding a dependency, we check: when was the last commit? How many open issues are there? Is the maintainer actively engaged? A package with 400 open issues and the last commit 18 months ago is a dependency we'd rather not take on.

**Prefer fewer dependencies.** Every dependency is code we don't control but are responsible for. A function that could be written in 10 lines doesn't need a package. We've removed packages and replaced them with small utility functions when the utility was narrow enough.

**Prefer packages that do one thing.** Large, all-in-one packages (full UI component libraries, monolithic utility packages) are harder to replace when they have problems and often include features we don't use. Focused, single-purpose packages are easier to reason about and replace.

## The update cadence

We run dependency updates on a monthly schedule:

```bash
npm outdated          # See what's behind
npm audit             # Check for known vulnerabilities
npx npm-check-updates # Interactive update tool
```

Monthly updates have two benefits over continuous updating: they're predictable (we know when updates happen), and they batch the testing cost (one review session per month rather than per update).

The exception: security vulnerabilities with CRITICAL or HIGH severity get patched immediately. `npm audit` with CVE scores above 7.0 → fix the same day.

## Handling breaking changes

Major version bumps (1.x → 2.x) often include breaking changes. Our process for major version upgrades:

1. Read the changelog or migration guide for the new version
2. Check if any APIs we use have changed
3. Create a branch and upgrade in isolation
4. Run the TypeScript type check (`npx tsc --noEmit`) — breaking API changes often produce type errors
5. Run the build (`npm run build`)
6. Test the affected features manually
7. Merge if everything passes

Next.js major version upgrades deserve particular care — the Next.js ecosystem evolves quickly, and library compatibility can lag. We check the Next.js compatibility notes for each library we use before upgrading Next.js itself.

## The lock file

We commit `package-lock.json` (npm) or `yarn.lock` to the repository. This ensures that CI builds and production deployments use exactly the same dependency versions we tested with.

Not committing the lock file means `npm install` on a fresh machine resolves to the latest minor/patch versions of all transitive dependencies — which might differ from what we developed and tested with. A transitive dependency update that breaks a feature would be very hard to diagnose.

## Security audit automation

We've added `npm audit --audit-level=high` to our Amplify build pipeline:

```yaml
# In amplify.yml preBuild
commands:
  - npm ci
  - npm audit --audit-level=high  # Fail build if HIGH or CRITICAL vulnerabilities found
  - npm run build
```

This fails the build if any HIGH or CRITICAL security vulnerabilities are present in the dependency tree. It's a safety net — catching vulnerabilities before production, not after.

The practical effect: we've had three build failures from security vulnerabilities. In each case, the fix was a minor version upgrade of the vulnerable package. The build failure was the correct signal.

## Pruning unused dependencies

Quarterly, we run a check for unused dependencies:

```bash
npx depcheck
```

Depcheck identifies packages in `package.json` that aren't actually imported anywhere in the codebase. These accumulate as features are removed or refactored.

Removing unused dependencies reduces bundle size, reduces the attack surface, and makes the dependency tree easier to understand. We've removed 12 unused packages across the three products over the past six months.

## The transitive dependency reality

When you install a package, you install all of its dependencies too — and their dependencies, recursively. A Next.js project with 30 direct dependencies might have 400 transitive dependencies. You're responsible for all of them.

This is sobering and mostly manageable. The npm audit system tracks known vulnerabilities across the entire dependency tree. Keeping direct dependencies current generally keeps transitive dependencies in a reasonable state.

What you can't control: a transitive dependency that becomes abandoned or compromised without a security advisory. This is rare but real (the left-pad incident, the event-stream incident). The mitigations are: prefer well-maintained direct dependencies, monitor security feeds, and don't use packages from unknown maintainers for critical paths.
