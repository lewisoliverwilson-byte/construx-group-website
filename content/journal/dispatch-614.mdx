Before `satisfies`, you had two options when defining a typed object:

1. Annotate with the type: type checking works, but the inferred type is widened to the annotation
2. No annotation: the literal type is preserved, but there's no type checking

`satisfies` gives you both: type checking at the definition site, narrow inferred type at the use site.

## The problem

```ts
type Route = {
  path:    string;
  method:  'GET' | 'POST' | 'PUT' | 'DELETE';
  handler: (req: Request) => Response;
};

// Option 1: type annotation — type checking works, but type is widened
const postsRoute: Route = {
  path:    '/api/posts',
  method:  'GET',
  handler: (req) => new Response(),
};

// postsRoute.method is inferred as 'GET' | 'POST' | 'PUT' | 'DELETE'
// Not as 'GET' — the literal type is lost

// Option 2: no annotation — literal type is preserved, no type checking
const postsRoute2 = {
  path:    '/api/posts',
  method:  'GET' as const,
  handler: (req: Request) => new Response(),
};

// postsRoute2.method is 'GET' — preserved
// But no error if you typo 'GETT'
```

## satisfies: best of both

```ts
const postsRoute = {
  path:    '/api/posts',
  method:  'GET',
  handler: (req: Request) => new Response(),
} satisfies Route;

// postsRoute.method is inferred as 'GET' — literal type preserved
// TypeScript also checks the object conforms to Route — method must be a valid HTTP verb
```

A typo is caught:

```ts
const badRoute = {
  path:    '/api/posts',
  method:  'GETT',  // TS error: Type '"GETT"' is not assignable to type '"GET" | "POST" | ...
} satisfies Route;
```

## Practical: configuration objects

```ts
type Config = {
  db:    { host: string; port: number; name: string };
  redis: { host: string; port: number };
  smtp:  { host: string; port: number; secure: boolean };
};

const config = {
  db:    { host: 'localhost', port: 5432, name: 'construx' },
  redis: { host: 'localhost', port: 6379 },
  smtp:  { host: 'smtp.resend.com', port: 465, secure: true },
} satisfies Config;

// config.db.port is number — works normally
// config.smtp.secure is boolean — works normally
// TypeScript validates all fields exist and have correct types
```

Without `satisfies`:

```ts
const config: Config = { ... };
// config.db.host is string — fine
// config.db.port is number — fine, but no literal info
```

The difference matters when you extract values and use them in switch statements or template literals — the literal type gives you exhaustiveness checking.

## Practical: discriminated union narrowing

```ts
type Action =
  | { type: 'increment'; by: number }
  | { type: 'decrement'; by: number }
  | { type: 'reset' };

const actions = [
  { type: 'increment', by: 1 },
  { type: 'decrement', by: 2 },
  { type: 'reset' },
] satisfies Action[];

// actions[0].type is 'increment' — literal type preserved
// TypeScript validates each element conforms to Action

// Without satisfies:
const actionsAnnotated: Action[] = [...];
// actionsAnnotated[0].type is 'increment' | 'decrement' | 'reset'
// Literal type is lost — narrowing downstream is harder
```

## Practical: palette / enum-like objects

```ts
const palette = {
  construx: '#F97316',
  cyan:     '#67e8f9',
  purple:   '#a78bfa',
  green:    '#4ade80',
  amber:    '#fbbf24',
} satisfies Record<string, `#${string}`>;

// palette.construx is '#F97316' — literal
// TypeScript checks all values start with '#'

type PaletteKey = keyof typeof palette;
// 'construx' | 'cyan' | 'purple' | 'green' | 'amber'
// Exact keys, not widened to string
```

If you used `const palette: Record<string, string>`, `PaletteKey` would be `string` — useless.

## When to use satisfies vs type annotation

Use `satisfies` when:
- You need type checking on an object/array literal
- You also need to use the literal types of properties downstream
- You're defining configuration, route tables, style maps, or any value where the specific literal matters

Use a type annotation when:
- You want to explicitly widen the type (e.g., `const method: string = 'GET'`)
- You're assigning to a variable that will be reassigned
- The literal type doesn't matter downstream

Use `as const` when:
- You want the deepest possible literal types (`readonly`, tuple types, etc.)
- There's no type to check against

In practice, `satisfies` is the right choice for most configuration objects and data tables in a TypeScript codebase.
