"Mobile-first" has become a default instruction in web development that's often applied without thinking about whether it's the right approach for the specific product.

Mobile-first originated as a response to the web development practice of building for desktop and then "making it responsive" as an afterthought. The insight: designing for constraints (small screen, touch interaction, slow network) first produces better designs for all screen sizes.

Here's how we apply this principle — and where we deliberately don't.

## Usage patterns for professional tools

Scoutr is used by eBay resellers during their sourcing workflow. The sourcing workflow typically happens in physical retail environments — in a supermarket aisle, at a charity shop, in a discount store. These users are mobile-first by necessity.

The Marqet is used by buyers looking for professional services. Service buying typically happens at a desk, where buyers are evaluating multiple listings, reading detailed descriptions, and making considered purchases. Desktop usage dominates.

The Hyve is used by teams communicating and working together. Like Slack, which The Hyve is inspired by, desktop usage predominates for longer work sessions; mobile is used for checking in and quick responses.

**Implication:** Mobile-first isn't a blanket policy for all three products. We apply it where the usage pattern warrants it (Scoutr), and we apply desktop-first for products where that's the primary context (The Marqet's listing detail, The Hyve's channel view).

## Scoutr: genuinely mobile-first

Scoutr's primary use case — scanning a product in a physical store — happens on a phone. The core flow (paste URL or scan barcode, get analysis, make purchase decision) must work perfectly on mobile.

Our mobile-first implementation for Scoutr's scan interface:
- Input field: full-width, large touch target (48px height minimum)
- Result presentation: single-column, vertically stacked
- Confidence score: large, prominently displayed, interpretable at a glance
- Action buttons: bottom-anchored on mobile for thumb reach
- Loading state: skeleton UI rather than spinner (preserves layout)

The desktop view of Scoutr's scan results adds a side panel with historical analysis and comparable sold listings. The mobile view presents the essential confidence score and margin estimate prominently, with detailed data accessible via expandable sections.

## The group website: both

This website is a mix of content types:
- Journal posts: read on any device, mobile reading is common
- Marketing pages: both device types
- The solar system: desktop-first (Three.js 3D on mobile is battery-intensive)

We made explicit decisions per page section rather than applying a blanket policy.

The journal post page is mobile-responsive with readable type (16px base, 1.7 line height), appropriate content width (650-700px max on desktop, full-width on mobile with horizontal padding), and a reading progress bar that works on both.

The solar system has a fallback: on mobile, we show the static brand mark and a simplified hero rather than the Three.js animation. This is both a performance decision and a design decision — the solar system doesn't add much to the mobile experience.

## Tailwind's mobile-first classes

Tailwind uses mobile-first breakpoints by default. Unprefixed classes apply to all screen sizes; prefixed classes (sm:, md:, lg:) apply at and above the breakpoint.

```tsx
<div className="
  flex flex-col          // mobile: vertical stack
  sm:flex-row            // tablet+: horizontal row
  gap-4                  // always: 16px gap
  px-4 sm:px-8 lg:px-16 // padding scales with screen size
">
```

This is the right direction for most components: start with the mobile layout, progressively enhance for larger screens.

The exception: components where the mobile version is a significant simplification of the desktop version. In these cases, we sometimes write the desktop layout first (it's easier to reason about) and then apply mobile overrides. Not ideal, but sometimes pragmatic.

## The 320px problem

We test down to 320px width (iPhone SE, older Android phones). Many developers test on iPhone 14 Pro (390px) and declare the site mobile-friendly. At 320px, several common patterns break:

- Long words that don't break (`overflow-wrap: break-word` or `word-break: break-word` is necessary for dispatch titles)
- Flex rows with multiple items that overflow
- Fixed-width elements that extend beyond the viewport

We run a manual 320px test before every major UI deployment. It consistently catches issues that would otherwise be discovered by users.

## Font size on mobile

WCAG recommends 16px minimum for body text. We use 16px (`text-base` in Tailwind) for body text in journal posts and product copy. UI chrome elements (labels, timestamps, metadata) use smaller sizes (10-12px) where the density serves the design.

The gotcha: iOS will auto-zoom any text input where the font size is below 16px. This produces a jarring zoom-in effect when the user taps the input. We set all input font sizes to 16px, even when the surrounding text is smaller:

```css
input, textarea, select {
  font-size: 16px; /* Prevent iOS auto-zoom */
}
```

This is one of those details that's easy to miss and immediately noticed by iPhone users.
