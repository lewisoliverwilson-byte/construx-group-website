date: "2033-10-04"
excerpt: "Apache Pulsar is a distributed messaging and streaming platform that separates the serving layer (brokers) from the storage layer (BookKeeper). Unlike Kafka, where partitions are pinned to specific brokers and rebalancing requires data movement, Pulsar brokers are stateless — they own topics temporarily and hand them off with no data movement on broker failure or cluster scale. BookKeeper stores the message ledgers, distributed across bookie nodes with configurable acknowledgement quorum and write quorum. This architecture lets Pulsar scale brokers and storage independently. Pulsar has native multi-tenancy: tenants, namespaces, and topics form a three-level hierarchy, with quotas, policies, and authentication applied at each level. Geo-replication between Pulsar clusters is built-in: declare a replicated namespace and messages published to the Paris cluster appear automatically in the London and Tokyo clusters. Pulsar's tiered storage offloads old ledger segments to object storage (S3, GCS) automatically, keeping the BookKeeper cluster small while retaining unlimited message history. The Pulsar Functions runtime runs lightweight stateful processing functions (filter, transform, enrich) co-located with the broker, without requiring a separate Flink or Spark deployment."

## Pulsar deployment and topic configuration

```bash
# Pulsar standalone (dev mode — all components in one process)
docker run -d -p 6650:6650 -p 8080:8080 apachepulsar/pulsar:3.3.1 \
  bin/pulsar standalone

# Production: separate broker and BookKeeper tiers via Helm
helm repo add apache https://pulsar.apache.org/charts
helm install pulsar apache/pulsar \
  --namespace pulsar \
  --create-namespace \
  --set initialize=true \
  --set bookkeeper.replicaCount=3 \
  --set broker.replicaCount=3 \
  --set proxy.replicaCount=2 \
  --set zookeeper.replicaCount=3 \
  --version 3.3.1

# Create tenant and namespace hierarchy
bin/pulsar-admin tenants create construx \
  --admin-roles construx-admin \
  --allowed-clusters eu-west-2,us-east-1

bin/pulsar-admin namespaces create construx/events \
  --clusters eu-west-2,us-east-1 \   # geo-replicated to both clusters
  --retention-time 7d \
  --retention-size 50G

# Create a persistent topic with 12 partitions
bin/pulsar-admin topics create-partitioned-topic \
  persistent://construx/events/order-placed \
  --partitions 12

# Topic stats
bin/pulsar-admin topics stats persistent://construx/events/order-placed
# {
#   "msgRateIn":       8421.3,
#   "msgRateOut":      8419.1,
#   "msgThroughputIn": 4214288.0,   // bytes/s
#   "storageSize":     184221840384,
#   "publishers":      3,
#   "subscriptions":   2
# }
```

## Producers, consumers, and geo-replication

```python
# Python client: producer and consumer

import pulsar

client = pulsar.Client('pulsar://pulsar-proxy.construx.internal:6650')

# Producer: publish to partitioned topic
producer = client.create_producer(
    'persistent://construx/events/order-placed',
    producer_name       = 'order-service-producer',
    send_timeout_millis = 3000,
    compression_type    = pulsar.CompressionType.ZSTD,
    batching_enabled    = True,
    batching_max_messages          = 1000,
    batching_max_publish_delay_ms  = 5,
)

producer.send(
    b'{"order_id": "ord_abc123", "tenant_id": "t_42", "amount": 149.99}',
    partition_key = 't_42',    # route to same partition for tenant
)

# Consumer: exclusive subscription (single consumer per subscription)
consumer = client.subscribe(
    'persistent://construx/events/order-placed',
    subscription_name     = 'payments-processor',
    consumer_type         = pulsar.ConsumerType.Shared,  # multiple consumers
    receiver_queue_size   = 1000,
    dead_letter_policy    = pulsar.DeadLetterPolicy(
        max_redeliver_count   = 5,
        dead_letter_topic     = 'persistent://construx/events/order-placed-dlq',
    ),
)

while True:
    msg = consumer.receive(timeout_millis=5000)
    try:
        process(msg.data())
        consumer.acknowledge(msg)
    except Exception:
        consumer.negative_acknowledge(msg)   # triggers redelivery
```

Apache Pulsar vs Apache Kafka vs RabbitMQ vs Redpanda: Kafka (and Redpanda, its C++ reimplementation) couple brokers to storage — each partition has a designated leader broker that owns the log segment files. Broker failure requires partition leader election and in-flight rebalancing. Pulsar's stateless brokers can take over topics instantly because the ledger data lives in BookKeeper. The practical implication: Pulsar handles broker failure and cluster scaling more gracefully at the cost of BookKeeper's added operational complexity (you're running two layers instead of one). Kafka's ecosystem maturity (Kafka Connect, Kafka Streams, the Flink-Kafka integration, the KSQL tooling) is significantly deeper — most organisations reach for Kafka first. Pulsar is the right choice when you need built-in multi-tenancy (multiple teams sharing one cluster with strict quota isolation), built-in geo-replication (without MirrorMaker 2 setup), or tiered storage without separate archival infrastructure. RabbitMQ is a traditional message broker (AMQP) optimised for task queues and low-latency routing, not high-throughput streaming. Redpanda (covered in dispatch-1058) is the fastest Kafka-compatible option for teams that want Kafka API compatibility with lower JVM overhead.
