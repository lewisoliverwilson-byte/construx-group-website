title: "Flux CD: pull-based GitOps with source, Helm, and image automation controllers"
date: "2033-01-01"
excerpt: "Flux is a CNCF GitOps toolkit composed of independent controllers: Source Controller watches git repos and OCI registries for changes, Kustomize Controller applies manifests to the cluster, Helm Controller manages Helm releases, and Image Automation Controller updates image tags in git when new images are pushed. Each controller is a separate deployment — you install only what you need. Flux is entirely pull-based: the cluster watches git, not the other way around. The Image Automation Controller is Flux's strongest differentiator — it creates a closed CD loop: a new image push triggers a tag update in git, which Flux then applies to the cluster, without any external CI system needing cluster credentials."
author: "Lewis Wilson"

Pull-based. Source, Kustomize, Helm, Image controllers. Image automation closes the CD loop.

## Bootstrap and GitOps flow

```bash
# Install Flux CLI
curl -s https://fluxcd.io/install.sh | bash
flux version
# flux: v2.4.0

# Bootstrap: install Flux into the cluster and connect it to a git repo
flux bootstrap github \
  --owner=construx \
  --repository=fleet-infra \
  --branch=master \
  --path=clusters/prod-eu \
  --personal \
  --token-auth

# What bootstrap created in the fleet-infra repo:
# clusters/prod-eu/flux-system/
#   gotk-components.yaml       ← all Flux controllers
#   gotk-sync.yaml             ← points Flux at this repo

# From this point: everything goes through git
# Push to clusters/prod-eu/ → Flux applies it within 1 minute

# Check Flux health
flux check
# ✔ Kubernetes 1.31.2 >=1.28.0-0
# ✔ source-controller:         v1.4.1
# ✔ kustomize-controller:      v1.4.0
# ✔ helm-controller:           v1.1.0
# ✔ notification-controller:   v1.4.0
# ✔ image-reflector-controller: v0.33.0
# ✔ image-automation-controller: v0.39.0

# Get the status of all Flux resources
flux get all --all-namespaces
```

## GitRepository and Kustomization

```yaml
# Add a new application to manage:
# 1. Create a GitRepository pointing at the app's manifests
# 2. Create a Kustomization that applies them

# clusters/prod-eu/construx-api/source.yaml
apiVersion: source.toolkit.fluxcd.io/v1
kind: GitRepository
metadata:
  name: construx-api
  namespace: flux-system
spec:
  interval: 1m
  url: https://github.com/construx/construx-api
  ref:
    branch: master
  secretRef:
    name: github-token

---
# clusters/prod-eu/construx-api/kustomization.yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: construx-api
  namespace: flux-system
spec:
  interval: 5m                # re-apply every 5 min even without git changes
  retryInterval: 1m
  timeout: 3m
  prune: true                 # delete resources removed from git
  sourceRef:
    kind: GitRepository
    name: construx-api
  path: ./k8s/overlays/production
  healthChecks:
    - apiVersion: apps/v1
      kind: Deployment
      name: construx-api
      namespace: construx-prod
  # Variable substitution: replace ${CLUSTER_ENV} in manifests
  postBuild:
    substituteFrom:
      - kind: ConfigMap
        name: cluster-vars
```

```bash
# Push the new files to fleet-infra
git add clusters/prod-eu/construx-api/
git commit -m "feat: add construx-api gitops config"
git push

# Flux detects the change within 1 minute and applies it
flux get kustomizations --watch
# NAME          READY  STATUS
# construx-api  True   Applied revision: master/abc1234

# Manual reconciliation (don't wait for the interval)
flux reconcile source git construx-api
flux reconcile kustomization construx-api

# Suspend reconciliation (during incident, manual override needed)
flux suspend kustomization construx-api
# ... manual kubectl apply or patch ...
flux resume kustomization construx-api
```

## Helm Controller

```yaml
# Helm releases managed by Flux (declarative, version-locked)

# HelmRepository: add a chart repository
apiVersion: source.toolkit.fluxcd.io/v1
kind: HelmRepository
metadata:
  name: construx-charts
  namespace: flux-system
spec:
  interval: 1h
  url: https://charts.construx.io

---
# HelmRelease: declare a Helm release
apiVersion: helm.toolkit.fluxcd.io/v2
kind: HelmRelease
metadata:
  name: construx-api
  namespace: construx-prod
spec:
  interval: 5m
  chart:
    spec:
      chart: construx-api
      version: ">=1.8.0 <2.0.0"    # semver constraint — auto-upgrades within range
      sourceRef:
        kind: HelmRepository
        name: construx-charts
        namespace: flux-system

  values:
    replicaCount: 3
    autoscaling:
      enabled: true
      minReplicas: 3
      maxReplicas: 20

  valuesFrom:
    - kind: Secret
      name: construx-api-helm-values  # merge additional values from a Secret
      optional: true

  # Automated rollback on upgrade failure
  upgrade:
    remediation:
      retries: 3
      remediateLastFailure: true   # rollback to last good state
  rollback:
    cleanupOnFail: true
    timeout: 5m
```

## Image Automation — closed CD loop

```yaml
# The full automated image promotion workflow:
# 1. CI builds and pushes image → registry.construx.io/construx/api:v1.8.4
# 2. ImageRepository detects the new tag
# 3. ImagePolicy selects it (semver: >=1.8.0 <2.0.0)
# 4. ImageUpdateAutomation commits the new tag to git
# 5. GitRepository detects the commit
# 6. Kustomization/HelmRelease applies the updated manifest
# 7. Cluster runs v1.8.4 — no human intervention

apiVersion: image.toolkit.fluxcd.io/v1beta2
kind: ImageRepository
metadata:
  name: construx-api
  namespace: flux-system
spec:
  image: registry.construx.io/construx/api
  interval: 5m

---
apiVersion: image.toolkit.fluxcd.io/v1beta2
kind: ImagePolicy
metadata:
  name: construx-api
  namespace: flux-system
spec:
  imageRepositoryRef:
    name: construx-api
  policy:
    semver:
      range: ">=1.8.0 <2.0.0"

---
apiVersion: image.toolkit.fluxcd.io/v1beta2
kind: ImageUpdateAutomation
metadata:
  name: construx-api
  namespace: flux-system
spec:
  interval: 5m
  sourceRef:
    kind: GitRepository
    name: construx-api
  git:
    checkout:
      ref:
        branch: master
    commit:
      author:
        name: Flux Bot
        email: flux@construx.io
      messageTemplate: "chore: update construx-api to {{range .Updated.Images}}{{.NewTag}}{{end}}"
    push:
      branch: master
  update:
    strategy: Setters
    path: ./k8s/overlays/production
```

```yaml
# In the Deployment manifest — annotate the image field for Flux to update
containers:
  - name: api
    image: registry.construx.io/construx/api:v1.8.3  # {"$imagepolicy": "flux-system:construx-api"}
    # ↑ Flux replaces v1.8.3 with the new tag automatically
```

```bash
# After CI pushes v1.8.4:
# Flux commits: "chore: update construx-api to v1.8.4"
# Flux applies: Deployment with image:v1.8.4

# Check what Flux is tracking
flux get images repository construx-api
flux get images policy construx-api
# POLICY                READY  LATEST TAG
# flux-system/construx-api  True   v1.8.4

# Diff before Flux applies (see what's pending)
flux diff kustomization construx-api
```

Flux vs ArgoCD: ArgoCD has a polished web UI and strong multi-cluster RBAC — better for organizations that want visibility across many teams and clusters. Flux is CRD-native, more composable (each controller is independent), and the Image Automation Controller creates a fully automated CD loop that ArgoCD doesn't natively provide. The operational difference: ArgoCD has a server component with its own auth; Flux is just controllers — smaller attack surface, simpler operation. Most teams that choose Flux cite the image automation and the pure Kubernetes-native model as the deciding factors.
