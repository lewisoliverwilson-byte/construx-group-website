Server Actions are async functions that run on the server but can be called from the client — directly from form `action` attributes or `onClick` handlers. No API route needed. The Next.js compiler handles the RPC boundary.

## The basic pattern

```tsx
// app/actions/posts.ts
'use server';

import { db } from '@/lib/db';
import { revalidatePath } from 'next/cache';

export async function createPost(formData: FormData) {
  const title = formData.get('title') as string;
  const body = formData.get('body') as string;

  await db.insert(posts).values({ title, body });
  revalidatePath('/posts');
}
```

```tsx
// app/posts/new/page.tsx — Server Component
import { createPost } from '@/actions/posts';

export default function NewPostPage() {
  return (
    <form action={createPost}>
      <input name="title" placeholder="Title" />
      <textarea name="body" placeholder="Content" />
      <button type="submit">Create post</button>
    </form>
  );
}
```

That's it. The `action={createPost}` wires directly to the server function. When the form submits, Next.js serializes the `FormData`, ships it to the server, runs `createPost`, and returns. No route handler, no `fetch('/api/posts')`, no JSON parsing.

## Progressive enhancement

The form above works without JavaScript. When JS is disabled, the form submits as a standard HTML form POST. When JS is enabled, it's intercepted by React, preventing full page navigation. This is the Web Platform working as intended — your form degrades gracefully.

## `useActionState` for feedback

```tsx
'use client';

import { useActionState } from 'react';
import { createPost } from '@/actions/posts';

type State = { error?: string; success?: boolean };

const initialState: State = {};

export function NewPostForm() {
  const [state, formAction, pending] = useActionState(createPost, initialState);

  return (
    <form action={formAction}>
      <input name="title" placeholder="Title" />
      <textarea name="body" placeholder="Content" />
      {state.error && <p className="text-red-500">{state.error}</p>}
      {state.success && <p className="text-green-500">Post created!</p>}
      <button type="submit" disabled={pending}>
        {pending ? 'Creating…' : 'Create post'}
      </button>
    </form>
  );
}
```

```ts
// Updated action — returns state instead of void
'use server';

export async function createPost(prevState: State, formData: FormData): Promise<State> {
  const title = formData.get('title') as string;
  if (!title?.trim()) return { error: 'Title is required' };

  try {
    await db.insert(posts).values({ title, body: formData.get('body') as string });
    revalidatePath('/posts');
    return { success: true };
  } catch {
    return { error: 'Failed to create post' };
  }
}
```

`useActionState` manages the pending state and the returned error/success — no manual `useState` for loading or errors.

## Calling actions from event handlers

```tsx
'use client';

import { deletePost } from '@/actions/posts';
import { useTransition } from 'react';

export function DeleteButton({ postId }: { postId: string }) {
  const [isPending, startTransition] = useTransition();

  return (
    <button
      disabled={isPending}
      onClick={() => startTransition(() => deletePost(postId))}
    >
      {isPending ? 'Deleting…' : 'Delete'}
    </button>
  );
}
```

`startTransition` marks the update as non-urgent, keeping the UI responsive while the action runs. The button doesn't block the UI.

## Authentication in actions

Server Actions run on the server, so you can access auth session normally:

```ts
'use server';

import { auth } from '@/auth';

export async function deletePost(postId: string) {
  const session = await auth();
  if (!session?.user) throw new Error('Unauthorized');

  const post = await db.query.posts.findFirst({
    where: eq(posts.id, postId),
  });

  if (post?.authorId !== session.user.id) throw new Error('Forbidden');

  await db.delete(posts).where(eq(posts.id, postId));
  revalidatePath('/posts');
}
```

**Never skip the authorization check.** Server Actions are public endpoints — anyone can call them with the right payload. The `'use server'` directive doesn't add any security; it just moves execution to the server.

## Server Actions vs route handlers

Use Server Actions when:
- You're submitting a form
- You're mutating data from a Client Component
- You want progressive enhancement
- You need access to cookies, headers, or auth session

Use route handlers (`app/api/`) when:
- External systems need to call you (webhooks, mobile apps, third-party integrations)
- You need custom response headers or status codes
- You're building a public API

The rule: if you're the only caller, use a Server Action. If external systems call you, use a route handler.

## Revalidation after mutation

```ts
import { revalidatePath, revalidateTag } from 'next/cache';

// Revalidate a specific page
revalidatePath('/posts');

// Revalidate a specific post page
revalidatePath(`/posts/${postId}`);

// Revalidate all pages using a tag
revalidateTag('posts');

// Redirect after mutation
import { redirect } from 'next/navigation';
redirect('/posts');
```

`redirect()` in a Server Action triggers a client-side navigation — no full page reload.

## Input validation

Always validate. `formData.get()` returns `string | null` — the type system won't save you:

```ts
import { z } from 'zod';

const PostSchema = z.object({
  title: z.string().min(1, 'Title required').max(200),
  body: z.string().min(10, 'Body too short'),
});

export async function createPost(prevState: State, formData: FormData): Promise<State> {
  const raw = {
    title: formData.get('title'),
    body: formData.get('body'),
  };

  const parsed = PostSchema.safeParse(raw);
  if (!parsed.success) {
    return { error: parsed.error.issues[0].message };
  }

  await db.insert(posts).values(parsed.data);
  revalidatePath('/posts');
  return { success: true };
}
```

Zod with `safeParse` avoids throwing — you get structured errors back to the client.
