excerpt: "AlertManager receives firing alerts from Prometheus, deduplicates them, groups them, and routes them to the right receiver (PagerDuty, Slack, email, webhook). Routing is a tree of match rules: alerts flow from the root route down through child routes until a match. Inhibitions suppress lower-severity alerts when a higher-severity alert is already firing. Silences mute alerts during planned maintenance. Together they prevent alert fatigue — the failure mode where too many low-signal alerts cause engineers to ignore everything."

Receive. Deduplicate. Route. Inhibit. Silence. Never page for noise.

## Prometheus alerting rules

```yaml
# /etc/prometheus/rules/construx.yml
# Alert rules evaluated every 15s by Prometheus

groups:
  - name: construx.api
    interval: 15s
    rules:
      - alert: HighErrorRate
        # expr: error rate > 5% for 2 consecutive minutes
        expr: |
          (
            sum(rate(http_requests_total{job="construx-api", status=~"5.."}[5m]))
            /
            sum(rate(http_requests_total{job="construx-api"}[5m]))
          ) > 0.05
        for: 2m    # Must be true for 2 minutes before firing (prevents flapping)
        labels:
          severity: critical
          team: platform
        annotations:
          summary: "High error rate on construx-api"
          description: "Error rate is {{ $value | humanizePercentage }} (threshold: 5%)"
          runbook_url: "https://runbook.construx.io/high-error-rate"

      - alert: PostgresConnectionsHigh
        expr: |
          pg_stat_database_numbackends{datname="construx_production"}
          / pg_settings_max_connections > 0.80
        for: 5m
        labels:
          severity: warning
          team: platform
        annotations:
          summary: "PostgreSQL connections above 80% of max"
          description: "{{ $value | humanizePercentage }} of max_connections used"

      - alert: DiskSpaceLow
        expr: |
          (node_filesystem_avail_bytes{fstype!="tmpfs", mountpoint="/"}
          / node_filesystem_size_bytes) < 0.15
        for: 10m
        labels:
          severity: warning
          team: ops
        annotations:
          summary: "Disk space below 15% on {{ $labels.instance }}"
```

## AlertManager configuration — routing tree

```yaml
# /etc/alertmanager/alertmanager.yml

global:
  resolve_timeout: 5m
  slack_api_url: 'https://hooks.slack.com/services/...'
  pagerduty_url: 'https://events.pagerduty.com/v2/enqueue'

# Grouping: batch alerts with the same labels into one notification
# group_wait: how long to wait before sending the first group notification
# group_interval: minimum time between notifications for the same group
# repeat_interval: how long before resending an unresolved alert

route:
  receiver: 'slack-monitoring'    # Default receiver
  group_by: ['alertname', 'job']
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h

  routes:
    # Critical alerts: immediate PagerDuty page
    - match:
        severity: critical
      receiver: pagerduty-on-call
      group_wait: 10s
      repeat_interval: 30m
      continue: true              # Also send to Slack after PagerDuty

    # Critical alerts also go to Slack for visibility
    - match:
        severity: critical
      receiver: 'slack-critical'
      group_wait: 10s
      repeat_interval: 30m

    # Warning alerts: Slack only, grouped by team
    - match:
        severity: warning
        team: platform
      receiver: 'slack-platform'
      repeat_interval: 2h

    - match:
        severity: warning
        team: ops
      receiver: 'slack-ops'
      repeat_interval: 2h

receivers:
  - name: 'slack-monitoring'
    slack_configs:
      - channel: '#monitoring'
        title: '{{ .GroupLabels.alertname }}'
        text: '{{ range .Alerts }}{{ .Annotations.description }}{{ end }}'

  - name: 'slack-critical'
    slack_configs:
      - channel: '#alerts-critical'
        color: '{{ if eq .Status "firing" }}danger{{ else }}good{{ end }}'
        title: '[{{ .Status | toUpper }}] {{ .GroupLabels.alertname }}'
        text: |
          *Description:* {{ .Annotations.description }}
          *Runbook:* {{ .Annotations.runbook_url }}

  - name: 'pagerduty-on-call'
    pagerduty_configs:
      - routing_key: '<PAGERDUTY_INTEGRATION_KEY>'
        description: '{{ .GroupLabels.alertname }}: {{ .Annotations.summary }}'
        severity: '{{ .CommonLabels.severity }}'
        details:
          runbook: '{{ .Annotations.runbook_url }}'
          value: '{{ .Annotations.description }}'
```

## Inhibitions — suppress low-severity when high-severity fires

```yaml
# inhibit_rules: if a "source" alert is firing, suppress matching "target" alerts
# Use case: if the whole cluster is down (NodeDown), suppress individual service alerts
inhibit_rules:
  # If a node is down, suppress all alerts from that node's services
  - source_match:
      alertname: NodeDown
      severity: critical
    target_match_re:
      alertname: (HighErrorRate|PostgresConnectionsHigh|DiskSpaceLow)
    equal:
      - instance    # Only inhibit alerts from the same instance

  # If a critical alert fires, suppress its warning variant
  - source_match:
      severity: critical
    target_match:
      severity: warning
    equal:
      - alertname    # Same alert, different severity
      - job
```

## amtool — AlertManager CLI

```bash
# Query current state of AlertManager
amtool --alertmanager.url http://localhost:9093 alert query

# Filter by severity
amtool alert query severity=critical

# Create a silence for planned maintenance (4-hour maintenance window)
amtool silence add \
  --comment "Scheduled DB maintenance 02:00-06:00" \
  --duration 4h \
  alertname=PostgresConnectionsHigh instance=db-01

# Silence ID returned: 8d7f3a29-1c2e-4b8f-9d1a-3e5f7c9b2a4d

# List active silences
amtool silence query

# Expire a silence early
amtool silence expire 8d7f3a29-1c2e-4b8f-9d1a-3e5f7c9b2a4d

# Check route matching for a given label set
amtool config routes test \
  severity=critical team=platform alertname=HighErrorRate
# Matching routes:
# → pagerduty-on-call (repeat: 30m)
# → slack-critical    (repeat: 30m)
```

Alert fatigue is the real problem. AlertManager's inhibitions and silences are not workarounds — they're the design. A team that gets paged for DiskSpaceLow while a NodeDown alert fires for the same host will eventually ignore all pages. Inhibitions prevent this mechanically: the NodeDown suppresses the disk alert so the on-call engineer sees one signal, not ten. The goal is never "more alerts." It's "no alert that doesn't require human action."
