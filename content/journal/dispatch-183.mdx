Indexes are the most impactful performance intervention available at the database level. A query that takes 2 seconds without an index can take 5ms with one. Getting indexing right is cheap; getting it wrong creates production incidents.

Here's how we approach it.

## The principle: index for reads, not for writes

Every index makes writes slightly slower (the index must be updated when a row is inserted or updated) and reads significantly faster (the index enables efficient lookup). For read-heavy applications (which most SaaS products are), the tradeoff is almost always worth it.

We add indexes proactively for:
- All foreign keys
- All columns used in `WHERE` clauses on large tables
- All columns used in `ORDER BY` on paginated queries
- All columns used in `JOIN` conditions

We don't add indexes preemptively for columns that might be queried in the future. We add them when the query exists.

## The foreign key index gap

PostgreSQL does not automatically create indexes on foreign key columns. This is a common oversight:

```sql
-- Table: messages
-- message.channel_id references channels.id
-- Without an index:

SELECT * FROM messages WHERE channel_id = $1 ORDER BY created_at DESC LIMIT 50;
-- → Sequential scan on messages table (potentially millions of rows)

-- With the index:
CREATE INDEX idx_messages_channel_id ON messages(channel_id, created_at DESC);
-- → Index scan (milliseconds regardless of table size)
```

We add indexes on all foreign key columns as part of the migration that creates the relationship. The cost is negligible; the benefit is avoiding a class of slow queries that only manifest under real data volumes.

## Composite indexes for common query patterns

A single-column index on `channel_id` helps `WHERE channel_id = $1`. A composite index on `(channel_id, created_at DESC)` helps `WHERE channel_id = $1 ORDER BY created_at DESC LIMIT 50`.

The most common The Hyve query is: fetch the last N messages for a channel, ordered by time. The composite index on `(channel_id, created_at DESC)` is the right tool:

```sql
CREATE INDEX idx_messages_channel_created ON messages(channel_id, created_at DESC);
```

PostgreSQL can use this index for the full query: filter by `channel_id` and return rows in `created_at DESC` order without a sort step.

## The partial index

Partial indexes index only rows matching a filter condition. They're smaller and faster than full indexes for filtered queries:

```sql
-- Only active listings, only in specific categories
CREATE INDEX idx_listings_active_category ON listings(category, created_at DESC)
WHERE status = 'active';

-- Only pending webhook deliveries, ordered by retry time
CREATE INDEX idx_webhooks_pending ON webhook_deliveries(next_retry_at)
WHERE status = 'pending';
```

The webhook delivery worker queries for `WHERE status = 'pending' AND next_retry_at <= now()`. A partial index on `next_retry_at WHERE status = 'pending'` is significantly smaller than a full index on `next_retry_at` and faster for this specific query.

## The `EXPLAIN ANALYZE` habit

Before adding any new index, we run `EXPLAIN ANALYZE` to understand the current query plan:

```sql
EXPLAIN ANALYZE
SELECT id, title, seller_id, category
FROM listings
WHERE status = 'active' AND category = 'design'
ORDER BY created_at DESC
LIMIT 20;
```

The output shows whether the query is using a sequential scan (slow for large tables) or an index scan (fast). It also shows the estimated vs. actual row counts, which can reveal stale statistics.

After adding the index, we run `EXPLAIN ANALYZE` again to confirm the query now uses it.

## The maintenance window

Large indexes on large tables take time to build. `CREATE INDEX CONCURRENTLY` builds the index without locking the table for writes, at the cost of taking longer:

```sql
-- Without CONCURRENTLY: table locked for writes during build (bad for production)
CREATE INDEX idx_listings_search ON listings USING GIN(search_vector);

-- With CONCURRENTLY: no write lock (good for production)
CREATE INDEX CONCURRENTLY idx_listings_search ON listings USING GIN(search_vector);
```

We always use `CONCURRENTLY` for index creation in production. The only exception: migration scripts that run on an empty or low-traffic database during initial setup.

## The index we removed

Early in The Marqet's development, we added an index on `listings.description` for full-text search:

```sql
CREATE INDEX idx_listings_description ON listings USING GIN(to_tsvector('english', description));
```

When we added the `search_vector` generated column (which combines title, description, skills, and location), this index became redundant. Every query that used the description index was better served by the search_vector index.

We dropped it:

```sql
DROP INDEX idx_listings_description;
```

An unused index has a real cost: it consumes disk space and makes every INSERT/UPDATE to the `listings` table slightly slower. Audit your indexes periodically and drop the ones that aren't being used.

```sql
-- Find indexes that haven't been used since the last stats reset
SELECT 
  indexrelname AS index_name,
  pg_size_pretty(pg_relation_size(indexrelid)) AS size,
  idx_scan AS scans
FROM pg_stat_user_indexes
WHERE schemaname = 'public' AND idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;
```

## The practical summary

1. Index all foreign keys at creation time
2. Use composite indexes that match common query patterns
3. Use partial indexes for filtered queries on large tables
4. Always `EXPLAIN ANALYZE` before and after adding an index
5. Use `CREATE INDEX CONCURRENTLY` in production
6. Periodically audit and drop unused indexes

The most important of these: run `EXPLAIN ANALYZE` on any query that's slow. The query plan almost always reveals the problem, and the fix is usually an index.
