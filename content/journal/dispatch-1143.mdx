excerpt: "LitmusChaos is a Kubernetes-native chaos engineering platform. It provides a library of fault experiments (pod kill, CPU hog, network latency, disk fill, node drain, DNS error) delivered as Kubernetes CRDs. A ChaosEngine links a target application (by label selector) to a ChaosExperiment, and the LitmusChaos operator runs the fault, monitors the application's steady-state health check, and computes a Resilience Score based on what percentage of hypotheses passed. The Resilience Score is the key metric: a score of 100 means the system remained healthy under every fault; a score of 60 means 40% of fault scenarios caused degradation. ChaosExperiments can be scheduled via Litmus Chaos Center (the control plane UI/API) and integrated into CI/CD pipelines — a failed chaos run can block a deployment in the same way a failed test does. Litmus supports 'probes' — pre/post-conditions that validate system health using HTTP, command, Prometheus, or Kubernetes API checks. At Construx, LitmusChaos runs a weekly GameDay: 6 experiments targeting the orders pipeline (pod-delete, network-latency-inject, kafka-broker-pod-failure, node-drain, memory-hog, disk-fill), and the results feed into a Grafana dashboard that tracks Resilience Score over time."

## LitmusChaos experiment configuration

```yaml
# ChaosExperiment: inject 500ms latency on orders-api egress network
# Tests whether orders-api circuit breaker opens and returns graceful degradation

apiVersion: litmuschaos.io/v1alpha1
kind: ChaosExperiment
metadata:
  name: pod-network-latency
  namespace: litmus
spec:
  definition:
    scope: Namespaced
    permissions:
      - apiGroups: [""]
        resources: ["pods"]
        verbs: ["get", "list"]
    image: litmuschaos/go-runner:3.9.0
    args:
      - -c
      - ./experiments -name pod-network-latency
    command:
      - /bin/bash
    env:
      - name: TOTAL_CHAOS_DURATION
        value: "120"          # inject for 120 seconds
      - name: NETWORK_LATENCY
        value: "500"          # 500ms latency in ms
      - name: JITTER
        value: "50"           # ±50ms jitter
      - name: TARGET_PODS
        value: ""             # selected by label in ChaosEngine
      - name: PODS_AFFECTED_PERC
        value: "50"           # inject into 50% of matching pods
      - name: CONTAINER_RUNTIME
        value: "containerd"
      - name: SOCKET_PATH
        value: "/run/containerd/containerd.sock"
    labels:
      name: pod-network-latency
      app.kubernetes.io/part-of: litmus

---
# ChaosEngine: run pod-network-latency against orders-api
# Validates that circuit breaker opens and graceful fallback activates

apiVersion: litmuschaos.io/v1alpha1
kind: ChaosEngine
metadata:
  name: orders-api-latency-chaos
  namespace: construx-prod
spec:
  appinfo:
    appns: construx-prod
    applabel: "app=orders-api"
    appkind: deployment

  engineState: active
  chaosServiceAccount: litmus-admin

  # Probes: validate steady state before AND after the fault
  components:
    runner:
      image: litmuschaos/chaos-runner:3.9.0

  experiments:
    - name: pod-network-latency
      spec:
        components:
          env:
            - name: TOTAL_CHAOS_DURATION
              value: "120"
            - name: NETWORK_LATENCY
              value: "500"
            - name: PODS_AFFECTED_PERC
              value: "50"

        # Probes: hypothesis checks during chaos
        probe:
          - name: orders-api-health-check
            type: httpProbe
            httpProbe/inputs:
              url: "https://orders-api.construx.io/health"
              insecureSkipVerify: false
              responseTimeout: 1000
              method:
                get:
                  criteria: ==
                  responseCode: "200"
            mode: Continuous    # check every interval during fault
            runProperties:
              probeTimeout: 5
              interval: 5
              retry: 2
              probePollingInterval: 5

          - name: error-rate-check
            type: prometheusProbe
            prometheusProbe/inputs:
              endpoint: "http://prometheus.construx-monitoring.svc.cluster.local:9090"
              query: >
                sum(rate(http_server_requests_total{service="orders-api",status=~"5.."}[1m]))
                / sum(rate(http_server_requests_total{service="orders-api"}[1m]))
              comparator:
                criteria: <=
                value: "0.01"   # error rate must stay ≤ 1% during fault
            mode: Continuous
            runProperties:
              probeTimeout: 10
              interval: 15
              retry: 2
```

```yaml
# ChaosSchedule: run weekly GameDay every Monday 03:00 UTC
# Six experiments in sequence — pod-delete, network-latency, kafka-broker, node-drain, memory-hog, disk-fill

apiVersion: litmuschaos.io/v1alpha1
kind: ChaosSchedule
metadata:
  name: weekly-gameday
  namespace: litmus
spec:
  schedule:
    cron: "0 3 * * 1"   # every Monday at 03:00 UTC
  engineTemplateSpec:
    appinfo:
      appns: construx-prod
      applabel: "app.kubernetes.io/part-of=construx"
      appkind: deployment
    engineState: active
    chaosServiceAccount: litmus-admin
    experiments:
      - name: pod-delete
        spec:
          components:
            env:
              - name: TOTAL_CHAOS_DURATION
                value: "60"
              - name: CHAOS_INTERVAL
                value: "10"
              - name: FORCE
                value: "false"   # graceful delete, not SIGKILL

      - name: node-drain
        spec:
          components:
            env:
              - name: TARGET_NODE
                value: ""            # random node selected at runtime
              - name: TOTAL_CHAOS_DURATION
                value: "120"
```

```bash
# LitmusChaos CLI (litmusctl): manage experiments and view results

# List all ChaosEngines and their status
kubectl get chaosengines -n construx-prod

# Output:
# NAME                        STATUS      EXPERIMENTSTATUS
# orders-api-latency-chaos    completed   Pass
# kafka-broker-pod-failure    completed   Fail    ← resilience gap found

# View chaos result: Resilience Score and probe outcomes
kubectl get chaosresult orders-api-latency-chaos-pod-network-latency -n construx-prod -o yaml | \
  yq '.status.experimentStatus'

# Output:
# phase: Completed
# verdict: Pass
# resiliencyScore: 87.5    ← 7/8 probes passed (1 probe caught brief degradation)
# failedRuns: 0

# Chaos Center: aggregate Resilience Score across weekly GameDay
# (REST API — also available in Grafana via datasource plugin)
curl -s "https://chaos.construx.io/api/query" \
  -H "Authorization: Bearer $LITMUS_TOKEN" \
  -d '{"query":"{ listWorkflowRuns(projectID: \"construx-prod\", request: {limit: 4}) { totalNoOfWorkflowRuns workflowRuns { resiliencyScore executionData } } }"}' \
  | jq '.data.listWorkflowRuns.workflowRuns[] | {score: .resiliencyScore}'

# Output:
# { "score": 87.5 }   ← this week
# { "score": 75.0 }   ← last week (kafka drain issue found and fixed)
# { "score": 100.0 }  ← 2 weeks ago
# { "score": 87.5 }   ← 3 weeks ago

# View failed probe details
kubectl describe chaosresult kafka-broker-pod-failure-result -n construx-prod | grep -A5 "Failed Probes"
# Failed Probes:
#   consumer-lag-check: value 142830 exceeded threshold 50000
#   → kafka consumer lag spiked during broker failover — circuit breaker too slow
```

LitmusChaos vs Chaos Monkey vs Gremlin vs Chaos Toolkit vs Steadybit: Netflix's Chaos Monkey was the original chaos engineering tool — it randomly terminates EC2 instances in production, specifically for AWS. It is not Kubernetes-native and only handles instance termination. Gremlin is a commercial SaaS chaos platform with a rich fault library (CPU, memory, network, disk, process, DNS, time) and a polished UI — it supports Kubernetes but is not open source. Chaos Toolkit is an open-source Python library for writing chaos experiments as JSON/YAML, with an extension ecosystem, but it requires more Python glue code than LitmusChaos's CRD model. Steadybit is a newer commercial platform focused on reliability testing with a drag-and-drop experiment builder. LitmusChaos's differentiator is its Kubernetes-native CRD model: experiments are Kubernetes resources, results are stored in etcd, and the Resilience Score provides a quantitative measure that can be tracked over time and integrated into GitOps workflows. The probe system is particularly powerful — Prometheus queries as hypothesis checks make it possible to define exactly what "healthy" means in the context of the specific business metric (error rate, queue lag, latency) rather than just "pod is running." At Construx, LitmusChaos GameDay results feed a Grafana dashboard that tracks Resilience Score per service per week, turning chaos engineering from a one-off exercise into an ongoing reliability metric alongside uptime and error rate.
