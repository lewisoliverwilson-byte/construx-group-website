title: "vals: YAML secret interpolation at apply-time from Vault, SSM, and GCP"
date: "2032-12-05"
excerpt: "vals is a CLI and Go library that resolves secret references embedded in YAML at apply-time, pulling values from HashiCorp Vault, AWS SSM Parameter Store, AWS Secrets Manager, GCP Secret Manager, Azure Key Vault, and other backends. References use the syntax `ref+<backend>://<path>#<field>` anywhere inside a YAML value. vals evaluates them and streams interpolated YAML to stdout — you pipe it to `kubectl apply` or `helm upgrade`. The key property: no secret ever touches disk, git, or logs. The `vals exec` subcommand injects secrets as environment variables into a child process, so even the application never sees the raw values in its config files."

Secret references in YAML. Apply-time resolution. Pipe to kubectl. No plaintext at rest.

## Reference backends and syntax

```bash
# vals reference syntax: ref+<backend>://<path>#<field>

# HashiCorp Vault (KV v2)
ref+vault://secret/data/construx/db#password
#           ^^^^^^^^                          ← "data/" required for KV v2
#                  ^^^^^^^^^^^^^^             ← Vault path
#                                   ^^^^^^^^ ← field key within the secret

# Vault KV v1 (no "data/" prefix)
ref+vault://secret/construx/db#password

# Vault dynamic secrets (database engine — creates ephemeral credentials)
ref+vault://database/creds/construx-read-role#password

# AWS SSM Parameter Store (SecureString auto-decrypted)
ref+awsssm:///construx/prod/db-password
ref+awsssm:///construx/prod/stripe-key

# AWS Secrets Manager (JSON secret, extract field)
ref+awssecrets:///construx/prod/db-creds#password
ref+awssecrets:///construx/prod/db-creds#username

# GCP Secret Manager
ref+gcpsecrets://construx-project/redis-url
ref+gcpsecrets://construx-project/gcp-sa-key#private_key

# Azure Key Vault
ref+azurekeyvault://my-vault/construx-db-password

# Plain file (useful for local dev)
ref+file:///etc/secrets/db-password

# Environment variable (rarely needed, but consistent)
ref+env:///DB_PASSWORD

# Check which backends are compiled in
vals --version
# vals version 0.37.2
# backends: vault awsssm awssecrets gcpsecrets azurekeyvault file env
```

## Kubernetes secrets workflow

```bash
# secrets.yaml — safe to commit (no plaintext)
cat k8s/secrets/construx-api.yaml
# apiVersion: v1
# kind: Secret
# metadata:
#   name: construx-api
#   namespace: construx-prod
# type: Opaque
# stringData:
#   db-password:      ref+vault://secret/data/construx/db#password
#   stripe-key:       ref+awsssm:///construx/prod/stripe-key
#   gcp-credentials:  ref+gcpsecrets://construx-project/gcp-sa-json
#   redis-url:        ref+awssecrets:///construx/prod/redis#url

# Resolve and apply (secrets are interpolated in-memory, never written to disk)
vals eval -f k8s/secrets/construx-api.yaml | kubectl apply -f -
# secret/construx-api configured

# Apply multiple files (all refs resolved before piping to kubectl)
vals eval \
  -f k8s/secrets/construx-api.yaml \
  -f k8s/secrets/construx-worker.yaml \
  | kubectl apply -f -

# Diff before applying (preview what kubectl would change)
vals eval -f k8s/secrets/construx-api.yaml | kubectl diff -f -

# Dry-run (validate without applying)
vals eval -f k8s/secrets/construx-api.yaml | kubectl apply --dry-run=client -f -

# Verify the secret was created correctly (check key names, not values)
kubectl describe secret construx-api -n construx-prod
# Name:     construx-api
# Data:
# db-password:      32 bytes
# stripe-key:       56 bytes
# gcp-credentials:  2347 bytes
# redis-url:        48 bytes
```

## vals exec — inject into process environment

```bash
# env-secrets.yaml — maps env var names to secret references
cat env-secrets.yaml
# DATABASE_PASSWORD:   ref+vault://secret/data/construx/db#password
# STRIPE_SECRET_KEY:   ref+awssecrets:///construx/prod/stripe#secret_key
# REDIS_URL:           ref+awsssm:///construx/prod/redis-url
# GCP_CREDENTIALS:     ref+gcpsecrets://construx-project/gcp-sa-json

# Inject into the API server process
# Secrets are in the process environment — not written to any file
vals exec -f env-secrets.yaml -- ./construx-api serve

# Inject into a database migration
vals exec -f env-secrets.yaml -- \
  atlas migrate apply \
  --url "postgres://construx:$DATABASE_PASSWORD@postgres:5432/construx_prod"

# Inject into a test suite (integration tests need real credentials)
vals exec -f env-secrets.yaml -- \
  go test -tags=integration -race ./...

# Inject into a script
vals exec -f env-secrets.yaml -- bash -c '
  echo "Connecting to $REDIS_URL"
  redis-cli -u "$REDIS_URL" ping
'

# Security: secrets appear in the process environment
# ps aux will show the process name but not env vars
# /proc/<pid>/environ is readable by root — use seccomp/AppArmor to restrict
```

## Helm integration

```bash
# values.yaml with secret references (safe to commit)
cat values.yaml
# image:
#   repository: registry.construx.io/construx/api
#   tag: v1.8.3
# database:
#   host: postgres.construx-prod.svc.cluster.local
#   port: 5432
#   password: ref+vault://secret/data/construx/db#password
# redis:
#   url: ref+awsssm:///construx/prod/redis-url
# stripe:
#   publishableKey: pk_live_...  # not secret
#   secretKey: ref+awssecrets:///construx/prod/stripe#secret_key

# Helm upgrade with interpolated values
vals eval -f values.yaml | \
  helm upgrade --install construx-api ./charts/construx-api \
  --namespace construx-prod \
  -f -

# Helm template (debug: see interpolated chart before applying)
vals eval -f values.yaml | \
  helm template construx-api ./charts/construx-api \
  -f - \
  | grep -A5 'kind: Secret'
# Shows: password: [REDACTED 32 chars]  ← vals masks secrets in template output

# Helmfile (built-in vals integration)
# helmfile.yaml
releases:
  - name: construx-api
    namespace: construx-prod
    chart: ./charts/construx-api
    values:
      - values.yaml   # vals refs resolved automatically

helmfile apply       # no extra steps — helmfile runs vals internally
```

## CI/CD with OIDC (no static credentials)

```bash
# GitHub Actions: no long-lived AWS credentials
# Uses OIDC to assume an IAM role → temporary credentials → vals reads SSM

# .github/workflows/deploy.yml
name: Deploy
on:
  push:
    branches: [master]

jobs:
  deploy:
    runs-on: ubuntu-latest
    permissions:
      id-token: write   # required for OIDC
      contents: read

    steps:
      - uses: actions/checkout@v4

      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789:role/github-construx-deploy
          aws-region: eu-west-1
          # OIDC: no AKID/secret needed — GitHub gets a temporary token

      - run: go install github.com/helmfile/vals@latest

      - name: Apply secrets and deploy
        run: |
          vals eval -f k8s/secrets/construx-api.yaml | kubectl apply -f -
          vals eval -f values.yaml | helm upgrade --install construx-api ./charts -f -

# Security model:
# - No static AWS credentials in GitHub secrets
# - OIDC token → STS AssumeRoleWithWebIdentity → 1h temporary credentials
# - vals uses temp credentials to read SSM/Secrets Manager
# - Full audit trail in CloudTrail (role ARN, time, parameters read)
# - Role trust policy restricts to specific repo and branch:
#   Condition:
#     StringEquals:
#       "token.actions.githubusercontent.com:sub":
#         "repo:construx/construx-api:ref:refs/heads/master"
```

vals vs External Secrets Operator vs Sealed Secrets: vals resolves secrets at apply-time in the CI pipeline — nothing stored in the cluster. External Secrets Operator (ESO) syncs secrets from external stores into Kubernetes Secret objects on a schedule — they live in the cluster, accessible to pods at any time without the pipeline. Sealed Secrets encrypts secrets for git — the cluster holds the decryption key. The choice: vals when you want apply-time resolution with no in-cluster secret storage. ESO when pods need secrets available independent of CI runs. Sealed Secrets when you want GitOps with a single cluster and no external secret store dependency.
