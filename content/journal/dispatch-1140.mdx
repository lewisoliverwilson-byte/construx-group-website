excerpt: "Istio's Telemetry API (v1alpha1 and v1) provides declarative control over what telemetry Istio's data plane emits: which metrics to collect (with custom tag extraction and filtering), how traces are sampled, what access log format to use, and which backends to send telemetry to. Before the Telemetry API, modifying Istio's default metrics required editing EnvoyFilter resources or Telemetry v1alpha1 API, which was complex. The v1 API provides a clean CRD model: a Telemetry resource in a namespace (or the root `istio-system` namespace for cluster-wide policy) overrides the default telemetry behaviour for all workloads in that namespace. Custom metrics allow service teams to extract business-relevant labels from request attributes — for example, adding a `tenant_id` tag to all HTTP metrics by extracting it from the `X-Tenant-ID` request header. This is essential for multi-tenant services where per-tenant error rates and latency are more actionable than aggregate metrics. Trace sampling configuration is a common need: default 100% sampling is too expensive for high-throughput services, but 0.1% sampling misses errors. Istio's Telemetry API supports custom sampling rates per workload, and the OpenTelemetry trace provider sends traces directly to the OTel Collector (which applies tail-based sampling) rather than sampling in the sidecar."

## Istio Telemetry API configuration

```yaml
# Telemetry: custom metrics with tenant_id tag extraction
# Applied to construx-prod namespace — overrides default Istio metrics

apiVersion: telemetry.istio.io/v1
kind: Telemetry
metadata:
  name: construx-prod-telemetry
  namespace: construx-prod
spec:
  metrics:
    - providers:
        - name: prometheus
      overrides:
        # Add tenant_id tag to all HTTP metrics from the X-Tenant-ID header
        - match:
            metric: REQUEST_COUNT
            mode: CLIENT_AND_SERVER
          tagOverrides:
            tenant_id:
              value: "request.headers['x-tenant-id'] | 'unknown'"
            api_version:
              value: "request.headers['x-api-version'] | 'v1'"

        # Disable some high-cardinality default labels to reduce metric series count
        - match:
            metric: ALL_METRICS
            mode: CLIENT_AND_SERVER
          tagOverrides:
            source_principal:
              operation: REMOVE    # high cardinality, rarely useful
            destination_principal:
              operation: REMOVE

        # Add custom histogram metric: request body size
        - match:
            metric: REQUEST_BYTES
          disabled: false

  tracing:
    - providers:
        - name: otel    # send traces to OTel Collector (which applies tail sampling)
      randomSamplingPercentage: 100.0   # sample everything — tail sampling in collector

  accessLogging:
    - providers:
        - name: otel
```

```yaml
# MeshConfig: configure telemetry providers
# Applied in istio-system namespace via IstioOperator or ConfigMap

apiVersion: v1
kind: ConfigMap
metadata:
  name: istio
  namespace: istio-system
data:
  mesh: |-
    extensionProviders:
      - name: otel
        opentelemetry:
          service: otelcol.construx-monitoring.svc.cluster.local
          port: 4317
          resource_detectors:
            - environment: {}

      - name: prometheus
        prometheus: {}

    defaultConfig:
      tracing: {}   # tracing configured via Telemetry API

    enablePrometheusMerge: true   # merge Envoy metrics with app /metrics
    outboundTrafficPolicy:
      mode: REGISTRY_ONLY   # block traffic to unregistered services

---
# Telemetry: access log format customisation
# Log structured JSON with request ID for correlation with traces

apiVersion: telemetry.istio.io/v1
kind: Telemetry
metadata:
  name: custom-access-log
  namespace: construx-prod
spec:
  accessLogging:
    - providers:
        - name: otel
      filter:
        expression: "response.code >= 400"   # only log errors (reduce volume)
```

```bash
# Istio telemetry: inspect and validate

# Check which Telemetry resources are applied to a pod
istioctl x authz check deploy/orders-api -n construx-prod

# View the Envoy metrics from Istio sidecar
kubectl exec -n construx-prod deploy/orders-api -c istio-proxy -- \
  curl -s http://localhost:15090/stats/prometheus | \
  grep -E "istio_requests_total{.*tenant_id"

# Output:
# istio_requests_total{reporter="server",source_app="frontend",destination_app="orders-api",
#   tenant_id="acme",response_code="200",api_version="v1"} 48291

# Verify trace headers are being propagated correctly
kubectl exec -n construx-prod deploy/orders-api -c orders-api -- \
  curl -v http://payments-api.construx-prod.svc.cluster.local/api/v1/payments 2>&1 | \
  grep -i "traceparent\|b3\|x-request-id"

# Get trace sampling config for a workload
istioctl proxy-config bootstrap deploy/orders-api -n construx-prod | \
  jq '.bootstrap.tracing'

# View access logs via OTel Collector → Loki
# (Istio access logs forwarded to OTel Collector → Loki → queryable in Grafana)
kubectl exec -n construx-monitoring deploy/loki-gateway -- \
  wget -qO- "http://loki.construx-monitoring.svc.cluster.local:3100/loki/api/v1/query_range" \
  --post-data 'query={job="istio-access-log",destination_app="orders-api"}&start=now-1h&end=now' | \
  jq '.data.result[0].values[-5:]'
```

Istio Telemetry API vs EnvoyFilter vs DestinationRule vs PeerAuthentication: EnvoyFilter provides the lowest-level override for Envoy proxy configuration — you can change any Envoy setting, but it requires understanding Envoy's xDS configuration model (dispatch-1111) and is brittle across Istio upgrades. The Telemetry API is a higher-level abstraction specifically for observability configuration — it is more stable across versions and requires no Envoy knowledge. DestinationRule controls traffic policy (connection pools, load balancing, mTLS configuration), not telemetry. PeerAuthentication configures mTLS authentication requirements — whether sidecars require mutual TLS for inbound traffic. These four APIs together cover the full sidecar configuration surface: Telemetry for observability, DestinationRule for traffic, PeerAuthentication for security, and EnvoyFilter for anything else. The custom metrics feature of the Telemetry API is particularly powerful for multi-tenant SaaS: standard Kubernetes and Istio metrics are service-level aggregates, but per-tenant error rates require extracting the tenant identifier from request headers and injecting it as a metric label — this is exactly what the `tagOverrides` mechanism enables without modifying application code.
