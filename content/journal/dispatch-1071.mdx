title: "OpenSearch: distributed search and analytics — inverted index, query DSL, vector search"
date: "2033-10-01"
excerpt: "OpenSearch is an open-source distributed search and analytics engine forked from Elasticsearch 7.10. It stores documents as JSON in an inverted index — every field in every document is indexed by default (unlike Loki, which only indexes labels). This means OpenSearch supports arbitrary full-text search across any field without pre-planning the index schema. OpenSearch organises data into indices; each index is divided into shards (primary and replica), which are distributed across the cluster's nodes. Queries fan out to all shards in parallel, results are merged and scored by relevance (BM25 by default), and the top-N results are returned. OpenSearch also supports vector search (approximate nearest-neighbour via FAISS or NMSLIB) alongside full-text search, making it viable for hybrid search pipelines where you need both keyword matching and semantic similarity. The OpenSearch Dashboards UI (a Kibana fork) provides index management, log exploration, and alerting. OpenSearch is used at Construx for application log search (complementing Loki's metric-style aggregations), audit log compliance queries, and full-text search on user-generated content."

## Index configuration and mapping

```json
// Create an index with explicit mapping
// Explicit mapping avoids field type inference mistakes on first document ingest

PUT /construx-logs-2033-10
{
  "settings": {
    "number_of_shards":   3,    // distribute across 3 data nodes
    "number_of_replicas": 1,    // 1 replica = 2 copies total (survive 1 node loss)
    "refresh_interval": "5s",   // index refresh: 5s delay before docs are searchable
    "index": {
      "codec": "best_compression"   // zstd compression — good for log data
    }
  },
  "mappings": {
    "properties": {
      "timestamp":   { "type": "date"     },
      "level":       { "type": "keyword"  },    // keyword = exact match, no analysis
      "service":     { "type": "keyword"  },
      "namespace":   { "type": "keyword"  },
      "message":     { "type": "text",          // text = analysed for full-text search
                       "analyzer": "standard" },
      "trace_id":    { "type": "keyword"  },
      "duration_ms": { "type": "integer"  },
      "status_code": { "type": "short"    },
      // Vector field: semantic embedding for hybrid search
      "embedding": {
        "type":            "knn_vector",
        "dimension":       1536,          // OpenAI text-embedding-3-small dimension
        "method": {
          "engine":         "faiss",
          "space_type":     "cosine",
          "name":           "hnsw",
          "parameters": { "ef_construction": 128, "m": 24 }
        }
      }
    }
  }
}
```

```json
// Query DSL: compound queries

// Full-text search with filters
POST /construx-logs-2033-10/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "message": "payment declined" } }  // full-text BM25
      ],
      "filter": [
        { "term":  { "level":   "error" } },            // exact keyword filter
        { "term":  { "service": "construx-payments" } },
        { "range": { "timestamp": { "gte": "now-1h" } } }
      ]
    }
  },
  "sort":  [{ "timestamp": "desc" }],
  "size":  20,
  "_source": ["timestamp", "message", "trace_id", "duration_ms"]
}

// Aggregation: error count by service in the last 24h
POST /construx-logs-*/_search
{
  "size": 0,
  "query": {
    "bool": {
      "filter": [
        { "term":  { "level": "error" } },
        { "range": { "timestamp": { "gte": "now-24h" } } }
      ]
    }
  },
  "aggs": {
    "errors_by_service": {
      "terms": { "field": "service", "size": 10 },
      "aggs": {
        "error_rate": {
          "date_histogram": { "field": "timestamp", "calendar_interval": "1h" }
        }
      }
    }
  }
}

// Hybrid search: combine BM25 full-text + vector ANN (kNN)
POST /construx-docs/_search
{
  "query": {
    "bool": {
      "must": { "match": { "content": "kubernetes autoscaling" } }
    }
  },
  "knn": {
    "field":          "embedding",
    "query_vector":   [0.021, -0.043, 0.118, ...],   // 1536-dim embedding of the query
    "k":              10,
    "num_candidates": 100
  },
  "rank": {
    "rrf": {}    // Reciprocal Rank Fusion: merge BM25 + kNN rankings
  }
}
```

## Index lifecycle management and cluster operations

```bash
# Index Lifecycle Management (ILM): rotate and expire log indices automatically
# Hot → Warm → Cold → Delete policy

curl -X PUT https://opensearch.construx.internal/_plugins/_ism/policies/logs-policy \
  -H 'Content-Type: application/json' -d '{
  "policy": {
    "description": "Log index lifecycle — hot 3d, warm 7d, delete at 30d",
    "states": [
      {
        "name": "hot",
        "actions": [{ "rollover": { "min_doc_count": 5000000, "min_index_age": "3d" } }],
        "transitions": [{ "state_name": "warm", "conditions": { "min_index_age": "3d" } }]
      },
      {
        "name": "warm",
        "actions": [
          { "replica_count": { "number_of_replicas": 0 } },   // drop replicas to save space
          { "force_merge":   { "max_num_segments": 1 } }
        ],
        "transitions": [{ "state_name": "delete", "conditions": { "min_index_age": "30d" } }]
      },
      {
        "name": "delete",
        "actions": [{ "delete": {} }]
      }
    ]
  }
}'
```

OpenSearch vs Elasticsearch vs Loki vs Clickhouse for log search: Elasticsearch (Elastic, commercial) and OpenSearch (AWS fork, Apache 2.0) are functionally near-identical for most use cases — OpenSearch is the right choice when you want to avoid Elastic's licensing restrictions (SSPL) on self-hosted deployments. Loki (covered in dispatch-1062) stores logs without full-text indexing — it is dramatically cheaper to operate at scale but loses the ability to search across un-labelled fields. If you need to ask "find all logs where the request body contains X" and X is not a pre-defined label, Loki cannot answer efficiently but OpenSearch can. ClickHouse (covered in dispatch-1048) is faster than OpenSearch for high-volume analytical queries on structured log data, but its SQL query model is less ergonomic for ad-hoc log exploration. OpenSearch's Query DSL and Dashboards UI are purpose-built for the log exploration workflow. For teams that need Loki for metric-style aggregations but also require full-text search across log content, running both (Loki for alerts and dashboards, OpenSearch for incident investigation) is the standard two-tier observability pattern.
