The admin API at `:9901` tells you everything. `/stats`, `/clusters`, `/config_dump`.

## Admin API — debugging live configuration

```bash
# Envoy admin endpoint (usually on port 9901 or localhost:15000 in Istio sidecars)
ENVOY_ADMIN=http://localhost:9901

# Dump the full running configuration (listeners + routes + clusters + endpoints)
curl -s $ENVOY_ADMIN/config_dump | jq '.configs[] | .["@type"]'
# "type.googleapis.com/envoy.admin.v3.BootstrapConfigDump"
# "type.googleapis.com/envoy.admin.v3.ListenersConfigDump"
# "type.googleapis.com/envoy.admin.v3.RoutesConfigDump"
# "type.googleapis.com/envoy.admin.v3.ClustersConfigDump"
# "type.googleapis.com/envoy.admin.v3.EndpointsConfigDump"

# List all clusters (upstream services Envoy knows about)
curl -s $ENVOY_ADMIN/clusters | grep "::"
# construx-postgres::default_priority::max_connections: 100
# construx-postgres::default_priority::pending_requests: 0
# construx-postgres::10.0.1.4:5432::cx_active: 14        ← active connections
# construx-postgres::10.0.1.4:5432::cx_connect_fail: 0
# construx-postgres::10.0.1.4:5432::health_flags: healthy

# Check circuit breaker state
curl -s $ENVOY_ADMIN/clusters | grep "overflow\|pending\|rq_retry"
# construx-api::default_priority::rq_retry: 23           ← 23 retries in flight
# construx-api::default_priority::rq_pending: 0

# Dump listeners
curl -s $ENVOY_ADMIN/listeners
# construx_outbound_8080::0.0.0.0:8080
# construx_inbound_8080::0.0.0.0:15006

# View all active connections
curl -s $ENVOY_ADMIN/stats?filter=downstream_cx_active
# http.construx_inbound.downstream_cx_active: 47

# Force a stats reset (useful before running a load test)
curl -X POST $ENVOY_ADMIN/reset_counters
```

## Stats and observability

```bash
# Key stats to monitor — all available via /stats

# Connection pool health
curl -s $ENVOY_ADMIN/stats | grep "upstream_cx"
# cluster.construx-postgres.upstream_cx_active: 14
# cluster.construx-postgres.upstream_cx_connect_fail: 0
# cluster.construx-postgres.upstream_cx_total: 38241
# cluster.construx-postgres.upstream_cx_overflow: 0     ← 0 = pool not saturated

# Circuit breaker activation
curl -s $ENVOY_ADMIN/stats | grep "overflow"
# cluster.construx-api.upstream_rq_pending_overflow: 0
# cluster.construx-api.upstream_rq_retry_overflow: 0    ← 0 = no retry budget exhausted

# Retry statistics
curl -s $ENVOY_ADMIN/stats | grep "retry"
# cluster.construx-api.upstream_rq_retry: 23
# cluster.construx-api.upstream_rq_retry_success: 21
# cluster.construx-api.upstream_rq_retry_limit_exceeded: 2   ← 2 requests gave up after max retries

# gRPC stats
curl -s $ENVOY_ADMIN/stats | grep "grpc"
# cluster.construx-grpc.upstream_rq_grpc_status.0: 1841   ← OK
# cluster.construx-grpc.upstream_rq_grpc_status.14: 3     ← UNAVAILABLE

# Prometheus metrics endpoint (Envoy native, no exporter needed)
curl -s $ENVOY_ADMIN/stats/prometheus | grep 'envoy_cluster_upstream_rq_total'
# envoy_cluster_upstream_rq_total{envoy_cluster_name="construx-api",envoy_response_code="200"} 38241
```

## xDS configuration (how Istio/control planes configure Envoy)

```bash
# xDS: eXtensible Discovery Service — gRPC streaming APIs
# LDS: Listener Discovery Service — creates/updates listeners
# RDS: Route Discovery Service   — HTTP routing rules
# CDS: Cluster Discovery Service — upstream service definitions
# EDS: Endpoint Discovery Service — IP:port of healthy instances

# In Istio: istiod acts as the xDS control plane
# Check what xDS config istiod has pushed to a sidecar
istioctl proxy-config listeners construx-api-6d9f5c4b8-xk2pq.construx
# ADDRESS       PORT  MATCH   DESTINATION
# 0.0.0.0       8080  ALL     Route: construx-api.construx.svc.cluster.local:8080
# 0.0.0.0       5432  ALL     Cluster: outbound|5432||postgres.construx.svc.cluster.local

istioctl proxy-config routes construx-api-6d9f5c4b8-xk2pq.construx
# NAME                                              DOMAINS             MATCH  VIRTUAL SERVICE
# construx-api.construx.svc.cluster.local:8080     construx-api        /*     construx-api-vs

istioctl proxy-config clusters construx-api-6d9f5c4b8-xk2pq.construx
# SERVICE FQDN                                        PORT  SUBSET    DIRECTION  TYPE
# construx-api.construx.svc.cluster.local             8080  -         outbound   EDS
# construx-api.construx.svc.cluster.local             8080  v1        outbound   EDS
# construx-api.construx.svc.cluster.local             8080  v2        outbound   EDS

# Sync status: is the sidecar up-to-date with istiod's config?
istioctl proxy-status
# NAME                                    CLUSTER         CDS     LDS     EDS     RDS     ECDS  ISTIOD
# construx-api-6d9f5c4b8-xk2pq.construx  Kubernetes      SYNCED  SYNCED  SYNCED  SYNCED  N/A   istiod-xxx

# Debug why a request is being rejected
istioctl proxy-config log construx-api-6d9f5c4b8-xk2pq.construx --level debug
kubectl logs construx-api-6d9f5c4b8-xk2pq -c istio-proxy | grep "response_flags"
# [2032-06-05T14:47:03Z] "POST /v1/orders" 503 UO 0 18 3 - "-" "construx-cli/1.4.2"
# UO = Upstream Overflow (circuit breaker triggered)
# UC = Upstream Connection Failure
# NR = No Route found
# UAEX = Unauthorized External Service
```

## Traffic management: VirtualService + DestinationRule

```yaml
# Istio VirtualService: routing rules applied at the Envoy sidecar
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: construx-api
  namespace: construx
spec:
  hosts:
    - construx-api
  http:
    # Route 10% of traffic to v2 (canary deployment)
    - route:
        - destination:
            host: construx-api
            subset: v1
          weight: 90
        - destination:
            host: construx-api
            subset: v2
          weight: 10
      timeout: 5s
      retries:
        attempts: 3
        perTryTimeout: 2s
        retryOn: "gateway-error,connect-failure,retriable-4xx"

---
# DestinationRule: circuit breaker, connection pool limits, mTLS
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: construx-api
  namespace: construx
spec:
  host: construx-api
  trafficPolicy:
    connectionPool:
      tcp:
        maxConnections: 100
      http:
        http2MaxRequests: 1000
        maxRequestsPerConnection: 10
    outlierDetection:
      # Circuit breaker: eject endpoints that fail 5+ times in 30s
      consecutiveGatewayErrors: 5
      interval: 30s
      baseEjectionTime: 30s
      maxEjectionPercent: 50
    tls:
      mode: ISTIO_MUTUAL   # mTLS with Istio-managed certificates
  subsets:
    - name: v1
      labels:
        version: v1
    - name: v2
      labels:
        version: v2
```

Envoy vs nginx vs HAProxy: nginx and HAProxy are static-configured — they reload on config change (nginx: graceful reload, HAProxy: hitless reload). Envoy was designed for dynamic configuration via xDS: a control plane can update routes, clusters, and endpoints in milliseconds via gRPC streaming without any restart or reload. This is why service meshes use Envoy — Istio can update routing rules across every pod in the cluster in under a second. Envoy also natively emits Prometheus metrics and distributed trace spans (Zipkin/Jaeger) for every request, without configuring logging. The trade-off: Envoy uses more memory per sidecar (~50-100MB per pod) and the xDS/proto configuration is complex. For static deployments, nginx or HAProxy are simpler. For dynamic microservices routing, Envoy's xDS model is the right foundation.
