Feature flags decouple deployment from release. You ship the code to production, behind a flag that's off. When ready, flip the flag in PostHog — no deploy, no git operation. If something goes wrong, flip it back.

## Setup

```bash
npm install posthog-js posthog-node
```

```ts
// lib/posthog.ts — server-side client
import { PostHog } from 'posthog-node';

export const posthogServer = new PostHog(process.env.NEXT_PUBLIC_POSTHOG_KEY!, {
  host: process.env.NEXT_PUBLIC_POSTHOG_HOST ?? 'https://app.posthog.com',
  flushAt: 1,
  flushInterval: 0,
});
```

```tsx
// components/PostHogProvider.tsx — already in this project
'use client';
import posthog from 'posthog-js';
import { PostHogProvider as PHProvider } from 'posthog-js/react';
import { useEffect } from 'react';

export function PostHogProvider({ children }: { children: React.ReactNode }) {
  useEffect(() => {
    posthog.init(process.env.NEXT_PUBLIC_POSTHOG_KEY!, {
      api_host: process.env.NEXT_PUBLIC_POSTHOG_HOST,
      person_profiles: 'identified_only',
      capture_pageview: false,
    });
  }, []);

  return <PHProvider client={posthog}>{children}</PHProvider>;
}
```

## Server-side flag evaluation

For Server Components, evaluate flags in the component using the server client. Flags resolved server-side don't add client-side latency and aren't visible in source:

```ts
// app/dashboard/page.tsx
import { posthogServer } from '@/lib/posthog';
import { auth } from '@/auth';

export default async function DashboardPage() {
  const session = await auth();
  const userId = session?.user?.id ?? 'anonymous';

  const isNewDashboardEnabled = await posthogServer.isFeatureEnabled(
    'new-dashboard-ui',
    userId,
    { personProperties: { plan: session?.user?.plan ?? 'free' } },
  );

  return isNewDashboardEnabled ? <NewDashboard /> : <OldDashboard />;
}
```

## Client-side flags

For client-side components, use the PostHog React hook:

```tsx
'use client';
import { useFeatureFlagEnabled } from 'posthog-js/react';

export function CheckoutButton() {
  const isOneClickEnabled = useFeatureFlagEnabled('one-click-checkout');

  if (isOneClickEnabled === undefined) return <Skeleton />;
  if (isOneClickEnabled) return <OneClickCheckout />;
  return <StandardCheckout />;
}
```

The `undefined` state is important — flags take a tick to load. Show a skeleton to avoid layout shift or flickering.

## Percentage rollout

In PostHog dashboard, create a flag with rollout conditions:

```
Flag key: new-editor
Rollout: 15% of users (random, consistent per user ID)
Conditions: plan = 'pro' (only show to pro users)
```

The user ID determines their bucket — the same user always gets the same flag value. This makes rollouts stable: a user who sees the new editor on Monday still sees it on Friday.

## A/B test variant

Beyond boolean flags, multivariate flags support A/B testing:

```ts
// Multivariate flag — returns a string variant
const variant = await posthogServer.getFeatureFlag(
  'checkout-button-copy',
  userId,
);

const buttonCopy = {
  control: 'Buy now',
  variant_a: 'Get started',
  variant_b: 'Continue to payment',
}[variant as string] ?? 'Buy now';
```

PostHog automatically splits traffic between variants and tracks conversion by variant in the Experiments dashboard.

## Bootstrap flags to avoid flicker

Server-rendering flag values as bootstrap data eliminates the client-side flag load:

```ts
// app/layout.tsx
import { posthogServer } from '@/lib/posthog';

export default async function RootLayout({ children }) {
  const session = await auth();
  const userId = session?.user?.id ?? 'anonymous';

  const flags = await posthogServer.getAllFlags(userId);

  return (
    <html>
      <body>
        <PostHogProvider bootstrapData={{ distinctID: userId, featureFlags: flags }}>
          {children}
        </PostHogProvider>
      </body>
    </html>
  );
}
```

Now `useFeatureFlagEnabled` returns synchronously on first render — no undefined state, no skeleton needed.

## Kill switch pattern

For risky features (third-party integrations, new payment flows), wrap in a flag that defaults to off:

```ts
// Always evaluate — even for critical paths
const isStripeV2Enabled = await posthogServer.isFeatureEnabled(
  'stripe-v2-checkout',
  userId,
);

// If the flag doesn't exist or PostHog is down, default to the safe path
const useStripeV2 = isStripeV2Enabled ?? false;
```

`isFeatureEnabled` returns `undefined` if PostHog is unreachable — the `?? false` makes outages fail safe.

## Deployment pattern

1. Ship code behind a disabled flag
2. Enable for 1% → watch error rates
3. Expand to 10% → watch metrics for 24h
4. Expand to 100% → remove the flag from code in next sprint
5. Archive the flag in PostHog

The flag removal step is important. Dead flag code accumulates fast and becomes hard to reason about.
