Next.js middleware runs at the Edge, before requests reach route handlers or pages. It can read and modify requests, redirect, rewrite, and short-circuit with a response — all without the overhead of a full server invocation.

The key constraint: middleware runs on the Edge runtime. No Node.js APIs, no file system access, no native modules. Everything must work in a V8 isolate.

## The basic structure

```ts
// middleware.ts (in the project root)
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

export function middleware(req: NextRequest) {
  return NextResponse.next();
}

// Which paths the middleware runs on
export const config = {
  matcher: [
    // Skip static files and Next.js internals
    '/((?!_next/static|_next/image|favicon.ico|apple-icon|icon).*)',
  ],
};
```

## Authentication guard

The most common middleware use case: redirect unauthenticated users to login:

```ts
// middleware.ts
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

const PROTECTED_PATHS = ['/dashboard', '/settings', '/billing', '/api/user'];
const PUBLIC_PATHS = ['/login', '/signup', '/'];

export async function middleware(req: NextRequest) {
  const path = req.nextUrl.pathname;
  const isProtected = PROTECTED_PATHS.some((p) => path.startsWith(p));

  if (!isProtected) return NextResponse.next();

  const sessionToken = req.cookies.get('session')?.value;

  if (!sessionToken) {
    const loginUrl = new URL('/login', req.url);
    loginUrl.searchParams.set('redirect', path);
    return NextResponse.redirect(loginUrl);
  }

  // Validate the session — must be fast (no DB calls in Edge)
  // JWT verification is fine; DB lookup is not
  try {
    const payload = verifySessionToken(sessionToken);
    
    // Pass user context to downstream routes via headers
    const res = NextResponse.next({
      request: {
        headers: new Headers({
          ...Object.fromEntries(req.headers.entries()),
          'x-user-id': payload.userId,
          'x-user-role': payload.role,
        }),
      },
    });

    return res;
  } catch {
    // Invalid or expired token
    const loginUrl = new URL('/login', req.url);
    loginUrl.searchParams.set('redirect', path);
    const res = NextResponse.redirect(loginUrl);
    res.cookies.delete('session'); // Clear the bad cookie
    return res;
  }
}
```

The `verifySessionToken` function should use a JWT or a HMAC-signed cookie — something that can be verified cryptographically without a database round trip. This is the main reason to prefer signed tokens in middleware: database calls in the Edge add latency and can fail.

## Reading context in route handlers

Middleware sets headers that routes can read:

```ts
// app/dashboard/page.tsx
import { headers } from 'next/headers';

export default async function DashboardPage() {
  const userId = (await headers()).get('x-user-id');
  // userId is guaranteed to be present — middleware redirected if missing
  
  const data = await loadDashboardData(userId!);
  return <Dashboard data={data} />;
}
```

```ts
// app/api/user/route.ts
export async function GET(req: Request) {
  const userId = req.headers.get('x-user-id');
  // Same guarantee from middleware
  
  const user = await db.select().from(users).where(eq(users.id, userId!));
  return Response.json(user[0]);
}
```

## Route rewrites for A/B testing

Middleware can silently rewrite requests to different page implementations:

```ts
export function middleware(req: NextRequest) {
  const path = req.nextUrl.pathname;

  if (path === '/pricing') {
    // 50% of users see the new pricing page
    const bucket = req.cookies.get('ab-bucket')?.value ?? (Math.random() < 0.5 ? 'b' : 'a');
    
    const res = NextResponse.rewrite(
      new URL(bucket === 'b' ? '/pricing-v2' : '/pricing', req.url)
    );
    
    // Set the bucket cookie so the same user always sees the same variant
    if (!req.cookies.get('ab-bucket')) {
      res.cookies.set('ab-bucket', bucket, {
        maxAge: 60 * 60 * 24 * 30, // 30 days
        httpOnly: true,
        sameSite: 'lax',
      });
    }

    return res;
  }

  return NextResponse.next();
}
```

The rewrite changes what page is rendered but not the URL the user sees. `/pricing` stays in the address bar.

## Locale detection and routing

```ts
const SUPPORTED_LOCALES = ['en', 'fr', 'de', 'es'];
const DEFAULT_LOCALE = 'en';

export function middleware(req: NextRequest) {
  const path = req.nextUrl.pathname;

  // Don't redirect if already localised
  const hasLocale = SUPPORTED_LOCALES.some(
    (locale) => path.startsWith(`/${locale}/`) || path === `/${locale}`
  );
  if (hasLocale) return NextResponse.next();

  // Detect from Accept-Language header
  const acceptLanguage = req.headers.get('accept-language') ?? '';
  const preferredLocale = SUPPORTED_LOCALES.find((locale) =>
    acceptLanguage.toLowerCase().includes(locale)
  ) ?? DEFAULT_LOCALE;

  return NextResponse.redirect(
    new URL(`/${preferredLocale}${path}`, req.url)
  );
}
```

## Rate limiting in middleware

Middleware can check a rate limit before the request reaches any business logic:

```ts
// Rate limiting using Upstash Redis (Edge-compatible)
import { Ratelimit } from '@upstash/ratelimit';
import { Redis } from '@upstash/redis';

const ratelimit = new Ratelimit({
  redis: Redis.fromEnv(),
  limiter: Ratelimit.slidingWindow(20, '1 m'),
});

export async function middleware(req: NextRequest) {
  const ip = req.headers.get('cloudfront-viewer-address')?.split(':')[0]
    ?? req.headers.get('x-forwarded-for')?.split(',')[0]
    ?? '127.0.0.1';

  const { success, remaining, reset } = await ratelimit.limit(ip);

  if (!success) {
    return new Response('Too Many Requests', {
      status: 429,
      headers: {
        'Retry-After': String(Math.ceil((reset - Date.now()) / 1000)),
      },
    });
  }

  return NextResponse.next({
    headers: {
      'X-RateLimit-Remaining': String(remaining),
    },
  });
}
```

Upstash Redis is Edge-compatible — it uses HTTP rather than a persistent TCP connection, which is what the Edge runtime requires.

## What not to put in middleware

**Database queries** — the Edge runtime uses HTTP-based database clients (like Neon's `@neondatabase/serverless`) but a DB call on every request adds latency to every page. Use JWTs or signed cookies for session verification; do DB work in route handlers.

**Heavy computation** — middleware runs synchronously on the critical path. Anything CPU-intensive adds latency to every request.

**Large dependencies** — the Edge runtime has a 1MB bundle limit. Import only what you need. Native modules (like bcrypt) don't work at all.

The golden rule for middleware: fast, lightweight, and infallible. Middleware failures affect all routes — any exception crashes the request. Defensive error handling is non-optional.
