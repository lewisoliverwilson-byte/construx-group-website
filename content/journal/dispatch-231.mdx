The Hyve's AI agent has a 50-message context window. It's excellent at answering questions within that window; it's useless for questions that require knowing what was decided six weeks ago in a different channel.

"What did we decide about the API rate limit?" might have been answered three months ago in #backend-discussions. The agent in #engineering-today knows nothing about it.

The solution is persistent semantic memory: embed message history as vectors, store them in PostgreSQL using pgvector, and retrieve relevant past messages when the agent needs to answer a question.

## What vector embeddings are

A vector embedding is a numerical representation of a piece of text — a list of numbers that captures its meaning. Two pieces of text with similar meaning have similar embeddings (small cosine distance). Two pieces of text with different meanings have different embeddings (large cosine distance).

This enables semantic search: given a query ("what did we decide about rate limits?"), find the messages in history whose embeddings are most similar to the query's embedding — regardless of exact keyword matches.

```ts
// Generating an embedding for a message
const embedding = await anthropic.embeddings.create({
  model: 'voyage-3',
  input: message.content,
});
// embedding.data[0].embedding is a 1024-dimensional vector [0.023, -0.41, ...]
```

We use Voyage AI's `voyage-3` model for embeddings (Anthropic's recommended embedding model). Each message is embedded as a 1024-dimensional vector.

## pgvector: storing vectors in PostgreSQL

pgvector is a PostgreSQL extension that adds a `vector` column type and vector similarity operators:

```sql
-- Enable the extension
CREATE EXTENSION IF NOT EXISTS vector;

-- Add vector column to messages
ALTER TABLE messages ADD COLUMN embedding vector(1024);

-- Create an IVFFlat index for approximate nearest-neighbour search
CREATE INDEX messages_embedding_idx ON messages 
  USING ivfflat (embedding vector_cosine_ops) 
  WITH (lists = 100);
```

The IVFFlat index organises vectors into clusters for faster approximate nearest-neighbour search. Without the index, every similarity search scans the entire table.

## The embedding pipeline

Messages are embedded asynchronously, not inline with message delivery. The delivery path must be fast; embedding takes 100-200ms per message.

```ts
// BullMQ worker: embed messages in the background
const embeddingWorker = new Worker('embed-message', async (job) => {
  const { messageId, content, workspaceId } = job.data;
  
  const response = await voyage.embed({
    input: [content],
    model: 'voyage-3',
  });
  
  const embedding = response.data[0].embedding;
  
  await db.update(messages)
    .set({ embedding: sql`${JSON.stringify(embedding)}::vector` })
    .where(eq(messages.id, messageId));
}, { connection: redis });

// When a message is created, queue embedding
await embeddingQueue.add('embed', {
  messageId: message.id,
  content: message.content,
  workspaceId: message.workspaceId,
});
```

Messages without embeddings (older messages or those pending processing) are excluded from semantic search results.

## Retrieval-augmented generation (RAG)

When the AI agent is invoked, we add a retrieval step: find the top 10 most semantically similar messages to the user's query from across the workspace history, and include them in the system prompt.

```ts
async function retrieveRelevantContext(query: string, workspaceId: string): Promise<string> {
  // Embed the query
  const queryEmbedding = await voyage.embed({ input: [query], model: 'voyage-3' });
  const vec = queryEmbedding.data[0].embedding;
  
  // Find the 10 most similar messages in the workspace
  const relevant = await db.execute(sql`
    SELECT m.content, m.created_at, c.name as channel_name
    FROM messages m
    JOIN channels c ON c.id = m.channel_id
    WHERE m.workspace_id = ${workspaceId}
      AND m.embedding IS NOT NULL
    ORDER BY m.embedding <=> ${JSON.stringify(vec)}::vector
    LIMIT 10
  `);
  
  if (relevant.rows.length === 0) return '';
  
  return `
Relevant past messages from workspace history:
${relevant.rows.map((r) => `[${r.channel_name} • ${r.created_at}] ${r.content}`).join('\n')}
  `.trim();
}

// In the agent invocation:
const historicalContext = await retrieveRelevantContext(userMessage, workspaceId);
const systemPrompt = [staticWorkspaceContext, historicalContext].filter(Boolean).join('\n\n');
```

The `<=>` operator in PostgreSQL with pgvector performs cosine distance search — returns the vectors with smallest cosine distance to the query vector.

## The accuracy concern

Semantic search is probabilistic. A search for "API rate limit decision" will retrieve messages about rate limits, but might also surface messages about API design in general, or about rate limits in other contexts (billing rates, ship rates). The retrieval isn't guaranteed to include the specific message the user wants.

Mitigation strategies:

1. **Metadata filtering:** Filter by channel, date range, or author before semantic search. "What did the backend team decide last month?" scopes the retrieval to #backend channel, last 30 days.

2. **Re-ranking:** Retrieve 20 candidates, then re-rank with a more expensive model that understands the full query context.

3. **Transparency:** When the agent uses historical context, attribute it: "Based on a conversation in #backend-discussions on Nov 15: [quote]." The user can verify.

## Implementation status

This is being built in Q1. The embedding pipeline is designed but not deployed. The existing agent runs on the 50-message context window only.

Once deployed, messages will be embedded retroactively (a one-time backfill job for existing message history) and prospectively (the BullMQ worker processes every new message).

The retrieval step adds ~200ms to agent invocation latency (one embedding API call + one indexed vector search). This is acceptable for a feature that unlocks cross-channel memory.

## Why not a dedicated vector database?

Pinecone, Weaviate, and Qdrant are dedicated vector databases. They offer better performance at large scale and more sophisticated filtering options.

For The Hyve's scale (thousands of workspaces, millions of messages), pgvector with IVFFlat indexing is sufficient. The integrated storage (messages and embeddings in the same database) simplifies the architecture — no sync job between the primary database and a vector store.

If we reach the point where pgvector's performance is a bottleneck, migrating to a dedicated vector database is straightforward — the embedding pipeline doesn't care where the vectors are stored.
