TypeScript's value isn't in annotating what already works — it's in making wrong states unrepresentable. The three patterns below aren't clever tricks; they're the natural way to model the problems they solve, and each one eliminates a class of bug entirely.

## Generics with constraints

Generics without constraints are too permissive. Constraints let you write functions that are flexible but still type-safe.

```ts
// Without constraint — works on anything, no type safety
function getProperty<T>(obj: T, key: string) {
  return (obj as any)[key];  // defeats the purpose
}

// With keyof constraint — TypeScript knows the return type
function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const user = { name: 'Lewis', age: 30 };
const name = getProperty(user, 'name');  // string — TypeScript knows this
const age = getProperty(user, 'age');   // number
// getProperty(user, 'email');  // Error: Argument of type '"email"' is not assignable to...
```

A practical pattern: a type-safe `pick` function:

```ts
function pick<T, K extends keyof T>(obj: T, keys: K[]): Pick<T, K> {
  return keys.reduce((acc, key) => {
    acc[key] = obj[key];
    return acc;
  }, {} as Pick<T, K>);
}

const { name, age } = pick(user, ['name', 'age']);
// name: string, age: number — correctly inferred
```

Generic constraints on async functions:

```ts
async function fetchWithRetry<T>(
  fn: () => Promise<T>,
  retries: number = 3,
): Promise<T> {
  let lastError: Error;
  for (let i = 0; i < retries; i++) {
    try {
      return await fn();
    } catch (e) {
      lastError = e as Error;
      await new Promise((r) => setTimeout(r, 1000 * 2 ** i));
    }
  }
  throw lastError!;
}
```

The generic `T` flows through — the caller's return type is preserved without casting.

## Discriminated unions for state modeling

The classic mistake: representing async state with three separate booleans.

```ts
// Wrong — invalid combinations are possible
interface State {
  loading: boolean;
  data: User | null;
  error: string | null;
}
// What does { loading: true, data: someUser, error: 'network error' } mean?
```

A discriminated union makes invalid states unrepresentable:

```ts
type AsyncState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: string };
```

Now TypeScript narrows the type inside conditionals:

```ts
function UserDisplay({ state }: { state: AsyncState<User> }) {
  if (state.status === 'loading') return <Spinner />;
  if (state.status === 'error') return <Error message={state.error} />;
  if (state.status === 'success') return <Profile user={state.data} />;
  return null;  // idle
}
```

Inside `status === 'success'`, TypeScript knows `state.data` exists and is a `User`. Inside `status === 'error'`, it knows `state.error` is a `string`. No nullability guards needed.

For form state:

```ts
type FormState<T> =
  | { stage: 'editing'; values: T; errors: Partial<Record<keyof T, string>> }
  | { stage: 'submitting'; values: T }
  | { stage: 'success'; result: string }
  | { stage: 'failed'; error: string; values: T };
```

This completely describes the form lifecycle. Each stage carries exactly the data it needs — no more, no less.

## Branded types for ID safety

When every entity has a string ID, it's easy to pass the wrong ID to the wrong function. Branded types make this a compile-time error.

```ts
type UserId = string & { readonly __brand: 'UserId' };
type PostId = string & { readonly __brand: 'PostId' };
type VentureId = string & { readonly __brand: 'VentureId' };

function createUserId(id: string): UserId {
  return id as UserId;
}

function createPostId(id: string): PostId {
  return id as PostId;
}
```

```ts
async function deletePost(postId: PostId, userId: UserId): Promise<void> {
  // ...
}

const userId = createUserId('user_123');
const postId = createPostId('post_456');

deletePost(postId, userId);  // ✓ correct
deletePost(userId, postId);  // ✗ Error: Argument of type 'UserId' is not assignable to 'PostId'
```

This catches the classic argument-order bug — passing `userId` where `postId` is expected — at compile time instead of in production.

The brand lives only in the type system; at runtime it's a plain string. No performance cost, no runtime overhead.

```ts
// Pattern: result type for operations that can fail
type Result<T, E = string> =
  | { ok: true; value: T }
  | { ok: false; error: E };

async function validateAndCreateUser(email: string): Promise<Result<UserId>> {
  if (!email.includes('@')) {
    return { ok: false, error: 'Invalid email' };
  }

  const user = await db.insert(users).values({ email }).returning();
  return { ok: true, value: createUserId(user[0].id) };
}

const result = await validateAndCreateUser(email);
if (!result.ok) {
  // result.error is string
  return console.error(result.error);
}
// result.value is UserId
await sendWelcomeEmail(result.value);
```

## Template literal types for string patterns

For strings with structure, template literal types give you compile-time validation:

```ts
type EventName = `${string}:${string}`;  // must contain a colon
type Env = 'dev' | 'staging' | 'prod';
type EnvVar = `${Uppercase<string>}_${Env}`;

type CSSUnit = 'px' | 'rem' | 'em' | 'vw' | 'vh' | '%';
type CSSValue = `${number}${CSSUnit}`;

// Extract parts of a string type
type ExtractEntity<T extends `${string}:${string}`> =
  T extends `${infer Entity}:${string}` ? Entity : never;

type PostEvent = ExtractEntity<'post:created'>;  // 'post'
```

Practical use: typed event bus:

```ts
type AppEvents = {
  'user:created': { userId: UserId; email: string };
  'post:published': { postId: PostId; authorId: UserId };
  'payment:failed': { userId: UserId; amount: number; error: string };
};

function emit<K extends keyof AppEvents>(event: K, payload: AppEvents[K]) {
  // type-safe emit
}

function on<K extends keyof AppEvents>(event: K, handler: (payload: AppEvents[K]) => void) {
  // type-safe subscription
}

// Usage — TypeScript knows the payload shape for each event
emit('user:created', { userId: createUserId('u1'), email: 'test@example.com' });
on('payment:failed', ({ userId, amount, error }) => {
  // userId: UserId, amount: number, error: string — all correctly typed
});
```

These patterns compound: use discriminated unions to model state, branded types to distinguish IDs, generics to write reusable utilities, and template literals to validate string shapes. Each one is additive — they work together without fighting each other.
