date: "2034-03-15"
excerpt: "The Vertical Pod Autoscaler (VPA) automatically sets CPU and memory requests and limits for containers based on observed resource usage. The fundamental problem it solves: Kubernetes resource requests are set by engineers at deployment time, based on estimates that are almost always wrong — either over-provisioned (wasting cluster capacity and money) or under-provisioned (causing OOMKill events and CPU throttling). VPA runs in three modes: Off (just stores recommendations, no changes), Initial (sets requests only when pods are first created), and Auto (updates running pods by evicting and recreating them with new requests). The recommendation algorithm uses a histogram of resource usage over a configurable window (8 days by default) and targets the 90th percentile for requests and 95th percentile for limits. Goldilocks (from Fairwinds) extends VPA in recommendation mode: it runs VPA as a pure advisor and surfaces recommendations through a dashboard, letting engineers review and apply them manually — the safest way to use VPA in production without unexpected pod restarts. The key insight: most Kubernetes clusters have 40-60% of their capacity allocated to over-provisioned requests that never materialise as actual usage. VPA + Goldilocks makes this visible, and applying recommendations consistently reduces cluster cost while improving scheduling density."

## VPA config and Goldilocks recommendations

```yaml
# VPA: recommendation mode (no automatic pod restarts)
# Reads recommendations via kubectl describe vpa, or via Goldilocks dashboard

apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: orders-api
  namespace: construx-prod
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: orders-api

  updatePolicy:
    updateMode: "Off"    # Off = recommendation only, no automatic changes

  resourcePolicy:
    containerPolicies:
      - containerName: orders-api
        minAllowed:
          cpu: 50m
          memory: 64Mi
        maxAllowed:
          cpu: 4
          memory: 4Gi
        controlledResources: ["cpu", "memory"]
        controlledValues: RequestsAndLimits
```

```bash
# Read VPA recommendations (after Off-mode VPA has collected 24h+ of data)
kubectl describe vpa orders-api -n construx-prod

# Output (showing over-provisioning):
# Status:
#   Recommendation:
#     Container Recommendations:
#       Container Name:  orders-api
#       Lower Bound:
#         Cpu:     50m
#         Memory:  128Mi
#       Target:
#         Cpu:     120m      ← currently set to 500m (4x over-provisioned)
#         Memory:  256Mi     ← currently set to 1Gi (4x over-provisioned)
#       Uncapped Target:
#         Cpu:     120m
#         Memory:  236Mi
#       Upper Bound:
#         Cpu:     340m
#         Memory:  512Mi

# Apply VPA recommendations manually after review
# (safer than Auto mode for production workloads)
kubectl patch deployment orders-api -n construx-prod --type='json' -p='[
  {"op": "replace", "path": "/spec/template/spec/containers/0/resources/requests/cpu",    "value": "120m"},
  {"op": "replace", "path": "/spec/template/spec/containers/0/resources/requests/memory", "value": "256Mi"},
  {"op": "replace", "path": "/spec/template/spec/containers/0/resources/limits/cpu",      "value": "340m"},
  {"op": "replace", "path": "/spec/template/spec/containers/0/resources/limits/memory",   "value": "512Mi"}
]'

# Goldilocks: enable VPA recommendations for a namespace
kubectl label namespace construx-prod goldilocks.fairwinds.com/enabled=true

# Goldilocks dashboard: port-forward to see all recommendations
kubectl port-forward -n goldilocks svc/goldilocks-dashboard 8080:80
# Browse to http://localhost:8080 to see all VPAs and recommendations

# Goldilocks CLI: show all recommendations in a namespace
kubectl get verticalpodautoscalers -n construx-prod -o json | \
  jq '.items[] | {
    name: .metadata.name,
    current_cpu: .spec.resourcePolicy.containerPolicies[0].minAllowed.cpu,
    recommended_cpu: .status.recommendation.containerRecommendations[0].target.cpu,
    current_mem: .spec.resourcePolicy.containerPolicies[0].minAllowed.memory,
    recommended_mem: .status.recommendation.containerRecommendations[0].target.memory
  }'
```

```yaml
# Cluster-wide VPA deployment: install the VPA components
# Fair usage: VPA admission controller only modifies pods that have a VPA object

# Install VPA CRDs and components
kubectl apply -f https://raw.githubusercontent.com/kubernetes/autoscaler/master/vertical-pod-autoscaler/deploy/vpa-v1-crd-gen.yaml
kubectl apply -f https://raw.githubusercontent.com/kubernetes/autoscaler/master/vertical-pod-autoscaler/deploy/vpa-rbac.yaml

# VPA components:
# - vpa-recommender: watches CPU/memory usage, computes recommendations
# - vpa-admission-controller: injects recommended resources at pod creation (Initial/Auto mode)
# - vpa-updater: evicts pods that are significantly off the recommendation (Auto mode only)

# Goldilocks Helm deployment
helm upgrade --install goldilocks \
  fairwinds-stable/goldilocks \
  --namespace goldilocks \
  --create-namespace \
  --set controller.flags.vpa-update-mode=off \   # recommendation-only mode
  --set dashboard.replicaCount=1

# Alert: workload with resources significantly over VPA recommendation
# (Prometheus rule to surface right-sizing opportunities)
- alert: OverProvisionedCpu
  expr: |
    (
      kube_pod_container_resource_requests{resource="cpu", namespace=~"construx-.*"}
      /
      label_replace(
        kube_verticalpodautoscaler_status_recommendation_containerrecommendations_target{resource="cpu"},
        "pod", "$1", "pod", "(.*)"
      )
    ) > 3   # current request > 3x VPA recommendation
  for: 1h
  labels:
    severity: info
  annotations:
    summary: "Container {{ $labels.container }} in {{ $labels.namespace }} is 3x over-provisioned on CPU"
```

VPA vs HPA vs KEDA vs manual right-sizing vs node auto-provisioner: HPA (Horizontal Pod Autoscaler) scales replica count based on CPU/memory utilisation or custom metrics — it assumes you've set correct resource requests. If requests are set too high, HPA never scales down because utilisation (actual/requested) appears low. VPA and HPA are complementary: VPA sets the correct requests; HPA scales replicas based on those correct requests. KEDA (Kubernetes Event-driven Autoscaling) scales based on external event sources (queue depth, message lag, DB query results) — it extends HPA with custom scalers rather than replacing the vertical dimension. Manual right-sizing without VPA is what most teams do: ad hoc Prometheus queries, manual adjustment, then forgetting again until the next OOMKill incident. The VPA + Goldilocks combination is the correct production pattern: run in Off mode to collect data without disruption, review Goldilocks dashboard weekly, apply recommendations to each service during the normal deployment cycle. Auto mode is appropriate for batch workloads (Argo Workflows steps, Spark executors) where pod restarts are acceptable; for stateful services and databases, Off mode + manual application is safer.
