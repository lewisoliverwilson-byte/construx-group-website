Observability is the ability to understand a system's internal state from its external outputs. The three pillars: metrics (what is happening), logs (what happened), traces (why it happened). A dashboard is metrics made visible.

The question isn't "what can I measure?" It's "what do I need to know to detect and diagnose failures fast?"

## The four golden signals

Google SRE coined the four golden signals. They apply to any service:

**Latency** — how long requests take. Not just average — p50, p95, p99. The average hides tail latency that affects 1% of users, which at scale is a lot of users.

**Traffic** — how many requests per second. Sudden drops indicate a problem as clearly as sudden spikes.

**Errors** — the error rate. Split by 4xx (client errors) and 5xx (server errors). A spike in 4xx might be normal (bots); a spike in 5xx is your service breaking.

**Saturation** — how "full" your service is. CPU, memory, connection pool utilisation. Saturation predicts failure before it happens.

## PostHog for product metrics

PostHog handles user-facing metrics — what users are doing in the product. Custom events track the things that matter:

```ts
// lib/analytics.ts
import PostHog from 'posthog-node';

const posthog = new PostHog(process.env.POSTHOG_KEY!, {
  host: process.env.POSTHOG_HOST,
});

export function track(event: string, properties?: Record<string, unknown>) {
  posthog.capture({ distinctId: 'server', event, properties });
}

export function trackUser(userId: string, event: string, properties?: Record<string, unknown>) {
  posthog.capture({ distinctId: userId, event, properties });
}
```

Events to track at the product level:
- Feature adoption (did users actually use the feature you shipped?)
- Conversion funnel drop-off (where in the flow do users leave?)
- Search quality (what do users search for, what do they click?)
- AI response quality (thumbs up/down on generated content)

## Structured logging for operational metrics

Structured logs are queryable. A log line that's a JSON object can be filtered, aggregated, and graphed. A log line that's a string can only be text-searched.

```ts
// lib/logger.ts
export function log(level: 'info' | 'warn' | 'error', message: string, data?: Record<string, unknown>) {
  const entry = {
    ts: new Date().toISOString(),
    level,
    message,
    ...data,
  };
  console.log(JSON.stringify(entry));
}

// Usage
log('info', 'api.request', {
  method: req.method,
  path: pathname,
  duration_ms: Date.now() - startTime,
  status: 200,
  user_id: session?.userId,
});

log('error', 'api.error', {
  path: pathname,
  error: err.message,
  stack: err.stack,
});
```

AWS Amplify sends function logs to CloudWatch. With structured JSON output, CloudWatch Insights can query: "give me the p99 latency for the `/api/scan` endpoint over the last hour."

## The dashboard

A useful dashboard has three tiers:

**Top-level health** — one panel that answers "is the system up?" for each critical endpoint. Traffic, error rate, p50/p99 latency. If these look normal, everything else can wait.

**Service detail** — per-service breakdowns. For an AI product: Claude API call volume, token costs, cache hit rate, error types. For a background job system: queue depth, job success rate, processing time.

**Business metrics** — user signups, active sessions, feature usage. These move slower than operational metrics but tell you if the service is doing what it's supposed to do.

## Alerting rules

Alerts should wake someone up only when action is required. Noisy alerts get ignored.

Rules that work:
- Error rate above 1% for 5 minutes → page
- p99 latency above 5s for 3 minutes → page
- Zero traffic for 10 minutes (outside maintenance windows) → page
- Claude API quota at 80% → Slack notification
- DB connection pool utilisation above 80% → Slack notification

Rules that don't work:
- CPU above 70% for 1 minute (too sensitive, CPU spikes are normal)
- Any 5xx error (a single error shouldn't wake anyone)

The threshold calibration comes from knowing what's normal. Baseline your metrics during a typical week before setting alert thresholds.

## Making data useful

Raw numbers aren't useful. Context is:
- Latency is 400ms. Is that normal? Is the baseline 100ms or 800ms?
- Error rate is 0.3%. Is that up or down from yesterday?

Every panel should show a comparison period — "this week vs last week" or "now vs 7 days ago." Anomalies are only visible relative to a baseline.

The second thing that makes data useful: acting on it. A dashboard that gets opened only when something is already broken is a post-mortem tool, not an observability tool. The weekly ritual of reviewing metrics during normal operation builds the baseline knowledge that makes dashboards meaningful under pressure.
