An optimistic update shows the user what they expect to see before the server confirms it. Clicking "like" increments the count immediately — the server call happens in the background. If the server fails, you roll back. If it succeeds, the UI is already correct.

The tradeoff: the UI assumes success. When the server fails (rarely), you need to roll back cleanly. This is manageable. The alternative — waiting for the server on every interaction — adds hundreds of milliseconds of perceptible latency to every tap.

## With React Query

React Query's `useMutation` has built-in optimistic update support:

```tsx
import { useMutation, useQueryClient } from '@tanstack/react-query';

type Post = { id: string; likeCount: number; likedByMe: boolean };

function LikeButton({ post }: { post: Post }) {
  const queryClient = useQueryClient();

  const { mutate: toggleLike } = useMutation({
    mutationFn: (postId: string) =>
      fetch(`/api/posts/${postId}/like`, { method: 'POST' }).then((r) => r.json()),

    onMutate: async (postId) => {
      // Cancel any in-flight fetches for this query
      await queryClient.cancelQueries({ queryKey: ['post', postId] });

      // Snapshot the previous value
      const previousPost = queryClient.getQueryData<Post>(['post', postId]);

      // Optimistically update
      queryClient.setQueryData<Post>(['post', postId], (old) => ({
        ...old!,
        likeCount: old!.likedByMe ? old!.likeCount - 1 : old!.likeCount + 1,
        likedByMe: !old!.likedByMe,
      }));

      // Return context for rollback
      return { previousPost };
    },

    onError: (err, postId, context) => {
      // Roll back to the snapshot
      queryClient.setQueryData(['post', postId], context?.previousPost);
    },

    onSettled: (data, error, postId) => {
      // Always refetch to sync with server truth
      queryClient.invalidateQueries({ queryKey: ['post', postId] });
    },
  });

  return (
    <button onClick={() => toggleLike(post.id)}>
      {post.likedByMe ? '♥' : '♡'} {post.likeCount}
    </button>
  );
}
```

`onMutate` → apply optimistic change
`onError` → roll back
`onSettled` → invalidate and refetch regardless of outcome

## With Next.js Server Actions and useOptimistic

React 19 ships `useOptimistic` — a hook designed for this exact pattern:

```tsx
'use client';

import { useOptimistic, useTransition } from 'react';

async function toggleLikeAction(postId: string, likedByMe: boolean) {
  'use server';
  if (likedByMe) {
    await removeLike(postId);
  } else {
    await addLike(postId);
  }
}

function LikeButton({ post }: { post: Post }) {
  const [isPending, startTransition] = useTransition();
  const [optimisticPost, setOptimisticPost] = useOptimistic(
    post,
    (state, action: 'like' | 'unlike') => ({
      ...state,
      likeCount: action === 'like' ? state.likeCount + 1 : state.likeCount - 1,
      likedByMe: action === 'like',
    }),
  );

  const handleClick = () => {
    startTransition(async () => {
      // Apply optimistic update
      setOptimisticPost(optimisticPost.likedByMe ? 'unlike' : 'like');
      // Call server action
      await toggleLikeAction(post.id, optimisticPost.likedByMe);
    });
  };

  return (
    <button onClick={handleClick} disabled={isPending}>
      {optimisticPost.likedByMe ? '♥' : '♡'} {optimisticPost.likeCount}
    </button>
  );
}
```

`useOptimistic` works with React's concurrent rendering. When the transition completes, the optimistic state collapses to the actual post value returned by the server. If the server action throws, the optimistic state is discarded and the real value is used.

## List mutations — adding and removing items

The most common case: adding an item to a list without waiting for the server:

```tsx
function TodoList({ initialItems }: { initialItems: Todo[] }) {
  const [isPending, startTransition] = useTransition();
  const [optimisticItems, addOptimisticItem] = useOptimistic(
    initialItems,
    (state, newItem: Todo) => [...state, newItem],
  );

  const handleAdd = (text: string) => {
    const tempItem: Todo = {
      id: `temp-${Date.now()}`,
      text,
      completed: false,
    };

    startTransition(async () => {
      addOptimisticItem(tempItem);
      await createTodo(text);  // Server action — revalidates the list
    });
  };

  return (
    <ul>
      {optimisticItems.map((item) => (
        <li key={item.id} style={{ opacity: item.id.startsWith('temp-') ? 0.6 : 1 }}>
          {item.text}
        </li>
      ))}
    </ul>
  );
}
```

The temporary `id` prefix lets you style in-flight items differently — a subtle opacity reduction signals "saving..." without blocking the user.

## Handling conflicts

When the server returns a different value than the optimistic one, you have a conflict. The general rule: trust the server. After `onSettled`, always invalidate and refetch. The brief flash from optimistic-to-real is acceptable when rare. Never try to merge conflicting values client-side.

For operations that must be conflict-free (financial transactions, inventory), don't use optimistic updates. Show a loading state. The latency is worth the accuracy guarantee.

The mental model: optimistic updates are a UX enhancement, not a data strategy. The server is truth. The client is hopeful.
