Kafka is not a message queue in the traditional sense. A queue removes messages after they're consumed. Kafka keeps all messages for a retention period (default: 7 days) and lets any number of consumers read from any position. This changes what you can build: multiple independent consumers can process the same events simultaneously, and a new consumer can replay the entire history.

## Core concepts

**Topic**: a named, ordered log of events. Think of it like a database table — append-only, with each row being one event.

**Partition**: each topic is split into N partitions for parallel writes. Events within a partition are ordered; events across partitions are not.

**Offset**: the position of an event within a partition. Consumers commit their offset to track progress.

**Consumer group**: a set of consumers that share a topic's partitions. Each partition is assigned to one consumer in the group. If you have 4 partitions and 2 consumers, each consumer gets 2 partitions — parallel processing.

**Retention**: events are stored for a configurable duration (`log.retention.hours`) or up to a configurable size (`log.retention.bytes`). After retention expires, events are deleted.

## Basic producer and consumer (Node.js)

```bash
npm install kafkajs
```

```ts
// lib/kafka.ts
import { Kafka } from 'kafkajs';

export const kafka = new Kafka({
  clientId: 'construx-api',
  brokers:  ['kafka-1:9092', 'kafka-2:9092', 'kafka-3:9092'],
  ssl:      true,
  sasl: {
    mechanism: 'scram-sha-256',
    username:  process.env.KAFKA_USERNAME!,
    password:  process.env.KAFKA_PASSWORD!,
  },
});
```

```ts
// Producer
const producer = kafka.producer();
await producer.connect();

await producer.send({
  topic: 'order-events',
  messages: [
    {
      key:   'order-123',  // partition by order ID — same order always same partition
      value: JSON.stringify({
        type:      'order.placed',
        orderId:   'order-123',
        userId:    'user-456',
        totalCents: 4999,
        timestamp:  new Date().toISOString(),
      }),
    },
  ],
});

await producer.disconnect();
```

```ts
// Consumer
const consumer = kafka.consumer({ groupId: 'order-processor' });
await consumer.connect();
await consumer.subscribe({ topic: 'order-events', fromBeginning: false });

await consumer.run({
  eachMessage: async ({ topic, partition, message }) => {
    const event = JSON.parse(message.value!.toString());

    if (event.type === 'order.placed') {
      await processOrder(event);
    }
    // Offset committed automatically after eachMessage returns
  },
});
```

## Exactly-once semantics

By default, Kafka guarantees at-least-once delivery — a message may be delivered more than once if the consumer crashes before committing its offset. For idempotent processing:

```ts
// Option 1: make your handler idempotent (preferred)
async function processOrder(event: OrderEvent) {
  const existing = await db.order.findUnique({ where: { id: event.orderId } });
  if (existing?.status === 'processed') return;  // already done
  // ... process
}

// Option 2: Kafka transactions (complex, requires specific broker config)
const producer = kafka.producer({ transactional: true });
await producer.transaction().send({ /* ... */ }).commit();
```

Idempotent processing is simpler and handles the vast majority of cases.

## Partitioning strategy

```ts
// Partition by entity ID for ordering guarantees
await producer.send({
  topic: 'order-events',
  messages: [{
    key:   event.orderId,  // all events for this order go to the same partition
    value: JSON.stringify(event),
  }],
});
```

Events with the same key go to the same partition, preserving order per entity. If you don't need ordering, use `null` keys — events distribute round-robin across partitions.

## Schema registry

Raw JSON in Kafka is a maintenance problem: if a producer changes a field name, all consumers break silently. A schema registry (Confluent Schema Registry, Redpanda's built-in) enforces a contract:

```ts
// Producer: encode with schema
import { SchemaRegistry } from '@kafkajs/confluent-schema-registry';

const registry = new SchemaRegistry({ host: 'https://schema-registry:8081' });
const schemaId = await registry.getLatestSchemaId('order-events-value');

const encoded = await registry.encode(schemaId, event);
await producer.send({ topic: 'order-events', messages: [{ value: encoded }] });

// Consumer: decode with schema
const decoded = await registry.decode(message.value);
```

Schemas are versioned. Breaking changes are rejected at the producer side before reaching consumers.

## Kafka vs Redis Streams vs RabbitMQ

| Feature             | Kafka                    | Redis Streams           | RabbitMQ               |
|---------------------|--------------------------|-------------------------|------------------------|
| Retention           | Days/weeks               | Configurable (trimmed)  | ACK-based removal      |
| Replay              | Yes (from any offset)    | Yes (from any offset)   | No                     |
| Throughput          | Millions/s               | Hundreds of thousands/s | Thousands/s            |
| Operational cost    | High (cluster, Zookeeper)| Low (one Redis)         | Medium                 |
| Message ordering    | Per partition            | Per stream              | Per queue              |

Kafka is right for: high-throughput event streams, event sourcing, audit logs, real-time analytics pipelines. Redis Streams work for most application-scale use cases with lower operational overhead. RabbitMQ is for traditional message queue patterns with complex routing.

For most web applications: Redis Streams or a managed Kafka-compatible service (Upstash Kafka, Confluent Cloud, Redpanda) rather than self-hosted Kafka.
