excerpt: "Knative Serving is a Kubernetes extension for deploying serverless containers — it adds autoscaling (including scale-to-zero), traffic splitting across revisions, and a URL-based routing model on top of standard Kubernetes Deployments. The core concept is the Revision: each deployment of a Knative Service creates a new Revision, and traffic can be split between revisions by percentage — 90% to revision-v3, 10% to revision-v4 for canary testing. Revisions can scale to zero when there are no requests, with a configurable cold start buffer (keep-alive replicas). Knative's autoscaler (KPA — Knative Pod Autoscaler) uses concurrent request count rather than CPU as the scaling metric — it targets a configurable number of concurrent requests per pod, scaling up when the actual concurrency exceeds the target and down when it drops. The KPA can respond to traffic changes within seconds (faster than HPA's 15-second polling interval), making it well-suited for bursty serverless workloads. Knative Serving integrates with Istio (or Contour, or Kourier) for traffic routing and mTLS. The Queue Proxy sidecar (injected by Knative into each pod) reports request counts to the Autoscaler and handles graceful drain during scale-down. At Construx, Knative Serving handles webhook processing and scheduled report generation — workloads that need to scale to zero overnight and back to multiple replicas within seconds when traffic arrives."

## Knative Service configuration and traffic management

```yaml
# Knative Service: deploys a serverless container with autoscaling
# Integrates with Istio for routing — creates VirtualService automatically

apiVersion: serving.knative.dev/v1
kind: Service
metadata:
  name: webhook-processor
  namespace: construx-prod
  annotations:
    # Autoscaling: target 50 concurrent requests per pod
    autoscaling.knative.dev/target: "50"
    autoscaling.knative.dev/metric: "concurrency"

    # Scale-to-zero: scale down after 300s of no traffic
    autoscaling.knative.dev/scale-to-zero-grace-period: "300s"

    # Initial scale: start with 1 pod immediately on first request (avoid cold start)
    autoscaling.knative.dev/initial-scale: "1"

    # Min/max replicas
    autoscaling.knative.dev/min-scale: "0"     # 0 = scale to zero
    autoscaling.knative.dev/max-scale: "50"

spec:
  template:
    metadata:
      annotations:
        # Concurrency limit: max concurrent requests per pod before scaling
        autoscaling.knative.dev/target: "50"
    spec:
      containerConcurrency: 100   # max concurrent requests per container instance
      timeoutSeconds: 300         # request timeout

      containers:
        - image: ghcr.io/construx/webhook-processor:latest
          ports:
            - containerPort: 8080

          resources:
            requests:
              cpu: "200m"
              memory: "256Mi"
            limits:
              cpu: "1"
              memory: "1Gi"

          env:
            - name: MAX_WORKERS
              value: "10"

          readinessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 3
            periodSeconds: 5

  traffic:
    - latestRevision: true
      percent: 100   # all traffic to latest revision
```

```yaml
# Traffic splitting: canary deployment between revisions
# Route 90% to stable, 10% to canary

apiVersion: serving.knative.dev/v1
kind: Service
metadata:
  name: orders-api-knative
  namespace: construx-prod
spec:
  template:
    metadata:
      name: orders-api-v4   # explicit revision name
    spec:
      containers:
        - image: ghcr.io/construx/orders-api:v4.0.0

  traffic:
    - revisionName: orders-api-v3
      percent: 90
      tag: stable     # accessible at stable-orders-api-knative.construx-prod.svc.cluster.local

    - revisionName: orders-api-v4
      percent: 10
      tag: canary     # accessible at canary-orders-api-knative.construx-prod.svc.cluster.local

    - latestRevision: true
      percent: 0      # latest revision gets 0% production traffic (canary testing first)
      tag: latest

---
# Promote canary to 100% (no downtime — Knative revision stays warm)
apiVersion: serving.knative.dev/v1
kind: Service
metadata:
  name: orders-api-knative
  namespace: construx-prod
spec:
  traffic:
    - revisionName: orders-api-v4
      percent: 100
      tag: stable
```

```bash
# Knative CLI (kn): service management

# List all Knative Services and their traffic configuration
kn service list -n construx-prod

# Output:
# NAME                NAMESPACE      URL                                          READY   AGE
# webhook-processor   construx-prod  https://webhook-processor.construx.io        True    14d
# orders-api-knative  construx-prod  https://orders-api.construx.io               True    7d

# Describe a service (shows revisions and traffic)
kn service describe webhook-processor -n construx-prod

# List revisions (all deployed versions)
kn revision list -n construx-prod --service webhook-processor

# Scale to zero manually (for cost savings during maintenance)
kn service update webhook-processor -n construx-prod \
  --annotation autoscaling.knative.dev/min-scale=0 \
  --annotation autoscaling.knative.dev/initial-scale=0

# Check current scaling state (replica count)
kubectl get pods -n construx-prod -l serving.knative.dev/service=webhook-processor
# No resources found — scaled to zero

# Send a test request (triggers cold start, then processing)
curl -H "Host: webhook-processor.construx-prod.svc.cluster.local" \
  https://webhook-processor.construx.io/webhook \
  -d '{"event": "order.created", "orderId": "ord_1234"}'

# View autoscaler metrics
kubectl describe podautoscaler webhook-processor-xxxxx -n construx-prod
# Status:
#   Desired Scale: 0
#   Actual Scale: 0
#   Ready Pods:   0
# Conditions:
#   ScaleTargetInitialized: True
#   Active: False "No traffic"
```

Knative Serving vs KEDA vs AWS Lambda vs standard Deployment + HPA vs Google Cloud Run: AWS Lambda and Google Cloud Run are managed serverless platforms — zero Kubernetes to manage, instant global availability, and pay-per-invocation billing. The trade-off is platform lock-in and less container control. Knative Serving brings the same model (scale-to-zero, revision-based traffic splitting) to self-hosted Kubernetes, allowing teams to run Lambda-style workloads on their own infrastructure. Standard Deployment + HPA doesn't scale to zero — you always pay for at least one pod. KEDA (dispatch-1128) can scale to zero using event-driven metrics (queue depth), but it's designed for event-driven batch processing (ScaledJob) rather than HTTP request serving. The key difference between KEDA and Knative for HTTP: Knative's Queue Proxy holds incoming HTTP requests during cold start (the activator keeps them warm while the pod starts up), so the caller waits rather than getting an error. KEDA has no such mechanism for HTTP workloads without the HTTP Add-on. Knative's traffic splitting is unique among these options — no other Kubernetes tool provides revision-level canary deployment at the routing layer without an Istio VirtualService. For Construx, Knative handles workloads where scale-to-zero economics matter (overnight batch triggers, webhook handlers with sporadic traffic) and KEDA handles queue-driven batch jobs (image processing, ML inference).
