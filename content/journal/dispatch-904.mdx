Unlike InfluxDB or Prometheus (purpose-built TSDBs with their own query languages), TimescaleDB is pure PostgreSQL — the same SQL, JOINs to relational tables, and existing tooling. A hypertable transparently partitions data into chunks by time interval; TimescaleDB routes inserts and queries to the right chunks automatically. Continuous aggregates pre-compute rollups incrementally, making dashboard queries over months of data fast without materialising the full table."

Hypertables partition by time. Continuous aggregates pre-compute rollups. It's still SQL.

## Creating hypertables and inserting data

```sql
-- TimescaleDB extension
CREATE EXTENSION IF NOT EXISTS timescaledb;

-- Regular table first
CREATE TABLE metrics (
    time        TIMESTAMPTZ NOT NULL,
    service     TEXT        NOT NULL,
    metric_name TEXT        NOT NULL,
    value       DOUBLE PRECISION NOT NULL,
    labels      JSONB
);

-- Convert to hypertable — TimescaleDB partitions it by time automatically
-- chunk_time_interval: each chunk covers 1 day of data
SELECT create_hypertable('metrics', by_range('time', INTERVAL '1 day'));

-- Insert metrics as normal — TimescaleDB routes to the right chunk
INSERT INTO metrics VALUES
    (NOW(), 'construx-api', 'request_duration_ms', 4.2,  '{"method":"POST","path":"/api/orders"}'::jsonb),
    (NOW(), 'construx-api', 'request_duration_ms', 2.1,  '{"method":"GET","path":"/api/orders"}'),
    (NOW(), 'postgres',     'active_connections',   42,   '{"pool":"primary"}'),
    (NOW(), 'nats',         'messages_per_sec',     1284, '{"subject":"orders.created"}');

-- View chunk information — one chunk per time interval
SELECT chunk_schema, chunk_name, range_start, range_end
FROM timescaledb_information.chunks
WHERE hypertable_name = 'metrics'
ORDER BY range_start DESC
LIMIT 5;
-- chunk_schema | chunk_name | range_start              | range_end
-- _timescaledb_internal | _hyper_1_42_chunk | 2032-03-25 00:00:00+00 | 2032-03-26 00:00:00+00
-- _timescaledb_internal | _hyper_1_41_chunk | 2032-03-24 00:00:00+00 | 2032-03-25 00:00:00+00
```

## Time-series SQL functions

```sql
-- time_bucket: group by time interval (replaces date_trunc for time-series)
-- Average request latency per 5-minute bucket for the last 6 hours
SELECT
    time_bucket('5 minutes', time) AS bucket,
    service,
    AVG(value)  AS avg_ms,
    MAX(value)  AS p99_proxy,   -- Approximation: use percentile_agg for true p99
    COUNT(*)    AS samples
FROM metrics
WHERE
    metric_name = 'request_duration_ms'
    AND time > NOW() - INTERVAL '6 hours'
GROUP BY bucket, service
ORDER BY bucket DESC;

-- time_bucket_gapfill: fill gaps where no data was written
-- Useful for dashboards that must show empty intervals
SELECT
    time_bucket_gapfill('5 minutes', time) AS bucket,
    service,
    AVG(value) AS avg_ms,
    LOCF(AVG(value)) AS avg_ms_filled    -- Last Observation Carried Forward for gaps
FROM metrics
WHERE
    metric_name = 'request_duration_ms'
    AND time BETWEEN NOW() - INTERVAL '1 hour' AND NOW()
GROUP BY bucket, service;

-- Percentile aggregation (hyperloglog-based, approximate but fast)
-- Requires the timescaledb_toolkit extension
SELECT
    time_bucket('5 minutes', time) AS bucket,
    approx_percentile(0.99, percentile_agg(value)) AS p99_ms,
    approx_percentile(0.50, percentile_agg(value)) AS p50_ms
FROM metrics
WHERE metric_name = 'request_duration_ms'
    AND time > NOW() - INTERVAL '1 hour'
GROUP BY bucket
ORDER BY bucket;
```

## Continuous aggregates — incremental pre-computation

```sql
-- Continuous aggregate: a materialised view that updates incrementally
-- TimescaleDB only re-computes changed time buckets, not the full table
-- Makes dashboard queries over months of data fast

CREATE MATERIALIZED VIEW metrics_hourly
WITH (timescaledb.continuous) AS
SELECT
    time_bucket('1 hour', time) AS bucket,
    service,
    metric_name,
    AVG(value)   AS avg_value,
    MAX(value)   AS max_value,
    MIN(value)   AS min_value,
    COUNT(*)     AS sample_count
FROM metrics
GROUP BY bucket, service, metric_name
WITH NO DATA;

-- Populate the view for historical data
CALL refresh_continuous_aggregate('metrics_hourly', NULL, NOW());

-- Set automatic refresh policy: refresh every 1 hour, covering last 6 hours
SELECT add_continuous_aggregate_policy('metrics_hourly',
    start_offset => INTERVAL '6 hours',
    end_offset   => INTERVAL '1 hour',    -- Don't refresh last hour (data still arriving)
    schedule_interval => INTERVAL '1 hour'
);

-- Now query the aggregate — sub-millisecond even for months of data
SELECT bucket, service, avg_value, max_value
FROM metrics_hourly
WHERE
    metric_name = 'request_duration_ms'
    AND bucket > NOW() - INTERVAL '7 days'
ORDER BY bucket DESC;
```

## Data retention and compression

```sql
-- Compression: columnar compression for old chunks
-- Typically 90-95% size reduction for time-series data

-- Enable compression on the hypertable
ALTER TABLE metrics SET (
    timescaledb.compress,
    timescaledb.compress_orderby = 'time DESC',
    timescaledb.compress_segmentby = 'service, metric_name'
);

-- Add a compression policy: compress chunks older than 7 days
SELECT add_compression_policy('metrics', INTERVAL '7 days');

-- Check compression ratio
SELECT
    chunk_name,
    before_compression_total_bytes,
    after_compression_total_bytes,
    round(100 - (after_compression_total_bytes::numeric /
                 before_compression_total_bytes::numeric) * 100, 1) AS compression_pct
FROM chunk_compression_stats('metrics')
ORDER BY chunk_name;
-- chunk_name       | before_bytes | after_bytes | compression_pct
-- _hyper_1_35_chunk | 482,124,800  | 28,311,040  | 94.1%  ← 94% compression

-- Data retention: drop chunks older than 90 days
SELECT add_retention_policy('metrics', INTERVAL '90 days');

-- Manual chunk inspection
SELECT * FROM timescaledb_information.hypertables;
-- total_chunks: 90, compression_enabled: true, replication_factor: 1
```

TimescaleDB vs InfluxDB vs Prometheus: Prometheus is a pull-based metrics store with a 2-week default retention, designed for real-time alerting — not long-term storage. InfluxDB has its own query language (Flux) and is optimised for high-ingest write throughput. TimescaleDB's advantage is SQL compatibility: you can JOIN metrics to your orders table, use familiar PostgreSQL tools, and run the same database for both transactional data and time-series metrics. The operational win is real — one database to backup, monitor, and understand instead of three. The tradeoff: TimescaleDB's write throughput peaks around 1-2M rows/second per node, where a purpose-built TSDB like InfluxDB or ClickHouse can ingest 10x that.
