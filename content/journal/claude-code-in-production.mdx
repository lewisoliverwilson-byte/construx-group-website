The most common misconception about AI-assisted development is that it's autocomplete at scale — you type a prompt, you paste the output. That's not how we work, and in our experience, it's not how you get production-quality software out of it.

Claude Code is the primary development tool at Construx. Here's what that actually means in practice.

## The role it plays

We think of Claude Code as a technical collaborator, not a code generator. The distinction shapes everything about how you interact with it.

A code generator takes a specification and outputs code. You evaluate the output, decide whether it's right, and fix what's wrong. The cognitive load is still with you, the human — you're just skipping the typing.

A technical collaborator holds context across the project, understands the architectural decisions you've already made, asks clarifying questions when the spec is ambiguous, and pushes back when it thinks you're going in the wrong direction. Claude Code, given enough project context, does all of those things.

The practical result: design conversations happen in plain language. "I need a vector search over the project history that prioritises recent content and boosts decision records" becomes a real back-and-forth about retrieval architecture, not just a prompt into a void.

## How we set context

Context is everything in Claude Code sessions. A cold session with no context produces generic output. A warm session with full project state produces output that slots into the existing codebase without surgery.

Our approach to context:

**CLAUDE.md files.** Every project has a `CLAUDE.md` at the root that documents the architecture decisions, coding conventions, and anything Claude needs to know about how the project is organised. This gets loaded automatically and gives Claude the background it needs to write code that fits.

**Read before write.** Before asking Claude Code to write new code, we explicitly read the relevant files it needs to understand. Reading the existing auth middleware before asking Claude to extend it produces much better output than asking cold.

**State the constraints.** We tell Claude Code what we care about before it writes anything. "This needs to work in an Edge Runtime, no Node.js APIs." "This component gets rendered 1,000 times on a single page, keep it lightweight." Constraints shaped in before generation produces cleaner output than constraints corrected after.

## The edit loop

Claude Code writes code. We read it. We ask questions. We edit. We iterate.

The edit loop is faster than a traditional development loop because the gap between "I have an idea" and "I have working code to react to" is measured in seconds, not hours. But the loop doesn't disappear — it just gets tighter.

What we've learned about getting the most out of the edit loop:

**React to working code, not specifications.** It's faster to get Claude to write a first version and then shape it with edits than to specify a complete solution upfront. The concrete version of a thing tells you things the abstract specification doesn't.

**Be specific about what's wrong.** "This doesn't feel right" produces worse responses than "This function returns an array but the caller expects a Promise. Also, the error case needs to return a specific error code for the client." Specificity compresses iterations.

**Don't accept hallucinated APIs.** Claude Code occasionally invents function signatures or imports that don't exist. We catch these by reading the imports carefully and running TypeScript checks frequently. `npx tsc --noEmit` after every significant change is a habit that catches this class of error quickly.

## What we never skip

Three things that don't get automated or abbreviated, regardless of how confident Claude Code seems:

**Architecture decisions.** Claude Code can explain options and tradeoffs, but the decision stays with us. Which retrieval approach? Which auth pattern? Whether to use Server Components or Client Components? We make those calls based on the project constraints Claude might not fully understand.

**Security-sensitive code.** Any code that handles user data, authentication, or financial information gets reviewed as carefully as code we'd write ourselves. Claude Code can write insecure code. It usually doesn't, but it can. We read this code word by word.

**The final review before deploy.** Before anything goes to production, we read the diff. The whole thing. Claude Code keeps a mental model of what it changed, but that model has gaps. Reading the actual diff catches what the session context misses.

## The compounding effect

The thing that's hard to communicate without experiencing it: the benefits compound.

After several months of building with Claude Code, there are architectural patterns, coding conventions, and product decisions that Claude Code has seen repeatedly. It defaults to the patterns we've established rather than generic patterns. It knows that we prefer certain error handling approaches, that we use specific naming conventions, that we avoid certain dependency patterns.

The result is that later sessions start better than earlier ones. The model builds a picture of how the team works. That picture isn't perfect — each session starts fresh — but it can be rebuilt quickly from the project context we've set up to make that fast.

This is the compounding effect in practice. The investment in good project context pays forward indefinitely.

## The honest limit

Claude Code is not good at every kind of decision. It can write code that implements a decision. It cannot reliably make the decision.

"Should this product charge upfront or per-use?" is not a question for Claude Code. "Given we've decided to charge per-use, what's the cleanest way to implement usage tracking without hitting the database on every request?" is exactly right.

The distinction sounds simple. In practice, it requires constant vigilance about which side of the line you're on. When you're deep in a session, it's easy to let Claude Code make choices that should be made by the people who understand the business. Staying on the right side of that line is the most important discipline in AI-assisted development.

The teams that get the most out of tools like Claude Code aren't the ones who delegate the most. They're the ones who stay clear about what's theirs to decide.
