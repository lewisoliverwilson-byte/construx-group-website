title: "Contour: Kubernetes ingress controller on Envoy — HTTPProxy, rate limiting, TLS passthrough"
date: "2033-10-13"
excerpt: "Contour is a Kubernetes ingress controller that uses Envoy proxy as the data plane. Unlike NGINX Ingress (which generates an nginx.conf and reloads on every change) or Traefik (which polls Kubernetes API), Contour runs an Envoy management server (using the Envoy xDS API) that streams configuration changes to Envoy in real time with zero reload. When a new Ingress or HTTPProxy resource is created, Contour translates it into xDS API responses (Listener Discovery Service, Route Discovery Service, Cluster Discovery Service) and pushes them to Envoy without interrupting in-flight connections. Contour introduces HTTPProxy, an extended CRD that goes beyond Kubernetes Ingress: it supports multi-team delegation (a platform team owns the root HTTPProxy for a domain, application teams define sub-resources for their own paths), weighted routing and traffic mirroring, TLS passthrough, request and response header manipulation, and rate limiting via an external rate-limit service. Contour integrates with cert-manager for automatic TLS certificate provisioning and with Prometheus via Envoy's metrics endpoint."
author: "Lewis Wilson"
tag: "Build Log"

HTTPProxy CRD. xDS API. Zero-reload. Delegation. Rate limiting. TLS passthrough.

## HTTPProxy configuration and delegation

```yaml
# HTTPProxy: Contour's extended ingress resource
# Root HTTPProxy: owned by the platform team for construx.io

apiVersion: projectcontour.io/v1
kind: HTTPProxy
metadata:
  name: root
  namespace: ingress-contour   # root proxy lives in the platform namespace
spec:
  virtualhost:
    fqdn: construx.io
    tls:
      secretName: construx-io-wildcard-tls   # cert-manager-provisioned wildcard cert
  routes:
    # Delegate /api/* to the construx-prod namespace
    - conditions:
        - prefix: /api
      services:
        - name: construx-api
          port: 80
          weight: 100

  # Delegation: app teams own their own HTTPProxy objects
  includes:
    - name:      construx-api-routes
      namespace: construx-prod
      conditions:
        - prefix: /api
    - name:      construx-dashboard-routes
      namespace: construx-dashboard
      conditions:
        - prefix: /dashboard
---
# Child HTTPProxy: owned by the construx-prod team — no access to root domain config
apiVersion: projectcontour.io/v1
kind: HTTPProxy
metadata:
  name: construx-api-routes
  namespace: construx-prod
spec:
  routes:
    - conditions:
        - prefix: /api/v1
      services:
        - name: construx-api
          port: 8080
      # Per-route timeout and retry policy
      timeoutPolicy:
        response: 30s
        idle:     60s
      retryPolicy:
        count:              3
        perTryTimeout:      10s
        retriableStatusCodes: [503, 429]

    - conditions:
        - prefix: /api/v2
      # Weighted traffic split: 90% stable, 10% canary
      services:
        - name: construx-api-stable
          port: 8080
          weight: 90
        - name: construx-api-canary
          port: 8080
          weight: 10
```

```yaml
# Rate limiting via external rate-limit service (envoy ratelimit)

apiVersion: projectcontour.io/v1
kind: HTTPProxy
metadata:
  name: rate-limited-api
  namespace: construx-prod
spec:
  routes:
    - conditions:
        - prefix: /api
      rateLimitPolicy:
        global:
          descriptors:
            - entries:
                # Rate limit per remote IP address
                - remoteAddress: {}
            - entries:
                # Rate limit per X-Tenant-ID header value
                - requestHeader:
                    headerName:    X-Tenant-ID
                    descriptorKey: tenant
      services:
        - name: construx-api
          port: 8080
---
# TLS passthrough: terminate TLS in the backend pod, not at the ingress
# (required when the backend must see the client certificate, e.g., mTLS)
apiVersion: projectcontour.io/v1
kind: HTTPProxy
metadata:
  name: tls-passthrough-service
  namespace: construx-prod
spec:
  virtualhost:
    fqdn: grpc.construx.io
    tls:
      passthrough: true   # Contour/Envoy do not terminate TLS — raw TCP forwarded
  tcpproxy:
    services:
      - name: construx-grpc
        port: 443
```

Contour vs NGINX Ingress vs Traefik vs Istio vs AWS ALB Ingress: NGINX Ingress is the most widely deployed — stable, well-documented, but reloads nginx.conf on every Ingress change, which can cause brief connection drops under high traffic. Traefik is developer-friendly with a good dashboard and automatic service discovery, but also reloads on configuration changes. Contour's zero-reload advantage (xDS streaming) matters at scale when you have many services updating routes frequently. Istio (covered in dispatch-1040) is a full service mesh with its own ingress gateway — it does everything Contour does and more, but at significantly higher operational complexity; using Istio as an ingress controller for teams that don't need the service mesh capabilities is overkill. AWS ALB Ingress Controller is the right choice for EKS workloads that terminate TLS at the load balancer and need AWS WAF integration — but it's AWS-specific and adds AWS API call latency on each route change. Contour is the right choice for teams that want Envoy's performance and observability, HTTPProxy's multi-team delegation model, and zero-reload behavior — without the full service mesh overhead of Istio.
