Zod v4 ships with a rewritten parser engine that's 4-10x faster than v3 for deeply nested schemas, better error messages, and cleaner TypeScript inference. The public API is mostly unchanged — `z.string()`, `z.object()`, `z.parse()` all work the same way. The breaking changes are at the edges.

## What's the same

Core schema definitions are unchanged:

```ts
import { z } from 'zod';

const PostSchema = z.object({
  id:        z.string().uuid(),
  title:     z.string().min(1).max(200),
  status:    z.enum(['draft', 'published', 'archived']),
  createdAt: z.string().datetime(),
  tags:      z.array(z.string()).default([]),
  author:    z.object({
    id:    z.string(),
    name:  z.string(),
    email: z.string().email(),
  }),
});

type Post = z.infer<typeof PostSchema>;

const result = PostSchema.safeParse(rawData);
if (!result.success) {
  console.error(result.error.issues);
} else {
  const post = result.data;  // Post type
}
```

This is identical in v3 and v4.

## Breaking change: error format

Zod v4 changes the error issue structure. The `message` field is still there, but the issue object is restructured.

```ts
// v3
result.error.errors[0].message     // 'Invalid email'
result.error.errors[0].path        // ['author', 'email']
result.error.errors[0].code        // 'invalid_string'

// v4 — issues instead of errors, same path/code structure
result.error.issues[0].message     // 'Invalid email'
result.error.issues[0].path        // ['author', 'email']
result.error.issues[0].code        // 'invalid_string'
```

`result.error.errors` still works (aliased to `issues`), but `result.error.format()` output changes:

```ts
// v3 format()
const formatted = result.error.format();
// { _errors: [], author: { email: { _errors: ['Invalid email'] } } }

// v4 format() is deprecated — use flatten() instead
const flat = result.error.flatten();
// { formErrors: [], fieldErrors: { 'author.email': ['Invalid email'] } }
```

If you use `format()` to map errors onto form fields, switch to `flatten()` and update the dotted path structure.

## Breaking change: discriminated unions

v4's discriminated union is stricter and faster:

```ts
// v3: discriminated union with lazy type inference
const Shape = z.discriminatedUnion('type', [
  z.object({ type: z.literal('circle'),    radius: z.number() }),
  z.object({ type: z.literal('rectangle'), width: z.number(), height: z.number() }),
]);

// v4: same syntax, but the discriminant must be a literal in all members
// Non-literal discriminants now throw at schema definition time
const Shape = z.discriminatedUnion('type', [
  z.object({ type: z.literal('circle'),    radius: z.number() }),
  z.object({ type: z.literal('rectangle'), width: z.number(), height: z.number() }),
]);
```

The API is the same, but v4 validates the discriminant at schema creation rather than parse time. If you have a discriminated union where the discriminant isn't a literal, you'll get an error at startup.

## New: `z.pipe()` for transform chaining

```ts
// v3: transform chaining via .transform()
const Schema = z.string()
  .transform((s) => s.trim())
  .refine((s) => s.length > 0, 'Required')
  .transform((s) => s.toLowerCase());

// v4: z.pipe() for explicit chaining (more composable)
const Schema = z.pipe(
  z.string().trim(),
  z.string().min(1, 'Required'),
  z.string().transform((s) => s.toLowerCase()),
);
```

`.transform()` still works. `z.pipe()` makes the transformation steps explicit and easier to compose separately.

## New: `z.templateLiteral()` and `z.brand()`

```ts
// Template literal types
const HexColor = z.templateLiteral([z.literal('#'), z.string().length(6)]);
// Matches: '#FF5F57', '#4ade80'

// Branded types (v3 had this, v4 improves the TypeScript inference)
const UserId   = z.string().uuid().brand('UserId');
const PostId   = z.string().uuid().brand('PostId');

type UserId  = z.infer<typeof UserId>;   // string & { [brand]: 'UserId' }
type PostId  = z.infer<typeof PostId>;   // string & { [brand]: 'PostId' }

// TypeScript rejects mixing branded types
function getUser(id: UserId) {}
const postId: PostId = PostId.parse('...');
getUser(postId);  // TS error: PostId is not assignable to UserId
```

## Performance improvements

The rewritten engine eliminates per-parse allocations for the happy path. In benchmarks:

- Simple object parse: 3x faster
- Nested objects (5+ levels): 8x faster
- Array of 100 objects: 5x faster

For API route validation on hot paths, this is meaningful.

## Migration steps

1. Update: `npm install zod@4`
2. Find all `result.error.format()` calls and replace with `result.error.flatten()`
3. Check discriminated unions — ensure discriminant fields are always literals
4. Run your type checker: `tsc --noEmit`
5. Run your test suite

For most codebases, the migration is 1-2 hours. The parser is backwards-compatible for schemas; only the error API and some edge cases in discriminated unions need changes.
