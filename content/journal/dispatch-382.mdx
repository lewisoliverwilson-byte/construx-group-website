Error handling in Next.js has three distinct layers. Rendering errors crash the UI — React error boundaries contain them. API errors should return structured responses, not stack traces. Background failures (queues, crons, third-party webhooks) need monitoring because no user sees them.

## Error boundaries in the App Router

Next.js uses `error.tsx` files to colocate error boundaries with route segments:

```tsx
// app/error.tsx — catches errors anywhere in the root layout
'use client';

import { useEffect } from 'react';
import { AlertTriangle } from 'lucide-react';

export default function GlobalError({
  error,
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  useEffect(() => {
    // Log to your error tracking service
    reportError(error);
  }, [error]);

  return (
    <div className="min-h-screen flex items-center justify-center px-5">
      <div className="text-center max-w-sm">
        <AlertTriangle className="mx-auto mb-4 text-orange-400" size={32} />
        <h2 className="text-lg font-bold text-text-base mb-2">Something went wrong</h2>
        <p className="text-sm text-text-muted mb-6">
          {error.digest ? `Error ID: ${error.digest}` : 'An unexpected error occurred.'}
        </p>
        <button
          onClick={reset}
          className="px-5 py-2.5 font-mono text-xs bg-construx text-black uppercase tracking-wider"
          style={{ borderRadius: '3px' }}
        >
          Try again
        </button>
      </div>
    </div>
  );
}
```

```tsx
// app/journal/error.tsx — catches errors only within /journal
'use client';

export default function JournalError({ error, reset }: { error: Error; reset: () => void }) {
  return (
    <div className="py-20 text-center">
      <p className="font-mono text-[10px] text-text-dim mb-4">SIGNAL: LOST</p>
      <button onClick={reset}>Retry</button>
    </div>
  );
}
```

The `error.tsx` component must be a Client Component (`'use client'`) because it receives an `Error` object.

## Structured API error responses

Never return a raw error message or stack trace from an API:

```ts
// lib/errors.ts
export class AppError extends Error {
  constructor(
    public message: string,
    public statusCode: number = 500,
    public code?: string,
  ) {
    super(message);
    this.name = 'AppError';
  }
}

// Standard error response shape
export function errorResponse(
  message: string,
  statusCode: number = 500,
  details?: unknown,
) {
  return Response.json(
    {
      error: {
        message,
        code: statusCode,
        ...(details && process.env.NODE_ENV === 'development' && { details }),
      },
    },
    { status: statusCode },
  );
}
```

```ts
// app/api/posts/[id]/route.ts
export async function GET(req: NextRequest, { params }: { params: { id: string } }) {
  try {
    const post = await db.query.posts.findFirst({
      where: eq(posts.id, params.id),
    });

    if (!post) return errorResponse('Post not found', 404);
    return Response.json(post);

  } catch (err) {
    console.error('Failed to fetch post:', err);
    // Don't leak internal error details to clients
    return errorResponse('Internal server error', 500);
  }
}
```

## Error monitoring with Sentry

```bash
npm install @sentry/nextjs
npx @sentry/wizard@latest -i nextjs
```

```ts
// sentry.server.config.ts
import * as Sentry from '@sentry/nextjs';

Sentry.init({
  dsn: process.env.SENTRY_DSN,
  environment: process.env.NODE_ENV,
  tracesSampleRate: 0.1,  // 10% of requests — adjust for your volume
  beforeSend(event) {
    // Don't send errors that are expected
    if (event.exception?.values?.[0]?.type === 'NotFound') return null;
    return event;
  },
});
```

```ts
// sentry.client.config.ts
import * as Sentry from '@sentry/nextjs';

Sentry.init({
  dsn: process.env.NEXT_PUBLIC_SENTRY_DSN,
  replaysSessionSampleRate: 0.01,  // 1% session replay
  replaysOnErrorSampleRate: 1.0,   // 100% replay on errors
});
```

## Graceful degradation patterns

Errors in one part of the page shouldn't break everything else:

```tsx
// Isolate optional features with their own error boundary
import { Suspense } from 'react';
import { ErrorBoundary } from 'react-error-boundary';

function RecommendedPosts() {
  return (
    <ErrorBoundary fallback={null}>  {/* fails silently */}
      <Suspense fallback={<RecommendedPostsSkeleton />}>
        <RecommendedPostsContent />
      </Suspense>
    </ErrorBoundary>
  );
}
```

```ts
// Provide a fallback value when a non-critical fetch fails
async function getViewCount(postId: string): Promise<number> {
  try {
    const result = await redis.get<number>(`views:${postId}`);
    return result ?? 0;
  } catch {
    return 0;  // view count is non-critical — fail silently
  }
}
```

## Retry logic for transient failures

```ts
// lib/retry.ts
export async function withRetry<T>(
  fn: () => Promise<T>,
  {
    maxAttempts = 3,
    delay = 1000,
    backoff = 2,
  }: { maxAttempts?: number; delay?: number; backoff?: number } = {},
): Promise<T> {
  let lastError: Error;

  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    try {
      return await fn();
    } catch (err) {
      lastError = err as Error;
      if (attempt < maxAttempts) {
        await new Promise((r) => setTimeout(r, delay * backoff ** (attempt - 1)));
      }
    }
  }

  throw lastError!;
}

// Usage
const data = await withRetry(
  () => fetch('https://api.example.com/data').then((r) => r.json()),
  { maxAttempts: 3, delay: 500 },
);
```

## The hierarchy

1. Expected errors (not found, unauthorized) — return structured error responses, don't throw
2. Unexpected rendering errors — caught by `error.tsx`, reported to Sentry
3. Unhandled promise rejections in background jobs — monitored via your job queue's failure handler
4. External service failures — retry with backoff, fall back to cached or default values

Never surface internal error details to users. Always log enough context internally to debug.
