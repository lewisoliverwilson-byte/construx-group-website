The naive approach to migrations — `ALTER TABLE` in production, hope it's fast — works until it doesn't. On small tables it's fine. On large tables, some operations hold an exclusive lock while they complete, blocking all reads and writes. Here's the safe pattern.

## Drizzle setup

```bash
npm install drizzle-orm drizzle-kit pg
```

```ts
// drizzle.config.ts
import { defineConfig } from 'drizzle-kit';

export default defineConfig({
  schema: './src/db/schema.ts',
  out: './drizzle',
  dialect: 'postgresql',
  dbCredentials: {
    url: process.env.DATABASE_URL!,
  },
});
```

```ts
// db/schema.ts
import { pgTable, uuid, text, timestamp, integer, boolean, index } from 'drizzle-orm/pg-core';

export const posts = pgTable('posts', {
  id: uuid('id').defaultRandom().primaryKey(),
  title: text('title').notNull(),
  slug: text('slug').notNull().unique(),
  content: text('content').notNull(),
  authorId: uuid('author_id').notNull(),
  publishedAt: timestamp('published_at'),
  createdAt: timestamp('created_at').defaultNow().notNull(),
}, (t) => ({
  slugIdx: index('posts_slug_idx').on(t.slug),
  authorIdx: index('posts_author_id_idx').on(t.authorId),
}));
```

Generate migrations with `npx drizzle-kit generate` and apply with `npx drizzle-kit migrate`.

## What operations are unsafe

**Table-locking operations** (avoid on large tables):
- `ALTER TABLE t ADD COLUMN x NOT NULL` without a default
- `ALTER TABLE t DROP COLUMN x`
- `ALTER TABLE t ALTER COLUMN x TYPE y` (type change)
- Adding a unique constraint (requires full scan + lock)

**Safe operations** (no lock or brief lock):
- `ALTER TABLE t ADD COLUMN x` with a default or nullable
- `DROP INDEX CONCURRENTLY`
- `CREATE INDEX CONCURRENTLY`
- Adding a nullable column and backfilling

## Adding a NOT NULL column safely (expand/contract)

**Unsafe**:
```sql
-- Locks the table for the duration of the backfill
ALTER TABLE users ADD COLUMN phone TEXT NOT NULL DEFAULT '';
```

**Safe (expand)**:
```ts
// Migration 1: add as nullable
export const addPhoneNullable = pgTable('users', {
  // ... existing columns
  phone: text('phone'), // nullable, no lock
});
```

```ts
// Migration 2: backfill in batches (run separately, no lock)
async function backfillPhone() {
  const batchSize = 1000;
  let lastId = '';

  while (true) {
    const rows = await db.execute(sql`
      UPDATE users
      SET phone = ''
      WHERE id > ${lastId}
        AND phone IS NULL
      RETURNING id
      LIMIT ${batchSize}
    `);

    if (rows.length === 0) break;
    lastId = rows[rows.length - 1].id;
    await new Promise((r) => setTimeout(r, 50)); // brief pause
  }
}
```

```sql
-- Migration 3: add NOT NULL constraint (after all rows are filled)
-- This is instant in PostgreSQL 12+ if no nulls exist
ALTER TABLE users ALTER COLUMN phone SET NOT NULL;
```

## Renaming a column

You can't rename a column in one step without risking downtime (application reads old name, migration renames it, application breaks).

**Safe sequence**:

1. **Expand**: add the new column alongside the old one
   ```sql
   ALTER TABLE users ADD COLUMN full_name TEXT;
   ```

2. **Sync**: write to both columns in application code
   ```ts
   await db.update(users).set({ name: value, fullName: value });
   ```

3. **Backfill**: copy data from old to new
   ```sql
   UPDATE users SET full_name = name WHERE full_name IS NULL;
   ```

4. **Switch reads**: application reads from new column only, writes still go to both

5. **Contract**: remove the old column after confirming the new column is correct
   ```sql
   ALTER TABLE users DROP COLUMN name;
   ```

This takes 5 separate deploys but each step is reversible and zero-downtime.

## Building indexes without locking

A standard `CREATE INDEX` holds a lock on the table. For large tables, use `CONCURRENTLY`:

```sql
-- Takes a share lock only briefly, doesn't block writes
CREATE INDEX CONCURRENTLY posts_author_id_idx ON posts (author_id);
```

In Drizzle, run concurrent index creation as a raw SQL migration:

```ts
// drizzle/0012_add_author_index.sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS posts_author_id_idx ON posts (author_id);
```

**Note**: `CONCURRENTLY` can't run inside a transaction. Run it as a standalone migration, not inside a Drizzle transaction block.

## Running migrations on deploy

For Amplify/Vercel, run migrations as part of the build step, not at startup:

```json
// package.json
{
  "scripts": {
    "build": "drizzle-kit migrate && next build",
    "migrate": "drizzle-kit migrate"
  }
}
```

For long-running migrations (backfills), run them manually before the deploy, not automatically.

## Schema changes that require two deploys

Some changes require the old code and new code to coexist:

1. **Column rename**: as described above — add new, deploy, backfill, deploy, drop old
2. **Changing a nullable column to NOT NULL**: add constraint after verifying no nulls
3. **Splitting a table**: add new table with FK, migrate data, switch reads, remove old

The pattern: always make the database schema compatible with the currently-running version of the application before changing the application. Never deploy a schema change that breaks the running code.

## Rollback strategy

Drizzle doesn't auto-generate rollback migrations. Write them manually for any risky change:

```ts
// drizzle/0011_rollback.sql
ALTER TABLE users DROP COLUMN IF EXISTS full_name;
```

Store rollback scripts next to forward migrations. Before any major migration, test the rollback on a staging database restored from a production snapshot.

The safety principle: run the migration in staging against production-scale data. If it takes 40 seconds in staging, it'll take 40 seconds in production.
