excerpt: "eBPF (extended Berkeley Packet Filter) lets you run sandboxed programs in the Linux kernel in response to events — system calls, network packets, kernel function calls, tracepoints, and uprobes — without writing a kernel module or rebooting. The programs are verified by the kernel before execution (no crashes, no infinite loops, bounded memory access) and can emit data to user space via ring buffers and maps. bpftrace is the high-level scripting interface; BCC is the Python-based toolkit; libbpf is the portable C library for production eBPF programs. Attach to any kernel event. Verified by the kernel. Zero kernel module restarts. Data via maps.

## bpftrace — eBPF scripting

```bash
# bpftrace: one-liner eBPF programs — like awk for the kernel

# Count syscalls by process name (top 10 over 5 seconds)
bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); }
             interval:s:5 { print(@); clear(@); exit(); }'
# @[construx-api]: 38241
# @[postgres]:      12847
# @[node]:           8241
# @[kernel]:         4103

# Trace every open() call (file opens system-wide)
bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s %s\n", comm, str(args->filename)); }'
# construx-api  /etc/construx/config.yaml
# construx-api  /var/lib/construx/state.db
# postgres      /var/lib/postgresql/data/pg_wal/000000010000000000000001

# Histogram of read() sizes (per process)
bpftrace -e '
  tracepoint:syscalls:sys_exit_read /args->ret > 0/ {
    @read_size[comm] = hist(args->ret);
  }'
# @read_size[construx-api]:
# [0, 1)      0 |
# [64, 128)   4 |@
# [1K, 2K)   38 |@@@@@@@@@@
# [4K, 8K)   82 |@@@@@@@@@@@@@@@@@@@@@@

# Measure function latency (kernel function timing)
bpftrace -e '
  kprobe:tcp_sendmsg { @start[tid] = nsecs; }
  kretprobe:tcp_sendmsg /@start[tid]/ {
    @latency = hist(nsecs - @start[tid]);
    delete(@start[tid]);
  }'

# Trace Go function calls via uprobe (without modifying the binary)
bpftrace -e '
  uprobe:/usr/local/bin/construx-api:main.(*Handler).ServeHTTP {
    printf("ServeHTTP called by goroutine %d\n", tid);
  }'
```

## BCC — Python + eBPF

```python
# BCC: write eBPF in C, interface from Python

from bcc import BPF

# eBPF program (C) — trace TCP connections and their latency
prog = """
#include <net/sock.h>

BPF_HASH(start, u64);      // tid → start timestamp
BPF_HISTOGRAM(dist);        // latency distribution

void trace_tcp_connect(struct pt_regs *ctx, struct sock *sk) {
    u64 tid = bpf_get_current_pid_tgid();
    u64 ts = bpf_ktime_get_ns();
    start.update(&tid, &ts);
}

int trace_tcp_connect_return(struct pt_regs *ctx) {
    u64 tid = bpf_get_current_pid_tgid();
    u64 *tsp = start.lookup(&tid);
    if (!tsp) return 0;

    u64 latency = bpf_ktime_get_ns() - *tsp;
    dist.increment(bpf_log2l(latency / 1000));   // microseconds, log2 histogram
    start.delete(&tid);
    return 0;
}
"""

b = BPF(text=prog)
b.attach_kprobe(event="tcp_v4_connect", fn_name="trace_tcp_connect")
b.attach_kretprobe(event="tcp_v4_connect", fn_name="trace_tcp_connect_return")

print("Tracing TCP connect latency... Ctrl-C to stop")
try:
    b.trace_print()
except KeyboardInterrupt:
    b["dist"].print_log2_hist("TCP connect latency (µs)")
```

## libbpf — portable CO-RE eBPF programs

```c
// construx_probe.bpf.c — production eBPF program using CO-RE (Compile Once, Run Everywhere)
// CO-RE programs work across kernel versions without recompilation

#include <vmlinux.h>
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_tracing.h>
#include <bpf/bpf_core_read.h>

// Ring buffer: efficient kernel → user space data transfer
struct {
    __uint(type, BPF_MAP_TYPE_RINGBUF);
    __uint(max_entries, 256 * 1024);   // 256KB ring buffer
} events SEC(".maps");

// Hash map: PID → start timestamp (for latency calculation)
struct {
    __uint(type, BPF_MAP_TYPE_HASH);
    __uint(max_entries, 10240);
    __type(key, u32);
    __type(value, u64);
} start_times SEC(".maps");

struct event {
    u32 pid;
    char comm[16];
    u64 latency_ns;
    char filename[256];
};

// Trace openat() entry: record start time
SEC("tracepoint/syscalls/sys_enter_openat")
int trace_openat_enter(struct trace_event_raw_sys_enter *ctx) {
    u32 tid = bpf_get_current_pid_tgid();
    u64 ts = bpf_ktime_get_ns();
    bpf_map_update_elem(&start_times, &tid, &ts, BPF_ANY);
    return 0;
}

// Trace openat() exit: calculate latency and emit event
SEC("tracepoint/syscalls/sys_exit_openat")
int trace_openat_exit(struct trace_event_raw_sys_exit *ctx) {
    u32 tid = bpf_get_current_pid_tgid();
    u64 *start_ts = bpf_map_lookup_elem(&start_times, &tid);
    if (!start_ts) return 0;

    struct event *e = bpf_ringbuf_reserve(&events, sizeof(*e), 0);
    if (!e) { bpf_map_delete_elem(&start_times, &tid); return 0; }

    e->pid = tid >> 32;
    e->latency_ns = bpf_ktime_get_ns() - *start_ts;
    bpf_get_current_comm(&e->comm, sizeof(e->comm));

    bpf_ringbuf_submit(e, 0);
    bpf_map_delete_elem(&start_times, &tid);
    return 0;
}

char LICENSE[] SEC("license") = "GPL";
```

## eBPF in production — Cilium and Pixie

```bash
# Cilium uses eBPF for Kubernetes network policy enforcement
# Every packet is checked against policy in kernel — no iptables chain traversal

# View Cilium's eBPF programs loaded in the kernel
bpftool prog list | grep cilium
# 841: sched_cls  name from_container  prog_id 841
# 842: sched_cls  name to_container    prog_id 842
# 843: xdp        name bpf_xdp_policy  prog_id 843

# View Cilium's eBPF maps (policy tables, connection tracking)
bpftool map list | grep cilium
# 123: hash  name cilium_calls_00000  key 4B  value 4B  max_entries 1024

# Pixie: observability platform built entirely on eBPF
# Auto-instruments HTTP, gRPC, PostgreSQL, Redis, Kafka without code changes
px run px/http_data -- -start_time '-5m' | head -20
# REQID  REMOTE_ADDR      LATENCY_P99  STATUS
# req_1  10.0.1.100:42871 41ms         200
# req_2  10.0.1.101:38291 320ms        503   ← slow request detected

# Parca: continuous profiling using eBPF (no instrumentation)
# Runs at 19Hz by default, samples stack traces across all processes
# Produces flamegraphs in the Parca UI without any code changes
```

eBPF vs kernel modules: a kernel module runs with full kernel privileges and can crash the kernel (or be exploited to escalate privileges). eBPF programs are verified before loading — the kernel verifier checks that they terminate, don't access out-of-bounds memory, and don't call dangerous kernel functions. A buggy eBPF program is rejected at load time; a buggy kernel module crashes the system. The practical trade-off: eBPF programs are sandboxed (can't do everything a module can), but they're safe enough to run in production, don't require a kernel restart to load, and are portable across kernel versions with CO-RE. The canonical example: Cilium replaced its iptables/ipvs implementation with an eBPF data plane — network policy is enforced at the packet level in kernel, without any user-space process in the hot path.
