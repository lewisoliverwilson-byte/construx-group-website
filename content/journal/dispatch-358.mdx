Every public API route is an invitation to abuse. AI endpoints that call external models are especially expensive — a single bot can burn through a month's token budget in hours. Rate limiting is not optional.

The challenge in serverless: each function invocation is stateless. You can't use in-memory counters. The rate limiter state has to live in a shared store — Redis.

## Upstash Redis for serverless rate limiting

Upstash is a serverless Redis provider. Pay per request, no idle cost, HTTP-based client that works in edge environments.

```bash
npm install @upstash/ratelimit @upstash/redis
```

```ts
// lib/rate-limit.ts
import { Ratelimit } from '@upstash/ratelimit';
import { Redis } from '@upstash/redis';

const redis = new Redis({
  url: process.env.UPSTASH_REDIS_REST_URL!,
  token: process.env.UPSTASH_REDIS_REST_TOKEN!,
});

// Sliding window: 10 requests per 60 seconds
export const ratelimit = new Ratelimit({
  redis,
  limiter: Ratelimit.slidingWindow(10, '60 s'),
  analytics: true,  // track usage in Upstash dashboard
  prefix: 'construx:rl',
});

// Stricter limiter for AI endpoints
export const aiRatelimit = new Ratelimit({
  redis,
  limiter: Ratelimit.slidingWindow(3, '60 s'),
  analytics: true,
  prefix: 'construx:rl:ai',
});
```

## Using it in a route handler

```ts
// app/api/chat/route.ts
import { NextRequest } from 'next/server';
import { aiRatelimit } from '@/lib/rate-limit';

function getIdentifier(req: NextRequest): string {
  // Use authenticated user ID if available, otherwise IP
  const forwarded = req.headers.get('x-forwarded-for');
  const ip = forwarded?.split(',')[0].trim() ?? req.headers.get('x-real-ip') ?? 'anonymous';
  return ip;
}

export async function POST(req: NextRequest) {
  const identifier = getIdentifier(req);
  const { success, limit, reset, remaining } = await aiRatelimit.limit(identifier);

  if (!success) {
    return Response.json(
      { error: 'Rate limit exceeded. Try again later.' },
      {
        status: 429,
        headers: {
          'X-RateLimit-Limit': String(limit),
          'X-RateLimit-Remaining': String(remaining),
          'X-RateLimit-Reset': String(reset),
          'Retry-After': String(Math.ceil((reset - Date.now()) / 1000)),
        },
      }
    );
  }

  // Proceed with the actual handler
  const { messages } = await req.json();
  // ... AI call
}
```

## Middleware-level rate limiting

For broader protection, apply rate limiting in middleware before requests reach your routes:

```ts
// middleware.ts
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';
import { Ratelimit } from '@upstash/ratelimit';
import { Redis } from '@upstash/redis';

const redis = Redis.fromEnv();

const ratelimit = new Ratelimit({
  redis,
  limiter: Ratelimit.slidingWindow(30, '60 s'),
  prefix: 'construx:rl:global',
});

export async function middleware(request: NextRequest) {
  if (!request.nextUrl.pathname.startsWith('/api/')) {
    return NextResponse.next();
  }

  const ip = request.headers.get('x-forwarded-for')?.split(',')[0].trim() ?? 'anonymous';
  const { success, remaining, reset } = await ratelimit.limit(ip);

  if (!success) {
    return new Response('Too Many Requests', {
      status: 429,
      headers: {
        'X-RateLimit-Remaining': String(remaining),
        'X-RateLimit-Reset': String(reset),
      },
    });
  }

  return NextResponse.next();
}

export const config = {
  matcher: '/api/:path*',
};
```

## Token bucket for burst tolerance

Sliding window is strict — exactly N requests per window. Token bucket allows bursts while still enforcing an average rate:

```ts
// Allow bursts of up to 20, refilling at 5 per minute
export const burstRatelimit = new Ratelimit({
  redis,
  limiter: Ratelimit.tokenBucket(5, '60 s', 20),
  prefix: 'construx:rl:burst',
});
```

Good for endpoints where a user might legitimately do 10 actions quickly (bulk imports, multi-select operations) but you still want to cap sustained throughput.

## Per-user rate limits from JWT

If users are authenticated, rate limit by user ID instead of IP:

```ts
import { getServerSession } from 'next-auth';

export async function POST(req: NextRequest) {
  const session = await getServerSession();
  const identifier = session?.user?.id ?? getIpIdentifier(req);

  const { success } = await ratelimit.limit(identifier);
  // ...
}
```

User ID rate limiting is more accurate: multiple users behind the same corporate proxy share an IP but shouldn't share a rate limit. A malicious user can't bypass limits by switching IPs.

## Rate limit response headers

Always return rate limit metadata in headers — clients can use these to back off gracefully:

```
X-RateLimit-Limit: 10
X-RateLimit-Remaining: 3
X-RateLimit-Reset: 1732147200000
Retry-After: 45
```

The `Retry-After` header (seconds until reset) is what well-behaved clients use to schedule retries.

## Monitoring limits

Upstash's dashboard shows per-prefix usage. For production, set alerts: if a single identifier accounts for more than 20% of requests in a window, that's worth investigating.

The rule: implement rate limiting before you need it, not after you get the unexpected bill.
