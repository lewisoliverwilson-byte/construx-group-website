React Server Components (RSCs) exist because the client bundle has always been the wrong place for database queries, API secrets, and large dependencies like date parsers or markdown renderers. RSCs let you write React components that run only on the server — never downloaded to the browser, never re-rendered on interaction.

## The mental model

Three categories of code:

1. **Server Components** — run on server only. Can `await` directly, read env vars, query the DB, import heavy packages. Zero JavaScript sent to the browser.
2. **Client Components** — the React you already know. Can use hooks, handle events, manage state. Marked with `'use client'`.
3. **Shared components** — no browser APIs or server APIs. Pure presentation.

In Next.js App Router, every component is a Server Component by default. You opt into client components with `'use client'`.

## What belongs on the server

```tsx
// app/products/page.tsx — Server Component
// No 'use client' directive = runs on server

import { db } from '@/lib/db';

export default async function ProductsPage() {
  // Direct DB query — no API route needed
  const products = await db.query.products.findMany({
    orderBy: (p, { desc }) => desc(p.createdAt),
    limit: 20,
  });

  // products is fully typed — TypeScript knows the schema
  return (
    <ul>
      {products.map((p) => (
        <li key={p.id}>
          <span>{p.title}</span>
          <span>£{p.price}</span>
        </li>
      ))}
    </ul>
  );
}
```

This component never becomes JavaScript in the browser. It renders to HTML on the server, ships the HTML, done. No hydration cost, no bundle size, no API round-trip.

## What requires a Client Component

```tsx
// components/AddToCart.tsx
'use client';

import { useState } from 'react';

export function AddToCart({ productId }: { productId: string }) {
  const [loading, setLoading] = useState(false);

  const handleClick = async () => {
    setLoading(true);
    await fetch('/api/cart', {
      method: 'POST',
      body: JSON.stringify({ productId }),
    });
    setLoading(false);
  };

  return (
    <button onClick={handleClick} disabled={loading}>
      {loading ? 'Adding...' : 'Add to cart'}
    </button>
  );
}
```

Client Components need `'use client'` if they use: hooks (`useState`, `useEffect`, `useRef`), browser APIs (`window`, `document`), event handlers, or any third-party library that uses these.

## Composing server and client components

The key pattern: Server Components can render Client Components, but not the other way around.

```tsx
// app/products/[id]/page.tsx — Server Component
import { db } from '@/lib/db';
import { AddToCart } from '@/components/AddToCart';
import { ProductImages } from '@/components/ProductImages';

export default async function ProductPage({ params }: { params: { id: string } }) {
  // Data fetching on the server
  const product = await db.query.products.findFirst({
    where: (p, { eq }) => eq(p.id, params.id),
    with: { images: true, reviews: true },
  });

  if (!product) notFound();

  return (
    <div>
      {/* Server-rendered static content */}
      <h1>{product.title}</h1>
      <p>{product.description}</p>

      {/* Client component for interactivity */}
      <AddToCart productId={product.id} />

      {/* Another client component for carousel */}
      <ProductImages images={product.images} />
    </div>
  );
}
```

The product data is fetched once on the server. The client components get the data as props — no second fetch, no loading state at the top level.

## Passing server data to client components via props

```tsx
// ✓ Works — primitives and plain objects are serialisable
<UserProfile name={user.name} email={user.email} role={user.role} />

// ✗ Won't work — functions and class instances aren't serialisable
<UserProfile onSave={handleSave} db={dbInstance} />
```

Data passed as props from server to client must be serialisable to JSON. Functions, class instances, and Dates (pre-serialisation) don't cross the boundary.

## Server Actions for mutations

Server Actions are functions that run on the server, called from client components — the inversion of the pattern:

```tsx
// app/products/actions.ts
'use server';

import { db } from '@/lib/db';
import { revalidatePath } from 'next/cache';

export async function updateProduct(id: string, data: { title: string; price: number }) {
  await db.update(products).set(data).where(eq(products.id, id));
  revalidatePath('/products');
}
```

```tsx
// components/ProductEditor.tsx
'use client';

import { updateProduct } from '@/app/products/actions';

export function ProductEditor({ product }: { product: Product }) {
  return (
    <form action={async (formData) => {
      await updateProduct(product.id, {
        title: formData.get('title') as string,
        price: Number(formData.get('price')),
      });
    }}>
      <input name="title" defaultValue={product.title} />
      <input name="price" type="number" defaultValue={product.price} />
      <button type="submit">Save</button>
    </form>
  );
}
```

`revalidatePath` invalidates the Next.js cache for that route — the next request re-renders the Server Component with fresh data.

## What RSCs mean for architecture

The practical shift: most data-fetching logic moves out of `useEffect` and API routes into Server Components. API routes still exist for external callers and webhooks — but the application's own data layer talks directly to the database from Server Components and Server Actions.

The result is fewer network round-trips, smaller client bundles, and no prop-drilling of data that was fetched on the server anyway.
