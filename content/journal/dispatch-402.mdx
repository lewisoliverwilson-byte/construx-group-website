Multi-tenancy means multiple customers (tenants) share the same application infrastructure while keeping their data isolated from each other. Getting this wrong is a serious security issue. Getting it right determines how well you scale.

## Three patterns

**Separate databases** — one database per tenant. Total isolation. Simple mental model. Expensive at scale. Hard to run cross-tenant analytics. Works well at lower tenant counts with high-value customers.

**Schema-per-tenant** — one database, one PostgreSQL schema per tenant. Good isolation. Tables are namespaced. Allows cross-schema queries when needed. More complex than row isolation.

**Row-level isolation** — one database, one schema, every table has a `tenant_id` column. Simplest to implement. Relies on application code to filter correctly. Row-Level Security (RLS) in PostgreSQL makes this safe.

For most SaaS products: row-level isolation with PostgreSQL RLS is the right default.

## Row-level isolation with RLS

```sql
-- Enable RLS on all tenant tables
ALTER TABLE posts ENABLE ROW LEVEL SECURITY;
ALTER TABLE comments ENABLE ROW LEVEL SECURITY;

-- Create a policy — only rows where tenant_id matches can be accessed
CREATE POLICY tenant_isolation ON posts
  USING (tenant_id = current_setting('app.current_tenant_id')::uuid);

-- Same for comments
CREATE POLICY tenant_isolation ON comments
  USING (tenant_id = current_setting('app.current_tenant_id')::uuid);
```

```ts
// lib/db.ts — set tenant context before every query
import { Pool } from 'pg';

const pool = new Pool({ connectionString: process.env.DATABASE_URL });

export async function withTenant<T>(
  tenantId: string,
  callback: (client: import('pg').PoolClient) => Promise<T>,
): Promise<T> {
  const client = await pool.connect();
  try {
    await client.query(`SET LOCAL app.current_tenant_id = '${tenantId}'`);
    return await callback(client);
  } finally {
    client.release();
  }
}
```

```ts
// Route Handler — always set tenant context
export async function GET(req: Request) {
  const session = await auth();
  const tenantId = session?.user?.tenantId;

  if (!tenantId) return Response.json({ error: 'Unauthorized' }, { status: 401 });

  const posts = await withTenant(tenantId, async (client) => {
    const result = await client.query('SELECT * FROM posts ORDER BY created_at DESC');
    return result.rows;
  });

  return Response.json(posts);
}
```

RLS enforces isolation at the database level, not just application code. Even if application code has a bug that forgets to filter by `tenant_id`, the database won't return rows from other tenants.

## Schema with Drizzle

```ts
// db/schema.ts — add tenant_id to every table
export const posts = pgTable('posts', {
  id: text('id').primaryKey().$defaultFn(() => crypto.randomUUID()),
  tenantId: uuid('tenant_id').notNull(),
  title: text('title').notNull(),
  content: text('content').notNull(),
  createdAt: timestamp('created_at').notNull().defaultNow(),
}, (table) => ({
  tenantIdx: index('idx_posts_tenant').on(table.tenantId),
  tenantCreatedIdx: index('idx_posts_tenant_created').on(table.tenantId, table.createdAt),
}));
```

The `tenantId` index on every table is mandatory. Without it, tenant queries do full table scans.

## Tenant resolution

Where does the `tenantId` come from? Subdomain is the cleanest approach:

```ts
// middleware.ts — resolve tenant from subdomain
export async function middleware(req: NextRequest) {
  const hostname = req.headers.get('host') ?? '';

  // customer.construxgroup.io → tenant slug 'customer'
  const subdomain = hostname.replace('.construxgroup.io', '');
  const isSubdomain = subdomain !== 'construxgroup' && subdomain !== 'www';

  if (isSubdomain) {
    const response = NextResponse.next();
    response.headers.set('x-tenant-slug', subdomain);
    return response;
  }

  return NextResponse.next();
}
```

```ts
// lib/tenant.ts — resolve tenant ID from slug (cached)
import { headers } from 'next/headers';

export async function getCurrentTenant() {
  const slug = (await headers()).get('x-tenant-slug');
  if (!slug) return null;

  return cache(async (s: string) => {
    return db.query.tenants.findFirst({ where: eq(tenants.slug, s) });
  })(slug);
}
```

## Cross-tenant operations (admin only)

Some operations need to cross tenant boundaries — analytics dashboards, admin searches, billing reconciliation. Handle these in a separate database role that bypasses RLS:

```sql
-- Admin role bypasses RLS
CREATE ROLE app_admin BYPASSRLS;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_admin;
```

```ts
// Only use this connection for admin operations
const adminPool = new Pool({
  connectionString: process.env.DATABASE_URL,
  user: process.env.ADMIN_DB_USER,  // app_admin role
});
```

Never expose the admin pool to user-facing endpoints. Keep it in a separate admin service or API route with its own auth layer.

## Tenant onboarding

```ts
// Create tenant and seed initial data in a transaction
export async function createTenant(name: string, ownerEmail: string) {
  return db.transaction(async (tx) => {
    const [tenant] = await tx.insert(tenants)
      .values({ name, slug: slugify(name) })
      .returning();

    const [owner] = await tx.insert(users)
      .values({ email: ownerEmail, tenantId: tenant.id, role: 'owner' })
      .returning();

    // Seed default settings, plans, etc.
    await tx.insert(tenantSettings)
      .values({ tenantId: tenant.id, plan: 'trial' });

    return { tenant, owner };
  });
}
```

The pattern: RLS at the database level for safety, `tenantId` in every query for performance, subdomain resolution in middleware for clean URLs. Never rely on application-level filtering alone.
