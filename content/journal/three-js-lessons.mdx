The homepage of the Construx Group website has a 3D solar system — a central sun representing Construx Group, with three orbiting planets representing Scoutr, The Marqet, and The Hyve. Each planet has a distinct color and orbital period; clicking it navigates to the venture page.

Building this with Three.js inside a Next.js 15 App Router site required solving a specific set of integration problems. Here's what they were and how we solved them.

## The SSR problem

Three.js requires a browser environment — it uses the DOM and WebGL APIs that don't exist on the server. Next.js App Router renders server components on the server, which means any component that imports Three.js will fail at build time.

The solution: dynamic import with `ssr: false`.

```tsx
// app/page.tsx (server component)
import dynamic from 'next/dynamic';

const SolarSystemLoader = dynamic(
  () => import('@/components/SolarSystem'),
  {
    ssr: false,
    loading: () => (
      <div className="h-[600px] flex items-center justify-center">
        <span className="font-mono text-xs text-text-dim animate-pulse">
          initializing...
        </span>
      </div>
    ),
  }
);
```

The `ssr: false` flag tells Next.js not to render this component on the server. The `loading` function provides a placeholder during the time between page load (when the HTML is delivered) and when Three.js has loaded and initialized.

Without the loading placeholder, the area where the solar system will appear is empty for a noticeable instant. With it, there's a smooth transition from the "initializing..." state to the fully rendered scene.

## The resize problem

Three.js renderers have a fixed pixel size. When the window resizes, the canvas stays at its original size unless you explicitly handle the resize event.

```typescript
useEffect(() => {
  function handleResize() {
    const width = mount.current!.clientWidth;
    const height = mount.current!.clientHeight;
    renderer.setSize(width, height);
    camera.aspect = width / height;
    camera.updateProjectionMatrix();
  }
  
  window.addEventListener('resize', handleResize);
  return () => window.removeEventListener('resize', handleResize);
}, []);
```

The `handleResize` function updates both the renderer size and the camera's aspect ratio. Both are necessary — updating the renderer without updating the camera produces a correctly-sized canvas with distorted geometry.

## The cleanup problem

Three.js allocates GPU memory for geometries, materials, and textures. If a component unmounts without releasing these resources, the memory stays allocated. In React development mode (with StrictMode double-mounting), this can cause visible flickering or errors.

The solution: release resources in the useEffect cleanup:

```typescript
return () => {
  // Remove resize listener
  window.removeEventListener('resize', handleResize);
  
  // Dispose of Three.js resources
  scene.traverse((object) => {
    if (object instanceof THREE.Mesh) {
      object.geometry.dispose();
      if (Array.isArray(object.material)) {
        object.material.forEach(m => m.dispose());
      } else {
        object.material.dispose();
      }
    }
  });
  
  renderer.dispose();
  
  // Remove the canvas from the DOM
  if (mount.current && mount.current.contains(renderer.domElement)) {
    mount.current.removeChild(renderer.domElement);
  }
};
```

Without this cleanup, React StrictMode's double-mounting creates two renderers, one orphaned, and the GPU resources are never freed.

## The animation loop and React reconciliation

The Three.js animation loop (via `requestAnimationFrame`) runs continuously. React's reconciliation cycle also runs periodically. These two loops need to co-exist without interference.

The pattern we use: run the Three.js animation loop independently of React state. The loop only updates Three.js objects (planet positions, rotations); it never calls `setState` or touch React-managed state.

```typescript
function animate() {
  animationFrameRef.current = requestAnimationFrame(animate);
  const elapsed = clock.getElapsedTime();
  
  // Update planet positions along orbital paths
  planets.forEach((planet) => {
    planet.mesh.position.x = Math.cos(elapsed * planet.speed) * planet.radius;
    planet.mesh.position.z = Math.sin(elapsed * planet.speed) * planet.radius;
  });
  
  renderer.render(scene, camera);
}
```

No `setState` in the animation loop. React state manages UI elements (the labels, the navigation on click); Three.js state manages the 3D scene. The two systems don't touch each other's state.

## Interaction: click targets vs. 3D objects

Detecting clicks on 3D objects requires raycasting — projecting a ray from the camera through the mouse position and checking which objects intersect.

```typescript
const raycaster = new THREE.Raycaster();
const mouse = new THREE.Vector2();

function onMouseClick(event: MouseEvent) {
  const rect = renderer.domElement.getBoundingClientRect();
  mouse.x = ((event.clientX - rect.left) / rect.width) * 2 - 1;
  mouse.y = -((event.clientY - rect.top) / rect.height) * 2 + 1;
  
  raycaster.setFromCamera(mouse, camera);
  const intersects = raycaster.intersectObjects(clickablePlanets, true);
  
  if (intersects.length > 0) {
    const planet = intersects[0].object.userData.planet;
    router.push(`/ventures/${planet.slug}`);
  }
}
```

The raycaster works in normalised device coordinates (NDC): x from -1 to 1 left-to-right, y from -1 to 1 bottom-to-top (inverted from screen coordinates, hence the negation of the y component).

## What we'd do differently

**Use react-three-fiber.** The Three.js integration we have is the raw imperative API, which is harder to reason about than the declarative component model that `@react-three/fiber` provides. We'd use react-three-fiber for any new Three.js work.

**Start with a simpler scene.** The solar system had a clear reference (actual astronomy), which helped. A more abstract visualization would have required more design iteration. Starting with a concrete, understood reference made the creative decisions faster.
