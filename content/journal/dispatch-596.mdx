Rate limiting answers a simple question: how many requests should a client be allowed to make in a given time window? The answer determines which algorithm to use.

## Fixed window

The simplest approach. Count requests in a fixed time window (e.g., the current minute). Reset the counter at the start of each window.

```ts
// Redis implementation
async function fixedWindowRateLimit(
  key:    string,
  limit:  number,
  window: number,  // seconds
): Promise<{ allowed: boolean; remaining: number }> {
  const windowKey = `ratelimit:${key}:${Math.floor(Date.now() / (window * 1000))}`;

  const [count] = await redis.pipeline()
    .incr(windowKey)
    .expire(windowKey, window * 2)
    .exec() as [number, number];

  return {
    allowed:   count <= limit,
    remaining: Math.max(0, limit - count),
  };
}
```

**The problem**: boundary bursting. A client can make `limit` requests at 00:59 and another `limit` at 01:00 — 2x the intended limit in 2 seconds.

## Sliding window

Tracks requests across a rolling window, not a fixed boundary. More accurate than fixed window; more expensive to compute.

```ts
async function slidingWindowRateLimit(
  key:    string,
  limit:  number,
  window: number,  // seconds
): Promise<{ allowed: boolean; remaining: number }> {
  const now     = Date.now();
  const cutoff  = now - window * 1000;
  const rateKey = `ratelimit:sw:${key}`;

  // Add this request's timestamp; remove old timestamps; count remaining
  const [, , count] = await redis.pipeline()
    .zadd(rateKey, now, `${now}-${Math.random()}`)
    .zremrangebyscore(rateKey, 0, cutoff)
    .zcard(rateKey)
    .expire(rateKey, window)
    .exec() as [unknown, unknown, number, unknown];

  return {
    allowed:   count <= limit,
    remaining: Math.max(0, limit - count),
  };
}
```

Uses a Redis sorted set where each member is a request timestamp. `ZREMRANGEBYSCORE` removes requests older than the window. `ZCARD` gives the current count.

**Tradeoff**: more storage (one entry per request vs. one counter per window) and more Redis operations per check. For high-traffic endpoints, use the log-approximation variant instead.

## Token bucket

Models a bucket that fills with tokens at a constant rate. Each request consumes one token. Allows bursting up to the bucket capacity.

```ts
interface TokenBucket {
  tokens:      number;
  lastRefillMs: number;
}

async function tokenBucketRateLimit(
  key:          string,
  capacity:     number,  // max burst
  refillRate:   number,  // tokens per second
): Promise<{ allowed: boolean; remaining: number }> {
  const bucketKey = `ratelimit:tb:${key}`;
  const now       = Date.now();

  const raw = await redis.get(bucketKey);
  const bucket: TokenBucket = raw
    ? JSON.parse(raw)
    : { tokens: capacity, lastRefillMs: now };

  // Refill tokens based on elapsed time
  const elapsed      = (now - bucket.lastRefillMs) / 1000;
  const newTokens    = Math.min(capacity, bucket.tokens + elapsed * refillRate);
  const allowed      = newTokens >= 1;
  const finalTokens  = allowed ? newTokens - 1 : newTokens;

  await redis.set(
    bucketKey,
    JSON.stringify({ tokens: finalTokens, lastRefillMs: now }),
    { ex: Math.ceil(capacity / refillRate) * 2 },
  );

  return { allowed, remaining: Math.floor(finalTokens) };
}
```

**Advantage**: smooth limiting with burst tolerance. A client that hasn't used their API in a while accumulates tokens and can make several requests quickly. **Tradeoff**: more complex state (tokens + last refill time) and floating-point arithmetic in the critical path.

## Next.js middleware integration

```ts
// middleware.ts
import { NextRequest, NextResponse } from 'next/server';

export async function middleware(req: NextRequest) {
  if (!req.nextUrl.pathname.startsWith('/api/')) {
    return NextResponse.next();
  }

  const ip     = req.ip ?? req.headers.get('x-forwarded-for') ?? 'anonymous';
  const { allowed, remaining } = await slidingWindowRateLimit(ip, 100, 60);

  const headers = new Headers();
  headers.set('X-RateLimit-Limit',     '100');
  headers.set('X-RateLimit-Remaining', String(remaining));
  headers.set('X-RateLimit-Reset',     String(Math.ceil(Date.now() / 1000) + 60));

  if (!allowed) {
    return new NextResponse('Too Many Requests', { status: 429, headers });
  }

  const res = NextResponse.next();
  headers.forEach((v, k) => res.headers.set(k, v));
  return res;
}

export const config = {
  matcher: '/api/:path*',
};
```

## Which algorithm to use

| Algorithm      | Burst tolerance | Accuracy | Complexity | Best for                     |
|----------------|-----------------|----------|------------|------------------------------|
| Fixed window   | None (boundary) | Low      | Lowest     | Simple internal APIs         |
| Sliding window | Low             | High     | Medium     | Public APIs, auth endpoints  |
| Token bucket   | Yes             | High     | Highest    | APIs with legitimate bursting|

For most web APIs: sliding window with Redis. It's accurate, doesn't permit boundary bursts, and the implementation is straightforward.

Token bucket is better when clients legitimately need to burst — a batch job that sends 50 API calls at startup, then goes quiet for minutes. Fixed window is fine for internal services where boundary bursting is acceptable and simplicity wins.

## Upstash Ratelimit: production shortcut

```ts
import { Ratelimit } from '@upstash/ratelimit';
import { Redis }     from '@upstash/redis';

const ratelimit = new Ratelimit({
  redis:     Redis.fromEnv(),
  limiter:   Ratelimit.slidingWindow(100, '60s'),
  analytics: true,
});

const { success, remaining } = await ratelimit.limit(ip);
```

`@upstash/ratelimit` implements all three algorithms against an Upstash Redis instance. It uses a Lua script to make each check atomic — no race conditions between the zadd, zremrangebyscore, and zcard operations.
