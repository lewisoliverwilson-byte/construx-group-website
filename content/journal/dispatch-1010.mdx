date: "2033-04-01"
excerpt: "Cilium's Gateway API implementation replaces Ingress and classic service mesh proxies with Kubernetes-native L7 traffic routing powered by eBPF and Envoy. The Gateway API is the successor to the Ingress resource — it separates concerns into GatewayClass (defines the infrastructure), Gateway (the actual load balancer), HTTPRoute (URL routing rules), and GRPCRoute (gRPC routing). Cilium wires Gateway API resources to its eBPF-based dataplane: simple routing decisions happen directly in the kernel without a userspace proxy, while complex L7 decisions (header manipulation, GRPC routing) go through an embedded Envoy. The result is lower latency than pure Envoy-based gateways for the common path."

Gateway API. HTTPRoute. eBPF + Envoy hybrid. Header manipulation. Traffic splitting. TLS termination.

## Gateway API resource hierarchy

```yaml
# Gateway API: four resource types replace the single Ingress resource

# GatewayClass: defines which controller implements the gateway
# (created by Cilium on install — you don't manage this)
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: cilium
spec:
  controllerName: io.cilium/gateway-controller

---
# Gateway: the actual load balancer (creates a service + provisioned LB)
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: construx-gateway
  namespace: construx-prod
spec:
  gatewayClassName: cilium

  listeners:
    # HTTPS listener with TLS termination
    - name: https
      protocol: HTTPS
      port: 443
      tls:
        mode: Terminate
        certificateRefs:
          - kind: Secret
            name: construx-tls-cert  # cert-manager-issued certificate
      allowedRoutes:
        namespaces:
          from: Selector
          selector:
            matchLabels:
              kubernetes.io/metadata.name: construx-prod

    # HTTP listener: redirect to HTTPS
    - name: http
      protocol: HTTP
      port: 80
      allowedRoutes:
        namespaces:
          from: Same

---
# HTTPRoute: URL routing rules attached to the gateway
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: construx-api-route
  namespace: construx-prod
spec:
  parentRefs:
    - name: construx-gateway
      sectionName: https

  hostnames:
    - api.construxgroup.io

  rules:
    # API v1 routes to construx-api service
    - matches:
        - path:
            type: PathPrefix
            value: /api/v1/
      backendRefs:
        - name: construx-api
          port: 8080
          weight: 100

    # Admin routes: only allow from specific source IPs
    - matches:
        - path:
            type: PathPrefix
            value: /api/admin/
      filters:
        - type: ExtensionRef
          extensionRef:
            group: cilium.io
            kind: CiliumHTTPRoute
            name: admin-restrict
      backendRefs:
        - name: construx-api
          port: 8080

    # Static assets: route to CDN origin
    - matches:
        - path:
            type: PathPrefix
            value: /static/
      backendRefs:
        - name: construx-cdn-origin
          port: 80

    # Redirect: /v1/ → /api/v1/
    - matches:
        - path:
            type: Exact
            value: /v1/
      filters:
        - type: RequestRedirect
          requestRedirect:
            scheme: https
            path:
              type: ReplaceFullPath
              replaceFullPath: /api/v1/
            statusCode: 301
```

## Traffic splitting and canary deployments

```yaml
# Traffic splitting: route a percentage to a canary backend
# Use weighted backendRefs on an HTTPRoute

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: construx-api-canary
  namespace: construx-prod
spec:
  parentRefs:
    - name: construx-gateway
      sectionName: https
  hostnames:
    - api.construxgroup.io

  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /api/v1/orders
      backendRefs:
        # 90% stable, 10% canary
        - name: construx-api-stable
          port: 8080
          weight: 90
        - name: construx-api-canary
          port: 8080
          weight: 10

---
# Header-based canary: route requests with X-Canary: true to the canary
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: construx-api-header-canary
  namespace: construx-prod
spec:
  parentRefs:
    - name: construx-gateway
  rules:
    # Canary: requests with X-Canary header go to canary service
    - matches:
        - path:
            type: PathPrefix
            value: /api/v1/
          headers:
            - name: X-Canary
              value: "true"
      backendRefs:
        - name: construx-api-canary
          port: 8080

    # Default: all other requests go to stable
    - matches:
        - path:
            type: PathPrefix
            value: /api/v1/
      backendRefs:
        - name: construx-api-stable
          port: 8080
```

## Header manipulation and request modification

```yaml
# Header manipulation: add, remove, or modify headers at the gateway

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: construx-api-headers
  namespace: construx-prod
spec:
  parentRefs:
    - name: construx-gateway
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /api/v1/
      filters:
        # Add headers before forwarding to backend
        - type: RequestHeaderModifier
          requestHeaderModifier:
            add:
              - name: X-Forwarded-For-Original
                value: "true"
              - name: X-Gateway-Version
                value: "cilium-1.16"
            remove:
              - X-Internal-Debug  # strip internal debug header before reaching app

        # Modify response headers before returning to client
        - type: ResponseHeaderModifier
          responseHeaderModifier:
            add:
              - name: Strict-Transport-Security
                value: "max-age=31536000; includeSubDomains"
              - name: X-Content-Type-Options
                value: "nosniff"
              - name: X-Frame-Options
                value: "DENY"
            remove:
              - Server      # don't expose server software version
              - X-Powered-By
      backendRefs:
        - name: construx-api
          port: 8080
```

## gRPC routing

```yaml
# GRPCRoute: native gRPC routing (no HTTP/1.1 protocol translation needed)
# Cilium Gateway API supports gRPC routing natively

apiVersion: gateway.networking.k8s.io/v1alpha2
kind: GRPCRoute
metadata:
  name: construx-grpc-route
  namespace: construx-prod
spec:
  parentRefs:
    - name: construx-gateway
      sectionName: https

  hostnames:
    - grpc.construxgroup.io

  rules:
    # Route all ProductService calls to construx-api
    - matches:
        - method:
            type: Exact
            service: construx.api.ProductService
      backendRefs:
        - name: construx-api
          port: 9090

    # Route OrderService to the orders microservice
    - matches:
        - method:
            type: Exact
            service: construx.api.OrderService
      backendRefs:
        - name: construx-orders
          port: 9090

    # Route specific method to a canary
    - matches:
        - method:
            type: Exact
            service: construx.api.SearchService
            method:  Search
      backendRefs:
        - name: construx-search-v2
          port: 9090
          weight: 20
        - name: construx-search
          port: 9090
          weight: 80
```

Gateway API vs Ingress vs Istio VirtualService: The Ingress resource is limited — one spec covers both infrastructure (which LB provider) and routing (which paths go where), making it hard for platform teams and application teams to manage separately. Istio VirtualService is powerful but tied to Istio and has no equivalent of the GatewayClass/Gateway separation. Gateway API's four-resource model lets the platform team manage GatewayClass + Gateway (infrastructure) while app teams manage HTTPRoute (routing), in different namespaces with different RBAC. Cilium's implementation is notable for the eBPF/Envoy hybrid: simple routing decisions (path prefix matching) happen in eBPF at kernel level with minimal overhead, while complex decisions (header manipulation, gRPC routing) route through Envoy. For teams on Cilium already, the Gateway API implementation is the natural evolution from Ingress.
