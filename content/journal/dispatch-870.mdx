Traces in S3. TraceQL to find them. No index to maintain.

## Send traces to Tempo with OpenTelemetry

```python
# requirements: opentelemetry-sdk, opentelemetry-exporter-otlp-proto-grpc
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
from opentelemetry.sdk.resources import Resource

# Configure the tracer with service metadata
resource = Resource.create({
    "service.name":    "construx-api",
    "service.version": "2.4.1",
    "deployment.environment": "production",
})

provider = TracerProvider(resource=resource)
provider.add_span_processor(
    BatchSpanProcessor(
        OTLPSpanExporter(endpoint="http://tempo.construx.internal:4317"),
        max_export_batch_size=512,
        export_timeout_millis=5000,
    )
)
trace.set_tracer_provider(provider)

tracer = trace.get_tracer("construx.api")

# Instrument a checkout endpoint
def process_order(order_id: str, customer_id: str):
    with tracer.start_as_current_span("process_order") as span:
        span.set_attributes({
            "order.id":      order_id,
            "customer.id":   customer_id,
            "http.route":    "/api/orders",
            "http.method":   "POST",
        })

        with tracer.start_as_current_span("validate_payment") as child:
            child.set_attribute("payment.provider", "stripe")
            result = validate_payment(order_id)
            child.set_attribute("payment.outcome", result.status)

        with tracer.start_as_current_span("write_order_db") as child:
            child.set_attribute("db.system", "postgresql")
            child.set_attribute("db.statement", "INSERT INTO orders ...")
            write_to_db(order_id)

        span.set_attribute("order.status", "accepted")
```

## TraceQL — query traces like a database

```
# Find all traces where any span took > 2 seconds
{ duration > 2s }

# Find traces from the construx-api service with 5xx errors
{ resource.service.name = "construx-api" && status = error }

# Find the specific checkout span that failed
{ span.http.route = "/api/checkout" && status = error && duration > 1s }

# Aggregate: p99 latency by service (Tempo 2.x metrics from traces)
{ resource.service.name =~ "construx-.*" }
| rate()
| by(resource.service.name)

# Find traces where payment span failed but order span succeeded
{ span.name = "validate_payment" && status = error }
  && { span.name = "process_order" && status = ok }

# Structural query: spans that are children of a failed parent
{ parent.status = error } && { span.name = "write_order_db" }
```

## tempo.yaml — object storage backend

```yaml
# /etc/tempo/tempo.yaml
server:
  http_listen_port: 3200

distributor:
  receivers:
    otlp:
      protocols:
        grpc:
          endpoint: 0.0.0.0:4317
        http:
          endpoint: 0.0.0.0:4318

storage:
  trace:
    backend: s3
    s3:
      bucket: construx-tempo-traces
      region: eu-west-2
      # No index — traces stored as bloom filter + parquet blocks
    pool:
      max_workers: 100
      queue_depth: 10000

# Trace retention — delete blocks older than 30 days
compactor:
  compaction:
    block_retention: 720h    # 30 days

# Metrics from traces (RED metrics: rate, error, duration)
# Generates Prometheus metrics automatically from span data
metrics_generator:
  storage:
    path: /var/tempo/generator/wal
  processors:
    - service-graphs
    - span-metrics
```

## Correlate traces with logs in Grafana

```yaml
# grafana/datasource.yaml — link Tempo traces to Loki logs
# When viewing a trace in Grafana, click through to the correlated log lines

datasources:
  - name: Tempo
    type: tempo
    url: http://tempo.construx.internal:3200
    jsonData:
      tracesToLogsV2:
        datasourceUid: loki_uid
        spanStartTimeShift: '-1m'
        spanEndTimeShift:   '1m'
        filterByTraceID: true
        filterBySpanID:  false
        customQuery: true
        query: '{service_name="${__span.tags["service.name"]}"} |= "${__trace.traceId}"'

  - name: Loki
    type: loki
    uid: loki_uid
    url: http://loki.construx.internal:3100
```

Tempo vs Jaeger: Jaeger requires Cassandra or Elasticsearch for storage — expensive to run at scale, and the storage bill grows with trace volume. Tempo writes traces directly to object storage as Parquet-format blocks with a bloom filter index (no secondary index). A Jaeger cluster storing 10TB of traces costs ~$5k/month on Elasticsearch. The same data in Tempo on S3 costs ~$230/month. The tradeoff: Tempo is query-slower on cold data (has to fetch blocks from S3), and TraceQL is less mature than Jaeger's UI. For high-volume production tracing, the cost difference is decisive.
