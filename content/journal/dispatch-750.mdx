Postgres that branches like git, scales to zero, and runs at the edge. This is what database infrastructure looks like now.

## Connect with Drizzle ORM

```ts
// src/lib/db.ts
import { drizzle }  from 'drizzle-orm/neon-http';
import { neon }     from '@neondatabase/serverless';
import * as schema  from './schema';

const sql = neon(process.env.DATABASE_URL!);
export const db = drizzle(sql, { schema });
```

The `neon-http` adapter works in any HTTP context — Vercel Edge Functions, Cloudflare Workers, Next.js Server Actions — without a persistent connection pool.

## Schema with Drizzle

```ts
// src/lib/schema.ts
import { pgTable, text, timestamp, uuid, boolean } from 'drizzle-orm/pg-core';

export const users = pgTable('users', {
  id:          uuid('id').primaryKey().defaultRandom(),
  email:       text('email').notNull().unique(),
  name:        text('name'),
  onboardedAt: timestamp('onboarded_at'),
  createdAt:   timestamp('created_at').notNull().defaultNow(),
});

export const workspaces = pgTable('workspaces', {
  id:        uuid('id').primaryKey().defaultRandom(),
  ownerId:   uuid('owner_id').notNull().references(() => users.id),
  slug:      text('slug').notNull().unique(),
  name:      text('name').notNull(),
  plan:      text('plan').notNull().default('free'),
  isActive:  boolean('is_active').notNull().default(true),
  createdAt: timestamp('created_at').notNull().defaultNow(),
});
```

## Branch per PR with the Neon API

```ts
// scripts/create-branch.ts — called from CI on PR open
import { createApiClient } from '@neondatabase/api-client';

const client = createApiClient({ apiKey: process.env.NEON_API_KEY! });

const { data: branch } = await client.createProjectBranch(
  process.env.NEON_PROJECT_ID!,
  {
    branch:   { name: `pr-${process.env.PR_NUMBER}` },
    endpoints: [{ type: 'read_write' }],
  },
);

console.log(branch.connection_uris[0].connection_uri);
// Use this URI as DATABASE_URL in the preview deployment
```

Each PR gets a real Postgres branch — a copy-on-write clone of main, ready in under a second. Delete the branch when the PR closes.

## Autoscaling and scale-to-zero

Neon compute suspends after a configurable idle period (default: 5 minutes). On the next query, it resumes in ~500ms. For background jobs that run infrequently, this means zero database cost during idle hours.

```ts
// Handle the cold-start reconnect transparently
// The neon() driver retries automatically — no extra code needed
const result = await db.select().from(users).where(eq(users.id, userId));
```

## Read replicas for analytics

```ts
// Read replica for heavy queries — doesn't touch primary
const readSql    = neon(process.env.DATABASE_URL_REPLICA!);
const readDb     = drizzle(readSql, { schema });

const analytics = await readDb
  .select({ count: count() })
  .from(workspaces)
  .where(eq(workspaces.plan, 'pro'));
```

## Connection pooling with PgBouncer

For high-concurrency workloads (Next.js with many concurrent requests), use the pooled connection string:

```
postgresql://user:pass@ep-xxx.us-east-2.aws.neon.tech/neondb?pgbouncer=true
```

Neon provides PgBouncer as a built-in option per endpoint. No separate deployment.

## Neon vs PlanetScale vs Supabase vs Railway

Neon: real Postgres, branching, scale-to-zero, edge-compatible HTTP driver. PlanetScale: MySQL (now paid-only), schema branching, no foreign keys. Supabase: Postgres + auth + storage + realtime — more opinionated, more features. Railway: managed Postgres on your own infra, no branching, no scale-to-zero. The Construx default: Neon for solo and small-team projects; Supabase when auth and storage integration is needed.
