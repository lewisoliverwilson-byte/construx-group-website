excerpt: "Terraform is the dominant infrastructure-as-code tool: you declare resources in HCL (HashiCorp Configuration Language), Terraform computes a plan (diff between desired and current state), and applies changes idempotently. The state file (terraform.tfstate) is the source of truth — it maps your HCL resources to real infrastructure IDs. For teams, state must live in a remote backend (S3 + DynamoDB for locking, Terraform Cloud, or Atlantis) so multiple engineers don't corrupt each other's state. Modules make configs reusable across environments."

Declare the end state. Terraform reconciles. State holds the mapping.

## Core resource declaration

```hcl
# main.tf — construx production infrastructure

terraform {
  required_version = ">= 1.9.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.82"
    }
  }

  # Remote state: S3 bucket + DynamoDB for distributed locking
  backend "s3" {
    bucket         = "construx-terraform-state"
    key            = "production/terraform.tfstate"
    region         = "eu-west-2"
    dynamodb_table = "construx-tf-locks"   # Prevents concurrent applies
    encrypt        = true
  }
}

provider "aws" {
  region = var.aws_region
  default_tags {
    tags = {
      Project     = "construx"
      Environment = var.environment
      ManagedBy   = "terraform"
    }
  }
}

# Variables — overridden per environment via .tfvars files
variable "aws_region"   { default = "eu-west-2" }
variable "environment"  { default = "production" }
variable "instance_type" { default = "t3.medium" }

# EC2 instance
resource "aws_instance" "api_server" {
  count         = 2
  ami           = data.aws_ami.ubuntu.id
  instance_type = var.instance_type

  vpc_security_group_ids = [aws_security_group.api_sg.id]
  iam_instance_profile   = aws_iam_instance_profile.api.name
  user_data              = file("${path.module}/scripts/bootstrap.sh")

  tags = { Name = "construx-api-${count.index}" }
}

# Look up latest Ubuntu 24.04 AMI — data sources are read-only
data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"]  # Canonical
  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd/ubuntu-noble-24.04-amd64-server-*"]
  }
}
```

## Modules — reusable infrastructure components

```hcl
# modules/rds-postgres/main.tf
# Usage: module "db" { source = "./modules/rds-postgres" ... }

variable "identifier"      { type = string }
variable "instance_class"  { default = "db.t3.medium" }
variable "storage_gb"      { default = 100 }
variable "database_name"   { type = string }
variable "vpc_id"          { type = string }
variable "subnet_ids"      { type = list(string) }

resource "aws_db_instance" "this" {
  identifier        = var.identifier
  engine            = "postgres"
  engine_version    = "16.1"
  instance_class    = var.instance_class
  allocated_storage = var.storage_gb
  db_name           = var.database_name

  username = "construx"
  password = random_password.db.result  # Managed by Terraform, stored in state

  vpc_security_group_ids = [aws_security_group.db.id]
  db_subnet_group_name   = aws_db_subnet_group.this.name
  multi_az               = true
  deletion_protection    = true
  skip_final_snapshot    = false
  final_snapshot_identifier = "${var.identifier}-final"

  backup_retention_period = 7
  backup_window           = "03:00-04:00"
  maintenance_window      = "Mon:04:00-Mon:05:00"
}

output "endpoint" { value = aws_db_instance.this.endpoint }
output "db_name"  { value = var.database_name }
```

```hcl
# Root module uses the rds-postgres module
module "primary_db" {
  source = "./modules/rds-postgres"

  identifier    = "construx-prod"
  instance_class = "db.r8g.large"
  storage_gb    = 200
  database_name = "construx_production"
  vpc_id        = module.vpc.vpc_id
  subnet_ids    = module.vpc.private_subnets
}
```

## Terraform workflow — plan, apply, state

```bash
# Init: download providers and configure backend
terraform init

# Plan: show what would change (safe to run anytime)
terraform plan -out=tfplan
# + aws_instance.api_server[0]    (create)
# + aws_instance.api_server[1]    (create)
# ~ aws_db_instance.postgres      (update: storage 100GB → 200GB)
# Plan: 2 to add, 1 to change, 0 to destroy.

# Apply the saved plan exactly — no surprises
terraform apply tfplan

# Inspect state — what Terraform knows about the world
terraform state list
# aws_instance.api_server[0]
# aws_instance.api_server[1]
# module.primary_db.aws_db_instance.this

terraform state show aws_instance.api_server[0]
# Shows all attributes Terraform tracks for this resource

# Import existing resources into state (bring unmanaged infra under control)
terraform import aws_s3_bucket.assets construx-static-assets-prod

# Move state entries when refactoring module structure
terraform state mv aws_instance.api 'module.compute.aws_instance.api'
```

## Atlantis — Terraform PRs with policy gates

```yaml
# atlantis.yaml — run Terraform plans as GitHub PR checks
version: 3
projects:
  - name: production
    dir: infra/production
    workflow: default
    apply_requirements:
      - approved          # At least one approval before apply
      - mergeable         # PR must be mergeable (no conflicts)
      - undiverged        # Branch must be up to date with main

workflows:
  default:
    plan:
      steps:
        - run: terraform fmt -check
        - init
        - plan:
            extra_args: ["-var-file=production.tfvars"]
    apply:
      steps:
        - apply

# PR workflow:
# 1. Engineer opens PR with infrastructure change
# 2. Atlantis runs `terraform plan` and posts the output as a PR comment
# 3. Team reviews the plan diff — sees exactly what will change
# 4. Approvals trigger `atlantis apply` — applies and auto-merges
```

Terraform vs Pulumi: Terraform uses HCL — a declarative language with limited expressiveness (no real loops, no functions). Pulumi uses general-purpose languages (TypeScript, Python, Go) — you write infrastructure with `if` statements, loops, and real abstractions. HCL is simpler to review; Pulumi is more powerful. For most teams, Terraform's larger ecosystem (Terraform Registry has 4000+ providers vs Pulumi's ~300) and wider knowledge base wins. Pulumi wins when your infrastructure is highly dynamic or you need tight language-level integration with application code.
