date: "2031-12-25"
excerpt: "Istio is a service mesh for Kubernetes. It injects a sidecar proxy (Envoy) into every pod and intercepts all network traffic. The result is automatic mutual TLS between every service, traffic management (load balancing, retries, circuit breakers, canary splits) configured via Kubernetes CRDs, and distributed tracing emitted by the sidecar without any code changes. Istio's control plane (Istiod) distributes xDS configuration to every Envoy sidecar dynamically."

Sidecar in every pod. Automatic mTLS. Traffic policy as Kubernetes config.

## Install Istio

```bash
# Install Istio with the default profile
istioctl install --set profile=default -y

# Verify installation
istioctl verify-install

# Enable sidecar injection for a namespace
kubectl label namespace production istio-injection=enabled

# After labelling, new pods get the Envoy sidecar automatically
# Existing pods: kubectl rollout restart deployment -n production

# Check sidecar injection
kubectl get pods -n production -o jsonpath='{.items[*].metadata.annotations.sidecar\.istio\.io/status}'
```

## PeerAuthentication — enforce mTLS

```yaml
# k8s/istio-mtls.yaml
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name:      default
  namespace: production
spec:
  mtls:
    mode: STRICT   # Reject all plaintext traffic between services
```

```yaml
# Verify mTLS is working
# In STRICT mode, all service-to-service traffic is mutually authenticated
# Certificate rotation is handled automatically by Istiod

# Check certificate for a pod's sidecar
istioctl proxy-config secret orders-api-7b9f4-xk2m.production
```

## VirtualService — traffic management

```yaml
# k8s/orders-vs.yaml
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name:      orders-api
  namespace: production
spec:
  hosts: [orders-api]
  http:
    # Canary: route 10% to v2
    - route:
        - destination:
            host:   orders-api
            subset: stable
          weight: 90
        - destination:
            host:   orders-api
            subset: canary
          weight: 10

    # Retry policy
    retries:
      attempts:      3
      perTryTimeout: 10s
      retryOn:       "5xx,gateway-error,connect-failure"

    # Timeout
    timeout: 30s
```

```yaml
# k8s/orders-dr.yaml — DestinationRule: define subsets
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name:      orders-api
  namespace: production
spec:
  host: orders-api
  trafficPolicy:
    connectionPool:
      tcp:  { maxConnections: 1000 }
      http: { h2UpgradePolicy: UPGRADE, http2MaxRequests: 1000 }
    outlierDetection:
      consecutive5xxErrors:  5
      interval:              10s
      baseEjectionTime:      30s
      maxEjectionPercent:    50
  subsets:
    - name:   stable
      labels: { version: stable }
    - name:   canary
      labels: { version: canary }
```

## AuthorizationPolicy — zero-trust access control

```yaml
# k8s/orders-authz.yaml
# Only allow the API gateway and payments service to call the orders service
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name:      orders-authz
  namespace: production
spec:
  selector:
    matchLabels:
      app: orders-api
  rules:
    - from:
        - source:
            principals:
              - "cluster.local/ns/production/sa/api-gateway"
              - "cluster.local/ns/production/sa/payments-service"
      to:
        - operation:
            methods: ["GET", "POST"]
            paths:   ["/api/orders*"]
```

## Distributed tracing — automatic with no code changes

```bash
# Istio emits Zipkin/Jaeger traces via the Envoy sidecar
# Every request gets trace headers injected automatically

# View traces in Kiali (Istio's dashboard)
istioctl dashboard kiali

# Or port-forward Jaeger directly
kubectl port-forward svc/tracing 16686:80 -n istio-system

# Check trace propagation — Istio adds these headers automatically:
# x-request-id
# x-b3-traceid
# x-b3-spanid
# x-b3-parentspanid
# x-b3-sampled

# Your application code must propagate these headers for end-to-end traces
# (Istio only connects adjacent spans — app must forward headers to complete the chain)
```

## Mesh topology in Kiali

```bash
istioctl dashboard kiali
# Opens browser at localhost:20001
# Shows:
# - Service dependency graph (which services call which)
# - Traffic flow rates (req/s per edge)
# - Error rates per service (red = > 5% errors)
# - mTLS status (lock icon = encrypted, plain = not)
# - Canary traffic split visualisation (90/10 shown graphically)
```

Istio vs Linkerd: Linkerd is a lighter service mesh written in Rust — less resource overhead (~50MB per pod vs ~100MB for Envoy), simpler installation, mTLS by default, and a smaller feature set. Istio has more features (WebAssembly extensions, full xDS control plane, richer traffic management) at the cost of complexity and resource consumption. For a team that wants mTLS and basic traffic management without deep proxy configuration, Linkerd. For teams that need WebAssembly extensions, complex routing, or full Envoy feature access, Istio.
