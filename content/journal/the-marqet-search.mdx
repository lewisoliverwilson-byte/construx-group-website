The Marqet's catalogue has 167 AI configurations across dozens of professional use cases. Browsing by category works for users who know what they want. Search is for users who know what they need but can't name it.

Keyword search fails for this use case. "Social media" matches listings that include the phrase "social media" in their title or description — but the user who wants help planning a social media calendar might find better results searching by "content planning" or "brand consistency" or "audience building," not "social media."

Semantic search finds listings by meaning, not by keyword. Here's how we built it.

## The problem with keyword search for AI prompts

AI configuration listings have two properties that make keyword search particularly bad:

**Vocabulary mismatch.** The user's vocabulary for what they need ("help me write better emails") doesn't necessarily match the listing author's vocabulary for what they built ("professional communication template" or "executive communication toolkit"). Both describe the same thing; keyword search finds neither.

**Latent utility.** A listing for a "brand narrative architect" might be exactly what a user needs when searching for "competitive positioning help" — but the two phrases share no keywords. The semantic connection is obvious to a human; invisible to keyword search.

Traditional search fixes these problems with synonym dictionaries and relevance tuning. For a small catalogue with evolving content, we wanted something that understood meaning natively.

## The architecture

The search pipeline has three components:

**Embedding generation** — Each listing has its title, description, and use cases embedded using Claude's embedding model. The embedding is a dense vector that captures the semantic meaning of the listing in a high-dimensional space.

**Embedding storage** — We store embeddings in a pgvector column alongside the listing data. pgvector adds vector similarity operators to Postgres, so we can query "find the N listings most similar to this query vector" as a standard SQL query.

**Query processing** — When a user searches, we embed their query using the same model, then execute a nearest-neighbour query in pgvector to find the most semantically similar listings.

```sql
SELECT id, title, description,
       embedding <=> $1 AS distance
FROM listings
ORDER BY embedding <=> $1
LIMIT 12;
```

The `<=>` operator in pgvector is cosine distance. We order by distance (lower = more similar) and return the top 12 results.

## Generating and storing embeddings

Listing embeddings are generated when a listing is created or updated. We concatenate the title, description, and key use cases into a single text string and pass it to the embedding API:

```typescript
async function generateListingEmbedding(listing: Listing): Promise<number[]> {
  const text = [
    listing.title,
    listing.description,
    ...listing.useCases,
  ].join('\n\n');

  const response = await anthropic.embeddings.create({
    model: 'claude-embedding-v1',
    input: text,
  });

  return response.embedding;
}
```

The embedding is stored as a `vector(1536)` column in Postgres. On listing creation or update, we regenerate the embedding asynchronously — the listing goes live immediately, the embedding is available within seconds.

## The query flow

User search request → embed query → pgvector nearest-neighbour → rerank → return results.

The reranking step: pure vector similarity returns results that are semantically close but may not be the most commercially relevant. We apply a light reranking that boosts:
- Listings with high usage (more users have viewed or purchased)
- Listings that match the user's stated professional role
- Recent listings (recency bias for a catalogue that's actively growing)

The reranking is a weighted score combination, not another model call. It's deterministic and fast.

## What we learned from testing

Semantic search is qualitatively better for ambiguous queries and about equal to keyword search for exact queries.

For "content strategy", semantic search returns: brand narrative architect, editorial calendar builder, marketing copy specialist, content planning assistant. Keyword search returns only listings that include the phrase "content strategy" verbatim.

For "javascript async", semantic search returns mostly the same listings as keyword search, with a few additions that describe async patterns without using the term.

We run both approaches and blend the results for queries where the overlap is low — this handles the case where the user is doing a specific keyword lookup and semantic search adds noise.

## The edge cases

**Short queries** are harder. A one or two-word query produces an embedding that's less specific than a longer phrase. "Design" could mean UI design, graphic design, product design, architectural design, or a dozen other things. We handle this by showing a disambiguation prompt for very short queries: "Are you looking for: [UI Design tools] [Brand Design tools] [Product Design tools]..."

**Empty results** — when the nearest-neighbour returns listings that are below a similarity threshold (distance > 0.4 in our tuning), we fall back to keyword search. This prevents returning results that are technically the closest but semantically unrelated.

**Embedding drift** — as we improve listing descriptions, the text used to generate embeddings changes. We run a weekly job that regenerates embeddings for listings where the text has changed. This keeps the search index current.

## The result

Search converted from a feature with low engagement (most users browsed by category) to one with meaningful usage. Users who arrive via search convert to purchase at a higher rate than users who browse — which makes sense, because search users arrive with more specific intent.

The pgvector implementation adds about 30ms to the search query versus a standard text search. That's the right trade for qualitatively better results.
