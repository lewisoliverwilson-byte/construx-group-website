excerpt: "Ory Hydra is an open-source OAuth2 and OpenID Connect server that implements the protocol without handling user management — it delegates authentication to an external login provider via a consent flow. This separation is deliberate: Hydra focuses entirely on the OAuth2 token lifecycle (authorization codes, access tokens, refresh tokens, JWTs), while the identity layer (username/password, MFA, social login) is handled by Ory Kratos or an existing identity provider. Hydra supports all major OAuth2 grant types: authorization code with PKCE (the secure flow for SPAs and mobile apps), client credentials (machine-to-machine), device code (CLI tools and IoT), and token introspection (resource servers validate tokens against Hydra's introspection endpoint). The authorization code flow with PKCE is the current best practice for all public clients: the client generates a code_verifier and code_challenge, the authorization endpoint issues a code, and the token endpoint validates the code_challenge before issuing tokens — preventing authorization code interception attacks without requiring client secrets. Hydra stores OAuth2 state in PostgreSQL or CockroachDB, supports horizontal scaling (stateless), and exposes both a public API (for OAuth2 flows) and an admin API (for client management, token revocation, and introspection). At Construx, Hydra provides OAuth2 for the public API and M2M authentication for service-to-service calls within the platform."

## Hydra OAuth2 flows and client configuration

```bash
# Ory Hydra: create OAuth2 clients and inspect tokens

# Create a public client (SPA / mobile app) — authorization code + PKCE
hydra clients create \
  --endpoint http://hydra-admin.construx-auth.svc.cluster.local:4445 \
  --id construx-dashboard \
  --secret "" \   # public clients have no secret (PKCE replaces it)
  --grant-types authorization_code,refresh_token \
  --response-types code \
  --scope "openid profile email orders:read orders:write" \
  --redirect-uris "https://app.construx.io/auth/callback" \
  --token-endpoint-auth-method none \  # public client
  --post-logout-redirect-uris "https://app.construx.io/logout"

# Create a confidential client (backend service / machine-to-machine)
hydra clients create \
  --endpoint http://hydra-admin.construx-auth.svc.cluster.local:4445 \
  --id payments-service \
  --secret "${PAYMENTS_SERVICE_SECRET}" \
  --grant-types client_credentials \
  --response-types token \
  --scope "orders:read payments:write" \
  --token-endpoint-auth-method client_secret_post

# List all clients
hydra clients list --endpoint http://hydra-admin.construx-auth.svc.cluster.local:4445

# Token introspection: validate and inspect a token
hydra token introspect \
  --endpoint http://hydra-admin.construx-auth.svc.cluster.local:4445 \
  "${ACCESS_TOKEN}"

# Output:
```

```go
// Authorization code flow with PKCE: Go implementation for CLI tool

package auth

import (
    "crypto/rand"
    "crypto/sha256"
    "encoding/base64"
    "fmt"
    "net/http"
    "net/url"

    "golang.org/x/oauth2"
)

type PKCEClient struct {
    config oauth2.Config
}

// generatePKCE generates code_verifier and code_challenge for PKCE flow
func generatePKCE() (verifier, challenge string, err error) {
    buf := make([]byte, 32)
    if _, err = rand.Read(buf); err != nil {
        return
    }
    verifier  = base64.RawURLEncoding.EncodeToString(buf)
    hash      := sha256.Sum256([]byte(verifier))
    challenge  = base64.RawURLEncoding.EncodeToString(hash[:])
    return
}

func (c *PKCEClient) StartAuthFlow() (authURL, verifier string, err error) {
    verifier, challenge, err := generatePKCE()
    if err != nil {
        return "", "", err
    }

    state := make([]byte, 16)
    rand.Read(state)
    stateStr := base64.RawURLEncoding.EncodeToString(state)

    authURL = c.config.AuthCodeURL(stateStr,
        oauth2.SetAuthURLParam("code_challenge",        challenge),
        oauth2.SetAuthURLParam("code_challenge_method", "S256"),
    )
    return authURL, verifier, nil
}

func (c *PKCEClient) ExchangeCode(code, verifier string) (*oauth2.Token, error) {
    return c.config.Exchange(
        context.Background(),
        code,
        oauth2.SetAuthURLParam("code_verifier", verifier),
    )
}
```

Hydra vs Keycloak vs Auth0 vs AWS Cognito vs Ory Kratos: Keycloak is the most feature-complete self-hosted identity solution — it handles everything (OAuth2, OIDC, SAML, user management, MFA, social login, admin console, fine-grained authorization) in one system. The trade-off is operational weight: Keycloak requires a JVM, significant memory, and is complex to configure. Auth0 and AWS Cognito are managed identity platforms — excellent developer experience, no infrastructure to manage, but per-MAU pricing becomes significant at scale and data residency may be a concern. Ory Kratos handles user identity (self-service registration, login, MFA, profile management) without implementing OAuth2 — it pairs with Hydra for the OAuth2 layer, giving a clean separation of concerns. This architecture is operationally more complex than Keycloak (two systems instead of one) but each component is lighter and more focused. For Construx, the Hydra + Kratos combination provides: Kratos for the user-facing login UI and session management; Hydra for OAuth2 tokens used by the API and service-to-service calls; SpiceDB for fine-grained authorisation decisions after authentication.
