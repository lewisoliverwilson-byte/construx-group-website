API-first design means thinking about your product's core functionality as a set of capabilities that can be called programmatically, before (or alongside) building the user interface that provides human access to those capabilities.

This is a design philosophy, not just a technical choice. It shapes what you build and how it's composed.

## The practical definition

For Scoutr, the core capability is: given a product URL, return fee calculations and profit margin analysis for Amazon and eBay resale.

API-first means that capability exists as a standalone function or endpoint that takes a URL and returns structured data. The user interface (the web app with its scan button and results display) is built on top of that function — it's one consumer of the capability.

A non-API-first approach: the fee calculation logic is embedded in the web interface, tightly coupled to the HTML rendering, impossible to call without triggering the UI. This works for the initial use case and fails as soon as someone wants to use the capability differently (in batch, via script, from another tool).

## Why it matters for AI products specifically

AI products have capabilities that are more complex and valuable than typical CRUD applications. An AI that can classify products, generate summaries, or make recommendations is a significant capability. If that capability is locked inside a web UI, its value is bounded by what the UI allows.

API exposure unlocks:
- **Batch processing**: a Scoutr user who wants to scan 500 products from a spreadsheet needs an API, not a web interface
- **Integration**: a user who wants Scoutr to feed data into their own inventory management system needs an API
- **Automation**: a user who wants scans triggered nightly without manual input needs an API
- **Building on top**: developers who want to build their own tools using Scoutr's capability need an API

These aren't features we've built yet (the Business tier API is in progress). But designing the core capabilities as functions from the start means the API can be exposed without significant refactoring.

## How we implement it

Every significant product capability in the Construx products lives in a function in `lib/` that:
- Takes typed inputs
- Returns typed outputs
- Has no side effects on the UI
- Can be called from anywhere (API routes, server components, background jobs, tests)

For Scoutr:
```typescript
// lib/scanner.ts
export async function scanProduct(url: string, options?: ScanOptions): Promise<ScanResult> {
  // product detection, fee calculation, margin analysis
  // no UI concerns, no state management
}
```

The web interface calls this function. The API route calls this function. A future batch processor would call this function. The function doesn't know or care who's calling it.

## The "what is the API of this product?" test

For any product feature, we ask: "if this were an API endpoint, what would the request look like and what would the response contain?"

This test reveals:
- What the input contract is (what data the feature needs)
- What the output contract is (what the feature promises to deliver)
- Whether the feature is doing too many things at once (a function that does 5 distinct things is not a clean API)
- Whether the feature has implicit UI dependencies that should be separated

If you can write the API signature clearly, you understand the feature. If you can't, the feature is either underspecified or doing too much.

## API design for external consumption

Scoutr's Business tier API (in progress) is designed for external developers. The design principles:

**RESTful resources over RPC calls.** `/api/scans` not `/api/doScan`. The resource model is predictable.

**Consistent error responses.** Every error returns `{ error: string, code: string, details?: object }`. Clients can handle errors consistently without per-endpoint special cases.

**Pagination for list endpoints.** Any endpoint that returns multiple items should support cursor-based pagination. An API that returns unbounded lists will cause problems as the data grows.

**Versioned.** `/api/v1/scans` allows introducing breaking changes in `/api/v2/` without breaking existing clients. We start with versioning from day one.

**Rate limiting headers.** Every response includes `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset` so clients can handle their own rate limiting behaviour.

**Webhooks for async operations.** A scan that takes 4 seconds shouldn't require the API client to poll. A webhook allows us to notify the client when the scan is complete.

## What API-first costs

The overhead is real: additional architecture thinking upfront, type definitions for request/response shapes, separate route handlers for API vs. UI, API documentation. For a two-person team building fast, this adds time.

The payoff: the product's capabilities are accessible and composable from the start. When a user asks for something we haven't built yet ("can I get this via API?"), the answer is often "almost — here's what it would take" rather than "that would require a complete rewrite."
