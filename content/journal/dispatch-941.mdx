excerpt: "vegeta is an HTTP load testing tool that attacks a target at a precise, constant request rate — not a concurrency pool like wrk or ab, which push as many requests as they can. The pipeline is three separate commands: `attack` (sends requests, encodes results as binary), `encode` (converts between formats), and `report` (aggregates statistics). The binary encoding allows live attack results to be piped, tee'd to disk, and replayed later. `report -type=hist` renders a latency histogram with configurable buckets. `plot` generates an interactive SVG. The rate sweep pattern — running attack at increasing rates and checking p99 vs SLO — is the standard way to find the saturation point of an HTTP service."

Constant rate. Pipe to disk. Replay anytime. p99 SLO tracking across a rate sweep.

## Attack, encode, report pipeline

```bash
# vegeta: the pipeline is attack → [encode] → report
# attack reads targets from stdin, encodes responses as binary to stdout

# Simplest form: GET a single endpoint at 500 RPS for 30 seconds
echo 'GET https://api.construx.io/v1/health' | \
  vegeta attack -rate=500 -duration=30s | \
  vegeta report

# Requests      [total, rate, throughput]  15000, 500.0/s, 499.1/s
# Duration      [total, attack, wait]      30.018s, 30.000s, 17.832ms
# Latencies     [min, mean, 50, 90, 95, 99, max]
#               1.2ms  18.4ms  12.1ms  38.7ms  54.2ms  142.3ms  384.1ms
# Bytes In      [total, mean]              1,350,000, 90.00
# Bytes Out     [total, mean]              0, 0.00
# Success       [ratio]                    99.84%
# Status Codes  [code:count]               200:14976  429:18  503:6

# Tee to disk while running (replay later without re-attacking)
echo 'GET https://api.construx.io/v1/health' | \
  vegeta attack -rate=500 -duration=30s | \
  tee results.bin | \
  vegeta report

# Report on saved results
vegeta report results.bin

# Multiple target files: one request per line
cat targets.txt
# GET https://api.construx.io/v1/orders
# GET https://api.construx.io/v1/customers
# POST https://api.construx.io/v1/orders
# @headers.txt   (inject per-request headers)
# @body.json     (inject per-request body)

cat targets.txt | vegeta attack -rate=200 -duration=60s | vegeta report

# targets with headers and body
cat <<'EOF' > targets.txt
GET https://api.construx.io/v1/orders
Authorization: Bearer eyJhbGc...
Content-Type: application/json

POST https://api.construx.io/v1/orders
Authorization: Bearer eyJhbGc...
Content-Type: application/json
@/tmp/order-payload.json
EOF
```

## Latency histograms and plots

```bash
# report -type=hist: latency distribution with configurable buckets
vegeta report results.bin -type='hist[0,10ms,50ms,100ms,500ms,1s]'

# Bucket           #       %        Histogram
# [0,    10ms]    3841  25.61%  ████████████████
# [10ms, 50ms]    8923  59.49%  ████████████████████████████████████████
# [50ms,100ms]    1894  12.63%  ████████
# [100ms,500ms]    318   2.12%  █
# [500ms,  1s]      24   0.16%

# plot: generate an interactive SVG (latency over time)
vegeta plot results.bin > results.html
open results.html   # opens in browser — scatter plot with percentile lines

# Combine multiple attacks for comparison
vegeta report -type=hist[0,10ms,100ms,1s] v1-results.bin v2-results.bin

# encode: convert binary to JSON for external analysis
vegeta encode results.bin | jq '.latency / 1e6'  # latency in ms, one per line

# encode to CSV
vegeta encode results.bin --to=csv > results.csv
```

## Rate sweep — finding saturation

```bash
# Pattern: ramp rate from low to high, record p99 at each step
# Find where p99 crosses the SLO threshold (e.g. 200ms)

for rate in 100 200 400 600 800 1000; do
  echo "GET https://api.construx.io/v1/orders" | \
    vegeta attack -rate=${rate} -duration=20s > /tmp/v-${rate}.bin 2>&1

  p99=$(vegeta report /tmp/v-${rate}.bin 2>/dev/null | \
    awk '/Latencies/{getline; print $6}' | sed 's/ms//')

  success=$(vegeta report /tmp/v-${rate}.bin 2>/dev/null | \
    awk '/Success/{print $2}')

  printf "rate=%4d  p99=%7s ms  success=%s\n" $rate $p99 $success
done

# rate= 100  p99=  14.2 ms  success=100.00%
# rate= 200  p99=  18.7 ms  success=100.00%
# rate= 400  p99=  38.4 ms  success= 99.98%
# rate= 600  p99=  94.1 ms  success= 99.81%
# rate= 800  p99= 241.3 ms  success= 98.42%  ← SLO breach (p99 > 200ms)
# rate=1000  p99= 984.2 ms  success= 91.17%

# The saturation point is between 600 and 800 RPS — binary search to find it precisely

# Automate SLO validation in CI
P99_LIMIT_MS=200
echo 'GET https://api.construx.io/v1/health' | \
  vegeta attack -rate=500 -duration=30s | vegeta report > /tmp/report.txt

P99=$(grep Latencies /tmp/report.txt | awk '{print $7}' | sed 's/ms//')
awk -v p99="$P99" -v limit="$P99_LIMIT_MS" \
  'BEGIN { if (p99+0 > limit+0) { print "SLO breach: p99="p99"ms > "limit"ms"; exit 1 } else { print "SLO OK: p99="p99"ms"; exit 0 } }'
```

## Advanced: custom clients and chunked uploads

```bash
# -workers: number of goroutines sending requests (default: max-workers or 10)
# Increase if the attack can't sustain the target rate (check rate vs throughput)
echo 'GET https://api.construx.io/v1/health' | \
  vegeta attack -rate=2000 -duration=10s -workers=50 | vegeta report

# -max-body: limit response body read (saves memory for large responses)
echo 'GET https://api.construx.io/v1/orders?limit=1000' | \
  vegeta attack -rate=50 -duration=60s -max-body=1024 | vegeta report

# -http2: force HTTP/2 (default: auto-negotiate)
echo 'GET https://api.construx.io/v1/health' | \
  vegeta attack -rate=500 -duration=30s -http2 | vegeta report

# -insecure: skip TLS verification (for staging with self-signed certs)
echo 'GET https://staging.construx.io/v1/health' | \
  vegeta attack -rate=100 -duration=10s -insecure | vegeta report

# -keepalive=false: disable keep-alive (tests connection establishment overhead)
echo 'GET https://api.construx.io/v1/health' | \
  vegeta attack -rate=100 -duration=10s -keepalive=false | vegeta report

# Latency with keepalive=false:
# min=8.2ms  mean=22.4ms  p99=84.1ms  (TLS+TCP setup on every request)
# vs keepalive=true:
# min=1.2ms  mean=18.4ms  p99=42.3ms
```

vegeta vs wrk vs k6: wrk uses a concurrency model — N threads × M connections, pushing as fast as possible. This measures max throughput but doesn't model a real traffic pattern. vegeta attacks at a constant rate, which is what actually happens in production (users don't wait for the previous request to finish). k6 is the most feature-rich: JavaScript scripting, checks, thresholds, scenarios, and cloud execution — but heavier to set up. The practical split: use vegeta for a quick rate vs p99 characterisation, wrk to find raw throughput ceiling, and k6 for full scenario testing with business logic checks. vegeta's binary encoding is its killer feature — tee to disk during an incident, then replay and analyse later without touching the service again.
