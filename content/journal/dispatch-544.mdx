Postgres creates a new process for every connection. Each process costs memory — typically 5-10MB — and the connection setup itself takes time. At scale, connection count becomes a resource problem. PgBouncer solves it by acting as a proxy that holds the real Postgres connections and shares them across application requests.

## Why connection count matters

A typical Next.js application running on a serverless host (Vercel, Railway, Fly) can spin up dozens of instances simultaneously, each with their own database connection pool. 100 instances × 10 connections per pool = 1,000 Postgres connections. Postgres's default `max_connections` is 100. That's a problem.

```
Without PgBouncer:
App instances → [each makes direct connections] → Postgres
100 instances × 10 conns = 1,000 connections → Postgres crashes

With PgBouncer:
App instances → PgBouncer (maintains 20-50 real connections) → Postgres
1,000 app connections → 20 Postgres connections → no problem
```

## PgBouncer pooling modes

PgBouncer has three modes with different trade-offs:

**Transaction pooling** (recommended for most apps): A Postgres connection is held only during a transaction. As soon as the transaction commits or rolls back, the connection returns to the pool. This gives the highest connection multiplexing.

**Session pooling**: A Postgres connection is assigned for the lifetime of the client session. Least efficient but required if you use session-level features like `SET` variables, advisory locks, or prepared statements that span transactions.

**Statement pooling**: A Postgres connection is held only for a single statement. Doesn't work with transactions that span multiple statements. Too restrictive for most apps.

Most apps should use transaction pooling. The limitation: you cannot use session-level features, which means no `SET LOCAL app.tenant_id = $1` for row-level security. For that, use session mode or pass tenant context in each query.

## PgBouncer configuration

```ini
# pgbouncer.ini
[databases]
construxdb = host=postgres port=5432 dbname=construxdb

[pgbouncer]
listen_port          = 6432
listen_addr          = *
auth_type            = scram-sha-256
auth_file            = /etc/pgbouncer/userlist.txt
pool_mode            = transaction
max_client_conn      = 1000
default_pool_size    = 25
min_pool_size        = 5
reserve_pool_size    = 5
reserve_pool_timeout = 3
server_idle_timeout  = 600
client_idle_timeout  = 0
log_connections      = 0
log_disconnections   = 0
```

```
# /etc/pgbouncer/userlist.txt
"construx_user" "scram-sha-256$..."
```

Application connects to port 6432 (PgBouncer) instead of 5432 (Postgres directly).

## Built-in pooling in Drizzle and Postgres.js

If you're using Drizzle with `postgres-js` or `node-postgres`, both have built-in connection pools. These reduce connections per application instance but don't help when you have many application instances.

```ts
// lib/db.ts — postgres-js pool
import postgres from 'postgres';

const sql = postgres(process.env.DATABASE_URL!, {
  max:       10,    // max connections per instance
  idle_timeout: 20, // close idle connections after 20s
  connect_timeout: 10,
});
```

For serverless deployments, built-in pooling is often insufficient because each function invocation may spin up a new instance with its own pool. PgBouncer handles this at the infrastructure level.

## Neon and Supabase connection pooling

Managed Postgres providers handle this for you:

**Neon** provides a serverless driver with connection pooling built in via their HTTP proxy:

```ts
import { neon } from '@neondatabase/serverless';
const sql = neon(process.env.DATABASE_URL!);
```

Each query is a stateless HTTP request — no persistent connections, no pool management.

**Supabase** runs PgBouncer in front of Postgres for all projects. You connect to the pooler URL (port 6543) instead of Postgres directly (port 5432).

## Monitoring connection count

Watch connection count in production before it becomes a problem:

```sql
-- Current connections by state
SELECT state, count(*)
FROM pg_stat_activity
WHERE datname = 'construxdb'
GROUP BY state;

-- Connections per application
SELECT application_name, count(*)
FROM pg_stat_activity
WHERE datname = 'construxdb'
GROUP BY application_name
ORDER BY count DESC;
```

In Prometheus:

```promql
# Alert if connections exceed 80% of max_connections
pg_stat_activity_count > (pg_settings_max_connections * 0.8)
```

## Our setup

Scoutr runs PgBouncer in transaction mode in front of Postgres. The Next.js API connects to PgBouncer's port. The worker processes (which use background jobs and need session-level `SET` for multi-tenancy) connect directly to Postgres, bypassing the pooler.

For row-level security with PgBouncer in transaction mode, we pass the tenant ID at the query level rather than using `SET LOCAL`:

```ts
// Instead of SET LOCAL, embed tenant context in the query
const result = await db.execute(
  sql`SELECT set_config('app.tenant_id', ${tenantId}, true), * FROM posts`
);
```

`set_config` with `is_local = true` scopes to the current transaction, which works in transaction pooling mode.
