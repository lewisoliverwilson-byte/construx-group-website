date: "2034-04-05"
excerpt: "Apache Airflow is the dominant workflow orchestration platform for data pipelines. A DAG (Directed Acyclic Graph) defines a pipeline as a set of tasks with dependency relationships — extract data from the source, validate schema, transform, load to the warehouse, notify. Airflow schedules DAG runs on cron expressions, triggers them on events, or runs them on demand. The executor model determines how tasks run: the CeleryExecutor distributes tasks to a pool of worker pods via Redis or RabbitMQ, enabling parallel execution across hundreds of concurrent tasks; the KubernetesExecutor creates a fresh pod for each task and terminates it when done — better isolation but slower startup. Sensors block execution until a condition is met: S3KeySensor waits for a file to appear; TimeSensor waits until a specific time; ExternalTaskSensor waits for a task in another DAG to complete. XCom (cross-communication) passes small data between tasks — the transform task pushes a row count XCom; the validation task reads it and fails the run if it's below threshold. Dynamic task mapping (Airflow 2.3+) creates task instances at runtime based on upstream data — instead of hardcoding 50 parallel extract tasks, the DAG maps over a list of table names returned by an upstream task, creating one extract task per table dynamically. Airflow 2.x introduced TaskFlow API (Python decorators) for cleaner DAG definition, replacing the verbose operator instantiation pattern."

# dags/etl_orders_daily.py
# Daily order ETL: extract from source DB, validate, transform, load to warehouse
# Uses TaskFlow API (Python decorators) and dynamic task mapping

from __future__ import annotations

import pendulum
from airflow.decorators import dag, task
from airflow.providers.postgres.hooks.postgres import PostgresHook
from airflow.providers.amazon.aws.hooks.s3 import S3Hook
from airflow.sensors.s3_key_sensor import S3KeySensor
import pandas as pd


@dag(
    dag_id="etl_orders_daily",
    schedule="0 2 * * *",          # Run at 02:00 UTC daily
    start_date=pendulum.datetime(2034, 1, 1, tz="UTC"),
    catchup=False,
    tags=["etl", "orders", "warehouse"],
    default_args={
        "retries": 3,
        "retry_delay": pendulum.duration(minutes=5),
        "owner": "data-platform",
    },
    max_active_runs=1,              # don't run concurrent instances
    doc_md="""
    Daily order ETL pipeline.
    Extracts orders from PostgreSQL, validates schema, transforms, and loads to ClickHouse.
    """,
)
def etl_orders_daily():

    @task()
    def extract_orders(logical_date=None) -> dict:
        """Extract orders for the logical date from PostgreSQL."""
        hook = PostgresHook(postgres_conn_id="construx_prod_postgres")
        df = hook.get_pandas_df(
            sql="""
                SELECT order_id, tenant_id, status, total_pence, created_at, line_items
                FROM orders
                WHERE DATE(created_at) = %(date)s
                  AND deleted_at IS NULL
            """,
            parameters={"date": str(logical_date.date())},
        )
        # Push to XCom (max 48KB — use S3 for large data)
        return {"row_count": len(df), "date": str(logical_date.date())}

    @task()
    def validate_schema(extract_result: dict) -> dict:
        """Validate row count and schema invariants."""
        row_count = extract_result["row_count"]
        if row_count < 100:
            raise ValueError(f"Suspiciously low row count: {row_count} (expected > 100)")
        return {"validated": True, "row_count": row_count}

    @task.branch()
    def route_by_volume(validation_result: dict) -> str:
        """Route to full transform or lightweight transform based on row count."""
        if validation_result["row_count"] > 100_000:
            return "transform_large"
        return "transform_standard"

    @task()
    def transform_standard(validation_result: dict) -> str:
        """Transform: single-pass SQL transform for standard daily volumes."""
        # In practice: run dbt model or SQL transform
        return "transform_complete"

    @task()
    def transform_large(validation_result: dict) -> str:
        """Transform: chunked transform for large volumes (Spark job via SparkSubmitOperator)."""
        return "transform_complete"

    @task(trigger_rule="none_failed_min_one_success")
    def load_warehouse(transform_status: list[str]) -> None:
        """Load transformed data to ClickHouse warehouse."""
        # Insert from S3 staging area into ClickHouse
        pass

    @task()
    def notify_success(row_count: int) -> None:
        """Post completion metrics to Prometheus pushgateway."""
        import requests
        requests.post(
            "http://pushgateway.construx-monitoring.svc.cluster.local:9091/metrics/job/airflow_etl",
            data=f'etl_orders_rows_loaded{{dag="etl_orders_daily"}} {row_count}\n',
        )

    # Wire the DAG

    validation_result  = validate_schema(extract_result)

# dags/ml_feature_pipeline.py
# Dynamic task mapping: create one feature extraction task per table
# Uses Airflow 2.3+ dynamic task mapping

from airflow.decorators import dag, task
import pendulum


@dag(
    dag_id="ml_feature_pipeline",
    schedule="0 */6 * * *",    # every 6 hours
    start_date=pendulum.datetime(2034, 1, 1, tz="UTC"),
    catchup=False,
    tags=["ml", "features"],
)
def ml_feature_pipeline():

    @task()
    def get_feature_tables() -> list[dict]:
        """Return list of tables that need feature extraction."""
        return [
            {"table": "orders",   "feature_set": "order_features"},
            {"table": "sessions", "feature_set": "session_features"},
            {"table": "products", "feature_set": "product_features"},
            {"table": "users",    "feature_set": "user_features"},
        ]

    @task()
    def extract_features(table_config: dict) -> dict:
        """Extract features for one table — runs in parallel for all tables."""
        table   = table_config["table"]
        feature = table_config["feature_set"]
        # Run feature extraction SQL, write result to feature store (Redis or S3)
        print(f"Extracting features from {table} → {feature}")
        return {"feature_set": feature, "rows": 142000}

    @task()
    def publish_to_feature_store(feature_results: list[dict]) -> None:
        """Publish all feature sets to the online feature store."""
        for result in feature_results:
            print(f"Publishing {result['feature_set']}: {result['rows']} rows")

    # Dynamic mapping: creates 4 parallel extract_features task instances
    tables   = get_feature_tables()
    features = extract_features.expand(table_config=tables)
    publish_to_feature_store(features)

ml_feature_pipeline()

Airflow vs Prefect vs Dagster vs Temporal vs Argo Workflows: Prefect and Dagster are the modern Python-first alternatives to Airflow — they have cleaner APIs, better local development experience, and native cloud deployments. Prefect's flows run anywhere Python runs, with a hosted orchestration layer (Prefect Cloud) or self-hosted server. Dagster's asset-oriented model (define data assets and their dependencies, not just tasks) is conceptually more correct for data engineering and gives better observability into what data was produced by which pipeline run. Temporal (dispatch-1108) is a durable workflow engine for long-running business processes — not designed for data pipeline scheduling. Argo Workflows is Kubernetes-native and better for containerised steps that don't need Python — each task is a container, with no shared Python runtime. Airflow's advantage is its 10+ years of community maturity: 1500+ operators, integrations for every cloud service and data platform, and an enormous user base that means answers to operational questions are easy to find. Its weaknesses are well-known: the scheduler bottleneck at scale (being addressed with the DAGS_IN_AIRFLOW_DB model), poor local development (running a full Airflow stack locally is heavy), and the complexity of managing connections and variables. For data teams that have grown into Airflow and invested in its operator ecosystem, migration is expensive. For new projects, Prefect or Dagster often provide a better developer experience with comparable production capabilities.
