`strict: true` in your `tsconfig.json` enables eight flags at once. Most TypeScript projects enable it and stop there. But there are additional flags outside the strict bundle worth knowing about — and understanding what each flag catches changes how you write code.

## The strict bundle

```json
{
  "compilerOptions": {
    "strict": true,
    // This enables all of the following:
    // "noImplicitAny": true
    // "noImplicitThis": true
    // "strictNullChecks": true
    // "strictFunctionTypes": true
    // "strictBindCallApply": true
    // "strictPropertyInitialization": true
    // "alwaysStrict": true
    // "useUnknownInCatchVariables": true
  }
}
```

## The flags that matter most

### `strictNullChecks`

The highest-impact flag. Without it, `null` and `undefined` are assignable to every type:

```ts
// Without strictNullChecks — no error
const user: User = null;
user.name;  // Runtime crash

// With strictNullChecks — caught at compile time
const user: User | null = null;
user.name;  // Error: Object is possibly 'null'
user?.name; // OK
```

### `noImplicitAny`

Forces you to annotate anything TypeScript can't infer:

```ts
// Error: Parameter 'data' implicitly has an 'any' type
function process(data) { return data.id; }

// Fix
function process(data: { id: string }) { return data.id; }
```

### `useUnknownInCatchVariables`

`catch` clause variables default to `unknown` instead of `any`:

```ts
try {
  await fetchData();
} catch (error) {
  // error is unknown — not any
  if (error instanceof Error) {
    console.error(error.message);
  } else {
    console.error(String(error));
  }
}
```

### `strictPropertyInitialization`

Class properties must be initialised in the constructor:

```ts
class User {
  name: string;      // Error: not initialised
  name: string = ''; // OK
  name!: string;     // OK — definite assignment assertion (use sparingly)
}
```

## Additional flags worth enabling

```json
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noImplicitOverride": true,
    "noPropertyAccessFromIndexSignature": true
  }
}
```

### `noUncheckedIndexedAccess`

Array indexing returns `T | undefined`, not `T`:

```ts
const items = ['a', 'b', 'c'];

// Without noUncheckedIndexedAccess
const first: string = items[0];  // Type is string — could be undefined

// With noUncheckedIndexedAccess
const first: string | undefined = items[0];  // Correct
if (first) console.log(first.toUpperCase());  // Must narrow
```

This forces you to handle the "empty array" case. Tedious at first, catches real bugs.

### `exactOptionalPropertyTypes`

Prevents assigning `undefined` to optional properties:

```ts
interface Config {
  timeout?: number;  // timeout can be absent, but not explicitly undefined
}

// Without exactOptionalPropertyTypes — fine
const config: Config = { timeout: undefined };

// With exactOptionalPropertyTypes — error
const config: Config = { timeout: undefined };  // Error
const config: Config = {};  // OK — timeout is absent
```

### `noImplicitOverride`

Methods that override base class methods must be marked `override`:

```ts
class Animal {
  speak(): string { return 'generic sound'; }
}

class Dog extends Animal {
  speak(): string { return 'woof'; }  // Error: missing 'override' keyword

  override speak(): string { return 'woof'; }  // OK
}
```

Catches typos in method names: if you write `speek()`, TypeScript tells you there's no method to override.

```json
{
  "compilerOptions": {
    "target": "ES2017",
    "lib": ["dom", "dom.iterable", "esnext"],

    "exactOptionalPropertyTypes": true,

    "moduleResolution": "bundler",
    "resolveJsonModule": true,
    "isolatedModules": true,

    "paths": {
      "@/*": ["./src/*"]
```

`noUnusedLocals` and `noUnusedParameters` are outside the strict bundle but catch dead code that's worth removing.

## The patterns strict mode forces

**Nullish coalescing over OR for defaults:**
```ts
// Bad — `0` and `''` are falsy
const name = user.name || 'Anonymous';

// Good — only catches null/undefined
const name = user.name ?? 'Anonymous';
```

**Optional chaining over explicit null checks:**
```ts
// Verbose
if (user && user.profile && user.profile.avatar) { ... }

// Better
if (user?.profile?.avatar) { ... }
```

**Discriminated unions over nullable types:**
```ts
// Avoid
type State = { loading: boolean; data: User | null; error: string | null };

// Better — states are mutually exclusive
type State =
  | { status: 'loading' }
  | { status: 'success'; data: User }
  | { status: 'error'; error: string };
```

The discriminated union makes the `status` field the discriminant — TypeScript narrows the type correctly in switch statements.

**Type narrowing over assertions:**
```ts
// Avoid
const user = getUser() as User;  // Bypasses the type checker

// Better
const raw = getUser();
if (raw === null) throw new Error('User not found');
const user: User = raw;  // TypeScript knows this is User

// Or
const user = getUser();
if (!user) { return null; }
// TypeScript now knows user is User below this point
```

Type assertions (`as`) are a code smell in application code. They exist for library boundary cases. Inside your app, narrow instead of assert.
