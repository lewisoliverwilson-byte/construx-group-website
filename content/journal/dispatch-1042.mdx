title: "Pyroscope: continuous profiling — always-on CPU and memory flame graphs in production"
date: "2033-07-06"
excerpt: "Pyroscope is a continuous profiling database that ingests CPU, memory, goroutine, and mutex profiles from running applications and stores them in a time-series format. Unlike ad-hoc profiling (go tool pprof, async-profiler), Pyroscope runs permanently in production — a lightweight agent or SDK samples the call stack every 10ms and pushes profiles to the Pyroscope server. Because profiles are time-indexed, you can correlate a CPU spike at 14:32 with a specific flame graph showing which function consumed the CPU during that window. Pyroscope integrates with Grafana: profiles appear as a data source alongside metrics (Prometheus) and traces (Tempo), so you can navigate from a slow trace span directly to the flame graph of the function that caused it. The storage backend is Parquet over object storage (S3/GCS), making it cheap to retain months of continuous profiling data."

Always-on sampling. Flame graphs. Time-indexed profiles. Grafana integration. Parquet storage.

## Go SDK instrumentation

```go
// Go: Pyroscope SDK — attach to a running Go service
// main.go

package main

import (
    "context"
    "log"
    "net/http"
    "os"

    "github.com/grafana/pyroscope-go"
)

func main() {
    // Start Pyroscope profiler
    profiler, err := pyroscope.Start(pyroscope.Config{
        ApplicationName: "construx.payments-api",
        ServerAddress:   "http://pyroscope.monitoring.svc.cluster.local:4040",
        Logger:          pyroscope.StandardLogger,
        Tags: map[string]string{
            "env":     os.Getenv("ENVIRONMENT"),    // "prod", "staging"
            "region":  os.Getenv("AWS_REGION"),
            "version": os.Getenv("APP_VERSION"),
        },
        ProfileTypes: []pyroscope.ProfileType{
            pyroscope.ProfileCPU,
            pyroscope.ProfileAllocObjects,
            pyroscope.ProfileAllocSpace,
            pyroscope.ProfileInuseObjects,
            pyroscope.ProfileInuseSpace,
            pyroscope.ProfileGoroutines,
            pyroscope.ProfileMutexCount,
            pyroscope.ProfileMutexDuration,
            pyroscope.ProfileBlockCount,
            pyroscope.ProfileBlockDuration,
        },
    })
    if err != nil {
        log.Fatalf("pyroscope.Start: %v", err)
    }
    defer profiler.Stop()

    http.ListenAndServe(":8080", newRouter())
}

// Tag a specific code block — profile segment shows up separately in Pyroscope
func processPayment(ctx context.Context, payment Payment) error {
    pyroscope.TagWrapper(ctx, pyroscope.Labels("handler", "processPayment"), func(c context.Context) {
        // Expensive work here — will show as a separate segment in the flame graph
        result, err := db.Exec(c, insertPaymentSQL, payment.ID, payment.Amount)
        if err != nil {
            return
        }
        notifyWebhook(c, payment)
    })
}
```

## Kubernetes deployment

```yaml
# Pyroscope server: Helm chart
# values.yaml

pyroscope:
  replicaCount: 2
  storage:
    backend: s3
    s3:
      bucket: construx-pyroscope-prod
      region: eu-west-2
      endpoint: ""   # AWS S3 default
  serviceMonitor:
    enabled: true   # Prometheus scrape of Pyroscope's own metrics

# Grafana data source: add Pyroscope as a profile source
grafana:
  additionalDataSources:
    - name: Pyroscope
      type: grafana-pyroscope-datasource
      url: http://pyroscope.monitoring.svc.cluster.local:4040
      jsonData:
        keepCookies: []
---
# Ebpf-based auto-instrumentation: no SDK needed — profiles any process
# Pyroscope eBPF agent (runs as DaemonSet, profiles all pods automatically)
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: pyroscope-ebpf-agent
  namespace: monitoring
spec:
  selector:
    matchLabels:
      app: pyroscope-ebpf-agent
  template:
    spec:
      hostPID: true
      containers:
        - name: agent
          image: grafana/pyroscope-ebpf:v0.4.0
          securityContext:
            privileged: true   # required for eBPF
          env:
            - name: PYROSCOPE_SERVER_ADDRESS
              value: http://pyroscope.monitoring.svc.cluster.local:4040
          volumeMounts:
            - name: sys
              mountPath: /sys
              readOnly: true
      volumes:
        - name: sys
          hostPath:
            path: /sys
```

## Querying profiles from the CLI and API

```bash
# Query profiles via the Pyroscope HTTP API
# Find the top functions by CPU during a time window

curl -s "http://pyroscope.monitoring.svc.cluster.local:4040/render?
  query=construx.payments-api:cpu:nanoseconds:cpu:nanoseconds%7Benv%3D%22prod%22%7D
  &from=now-1h&until=now&format=json" | jq '.flamebearer.names[:10]'

# [
#   "total",
#   "github.com/construx/payments-api/db.(*Pool).ExecContext",
#   "database/sql.(*DB).ExecContext",
#   "github.com/jackc/pgx/v5.(*Conn).Exec",
#   "net/http.(*conn).serve",
#   "github.com/construx/payments-api/handlers.ProcessPayment",
#   "runtime.gcBgMarkWorker",
#   "runtime.mallocgc",
#   "github.com/construx/payments-api/notify.(*WebhookSender).Send",
#   "encoding/json.Marshal"
# ]

# pprof-compatible export: download and analyse locally
curl "http://pyroscope.monitoring.svc.cluster.local:4040/pyroscope/render?
  query=construx.payments-api:cpu:nanoseconds:cpu:nanoseconds
  &from=1720000000&until=1720003600&format=pprof" \
  --output profile.pb.gz

go tool pprof -http=:6060 profile.pb.gz
# Opens interactive flame graph in browser

# Diff profiles: compare two time windows (before vs after a deploy)
curl -s "http://pyroscope.monitoring.svc.cluster.local:4040/render-diff?
  leftQuery=construx.payments-api:cpu:nanoseconds:cpu:nanoseconds%7Bversion%3D%22v2.2.0%22%7D
  &leftFrom=now-2h&leftUntil=now-1h
  &rightQuery=construx.payments-api:cpu:nanoseconds:cpu:nanoseconds%7Bversion%3D%22v2.3.0%22%7D
  &rightFrom=now-1h&rightUntil=now
  &format=json" | jq '.diff | sort_by(-.self) | .[:5]'
# Shows which functions got faster or slower between versions
```

Pyroscope vs pprof ad-hoc vs Datadog Continuous Profiler vs Elastic APM: Ad-hoc pprof captures a 30-second profile on demand — useful for investigating a known incident but blind to everything before you thought to run it. Datadog Continuous Profiler and Elastic APM both support continuous profiling but are priced per host per month, which adds up at scale. Pyroscope is open source (Apache 2.0) and self-hosted on object storage — the storage cost for months of profiling data is a few dollars of S3. The Grafana integration is the key operational win: in Grafana you can go from a Prometheus alert (p99 latency spiked) → a Tempo trace (slow span in processPayment) → a Pyroscope flame graph (db.ExecContext consuming 80% of CPU at that moment), all in one tool. This observability trifecta (metrics + traces + profiles) surfaces root causes that metrics and traces alone cannot reach.
