date: "2033-06-18"
excerpt: "Neon is a serverless PostgreSQL service that separates storage from compute. The Neon storage layer (Pageserver) stores PostgreSQL pages in object storage (S3) and maintains a WAL log for every branch. Compute nodes (Safekeeper + Postgres) are stateless — they read pages from Pageserver and write WAL. This separation enables the two headline features: database branching (copy-on-write branches from any historical point, like Git branches for databases, created instantly at any size) and scale-to-zero (compute shuts down after 5 minutes of inactivity and resumes on the next connection, typically in 500ms). Database branching is the feature teams use in CI: your CI pipeline creates a branch from the production database, runs migrations against the branch, runs tests, and the branch is automatically deleted. No shared database, no manual teardown, no state leakage between test runs."

Serverless PostgreSQL. Database branching. Copy-on-write. Scale to zero. WAL archive. CI preview.

## Creating branches and connecting

```bash
# Neon CLI: manage Neon projects and branches
npm install -g neonctl

# Login
neonctl auth

# Create a Neon project
neonctl projects create --name construx-prod --region eu-central-1

# List projects
neonctl projects list
# id                    name           region           created_at
# proud-hall-a1b2c3d4   construx-prod  eu-central-1    2033-06-18

# Get connection string for the main branch
neonctl connection-string --project-id proud-hall-a1b2c3d4 --branch main
# postgresql://construx:password@ep-gentle-meadow-a1b2c3d4.eu-central-1.aws.neon.tech/construx

# Create a branch from main (copy-on-write — instant regardless of database size)
neonctl branches create \
  --project-id proud-hall-a1b2c3d4 \
  --name feature/add-engagement-score \
  --parent main

# List branches
neonctl branches list --project-id proud-hall-a1b2c3d4
# id            name                           parent  created_at
# br-main-...   main                           —       2033-06-18 08:00
# br-feat-...   feature/add-engagement-score   main    2033-06-18 12:14

# Get connection string for the feature branch
neonctl connection-string \
  --project-id proud-hall-a1b2c3d4 \
  --branch feature/add-engagement-score
# postgresql://construx:password@ep-quiet-pond-b2c3d4e5.eu-central-1.aws.neon.tech/construx

# Run a migration on the branch (isolated — doesn't affect main)
DATABASE_URL="$(neonctl connection-string --project-id ... --branch feature/add-engagement-score)" \
  npx prisma migrate deploy

# Delete the branch when done (or let the CI cleanup script do it)
neonctl branches delete br-feat-... --project-id proud-hall-a1b2c3d4
```

## CI integration — branch per PR

```yaml
# GitHub Actions: create a Neon branch for each PR, run migrations and tests,
# delete the branch when the PR is merged or closed

name: pr-database-branch

on:
  pull_request:
    types: [opened, synchronize, reopened, closed]

jobs:
  create-branch:
    if: github.event.action != 'closed'
    runs-on: ubuntu-latest
    outputs:
      branch-id:   ${{ steps.create.outputs.branch_id }}
      db-url:      ${{ steps.url.outputs.url }}

    steps:
      - name: Install Neon CLI
        run: npm install -g neonctl

      - name: Create branch
        id: create
        env:
          NEON_API_KEY: ${{ secrets.NEON_API_KEY }}
        run: |
          BRANCH=$(neonctl branches create \
            --project-id ${{ vars.NEON_PROJECT_ID }} \
            --name "pr-${{ github.event.number }}" \
            --parent main \
            --output json)
          echo "branch_id=$(echo $BRANCH | jq -r '.id')" >> $GITHUB_OUTPUT

      - name: Get connection string
        id: url
        env:
          NEON_API_KEY: ${{ secrets.NEON_API_KEY }}
        run: |
          URL=$(neonctl connection-string \
            --project-id ${{ vars.NEON_PROJECT_ID }} \
            --branch pr-${{ github.event.number }})
          echo "url=$URL" >> $GITHUB_OUTPUT

      - uses: actions/checkout@v4

      - name: Run migrations on branch
        env:
          DATABASE_URL: ${{ steps.url.outputs.url }}
        run: npx prisma migrate deploy

      - name: Run tests against branch
        env:
          DATABASE_URL: ${{ steps.url.outputs.url }}
        run: npm test

  delete-branch:
    if: github.event.action == 'closed'
    runs-on: ubuntu-latest
    steps:
      - name: Delete Neon branch
        env:
          NEON_API_KEY: ${{ secrets.NEON_API_KEY }}
        run: |
          neonctl branches delete pr-${{ github.event.number }} \
            --project-id ${{ vars.NEON_PROJECT_ID }}
```

## Scale-to-zero and point-in-time restore

```bash
# Scale-to-zero: compute shuts down after inactivity timeout (default: 5 minutes)
# When the next connection arrives, compute restarts (typically 500ms)
# Storage (Pageserver) is always-on — pages are preserved

# Configure the autosuspend timeout
neonctl endpoints update ep-gentle-meadow-... \
  --project-id proud-hall-a1b2c3d4 \
  --autosuspend-delay 300   # 5 minutes

# Set to 0 to disable autosuspend (always-on compute)
neonctl endpoints update ep-gentle-meadow-... \
  --autosuspend-delay 0

# Point-in-time restore: create a branch from a historical timestamp
# Useful for recovering from accidental data deletion
neonctl branches create \
  --project-id proud-hall-a1b2c3d4 \
  --name recovery-2033-06-18-12-00 \
  --parent main \
  --point-in-time "2033-06-18T12:00:00Z"

# Connect to the restore branch and export the data
RECOVERY_URL="$(neonctl connection-string --branch recovery-2033-06-18-12-00 ...)"
psql "$RECOVERY_URL" -c "SELECT * FROM orders WHERE id = 'accidentally-deleted-id'" \
  | psql "$PRODUCTION_URL" -c "COPY orders FROM STDIN"
```

Neon vs PlanetScale vs Supabase vs self-hosted PostgreSQL: PlanetScale is MySQL (Vitess-backed) — different database, different compatibility constraints. Supabase wraps PostgreSQL with Auth, Storage, and Realtime — it's a development platform, not just a database. Self-hosted PostgreSQL on EC2 or EKS gives you full control but requires managing backups, replication, upgrades, and failover. Neon's specific advantages: database branching for CI (the killer feature), scale-to-zero for development and staging environments (cost savings), and instant provisioning. It's standard PostgreSQL at the query level — no vendor-specific SQL extensions for the branching (branching is infrastructure, not SQL). The cold start (500ms) is fine for batch workloads and CI but not for production-grade hot paths that need sub-100ms connection time. Neon's compute autoscaling (scale up CPU and memory on read spikes) is also notable for analytics workloads that have bursty query patterns.
