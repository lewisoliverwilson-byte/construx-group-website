title: "Grafana Loki: log aggregation without full-text indexing"
date: "2033-02-18"
excerpt: "Loki is Grafana's log aggregation system. Unlike Elasticsearch, which indexes every word in every log line, Loki indexes only the labels (structured key-value pairs like job=construx-api, namespace=construx-prod, level=error). The log lines themselves are stored compressed in object storage. The tradeoff: Loki uses a fraction of the disk and RAM that Elasticsearch needs, but full-text search requires scanning log chunks rather than hitting an index. For most use cases — 'show me all error logs from construx-api in the last hour' — the label-first approach is fast enough and dramatically cheaper. LogQL is Loki's query language: filter by label, then grep/parse the log lines. Promtail or the Grafana Agent ships logs from pods or VMs to Loki."
author: "Lewis Wilson"
tag: "Build Log"

Label-only indexing. Object storage backend. LogQL. Promtail. Chunk compression. Ruler alerts.

## Architecture and deployment

```bash
# Loki components:
# - Distributor:  receives log writes, validates, and shards to ingesters
# - Ingester:     holds recent logs in memory, flushes chunks to object store
# - Querier:      handles LogQL queries, reads from ingesters + object store
# - Ruler:        evaluates LogQL rules and fires alerts to Alertmanager
# - Compactor:    merges small chunks, applies retention deletions

# Install via Helm (Loki + Grafana Agent in monolithic mode for small clusters)
helm repo add grafana https://grafana.github.io/helm-charts
helm upgrade --install loki grafana/loki \
  --namespace monitoring \
  -f loki-values.yaml

cat > loki-values.yaml <<'EOF'
loki:
  auth_enabled: false  # single tenant mode
  commonConfig:
    replication_factor: 1  # set to 3 for production HA

  storage:
    type: s3
    s3:
      endpoint: s3.eu-west-1.amazonaws.com
      bucketnames: construx-loki-chunks
      region: eu-west-1
      s3ForcePathStyle: false

  schemaConfig:
    configs:
      - from: 2033-01-01
        store: tsdb
        object_store: s3
        schema: v13
        index:
          prefix: loki_index_
          period: 24h

  limits_config:
    retention_period: 90d      # log retention
    ingestion_rate_mb: 16      # per-tenant ingestion limit
    max_streams_per_user: 0    # 0 = unlimited

  rulerConfig:
    storage:
      type: local
      local:
        directory: /etc/loki/rules
    alertmanager_url: http://alertmanager.monitoring.svc:9093
EOF

# Install Grafana Agent as log shipper (replace Promtail)
helm upgrade --install grafana-agent grafana/grafana-agent \
  --namespace monitoring \
  -f agent-values.yaml
```

## Promtail: shipping logs from Kubernetes pods

```yaml
# Promtail: traditional log shipper (DaemonSet) for Loki
# Or use Grafana Agent (newer, handles metrics + logs + traces)

# promtail-config.yaml
server:
  http_listen_port: 9080

positions:
  filename: /tmp/positions.yaml

clients:
  - url: http://loki.monitoring.svc:3100/loki/api/v1/push

scrape_configs:
  # Kubernetes pod logs — auto-discover via Kubernetes API
  - job_name: kubernetes-pods
    kubernetes_sd_configs:
      - role: pod

    pipeline_stages:
      # Extract level from JSON logs: {"level":"error","msg":"..."} 
      - json:
          expressions:
            level: level
            msg:   msg

      # Add the extracted level as a label (enables fast filtering by level)
      - labels:
          level:

      # Drop debug logs in production (reduces volume)
      - match:
          selector: '{namespace="construx-prod",level="debug"}'
          action: drop

      # Parse duration from log lines: "request completed in 142ms"
      - regex:
          expression: 'in (?P<duration>[0-9]+)ms'
      - metrics:
          duration_ms:
            type: Histogram
            description: "Request duration from logs"
            source: duration
            config:
              buckets: [10, 50, 100, 500, 1000, 5000]

    relabel_configs:
      - source_labels: [__meta_kubernetes_namespace]
        target_label: namespace
      - source_labels: [__meta_kubernetes_pod_name]
        target_label: pod
      - source_labels: [__meta_kubernetes_container_name]
        target_label: container
      - source_labels: [__meta_kubernetes_pod_label_app]
        target_label: app
```

## LogQL: querying logs

```bash
# LogQL: Loki's query language — two phases:
# 1. Log stream selector (label filters, fast — hits the index)
# 2. Pipeline (log filters, grep, parsing, metrics — scans chunks)

# Basic query: all logs from construx-api in namespace construx-prod
{namespace="construx-prod", app="construx-api"}

# Filter by level label (fast — uses index)
{namespace="construx-prod", app="construx-api", level="error"}

# Grep within the log lines (slower — scans chunks)
{namespace="construx-prod"} |= "timeout"

# Regex filter
{namespace="construx-prod"} |~ "error|fatal|panic"

# Exclude pattern
{namespace="construx-prod"} != "healthz"

# Parse JSON logs and filter on a field
{namespace="construx-prod", app="construx-api"}
  | json
  | status_code >= 500

# Parse structured log line with logfmt
{namespace="construx-prod", app="construx-api"}
  | logfmt
  | method="POST"
  | duration > 1000

# Pattern parser for unstructured logs
{namespace="construx-prod"}
  | pattern `<ip> - - [<timestamp>] "<method> <path> HTTP/<version>" <status> <size>`
  | status >= 500
  | line_format "{{.ip}} → {{.path}} ({{.status}})"

# Log volume over time (metric query from logs)
rate({namespace="construx-prod", app="construx-api", level="error"}[5m])
# Returns errors per second as a time series — use in Grafana

# Top-N: which pods are producing the most errors?
topk(5, sum by (pod) (
  rate({namespace="construx-prod", level="error"}[5m])
))

# Latency from logs: p99 of a parsed duration field
quantile_over_time(0.99,
  {namespace="construx-prod", app="construx-api"}
    | json
    | unwrap duration_ms [5m]
)
```

## Loki Ruler: log-based alerting

```yaml
# Alert when error rate from logs exceeds a threshold
# Complements Prometheus alerts — catches errors that don't surface in metrics

# /etc/loki/rules/construx-prod.yaml
groups:
  - name: construx-api-log-alerts
    interval: 1m
    rules:
      - alert: HighErrorRateFromLogs
        expr: |
          sum(rate({namespace="construx-prod", app="construx-api", level="error"}[5m])) > 5
        for: 2m
        labels:
          severity: critical
          source: logs
        annotations:
          summary: "construx-api error rate {{ $value | humanize }} errors/s from logs"
          runbook: "https://construx.internal/runbooks/api-errors"

      - alert: PanicDetected
        expr: |
          count_over_time({namespace="construx-prod"} |= "panic" [5m]) > 0
        for: 0m   # fire immediately on any panic log line
        labels:
          severity: page
        annotations:
          summary: "Panic detected in {{ $labels.namespace }}"

      - alert: SlowRequests
        expr: |
          quantile_over_time(0.99,
            {namespace="construx-prod", app="construx-api"}
              | json
              | unwrap duration_ms [5m]
          ) > 1000
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "p99 latency {{ $value | humanizeDuration }} from log parsing"

  - name: construx-audit-alerts
    interval: 5m
    rules:
      - alert: SuspiciousAdminAccess
        expr: |
          count_over_time(
            {namespace="construx-prod"}
              |= "/api/admin"
              | logfmt
              | status < 400    # successful admin access
            [10m]
          ) > 10
        for: 0m
        labels:
          severity: warning
          team: security
```

Loki vs Elasticsearch vs ClickHouse: Elasticsearch indexes every token in every log line — queries are fast for any search pattern but storage is expensive (5-10x the raw log volume). ClickHouse is a columnar analytical database that works well for logs when you structure them as rows with typed columns — query performance is excellent for analytical queries (GROUP BY, aggregations) but setup is more complex. Loki's bet is that most log use cases are label-first: you almost always start with "show me logs from service X in namespace Y" before grepping the content. The label index handles that part cheaply, and chunk scanning handles the rest. For teams already using Grafana, the LGTM (Loki, Grafana, Tempo, Mimir/Prometheus) stack integrates tightly — you can jump from a Loki error log to the corresponding Tempo trace via trace ID correlation with no separate tooling.
