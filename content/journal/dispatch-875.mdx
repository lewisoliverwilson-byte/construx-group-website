Scan the image. Know every package. Block on critical CVEs.

## trivy image — scan a container image

```bash
# Scan a local image
trivy image construx-api:2.4.1

# Scan and fail CI if any critical/high CVEs are found
trivy image --exit-code 1 --severity CRITICAL,HIGH construx-api:2.4.1

# Output:
# construx-api:2.4.1 (ubuntu 24.04)
# ================================
# Total: 5 (CRITICAL: 1, HIGH: 2, MEDIUM: 1, LOW: 1)
#
# ┌──────────────┬────────────────┬──────────┬──────────────┬──────────┬─────────────────────────────────────────┐
# │   Library    │  Vulnerability │ Severity │   Status     │ Fix Ver  │                 Title                   │
# ├──────────────┼────────────────┼──────────┼──────────────┼──────────┼─────────────────────────────────────────┤
# │ xz-utils     │ CVE-2024-3094  │ CRITICAL │ fixed        │ 5.4.6    │ Backdoor in liblzma supply chain        │
# │ git          │ CVE-2024-32002 │ HIGH     │ fixed        │ 2.43.4   │ Arbitrary code exec via recursive clone │
# │ bind9        │ CVE-2023-50387 │ HIGH     │ fixed        │ 9.18.24  │ KeyTrap DNSSEC denial of service        │
# └──────────────┴────────────────┴──────────┴──────────────┴──────────┴─────────────────────────────────────────┘

# JSON output for automation
trivy image --format json --output results.json construx-api:2.4.1

# Filter: only show fixable vulnerabilities
trivy image --ignore-unfixed construx-api:2.4.1
```

## SBOM generation — software bill of materials

```bash
# Generate SBOM in CycloneDX format (machine-readable, used by compliance tools)
trivy image --format cyclonedx --output sbom.cdx.json construx-api:2.4.1

# SBOM in SPDX format (Linux Foundation standard)
trivy image --format spdx-json --output sbom.spdx.json construx-api:2.4.1

# Scan an existing SBOM for vulnerabilities (offline scan)
trivy sbom sbom.cdx.json

# Attest the SBOM to the image (sigstore/cosign)
cosign attest --predicate sbom.cdx.json \
  --type cyclonedx \
  construx-api:2.4.1
# The SBOM is now cryptographically attached to the image in the registry
# Verifiers can: cosign verify-attestation --type cyclonedx construx-api:2.4.1
```

## Trivy in CI — GitHub Actions gate

```yaml
# .github/workflows/security.yml
name: Security scan

on:
  push:
    branches: [master]
  pull_request:

jobs:
  trivy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Build image
        run: docker build -t construx-api:${{ github.sha }} .

      - name: Trivy vulnerability scan
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: construx-api:${{ github.sha }}
          format: sarif
          output: trivy-results.sarif
          exit-code: '1'
          severity: 'CRITICAL,HIGH'
          ignore-unfixed: true

      - name: Upload SARIF to GitHub Security tab
        uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: trivy-results.sarif
        if: always()    # Upload even if the scan found issues

      - name: Generate SBOM
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: construx-api:${{ github.sha }}
          format: cyclonedx
          output: sbom.cdx.json

      - name: Upload SBOM as artifact
        uses: actions/upload-artifact@v4
        with:
          name: sbom
          path: sbom.cdx.json
```

## Trivy scan beyond images — filesystems and IaC

```bash
# Scan a local filesystem (e.g., before building the image)
trivy fs --scanners vuln,secret,misconfig .

# Detect hardcoded secrets (AWS keys, API tokens, private keys)
trivy fs --scanners secret .
# [HIGH] AWS access key found in src/config.ts:14
# [CRITICAL] Private key found in certs/dev.key

# Scan Terraform configs for misconfigurations
trivy config ./infra/
# [HIGH] Security group allows unrestricted SSH (0.0.0.0/0) on port 22
# [MEDIUM] S3 bucket versioning not enabled

# Scan a running Kubernetes cluster
trivy k8s --report summary cluster
# Namespace: production
# CRITICAL: 2 (Pod with hostNetwork=true, Container running as root)
# HIGH:     5 (Missing resource limits, privileged containers)
```

The SBOM matters as much as the scan. A CVE database is only as good as its last update — a new vulnerability (like xz-utils CVE-2024-3094) may not be in the database when you build your image. If you have an SBOM and attach it to every image in the registry, you can re-scan all historical images the moment a new CVE is published. Without the SBOM, you'd need to rebuild every image to scan it. With the SBOM, you scan in minutes.
