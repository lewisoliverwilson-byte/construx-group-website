We ship daily. Not as a goal or a principle, but as a natural output of the way we work. Here's what makes it possible.

## The mechanics

Each product deploys through a standard pipeline:

1. Push to `master` branch
2. Amplify detects the push, triggers a build
3. Build: `npm ci && npm run build`
4. TypeScript compilation as part of the build (any type error fails the build)
5. Linting (ESLint) — warnings don't block, errors block
6. If build passes: deploy to production

There's no staging environment for the website (this site, the journal). There is a staging environment for each product (Scoutr, The Marqet, The Hyve) that mirrors production. Changes that affect backend logic or database schema go through staging first; frontend changes go direct.

## Why this doesn't feel reckless

**The unit of deployment is small.** A daily deploy typically contains 2-5 hours of work. Small units of change are easy to reason about and easy to roll back.

**TypeScript and ESLint catch errors before they reach production.** The combination of strict TypeScript and ESLint reduces the class of errors that make it to production to: logic errors, edge cases, and external dependency failures. Runtime type errors, common null reference issues, and structural problems are caught at build time.

**Rollback is fast.** Amplify keeps the last 10 builds. A rollback to the previous version takes 90 seconds — select the previous build, redeploy. This makes shipping feel safe: the blast radius of a bad deploy is limited by the speed of rollback.

**We don't ship after 16:00.** Unwritten rule. Late deploys create late incidents. The edge of the working day is the wrong time to introduce change.

## The pre-deploy mental checklist

Before pushing to master, we run through:

**What does this change?** Name the specific thing being changed. If you can't name it, you're not confident enough to ship it.

**What could break?** For every change, identify the failure mode. A new query could be slow. A new component could have layout issues on mobile. A new API route could fail on edge inputs.

**Have you tested it locally?** The embarrassingly basic step that gets skipped when you're in a hurry.

**Does this touch a database migration?** If yes, use staging first. Migrations are the highest-risk class of change.

**Is this reversible?** Adding is reversible (remove it). Deleting is irreversible (if you delete data, it's gone). Changes that remove data or schema require more caution than changes that add.

This checklist isn't a written document — it's the habit of thinking before pushing. The habit becomes automatic.

## Feature flags vs. shipping dark

We don't have a feature flag system. The cost of maintaining feature flags (the cognitive overhead, the cleanup debt, the testing surface area) isn't worth the benefit at our scale.

Instead, we ship dark: incomplete features are deployed but not exposed to users. A new journal component deployed in a comment, a new API route that isn't yet linked from the UI, a new database column with no migration side effects.

The "ship dark" approach works when: (1) the hidden code doesn't affect performance, and (2) you have a plan for when to unhide it. It doesn't work for large features with complex dependencies.

## Database migrations in a daily ship culture

Migrations are the exception to daily shipping. We're conservative:

**Additive migrations (new column, new table):** Safe to ship any time. Additive changes don't break existing functionality.

**Destructive migrations (drop column, drop table, column type change):** Multi-step process: (1) deploy code that stops using the column, (2) wait for confirmation that no code references it, (3) drop the column. Never in a single deploy.

**Backfills (populate an existing column with data):** Run during low-traffic periods. A backfill that locks rows for 30 seconds during a peak-traffic period is an incident.

We use Drizzle's migration system. Every migration is a SQL file that gets committed to the repo and applied in order. The migration state is tracked in a `drizzle_migrations` table.

## The culture part

Shipping culture isn't primarily about tools or process — it's about the relationship with production. Treating production as something you approach carefully and rarely produces a culture of infrequent, large, risky deployments. Treating production as the natural endpoint of your work produces a culture of small, frequent, routine deployments.

The teams that ship daily aren't the ones with the most sophisticated tooling. They're the ones who've made shipping feel normal.

The tools help. The process helps. But the thing that matters most is the disposition: production is where your work lives, and getting there quickly and routinely is the goal. Everything else is in service of that.
