Feature flags solve a real problem: the ability to ship code to production without immediately exposing it to all users. The standard answer is a platform like LaunchDarkly or Growthbook — powerful, fully-featured, and $hundreds/month for anything beyond the free tier.

For a two-person team shipping to a user base that's still growing, a simpler approach makes more sense. Here's ours.

## What we actually need

The use cases that justify feature flags at our stage:

1. **Kill switches:** Turn off a feature that's causing issues without a deployment
2. **Gradual rollouts:** Enable a feature for 10% of users, then 50%, then 100%
3. **Internal-only flags:** Enable a feature only for our own accounts to test in production
4. **A/B experiments:** Show variant A to half the users, variant B to the other half

We don't need: real-time flag evaluation (100ms update propagation), complex targeting rules by country/device/custom attributes, integrated analytics, or multi-environment syncing. Not yet.

## The implementation

A single database table:

```sql
CREATE TABLE feature_flags (
  key         TEXT PRIMARY KEY,
  enabled     BOOLEAN NOT NULL DEFAULT false,
  rollout_pct INTEGER NOT NULL DEFAULT 0  CHECK (rollout_pct BETWEEN 0 AND 100),
  user_ids    TEXT[] NOT NULL DEFAULT '{}',  -- Always-on user IDs
  description TEXT,
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

And the evaluation function:

```ts
import { createHash } from 'crypto';

interface FlagContext {
  userId: string;
  workspaceId?: string;
}

async function isEnabled(flagKey: string, ctx: FlagContext): Promise<boolean> {
  const flag = await db.query.featureFlags.findFirst({
    where: eq(featureFlags.key, flagKey),
  });

  if (!flag || !flag.enabled) return false;

  // Always-on user list (internal accounts etc.)
  if (flag.userIds.includes(ctx.userId)) return true;

  // Rollout percentage via consistent hashing
  if (flag.rolloutPct > 0) {
    const hash = createHash('sha256')
      .update(`${flagKey}:${ctx.userId}`)
      .digest('hex');
    const bucket = parseInt(hash.slice(0, 8), 16) % 100;
    if (bucket < flag.rolloutPct) return true;
  }

  return false;
}
```

The consistent hash ensures the same user always gets the same bucket — they're not flipping between feature states on each request. The hash includes the flag key so that a user in bucket 23 for flag A isn't necessarily in bucket 23 for flag B.

## Caching

A database query per flag evaluation per request would add latency and load. We cache flag state in Redis with a short TTL:

```ts
const CACHE_TTL = 60; // seconds

async function getFlagCached(flagKey: string): Promise<typeof featureFlags.$inferSelect | null> {
  const cached = await redis.get(`flag:${flagKey}`);
  if (cached) return JSON.parse(cached);

  const flag = await db.query.featureFlags.findFirst({
    where: eq(featureFlags.key, flagKey),
  });

  if (flag) {
    await redis.setex(`flag:${flagKey}`, CACHE_TTL, JSON.stringify(flag));
  }

  return flag ?? null;
}
```

60-second cache means kill switches take up to 60 seconds to propagate. That's acceptable for our use case — if we're killing a feature due to a production incident, 60 seconds is fine.

## The admin interface

We have a minimal admin page (internal, auth-gated) that shows all flags and their current state, with toggle controls:

```
FLAG                    ENABLED   ROLLOUT   USERS
──────────────────────────────────────────────────────
ai_invoke_streaming      YES       100%      —
marketplace_v2           YES        10%      admin_001
lattice_early_access     NO          0%      admin_001
scoutr_bulk_scan         NO          0%      —
```

Toggle, set rollout percentage, add/remove always-on users — all via a simple form. No third-party dashboard, no SDK to keep updated.

## Usage in code

Usage is a single async function call at the point of the feature:

```ts
// In a React Server Component
const showNewCheckout = await isEnabled('marketplace_v2', { userId: session.userId });

// In an API route
const streamingEnabled = await isEnabled('ai_invoke_streaming', { userId: ctx.userId });

// In middleware
const latticeAccess = await isEnabled('lattice_early_access', { userId: user.id });
if (!latticeAccess) return redirect('/waitlist');
```

## The trade-offs

**What we lose vs. a platform:**

- Real-time propagation (we have 60-second lag; platforms offer &lt;100ms)
- Advanced targeting (no country, device, custom attribute rules)
- Integrated analytics (we'd need to wire metrics separately)
- Audit log for flag changes (we don't track who changed what)

**What we gain:**

- Zero monthly cost
- No SDK dependency to keep updated
- Full control over the data model
- No latency added from third-party evaluation services
- The flag state is in our database, queryable alongside everything else

At our current scale (hundreds of users, not millions), the trade-offs are clearly in favour of the lightweight approach. The time to build and maintain this was under a day. LaunchDarkly at our scale would cost more per month than that day's work is worth.

## When to switch

The right time to switch to a real platform is when:
- We need sub-second flag propagation for safety-critical features
- We need sophisticated targeting (geographic, device type, custom segment)
- We have enough users that even a 60-second kill switch window causes meaningful customer impact

None of those conditions currently hold. We'll revisit when they do.
