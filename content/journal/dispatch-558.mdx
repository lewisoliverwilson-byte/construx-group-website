The event loop is how JavaScript handles concurrency without threads. Understanding it explains behaviour that otherwise seems arbitrary — and informs how to write code that doesn't block the UI.

## The structure

JavaScript runs in a single thread. The event loop manages four areas:

```
Call Stack         Task Queue          Microtask Queue    Web APIs
─────────────      ────────────────    ───────────────    ─────────────
Currently          setTimeout          Promise.then()     Timers
executing          setInterval         queueMicrotask     Fetch
function calls     I/O callbacks       MutationObserver   DOM Events
```

The event loop algorithm:
1. Execute everything in the call stack until it's empty.
2. Drain the entire microtask queue.
3. Take one task from the task queue and push it onto the call stack.
4. Repeat.

## Why setTimeout(fn, 0) doesn't run immediately

```ts
console.log('1');
setTimeout(() => console.log('2'), 0);
console.log('3');

// Output: 1, 3, 2
```

`setTimeout` with delay `0` schedules a callback in the task queue. The current call stack must finish executing, the microtask queue must drain, and then the event loop picks up the task. Even with a 0ms delay, the callback never runs before the current synchronous code finishes.

## Microtasks run before the next task

```ts
console.log('1');

setTimeout(() => console.log('setTimeout'), 0); // task queue

Promise.resolve().then(() => console.log('Promise.then')); // microtask queue

queueMicrotask(() => console.log('queueMicrotask')); // microtask queue

console.log('4');

// Output: 1, 4, Promise.then, queueMicrotask, setTimeout
```

Promises and `queueMicrotask` add to the microtask queue. Microtasks are processed immediately after the current call stack empties — before the next task from the task queue. This is why promise chains resolve before the next `setTimeout`.

## Why long synchronous computation freezes the UI

```ts
// This freezes the browser for N seconds
function heavyComputation(n: number): number {
  let result = 0;
  for (let i = 0; i < n; i++) {
    result += Math.sqrt(i);
  }
  return result;
}

heavyComputation(500_000_000); // 5+ seconds on the call stack
```

The event loop can't process user events (clicks, input), render frames, or run timer callbacks while a synchronous function is on the call stack. The UI freezes until the function returns.

Solutions:

**Web Workers**: offload heavy computation to a separate thread.

```ts
// worker.ts
self.onmessage = (e) => {
  const result = heavyComputation(e.data);
  self.postMessage(result);
};

// main.ts
const worker = new Worker('./worker.ts');
worker.postMessage(500_000_000);
worker.onmessage = (e) => console.log('Result:', e.data);
// Main thread not blocked
```

**Chunked processing**: break the work into pieces, yielding between chunks.

```ts
async function processInChunks(items: number[], chunkSize = 1000): Promise<void> {
  for (let i = 0; i < items.length; i += chunkSize) {
    const chunk = items.slice(i, i + chunkSize);
    processChunk(chunk);
    await new Promise(resolve => setTimeout(resolve, 0)); // yield to event loop
  }
}
```

The `await` on `setTimeout(resolve, 0)` schedules a task, yields control to the event loop, processes any pending events (render frame, user input), then resumes.

## async/await and the event loop

```ts
async function fetchData() {
  console.log('A');               // synchronous
  const data = await fetch(url); // yields here
  console.log('B');               // runs after fetch resolves
}

fetchData();
console.log('C');

// Output: A, C, B
```

`await` pauses the function at the `await` point, schedules a microtask to resume when the promise resolves, and returns control to the caller. `console.log('C')` runs while fetch is in progress. When fetch resolves, the continuation (`console.log('B')`) is enqueued as a microtask.

## Task vs microtask: the practical difference

```ts
// Task (macrotask) — runs after current tasks complete
setTimeout(callback, 0);
setInterval(callback, interval);
queueMacrotask(callback); // experimental, not in most environments

// Microtask — runs after current synchronous code, before next task
Promise.resolve().then(callback);
queueMicrotask(callback);
```

Prefer `queueMicrotask` over `Promise.resolve().then()` for custom scheduling — it's explicit and avoids creating an unnecessary promise object.

## Rendering and the event loop

The browser inserts render steps between tasks, not between microtasks. If your code creates a long microtask chain, rendering doesn't happen until the chain completes:

```ts
// This blocks rendering until all microtasks complete
function chainedMicrotasks() {
  let p = Promise.resolve();
  for (let i = 0; i < 100000; i++) {
    p = p.then(() => {});
  }
  return p;
}
```

Long microtask chains are unusual in practice, but the principle matters: `await` inside a loop doesn't automatically yield to the render step. If you have a long `for await` loop updating the DOM, use `await new Promise(r => setTimeout(r, 0))` periodically to let the browser render.

## requestAnimationFrame

```ts
function animate() {
  updateState();
  render();
  requestAnimationFrame(animate); // schedule next frame
}
requestAnimationFrame(animate);
```

`requestAnimationFrame` callbacks run before the browser's paint step — at the correct point in the render cycle. For animations, prefer `requestAnimationFrame` over `setInterval` — it runs at the display refresh rate (typically 60fps) and pauses when the tab is in the background.
