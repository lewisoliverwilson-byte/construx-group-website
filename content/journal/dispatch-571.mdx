The browser's rendering engine, event handling, and JavaScript all share one thread. If your JavaScript takes 500ms to run, the UI is frozen for 500ms — no scrolling, no clicks, no animations. The frame rate drops to zero.

Web Workers solve this by moving computation to a separate thread. The worker runs in its own context, communicates back via `postMessage`, and never touches the DOM.

## The basic pattern

```ts
// worker.ts
self.onmessage = (event: MessageEvent<number[]>) => {
  const result = heavyComputation(event.data);
  self.postMessage(result);
};

function heavyComputation(data: number[]): number {
  return data.reduce((sum, n) => sum + n * n, 0);
}
```

```ts
// main.ts
const worker = new Worker(new URL('./worker.ts', import.meta.url));

worker.postMessage([1, 2, 3, 4, 5]);

worker.onmessage = (event: MessageEvent<number>) => {
  console.log('Result:', event.data);
};
```

The `new URL('./worker.ts', import.meta.url)` pattern is the modern way to reference a worker file — it works with bundlers like webpack and Vite, which bundle the worker into a separate chunk.

## Transferable objects

`postMessage` serialises data using the structured clone algorithm — similar to JSON but supporting more types (Date, Map, Set, etc.). For large data (ArrayBuffer, ImageData), serialisation is expensive because it copies the data.

Transferable objects avoid the copy by transferring ownership of the memory:

```ts
const buffer = new ArrayBuffer(1024 * 1024 * 10); // 10MB

// Without transfer — copies 10MB
worker.postMessage(buffer);

// With transfer — zero-copy, but buffer is now unusable in main thread
worker.postMessage(buffer, [buffer]);
```

After transfer, `buffer.byteLength` is 0 in the main thread — ownership moved to the worker. Use this for image processing, audio data, WebAssembly memory.

## In React: using a worker with useEffect

```tsx
import { useState, useEffect, useRef } from 'react';

export function HeavyComputation({ input }: { input: number[] }) {
  const [result, setResult] = useState<number | null>(null);
  const workerRef = useRef<Worker | null>(null);

  useEffect(() => {
    workerRef.current = new Worker(new URL('../workers/compute.ts', import.meta.url));

    workerRef.current.onmessage = (e: MessageEvent<number>) => {
      setResult(e.data);
    };

    return () => {
      workerRef.current?.terminate();
    };
  }, []);

  useEffect(() => {
    workerRef.current?.postMessage(input);
  }, [input]);

  return <div>{result ?? 'Computing...'}</div>;
}
```

The worker is created once in the first `useEffect` and terminated on cleanup. The second effect sends new input whenever it changes. The component re-renders only when the worker responds — the heavy computation never blocks the UI.

## What workers can and can't do

**Can:**
- Run any JavaScript or TypeScript
- Use `fetch` and the Fetch API
- Use `setTimeout`/`setInterval`
- Import other modules (with Vite/webpack)
- Use IndexedDB
- Use WebSockets
- Use WebAssembly

**Can't:**
- Access the DOM (no `document`, `window`, or any DOM API)
- Access `localStorage` or `sessionStorage`
- Use `alert()`, `confirm()`, or `prompt()`

The inability to touch the DOM is by design — it prevents race conditions where both threads modify the same element simultaneously.

## Practical use cases

**Image processing**: resizing, filtering, format conversion. Image data is large; keeping this off the main thread keeps the UI smooth.

**CSV/JSON parsing**: large data files can take hundreds of milliseconds to parse. Off-thread, the user doesn't notice.

**Cryptography**: hashing, encryption. CPU-intensive by nature.

**Sorting and filtering large datasets**: for tables with tens of thousands of rows, moving sort/filter logic to a worker prevents keypress lag.

**WebAssembly execution**: WASM modules run in the same thread as the JavaScript that instantiates them. Running WASM in a worker isolates the CPU cost.

## When not to use workers

For computations under ~5ms, the overhead of `postMessage` serialisation outweighs the benefit. Workers are for genuinely heavy work.

Don't use a worker for API calls — `fetch` is already non-blocking. The browser handles network I/O on its own threads. Only the response processing (JSON parsing of large payloads) might benefit from a worker.

## Comlink: cleaner API

The raw worker API requires manual message passing. [Comlink](https://github.com/GoogleChromeLabs/comlink) wraps it in a Proxy, letting you call worker functions as if they were async functions:

```ts
// worker.ts
import { expose } from 'comlink';

const api = {
  async processData(data: number[]): Promise<number> {
    return data.reduce((sum, n) => sum + n * n, 0);
  },
};

expose(api);
```

```ts
// main.ts
import { wrap } from 'comlink';

const worker = new Worker(new URL('./worker.ts', import.meta.url));
const api = wrap<typeof import('./worker')['default']>(worker);

const result = await api.processData([1, 2, 3]); // Looks like a normal async call
```

Comlink eliminates the message-passing boilerplate while keeping the threading model intact.
