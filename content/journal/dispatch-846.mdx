excerpt: "Fly.io runs Docker containers on bare-metal servers using Firecracker microVMs. Each machine is a lightweight VM that boots in ~100ms — fast enough to start on the first HTTP request and stop when idle. The Machines API is a REST API for direct machine control: create, start, stop, destroy machines by API call. Fly Proxy routes requests to the nearest running machine; if no machine is running, it holds the connection while one starts. The result is scale-to-zero with no cold-start penalty visible to users."

Firecracker VMs. Millisecond boots. Scale to zero without visible cold starts.

## Deploy with flyctl

```bash
# Initialise a Fly.io app
fly launch --name construx-api --region lhr

# fly.toml is generated automatically
# Edit for your app's needs, then deploy
```

## fly.toml — machine configuration

```toml
# fly.toml
app    = "construx-api"
primary_region = "lhr"

[build]
  dockerfile = "Dockerfile"

[http_service]
  internal_port   = 3000
  force_https     = true
  auto_stop_machines  = "stop"      # Stop when no traffic
  auto_start_machines = true        # Start on first request
  min_machines_running = 0          # Allow scale-to-zero

  [http_service.concurrency]
    type       = "connections"
    hard_limit = 1000
    soft_limit = 800

[[vm]]
  size   = "shared-cpu-1x"         # 256MB RAM, 1 shared CPU
  memory = "512mb"

[checks.health]
  grace_period = "5s"
  interval     = "15s"
  method       = "GET"
  path         = "/health"
  timeout      = "2s"
```

## Machines API — direct control

```bash
# List machines in an app
curl -H "Authorization: Bearer $FLY_API_TOKEN" \
  "https://api.machines.dev/v1/apps/construx-api/machines" | jq '.[].id'

# Start a stopped machine
curl -X POST \
  -H "Authorization: Bearer $FLY_API_TOKEN" \
  "https://api.machines.dev/v1/apps/construx-api/machines/178148ef6e9389/start"

# Stop a running machine
curl -X POST \
  -H "Authorization: Bearer $FLY_API_TOKEN" \
  "https://api.machines.dev/v1/apps/construx-api/machines/178148ef6e9389/stop"
```

## Create a machine via API

```ts
// lib/fly-machines.ts
const FLY_API = 'https://api.machines.dev/v1';

interface MachineConfig {
  image:  string;
  env:    Record<string, string>;
  size:   string;
}

export async function createMachine(app: string, config: MachineConfig) {
  const res = await fetch(`${FLY_API}/apps/${app}/machines`, {
    method:  'POST',
    headers: {
      Authorization: `Bearer ${process.env.FLY_API_TOKEN}`,
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({
      config: {
        image:    config.image,
        env:      config.env,
        services: [{
          ports:          [{ port: 443, handlers: ['tls', 'http'] }],
          protocol:       'tcp',
          internal_port:  3000,
        }],
        checks: {
          health: {
            type:     'http',
            port:     3000,
            path:     '/health',
            interval: '15s',
            timeout:  '2s',
          },
        },
      },
      region: 'lhr',
      vm_size: config.size,
    }),
  });

  if (!res.ok) throw new Error(await res.text());
  return res.json();
}
```

## Volumes — persistent storage

```bash
# Create a volume (attached to a single machine, not shared)
fly volumes create construx_data --region lhr --size 10

# Mount in fly.toml
[mounts]
  source      = "construx_data"
  destination = "/data"

# Replicated volumes (beta) — sync across regions
fly volumes create construx_data --region lhr --size 10 --replication
```

Fly.io vs Render vs Railway: all three are container platforms with scale-to-zero. Fly.io is closest to bare metal — you control individual Machines via API, choose regions explicitly, and get Firecracker VM isolation. Render and Railway are higher-abstraction: point at a repo, it deploys. Fly.io requires more configuration but gives more control over routing, regions, and machine lifecycle. For latency-sensitive apps that need specific regions or machine-level control, Fly.io. For simplicity and fast setup, Render or Railway.
