Not just a cache. Sorted sets, streams, and pub/sub are the interesting parts.

## Sorted sets — leaderboards and rate limiting

```ts
import { Redis } from 'ioredis';
const redis = new Redis(process.env.REDIS_URL);

// Leaderboard — O(log N) insert and range query
async function recordScore(userId: string, score: number) {
  await redis.zadd('leaderboard:weekly', score, userId);
}

async function getTopUsers(n: number) {
  // ZREVRANGE — highest scores first
  const results = await redis.zrevrangebyscore(
    'leaderboard:weekly',
    '+inf', '-inf',
    'WITHSCORES',
    'LIMIT', 0, n,
  );

  const users: { userId: string; score: number }[] = [];
  for (let i = 0; i < results.length; i += 2) {
    users.push({ userId: results[i], score: parseFloat(results[i + 1]) });
  }
  return users;
}

// Rate limiting — sliding window with sorted set
async function checkRateLimit(ip: string, limit: number, windowMs: number): Promise<boolean> {
  const key = `ratelimit:${ip}`;
  const now  = Date.now();
  const pipe = redis.pipeline();

  pipe.zremrangebyscore(key, '-inf', now - windowMs);  // Remove old entries
  pipe.zadd(key, now, `${now}-${Math.random()}`);       // Add current request
  pipe.zcard(key);                                       // Count requests in window
  pipe.expire(key, Math.ceil(windowMs / 1000));

  const results = await pipe.exec();
  const count   = results![2][1] as number;
  return count <= limit;
}
```

## Streams — durable event log

```ts
// Append to a stream
await redis.xadd(
  'orders:events',
  '*',  // Auto-generate ID
  'type', 'order.created',
  'orderId', orderId,
  'userId', userId,
  'amount', String(amount),
);

// Read new events (consumer group pattern)
await redis.xgroup('CREATE', 'orders:events', 'email-service', '$', 'MKSTREAM');

// Process events — exactly-once per consumer group
async function processOrderEvents() {
  const results = await redis.xreadgroup(
    'GROUP', 'email-service', 'worker-1',
    'COUNT', 10,
    'BLOCK', 5000,  // Block 5s waiting for messages
    'STREAMS', 'orders:events', '>',  // > = only undelivered messages
  );

  if (!results) return;  // Timeout

  for (const [, messages] of results) {
    for (const [id, fields] of messages) {
      const event = Object.fromEntries(
        fields.reduce<[string, string][]>((pairs, f, i) => {
          if (i % 2 === 0) pairs.push([f, fields[i + 1]]);
          return pairs;
        }, []),
      );

      await handleEvent(event);
      await redis.xack('orders:events', 'email-service', id);  // Mark processed
    }
  }
}
```

## Pub/Sub — real-time broadcasting

```ts
// Publisher — any service
await redis.publish('notifications:user-123', JSON.stringify({
  type:    'payment_succeeded',
  amount:  4999,
  message: 'Your payment of £49.99 was successful',
}));

// Subscriber — WebSocket server
const subscriber = new Redis(process.env.REDIS_URL);

await subscriber.subscribe('notifications:user-123');

subscriber.on('message', (channel: string, message: string) => {
  const payload = JSON.parse(message);
  // Forward to WebSocket connection for user-123
  wsServer.sendToUser('123', payload);
});

// Pattern subscribe — all user notifications
await subscriber.psubscribe('notifications:user-*');
subscriber.on('pmessage', (pattern, channel, message) => {
  const userId = channel.split('-')[1];
  wsServer.sendToUser(userId, JSON.parse(message));
});
```

## Atomic operations with Lua scripts

```ts
// Atomic check-and-set: only increment if under limit
const script = `
  local current = tonumber(redis.call('get', KEYS[1])) or 0
  if current < tonumber(ARGV[1]) then
    return redis.call('incr', KEYS[1])
  else
    return -1
  end
`;

const result = await redis.eval(script, 1, `quota:${userId}`, dailyLimit);
if (result === -1) {
  throw new Error('Daily quota exceeded');
}
```

Redis Streams vs Kafka: Kafka handles much higher throughput (millions of events/sec), has better durability guarantees, and is designed for multi-datacenter replication. Redis Streams are simpler to run (no ZooKeeper, no broker cluster), fast enough for most internal event pipelines, and reuse existing Redis infrastructure. The Construx default: Redis Streams for internal event pipelines under ~50k events/day; Kafka only when throughput or multi-region consumption requires it.
