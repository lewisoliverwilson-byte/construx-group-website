Next.js App Router has four caches. They stack. When a page doesn't update after a data change, one of them is responsible. Here's each cache, what it stores, and how to control it.

## The four caches

| Cache | What it stores | Location | Invalidation |
|---|---|---|---|
| Request Memoization | `fetch()` deduplication within a single render | In-memory, per-request | Automatic (per request) |
| Data Cache | `fetch()` responses across requests | Server-side, persistent | `revalidate`, `cache: 'no-store'`, `revalidatePath` |
| Full Route Cache | Complete rendered HTML+RSC payload | Server-side, persistent | `revalidate`, `revalidatePath`, redeploy |
| Router Cache | Client-side navigation cache | Browser memory | Navigation, `router.refresh()` |

## Request Memoization

The least visible cache. Within a single server render, if two components call `fetch('/api/user/123')`, the second call returns the cached result from the first — no duplicate network request. Automatic, requires no configuration.

```tsx
// Both components call the same URL during one render
// The second fetch is deduplicated — only one network request goes out
async function UserName() {
  const user = await fetch('/api/users/123').then(r => r.json()); // fetches
  return <span>{user.name}</span>;
}

async function UserAvatar() {
  const user = await fetch('/api/users/123').then(r => r.json()); // returns memoized result
  return <img src={user.avatar} />;
}
```

This only applies to `fetch()` — not database calls, not SDK calls. Wrap those in `React.cache()` for the same effect:

```ts
import { cache } from 'react';
import { db } from '@/lib/db';

export const getUser = cache(async (id: string) => {
  return db.query.users.findFirst({ where: eq(users.id, id) });
});
```

## Data Cache

Persistent across requests. When you `fetch()` from a Server Component, Next.js caches the response server-side by default.

```ts
// Cached indefinitely (default)
const data = await fetch('https://api.example.com/posts');

// Cached for 60 seconds (revalidate after 60s)
const data = await fetch('https://api.example.com/posts', {
  next: { revalidate: 60 }
});

// Not cached — fresh on every request
const data = await fetch('https://api.example.com/posts', {
  cache: 'no-store'
});
```

For route segments, control the default at the layout or page level:

```ts
// app/dashboard/page.tsx
export const revalidate = 60;    // revalidate this page every 60 seconds
export const dynamic = 'force-dynamic';  // disable all caching for this page
```

**Database calls bypass the Data Cache** — `revalidate` and `cache: 'no-store'` only apply to `fetch()`. If you're using Drizzle or Prisma directly, the Data Cache doesn't apply to those calls.

## Full Route Cache

When Next.js pre-renders a page at build time (static rendering), the complete rendered output — HTML and the React Server Component payload — is stored. Subsequent requests serve this stored output without re-rendering.

A route is statically rendered when:
- No dynamic functions (`cookies()`, `headers()`, `searchParams`) are used
- All `fetch()` calls are cached (default or `revalidate`)

A route is dynamically rendered when any of the above applies — it renders on every request.

To see which pages are static vs dynamic, check the build output:

```
Route (app)                              Size     First Load JS
┌ ○ /                                    5.2 kB         87.4 kB
├ ○ /journal                             3.1 kB         85.3 kB
├ ƒ /journal/[slug]                      1.8 kB         84 kB
├ ○ /ventures                            4.9 kB         87.1 kB
└ ƒ /dashboard                           2.3 kB         84.5 kB
```

`○` = static, `ƒ` = dynamic.

## Router Cache

Client-side only. When you navigate with `<Link>`, Next.js stores the RSC payload in memory. Navigate back to a visited page and it renders from cache without a server request.

Duration: 30 seconds for dynamic routes, 5 minutes for static. Not configurable in App Router.

To force a fresh fetch from the router cache:

```ts
'use client';
import { useRouter } from 'next/navigation';

function RefreshButton() {
  const router = useRouter();
  return <button onClick={() => router.refresh()}>Refresh</button>;
}
```

`router.refresh()` re-fetches the current route's RSC payload from the server, invalidating the router cache entry.

## On-demand revalidation

For CMS integrations or webhooks — invalidate specific paths when data changes:

```ts
// app/api/revalidate/route.ts
import { revalidatePath, revalidateTag } from 'next/cache';
import { NextRequest } from 'next/server';

export async function POST(req: NextRequest) {
  const secret = req.headers.get('x-revalidation-secret');
  if (secret !== process.env.REVALIDATION_SECRET) {
    return Response.json({ error: 'Unauthorized' }, { status: 401 });
  }

  const { path, tag } = await req.json();

  if (tag) {
    revalidateTag(tag); // invalidate all fetches tagged with this tag
  } else if (path) {
    revalidatePath(path); // invalidate the full route cache for this path
  }

  return Response.json({ revalidated: true, at: Date.now() });
}
```

Tag individual fetches:

```ts
const posts = await fetch('https://cms.example.com/api/posts', {
  next: { tags: ['posts'] }
});
```

When a new post is published, the CMS hits your webhook, which calls `revalidateTag('posts')` — only pages using data tagged `posts` re-render.

## Debugging which cache is serving a response

Add `x-nextjs-cache` header checking:

```ts
const res = await fetch('https://api.example.com/data');
console.log(res.headers.get('x-nextjs-cache')); // HIT, MISS, STALE, SKIP
```

Or in the browser: Network tab → any server-rendered page → look for `x-nextjs-cache: HIT` in the response headers when the Full Route Cache is serving the page.

## The mental model

Think of the caches as layers: Router Cache (client) → Full Route Cache (server) → Data Cache (server) → Request Memoization (per-render). A request hits them in that order. Invalidating one layer doesn't automatically invalidate the layers below it — `revalidatePath` clears both Full Route Cache and Data Cache, but the client's Router Cache might still serve the old version until it expires or `router.refresh()` is called.
