Product analytics is one of those areas where more is not better. Every metric you add is a metric you need to interpret, maintain, and act on. Most teams track everything and then don't know what to look at.

Here's how we think about analytics across three products.

## The metric selection principle

A metric is worth tracking if it directly informs a decision. "How many page views did we get last week?" doesn't inform a decision on its own. "What percentage of users who start a scan complete it?" informs a product decision about scan flow friction.

For each metric we track, we can answer: if this number went up, what would we do? If this number went down, what would we investigate? If neither question has a clear answer, we don't track the metric.

## What we track for each product

**Scoutr:**

- *First scan completion rate* — percentage of new users who complete their first scan. Our leading indicator of onboarding quality.
- *Scans per session* — how many products users are scanning in a typical session. Low is bad (tool isn't sticky); very high suggests professional use (good).
- *Free-to-pro conversion rate* — percentage of free users who upgrade within 30 days.
- *Pro churn rate* — percentage of pro subscribers who cancel per month.
- *AI confidence vs. actual outcome correlation* — we periodically sample completed scans and check whether products with high AI confidence scores were actually profitable. This validates the model.

**The Marqet:**

- *Listing view-to-purchase rate* — percentage of listing views that convert to a purchase.
- *Search-to-listing-view rate* — how often search leads to a listing click.
- *Seller listing completion rate* — percentage of sellers who create at least one live listing after signing up.
- *Dispute rate* — disputes as a percentage of total transactions. Rising dispute rate signals listing quality or seller reliability problems.
- *Gross merchandise volume* — total value of transactions. Platform health indicator.

**The Hyve:**

- *Workspace message volume* — messages per active workspace per week. Declining message volume in a workspace may predict churn.
- *AI interaction rate* — percentage of workspace sessions that include an AI agent interaction.
- *Workspace retention at 30/60/90 days* — what percentage of workspaces that were active in week 1 are still active at each interval.
- *Team expansion rate* — average members added per workspace per month. Rising expansion indicates the product is spreading within organisations.

## What we don't track

- **Pageviews.** A vanity metric. We care about engagement, not traffic.
- **Sessions.** Similar — sessions can increase while engagement decreases (users visiting, bouncing, visiting, bouncing).
- **Time on page.** Could mean they're engaged; could mean they're confused.
- **Social media referral traffic.** Interesting but not actionable at our scale.
- **Geographic breakdown.** We don't make localisation decisions, so geographic breakdowns don't inform decisions.

## The implementation

We use Plausible for web analytics — a privacy-first, EU-hosted analytics tool that doesn't use cookies and doesn't send data to Google. The setup is a single script tag and a few custom events.

Custom events are the valuable part:

```ts
// Plausible custom event from client components
function trackEvent(name: string, props?: Record<string, string>) {
  if (typeof window !== 'undefined' && 'plausible' in window) {
    (window as any).plausible(name, { props });
  }
}

// Examples
trackEvent('scan_started', { tier: user.tier });
trackEvent('scan_completed', { confidence: String(analysis.confidenceScore) });
trackEvent('upgrade_clicked', { source: 'scan_limit_reached' });
trackEvent('listing_viewed', { category: listing.category });
trackEvent('purchase_completed', { listing_category: listing.category });
```

Plausible aggregates these events into filterable reports. We can see scan completion rates, upgrade conversion by source, and listing view-to-purchase by category — all from a single dashboard.

## The review cadence

We review metrics weekly, but not comprehensively. The weekly review looks at: are any of our core metrics moving significantly in either direction? If yes, why?

Monthly, we do a deeper review: trend analysis over the past three months, comparison against the same period last year (starting in month 13), and an evaluation of whether we're tracking the right things.

The question in the monthly review: are there decisions we're making without data that we should have data on? Are there metrics we're tracking that we never actually use to make decisions?

We've removed three metrics from our tracking in the past six months: referral source breakdown (we have no referral program to optimise), session duration (we realised we never acted on this data), and daily active users (too noisy; we care about weekly and monthly retention).

## The anti-pattern: metric as goal

The most dangerous analytics failure is when the metric becomes the goal rather than a proxy for the goal.

Example: if we set "daily active users" as a goal, we could game it by sending daily notification emails that bring users back to the product without delivering value. DAU goes up; user value doesn't.

We keep the distinction explicit: metrics are proxies for user value. When we improve a metric, we ask: is user value actually improving, or are we just moving the number?

The validation: user value is best assessed by talking to users. Analytics tells us what's happening; users tell us why. Both are necessary.
