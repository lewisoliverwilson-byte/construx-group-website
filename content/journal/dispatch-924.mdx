date: "2032-07-17"
excerpt: "Kafka is a distributed log — messages are appended to partitioned, replicated topics and retained for a configurable period regardless of whether they've been consumed. Consumer groups allow multiple independent consumers to read the same topic at their own pace; each group maintains its own offset per partition. Kafka's exactly-once semantics (EOS) combine idempotent producers, transactional APIs, and consumer-side offset management to guarantee each message is processed exactly once end-to-end. Kafka is the backbone of event-driven architectures: order events, CDC streams from Postgres (Debezium), audit logs, and real-time analytics pipelines."

Produce once. Consume at your own pace. Retain for days. Multiple consumer groups — zero coordination.

## Producer and consumer basics

```bash
# Kafka CLI tools (kafka-topics, kafka-console-producer, kafka-console-consumer)
# Set the broker address
BROKER=kafka-bootstrap.construx.svc.cluster.local:9092

# Create a topic with 6 partitions and replication factor 3
kafka-topics.sh --bootstrap-server $BROKER \
  --create --topic construx.orders \
  --partitions 6 \
  --replication-factor 3 \
  --config retention.ms=604800000   # 7-day retention

# List topics
kafka-topics.sh --bootstrap-server $BROKER --list

# Describe a topic (partitions, leaders, ISR)
kafka-topics.sh --bootstrap-server $BROKER --describe --topic construx.orders
# Topic: construx.orders  Partitions: 6  ReplicationFactor: 3
# Partition 0: Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
# Partition 1: Leader: 2  Replicas: 2,3,1  Isr: 2,3,1

# Produce messages (JSON)
kafka-console-producer.sh --bootstrap-server $BROKER \
  --topic construx.orders \
  --property "key.separator=:" \
  --property "parse.key=true" << 'EOF'
cust-001:{"order_id":"a3f9b2c1","status":"pending","total_cents":4999}
cust-002:{"order_id":"b4e8d9f2","status":"pending","total_cents":9999}
EOF

# Consume from the beginning
kafka-console-consumer.sh --bootstrap-server $BROKER \
  --topic construx.orders \
  --from-beginning \
  --property print.key=true \
  --max-messages 10
# cust-001  {"order_id":"a3f9b2c1",...}
# cust-002  {"order_id":"b4e8d9f2",...}
```

## Consumer groups and offset management

```bash
# Consumer groups: each group reads all partitions independently
# Group A (order-processor) reads at its own pace
kafka-console-consumer.sh --bootstrap-server $BROKER \
  --topic construx.orders \
  --group order-processor \
  --from-beginning

# Group B (analytics) reads the same topic independently
kafka-console-consumer.sh --bootstrap-server $BROKER \
  --topic construx.orders \
  --group analytics-pipeline \
  --from-beginning

# List consumer groups
kafka-consumer-groups.sh --bootstrap-server $BROKER --list
# order-processor
# analytics-pipeline
# email-notification

# Describe consumer group lag — key metric for monitoring
kafka-consumer-groups.sh --bootstrap-server $BROKER \
  --describe --group order-processor
# GROUP            TOPIC             PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
# order-processor  construx.orders   0          38241           38241           0
# order-processor  construx.orders   1          12847           12900           53   ← 53 behind
# order-processor  construx.orders   2          24103           24103           0

# Reset offsets — reprocess from beginning (dangerous in production)
kafka-consumer-groups.sh --bootstrap-server $BROKER \
  --group order-processor \
  --topic construx.orders \
  --reset-offsets --to-earliest --execute

# Reset to a specific timestamp (replay events from a point in time)
kafka-consumer-groups.sh --bootstrap-server $BROKER \
  --group order-processor \
  --topic construx.orders \
  --reset-offsets --to-datetime 2032-06-05T14:00:00.000 --execute
```

## Exactly-once semantics (EOS)

```python
# Python producer with exactly-once semantics
from confluent_kafka import Producer

producer = Producer({
    'bootstrap.servers': 'kafka-bootstrap.construx.svc.cluster.local:9092',
    'enable.idempotence': True,         # Idempotent producer (no duplicates on retry)
    'max.in.flight.requests.per.connection': 5,  # Required for idempotence
    'acks': 'all',                      # Wait for all ISR replicas to ack
    'retries': 2147483647,              # Retry forever on transient failures
    'delivery.timeout.ms': 120000,      # But timeout after 2 minutes total
    # Transactional ID for exactly-once (unique per producer instance)
    'transactional.id': 'construx-order-producer-1',
})

producer.init_transactions()

def produce_order_with_transaction(order):
    producer.begin_transaction()
    try:
        producer.produce(
            topic='construx.orders',
            key=order['customer_id'],
            value=json.dumps(order).encode(),
        )
        # Send offsets atomically with the transaction
        # (for consume-transform-produce patterns)
        producer.send_offsets_to_transaction(
            offsets,
            consumer.consumer_group_metadata(),
        )
        producer.commit_transaction()
    except Exception as e:
        producer.abort_transaction()
        raise
```

## Kafka Streams — stream processing in Java/Kotlin

```java
// construx-order-enrichment: read orders, join with customer data, emit enriched events
Properties props = new Properties();
props.put(StreamsConfig.APPLICATION_ID_CONFIG, "construx-order-enricher");
props.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka-bootstrap.construx.svc.cluster.local:9092");
props.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG, StreamsConfig.EXACTLY_ONCE_V2);

StreamsBuilder builder = new StreamsBuilder();

// Read the orders topic
KStream<String, Order> orders = builder
    .stream("construx.orders", Consumed.with(Serdes.String(), orderSerde));

// Load customer data as a GlobalKTable (replicated to all instances)
GlobalKTable<String, Customer> customers = builder
    .globalTable("construx.customers", Consumed.with(Serdes.String(), customerSerde));

// Join orders with customer data
KStream<String, EnrichedOrder> enriched = orders.join(
    customers,
    (orderId, order) -> order.getCustomerId(),   // Key extractor
    (order, customer) -> new EnrichedOrder(order, customer)  // Joiner
);

// Emit to the enriched topic
enriched.to("construx.orders.enriched", Produced.with(Serdes.String(), enrichedSerde));

KafkaStreams streams = new KafkaStreams(builder.build(), props);
streams.start();
```

## Monitoring with Kafka lag exporter

```bash
# Key metrics to monitor:
# kafka_consumer_group_lag          — messages behind per group per partition
# kafka_topic_partitions             — number of partitions per topic
# kafka_server_broker_topic_metrics  — bytes in/out per topic per broker

# Kafka Lag Exporter (prometheus-kafka-lag-exporter or burrow)
# Exposes consumer group lag as Prometheus metrics

# Critical alert: consumer group lag growing (processing can't keep up)
# PromQL alert:
sum by (group, topic) (kafka_consumer_group_lag) > 50000
# → alert: order-processor lag is 50k+ messages behind — scale up consumers

# Throughput per topic
sum(rate(kafka_server_broker_topic_metrics_bytes_in_per_sec[5m])) by (topic)

# Find the slowest consumer group
sort_desc(
  sum by (group) (kafka_consumer_group_lag)
) | head 10
```

Kafka vs RabbitMQ vs NATS JetStream: RabbitMQ is a traditional message broker — messages are delivered and deleted after consumption, routing is flexible (exchanges, queues, bindings), and it's better for task queues and RPC patterns. Kafka is a log — messages are retained regardless of consumption, allowing replay, multiple independent consumers, and audit trails. NATS JetStream is closer to Kafka's model (persistent, replayable) but simpler to operate (single binary, no ZooKeeper) and lower throughput ceiling. Choose Kafka when you need: replay capability (reprocess events from a timestamp), multiple independent consumer groups, very high throughput (millions of events/second), or CDC streams via Debezium. Choose RabbitMQ for traditional task queues or complex routing. Choose NATS JetStream for simpler architectures that need persistence without Kafka's operational complexity.
