The Hyve started as a team communication tool with an AI agent you could mention in messages. The natural extension is an API: let external tools trigger the AI agent, push messages into channels, and read workspace data. Here's how we designed the API layer.

## The versioning contract

A public API is a commitment. Once you publish an endpoint, consumers build on top of it. Breaking changes break integrations. The versioning strategy is the first decision:

**URL versioning** (`/api/v1/`, `/api/v2/`) is explicit and easy to reason about. Clients know exactly which contract they're on. Migration to a new version is opt-in.

**Header versioning** (`Accept: application/vnd.hyve+json;version=2`) is cleaner URL-wise but requires clients to set headers correctly and makes debugging harder.

We chose URL versioning. The overhead of maintaining `/v1/` and `/v2/` in parallel is worth the simplicity of the contract.

**Deprecation policy:** A version stays supported for 12 months after the successor is released. Deprecation notices go in response headers of old-version endpoints:

```
Deprecation: true
Sunset: Thu, 01 Jan 2028 00:00:00 GMT
Link: <https://api.thehyve.io/v2/messages>; rel="successor-version"
```

The `Sunset` header follows [RFC 8594](https://www.rfc-editor.org/rfc/rfc8594). Clients monitoring headers can detect deprecation and plan migration.

## Authentication

Internal API calls (Next.js server actions calling internal services) use shared secrets not exposed to clients. External API consumers need a different model.

We issue API keys scoped to workspaces:

```ts
interface ApiKey {
  keyId: string;        // Public identifier (shown in dashboard)
  keyHash: string;      // bcrypt hash of the actual key (never stored in plaintext)
  workspaceId: string;  // Scope
  name: string;         // Human-readable label ("Zapier integration")
  permissions: Permission[];  // Scoped capabilities
  createdAt: Date;
  lastUsedAt: Date | null;
  expiresAt: Date | null;
}

type Permission =
  | 'messages:read'
  | 'messages:write'
  | 'channels:read'
  | 'ai:invoke'
  | 'workspace:read';
```

The actual key is a 32-byte random value, base64-encoded: `hv_live_<base64>`. It's shown exactly once at creation — we store only the bcrypt hash.

Authentication middleware:

```ts
async function authenticateApiKey(req: Request): Promise<ApiKey | null> {
  const header = req.headers.get('Authorization');
  if (!header?.startsWith('Bearer ')) return null;
  
  const rawKey = header.slice(7);
  
  // Look up by prefix to find candidate keys
  // (bcrypt compare is expensive; we use key prefix for quick lookup)
  const prefix = rawKey.slice(0, 12);
  const candidates = await db
    .select()
    .from(apiKeys)
    .where(eq(apiKeys.keyPrefix, prefix));
  
  for (const candidate of candidates) {
    if (await bcrypt.compare(rawKey, candidate.keyHash)) {
      // Update lastUsedAt asynchronously
      void db.update(apiKeys)
        .set({ lastUsedAt: new Date() })
        .where(eq(apiKeys.keyId, candidate.keyId));
      return candidate;
    }
  }
  
  return null;
}
```

## Rate limiting

Rate limiting has two goals: protect the system from abuse and ensure fair allocation of capacity across consumers.

We use a token bucket model per API key:

```ts
interface RateLimit {
  keyId: string;
  tier: 'free' | 'standard' | 'enterprise';
}

const RATE_LIMITS = {
  free:       { requestsPerMinute: 20,  requestsPerHour: 100  },
  standard:   { requestsPerMinute: 100, requestsPerHour: 1000 },
  enterprise: { requestsPerMinute: 500, requestsPerHour: 10000 },
};

async function checkRateLimit(keyId: string, tier: RateLimit['tier']): Promise<{
  allowed: boolean;
  remaining: number;
  resetAt: number;
}> {
  const limits = RATE_LIMITS[tier];
  const minuteKey = `rate:${keyId}:minute:${Math.floor(Date.now() / 60000)}`;
  const hourKey = `rate:${keyId}:hour:${Math.floor(Date.now() / 3600000)}`;
  
  const [minuteCount, hourCount] = await Promise.all([
    redis.incr(minuteKey),
    redis.incr(hourKey),
  ]);
  
  if (minuteCount === 1) await redis.expire(minuteKey, 60);
  if (hourCount === 1) await redis.expire(hourKey, 3600);
  
  if (minuteCount > limits.requestsPerMinute || hourCount > limits.requestsPerHour) {
    return { allowed: false, remaining: 0, resetAt: (Math.floor(Date.now() / 60000) + 1) * 60000 };
  }
  
  return {
    allowed: true,
    remaining: Math.min(limits.requestsPerMinute - minuteCount, limits.requestsPerHour - hourCount),
    resetAt: (Math.floor(Date.now() / 60000) + 1) * 60000,
  };
}
```

Rate limit information goes in response headers on every request:

```
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 73
X-RateLimit-Reset: 1734400000
Retry-After: 60    (only on 429 responses)
```

## The AI invoke endpoint

The most interesting endpoint: triggering the AI agent via API.

```
POST /api/v1/ai/invoke
Authorization: Bearer hv_live_...
Content-Type: application/json

{
  "channelId": "ch_01...",
  "prompt": "Summarise the last 30 messages in this channel",
  "stream": false
}
```

This endpoint:
1. Authenticates the key
2. Verifies `ai:invoke` permission and workspace membership of the channel
3. Builds the same context the interactive agent uses (system prompt, channel history, RAG retrieval)
4. Calls the Claude API
5. Returns the response (or streams it if `stream: true`)

The streaming version uses SSE — the same pattern we use for the interactive message delivery. The client reads the `text/event-stream` response and processes tokens as they arrive.

## Error envelope

All API errors return a consistent envelope:

```json
{
  "error": {
    "code": "RATE_LIMIT_EXCEEDED",
    "message": "You have exceeded the rate limit for your API key. See the Retry-After header.",
    "docs": "https://docs.thehyve.io/errors/RATE_LIMIT_EXCEEDED"
  }
}
```

The `code` is a stable machine-readable string. The `message` is human-readable and may change. The `docs` link goes to a page explaining the error and how to resolve it.

Error codes are never HTTP status codes alone — HTTP status is a category, the code is specific. A 429 could be a per-minute limit, a per-hour limit, or an account-level suspension. The code distinguishes them.

## What we'd do differently

The API key prefix lookup (for fast bcrypt candidate lookup) is a pattern that works but requires storing the prefix separately. A cleaner approach: use a key format where the first N bytes are an opaque identifier that we can index directly, and the remainder is the secret — similar to how GitHub structures personal access tokens. We'd implement this in v2.

The tier-based rate limiting is blunt. Ideally, limits would be based on actual usage patterns (endpoints that hit the AI API have much higher compute cost than endpoints that read messages) rather than a flat request count. Per-endpoint weighting is the right model for v2.
