title: "Skaffold: inner-loop Kubernetes development — file sync, port-forward, hot reload"
date: "2034-03-06"
excerpt: "Skaffold is a command-line tool that automates the inner development loop for Kubernetes: it watches source files, rebuilds images when code changes, pushes to a local or remote registry, and re-deploys the affected workloads — all in a single `skaffold dev` command. The core problem it solves: Kubernetes development without tooling requires running `docker build && docker push && kubectl apply` on every change, which takes 30-90 seconds per iteration. Skaffold reduces this to under a second for interpreted languages by using file sync (rsync-style direct file copy into running containers) instead of rebuilding the image. For compiled languages, it rebuilds only the changed binary layer and replaces the container. Skaffold integrates with all major Kubernetes deployment tools: kubectl, Helm, Kustomize, and ko (for Go services). Its pipeline model is build → test → deploy → log-tail, with hooks for running tests after each deploy. The profiles system allows different configurations for local development (Minikube, Kind), staging (remote cluster, real registry), and production (CI-only, no auto-deploy). Port forwarding is automatic — Skaffold forwards all service ports to localhost during `skaffold dev`, so a developer reaches the orders-api at localhost:8080 without running kubectl port-forward manually. Skaffold has been superseded in some teams by Tilt (more powerful but more complex) and by Go-specific tooling like ko; it remains the pragmatic default for mixed-language Kubernetes development."

## Skaffold config and development workflow

```yaml
# skaffold.yaml — local development config for construx/orders-api
# Run: skaffold dev (watch + rebuild + redeploy on change)
# Run: skaffold run (one-shot build + deploy)
# Run: skaffold delete (tear down)

apiVersion: skaffold/v4beta11
kind: Config

metadata:
  name: orders-api

build:
  artifacts:
    - image: ghcr.io/construx/orders-api
      ko:                       # ko: fast Go image builder, no Dockerfile needed
        main: ./cmd/orders-api
        flags: ["-ldflags=-s -w"]
        env:
          - GOOS=linux
          - GOARCH=amd64
          - CGO_ENABLED=0

    - image: ghcr.io/construx/frontend
      docker:
        dockerfile: Dockerfile
        target: development     # multi-stage: development target for hot reload

      # File sync: copy changed .ts/.tsx files directly into container
      # Avoids full rebuild for frontend changes (Next.js HMR handles reload)
      sync:
        manual:
          - src: "src/**/*.ts"
            dest: /app/src
          - src: "src/**/*.tsx"
            dest: /app/src

  local:
    push: false           # don't push to registry in local dev
    useBuildkit: true

deploy:
  helm:
    releases:
      - name: orders-api
        chartPath: charts/orders-api
        valuesFiles:
          - charts/orders-api/values-local.yaml
        setValues:
          image.repository: ghcr.io/construx/orders-api
          image.tag: ""            # Skaffold replaces tag with content-addressed digest

portForward:
  - resourceType: service
    resourceName: orders-api
    namespace: construx-dev
    port: 8080
    localPort: 8080

  - resourceType: service
    resourceName: postgres
    namespace: construx-dev
    port: 5432
    localPort: 5432

profiles:
  # Local: use Kind cluster, skip registry push, file sync enabled
  - name: local
    activation:
      - kubeContext: kind-construx
    build:
      local:
        push: false
    deploy:
      helm:
        releases:
          - name: orders-api
            setValues:
              resources.requests.cpu: "100m"
              resources.requests.memory: "128Mi"
              replicaCount: 1

  # Staging: push to real registry, deploy to staging cluster
  - name: staging
    activation:
      - kubeContext: construx-staging
    build:
      local:
        push: true
    deploy:
      helm:
        releases:
          - name: orders-api
            valuesFiles:
              - charts/orders-api/values-staging.yaml
```

```bash
# Skaffold development workflow

# Start the inner development loop
# Watches files, rebuilds on change, re-deploys, tails logs
skaffold dev --profile=local --port-forward

# Output:
# Generating tags...
# Checking cache...
# Tags used in deployment:
#  - ghcr.io/construx/orders-api -> ghcr.io/construx/orders-api:sha256:abc123
# Starting deploy...
# Helm release orders-api: deployed
# Port forwarding service/orders-api in namespace construx-dev
# Forwarding from 0.0.0.0:8080 -> 8080
# Watching for changes...

# After editing src/handlers/order_handler.go:
# Syncing 1 files for ghcr.io/construx/orders-api:...
# Watching for changes...
# (file synced directly to container — no rebuild, < 100ms)

# One-shot build and deploy (CI or explicit refresh)
skaffold run --profile=staging

# Build only (produce image, don't deploy)
skaffold build --profile=staging --file-output=images.json

# Delete all deployed resources
skaffold delete --profile=local

# Debug mode: attach a debugger to the running container
# (injects delve for Go, pdb for Python)
skaffold debug --profile=local
```

```bash
# ko: fast Go container image builder (used by Skaffold for Go services)
# Produces minimal images from Go binaries without Dockerfile
# No Docker daemon required — builds directly to registry or tarball

# Build and push to GHCR
KO_DOCKER_REPO=ghcr.io/construx ko build ./cmd/orders-api

# Build to local Kind cluster (no registry push)
KO_DOCKER_REPO=kind.local ko build ./cmd/orders-api

# ko.yaml — configuration file
defaultBaseImage: gcr.io/distroless/static-debian12:nonroot
builds:
  - id: orders-api
    main: ./cmd/orders-api
    flags: ["-trimpath"]
    ldflags: ["-s", "-w", "-X main.version={{.Version}}"]
    env:
      - CGO_ENABLED=0
      - GOOS=linux
      - GOARCH=amd64
    platforms:
      - linux/amd64
      - linux/arm64    # multi-arch for Graviton nodes
```

Skaffold vs Tilt vs Garden vs manual kubectl vs DevSpace: Tilt is the most powerful inner-loop tool — it uses Starlark (Python-like) configuration, has an excellent browser-based UI showing which services are running and their logs, and supports sophisticated dependency graphs between services. It is more complex to configure than Skaffold but more capable for large multi-service projects. Garden is a full-featured development platform for microservices, with dependency-aware builds and tests — powerful but heavy. Manual kubectl + docker build is what most Kubernetes developers start with; it works but the feedback loop is 30-90 seconds per change. DevSpace is similar to Skaffold with a focus on developer productivity and team configuration sharing. Skaffold's strength is pragmatic integration with existing Kubernetes tooling — if you use Helm and kubectl, a Skaffold config requires minimal changes to your existing deployment setup. Ko is the right choice for pure Go projects — it is faster than any Dockerfile-based approach because it builds directly from Go's build cache and produces images in seconds. The combination of Skaffold + ko for Go services gives a development loop where code change → running pod takes under 5 seconds.
