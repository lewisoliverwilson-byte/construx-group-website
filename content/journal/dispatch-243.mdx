Three products with a shared aesthetic but distinct identities:
- Scoutr: lime green (#C8F50C)
- The Marqet: blue (#3B82F6)
- The Hyve: purple (#8B5CF6)

The challenge: a component library that adapts to each product's accent colour without per-product forks of every component.

The solution: CSS custom properties (CSS variables) as design tokens, with Tailwind using them as semantic colour names.

## The token structure

Each product's `globals.css` defines a small set of custom properties:

```css
/* scoutr/globals.css */
:root {
  --color-accent: #C8F50C;
  --color-accent-dim: rgba(200,245,12,0.1);
  --color-accent-border: rgba(200,245,12,0.2);
}

/* marqet/globals.css */
:root {
  --color-accent: #3B82F6;
  --color-accent-dim: rgba(59,130,246,0.1);
  --color-accent-border: rgba(59,130,246,0.2);
}

/* hyve/globals.css */
:root {
  --color-accent: #8B5CF6;
  --color-accent-dim: rgba(139,92,246,0.1);
  --color-accent-border: rgba(139,92,246,0.2);
}
```

All other colour values are shared across products in a `shared.css`:

```css
:root {
  --color-bg: #000006;
  --color-surface: rgba(5,5,18,0.8);
  --color-border: rgba(255,255,255,0.08);
  --color-text-base: rgba(240,239,255,0.9);
  --color-text-muted: rgba(240,239,255,0.55);
  --color-text-dim: rgba(240,239,255,0.3);
}
```

## Tailwind configuration

The `tailwind.config.ts` maps these CSS variables to Tailwind colour utilities:

```ts
// tailwind.config.ts (shared across products)
export default {
  theme: {
    extend: {
      colors: {
        accent: 'var(--color-accent)',
        'accent-dim': 'var(--color-accent-dim)',
        'accent-border': 'var(--color-accent-border)',
        bg: 'var(--color-bg)',
        surface: 'var(--color-surface)',
        border: 'var(--color-border)',
        'text-base': 'var(--color-text-base)',
        'text-muted': 'var(--color-text-muted)',
        'text-dim': 'var(--color-text-dim)',
      },
    },
  },
};
```

A button component written once works in all three products:

```tsx
function PrimaryButton({ children }: { children: React.ReactNode }) {
  return (
    <button
      className="px-5 py-2.5 font-mono text-sm font-semibold uppercase tracking-wider
                 bg-accent text-black hover:opacity-90 transition-opacity"
      style={{ borderRadius: '3px' }}
    >
      {children}
    </button>
  );
}
```

In Scoutr, `bg-accent` resolves to `#C8F50C`. In The Hyve, `bg-accent` resolves to `#8B5CF6`. The component is identical; the CSS variable does the work.

## The construxgroup.io site

This site doesn't use the shared Tailwind config because it has a different use case: it's not a product, it's a marketing site. The accent colour isn't a product colour — it's Construx Group orange (#F97316).

The site uses a slightly different token setup:

```ts
// construx-group-website/tailwind.config.ts
export default {
  theme: {
    extend: {
      colors: {
        construx: '#F97316', // Construx Group brand orange
        'construx-dim': 'rgba(249,115,22,0.1)',
        'text-base': 'rgba(240,239,255,0.9)',
        'text-muted': 'rgba(240,239,255,0.55)',
        'text-dim': 'rgba(240,239,255,0.3)',
        border: 'rgba(255,255,255,0.08)',
        'border-bright': 'rgba(255,255,255,0.14)',
        subtle: 'rgba(255,255,255,0.03)',
      },
    },
  },
};
```

Here the colours are literal values, not CSS variables, because the site has a fixed identity.

## Where CSS variables beat Tailwind's built-in approach

Tailwind's theme can be configured with literal values or CSS variables. The CSS variable approach is better when:

1. **The value changes by context.** A CSS variable can change based on the `:root` scope, a data attribute (`[data-theme="dark"]`), or a class. Tailwind literal values are static at build time.

2. **Dark mode variants.** If a product supports dark and light modes, CSS variables let you swap all colours by changing a single `:root` scope. Tailwind's `dark:` variant works too, but results in much larger output CSS when every colour has a `dark:` counterpart.

3. **Runtime theming.** If users can choose a colour theme (not a use case for any of our current products, but a common requirement), CSS variables allow runtime changes without a JavaScript-driven class swap on every element.

## The limitation: Tailwind opacity modifiers

Tailwind's opacity modifiers (`bg-accent/50` for 50% opacity) don't work with CSS variables that resolve to hex values. The modifier works by appending an alpha channel to the value using colour function syntax.

```css
/* Works */
.bg-blue-500/50 { background-color: rgb(59 130 246 / 0.5); }

/* Doesn't work — CSS can't append alpha to a var() that resolves to hex */
.bg-accent/50 { background-color: rgb(var(--color-accent) / 0.5); }
```

The fix: define CSS variables in RGB channel format, not hex:

```css
:root {
  --color-accent-rgb: 200 245 12; /* Space-separated, no commas */
}
```

Then in `tailwind.config.ts`:

```ts
colors: {
  accent: 'rgb(var(--color-accent-rgb))',
}
```

Now `bg-accent/50` resolves to `rgb(200 245 12 / 0.5)` and works correctly.

We use this pattern for the main accent colour. For derived colours like `accent-dim` and `accent-border`, we define them as full `rgba()` values in CSS because the opacity is fixed.

## The result

Shared components, shared design system, per-product personality. A status badge, a button, a loading spinner written once and deployed to three products — each with the correct accent colour, dark surface, and type treatment for that product's brand.

The shared npm package that the three products import (`@construx/ui`) contains the components and the shared `tailwind.config.ts`. Each product's CSS provides the accent variable. The system works.
