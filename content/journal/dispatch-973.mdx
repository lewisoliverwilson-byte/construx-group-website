title: "Boundary: identity-based access to infrastructure without static credentials"
date: "2032-12-11"
excerpt: "HashiCorp Boundary is a zero-trust access proxy that brokers connections to infrastructure (SSH, RDP, databases, Kubernetes) based on identity — no SSH keys, no VPN, no static credentials shared across teams. Users authenticate via their identity provider (Okta, GitHub, Azure AD), and Boundary issues short-lived, audited sessions to the specific target they're authorized to reach. The key design: targets are defined by address and type (TCP, SSH, database), sessions are logged with full metadata, and credentials are injected from Vault at session start so users never see the actual password. It's the operational security primitive that sits between IAM and the actual connection."

Identity-based access. Session brokering. Vault credential injection. Full audit log.

## Core concepts and setup

```bash
# Boundary components:
# - Controller:   hosts the API, policy engine, and session database
# - Worker:       proxies the actual network connections (placed near targets)
# - Target:       an endpoint (SSH host, database, Kubernetes API)
# - Host catalog: group of targets (dynamic: AWS instance discovery, static: IPs)
# - Auth method:  OIDC (Okta, GitHub, Azure AD), LDAP, or username/password

# Install Boundary CLI
brew tap hashicorp/tap
brew install hashicorp/tap/boundary
boundary version
# Boundary v0.17.1

# HCP Boundary (managed) or self-hosted
export BOUNDARY_ADDR=https://d1234567890.boundary.hashicorp.cloud

# Authenticate via OIDC (opens browser)
boundary authenticate oidc \
  --auth-method-id amoidc_1234567890

# List available targets (what you have access to)
boundary targets list -scope-id global -recursive

# Connect to an SSH target (Boundary handles the session proxy)
boundary connect ssh \
  --target-id tssh_1234567890 \
  -- -l ubuntu -p 22

# Connect to a Postgres database target
boundary connect postgres \
  --target-id ttcp_1234567890 \
  --dbname construx_prod \
  -- -c "SELECT count(*) FROM orders;"

# Connect to any TCP target (Boundary proxies the TCP connection)
boundary connect \
  --target-id ttcp_0987654321 \
  --listen-port 5432
# Opens local port 5432 → proxied through Boundary → target Postgres
```

## Terraform configuration

```hcl
# boundary.tf — define targets, roles, and grants with Terraform

terraform {
  required_providers {
    boundary = {
      source  = "hashicorp/boundary"
      version = "~> 1.1"
    }
  }
}

provider "boundary" {
  addr             = "https://d1234567890.boundary.hashicorp.cloud"
  auth_method_id   = var.boundary_auth_method_id
  password_auth_method_login_name = var.boundary_login
  password_auth_method_password   = var.boundary_password
}

# Scope: organizational unit (project or environment)
resource "boundary_scope" "construx_prod" {
  name                     = "construx-prod"
  description              = "Production environment"
  scope_id                 = "global"
  auto_create_admin_role   = true
  auto_create_default_role = true
}

# Static host catalog: explicitly defined hosts
resource "boundary_host_catalog_static" "prod_hosts" {
  name        = "construx-prod-hosts"
  description = "Production infrastructure"
  scope_id    = boundary_scope.construx_prod.id
}

resource "boundary_host_static" "api_server" {
  name            = "api-01"
  host_catalog_id = boundary_host_catalog_static.prod_hosts.id
  address         = "10.0.1.10"
}

resource "boundary_host_static" "postgres" {
  name            = "postgres-primary"
  host_catalog_id = boundary_host_catalog_static.prod_hosts.id
  address         = "10.0.2.10"
}

# Target: SSH access to the API server
resource "boundary_target" "api_ssh" {
  type                     = "ssh"
  name                     = "api-01-ssh"
  scope_id                 = boundary_scope.construx_prod.id
  session_max_seconds      = 3600   # 1 hour max session
  session_connection_limit = 1      # one connection per session

  host_source_ids = [
    boundary_host_set_static.api_servers.id
  ]

  # Vault credential injection: Boundary fetches SSH creds from Vault
  injected_application_credential_source_ids = [
    boundary_credential_library_vault_ssh_certificate.api_ssh.id
  ]
}

# Target: database access via TCP proxy
resource "boundary_target" "postgres" {
  type                     = "tcp"
  name                     = "postgres-primary"
  scope_id                 = boundary_scope.construx_prod.id
  default_port             = 5432
  session_max_seconds      = 1800   # 30 minute max session

  host_source_ids = [
    boundary_host_set_static.databases.id
  ]

  brokered_credential_source_ids = [
    boundary_credential_library_vault.postgres_creds.id
  ]
}
```

## Vault credential injection

```hcl
# Vault integration: Boundary fetches credentials from Vault at session start
# Users never see the actual credentials

# Vault credential store (connects Boundary to Vault)
resource "boundary_credential_store_vault" "construx" {
  name      = "construx-vault"
  scope_id  = boundary_scope.construx_prod.id
  address   = "https://vault.construx.io"
  token     = var.vault_boundary_token   # Vault token with limited permissions
  namespace = "construx"
}

# Vault credential library: SSH certificate (Vault signs the SSH key)
resource "boundary_credential_library_vault_ssh_certificate" "api_ssh" {
  name                = "api-ssh-cert"
  description         = "Vault-signed SSH certificates for API servers"
  credential_store_id = boundary_credential_store_vault.construx.id
  path                = "ssh/sign/construx-api-role"
  username            = "ubuntu"
  key_type            = "ed25519"
  ttl                 = "30m"
  extensions          = { permit-pty = "" }
}

# Vault credential library: Postgres dynamic credentials
resource "boundary_credential_library_vault" "postgres_creds" {
  name                = "postgres-dynamic-creds"
  credential_store_id = boundary_credential_store_vault.construx.id
  path                = "database/creds/construx-readonly"
  http_method         = "GET"
  credential_type     = "username_password"
}

# Session flow:
# 1. User: boundary connect postgres --target-id ttcp_...
# 2. Boundary: verifies user's identity and role grants
# 3. Boundary: requests dynamic credentials from Vault database engine
# 4. Vault: creates ephemeral Postgres user (valid for 30 minutes)
# 5. Boundary: brokers the connection, injects credentials
# 6. User: gets a psql prompt — never sees the password
# 7. Session ends: Vault revokes the ephemeral user automatically
```

## RBAC and grants

```hcl
# Role: engineers can connect to non-production targets
resource "boundary_role" "engineers" {
  name        = "engineers"
  description = "Read access and connections to non-production"
  scope_id    = boundary_scope.construx_prod.id

  # Grant set: what this role can do
  grant_strings = [
    "ids=*;type=target;actions=list,no-op",
    "ids=${boundary_target.staging_ssh.id};type=target;actions=authorize-session",
    "ids=${boundary_target.staging_postgres.id};type=target;actions=authorize-session",
  ]

  # Who gets this role (OIDC group from Okta)
  principal_ids = [
    boundary_group.engineers.id,
  ]
}

# Role: database administrators get production DB access
resource "boundary_role" "dba" {
  name        = "dba"
  scope_id    = boundary_scope.construx_prod.id

  grant_strings = [
    "ids=*;type=target;actions=list,no-op",
    "ids=${boundary_target.postgres.id};type=target;actions=authorize-session",
  ]

  principal_ids = [
    boundary_group.dba.id,
  ]
}
```

Boundary vs bastion hosts vs VPN: bastion hosts are the traditional model — an SSH jump server that everyone authenticates to, and then lateral-moves to internal hosts. The problem: broad network access, shared credentials, no per-session audit trail. VPN is similar — once connected, you have broad network access to internal resources. Boundary is identity-based: each session is authorized individually, credentials are ephemeral (Vault injection), and every connection is audited. The tradeoff: more infrastructure to operate (controller + workers), and a learning curve for teams used to SSH + bastion. The value: eliminates shared SSH keys, enables least-privilege access per session, and produces an audit trail that satisfies compliance requirements without the overhead of PAM solutions.
