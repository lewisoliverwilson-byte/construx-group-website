Rate limiting is one of those things that feels optional until someone discovers your AI endpoint costs $0.02 per call and hammers it ten thousand times. By then the damage is done.

The standard advice is Redis with a sliding window. Redis is fast, atomic, and purpose-built for this. It's also another dependency, another connection pool, another thing to monitor. For products that don't already have Redis in the stack, there's a simpler path.

## The sliding window

A sliding window rate limiter counts requests in a rolling time window. If you allow 20 requests per minute per user, you look at the last 60 seconds of requests for that user and reject if the count is at or above 20.

The naive implementation is a database table of request timestamps, queried on each request. That's one DB read per request, which is acceptable for protected endpoints — you're already doing a DB read for auth.

## The schema

```sql
CREATE TABLE rate_limit_requests (
  id          BIGSERIAL PRIMARY KEY,
  key         TEXT NOT NULL,         -- identifier: userId, IP, or composite
  endpoint    TEXT NOT NULL,         -- which endpoint/operation
  requested_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Index for the query pattern: key + endpoint + time range
CREATE INDEX idx_rate_limit_lookup
  ON rate_limit_requests (key, endpoint, requested_at DESC);

-- Cleanup old records: rows older than 24h are never needed
CREATE INDEX idx_rate_limit_cleanup
  ON rate_limit_requests (requested_at)
  WHERE requested_at < NOW() - INTERVAL '24 hours';
```

## The rate limiter

```ts
// lib/rate-limit.ts
import { db } from '@/lib/db';
import { sql } from 'drizzle-orm';

interface RateLimitConfig {
  limit: number;       // max requests
  windowMs: number;    // time window in milliseconds
}

interface RateLimitResult {
  success: boolean;
  remaining: number;
  resetAt: Date;
}

export async function checkRateLimit(
  key: string,
  endpoint: string,
  config: RateLimitConfig,
): Promise<RateLimitResult> {
  const windowStart = new Date(Date.now() - config.windowMs);
  const windowEnd = new Date(Date.now() + config.windowMs);

  // Count existing requests and insert the new one atomically
  // Using a CTE so count and insert happen in one round trip
  const result = await db.execute(sql`
    WITH inserted AS (
      INSERT INTO rate_limit_requests (key, endpoint)
      VALUES (${key}, ${endpoint})
      RETURNING requested_at
    ),
    window_count AS (
      SELECT COUNT(*) as count
      FROM rate_limit_requests
      WHERE key = ${key}
        AND endpoint = ${endpoint}
        AND requested_at > ${windowStart}
    )
    SELECT
      (SELECT count FROM window_count)::int as count,
      (SELECT requested_at FROM inserted) as requested_at
  `);

  const count = result.rows[0].count as number;
  const remaining = Math.max(0, config.limit - count);
  const resetAt = windowEnd;

  if (count > config.limit) {
    // Request was inserted but over limit — delete it
    await db.execute(sql`
      DELETE FROM rate_limit_requests
      WHERE key = ${key}
        AND endpoint = ${endpoint}
        AND requested_at = (SELECT MAX(requested_at) FROM rate_limit_requests WHERE key = ${key} AND endpoint = ${endpoint})
    `);
    return { success: false, remaining: 0, resetAt };
  }

  return { success: true, remaining, resetAt };
}
```

The CTE approach avoids two separate round trips for count + insert. The delete-on-over-limit keeps the table clean.

## Usage in route handlers

```ts
// app/api/ai/enrich/route.ts
import { checkRateLimit } from '@/lib/rate-limit';
import { getSession } from '@/lib/auth';

const ENRICH_RATE_LIMIT = {
  limit: 10,           // 10 requests
  windowMs: 60_000,    // per minute
};

export async function POST(req: Request) {
  const session = await getSession();
  if (!session) return new Response('Unauthorized', { status: 401 });

  const rateLimit = await checkRateLimit(
    session.userId,
    'ai-enrich',
    ENRICH_RATE_LIMIT,
  );

  if (!rateLimit.success) {
    return new Response('Rate limit exceeded', {
      status: 429,
      headers: {
        'Retry-After': String(Math.ceil((rateLimit.resetAt.getTime() - Date.now()) / 1000)),
        'X-RateLimit-Remaining': '0',
        'X-RateLimit-Reset': rateLimit.resetAt.toISOString(),
      },
    });
  }

  // Proceed with the expensive operation
  const { asin } = await req.json();
  const result = await runAiEnrichment(asin);

  return Response.json(result, {
    headers: {
      'X-RateLimit-Remaining': String(rateLimit.remaining),
      'X-RateLimit-Reset': rateLimit.resetAt.toISOString(),
    },
  });
}
```

The `Retry-After` header tells clients how long to wait. Well-behaved API clients respect it.

## Unauthenticated endpoints: IP-based limiting

For endpoints that don't require auth (like a public price check), key by IP:

```ts
function getClientIp(req: Request): string {
  // Amplify/CloudFront sets this header
  const cfIp = req.headers.get('cloudfront-viewer-address');
  if (cfIp) return cfIp.split(':')[0];

  // Fallback for local dev
  return req.headers.get('x-forwarded-for')?.split(',')[0] ?? '127.0.0.1';
}

export async function GET(req: Request) {
  const ip = getClientIp(req);

  const rateLimit = await checkRateLimit(ip, 'public-price-check', {
    limit: 30,
    windowMs: 60_000,
  });

  if (!rateLimit.success) {
    return new Response('Rate limit exceeded', { status: 429 });
  }

  // ...
}
```

IP-based limiting is weaker than user-based — IPs can be shared (corporate NAT, VPNs) or cycled (bot nets). Use it as a first line of defence for public endpoints, not as a primary abuse prevention mechanism.

## Cleanup job

Without cleanup, the `rate_limit_requests` table grows unbounded. A nightly cleanup job is sufficient:

```ts
// app/api/cron/cleanup-rate-limits/route.ts
// Called by Amplify scheduled rules or a cron service

export async function GET(req: Request) {
  const authHeader = req.headers.get('authorization');
  if (authHeader !== `Bearer ${process.env.CRON_SECRET}`) {
    return new Response('Unauthorized', { status: 401 });
  }

  const cutoff = new Date(Date.now() - 24 * 60 * 60 * 1000);

  const result = await db.execute(sql`
    DELETE FROM rate_limit_requests
    WHERE requested_at < ${cutoff}
  `);

  return Response.json({ deleted: result.rowCount });
}
```

## When to upgrade to Redis

This approach works until it doesn't. The limits:

- **Write-heavy endpoints**: If you're rate limiting something called thousands of times per second, the DB writes become a bottleneck. Redis handles this at a fraction of the latency.
- **Distributed state across processes**: This works fine on Amplify (Lambda per request, shared DB). If you have long-running servers with local caches, the distributed state is harder to reason about.
- **Precise guarantees**: The CTE approach has a small race window. For most products, "approximately 10 requests per minute" is fine. If you need exact guarantees, Redis's `INCR` with `EXPIRE` is atomic.

For products under a few million requests per day, the database approach is enough. Add Redis when the query latency shows up in your p99s.
