The hardest problem in early-stage product isn't building features — it's getting users to discover the features that matter. You can see it in the analytics: users sign up, poke around the homepage, never go deeper, and churn within a week.

This is an information architecture problem, not a feature problem. The fix is in how you surface what exists, not in what you add.

## Empty states are feature discovery opportunities

The first time a user opens Scoutr's scan history, it's empty. The worst thing you can do with an empty state is show nothing or a generic "no items" message.

The best thing: use the empty state to demonstrate the feature.

```tsx
// ✗ Useless empty state
{scans.length === 0 && (
  <div className="text-center py-12 text-text-muted">
    No scans yet. Start scanning products.
  </div>
)}

// ✓ Empty state that demonstrates the feature
{scans.length === 0 && (
  <div className="py-12 text-center">
    <p className="font-mono text-[10px] uppercase tracking-widest text-text-dim mb-3">
      // SCAN.HISTORY EMPTY
    </p>
    <p className="text-sm text-text-muted mb-6 max-w-sm mx-auto">
      Paste any Amazon or eBay product URL to get your first margin analysis.
      Results appear here.
    </p>
    <div className="font-mono text-[11px] bg-subtle border border-border rounded p-4 text-left max-w-sm mx-auto">
      <span className="text-text-dim">Try: </span>
      <button
        onClick={() => fillExampleUrl('https://www.amazon.co.uk/...')}
        className="text-construx underline"
      >
        amazon.co.uk/Blue-Wireless-Headphones...
      </button>
    </div>
    <Link href="/scan" className="mt-4 inline-block btn-primary">
      Start first scan
    </Link>
  </div>
)}
```

The empty state does three things: explains what the feature does, gives an example to lower the action cost, and provides a direct CTA.

## Contextual tooltips on first visit

Some features aren't discoverable through the UI alone — you have to know to look for them. For these, we show a brief tooltip on first visit, keyed to a `localStorage` flag:

```tsx
'use client';

import { useEffect, useState } from 'react';

function FirstVisitHint({ id, children, hint }: {
  id: string;
  children: React.ReactNode;
  hint: string;
}) {
  const [showHint, setShowHint] = useState(false);

  useEffect(() => {
    const seen = localStorage.getItem(`hint:${id}`);
    if (!seen) {
      setShowHint(true);
      // Don't show again
      localStorage.setItem(`hint:${id}`, '1');
    }
  }, [id]);

  return (
    <div className="relative">
      {children}
      {showHint && (
        <div
          className="absolute z-50 bottom-full left-0 mb-2 px-3 py-2 font-mono text-[10px] text-white bg-construx"
          style={{ borderRadius: '3px', maxWidth: '220px' }}
        >
          {hint}
          <button
            onClick={() => setShowHint(false)}
            className="ml-2 opacity-70 hover:opacity-100"
          >
            ✕
          </button>
        </div>
      )}
    </div>
  );
}

// Usage
<FirstVisitHint
  id="bulk-scan"
  hint="Scan multiple products at once — paste URLs separated by newlines."
>
  <BulkScanButton />
</FirstVisitHint>
```

First-visit hints are shown once. They're not a tour, not a modal — just a contextual note at the right moment.

## Progressive disclosure

Don't show advanced features to new users. Show them the core action.

In Scoutr, the core action is: paste a URL, get a margin. The batch scan, the portfolio tracker, the historical comparison — these are all more powerful but also more complex. New users get the simple interface. Advanced features appear as they use the product.

The pattern: hide controls behind a "More options" expansion, or show them only after the user has completed the primary action several times:

```tsx
const scanCount = useScanCount();  // from database

// Only show advanced options after 5 scans
const showAdvancedOptions = scanCount >= 5;

return (
  <>
    <ScanInput />
    {showAdvancedOptions && (
      <details className="mt-3">
        <summary className="font-mono text-[10px] text-text-dim cursor-pointer uppercase tracking-widest">
          Advanced options
        </summary>
        <AdvancedScanOptions />
      </details>
    )}
  </>
);
```

## Completion triggers

Some features are best discovered at the moment they become relevant. After a user completes their first scan, they see the next logical step:

```tsx
{scanCompleted && (
  <div className="mt-6 p-4 border border-construx/20 bg-construx/5">
    <p className="font-mono text-[10px] uppercase tracking-widest text-text-dim mb-2">
      // NEXT.STEP
    </p>
    <p className="text-sm text-text-muted mb-3">
      Add this product to a portfolio to track its margin over time.
    </p>
    <button className="btn-secondary text-sm">
      Save to portfolio →
    </button>
  </div>
)}
```

The completion trigger fires when the user has context — they just saw the margin analysis, so "track over time" means something to them. Showing this in an onboarding flow before they've seen the core feature doesn't land the same way.

## What we measure

Feature discovery effectiveness shows up in funnel analytics:
- Users who scan → users who batch scan (did they discover batch scan?)
- Users who view a scan → users who save to portfolio (did they discover portfolios?)
- Users who sign up → users who use a second feature (did they get past the first thing they tried?)

Each of these dropoffs is a discovery failure. The question is: at the moment the user was ready to go deeper, was the next action visible?

For Scoutr, we improved the "scan → batch scan" conversion rate by 40% by adding a hint on the scan input that said "You can paste multiple URLs." The feature existed. Users didn't know it existed.
