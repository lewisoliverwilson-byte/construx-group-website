You tell it the last known good commit and the first known bad commit; it checks out the commit halfway between them. You test it, mark it good or bad, and git bisect narrows the range. Binary search through history. N commits → log₂(N) steps.

## Manual bisect

```bash
# Start a bisect session
git bisect start

# Mark current HEAD as bad (has the bug)
git bisect bad HEAD

# Mark the last known good commit (or tag)
git bisect good v2.4.0

# Git checks out the midpoint commit:
# Bisecting: 23 revisions left to test after this (roughly 5 steps)
# [4e9c8b2] feat: add order validation middleware

# Test the current commit — run your test suite, check the bug, etc.
bun test orders.test.ts

# Mark the result
git bisect bad    # or: git bisect good

# Repeat until git reports:
# c1e6f9b is the first bad commit
# commit c1e6f9b
# Author: Lewis Wilson <lewis@construxgroup.io>
# Date:   Mon Sep 15 16:42:07 2031 +0000
#     fix: correct window calculation in sliding rate limit
```

## Automated bisect — script mode

```bash
# Write a test script that exits 0 for good, 1 for bad
cat > /tmp/test.sh << 'EOF'
#!/bin/bash
# Install deps silently, run the specific failing test
bun install --silent 2>/dev/null
bun test orders.test.ts --test-name-pattern='checkRateLimit' --reporter=min 2>&1
if [ $? -eq 0 ]; then exit 0; else exit 1; fi
EOF
chmod +x /tmp/test.sh

git bisect start
git bisect bad HEAD
git bisect good v2.4.0

# Let git bisect run the script automatically — no manual intervention
git bisect run /tmp/test.sh

# After N steps, git reports the first bad commit and stops

# Clean up
git bisect reset
```

## Bisect with a build step

```bash
# The test script handles the full lifecycle
cat > /tmp/bisect-test.sh << 'EOF'
#!/bin/bash
set -e

# Some commits may not build — treat build failure as "skip"
bun install --silent 2>/dev/null || exit 125

# Build might fail on broken intermediate commits
bun run build 2>/dev/null || exit 125

# Run the specific test
bun test --test-name-pattern='checkRateLimit' 2>&1
EOF
```

Exit code `125` tells git bisect to skip the current commit (can't test it) and move to the next one.

## Skip commits you can't test

```bash
# Skip a specific commit (e.g., broken build, unrelated test failures)
git bisect skip

# Skip a range
git bisect skip v2.5.0..v2.5.2

# Skip multiple commits at once
git bisect skip c1e6f9b 4e9c8b2
```

## Bisect log — save and replay

```bash
# Save the bisect session to a file
git bisect log > bisect.log

# View the log to understand what happened
cat bisect.log

# Replay a bisect session (useful for debugging the bisect itself)
git bisect replay bisect.log
```

## Visualise the bisect

```bash
# See which commits are still candidates (marked with ?)
git bisect visualize --oneline
# 4e9c8b2 (bad) feat: add order validation middleware
# 7f2d5a1 (good) refactor: extract rate limit logic to middleware
# c1e6f9b (bad) fix: correct window calculation in sliding rate limit
# 2a8d4c7 (bad) feat: pipeline redis commands for rate limit check

# Show bisect state
git bisect view
```

git bisect vs manually checking commits: for 100 commits, manual checking averages 50 attempts. git bisect needs 7. For 1,000 commits: manual is 500, bisect is 10. The efficiency gain makes it worth wiring into CI — a bisect script that runs automatically on regression detection can find the culprit commit before the developer even opens their laptop.
