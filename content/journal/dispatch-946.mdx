title: "cloudflared: Argo Tunnel for zero-trust ingress without inbound firewall rules"
date: "2032-09-21"
excerpt: "cloudflared is the client daemon for Cloudflare Tunnel (formerly Argo Tunnel) — it creates an outbound-only encrypted connection from your server to Cloudflare's edge, then routes public traffic through that tunnel to your service. No inbound firewall rules, no exposed ports, no public IP required. The tunnel is authenticated to your Cloudflare account; traffic is zero-trust: you can put Cloudflare Access (identity-aware proxy) in front of any tunnel, requiring SSO login before requests reach your service. cloudflared also runs as a forward proxy (for outbound traffic) and supports WARP routing for private network access. The `cloudflared tunnel run` daemon maintains multiple redundant connections to the Cloudflare edge across two data centers for resilience."

Outbound-only. No open ports. Zero-trust with Cloudflare Access. Four redundant connections.

## Creating and routing a tunnel

```bash
# cloudflared: authenticate to Cloudflare (opens browser)
cloudflared tunnel login
# Credentials saved to ~/.cloudflared/cert.pem

# Create a named tunnel
cloudflared tunnel create construx-prod
# Tunnel credentials written to ~/.cloudflared/abc123-construx-prod.json
# Created tunnel construx-prod with id abc123-4567-...

# Route a hostname to the tunnel (DNS CNAME → tunnel)
cloudflared tunnel route dns construx-prod api.construx.io
# Added CNAME api.construx.io → abc123-4567-....cfargotunnel.com

# Run the tunnel (routes traffic to localhost:8080)
cloudflared tunnel run --url http://localhost:8080 construx-prod

# Or using a config file:
cat ~/.cloudflared/config.yaml
# tunnel: abc123-4567-...
# credentials-file: /home/construx/.cloudflared/abc123-construx-prod.json
# ingress:
#   - hostname: api.construx.io
#     service: http://localhost:8080
#   - hostname: metrics.construx.io
#     service: http://localhost:9090
#   - service: http_status:404   # catch-all

cloudflared tunnel run construx-prod

# Tunnel status and connections (4 redundant connections to Cloudflare edge)
cloudflared tunnel info construx-prod
# NAME            ID                                    CREATED           CONNECTIONS
# construx-prod   abc123-4567-89ab-cdef-012345678901   2032-09-01 ...
#   ├── conn 0: fra06 (Frankfurt)  latency: 4.2ms  ✓
#   ├── conn 1: fra06 (Frankfurt)  latency: 4.8ms  ✓
#   ├── conn 2: ams09 (Amsterdam)  latency: 9.1ms  ✓
#   └── conn 3: ams09 (Amsterdam)  latency: 9.4ms  ✓
```

## Running as a systemd service

```bash
# Install as systemd service
cloudflared service install

# /etc/systemd/system/cloudflared.service
# [Unit]
# Description=Cloudflare Tunnel
# After=network.target
#
# [Service]
# TimeoutStartSec=0
# Type=notify
# ExecStart=/usr/bin/cloudflared tunnel run construx-prod
# Restart=on-failure
# RestartSec=5s
# User=cloudflared
# NoNewPrivileges=true
# PrivateTmp=true

systemctl enable cloudflared
systemctl start cloudflared
systemctl status cloudflared

# Metrics: cloudflared exposes Prometheus metrics at :2000/metrics
curl http://localhost:2000/metrics | grep cloudflared_tunnel_
# cloudflared_tunnel_total_requests_with_status{status_code="200"} 48291
# cloudflared_tunnel_timer_response_seconds_bucket{...} ...
# cloudflared_tunnel_ha_connections 4
```

## Cloudflare Access: zero-trust auth in front of the tunnel

```bash
# Cloudflare Access: put identity authentication in front of any tunnel route
# Users must authenticate (SSO, GitHub, Google, OTP) before reaching the service
# All traffic is authorized at the edge — your service only sees authenticated requests

# Access policy (configured via Cloudflare dashboard or Terraform):
# Rule: allow if email matches @construx.io
#   OR allow if GitHub org = construx

# cloudflared also sets cf-access-jwt-assertion header on every request
# Your service can validate this JWT to verify the user identity

# Verify the Access JWT in Go:
# certs := "https://construx.cloudflareaccess.com/cdn-cgi/access/certs"
# token := r.Header.Get("cf-access-jwt-assertion")
# ParseAndValidate(token, certs)  // uses Cloudflare's JWKS endpoint

# Service tokens: for machine-to-machine access (no browser auth)
cloudflared access token --app-url https://metrics.construx.io
# CF_Access_Client_Id + CF_Access_Client_Secret headers
```

## SSH and TCP tunnels

```bash
# SSH over Cloudflare Tunnel — no public SSH port required
# Server: expose SSH via tunnel (short-lived cert, no firewall rule)
cloudflared tunnel run --url ssh://localhost:22 construx-prod-ssh

# Client: proxy SSH through cloudflared
cat ~/.ssh/config
# Host construx-prod
#   HostName prod.construx.io
#   ProxyCommand /usr/bin/cloudflared access ssh --hostname %h
#   User construx
#   IdentityFile ~/.ssh/id_ed25519

ssh construx-prod   # SSH session over the tunnel — no open port 22

# Browser-based SSH (Cloudflare Access SSH)
# Users authenticate via SSO → browser terminal → cloudflared → SSH daemon
# No SSH client or keys needed on the client side

# TCP tunnel: expose any TCP service (database, Redis, gRPC)
# (Requires Cloudflare Access for auth)
cloudflared access tcp --hostname redis.construx.io --url localhost:6379

# Connect from client (proxies local port through Access-authenticated tunnel)
cloudflared access tcp --hostname redis.construx.io --url localhost:16379 &
redis-cli -p 16379   # connects to remote Redis through Cloudflare tunnel
```

## Kubernetes ingress with cloudflared

```bash
# cloudflared in Kubernetes: deploy as a Deployment with 2+ replicas
# Each replica maintains 4 connections = 8+ redundant paths to Cloudflare edge

cat cloudflared-deployment.yaml
# apiVersion: apps/v1
# kind: Deployment
# metadata:
#   name: cloudflared
#   namespace: construx
# spec:
#   replicas: 2
#   selector:
#     matchLabels:
#       app: cloudflared
#   template:
#     spec:
#       containers:
#         - name: cloudflared
#           image: cloudflare/cloudflared:latest
#           args: ["tunnel", "run"]
#           env:
#             - name: TUNNEL_TOKEN
#               valueFrom:
#                 secretKeyRef:
#                   name: cloudflared-token
#                   key: token

kubectl apply -f cloudflared-deployment.yaml
kubectl rollout status deployment/cloudflared -n construx

# Check connections (8 total from 2 replicas × 4 each)
kubectl logs -l app=cloudflared -n construx | grep "Registered tunnel connection"
# Registered tunnel connection  connIndex=0  location=fra06
# Registered tunnel connection  connIndex=1  location=ams09
# ... (× 2 replicas)
```

cloudflared vs nginx Ingress vs AWS ALB: nginx Ingress and ALB require a public IP and open inbound ports — they are the traditional approach. cloudflared flips the model: your servers make outbound connections to Cloudflare, which proxy inbound traffic. This means no open ports, no IP exposure, and DDoS protection at the Cloudflare edge before traffic reaches your infra. The trade-off: you are dependent on Cloudflare's network, and the free tier has rate limits. The practical use case: cloudflared is ideal for exposing services in environments where inbound firewall rules are difficult (home labs, corporate networks, air-gapped infrastructure), for securing internal tools with Cloudflare Access, and for SSH and database tunnels that replace bastion hosts. For high-traffic production services, a traditional load balancer gives you more control over routing logic and pricing.
