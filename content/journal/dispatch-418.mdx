A PostgreSQL database has a `max_connections` limit — typically 100 on a small instance. Each connection consumes ~5-10MB of RAM. In a traditional server setup, you have a connection pool shared across all requests. In a serverless setup, you potentially have hundreds of function instances, each opening its own connection.

At 200 concurrent Lambda invocations, you've saturated a 100-connection database. New connections start failing with `too many connections`.

## Why serverless is different

```
Traditional server:
  App process → Connection pool (10-20 connections) → Database

Serverless:
  Request 1 → Lambda instance A → Connection → Database
  Request 2 → Lambda instance B → Connection → Database
  Request 3 → Lambda instance C → Connection → Database
  ...
  Request 101 → Lambda instance D → ❌ too many connections
```

A Lambda function spins up in milliseconds, opens a connection, handles the request, and might be destroyed or kept alive. The connection lifecycle is unpredictable. You can't rely on a persistent pool.

## Solution 1: Neon with serverless driver

Neon's serverless PostgreSQL sends queries over HTTP rather than a persistent TCP connection. No connection to maintain:

```bash
npm install @neondatabase/serverless
```

```ts
// lib/db.ts
import { neon } from '@neondatabase/serverless';
import { drizzle } from 'drizzle-orm/neon-http';
import * as schema from '@/db/schema';

const sql = neon(process.env.DATABASE_URL!);
export const db = drizzle(sql, { schema });
```

Each query is an HTTP request. No connection pool, no connection limits, no warm-up overhead. The tradeoff: no transactions across multiple queries, no streaming, slightly higher latency per query (~2-5ms overhead vs persistent TCP).

For transactions, Neon offers a WebSocket-based driver:

```ts
// lib/db.ts — with transaction support
import { Pool, neonConfig } from '@neondatabase/serverless';
import { drizzle } from 'drizzle-orm/neon-serverless';
import ws from 'ws';

neonConfig.webSocketConstructor = ws;

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
export const db = drizzle({ client: pool, schema });
```

## Solution 2: PgBouncer

PgBouncer is a connection pooler that sits between your app and PostgreSQL. Your app connects to PgBouncer (which allows thousands of connections), and PgBouncer maintains a small pool to the actual database:

```
Lambda instances (100+) → PgBouncer → Database (10-20 connections)
```

Neon, Supabase, and PlanetScale all offer built-in PgBouncer. For self-hosted PostgreSQL on RDS or a VPS, you run PgBouncer yourself.

### PgBouncer modes

**Session mode** — one DB connection per client connection. Client connects, gets a DB connection, keeps it until disconnect. Good for: most apps. Supports all PostgreSQL features.

**Transaction mode** — DB connection assigned only during an active transaction. Highest connection multiplexing. Limitation: no `SET` commands, no advisory locks, prepared statements need configuration.

**Statement mode** — connection held only for the duration of one statement. Maximum multiplexing. Very limited use cases.

For serverless apps: transaction mode is the sweet spot. Most Drizzle queries don't need server-side state.

### PgBouncer config

```ini
; pgbouncer.ini
[databases]
app = host=your-postgres-host.us-east-1.rds.amazonaws.com port=5432 dbname=app

[pgbouncer]
listen_addr = 0.0.0.0
listen_port = 5432
auth_type = scram-sha-256
auth_file = /etc/pgbouncer/userlist.txt
pool_mode = transaction
default_pool_size = 20
max_client_conn = 1000
server_idle_timeout = 300
server_lifetime = 3600
```

Your app connects to PgBouncer at port 5432 (or 6432 by convention), and PgBouncer forwards to PostgreSQL.

## Solution 3: Prisma Accelerate / Drizzle with connection limit

If you're using Prisma or plain Drizzle with a traditional PostgreSQL driver, set a low connection limit:

```ts
// lib/db.ts — single connection per Lambda instance
import postgres from 'postgres';
import { drizzle } from 'drizzle-orm/postgres-js';

const client = postgres(process.env.DATABASE_URL!, {
  max: 1,          // single connection per Lambda instance
  idle_timeout: 20, // close idle connection after 20s
  connect_timeout: 10,
});

export const db = drizzle(client, { schema });
```

This doesn't solve the horizontal scaling problem — if you have 100 Lambda instances, you still have 100 connections. But it prevents one instance from opening 10+ connections.

## Monitoring

Watch `numbackends` in PostgreSQL:

```sql
SELECT count(*), state
FROM pg_stat_activity
WHERE datname = 'app'
GROUP BY state;
```

Or in your monitoring setup, alert when:
- `pg_stat_activity.count` > 80% of `max_connections`
- Connection wait time spikes (means pool is saturated)

## The practical recommendation

| Setup | Use |
|---|---|
| Neon serverless | First choice for Vercel/serverless. No pooling needed. |
| Supabase (has built-in Supavisor) | Second choice. Same HTTP approach. |
| RDS + PgBouncer | Self-hosted. Run PgBouncer on same VPC as RDS. |
| PlanetScale (MySQL) | If MySQL is acceptable. |

The pattern: HTTP-based databases (Neon, Supabase) remove the problem entirely. For traditional PostgreSQL, connection pooling isn't optional — it's table stakes for production.
