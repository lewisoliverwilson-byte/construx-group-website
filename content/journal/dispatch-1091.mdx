date: "2033-11-30"
excerpt: "Hubble is Cilium's eBPF-powered network observability platform. While Cilium handles networking and policy enforcement at the eBPF layer, Hubble adds visibility: it captures every network flow (source pod, destination pod, destination port, protocol, L7 method/status, verdict — allowed or dropped) without any application-side changes or sidecar proxies. The Hubble relay aggregates flow data from all nodes in the cluster and exposes it via a gRPC API. The Hubble UI renders a real-time service dependency map: which pods are talking to which, at what rate, and what HTTP/gRPC status codes are being returned. The Hubble CLI provides flow inspection, filtering, and real-time watch. For compliance and incident response, Hubble's L7 flow log can reconstruct exactly which service made which HTTP call to which endpoint at what time — without any application-level logging or tracing instrumentation. Hubble integrates with Prometheus and Grafana: per-endpoint HTTP error rates, latency distributions, and DNS query counts are all surfaced as metrics. The key architectural point is that all of this runs in the kernel via eBPF — there is no userspace proxy, no iptables overhead, and no impact on application latency."

## Hubble CLI: flow inspection and policy audit

```bash
# Install Hubble CLI and port-forward to relay
cilium hubble port-forward &

# Real-time flow watch: all traffic in construx-prod namespace
hubble observe \
  --namespace construx-prod \
  --follow \
  --output json

# Sample output:
# {
#   "time": "2033-11-30T10:14:22Z",
#   "verdict": "FORWARDED",
#   "IP": { "source": "10.0.1.42", "destination": "10.0.2.17" },
#   "source": { "namespace": "construx-prod", "labels": ["app=orders-api"] },
#   "destination": { "namespace": "construx-prod", "labels": ["app=payments-service"] },
#   "l4": { "TCP": { "destination_port": 8080 } },
#   "l7": { "type": "REQUEST", "http": { "method": "POST", "url": "/api/v1/charge", "code": 200 } },
#   "Type": "L3_L4"
# }

# Filter: only dropped flows (policy violations)
hubble observe \
  --namespace construx-prod \
  --verdict DROPPED \
  --follow

# Filter: L7 HTTP errors from orders-api
hubble observe \
  --namespace construx-prod \
  --from-label app=orders-api \
  --protocol http \
  --http-status-code 5.. \
  --follow

# DNS flows: see which services are resolving what
hubble observe \
  --namespace construx-prod \
  --protocol dns \
  --follow
# orders-api → DNS: payment-service.construx-prod.svc.cluster.local → 10.0.2.17
# orders-api → DNS: kafka.construx-infra.svc.cluster.local → 10.0.5.3

# Service map: inspect which endpoints are communicating
hubble observe \
  --namespace construx-prod \
  --last 5m \
  --output table
# SOURCE                DESTINATION              PORT  PROTO  VERDICT  COUNT
# orders-api            payments-service         8080  TCP    FORWARD  14,392
# orders-api            nats.construx-infra      4222  TCP    FORWARD  8,847
# payments-service      stripe-webhook           443   TCP    FORWARD  1,204
# analytics-service     clickhouse.construx-db   9000  TCP    FORWARD  42,011
```

```yaml
# Hubble enables on Cilium installation
# values.yaml for the cilium Helm chart

hubble:
  enabled: true

  relay:
    enabled: true         # aggregates flows across all nodes
    replicas: 2

  ui:
    enabled: true         # real-time service map in browser
    replicas: 1

  metrics:
    enabled:
      - dns:query;ignoreAAAA        # DNS query counts per service
      - drop:sourceContext=pod      # dropped packets per source pod
      - tcp                         # TCP syn/rst rates
      - flow:sourceContext=workload;destinationContext=workload
      - http                        # HTTP request/response rates and latency
      - icmp
      - port-distribution
    serviceMonitor:
      enabled: true       # Prometheus ServiceMonitor for scraping

  tls:
    enabled: true
    auto:
      enabled: true
      method: certmanager
      certManagerIssuerRef:
        name: cluster-issuer
        kind: ClusterIssuer
```

```promql
# Hubble Prometheus metrics: HTTP error rates and flow counts

# HTTP error rate per workload pair (5xx from orders-api to payments-service)
rate(
  hubble_http_responses_total{
    source="construx-prod/orders-api",
    destination="construx-prod/payments-service",
    status=~"5.."
  }[5m]
) /
rate(
  hubble_http_requests_total{
    source="construx-prod/orders-api",
    destination="construx-prod/payments-service"
  }[5m]
)

# Dropped packet rate (Cilium NetworkPolicy denials)
sum by (source, direction, reason) (
  rate(hubble_drop_total[5m])
)

# P99 HTTP latency between services
histogram_quantile(0.99,
  sum by (source, destination, le) (
    rate(hubble_http_request_duration_seconds_bucket[5m])
  )
)

# DNS query failure rate per namespace
rate(hubble_dns_queries_total{rcode!="NOERROR"}[5m])
```

Hubble vs Jaeger/Tempo vs traditional service mesh observability vs tcpdump: Traditional distributed tracing (Jaeger, Tempo via OTel instrumentation) requires explicit instrumentation in every service — the developer adds spans, attributes, and context propagation. Hubble adds network-layer visibility without any code changes: it captures every TCP connection and every HTTP/gRPC request at the kernel level via eBPF, even if the service has zero instrumentation. tcpdump/tshark give you raw packet captures at the node level — useful for debugging but not aggregated, searchable, or correlated across services. Service mesh sidecars (Istio Envoy, Linkerd proxy) add L7 observability via userspace proxies — same coverage as Hubble for HTTP/gRPC but with ~10ms added latency per hop and significant CPU overhead from the proxy processes. Hubble's eBPF path adds sub-microsecond overhead. The production pattern is: Hubble for always-on L4/L7 network flow visibility and DNS observability (zero instrumentation required), OTel SDK for business-domain spans and metrics (dispatch-1089), and Pixie (dispatch-1084) for deeper ad-hoc kernel-level profiling.
