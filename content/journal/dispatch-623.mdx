WebRTC (Web Real-Time Communication) is a browser API for direct peer-to-peer connections. Audio, video, and arbitrary data can flow between browsers without a relay server. The tradeoff: setup requires a signalling mechanism, and NAT traversal (connecting peers behind firewalls) requires STUN/TURN servers.

## The three-phase setup

1. **Signalling**: peers exchange SDP (Session Description Protocol) offers/answers and ICE candidates through any mechanism — WebSocket, HTTP polling, even copy-paste
2. **ICE negotiation**: the browser finds the best network path between peers (direct, via STUN, or via TURN relay)
3. **DTLS handshake**: encrypted connection established; media/data flows

You implement phase 1 (signalling). The browser handles phases 2 and 3.

## Basic peer connection

```ts
// Peer A: create offer
const pcA = new RTCPeerConnection({
  iceServers: [
    { urls: 'stun:stun.l.google.com:19302' },  // Google's free STUN server
    {
      urls:       'turn:turn.construxgroup.io:3478',
      username:   process.env.TURN_USERNAME,
      credential: process.env.TURN_CREDENTIAL,
    },
  ],
});

// Collect ICE candidates and send via signalling
pcA.onicecandidate = ({ candidate }) => {
  if (candidate) signal.send({ type: 'ice', candidate });
};

// Create and send offer
const offer = await pcA.createOffer();
await pcA.setLocalDescription(offer);
signal.send({ type: 'offer', sdp: offer });

// Peer B: receive offer, create answer
const pcB = new RTCPeerConnection({ iceServers: [...] });

signal.on('offer', async ({ sdp }) => {
  await pcB.setRemoteDescription(sdp);
  const answer = await pcB.createAnswer();
  await pcB.setLocalDescription(answer);
  signal.send({ type: 'answer', sdp: answer });
});

// Peer A: receive answer
signal.on('answer', async ({ sdp }) => {
  await pcA.setRemoteDescription(sdp);
});

// Both sides: add remote ICE candidates
signal.on('ice', async ({ candidate }) => {
  await pcA.addIceCandidate(candidate);  // or pcB depending on which peer
});
```

## Video call

```ts
// Get user's camera and microphone
const localStream = await navigator.mediaDevices.getUserMedia({
  video: true,
  audio: true,
});

// Add tracks to the connection
for (const track of localStream.getTracks()) {
  pcA.addTrack(track, localStream);
}

// Display local video
const localVideo = document.getElementById('local') as HTMLVideoElement;
localVideo.srcObject = localStream;

// Peer B: receive remote tracks
pcB.ontrack = ({ streams }) => {
  const remoteVideo = document.getElementById('remote') as HTMLVideoElement;
  remoteVideo.srcObject = streams[0];
};
```

## Data channels

```ts
// Create a data channel (Peer A)
const channel = pcA.createDataChannel('chat', {
  ordered:    true,  // TCP-like ordering
  maxRetransmits: 3, // or use maxPacketLifeTime for UDP-like
});

channel.onopen  = () => console.log('Data channel open');
channel.onmessage = (e) => console.log('Received:', e.data);

// Send
channel.send('Hello from Peer A');
channel.send(JSON.stringify({ type: 'cursor', x: 100, y: 200 }));

// Peer B: receive the data channel
pcB.ondatachannel = ({ channel }) => {
  channel.onmessage = (e) => {
    console.log('Peer A says:', e.data);
    channel.send('Hello back!');
  };
};
```

Data channels work for file transfer, collaborative editing cursors, game state — anything you'd normally send over a WebSocket, but without the server in the middle.

## Signalling server

The signalling server routes messages between peers before the P2P connection is established:

```ts
// Simple WebSocket signalling server
const rooms = new Map<string, Set<WebSocket>>();

wss.on('connection', (ws, req) => {
  const roomId = new URL(req.url!, 'ws://localhost').searchParams.get('room')!;

  if (!rooms.has(roomId)) rooms.set(roomId, new Set());
  rooms.get(roomId)!.add(ws);

  ws.on('message', (data) => {
    // Broadcast to all other peers in the room
    for (const peer of rooms.get(roomId)!) {
      if (peer !== ws && peer.readyState === WebSocket.OPEN) {
        peer.send(data);
      }
    }
  });

  ws.on('close', () => {
    rooms.get(roomId)?.delete(ws);
  });
});
```

## STUN and TURN

**STUN** (Session Traversal Utilities for NAT): helps peers discover their public IP address. Used for peer-to-peer connections when both peers are behind NAT. Free Google STUN servers work for most cases.

**TURN** (Traversal Using Relays around NAT): a relay server that forwards data between peers when direct connection isn't possible (symmetric NAT, restrictive firewalls). Required for ~15-20% of connections. TURN servers cost money — you need to self-host or pay for a service (Twilio, Xirsys).

```ts
// coturn (self-hosted TURN server)
// turnserver.conf
listening-port=3478
tls-listening-port=5349
realm=construxgroup.io
user=construx:$(openssl rand -hex 32)
lt-cred-mech
```

## Browser APIs for screen sharing

```ts
// Screen share (desktop, window, or tab)
const screenStream = await navigator.mediaDevices.getDisplayMedia({
  video: { cursor: 'always' },
  audio: true,
});

// Replace video track in existing connection
const videoTrack = screenStream.getVideoTracks()[0];
const sender     = pcA.getSenders().find((s) => s.track?.kind === 'video');
sender?.replaceTrack(videoTrack);
```

WebRTC is complex to implement from scratch — most production applications use a library (simple-peer, PeerJS) or a platform (Daily, LiveKit, Agora) that handles signalling, TURN, and connection management.
