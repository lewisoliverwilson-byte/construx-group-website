The Hyve's document feature allows teams to create persistent shared documents alongside their communication channels. A task discussed in a channel can be documented in a linked doc. Meeting notes, specs, and decision records live in The Hyve rather than a separate tool.

Building a document editor is non-trivial. The question was: use an existing rich text editor library or build something minimal from scratch?

## The libraries we evaluated

**Tiptap** is a headless rich text editor built on top of ProseMirror. It's well-documented, actively maintained, and has a large extension ecosystem. The headless model means you provide your own styling; Tiptap provides the editing engine.

Advantages:
- Comprehensive feature set with a well-designed extension system
- Collaborative editing (Tiptap Collaboration, built on Yjs) with WebSocket or WebRTC sync
- Strong TypeScript support
- The most production-ready option we looked at

Disadvantages:
- Bundle size: Tiptap core + common extensions is 80-100KB gzipped. For a feature that not all workspaces will use heavily, this is significant
- Collaborative editing adds cost: Tiptap's cloud collaboration server, or you self-host Hocuspocus
- The ProseMirror abstraction is complex; customisation beyond the extension API requires understanding ProseMirror's node/mark model

**Lexical** is Meta's open-source text editor framework, used in production on Facebook.

Advantages:
- Designed for performance at scale
- Maintained by a large team with strong testing
- Plugin architecture

Disadvantages:
- Less documentation than Tiptap
- Collaborative editing support is less mature
- React-specific at the API level

**Quill** is a well-established editor, though its development has slowed.

Advantages:
- Simple API, many examples
- Mature

Disadvantages:
- Limited TypeScript support
- Collaborative editing requires additional libraries (Quill + ShareDB or similar)
- The development cadence has slowed noticeably

## Why we built something minimal

The document feature in The Hyve is deliberately constrained. We looked at what teams actually need for internal documents:

- Headings (H1, H2, H3)
- Paragraphs with basic formatting (bold, italic, code)
- Unordered and ordered lists
- Code blocks with monospace rendering
- Inline links

That's it. No embedded images (we use Cloudflare Images for file attachments separately). No tables (they're almost never the right answer for team documentation). No nested sub-documents. No comments.

This scope is narrow enough that a custom implementation is manageable. The `contenteditable` API, combined with document.execCommand for formatting commands, handles this scope acceptably. The output is HTML stored as a string in the database.

```tsx
function DocumentEditor({ initialContent, onSave }: Props) {
  const editorRef = useRef<HTMLDivElement>(null);

  const format = (command: string, value?: string) => {
    document.execCommand(command, false, value);
    editorRef.current?.focus();
  };

  const handleKeyDown = (e: React.KeyboardEvent) => {
    if (e.metaKey || e.ctrlKey) {
      if (e.key === 'b') { e.preventDefault(); format('bold'); }
      if (e.key === 'i') { e.preventDefault(); format('italic'); }
      if (e.key === 's') { e.preventDefault(); onSave(editorRef.current?.innerHTML ?? ''); }
    }
  };

  return (
    <div>
      <Toolbar onFormat={format} />
      <div
        ref={editorRef}
        contentEditable
        suppressContentEditableWarning
        dangerouslySetInnerHTML={{ __html: initialContent }}
        onKeyDown={handleKeyDown}
        className="prose prose-invert max-w-none outline-none min-h-[400px] p-6"
      />
    </div>
  );
}
```

The Toolbar component renders buttons that call `format()` with the appropriate `execCommand` arguments.

## The tradeoffs

**We don't have real-time collaborative editing.** Multiple users can't edit the same document simultaneously — the last save wins. For a workspace where documents are usually owned and edited by one person at a time, this is acceptable. It's not acceptable if your use case is Google Docs-style concurrent editing.

**`document.execCommand` is deprecated.** The MDN docs mark execCommand as deprecated. It still works in all major browsers and will for the foreseeable future, but long-term it's not a path we can follow indefinitely. If we ever need to invest in the document editor meaningfully, we'd migrate to Tiptap or Lexical.

**Undo/redo is the browser's, not ours.** This is actually fine for our use case — the browser's built-in undo history works well enough. But it means we can't implement custom undo behaviour.

**Accessibility is lower than a purpose-built editor.** Tiptap has had years of accessibility work. Our contenteditable implementation hasn't. For the current product scope (internal tool used by self-selected technical teams), this is an acceptable compromise.

## What we got for free

**Zero bundle size cost.** The document editor adds no additional JavaScript to the bundle — it's a div with a ref and some event handlers.

**Complete control over styling.** The `prose` class from Tailwind Typography does the heavy lifting for content rendering. It looks consistent with the rest of The Hyve's design system without any Tiptap-to-Tailwind adaptation layer.

**Easy document storage.** The output is HTML; we store it as a `TEXT` column in Postgres. No custom schema for a document format.

**No additional dependency maintenance.** Tiptap releases regularly; keeping a production dependency up to date across its extensions is real maintenance work. We have zero document editor maintenance burden.

## The decision framework

The question for any "should we use a library or build our own" decision:

1. What's the scope of what we need?
2. Is the library's scope significantly larger?
3. What's the maintenance burden of each option?
4. What's the correctness risk of building our own?

For a rich text editor with collaborative editing, the answer is almost always "use a library." The scope of getting collaborative editing right is enormous.

For a rich text editor with no collaborative editing requirement and a narrow formatting scope, the balance tips toward a minimal implementation. We sacrificed collaborative editing to avoid 100KB of bundle, complex dependency management, and a learning curve that's significant for a non-core feature.

When the collaboration requirement becomes real — when teams are asking for it, when it's a reason someone didn't buy The Hyve — we'll migrate to Tiptap's collaborative stack. The migration path is clear. We're not paying the cost of it until we need it.
