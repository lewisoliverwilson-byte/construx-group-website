title: "Debezium: change data capture — stream database changes to Kafka in real time"
date: "2033-07-09"
excerpt: "Debezium is a distributed CDC (Change Data Capture) platform that reads the database transaction log and publishes every row-level change — INSERT, UPDATE, DELETE — as a structured event to Kafka. Instead of polling the database with SELECT WHERE updated_at > ? (which misses deletes, adds load, and has time-window gaps), Debezium reads PostgreSQL's WAL, MySQL's binlog, or MongoDB's oplog at the source. Each change event includes the full before/after row state, the transaction ID, the timestamp, and the schema. Downstream consumers — search indexes, read replicas, analytics pipelines, cache invalidation services — react to every change in order, without polling. Debezium runs as a Kafka Connect source connector: deploy it into a Kafka Connect cluster, configure a connector per database, and it handles WAL position tracking, schema evolution, and exactly-once delivery."
author: "Lewis Wilson"

WAL-based CDC. Kafka Connect source. Before/after state. Schema registry. Exactly-once.

## Change event structure and consuming

```typescript
// TypeScript: consume CDC events from Kafka
// Each message is a Debezium change event — before/after row state

import { Kafka } from "kafkajs";

const kafka = new Kafka({ brokers: ["kafka.construx.internal:9092"] });
const consumer = kafka.consumer({ groupId: "construx-search-indexer" });

interface DebeziumEvent<T> {
  before: T | null;    // null on INSERT
  after:  T | null;    // null on DELETE
  op:     "c" | "u" | "d" | "r";  // create, update, delete, read (snapshot)
  ts_ms:  number;
  table:  string;
  lsn:    string;      // WAL log sequence number — monotonically increasing
}

interface Order {
  id:         string;
  tenant_id:  string;
  status:     string;
  total_pence: number;
  created_at:  string;
}

await consumer.subscribe({ topics: ["construx.cdc.public.orders"], fromBeginning: false });

await consumer.run({
  eachMessage: async ({ message }) => {
    const event: DebeziumEvent<Order> = JSON.parse(message.value!.toString());

    switch (event.op) {
      case "c":   // INSERT
        await searchIndex.upsert(event.after!.id, event.after!);
        await cache.invalidate(`orders:${event.after!.tenant_id}`);
        break;

      case "u":   // UPDATE
        if (event.before?.status !== event.after?.status) {
          // Status changed — notify webhook subscribers
          await webhookQueue.publish({
            event:     "order.status_changed",
            orderId:   event.after!.id,
            from:      event.before?.status,
            to:        event.after?.status,
            tenantId:  event.after!.tenant_id,
          });
        }
        await searchIndex.upsert(event.after!.id, event.after!);
        break;

      case "d":   // DELETE
        await searchIndex.delete(event.before!.id);
        await cache.invalidate(`orders:${event.before!.tenant_id}`);
        break;
    }
  },
});
```

## PostgreSQL replication setup

```sql
-- PostgreSQL: configure for Debezium CDC
-- Run as superuser

-- Create replication user
CREATE USER debezium WITH REPLICATION LOGIN PASSWORD 'strong-password';
GRANT SELECT ON ALL TABLES IN SCHEMA public TO debezium;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO debezium;

-- Create publication: tells PostgreSQL which tables to include in WAL
CREATE PUBLICATION debezium_publication FOR TABLE
  public.orders,
  public.products,
  public.tenants,
  public.users;

-- Verify WAL level (must be logical for Debezium)
SHOW wal_level;
-- logical

-- If not set, update postgresql.conf:
-- wal_level = logical
-- max_wal_senders = 4
-- max_replication_slots = 4

-- Monitor replication slot lag (critical — lagging slots bloat WAL retention)
SELECT
  slot_name,
  plugin,
  active,
  pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS lag
FROM pg_replication_slots;
-- slot_name           plugin     active  lag
-- debezium_construx   pgoutput   t       128 kB   ← healthy
```

Debezium vs polling vs triggers vs logical replication directly: Polling with `WHERE updated_at > ?` misses deletes, requires an `updated_at` column on every table, adds periodic read load, and has a polling interval gap. Database triggers execute in-process and can block writes if the trigger logic is slow or the downstream system is unavailable. Direct logical replication consumers (pg_logical, pglogical) require building the WAL parsing and offset tracking yourself. Debezium handles all of this: WAL parsing, schema evolution (schema registry integration), at-least-once delivery with Kafka, offset tracking via Kafka consumer groups, and exactly-once downstream with the `lsn` field for idempotency. The constraint: Debezium adds Kafka Connect infrastructure overhead. For a single database feeding a single consumer, a simpler approach (outbox table + polling) may be lower-complexity. Debezium pays off when multiple consumers need the same change stream — deploy one connector, fan out to many consumers.
