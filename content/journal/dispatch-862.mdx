title: "React Server Components: rendering on the server without hydration overhead"
date: "2032-01-13"
excerpt: "React Server Components (RSC) render on the server and stream to the client as a serialised React tree — not HTML, not JSON, but a new wire format that preserves component identity. Server components have no JavaScript bundle cost: they never ship to the browser. They can await database queries, read files, and call APIs directly. Client components opt in with 'use client' and are hydrated normally. The split lets you compose server and client components in the same tree without prop-drilling through network boundaries."

No bundle for server components. Async by default. Compose with client islands.

## Server component — async by default

```tsx
// app/orders/page.tsx — Server Component (no 'use client')
import { db } from '@/lib/db';
import { orders } from '@/lib/schema';
import { desc } from 'drizzle-orm';
import { OrderCard } from '@/components/OrderCard';   // Client Component
import { Suspense } from 'react';

// This component runs on the server — no bundle cost in the browser
// It can be async and await directly
export default async function OrdersPage() {
  const recentOrders = await db
    .select()
    .from(orders)
    .orderBy(desc(orders.createdAt))
    .limit(20);

  return (
    <main>
      <h1>Orders</h1>
      {/* Suspense boundary — shows skeleton while slow children stream */}
      <Suspense fallback={<OrderListSkeleton />}>
        <SlowOrderStats />  {/* Another Server Component that fetches slow data */}
      </Suspense>
      <ul>
        {recentOrders.map((order) => (
          // OrderCard is a Client Component — rendered on client, hydrated
          <OrderCard key={order.id} order={order} />
        ))}
      </ul>
    </main>
  );
}
```

## Client component — 'use client' boundary

```tsx
// components/OrderCard.tsx — Client Component
'use client';

import { useState } from 'react';

interface Order {
  id:         string;
  status:     string;
  totalCents: number;
  createdAt:  string;
}

export function OrderCard({ order }: { order: Order }) {
  const [expanded, setExpanded] = useState(false);

  return (
    <li className="border rounded p-4">
      <button onClick={() => setExpanded(!expanded)}>
        {order.id} — £{(order.totalCents / 100).toFixed(2)}
      </button>
      {expanded && (
        <dl>
          <dt>Status</dt>  <dd>{order.status}</dd>
          <dt>Created</dt> <dd>{order.createdAt}</dd>
        </dl>
      )}
    </li>
  );
}
// OrderCard ships to the browser — useState, onClick, etc. work normally
// The `order` prop is serialised from the server and injected at hydration
```

## Server Actions — mutations without API routes

```tsx
// app/orders/actions.ts
'use server';

import { revalidatePath } from 'next/cache';
import { db } from '@/lib/db';
import { orders } from '@/lib/schema';

// Server Actions run on the server when called from client components
export async function cancelOrder(orderId: string) {
  await db.update(orders)
    .set({ status: 'cancelled' })
    .where(eq(orders.id, orderId));

  revalidatePath('/orders');    // Invalidate the cached server component
  return { success: true };
}
```

```tsx
// components/CancelButton.tsx — Client Component using a Server Action
'use client';

import { cancelOrder } from '@/app/orders/actions';
import { useTransition } from 'react';

export function CancelButton({ orderId }: { orderId: string }) {
  const [isPending, startTransition] = useTransition();

  return (
    <button
      disabled={isPending}
      onClick={() => startTransition(() => cancelOrder(orderId))}
    >
      {isPending ? 'Cancelling…' : 'Cancel order'}
    </button>
  );
}
// No fetch(), no API route, no JSON serialisation — just a function call
// Next.js serialises the action call to a POST request under the hood
```

## Streaming with Suspense

```tsx
// app/dashboard/page.tsx
import { Suspense } from 'react';

// Each Suspense boundary streams independently
// The page HTML starts streaming immediately; slow sections fill in later
export default function DashboardPage() {
  return (
    <div>
      {/* Fast — renders immediately */}
      <DashboardHeader />

      {/* Slow (queries an analytics database) — streams in ~200ms */}
      <Suspense fallback={<StatsCardSkeleton />}>
        <RevenueStats />
      </Suspense>

      {/* Very slow (calls an external API) — streams in ~800ms */}
      <Suspense fallback={<ChartSkeleton />}>
        <WeeklyChart />
      </Suspense>
    </div>
  );
}

// Each async Server Component resolves independently
async function RevenueStats() {
  const stats = await queryAnalytics('revenue', '7d');  // 200ms
  return <StatsCard data={stats} />;
}

async function WeeklyChart() {
  const data = await externalApi.getChartData();  // 800ms
  return <Chart data={data} />;
}
```

Server Components vs traditional SSR: with Next.js pages/ (SSR), the entire page waits for `getServerSideProps` before any HTML is sent. With RSC + Suspense, HTML starts streaming immediately — the shell renders at ~0ms, fast components stream at their own pace, and slow components stream when ready. The user sees content progressively rather than waiting for the slowest query. The tradeoff: RSC introduces the client/server boundary as a first-class concept that developers must reason about — which component runs where, what can be serialised across the boundary.
