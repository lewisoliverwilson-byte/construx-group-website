Bun benchmarks show 3-20x faster startup times and 10x faster package installs. In a real project, the gains are more nuanced. Here's where Bun actually helps.

## Installation: the obvious win

```bash
# npm — for a project with 800 packages
time npm install
# real: 1m 34s

# Bun — same project
time bun install
# real: 8s
```

`bun install` is 10-12x faster than `npm install` in practice. It downloads packages in parallel, uses a binary lockfile (`bun.lockb`), and caches aggressively. For CI pipelines that run `npm install` on every push, switching to Bun drops that step from 90 seconds to 8.

The lockfile (`bun.lockb`) is binary. To check what's in it: `bun bun.lockb | cat` which outputs the equivalent `yarn.lock` text.

## Startup time: faster for scripts

```bash
# Node.js
time node -e "console.log('hello')"
# real: 0.088s

# Bun
time bun -e "console.log('hello')"
# real: 0.012s
```

7x faster startup. This matters for scripts that run on every commit (linting, type checking, code generation). For long-running servers, startup time is irrelevant.

## Where Bun doesn't change much: Next.js

Next.js has its own build system (webpack/Turbopack). `bun next build` is roughly the same speed as `npm run build` — the bottleneck is the Next.js bundler, not the JavaScript runtime starting up.

```bash
# The same for both:
bun run dev     # same as npm run dev
bun run build   # same as npm run build
```

Bun runs the Next.js CLI correctly. Dev server startup is slightly faster (Bun loads the Next.js modules faster), but the difference is small.

## TypeScript execution: no compilation step

Bun runs TypeScript natively — no `ts-node`, no compilation step:

```bash
# No transpilation needed
bun run scripts/seed-db.ts

# Compare with Node.js requiring ts-node
npx ts-node scripts/seed-db.ts
```

For short-lived TypeScript scripts (database seeders, data migration scripts, code generators), this is a meaningful improvement. Scripts that took 3-4 seconds to start with `ts-node` start in under 200ms with Bun.

## The test runner

```bash
# Bun test runner — runs without configuration
bun test

# Jest equivalent
npx jest
```

Bun's test runner is Jest-compatible (same `describe`/`it`/`expect` API) and significantly faster for unit tests. For a test suite of 500 unit tests, `bun test` runs in ~400ms vs Jest's ~8 seconds.

It doesn't support all Jest features (some transform and coverage options differ), but for TypeScript unit tests it's a drop-in replacement.

## Migration steps

```bash
# Install Bun
curl -fsSL https://bun.sh/install | bash

# Replace npm install
bun install  # reads package.json, generates bun.lockb

# Run scripts
bun run dev
bun run build
bun run test  # if using Bun's test runner

# Execute TypeScript directly
bun run scripts/my-script.ts
```

For Next.js projects, keep `next` as the server runtime — Bun doesn't replace Next.js's Node.js server yet. Use Bun for the development toolchain (installs, scripts, tests) and keep the production server as-is.

## The compatibility edge cases

Most npm packages work with Bun. Edge cases:
- Packages that use Node.js native addons (`.node` files): may not work
- Packages that check `process.versions.node` or `process.version`: may behave unexpectedly
- Jest custom transformers: Bun's test runner has different transform semantics

Run `bun install && bun run test` in CI alongside your existing Node.js setup to catch incompatibilities before committing to Bun.

## Our setup

We use Bun for:
- `bun install` in all CI pipelines
- Running TypeScript scripts directly (database seeders, code generators, migration helpers)
- The test runner for unit tests
- Local dev toolchain

We keep Node.js for:
- Production Next.js servers (deployed on Railway, which runs Node.js)
- Packages with native addons

The install speedup alone — from 90s to 8s per CI run — justifies the migration. For a project running 50 CI jobs per day, that's 68 minutes of CI time saved daily. At cloud CI pricing, that's real money.
