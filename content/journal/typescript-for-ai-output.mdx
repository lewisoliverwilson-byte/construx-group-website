AI output arrives as a string. Everything after that — parsing, validation, type narrowing — is your problem.

This is a category of code that's easy to get wrong. Overconfident parsing (assume the JSON is valid, the structure matches what you expect) leads to runtime failures in production. Over-engineered validation (Zod schemas for every AI response, discriminated union types for every possible output) adds complexity that slows development without proportionate safety benefit.

Here's what we've found works.

## The baseline: don't trust the string

The first rule: never access properties of a parsed AI response without validating that those properties exist.

The common mistake:

```typescript
const result = JSON.parse(aiOutput);
const margin = result.products[0].projectedMargin; // dangerous
```

This will throw in production. The AI response might not be valid JSON. It might be valid JSON but not match the expected structure. The first product might not have a `projectedMargin` field.

The safe pattern:

```typescript
function parseProductResult(raw: string): ProductResult | null {
  try {
    const parsed = JSON.parse(raw);
    if (!Array.isArray(parsed.products)) return null;
    return parsed as ProductResult;
  } catch {
    return null;
  }
}
```

This returns `null` for invalid responses rather than throwing. The caller handles `null` explicitly.

## Structure validation without Zod

Zod is a fine library. For complex, deeply nested schemas that need detailed error messages, it's worth the dependency. For most AI output parsing, it's more than you need.

The lightweight alternative: a type guard function that validates structure and narrows the type.

```typescript
interface ScoutrProduct {
  title: string;
  category: string;
  projectedMargin: number;
  confidence: 'high' | 'medium' | 'low';
}

function isScoutrProduct(val: unknown): val is ScoutrProduct {
  if (typeof val !== 'object' || val === null) return false;
  const p = val as Record<string, unknown>;
  return (
    typeof p.title === 'string' &&
    typeof p.category === 'string' &&
    typeof p.projectedMargin === 'number' &&
    (p.confidence === 'high' || p.confidence === 'medium' || p.confidence === 'low')
  );
}
```

This is verbose for complex schemas but clear about exactly what's being validated. The type narrowing (`val is ScoutrProduct`) makes TypeScript aware that after a truthy guard check, the value is typed correctly.

## Structured output and type inference

The cleanest pattern for typed AI output: include the expected JSON schema in the prompt, then parse with a type guard.

The prompt:

```
Respond with a JSON object matching this structure exactly:
{
  "products": Array<{ "title": string, "category": string, "projectedMargin": number }>
}

No text before or after the JSON. No markdown code fence.
```

The parsing:

```typescript
type ScoutrResponse = {
  products: Array<{ title: string; category: string; projectedMargin: number }>;
};

function parseScoutrResponse(raw: string): ScoutrResponse | null {
  try {
    const parsed = JSON.parse(raw);
    if (!Array.isArray(parsed.products)) return null;
    if (!parsed.products.every(isValidProduct)) return null;
    return parsed as ScoutrResponse;
  } catch {
    return null;
  }
}
```

The type guard (`isValidProduct`) validates the array items. The return type is either the typed response or null, forcing callers to handle the failure case.

## Handling partial responses

Streaming AI output means you sometimes need to handle partial JSON — the response is still arriving when you first process it. The pattern for this: optimistic parsing with graceful handling of parse failures.

For Scoutr's streaming output, we try to parse the accumulated output as JSON after each token. If it fails (because it's still partial), we continue streaming. When the stream ends, we do a final parse. If the final parse fails, we surface an error.

```typescript
function tryParsePartial(accumulated: string): ScoutrResponse | null {
  try {
    return parseScoutrResponse(accumulated);
  } catch {
    return null; // still streaming
  }
}
```

The key: failures during streaming are expected and handled silently. The failure state only matters after the stream ends.

## Error types for AI failures

AI failures aren't generic errors — they have specific types that should be handled differently:

```typescript
type AIFailure =
  | { type: 'parse_error'; raw: string }
  | { type: 'structure_invalid'; parsed: unknown }
  | { type: 'api_error'; status: number }
  | { type: 'rate_limit'; retryAfter?: number }
  | { type: 'content_filter' };
```

Each failure type has different handling. A `parse_error` usually means the prompt needs a tighter format instruction. A `rate_limit` should trigger a retry with backoff. A `content_filter` means the input was flagged by the API's safety system.

Specific failure types produce specific responses to users. "We couldn't process this product page" is more useful than a generic error when the failure is a parse error on an unusual page format.

## The error handling boundary

One pattern we've adopted: a single function per AI feature that handles the full lifecycle (prompt assembly, API call, parsing, error handling) and returns a typed result union.

```typescript
type ScanResult =
  | { success: true; products: ScoutrProduct[] }
  | { success: false; error: AIFailure };

async function scanProductPage(url: string): Promise<ScanResult> {
  try {
    const response = await callClaude(buildScanPrompt(url));
    const parsed = parseScoutrResponse(response);
    if (!parsed) return { success: false, error: { type: 'parse_error', raw: response } };
    return { success: true, products: parsed.products };
  } catch (err) {
    return { success: false, error: classifyError(err) };
  }
}
```

The caller never handles raw errors — only the typed `ScanResult`. TypeScript enforces handling both the success and failure cases. The UI layer deals with types it understands, not raw strings or untyped errors.

This boundary isn't over-engineering — it's the right abstraction for any async operation that can fail in multiple specific ways.
