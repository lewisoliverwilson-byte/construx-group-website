title: "Skaffold: inner loop for Kubernetes development — auto-rebuild, auto-deploy, port-forward"
date: "2033-08-14"
excerpt: "Skaffold is a command-line tool that handles the inner development loop for Kubernetes applications: it watches your source files, rebuilds the container when files change, pushes the new image to a registry (or loads it directly into a local cluster), applies your Kubernetes manifests with the new image tag, and streams the pod logs back to your terminal. The result is a tight feedback loop: save a file, and within seconds the pod is running the updated code — no manual docker build, docker push, kubectl set image, kubectl logs. Skaffold is configured via a skaffold.yaml file that declares the build pipeline (Dockerfile, Buildpacks, Jib for Java), the deploy method (kubectl, Helm, Kustomize), and the port-forward rules. In development mode (skaffold dev), it watches and syncs; in CI mode (skaffold run), it does a one-shot build-and-deploy; in skaffold debug, it attaches language-specific debuggers. File sync can be configured to copy changed files directly into the running container without a rebuild (useful for interpreted languages like Python or Node.js)."

Inner loop automation. File sync. Multi-module pipelines. Helm deploy. Debug attach.

## skaffold.yaml configuration

```yaml
# skaffold.yaml: inner loop configuration for construx-api

apiVersion: skaffold/v4beta11
kind: Config
metadata:
  name: construx-api

build:
  artifacts:
    - image: registry.construx.internal/construx/api
      context: .
      docker:
        dockerfile: Dockerfile
        buildArgs:
          GOVERSION: "1.23"
      sync:
        # File sync: copy .go files into container without rebuild (for hot reload with Air)
        manual:
          - src: "**/*.go"
            dest: /app/src
    - image: registry.construx.internal/construx/worker
      context: ./worker
      docker:
        dockerfile: Dockerfile
  local:
    push: false       # don't push in dev — load directly into local cluster (minikube/kind)
    useBuildkit: true
    concurrency: 2    # build api and worker in parallel

deploy:
  helm:
    releases:
      - name: construx-api
        chartPath: ./charts/construx-api
        namespace: construx-dev
        createNamespace: true
        setValues:
          image.repository: registry.construx.internal/construx/api
          replicaCount: 1
          resources.requests.cpu: 100m
          resources.requests.memory: 128Mi
        valuesFiles:
          - ./charts/construx-api/values.dev.yaml

portForward:
  - resourceType: service
    resourceName: construx-api
    namespace: construx-dev
    port: 8080
    localPort: 8080
  - resourceType: service
    resourceName: postgres
    namespace: construx-dev
    port: 5432
    localPort: 5432

profiles:
  # CI profile: push to registry, deploy to staging namespace
  - name: ci
    build:
      local:
        push: true
    deploy:
      helm:
        releases:
          - name: construx-api
            chartPath: ./charts/construx-api
            namespace: construx-staging
            valuesFiles:
              - ./charts/construx-api/values.staging.yaml

  # Production profile: use Kustomize, real resource limits
  - name: prod
    build:
      local:
        push: true
    deploy:
      kustomize:
        paths: ["./k8s/overlays/prod"]
```

## Development workflow

```bash
# Start inner loop (watches files, rebuilds, deploys, streams logs)
skaffold dev

# Output:
# [construx-api] Building image registry.construx.internal/construx/api...
# [construx-api] Loading image into local cluster...
# [construx-api] Deploying construx-api via Helm...
# [construx-api] Port forwarding service/construx-api on :8080 → 8080
# [construx-api] Watching for changes...
# [construx-api]  construx-api-7d9f  construx.api  INFO  server started on :8080

# Save a .go file → Skaffold detects change
# [construx-api] Syncing files into running container...  (if file sync configured)
# OR
# [construx-api] Rebuilding image... (if full rebuild needed)
# [construx-api] Loading image into local cluster...
# [construx-api] Deploying updated pod...
# [construx-api]  construx-api-8e0g  construx.api  INFO  server restarted

# Debug mode: attach a debugger (Go: Delve, Node: --inspect, Python: debugpy)
skaffold debug
# Attaching debugger to construx-api via Delve on :56268
# IDE remote debug: set breakpoints and attach to localhost:56268

# CI: one-shot build + push + deploy
skaffold run --profile ci
# Building and pushing images...
# Deploying to construx-staging namespace...
# Waiting for deployments to stabilise...
# Deployment construx-api rolled out successfully

# Render: generate final Kubernetes manifests (without deploying)
skaffold render --profile prod > manifests.yaml

# Delete resources deployed by Skaffold
skaffold delete --profile ci
```

## Multi-module monorepo pipeline

```yaml
# skaffold.yaml for a monorepo with multiple services
# Each service is a separate Skaffold config in its own directory

# root skaffold.yaml (orchestrator)
apiVersion: skaffold/v4beta11
kind: Config
metadata:
  name: construx-platform
requires:
  - path: ./services/api          # builds + deploys api
  - path: ./services/worker       # builds + deploys worker
  - path: ./services/payments     # builds + deploys payments
  - path: ./infra/postgres        # deploys Helm chart for postgres
    activeProfiles:
      - name: dev
        activatedBy: [dev]

# Each submodule (./services/api/skaffold.yaml) has its own build/deploy config
# skaffold dev runs all of them in parallel — logs are prefixed by module name

# [api] Building...
# [worker] Building...
# [api] Deployed
# [worker] Deployed
# [api]  GET /health 200 2ms
```

Skaffold vs Tilt vs manual kubectl + watch vs ko: Manual docker build + push + kubectl set image + kubectl logs is repetitive and slow — the round-trip for a single file change is 30-90 seconds. ko (Kubernetes + Go) is a fast Go-specific alternative that builds Go binaries directly into container images (no Dockerfile) and deploys to Kubernetes in seconds — great for Go-only microservices. Tilt is a similar tool to Skaffold with a Tiltfile (Python-like DSL) that is more expressive than Skaffold's YAML — it has a web UI, better monorepo support, and richer extension system. Skaffold's advantage is its integration with all three deploy methods (kubectl, Helm, Kustomize), official Google/CNCF backing, and the profiles system that lets the same skaffold.yaml work across dev, CI, and prod environments. For teams using Helm for Kubernetes deployments who want a first-class development loop without writing custom watch scripts, Skaffold is the standard choice.
