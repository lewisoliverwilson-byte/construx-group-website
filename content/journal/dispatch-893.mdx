date: "2032-04-15"
excerpt: "Cilium is a CNI plugin for Kubernetes that replaces iptables with eBPF programs loaded directly into the kernel. Where iptables evaluates rules per-packet against static IP addresses, Cilium enforces policy based on workload identity (Kubernetes labels) at the eBPF level — faster, more flexible, and without the O(n) rule evaluation cost. Cilium also provides Hubble: a real-time observability layer built on the same eBPF flow data, giving you per-connection visibility across the entire cluster without traffic mirroring or sidecars."

eBPF replaces iptables. Identity replaces IP. Hubble sees every flow.

## Network policy — identity-based L3/L4/L7

```yaml
# CiliumNetworkPolicy — more expressive than Kubernetes NetworkPolicy
# Supports L7 (HTTP method/path), FQDN-based egress, and service identity

apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: allow-api-to-postgres
  namespace: construx
spec:
  endpointSelector:
    matchLabels:
      app: postgres     # This policy applies to pods with app=postgres

  ingress:
    # Allow construx-api to reach postgres on port 5432
    - fromEndpoints:
        - matchLabels:
            app: construx-api
      toPorts:
        - ports:
            - port: "5432"
              protocol: TCP

    # Allow construx-worker to reach postgres
    - fromEndpoints:
        - matchLabels:
            app: construx-worker
      toPorts:
        - ports:
            - port: "5432"
              protocol: TCP

  # Implicit: all other ingress is denied (zero-trust default)

---
# L7 HTTP policy — enforce at the application layer
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: restrict-api-http-methods
  namespace: construx
spec:
  endpointSelector:
    matchLabels:
      app: construx-api

  ingress:
    - fromEndpoints:
        - matchLabels:
            app: construx-frontend
      toPorts:
        - ports:
            - port: "8080"
              protocol: TCP
          rules:
            http:
              - method: GET
                path: "^/api/orders"
              - method: POST
                path: "^/api/orders$"
              # DELETE /api/orders is not listed → Cilium returns 403
```

## Hubble — real-time flow observability

```bash
# Hubble relay exposes a gRPC API for querying flows
# hubble CLI connects to the relay

# Enable Hubble in cilium helm values
helm upgrade cilium cilium/cilium \
  --set hubble.relay.enabled=true \
  --set hubble.ui.enabled=true \
  --set hubble.metrics.enabled="{dns,drop,tcp,flow,icmp,http}"

# Port-forward to Hubble relay
kubectl port-forward -n kube-system svc/hubble-relay 4245:80

# Observe all flows in the construx namespace
hubble observe --namespace construx --follow
# Mar 25 14:32:01  FORWARDED  construx-api/construx → postgres-0/construx  TCP :5432
# Mar 25 14:32:01  DROPPED    legacy-svc/construx   → postgres-0/construx  TCP :5432 [Policy denied]

# Filter to dropped flows only (find policy violations)
hubble observe --namespace construx --verdict DROPPED

# HTTP flows with L7 visibility
hubble observe --namespace construx --protocol HTTP
# Mar 25 14:32:04  GET /api/orders  200  construx-frontend → construx-api  2.4ms
# Mar 25 14:32:05  DELETE /api/orders  403  unknown-svc → construx-api  [L7 denied]

# DNS query flows
hubble observe --namespace construx --protocol DNS
# Mar 25 14:32:06  DNS Query  postgres.construx.svc.cluster.local → kube-dns:53
# Mar 25 14:32:06  DNS Answer A 10.96.12.44 (TTL 30s)

# Flow summary: dropped by reason
hubble observe --namespace construx --verdict DROPPED \
  --output json | jq -r '.flow.drop_reason' | sort | uniq -c | sort -rn
#  8421 Policy denied
#    12 Invalid packet
#     3 Connection reset
```

## Cilium vs kube-proxy — eBPF service routing

```bash
# Traditional kube-proxy: iptables DNAT rules for ClusterIP services
# iptables -L -n -t nat | grep KUBE-SVC
# Kubernetes clusters with many services have 10,000+ iptables rules
# Every new connection traverses all rules O(n)

# Cilium replaces kube-proxy with eBPF maps
# Service lookup is O(1) via eBPF hash map, not O(n) iptables traversal

# Disable kube-proxy and use Cilium's eBPF kube-proxy replacement
helm upgrade cilium cilium/cilium \
  --set kubeProxyReplacement=true \
  --set k8sServiceHost=192.168.1.10 \
  --set k8sServicePort=6443

# Verify kube-proxy replacement is active
cilium status | grep KubeProxyReplacement
# KubeProxyReplacement: True [ens3 192.168.1.11]

# Inspect eBPF service map
cilium service list
# ID   Frontend              Backend
# 1    10.96.0.1:443/TCP     192.168.1.10:6443 (kube-api)
# 8    10.96.12.44:5432/TCP  10.0.1.21:5432, 10.0.1.22:5432 (postgres)

# eBPF map lookups per second (from Prometheus)
# cilium_ebpf_map_ops_total{map_name="cilium_lb4_services_v2",op="lookup"}
# → 2.4M lookups/s at near-zero CPU cost vs iptables traversal
```

Cilium vs Calico: Both use eBPF (Calico's newer eBPF mode) but Cilium was designed eBPF-first — the dataplane, kube-proxy replacement, Hubble observability, and L7 policy enforcement are all native. Calico's eBPF mode is a migration path from its iptables mode. In practice, both work well for L3/L4 policy; Cilium's advantage is L7 enforcement (HTTP path/method filtering without a sidecar proxy) and Hubble's flow observability. At Construx scale (dozens of pods), either works fine; the Cilium choice was made for Hubble's debugging capabilities when tracing why one service can't reach another.
