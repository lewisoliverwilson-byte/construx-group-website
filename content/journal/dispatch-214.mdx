The Hyve's premise is that team communication should be AI-native, not AI-bolted-on. The AI agent isn't a feature you toggle — it's a participant in every workspace, available in every channel, able to read the conversation history and take actions on behalf of the team.

Here's what it actually does, how it's built, and where it falls short.

## What the agent does

**Answer questions with context.** The agent reads the last 50 messages of conversation before responding. If a teammate asked "what did we decide about the API rate limit?" three days ago and the team answered it then, the agent can surface that answer when someone asks again now.

**Draft and summarise.** Asking the agent to summarise a long thread, draft a reply to an external email pasted into the channel, or structure a decision that was made verbally — these are the high-volume, low-effort tasks that consume disproportionate meeting and async time.

**Act on integrations.** The Hyve has integrations with GitHub (PR status, issue creation), Linear (task creation, status update), and a generic webhook system. The agent can trigger these actions via natural language: "create a Linear task for the API rate limiting work we just discussed."

**Answer about the workspace.** Team size, current active channels, recent members — the agent can query workspace metadata. Useful for onboarding new team members.

## Architecture

The agent runs as a backend service, not a client-side feature. When a user invokes the agent (by mentioning it in a message), the message is sent to the backend via the same SSE event stream used for regular messages. The backend:

1. Pulls the conversation history (last 50 messages, structured)
2. Pulls relevant workspace context (members, integrations, recent activity)
3. Constructs a system prompt with the workspace context and conversation history
4. Sends the prompt to the Claude API (claude-sonnet-4-6)
5. Streams the response back through SSE to the channel
6. If the response includes a tool call, executes the tool and includes the result in the final response

```ts
async function handleAgentInvocation(
  message: Message,
  workspace: Workspace
): Promise<void> {
  const history = await getConversationHistory(message.channelId, { limit: 50 });
  const context = await buildWorkspaceContext(workspace);

  const stream = await anthropic.messages.stream({
    model: 'claude-sonnet-4-6',
    max_tokens: 2048,
    system: buildSystemPrompt(context),
    messages: formatHistory(history, message),
    tools: WORKSPACE_TOOLS,
  });

  for await (const chunk of stream) {
    await streamToChannel(message.channelId, chunk);
  }
}
```

The tool calls (GitHub, Linear, webhooks) are defined in `WORKSPACE_TOOLS` as Anthropic tool definitions. When the model decides to use a tool, we execute the tool server-side and pass the result back to the model for incorporation into the final response.

## What works well

**Context awareness.** The 50-message history window is sufficient for most conversational tasks. The agent can follow a multi-turn discussion and give coherent answers that reference earlier points in the conversation.

**Speed.** Streaming the response means the first token appears within ~300ms of invocation. The user sees the response build in real-time, which feels responsive even when the full response takes several seconds.

**Tool use.** The integration actions work reliably. "Create a Linear task for X" produces a correct task more than 95% of the time, with sensible defaults for title, description, and priority.

**Tone.** The agent matches the conversational register of the workspace. In a technical discussion, responses are technical. In a lighter channel, responses are more casual. This is a property of the model, not of our configuration.

## Where it falls short

**Long-running context.** 50 messages is usually enough. It isn't enough for long-running strategic discussions that span hundreds of messages over weeks. The agent doesn't have persistent memory across sessions — it only knows what's in the current context window. Teams working on complex multi-week projects find that the agent needs to be explicitly caught up when context has drifted far.

**Ambiguous actions.** When a tool call requires information that isn't present in the conversation, the agent asks for clarification — which is correct — but the turn-taking to get all the required information is friction. A well-designed action flow would batch-collect required information before executing. We haven't built this yet.

**Cross-channel awareness.** The agent can only read the channel it's invoked in. It can't answer "what did the #product channel decide about this?" without being invoked in that channel. Cross-channel context would require an additional retrieval step (vector search across message history) that we haven't implemented.

**Hallucination on specific facts.** The agent correctly says "I don't know" when asked about facts not in the context window — most of the time. Occasionally it synthesises a plausible-sounding answer that isn't accurate. This is the fundamental limitation of LLMs, not something we've solved. The mitigation is grounding: the more we can give the model explicit workspace data (retrieved from the database), the less it has to rely on priors.

**Rate limits.** The Claude API has rate limits. Under heavy concurrent usage (multiple workspaces invoking the agent simultaneously), requests can queue. We handle this with a BullMQ job queue — agent invocations are queued jobs, not blocking request handlers — but the latency is visible when the queue is deep.

## The honest assessment

The agent works well for the 80% of cases it's designed for: quick questions, summaries, drafts, and simple integrations. It doesn't work well for cases requiring deep historical context, complex multi-step actions, or cross-channel awareness.

These limitations are properties of the current architecture, not fundamental limits. Persistent memory (via vector embeddings of workspace history) would address the long-running context problem. Cross-channel retrieval would address the siloed context problem. A better action flow would address the ambiguous action problem.

We'll build these features as the product matures and we understand the actual usage patterns better. The current version proves the core premise — AI-native communication is useful — without over-engineering for patterns we haven't yet observed.
