excerpt: "Ray is a distributed computing framework for Python that makes it straightforward to scale ML workloads — training, hyperparameter tuning, inference, and data preprocessing — from a laptop to a multi-node cluster with minimal code changes. The core abstraction is the remote function (@ray.remote): decorate a function and calling it returns a future that executes on any available worker in the cluster. Ray handles task scheduling, data transfer between nodes, failure recovery, and actor state management. Ray's higher-level libraries (Ray Train for distributed training, Ray Tune for hyperparameter search, Ray Serve for model serving, Ray Data for data pipelines) build on this primitive. Ray clusters integrate with Kubernetes via KubeRay — a Kubernetes operator that provisions Ray head and worker nodes and autoscales based on queue depth."

## Core API — remote functions and actors

```python
import ray
import time

# Connect to a Ray cluster (or start a local one)
ray.init(address="ray://ray-head.ray.svc:10001")

# Remote function: executes on a worker node
@ray.remote
def compute_embedding(text: str, model_name: str) -> list[float]:
    from sentence_transformers import SentenceTransformer
    model = SentenceTransformer(model_name)
    return model.encode(text).tolist()

# Submit 1000 embedding tasks in parallel
texts = ["product description " + str(i) for i in range(1000)]
futures = [
    compute_embedding.remote(text, "sentence-transformers/all-MiniLM-L6-v2")
    for text in texts
]

# Wait for all results — Ray distributes across workers automatically
embeddings = ray.get(futures)
print(f"Computed {len(embeddings)} embeddings")

# Resource specification: request GPU workers for GPU-intensive tasks
@ray.remote(num_gpus=1, memory=4 * 1024**3)
def fine_tune_model(dataset_path: str, output_path: str) -> dict:
    import torch
    from transformers import AutoModelForCausalLM, Trainer
    # ... training code
    return {"loss": 0.42, "epochs": 3}

# Actor: stateful long-running process (model inference server)
@ray.remote
class ModelServer:
    def __init__(self, model_name: str):
        from sentence_transformers import SentenceTransformer
        self.model = SentenceTransformer(model_name)

    def embed(self, text: str) -> list[float]:
        return self.model.encode(text).tolist()

    def batch_embed(self, texts: list[str]) -> list[list[float]]:
        return self.model.encode(texts).tolist()

# Create 4 model server actors (one per GPU worker)
servers = [ModelServer.remote("sentence-transformers/all-MiniLM-L6-v2") for _ in range(4)]

# Route requests round-robin
for i, text in enumerate(texts):
    futures.append(servers[i % 4].embed.remote(text))
```

# Ray Train: distributed model training across multiple nodes

import ray.train as train
from ray.train.torch import TorchTrainer
from ray.train import RunConfig, ScalingConfig

def train_func():
    # This function runs on each worker node
    import torch
    from torch.nn.parallel import DistributedDataParallel

    model = MyModel()
    model = train.torch.prepare_model(model)  # wraps in DDP automatically

    optimizer = torch.optim.Adam(model.parameters(), lr=1e-4)
    dataloader = train.torch.prepare_data_loader(dataloader)  # shards data across workers

    for epoch in range(10):
        for batch in dataloader:
            loss = model(batch)
            loss.backward()
            optimizer.step()
            optimizer.zero_grad()

        train.report({"loss": loss.item(), "epoch": epoch})

trainer = TorchTrainer(
    train_loop_per_worker=train_func,
    scaling_config=ScalingConfig(
        num_workers=4,      # 4 worker nodes
        use_gpu=True,       # each worker gets a GPU
        resources_per_worker={"GPU": 1, "CPU": 4},
    ),
    run_config=RunConfig(
        storage_path="s3://construx-ml-checkpoints/",
    ),
)
result = trainer.fit()

apiVersion: ray.io/v1alpha1
kind: RayCluster
metadata:
  name: construx-ray
  namespace: ray
spec:
  rayVersion: "2.38.0"

    replicas: 1

      dashboard-host: "0.0.0.0"
    template:
      spec:
        containers:
          - name: ray-head
            image: rayproject/ray:2.38.0
            resources:
              requests: { cpu: "2", memory: "8Gi" }
              limits:   { cpu: "4", memory: "16Gi" }

  workerGroupSpecs:
    - groupName: gpu-workers
      replicas: 2
      minReplicas: 0        # scale to zero when no jobs
      maxReplicas: 8        # scale out for burst workloads
      rayStartParams: {}
      template:
        spec:
          containers:
            - name: ray-worker
              image: rayproject/ray:2.38.0-gpu
              resources:
                requests: { cpu: "4", memory: "16Gi", nvidia.com/gpu: "1" }
                limits:   { cpu: "8", memory: "32Gi", nvidia.com/gpu: "1" }

Ray vs Celery vs Dask vs Spark vs direct CUDA: Celery is task queue for small jobs — no GPU support, no data locality, designed for I/O-bound background tasks. Dask parallelises NumPy and pandas operations across cores or nodes — good for data preprocessing but less integrated with ML training. Spark is mature for large-scale data processing but Python ML workloads in Spark are awkward (PySpark adds overhead). Direct CUDA (writing PyTorch training and running it on one GPU) is the simplest — Ray adds value when you need to go beyond one GPU or one node. Ray's strength is the unified Python API for the entire ML lifecycle: data preprocessing (Ray Data), distributed training (Ray Train), hyperparameter search (Ray Tune), model serving (Ray Serve) — all on the same cluster with the same primitives.
