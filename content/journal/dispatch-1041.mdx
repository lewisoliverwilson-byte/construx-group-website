---
title: "Talos Linux: immutable, API-driven OS for Kubernetes nodes"
date: "2033-07-03"
excerpt: "Talos Linux is a minimal, immutable Linux distribution built specifically to run Kubernetes. There is no SSH, no shell, no package manager, and no way to log into a Talos node directly — all configuration and management happens through a gRPC API (talosctl). The OS is read-only: the root filesystem is mounted read-only at boot, system directories are tmpfs, and the only writable path is /var for Kubernetes state. Upgrades are atomic: Talos downloads a new OS image, writes it to the inactive partition, updates the bootloader, and reboots — if the node fails to come up healthy, it rolls back automatically. The attack surface is minimal by design: no userspace tools, no cron, no init.d, no systemd units for anything except Kubernetes. The machine config (a single YAML file) declares everything: network interfaces, Kubernetes version, control plane endpoints, etcd encryption, disk layout."
author: "Lewis Wilson"

Immutable root. API-only. Atomic upgrades. Declarative machine config. No shell.

## Machine config and cluster bootstrap

# Generated by talosctl gen config, committed to git, applied via API

  type: controlplane
  token: <machine-token>   # generated by talosctl gen config
  ca:
    crt: <base64-cert>
    key: <base64-key>
  network:
    hostname: construx-cp-01
    interfaces:
      - interface: eth0
        addresses:
          - 10.0.1.10/24

            gateway: 10.0.1.1

      - 10.0.1.0/24

## talosctl operations

```bash
# Bootstrap a new cluster
# 1. Generate config
talosctl gen config construx-prod https://construx-k8s.internal:6443 \
  --output-dir ./talos-config \
  --config-patch-control-plane @patches/controlplane.yaml \
  --config-patch-worker @patches/worker.yaml

# 2. Apply config to control plane nodes (boots Talos, configures networking)
talosctl apply-config \
  --nodes 10.0.1.10,10.0.1.11,10.0.1.12 \
  --file ./talos-config/controlplane.yaml \
  --insecure   # first apply before certs are established

# 3. Bootstrap etcd on the first control plane node
talosctl bootstrap --nodes 10.0.1.10

# 4. Get kubeconfig
talosctl kubeconfig --nodes 10.0.1.10 --force

# 5. Apply config to worker nodes
talosctl apply-config \
  --nodes 10.0.2.10,10.0.2.11 \
  --file ./talos-config/worker.yaml

# Check node health
talosctl health --nodes 10.0.1.10,10.0.1.11,10.0.1.12,10.0.2.10

# View node services (no SSH — all via API)
talosctl services --nodes 10.0.1.10
# SERVICE      STATE    HEALTH   LAST CHANGE
# apid         Running  OK       2033-07-03 09:00:01
# containerd   Running  OK       2033-07-03 09:00:02
# cri          Running  OK       2033-07-03 09:00:03
# etcd         Running  OK       2033-07-03 09:00:05
# kubelet      Running  OK       2033-07-03 09:00:06
# trustd       Running  OK       2033-07-03 09:00:01

# Read kernel logs (dmesg equivalent)
talosctl dmesg --nodes 10.0.1.10 --follow

# Read kubelet logs
talosctl logs --nodes 10.0.1.10 kubelet

# OS upgrade: atomic, with automatic rollback on failure
talosctl upgrade \
  --nodes 10.0.1.10 \
  --image ghcr.io/siderolabs/installer:v1.9.0 \
  --preserve   # preserve data disk — don't wipe /var

# Kubernetes upgrade
talosctl upgrade-k8s \
  --nodes 10.0.1.10 \
  --to 1.32.0

# Apply a config change (rolling update across all nodes)
talosctl apply-config \
  --nodes 10.0.1.10,10.0.1.11,10.0.1.12 \
  --file ./talos-config/controlplane-v2.yaml \
  --mode reboot   # or "no-reboot" for changes that don't require restart
```

## Patches and extensions

```yaml
# Talos machine config patch: install Cilium CNI via system extension
# patches/controlplane.yaml

- op: add
  path: /machine/install/extensions
  value:
    - image: ghcr.io/siderolabs/iscsi-tools:v0.1.4@sha256:...
    - image: ghcr.io/siderolabs/util-linux-tools:v2.40.1@sha256:...

# Inline manifests: deploy resources at cluster bootstrap before anything else
- op: add
  path: /cluster/inlineManifests
  value:
    - name: cilium
      contents: |
        apiVersion: v1
        kind: Namespace
        metadata:
          name: cilium
    - name: cilium-helm-release
      contents: |
        apiVersion: helm.cattle.io/v1
        kind: HelmChart
        metadata:
          name: cilium
          namespace: kube-system
        spec:
          chart: cilium
          repo: https://helm.cilium.io/
          version: 1.16.0
          targetNamespace: kube-system
          valuesContent: |-
            kubeProxyReplacement: true
            k8sServiceHost: construx-k8s.internal
            k8sServicePort: 6443
```

Talos Linux vs Ubuntu/Debian + kubeadm vs Flatcar vs k3OS: Ubuntu/Debian with kubeadm gives you full control but a large attack surface — SSH, apt, systemd units, cron, everything a general-purpose OS has. Securing it requires hardening scripts, CIS benchmarks, and ongoing patching of the OS itself. Flatcar is a Container Linux successor — immutable, auto-updating, but still has SSH. k3OS is purpose-built for k3s. Talos's distinguishing properties are the complete removal of SSH and interactive shell (the attack surface drops dramatically), the gRPC API for all operations (auditable, scriptable, no ad-hoc ssh-ing into nodes), and the atomic upgrade model. The tradeoff is the learning curve: debugging requires talosctl instead of SSH, and anything that used to be 'ssh in and check' now requires the right talosctl subcommand. For teams running managed cloud Kubernetes (EKS, GKE, AKS), Talos is irrelevant — the cloud provider handles the node OS. For bare metal or self-managed VMs where you control the OS, Talos significantly reduces the Kubernetes node attack surface.
