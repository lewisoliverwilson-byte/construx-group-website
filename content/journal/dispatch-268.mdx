Unprotected API endpoints invite abuse. A contact form without rate limiting gets hammered by bots. A scan endpoint without rate limiting gets scraped. A login endpoint without rate limiting gets brute-forced.

You can solve this at the gateway level (Cloudflare, AWS WAF, nginx). You can use a service (Upstash Rate Limit, Redis with a sliding window). Or you can implement it in the application layer. Here's what we do and why.

## The in-memory approach (and when it's fine)

For low-traffic endpoints where approximate limiting is acceptable, in-memory rate limiting is the simplest option:

```ts
const hitCounts = new Map<string, { count: number; resetAt: number }>();

function rateLimit(key: string, limit: number, windowMs: number): boolean {
  const now = Date.now();
  const entry = hitCounts.get(key);

  if (!entry || now > entry.resetAt) {
    hitCounts.set(key, { count: 1, resetAt: now + windowMs });
    return true;  // Allowed
  }

  if (entry.count >= limit) return false;  // Blocked

  entry.count++;
  return true;
}
```

Applied to a contact form:

```ts
export async function POST(req: Request) {
  const ip = req.headers.get('x-forwarded-for') ?? 'unknown';
  const allowed = rateLimit(`contact:${ip}`, 3, 60_000);  // 3 per minute

  if (!allowed) {
    return Response.json(
      { error: 'Too many requests. Wait a minute and try again.' },
      { status: 429 }
    );
  }

  // Process the form...
}
```

**The problem:** serverless functions are stateless. Each invocation may run in a different process, so in-memory rate limiting is per-process, not per-user. On a busy endpoint, you might have 10 processes and each allows 3 requests per minute — effectively 30 requests per minute per IP, not 3.

This is acceptable for a contact form (the blast radius of occasional bypass is low). It's not acceptable for a login endpoint.

## Redis-backed rate limiting for precise control

For endpoints where accurate counting matters, we use Upstash Redis with a sliding window algorithm:

```ts
import { Ratelimit } from '@upstash/ratelimit';
import { Redis } from '@upstash/redis';

const ratelimit = new Ratelimit({
  redis: Redis.fromEnv(),
  limiter: Ratelimit.slidingWindow(10, '1m'),  // 10 requests per minute
  prefix: 'ratelimit',
  analytics: true,
});

export async function POST(req: Request) {
  const ip = req.headers.get('x-forwarded-for') ?? 'fallback';
  const identifier = `scan:${ip}`;

  const { success, limit, remaining, reset } = await ratelimit.limit(identifier);

  if (!success) {
    return new Response('Too many requests', {
      status: 429,
      headers: {
        'X-RateLimit-Limit': String(limit),
        'X-RateLimit-Remaining': String(remaining),
        'X-RateLimit-Reset': String(reset),
        'Retry-After': String(Math.ceil((reset - Date.now()) / 1000)),
      },
    });
  }

  // Process the scan...
}
```

Upstash's `slidingWindow` algorithm is accurate across distributed invocations because the count is stored in Redis, not process memory. 10 requests per minute means 10 across all processes, not 10 per process.

The `analytics: true` option records hit rate data in Upstash, which gives visibility into rate limiting events.

## Different limits for different endpoints

Not all endpoints have the same abuse profile:

```ts
// Contact form: few users, high friction, low limit
const contactLimit = new Ratelimit({
  redis: Redis.fromEnv(),
  limiter: Ratelimit.slidingWindow(3, '5m'),  // 3 per 5 minutes
  prefix: 'ratelimit:contact',
});

// Scan endpoint: high-value, should be metered, authenticated users get higher limits
const scanLimit = new Ratelimit({
  redis: Redis.fromEnv(),
  limiter: Ratelimit.slidingWindow(30, '1m'),  // 30 per minute
  prefix: 'ratelimit:scan',
});

// Search: read-only, less critical, higher limits
const searchLimit = new Ratelimit({
  redis: Redis.fromEnv(),
  limiter: Ratelimit.slidingWindow(60, '1m'),  // 60 per minute
  prefix: 'ratelimit:search',
});
```

Authenticated users can get higher limits by using their user ID as the identifier instead of IP:

```ts
const identifier = session?.userId
  ? `scan:user:${session.userId}`
  : `scan:ip:${ip}`;

const { success } = await ratelimit.limit(identifier);
```

Authenticated users are rate limited per-user (so a user abusing their own account doesn't affect others). Unauthenticated requests are rate limited by IP.

## Middleware-level rate limiting

For endpoints that should be rate-limited before the route handler runs (to avoid unnecessary processing), Next.js middleware handles it:

```ts
// middleware.ts
import { Ratelimit } from '@upstash/ratelimit';
import { Redis } from '@upstash/redis';
import { NextResponse } from 'next/server';

const ratelimit = new Ratelimit({
  redis: Redis.fromEnv(),
  limiter: Ratelimit.slidingWindow(100, '1m'),
  prefix: 'ratelimit:global',
});

export async function middleware(request: NextRequest) {
  if (request.nextUrl.pathname.startsWith('/api/')) {
    const ip = request.headers.get('x-forwarded-for') ?? 'unknown';
    const { success } = await ratelimit.limit(ip);

    if (!success) {
      return NextResponse.json({ error: 'Rate limit exceeded' }, { status: 429 });
    }
  }

  return NextResponse.next();
}
```

Global middleware rate limiting applies a ceiling across all API routes, regardless of individual endpoint limits. This catches clients hitting many different endpoints in rapid succession.

## The 429 response matters

The response to a rate-limited request should include enough information for legitimate clients to back off gracefully:

```
HTTP/1.1 429 Too Many Requests
X-RateLimit-Limit: 30
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1738234567890
Retry-After: 45

{"error": "Rate limit exceeded. Please wait 45 seconds."}
```

`Retry-After` is the most important header — it tells well-behaved clients when they can retry without needing to implement exponential backoff themselves.
