Webhooks are how services tell your application that something happened: Stripe fires when a payment succeeds, GitHub fires when a push lands, Resend fires when an email bounces. The sending service calls your endpoint; you process the event.

The naïve implementation is a route handler that does everything inline. The event arrives, you update the database, send a confirmation email, update a cache — all in the same request. This breaks in predictable ways.

## The failure modes

**Duplicate delivery.** Webhooks are delivered at-least-once. Stripe may retry if your endpoint returns a 5xx, or if it times out. The same `payment_intent.succeeded` event can arrive twice.

**Out-of-order delivery.** Events don't always arrive in the order they happened. A `subscription.updated` can arrive before `subscription.created` if there's network asymmetry.

**Slow processing kills delivery.** If your handler takes 15 seconds (AI enrichment, external API calls), the sender may time out and retry. Now you have two concurrent processes for the same event.

**Verification gaps.** Without signature verification, anyone who discovers your webhook URL can send fabricated events.

## The pattern: ingest, store, process separately

```
[External service] → [Ingest endpoint] → [event_inbox table] → [Worker]
```

The ingest endpoint does three things: verify the signature, store the raw event, return 200. Processing happens asynchronously.

## The schema

```sql
CREATE TABLE webhook_events (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  source       TEXT NOT NULL,      -- 'stripe', 'resend', 'github'
  event_type   TEXT NOT NULL,      -- 'payment_intent.succeeded'
  external_id  TEXT NOT NULL,      -- provider's event ID
  payload      JSONB NOT NULL,
  status       TEXT NOT NULL DEFAULT 'pending',
  processed_at TIMESTAMPTZ,
  error        TEXT,
  received_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  UNIQUE (source, external_id)     -- idempotency key
);

CREATE INDEX idx_webhook_events_pending
  ON webhook_events (received_at, status)
  WHERE status = 'pending';
```

The `UNIQUE (source, external_id)` constraint is the idempotency key. A duplicate delivery from Stripe with the same event ID fails the unique constraint — no duplicate processing.

## The ingest endpoint

```ts
// app/api/webhooks/stripe/route.ts
import Stripe from 'stripe';
import { db } from '@/lib/db';
import { webhookEvents } from '@/lib/schema';

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY!);

export async function POST(req: Request) {
  const body = await req.text();
  const sig = req.headers.get('stripe-signature');

  if (!sig) return new Response('Missing signature', { status: 400 });

  let event: Stripe.Event;
  try {
    event = stripe.webhooks.constructEvent(
      body,
      sig,
      process.env.STRIPE_WEBHOOK_SECRET!,
    );
  } catch (err) {
    return new Response('Invalid signature', { status: 400 });
  }

  try {
    await db.insert(webhookEvents).values({
      source: 'stripe',
      eventType: event.type,
      externalId: event.id,
      payload: event as unknown as Record<string, unknown>,
    }).onConflictDoNothing();
    // onConflictDoNothing: duplicate event → ignore, return 200 anyway
  } catch (err) {
    console.error('[webhook] Failed to store event', { eventId: event.id, err });
    return new Response('Storage error', { status: 500 });
  }

  return new Response('OK', { status: 200 });
}
```

The handler returns 200 even on duplicate delivery — `onConflictDoNothing` means the duplicate is ignored silently. Stripe considers any 2xx a success and won't retry.

## The processor

The worker runs on a cron and processes pending events. Each event type gets a handler:

```ts
// lib/webhooks/processor.ts
type Handler = (payload: Record<string, unknown>) => Promise<void>;

const handlers: Record<string, Record<string, Handler>> = {
  stripe: {
    'payment_intent.succeeded': handlePaymentSucceeded,
    'customer.subscription.deleted': handleSubscriptionCancelled,
    'invoice.payment_failed': handlePaymentFailed,
  },
  resend: {
    'email.bounced': handleEmailBounced,
    'email.complained': handleEmailComplained,
  },
};

export async function processWebhookEvents(): Promise<void> {
  const pending = await db.execute(sql`
    UPDATE webhook_events
    SET status = 'processing'
    WHERE id IN (
      SELECT id FROM webhook_events
      WHERE status = 'pending'
      ORDER BY received_at
      LIMIT 20
      FOR UPDATE SKIP LOCKED
    )
    RETURNING *
  `);

  for (const event of pending.rows) {
    const sourceHandlers = handlers[event.source as string];
    const handler = sourceHandlers?.[event.event_type as string];

    if (!handler) {
      // No handler registered — mark as skipped, not failed
      await db.execute(sql`
        UPDATE webhook_events
        SET status = 'skipped', processed_at = NOW()
        WHERE id = ${event.id}
      `);
      continue;
    }

    try {
      await handler(event.payload as Record<string, unknown>);
      await db.execute(sql`
        UPDATE webhook_events
        SET status = 'processed', processed_at = NOW()
        WHERE id = ${event.id}
      `);
    } catch (err) {
      await db.execute(sql`
        UPDATE webhook_events
        SET status = 'failed',
            error = ${err instanceof Error ? err.message : 'Unknown error'}
        WHERE id = ${event.id}
      `);
    }
  }
}
```

## Handling out-of-order events

For events where order matters — a subscription that's created then updated then cancelled — check the state before applying:

```ts
async function handleSubscriptionCancelled(
  payload: Record<string, unknown>,
): Promise<void> {
  const sub = payload.data?.object as Stripe.Subscription;

  const existing = await db
    .select()
    .from(subscriptions)
    .where(eq(subscriptions.stripeSubscriptionId, sub.id))
    .limit(1);

  // If the subscription doesn't exist yet, we received cancel before create
  // Re-queue for later processing
  if (!existing[0]) {
    await db.insert(webhookEvents).values({
      source: 'stripe',
      eventType: 'customer.subscription.deleted',
      externalId: `${sub.id}-retry-${Date.now()}`,
      payload: payload,
      // Schedule 30 seconds in the future
      receivedAt: new Date(Date.now() + 30_000),
    });
    return;
  }

  await db.update(subscriptions)
    .set({ status: 'cancelled', cancelledAt: new Date(sub.canceled_at! * 1000) })
    .where(eq(subscriptions.stripeSubscriptionId, sub.id));
}
```

Re-queuing a delayed event is heavy-handed for most cases. More often, the right answer is idempotent handlers that apply the correct end state regardless of what arrived first — if `subscription.deleted` arrives, mark it cancelled whether or not `subscription.created` arrived.

## What to monitor

The `webhook_events` table is a built-in audit log. Monitor:

- `status = 'failed'` events: are handlers throwing unexpectedly?
- High `status = 'pending'` count: is the processor running? Is it keeping up?
- Events received with no registered handler (`status = 'skipped'`): did the provider add a new event type?

A simple admin query:

```sql
SELECT source, event_type, status, COUNT(*) as count
FROM webhook_events
WHERE received_at > NOW() - INTERVAL '24 hours'
GROUP BY source, event_type, status
ORDER BY count DESC;
```

This tells you whether anything is failing, what types are arriving, and whether processing is keeping up.
