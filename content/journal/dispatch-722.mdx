Hardcoded credentials and `.env` files are a liability. Vault makes secrets dynamic, audited, and short-lived.

## Core concepts

- **Secret engines** — plugins that generate or store secrets. KV (key-value), Database, AWS, PKI.
- **Auth methods** — how clients authenticate. AppRole for services, Kubernetes for pods, OIDC for humans.
- **Policies** — HCL rules that say which paths a token can read or write.
- **Leases** — every secret has a TTL. Dynamic secrets expire automatically.

## KV secrets engine

```bash
# Enable KV v2
vault secrets enable -path=construx kv-v2

# Write secrets
vault kv put construx/api \
  stripe_key="sk_live_..." \
  sendgrid_key="SG...." \
  jwt_secret="$(openssl rand -hex 32)"

# Read a secret
vault kv get construx/api

# Read a single field
vault kv get -field=jwt_secret construx/api

# List secrets at a path
vault kv list construx/
```

## Dynamic database credentials

```bash
# Configure database secrets engine
vault secrets enable database
vault write database/config/postgres \
  plugin_name=postgresql-database-plugin \
  allowed_roles="construx-*" \
  connection_url="postgresql://{{username}}:{{password}}@db.construxgroup.io:5432/prod" \
  username="vault-admin" \
  password="$(vault read -field=password construx/db-admin)"

# Define a role — Vault creates temp users with these privileges
vault write database/roles/construx-api \
  db_name=postgres \
  creation_statements="CREATE ROLE '{{name}}' WITH LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA public TO '{{name}}';" \
  default_ttl="1h" \
  max_ttl="24h"
```

```bash
# Application requests credentials
vault read database/creds/construx-api
# → username: v-app-abc123
# → password: A1B2-c3d4-E5F6
# → lease_duration: 1h
# → lease_id: database/creds/construx-api/xyz789
```

The credential expires after one hour. Compromising it gives an attacker a one-hour window, not permanent access.

## Kubernetes auth

```bash
# In-cluster pods authenticate with their service account token
vault auth enable kubernetes
vault write auth/kubernetes/config \
  kubernetes_host="https://kubernetes.default.svc"

# Policy
vault policy write construx-api - <<EOF
path "construx/data/api" {
  capabilities = ["read"]
}
path "database/creds/construx-api" {
  capabilities = ["read"]
}
EOF

# Role binding
vault write auth/kubernetes/role/construx-api \
  bound_service_account_names=construx-api \
  bound_service_account_namespaces=prod \
  policies=construx-api \
  ttl=1h
```

## Node.js integration

```ts
import { NodeHvac } from 'node-hvac';

const vault = new NodeHvac({
  endpoint: process.env.VAULT_ADDR!,
  token:    process.env.VAULT_TOKEN!,
});

async function getSecret(path: string, key: string): Promise<string> {
  const { data } = await vault.kv2.read({ mountPath: 'construx', path });
  return data[key];
}

async function getDatabaseCredentials() {
  const creds = await vault.read('database/creds/construx-api');
  return {
    user:     creds.data.username,
    password: creds.data.password,
  };
}
```

## Audit logging

```bash
# Enable file audit log
vault audit enable file file_path=/var/log/vault/audit.log

# Every access looks like:
# {
#   "time": "2030-11-18T09:00:00Z",
#   "type": "request",
#   "auth": { "client_token": "hmac:abc...", "policies": ["construx-api"] },
#   "request": { "operation": "read", "path": "construx/data/api" }
# }
```

Every read, write, and denied request is logged. Who accessed what, when, from where. Compliance and forensics from day one.
