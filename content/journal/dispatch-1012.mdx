excerpt: "Benthos (now Redpanda Connect) is a stream processing engine that defines data pipelines declaratively in YAML. A pipeline is a sequence of inputs, processors, and outputs — read from Kafka, transform the message, write to ClickHouse. The processing language is built on Bloblang, a mapping language designed for JSON transformation. Unlike Kafka Streams or Flink (which require Java code), or Apache Beam (which requires a runner setup), Benthos runs as a single binary with zero dependencies and handles the hard parts: batching, backpressure, error handling, dead-letter queues, and metric collection. The configuration-first approach means non-engineers can understand and modify pipelines, and changes can be applied via GitOps without rebuilding code."

YAML pipelines. Bloblang transforms. Kafka → ClickHouse. Dead-letter queues. Zero dependencies.

## Pipeline anatomy

```yaml
# Benthos pipeline: input → processors → output

# Simple example: consume from Kafka, filter, write to HTTP
input:
  kafka:
    addresses:
      - redpanda.messaging.svc:9092
    topics:
      - construx.events
    consumer_group: benthos-event-processor
    start_from_oldest: false
    tls:
      enabled: true

pipeline:
  processors:
    # Parse the JSON message
    - mapping: |
        root = this.parse_json()

    # Filter: only process checkout events
    - filter_processor:
        bloblang: |
          this.event_type == "checkout"

    # Transform: enrich the event
    - mapping: |
        root = this
        root.processed_at = now()
        root.total_gbp = this.total_cents / 100
        root.user_tier = if this.total_cents > 10000 { "premium" } else { "standard" }

output:
  # Fan out: write to multiple destinations simultaneously
  broker:
    pattern: fan_out
    outputs:
      # ClickHouse: insert for analytics
      - clickhouse:
          dsn: "clickhouse://clickhouse.analytics.svc:9000/construx"
          table: checkout_events
          init_files: []

      # HTTP: webhook notification for high-value orders
      - switch:
          cases:
            - check: this.total_gbp > 100
              output:
                http_client:
                  url: https://hooks.construx.internal/high-value-order
                  verb: POST
                  headers:
                    Content-Type: application/json
                  rate_limit: 10/1s
            - output:
                drop: {}   # discard low-value orders for the webhook
```

## Bloblang: the mapping language

```yaml
# Bloblang: functional mapping language for JSON transformation
# Runs in the `mapping` processor

pipeline:
  processors:
    # Transform a Kafka CDC event (Debezium format) into a clean model
    - mapping: |
        # Access nested fields
        let order_id    = this.payload.after.id
        let user_id     = this.payload.after.user_id
        let status      = this.payload.after.status
        let created_at  = this.payload.after.created_at

        # Reshape the output
        root.order_id   = $order_id
        root.user_id    = $user_id
        root.status     = $status
        root.created_at = $created_at.ts_unix()

        # Conditional transformation
        root.is_fulfilled = if $status == "shipped" || $status == "delivered" { true } else { false }

        # String manipulation
        root.order_ref = "ORD-" + $order_id.string()

        # Array operations
        root.item_count = this.payload.after.items.length()
        root.item_skus  = this.payload.after.items.map_each(item -> item.sku)

        # Delete fields you don't want
        root.payload = deleted()

    # Map over an array field
    - mapping: |
        root = this
        root.tags = this.tags.map_each(t -> t.uppercase())

    # Merge two messages (accumulate pattern)
    - mapping: |
        # Add server-generated fields
        root = this
        root.server_id  = uuid_v4()
        root.checksum   = this.string().hash("sha256").encode("hex")
```

## Error handling and dead-letter queues

```yaml
# Error handling: catch failures and route to DLQ

input:
  kafka:
    addresses: [redpanda.messaging.svc:9092]
    topics: [construx.events]
    consumer_group: benthos-processor

pipeline:
  processors:
    - try:
        - mapping: |
            root = this.parse_json()
            root.processed_at = now()

        - http:
            url: http://construx-enrichment.construx-prod.svc/enrich
            verb: POST
            retries: 3
            retry_period: 1s

    # If any processor in the `try` block fails:
    - catch:
        - mapping: |
            root.error = error()
            root.original_payload = content().string()
            root.failed_at = now()
        - log:
            message: "Failed to process event: ${!error()}"
            level: WARN

output:
  switch:
    cases:
      # Successful messages go to ClickHouse
      - check: errored() == false
        output:
          clickhouse:
            dsn: "clickhouse://clickhouse.analytics.svc:9000/construx"
            table: events

      # Failed messages go to the DLQ topic
      - output:
          kafka_franz:
            seed_brokers: [redpanda.messaging.svc:9092]
            topic: construx.events.dlq
            compression: snappy
```

## Kubernetes deployment and GitOps

```yaml
# Deploy Benthos as a Kubernetes Deployment
# Config lives in a ConfigMap — change the ConfigMap to update the pipeline

apiVersion: v1
kind: ConfigMap
metadata:
  name: benthos-checkout-processor
  namespace: construx-prod
data:
  config.yaml: |
    input:
      kafka:
        addresses: ["redpanda.messaging.svc:9092"]
        topics: ["construx.events"]
        consumer_group: benthos-checkout
    pipeline:
      processors:
        - mapping: |
            root = this.parse_json()
            root.processed_at = now()
    output:
      clickhouse:
        dsn: "clickhouse://clickhouse.analytics.svc:9000/construx"
        table: events

---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: benthos-checkout-processor
  namespace: construx-prod
spec:
  replicas: 3
  selector:
    matchLabels:
      app: benthos-checkout-processor
  template:
    spec:
      containers:
        - name: benthos
          image: ghcr.io/redpanda-data/connect:latest
          args: ["-c", "/config/config.yaml"]
          volumeMounts:
            - name: config
              mountPath: /config
          resources:
            requests:
              cpu: 200m
              memory: 256Mi
            limits:
              cpu: 500m
              memory: 512Mi
      volumes:
        - name: config
          configMap:
            name: benthos-checkout-processor
```

Benthos vs Kafka Streams vs Flink vs custom consumer: Kafka Streams and Flink are the right choice for stateful stream processing — windowed aggregations, joins across streams, exactly-once state updates. They're Java-native and require understanding the stream processing model (stateful operators, changelogs). Benthos is better for stateless ETL: read from Kafka, transform, write to another system. No Java, no cluster, no state management — just a config file and a binary. Custom consumers (Go/Python reading from Kafka and writing somewhere) are appropriate when you need precise control over the processing logic, have non-standard requirements, or want to avoid a dependency. Benthos sits in the middle: more expressive than a custom consumer (fan-out, DLQ, retries built in), less powerful than Flink (no windowed state). For pipelines that are mostly transformation (map-filter-route), Benthos wins on simplicity.
