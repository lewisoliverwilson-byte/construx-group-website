React is fast. The default rendering behavior is good enough for most apps, most of the time. Premature optimization — memoizing everything, aggressively managing re-renders — adds complexity without benefit. Measure first.

## Measuring

Open Chrome DevTools → Performance → record while using the slow part of your app. Look for:

- Long tasks (>50ms) — these block the main thread and cause jank
- Component re-renders — React DevTools Profiler shows what rendered and why
- Layout thrash — forced synchronous layouts after DOM mutations

The React DevTools Profiler is the right tool for React-specific problems:

```tsx
// Wrap a section to profile it
import { Profiler } from 'react';

function onRender(
  id: string,
  phase: 'mount' | 'update' | 'nested-update',
  actualDuration: number,
) {
  if (actualDuration > 16) {  // 16ms = 60fps budget
    console.warn(`Slow render: ${id} took ${actualDuration.toFixed(1)}ms (${phase})`);
  }
}

<Profiler id="PostList" onRender={onRender}>
  <PostList posts={posts} />
</Profiler>
```

## memo

`React.memo` prevents a component from re-rendering if its props haven't changed:

```tsx
// PostCard re-renders every time PostList re-renders — even if the post itself didn't change
function PostCard({ post, onBookmark }: { post: Post; onBookmark: (id: string) => void }) {
  return (
    <div>
      <h2>{post.title}</h2>
      <button onClick={() => onBookmark(post.id)}>Bookmark</button>
    </div>
  );
}

// memo wraps it — now only re-renders when post or onBookmark changes
const PostCard = memo(function PostCard({ post, onBookmark }: { ... }) {
  return (...);
});
```

The trap: if `onBookmark` is defined inline in the parent, it's a new function reference on every render, defeating memo:

```tsx
// Bad — new function on every render, memo doesn't help
function PostList({ posts }: { posts: Post[] }) {
  return posts.map((post) => (
    <PostCard
      key={post.id}
      post={post}
      onBookmark={(id) => bookmarkPost(id)}  // new function every render
    />
  ));
}

// Good — stable function reference
function PostList({ posts }: { posts: Post[] }) {
  const handleBookmark = useCallback((id: string) => {
    bookmarkPost(id);
  }, []);  // stable unless bookmarkPost changes

  return posts.map((post) => (
    <PostCard key={post.id} post={post} onBookmark={handleBookmark} />
  ));
}
```

## useMemo

Cache an expensive computed value:

```tsx
function Analytics({ events }: { events: Event[] }) {
  // Bad — recalculates on every render
  const processed = events
    .filter((e) => e.type === 'pageview')
    .reduce((acc, e) => {
      acc[e.path] = (acc[e.path] ?? 0) + 1;
      return acc;
    }, {} as Record<string, number>);

  // Good — only recalculates when events changes
  const processed = useMemo(() => {
    return events
      .filter((e) => e.type === 'pageview')
      .reduce((acc, e) => {
        acc[e.path] = (acc[e.path] ?? 0) + 1;
        return acc;
      }, {} as Record<string, number>);
  }, [events]);

  return <BarChart data={processed} />;
}
```

Only useMemo for genuinely expensive computation. A filter + reduce over 10 items is not expensive — over 10,000 items, it might be.

## Virtualization

Rendering 1,000 rows means 1,000 DOM nodes. The browser has to layout, paint, and composite all of them. Virtualization renders only the rows visible in the viewport.

```bash
npm install @tanstack/react-virtual
```

```tsx
import { useVirtualizer } from '@tanstack/react-virtual';

function VirtualList({ items }: { items: Post[] }) {
  const parentRef = useRef<HTMLDivElement>(null);

  const virtualizer = useVirtualizer({
    count: items.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 72,    // estimated row height
    overscan: 5,               // render 5 extra rows above/below viewport
  });

  return (
    <div ref={parentRef} style={{ height: '600px', overflow: 'auto' }}>
      <div style={{ height: virtualizer.getTotalSize(), position: 'relative' }}>
        {virtualizer.getVirtualItems().map((virtualItem) => (
          <div
            key={virtualItem.key}
            data-index={virtualItem.index}
            ref={virtualizer.measureElement}
            style={{
              position: 'absolute',
              top: 0,
              left: 0,
              width: '100%',
              transform: `translateY(${virtualItem.start}px)`,
            }}
          >
            <PostRow post={items[virtualItem.index]} />
          </div>
        ))}
      </div>
    </div>
  );
}
```

Use virtualization for lists over ~100 items, especially if each item is complex.

## Deferred updates with useTransition

Mark a state update as non-urgent so React can interrupt it to handle more important work:

```tsx
function SearchWithTransition() {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState<Post[]>([]);
  const [isPending, startTransition] = useTransition();

  const handleSearch = (value: string) => {
    setQuery(value);  // urgent — update the input immediately

    startTransition(() => {
      // Non-urgent — can be deferred if something more important comes in
      setResults(searchPosts(value));
    });
  };

  return (
    <div>
      <input value={query} onChange={(e) => handleSearch(e.target.value)} />
      {isPending ? <Spinner /> : <ResultsList results={results} />}
    </div>
  );
}
```

## When NOT to optimize

- memo on small components — the comparison has overhead too
- useMemo for cheap calculations — the memoization is slower than just recalculating
- Optimizing before you have a specific measured problem

The sequence: profile → identify the bottleneck → apply the smallest fix that solves it. A component that re-renders 10ms more than it should doesn't need optimization. A list rendering 10,000 items with no virtualization does.
