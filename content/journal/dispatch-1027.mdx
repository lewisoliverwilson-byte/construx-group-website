excerpt: "Crossplane extends Kubernetes to manage cloud infrastructure — AWS, GCP, Azure — using the Kubernetes API. You define an RDS database, S3 bucket, or GKE cluster as a Kubernetes Custom Resource, and the Crossplane provider reconciles the desired state against the cloud API. The model is the same as any Kubernetes controller: you declare what you want, the controller makes it real, and it continuously corrects drift. Crossplane adds a composition layer: you can define an XRD (Composite Resource Definition) that creates a 'Database' abstraction which internally provisions an RDS instance, a security group, a parameter group, and a Secrets Manager secret — all from a single kubectl apply. Application teams get a simple interface ('give me a database') without needing to know the underlying AWS resources. Platform teams control the composition, enforcing org-wide standards in code."

## Provider installation and configuration

```bash
# Install Crossplane
helm repo add crossplane-stable https://charts.crossplane.io/stable
helm upgrade --install crossplane crossplane-stable/crossplane \
  --namespace crossplane-system \
  --create-namespace

# Install the AWS provider
kubectl apply -f - <<EOF
apiVersion: pkg.crossplane.io/v1
kind: Provider
metadata:
  name: provider-aws-rds
spec:
  package: xpkg.upbound.io/upbound/provider-aws-rds:v1.14.0
EOF

# Configure provider credentials (using IRSA on EKS)
kubectl apply -f - <<EOF
apiVersion: aws.upbound.io/v1beta1
kind: ProviderConfig
metadata:
  name: default
spec:
  credentials:
    source: IRSA   # IAM Role for Service Accounts — no static keys
EOF
```

## Managed resources — direct cloud API

```yaml
# Managed resource: directly provisions an AWS RDS instance
# Crossplane reconciles continuously — if someone deletes it in the AWS console,
# Crossplane creates it again

apiVersion: rds.aws.upbound.io/v1beta1
kind: Instance
metadata:
  name: construx-postgres-prod
  annotations:
    crossplane.io/external-name: construx-postgres-prod  # AWS resource name
spec:
  forProvider:
    region: eu-west-1
    dbInstanceClass: db.t3.large
    engine: postgres
    engineVersion: "16.2"
    dbName: construx
    allocatedStorage: 100
    storageType: gp3
    multiAZ: true
    deletionProtection: true
    backupRetentionPeriod: 14
    vpcSecurityGroupIDRefs:
      - name: construx-rds-sg
    dbSubnetGroupNameRef:
      name: construx-private-subnet-group
    passwordSecretRef:
      namespace: crossplane-system
      name: construx-rds-password
      key: password

  writeConnectionSecretsToRef:
    namespace: construx-prod
    name: construx-postgres-connection   # Kubernetes Secret with DSN

---
# S3 bucket with versioning and server-side encryption
apiVersion: s3.aws.upbound.io/v1beta1
kind: Bucket
metadata:
  name: construx-uploads-prod
spec:
  forProvider:
    region: eu-west-1

---
apiVersion: s3.aws.upbound.io/v1beta1
kind: BucketVersioning
metadata:
  name: construx-uploads-prod-versioning
spec:
  forProvider:
    region: eu-west-1
    bucketRef:
      name: construx-uploads-prod
    versioningConfiguration:
      - status: Enabled

---
apiVersion: s3.aws.upbound.io/v1beta1
kind: BucketServerSideEncryptionConfiguration
metadata:
  name: construx-uploads-prod-sse
spec:
  forProvider:
    region: eu-west-1
    bucketRef:
      name: construx-uploads-prod
    rule:
      - applyServerSideEncryptionByDefault:
          - sseAlgorithm: aws:kms
```

## Composite resources — the abstraction layer

```yaml
# XRD: define a 'Database' abstraction that application teams request
# Platform team controls what resources are actually created underneath

apiVersion: apiextensions.crossplane.io/v1
kind: CompositeResourceDefinition
metadata:
  name: xdatabases.construx.io
spec:
  group: construx.io
  names:
    kind: XDatabase
    plural: xdatabases

  claimNames:
    kind: Database         # application teams create Claims, not Composites
    plural: databases

  versions:
    - name: v1alpha1
      served: true
      referenceable: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                parameters:
                  type: object
                  properties:
                    storageGB:
                      type: integer
                      default: 20
                    tier:
                      type: string
                      enum: [small, medium, large]

---
# Composition: what a 'Database' actually creates
apiVersion: apiextensions.crossplane.io/v1
kind: Composition
metadata:
  name: database-aws-postgres
spec:
  compositeTypeRef:
    apiVersion: construx.io/v1alpha1
    kind: XDatabase

  resources:
    - name: rds-instance
      base:
        apiVersion: rds.aws.upbound.io/v1beta1
        kind: Instance
        spec:
          forProvider:
            region: eu-west-1
            engine: postgres
            engineVersion: "16.2"
      patches:
        - type: FromCompositeFieldPath
          fromFieldPath: spec.parameters.storageGB
          toFieldPath: spec.forProvider.allocatedStorage

---
# Claim: application team requests a database (simple interface)
apiVersion: construx.io/v1alpha1
kind: Database
metadata:
  name: payments-db
  namespace: construx-prod
spec:
  parameters:
    storageGB: 50
    tier: medium
  writeConnectionSecretsToRef:
    name: payments-db-connection   # connection string written here automatically
```

Crossplane vs Terraform vs Pulumi vs AWS CDK vs manual kubectl: Terraform and Pulumi apply changes explicitly — you run a plan, review it, apply it. Crossplane applies continuously — like a Kubernetes controller, it watches actual cloud state and corrects drift automatically, which is more resilient but less predictable. AWS CDK generates CloudFormation, which has its own state management and provider limitations. Crossplane's advantage is that it lives entirely in Kubernetes: no separate state backend, no separate CLI to run, no separate CI step — just YAML applied to the cluster. The composition model lets platform teams hide AWS complexity behind simpler abstractions. The operational downside is that Crossplane is more complex to troubleshoot than Terraform: a stuck managed resource requires understanding the controller reconcile loop, not just reading a plan output.
