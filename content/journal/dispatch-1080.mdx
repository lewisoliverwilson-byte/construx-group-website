title: "Telepresence: local Kubernetes development — cluster traffic intercept, fast inner loop"
date: "2033-10-28"
excerpt: "Telepresence is a CNCF tool that connects your local development machine to a remote Kubernetes cluster, making the cluster's network and services accessible as if your machine were a pod inside the cluster. The core feature is traffic intercept: Telepresence replaces a Deployment in the cluster with a proxy, then forwards incoming traffic to that service to your local process. You run construx-api locally (with hot reload, a local debugger attached, printf debugging), and production traffic hits your local process. This closes the dev-to-production gap without deploying a container image. Telepresence also supports personal intercepts (intercept only traffic matching a specific HTTP header, leaving production traffic unaffected), which allows multiple developers to intercept the same service simultaneously for independent testing. The Telepresence daemon runs on your machine and sets up a two-way network tunnel: your local process can reach cluster services (postgres.construx-prod.svc.cluster.local) by DNS name, and cluster traffic destined for the intercepted service reaches your local port. The result is a development workflow where you iterate at local speed (sub-second hot reload) without needing to build and push a Docker image on every change."

Traffic intercept. Personal intercept. Cluster DNS resolution. Local hot reload. Inner loop.

## Telepresence setup and traffic intercept

```bash
# Install Telepresence CLI
brew install datawire/blackbird/telepresence   # macOS

# Connect to the cluster (installs Traffic Manager in cluster if not present)
telepresence connect --namespace construx-prod
# Launching Telepresence User Daemon...
# Connected to context construx-prod (https://api.construx.io)
# Status: connected

# Check connection status
telepresence status
# Root Daemon: Running
# User Daemon: Running
# Kubernetes context: construx-prod
# Namespace: construx-prod
# Intercepts: 0 total

# At this point, cluster DNS is accessible from your local machine:
curl http://construx-api.construx-prod.svc.cluster.local/healthz
# {"status":"ok","version":"v1.42.0"}   ← hitting the cluster pod directly

curl http://postgres.construx-prod.svc.cluster.local:5432
# (can connect to Postgres in the cluster from your local psql client)
```

```bash
# Global intercept: replace construx-api in the cluster with your local process
# ALL traffic to construx-api now goes to localhost:8080
telepresence intercept construx-api \
  --port 8080:8080 \
  --namespace construx-prod

# Intercept is active:
# Using Deployment construx-api
# intercepted
#     Intercept name     : construx-api
#     State              : ACTIVE
#     Workload kind      : Deployment
#     Namespace          : construx-prod
#     Service port name  : http
#     Volume Mount Point : /tmp/telfs-...
#     Intercepting       : all TCP requests

# Now run your service locally (with hot reload, debugger, whatever)
bun run dev   # or: go run ., cargo run, python app.py

# Traffic from other pods trying to reach construx-api → your local process
# Mounted volumes (ConfigMaps, Secrets) are accessible at the volume mount point

# Personal intercept: only intercept requests with X-Dev-Intercept: lewis header
# Other traffic continues hitting the real pod in the cluster
telepresence intercept construx-api \
  --port 8080:8080 \
  --namespace construx-prod \
  --http-header X-Dev-Intercept=lewis \
  --mechanism http

# Send test request to your intercept
curl -H "X-Dev-Intercept: lewis" \
  http://construx-api.construx-prod.svc.cluster.local/api/v1/orders
# → hits your local process

curl http://construx-api.construx-prod.svc.cluster.local/api/v1/orders
# → hits the real pod in the cluster (no intercept header)
```

```bash
# Ambassador Cloud: team intercepts management
# (optional — allows sharing intercept previews with team members)

# Create a preview URL for your intercept
telepresence intercept construx-api \
  --port 8080:8080 \
  --preview-url=true

# Intercept preview URL:
# https://construx-api-preview-xyz.preview.edgestack.me
# Share this URL with a teammate — their requests reach your local process

# List all active intercepts (across team)
telepresence list
# construx-api: intercepted by lewis (personal: X-Dev-Intercept=lewis)
# construx-worker: intercepted by james (personal: X-Dev-Intercept=james)

# Leave intercept (cluster traffic resumes hitting the real pod)
telepresence leave construx-api

# Disconnect (removes Traffic Manager from cluster if no other users)
telepresence quit
```

Telepresence vs Skaffold vs port-forward vs minikube vs no-local-dev: kubectl port-forward creates a local port bound to a specific pod — you can reach the pod, but the pod cannot reach your local machine (one-way). Minikube/kind runs a local Kubernetes cluster — isolated from production, so you need to replicate all dependencies (databases, other services) locally. Skaffold (covered in dispatch-1055) automates build-push-deploy for inner loop development but still requires a container build and push on every change. Telepresence is the only option that gives you bidirectional cluster traffic with your local process as a first-class cluster participant — no Docker build, no image push, and access to all real cluster services (the staging database, the staging Redis, the staging Kafka). The trade-off: intercepting production traffic with your local process means bugs in your code can affect production requests (use personal intercepts to avoid this). For teams where the dev environment gap (local vs Kubernetes) is causing bugs that only appear in staging, Telepresence collapses that gap at the cost of some complexity in the Traffic Manager deployment.
