A feature flag is a conditional that controls whether a code path runs. The flag value comes from configuration rather than the code itself, which means you can change it without deploying. Ship the code. Turn it on for 1% of users. Watch for errors. Ramp to 100%. Roll back instantly if something breaks.

## A minimal server-side flag system

For a Next.js App Router product, server-side evaluation is the right starting point. Flags are evaluated at request time, not in the browser:

```ts
// lib/flags.ts
interface FlagDefinition {
  defaultValue: boolean;
  rollout?: number; // 0–100 percentage
  allowlist?: string[]; // user IDs always enabled
  denylist?: string[]; // user IDs always disabled
}

const FLAGS: Record<string, FlagDefinition> = {
  new_dashboard:    { defaultValue: false, rollout: 10 },
  ai_suggestions:   { defaultValue: false, allowlist: ['user_abc', 'user_xyz'] },
  redesigned_nav:   { defaultValue: true,  rollout: 100 },
};

function hashUser(userId: string, flagName: string): number {
  let hash = 0;
  const input = `${flagName}:${userId}`;
  for (let i = 0; i < input.length; i++) {
    hash = ((hash << 5) - hash + input.charCodeAt(i)) | 0;
  }
  return Math.abs(hash) % 100;
}

export function isEnabled(flagName: string, userId?: string): boolean {
  const flag = FLAGS[flagName];
  if (!flag) return false;
  if (!userId) return flag.defaultValue;
  if (flag.denylist?.includes(userId)) return false;
  if (flag.allowlist?.includes(userId)) return true;
  if (flag.rollout !== undefined) {
    return hashUser(userId, flagName) < flag.rollout;
  }
  return flag.defaultValue;
}
```

The hash function is the key to consistent rollout: the same user always gets the same bucket (0–99), so they don't flip between enabled and disabled on each request.

## Using flags in Server Components

```tsx
// app/dashboard/page.tsx
import { isEnabled } from '@/lib/flags';
import { getCurrentUser } from '@/lib/auth';

export default async function DashboardPage() {
  const user = await getCurrentUser();
  const showNewDashboard = isEnabled('new_dashboard', user?.id);

  return showNewDashboard ? (
    <NewDashboard userId={user.id} />
  ) : (
    <LegacyDashboard userId={user.id} />
  );
}
```

No client-side flicker. No layout shift. The flag is evaluated before the HTML is rendered.

## Persisted flags with PostHog

For a production product, you want:
1. Flags stored outside your codebase so non-engineers can change them
2. Analytics on flag exposure so you can measure impact
3. A/B testing capability

PostHog handles all of this:

```ts
// lib/posthog-flags.ts
import { PostHog } from 'posthog-node';

const client = new PostHog(process.env.POSTHOG_API_KEY!, {
  host: process.env.POSTHOG_HOST,
});

export async function getFeatureFlag(
  flagKey: string,
  userId: string,
  userProperties?: Record<string, string | number | boolean>,
): Promise<boolean> {
  const value = await client.isFeatureEnabled(flagKey, userId, {
    personProperties: userProperties,
  });
  return value === true;
}
```

```tsx
// In a Server Component
const showFeature = await getFeatureFlag('new_checkout', user.id, {
  plan: user.plan,
  country: user.country,
});
```

PostHog evaluates flag targeting rules on the server (matching on user properties, percentages, cohorts). The analytics pipeline records flag exposure automatically — you can measure whether users in the flag-enabled group convert better.

## Cleanup

Feature flags are technical debt. A flag that's been 100% rolled out for a month should be deleted and the condition removed. A flag for a feature that was killed should be deleted immediately.

Add a comment when you create a flag:

```ts
const FLAGS = {
  // TODO: Remove after 2027-08-01 rollout complete
  new_dashboard: { defaultValue: false, rollout: 10 },
};
```

The date forces the conversation. When it passes, the flag should either be promoted to permanent code or deleted. Never let flags accumulate silently — they become untestable dead code paths.
