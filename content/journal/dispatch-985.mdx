excerpt: "Nomad is HashiCorp's workload orchestrator — it runs containers (Docker, Podman), VMs (QEMU), raw executables, and Java JARs across a cluster of machines. Unlike Kubernetes, Nomad's data model is simpler: a Job describes what you want to run, the scheduler places it on a node, and the client executes it. Nomad integrates natively with Consul (service discovery) and Vault (secrets). The operational simplicity argument: a single Nomad binary runs both the server (scheduler) and client (executor), and the entire cluster is configured with a single HCL file. For teams running non-containerized workloads — batch jobs, Windows services, legacy JARs — Nomad handles them alongside containers without requiring Kubernetes's container-first model."

## Job specification

```hcl
# construx-api.nomad — Nomad job file (HCL)
job "construx-api" {
  # Datacenter and region
  datacenters = ["eu-west-1"]
  region      = "eu"
  type        = "service"   # always running (vs batch = run once, sysbatch = periodic)

  # Update strategy: rolling deploy
  update {
    max_parallel     = 1           # update one allocation at a time
    min_healthy_time = "30s"       # wait 30s before updating next
    healthy_deadline = "3m"        # fail if not healthy within 3m
    auto_revert      = true        # revert if new version is unhealthy
    canary           = 1           # deploy 1 canary first
    auto_promote     = false       # require manual promotion of canary
  }

  # Group: unit of colocation (like a Kubernetes Pod)
  group "api" {
    count = 3   # run 3 instances

    # Spread across availability zones
    spread {
      attribute = "${meta.availability_zone}"
      weight    = 100
    }

    network {
      port "http" { to = 8080 }    # dynamic port mapping → container port 8080
      port "metrics" { to = 9090 }
    }

    # Consul service registration (automatic with Consul integration)
    service {
      name = "construx-api"
      port = "http"
      tags = ["v1", "production"]

      check {
        type     = "http"
        path     = "/health"
        interval = "10s"
        timeout  = "3s"
      }
    }

    # Task: the actual workload
    task "api" {
      driver = "docker"   # or: exec, raw_exec, java, qemu

      config {
        image   = "registry.construx.io/construx/api:v1.8.3"
        ports   = ["http", "metrics"]
        volumes = ["/data/construx:/data"]
      }

      # Resource allocation
      resources {
        cpu    = 500    # MHz (not millicores — Nomad uses MHz)
        memory = 512    # MiB
        memory_max = 768  # allow burst above reservation
      }

      # Environment variables
      env {
        LOG_LEVEL = "warn"
        PORT      = "${NOMAD_PORT_http}"    # Nomad injects the dynamic port
      }

      # Secrets from Vault (Nomad → Vault → template)
      template {
        data = <<EOT
{{ with secret "secret/data/construx/db" }}
DATABASE_URL=postgres://construx:{{ .Data.data.password }}@{{ env "NOMAD_IP_http" }}:5432/construx_prod
{{ end }}
EOT
        destination = "secrets/db.env"
        env         = true   # load as environment variables
        change_mode = "restart"  # restart the task when the secret changes
      }

      # Vault policy access
      vault {
        policies  = ["construx-api"]
        change_mode = "noop"
      }
    }
  }
}
```

## Running jobs

```bash
# Install Nomad
brew tap hashicorp/tap
brew install hashicorp/tap/nomad
nomad version
# Nomad v1.9.4

# Start a dev agent (single node, in-memory — for local testing)
nomad agent -dev &

# Validate job file syntax
nomad job validate construx-api.nomad

# Plan: see what will change (like terraform plan)
nomad job plan construx-api.nomad
# + Job: "construx-api"
# + Task Group: "api" (3 create)
#   + Task: "api" (forces create)
#     + Resources: CPU=500 MHz, Memory=512 MiB
#     + docker image: registry.construx.io/construx/api:v1.8.3
# Job Modify Index: 0
# To submit the job with version verification, use:
#   nomad job run -check-index 0 construx-api.nomad

# Submit the job
nomad job run construx-api.nomad
# ==> Monitoring evaluation "abc123..."
# ==> Evaluation "abc123" finished with status "complete"

# Check job status
nomad job status construx-api
```

## Batch and system jobs

```hcl
# Batch job: run once and exit
job "db-migration" {
  type = "batch"

  group "migration" {
    count = 1

    task "migrate" {
      driver = "docker"

      config {
        image   = "registry.construx.io/construx/api:v1.8.3"
        command = "/app/construx"
        args    = ["migrate", "up"]
      }

      resources {
        cpu    = 200
        memory = 256
      }

      # Restart policy: don't restart on failure (it's a migration)
      restart {
        attempts = 0
        mode     = "fail"
      }
    }
  }
}

# Periodic job (cron): run on a schedule
job "nightly-report" {
  type = "batch"

  periodic {
    cron             = "0 2 * * *"   # 02:00 UTC every night
    prohibit_overlap = true           # skip if previous run is still running
  }

  group "report" {
    count = 1
    task "generate" {
      driver = "docker"
      config {
        image = "registry.construx.io/construx/reporter:latest"
      }
      resources {
        cpu    = 1000
        memory = 2048
      }
    }
  }
}

# System job: run exactly one allocation per node (like a DaemonSet)
job "node-exporter" {
  type = "system"
  group "monitoring" {
    task "node-exporter" {
      driver = "docker"
      config {
        image        = "prom/node-exporter:v1.8.2"
        network_mode = "host"
        pid_mode     = "host"
      }
      resources {
        cpu    = 100
        memory = 64
      }
    }
  }
}
```

## Nomad vs Kubernetes

```bash
# The core difference in operational model:

# Kubernetes: container-first, complex, feature-rich
# - Pods, Deployments, StatefulSets, DaemonSets, Jobs, CronJobs
# - 30+ resource types before you add CRDs
# - Requires etcd, kube-apiserver, kube-scheduler, kube-controller-manager,
#   kubelet, kube-proxy, CNI, CSI — minimum 6 components
# - Industry standard for containers
# - Huge ecosystem (Helm, Kustomize, ArgoCD, Flux, Karpenter...)

# Nomad: workload-first, simple, multi-runtime
# - One binary: both server and client
# - One resource type: Job
# - Runs Docker, raw executables, JARs, VMs, and batch jobs equally
# - Native Consul + Vault integration
# - Good for: mixed workloads, legacy apps, edge/IoT, smaller teams

# Nomad CLI quick reference
nomad job list                    # list all jobs
nomad job status <name>           # detailed job status
nomad alloc list -job=<name>      # list allocations for a job
nomad alloc logs <alloc-id> <task># stream logs
nomad alloc exec <alloc-id> <cmd> # exec into an allocation
nomad node status                 # cluster node status
nomad monitor                     # stream cluster events

# Deploy a new version (rolling update)
nomad job run -check-index <modify-index> construx-api.nomad
# Nomad updates one allocation at a time, respecting min_healthy_time
# auto_revert=true means it rolls back if the new version fails health checks
```

Nomad vs Kubernetes: the argument for Nomad is simplicity and flexibility — one binary, one resource type (Job), and support for non-container workloads. If you're running Windows services, legacy JARs, or bare-metal executables alongside containers, Nomad handles them uniformly. Kubernetes's strength is its ecosystem — a decade of tooling, the largest community, and the widest cloud provider support. Most teams reaching for an orchestrator in 2033 should default to Kubernetes unless they have a specific reason (existing HashiCorp stack, non-container workloads, simpler operational model). Nomad makes most sense as part of the HashiCorp platform (Vault + Consul + Nomad + Boundary) where the integrations are first-class.
