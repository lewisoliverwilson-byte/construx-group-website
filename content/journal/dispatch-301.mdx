Service workers are a browser API that puts a programmable proxy between your app and the network. Requests go through the service worker before they reach the server; responses come back through it too. The worker can cache responses, serve cached content when offline, and run code in the background even when the page is closed.

That's a lot of surface area. Most apps need three things: a cache for static assets, an offline fallback page, and a sensible strategy for API calls.

## Registration

```ts
// app/layout.tsx or a client component
if (typeof window !== 'undefined' && 'serviceWorker' in navigator) {
  window.addEventListener('load', () => {
    navigator.serviceWorker.register('/sw.js').catch(console.error);
  });
}
```

The service worker file must be served from the root of your domain (or a sub-path that controls only that scope). For Next.js, place it in `/public/sw.js` — it will be served at `/sw.js`.

## The install event: pre-caching static assets

```js
// public/sw.js
const CACHE_VERSION = 'v1';
const STATIC_CACHE = `construx-static-${CACHE_VERSION}`;

const PRECACHE_URLS = [
  '/',
  '/offline',
  '/manifest.json',
];

self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open(STATIC_CACHE).then((cache) => {
      return cache.addAll(PRECACHE_URLS);
    }).then(() => self.skipWaiting())
  );
});
```

`skipWaiting()` makes the new service worker take over immediately on install, without waiting for the page to be refreshed. Pair it with `clients.claim()` in the activate event.

## The activate event: cleaning up old caches

```js
self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then((keys) => {
      return Promise.all(
        keys
          .filter((key) => key !== STATIC_CACHE)
          .map((key) => caches.delete(key))
      );
    }).then(() => self.clients.claim())
  );
});
```

Old cache versions accumulate. The activate event is the right place to delete them. `clients.claim()` makes the freshly activated worker control all existing tabs immediately.

## The fetch event: caching strategies

Different resources need different strategies:

**Cache-first for static assets** — serve from cache, fall back to network:

```js
function isStaticAsset(url) {
  return url.pathname.startsWith('/_next/static/') ||
    url.pathname.match(/\.(js|css|woff2|png|jpg|svg|ico)$/);
}

self.addEventListener('fetch', (event) => {
  const url = new URL(event.request.url);

  if (isStaticAsset(url)) {
    event.respondWith(
      caches.match(event.request).then((cached) => {
        return cached ?? fetch(event.request).then((response) => {
          const clone = response.clone();
          caches.open(STATIC_CACHE).then((cache) => cache.put(event.request, clone));
          return response;
        });
      })
    );
    return;
  }

  // For everything else: network-first with offline fallback
  event.respondWith(
    fetch(event.request).catch(() => {
      if (event.request.mode === 'navigate') {
        return caches.match('/offline');
      }
      return new Response('Offline', { status: 503 });
    })
  );
});
```

**Network-first for pages and API calls** — always try the network, fall back to cache if offline. The offline fallback page `/offline` was pre-cached in the install event.

## The offline page

A minimal page that renders without any network requests:

```tsx
// app/offline/page.tsx
export default function OfflinePage() {
  return (
    <div className="min-h-screen flex items-center justify-center px-5">
      <div className="text-center max-w-sm">
        <p className="font-mono text-sm text-text-dim mb-4">// NO NETWORK</p>
        <h1 className="text-2xl font-bold text-text-base mb-3">You're offline</h1>
        <p className="text-text-muted text-sm leading-relaxed">
          Check your connection and try again. Content you've visited before may still be available.
        </p>
      </div>
    </div>
  );
}
```

## Versioning

The cache version string in `STATIC_CACHE` controls when the cache is invalidated. Bump `CACHE_VERSION` when you want to force a full re-cache on next visit. A timestamp works: `const CACHE_VERSION = '2027-06-02'`.

Without versioning, users can get stuck on stale assets that will never be updated — because the cache-first strategy never checks the network.

## What to skip

Background sync (queuing form submissions to retry when online) is genuinely useful for some apps. For most, it's over-engineering. Push notifications require user permission and careful messaging. Pre-caching entire route segments is cache management you don't need if your pages are fast.

The useful 20% of service worker capability covers 80% of real offline needs: pre-cache the shell, serve statics from cache, show an offline page when navigation fails. That's the implementation above. Start there.

## Next.js specifics

Next.js generates unique hashes for `/_next/static/` assets on every build. The cache-first strategy above handles this correctly: new asset URLs are treated as cache misses and fetched fresh. Old asset URLs in old caches get cleaned up in the activate event.

The `next-pwa` package automates more of this, but it adds complexity you often don't need. The manual approach above is about 80 lines and does the right thing.
