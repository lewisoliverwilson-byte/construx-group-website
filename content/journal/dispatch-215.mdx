A schema migration is a change to the database structure: adding a column, dropping a table, changing a data type, adding an index. In development, migrations are cheap — run them, test, move on. In production, a bad migration can lock tables, corrupt data, or bring down the application.

Here's how we approach migrations safely.

## The core risk: table locks

Most `ALTER TABLE` operations in PostgreSQL acquire a full table lock for the duration of the operation. While the lock is held, no reads or writes can proceed on that table.

For a small table, this is milliseconds — imperceptible. For a large table with millions of rows, it's seconds or minutes. During that time, every request that touches the table fails or queues.

```sql
-- This locks the entire table for the duration
ALTER TABLE messages ADD COLUMN pinned BOOLEAN;
```

On a table with 10M rows, this is a problem. On a table with 1K rows, it isn't. Knowing which migrations are dangerous requires knowing your table sizes.

## Safe migration patterns

**Adding a nullable column:** Safe. PostgreSQL 11+ adds nullable columns without a table rewrite if there's no default or the default is literal `NULL`. Zero locks.

```sql
-- Safe: no lock, no rewrite
ALTER TABLE messages ADD COLUMN pinned BOOLEAN;
```

**Adding a column with a default:** In PostgreSQL 11+, adding a column with a `DEFAULT` is also safe (the default is stored in the catalog, not written to every row immediately). Earlier versions required a full table rewrite — dangerous at scale.

```sql
-- Safe in Postgres 11+ (stored default, no rewrite)
ALTER TABLE messages ADD COLUMN pinned BOOLEAN DEFAULT false;
```

**Adding a NOT NULL constraint:** Dangerous on large tables. PostgreSQL must scan every row to verify the constraint. The scan holds an `ACCESS EXCLUSIVE` lock.

```sql
-- Dangerous on large tables: full scan + lock
ALTER TABLE messages ADD COLUMN status TEXT NOT NULL DEFAULT 'active';
```

The safe pattern for large tables: add the column as nullable, backfill, then add the constraint after:

```sql
-- Step 1: add nullable (safe)
ALTER TABLE messages ADD COLUMN status TEXT;

-- Step 2: backfill in batches (safe, no lock)
UPDATE messages SET status = 'active' WHERE status IS NULL AND id < 100000;
UPDATE messages SET status = 'active' WHERE status IS NULL AND id BETWEEN 100000 AND 200000;
-- ... continue in batches

-- Step 3: add NOT NULL now that all rows are filled (fast check)
ALTER TABLE messages ALTER COLUMN status SET NOT NULL;
```

**Adding an index:** Creating an index locks the table. The safe alternative is `CREATE INDEX CONCURRENTLY`:

```sql
-- Dangerous: locks the table
CREATE INDEX messages_workspace_idx ON messages(workspace_id);

-- Safe: no lock, but takes longer and can't run in a transaction
CREATE INDEX CONCURRENTLY messages_workspace_idx ON messages(workspace_id);
```

`CONCURRENTLY` can't run inside a transaction block. This means it can't be part of a standard migration transaction. We run these as separate migration steps outside the transaction.

## Our migration tooling

We use Drizzle Kit for migration generation. Drizzle reads the schema definition (TypeScript) and generates SQL migrations for schema changes.

```ts
// schema.ts — the source of truth
export const messages = pgTable('messages', {
  id: uuid('id').primaryKey().defaultRandom(),
  workspaceId: uuid('workspace_id').notNull(),
  content: text('content').notNull(),
  authorId: uuid('author_id').notNull(),
  pinned: boolean('pinned').default(false),
  createdAt: timestamp('created_at').defaultNow(),
});
```

`drizzle-kit generate` produces a SQL migration from the diff between the current schema and the database state. We review every generated migration before running it.

## The deployment sequence

Our deployment sequence for schema changes:

1. **Deploy the migration first** (before code)
2. **Deploy the code** (after migration)

This sequence ensures the database schema is compatible with both the old code (still running during the migration window) and the new code. If the migration adds a column that the old code doesn't write to, that's fine — nullable columns with defaults are backward-compatible.

The reverse — deploying code that reads a new column before the column exists — produces errors in production.

For breaking changes (renaming or removing columns), we use a multi-step process:
1. Add the new column / add the new name
2. Deploy code that writes to both old and new
3. Backfill the new column from the old
4. Deploy code that reads from the new, ignores the old
5. Drop the old column

Each step is a separate deployment. It's slower but avoids the window where production code reads a column that doesn't exist.

## Rollback

Every migration should have a rollback plan. Drizzle Kit generates `up` migrations; we write corresponding `down` migrations manually.

For most additive changes (adding a column, adding an index), rolling back is trivial: `DROP COLUMN` or `DROP INDEX`. For changes that transform data (renaming a column, changing a type), rollback is harder or impossible if data has been written in the new format.

We classify migrations as:
- **Reversible:** Can roll back without data loss
- **Irreversible:** Cannot roll back without data loss (column type changes, removing tables)

Irreversible migrations require an explicit sign-off in the PR. We make sure the rollback plan is "accept the loss" or "restore from backup" before proceeding.

## What we've gotten wrong

**Running migrations in the same deployment as the code.** Early on, we deployed code and migrations simultaneously. This creates a window where the new code is running against the old schema (during the deployment) — which fails if the code expects new columns that don't exist yet.

**Not testing migrations against production data volume.** A migration that runs in &lt;1ms against a development database with 100 rows can take 5 minutes against a production table with 50M rows. We now test non-trivial migrations against a staging environment that mirrors production data volume.

**Forgetting `CONCURRENTLY`.** We've shipped index creation without `CONCURRENTLY` and created short table locks that caused visible latency spikes. The `CONCURRENTLY` flag is now checked in every migration review.

The discipline of treating migrations as potentially dangerous — even for small changes — has prevented several production incidents. Schema changes are the one area where moving slowly is worth it.
