title: "Longhorn: cloud-native distributed block storage for Kubernetes — replicated volumes, snapshots, backup"
date: "2033-09-16"
excerpt: "Longhorn is a CNCF distributed block storage system for Kubernetes. It runs entirely inside the cluster: each node that joins the Longhorn storage pool runs a Longhorn Manager daemonset and a Longhorn Engine instance per volume. When you create a PersistentVolumeClaim backed by the Longhorn StorageClass, Longhorn provisions a replicated volume — by default 3 replicas spread across 3 different nodes. Each replica is a sparse file on the node's disk; the Longhorn Engine synchronises writes to all replicas and handles replica rebuilding when a node fails. Longhorn volumes are mounted to pods via iSCSI. Longhorn includes a built-in snapshot and backup system: snapshots are space-efficient (copy-on-write deltas from the base layer), and backups ship the snapshot chain to S3 or NFS. Longhorn also supports volume expansion, encryption at rest (via LUKS), and recurring backup schedules. The Longhorn UI (deployed as a Kubernetes Deployment) shows volume health, replica distribution, and backup status in a web dashboard."

## Longhorn installation and StorageClass

```bash
# Install Longhorn via Helm
helm repo add longhorn https://charts.longhorn.io
helm repo update

helm install longhorn longhorn/longhorn \
  --namespace longhorn-system \
  --create-namespace \
  --set defaultSettings.defaultReplicaCount=3 \
  --set defaultSettings.storageMinimalAvailablePercentage=15 \
  --set defaultSettings.backupTarget=s3://construx-longhorn-backup@eu-west-2/ \
  --set defaultSettings.backupTargetCredentialSecret=longhorn-s3-secret \
  --set defaultSettings.concurrentAutomaticEngineUpgradePerNodeLimit=1 \
  --version 1.7.1

# Verify all Longhorn pods are running
kubectl get pods -n longhorn-system
# NAME                                        READY  STATUS   RESTARTS  AGE
# longhorn-manager-zk8j9                      1/1    Running  0         2m
# longhorn-manager-p2x4m                      1/1    Running  0         2m
# longhorn-manager-nq7k1                      1/1    Running  0         2m
# longhorn-driver-deployer-7b9f4c-r2k5s       1/1    Running  0         2m
# longhorn-ui-6d8b4c-p9j2n                    1/1    Running  0         2m
# csi-attacher-...                            1/1    Running  0         90s
# csi-provisioner-...                         1/1    Running  0         90s
```

```yaml
# StorageClass: Longhorn with 3 replicas, encrypted
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: longhorn-encrypted
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
provisioner: driver.longhorn.io
allowVolumeExpansion: true
reclaimPolicy: Retain    # keep volume data when PVC is deleted
volumeBindingMode: Immediate
parameters:
  numberOfReplicas:            "3"
  staleReplicaTimeout:         "30"     # minutes before a stale replica is removed
  diskSelector:                ""       # empty = any disk
  nodeSelector:                ""       # empty = any node
  # Encryption via LUKS — key stored in a Kubernetes secret
  encrypted:                   "true"
  csi.storage.k8s.io/provisioner-secret-name:       longhorn-crypto
  csi.storage.k8s.io/provisioner-secret-namespace:  longhorn-system
  csi.storage.k8s.io/node-publish-secret-name:      longhorn-crypto
  csi.storage.k8s.io/node-publish-secret-namespace: longhorn-system
---
# PersistentVolumeClaim: Longhorn-provisioned volume for stateful workload
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: construx-db-data
  namespace: construx-prod
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: longhorn-encrypted
  resources:
    requests:
      storage: 100Gi
```

## Snapshots and recurring backups

```yaml
# VolumeSnapshotClass: Longhorn CSI snapshot support
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: longhorn-snapshot
driver: driver.longhorn.io
deletionPolicy: Delete
parameters:
  type: snap   # in-cluster snapshot (not S3 backup — that's BackupTarget)
---
# VolumeSnapshot: on-demand snapshot of construx-db-data
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: construx-db-snapshot-20330916
  namespace: construx-prod
spec:
  volumeSnapshotClassName: longhorn-snapshot
  source:
    persistentVolumeClaimName: construx-db-data
---
# RecurringJob: scheduled backups to S3 via Longhorn CRD
apiVersion: longhorn.io/v1beta2
kind: RecurringJob
metadata:
  name: daily-backup
  namespace: longhorn-system
spec:
  cron:      "0 2 * * *"   # 02:00 UTC daily
  task:      backup          # ship to S3 backupTarget
  groups:    [default]       # apply to all volumes in the default group
  retain:    14              # keep 14 backup revisions
  concurrency: 1
```

```bash
  --type merge -p '{"spec":{"failedAt":"2033-09-16T03:00:00Z"}}'
# Longhorn detects degraded state, starts rebuilding on a healthy node
# Rebuilding: 100Gi at ~800MB/s ≈ 2 minutes
# Volume robustness: Degraded → Healthy after rebuild

# Volume expansion (online, no downtime)

  --type merge -p '{"spec":{"resources":{"requests":{"storage":"200Gi"}}}}'
# Longhorn expands the sparse file on all 3 replicas and resizes the filesystem
```

Longhorn vs Rook-Ceph vs AWS EBS CSI vs OpenEBS vs local-path: AWS EBS CSI is the correct answer for EKS workloads that don't need to share volumes across nodes — fast, managed, single-AZ block storage. Longhorn is correct for on-premise or bare-metal Kubernetes where cloud EBS isn't available, or when you need cross-node replica durability without managing Ceph. Rook-Ceph (covered earlier in this journal) is more capable than Longhorn — it supports block, object (S3-compatible), and file (CephFS) storage and handles larger-scale clusters — but it has higher operational complexity. Longhorn is simpler to install and operate for pure block storage use cases. OpenEBS is the closest alternative to Longhorn in terms of architecture (per-node engine, CSI driver); Longhorn edges it on backup UX and the built-in dashboard. Local-path provisioner (used by k3s by default) is a single-node solution with no replication — fine for dev clusters, not for production stateful workloads. For teams running bare-metal or on-premise Kubernetes who need replicated persistent volumes with automatic failover and S3-backed backups, Longhorn is the lowest-friction path.
