A monorepo keeps multiple projects in one repository. The appeal: shared code (types, components, utilities) without the overhead of publishing to a package registry. Changes to shared code don't require a publish/update cycle — they're immediately visible to dependent packages.

The cost: tooling complexity and slower CI if you rebuild everything on every change. Turborepo addresses the second problem.

## The workspace structure

```
my-monorepo/
├── apps/
│   ├── web/              # Next.js app
│   ├── api/              # Node.js API
│   └── docs/             # Documentation site
├── packages/
│   ├── ui/               # Shared React components
│   ├── database/         # Prisma schema + client
│   ├── types/            # Shared TypeScript types
│   └── config/           # Shared ESLint/Tailwind config
├── package.json          # Root workspace config
└── turbo.json            # Turborepo pipeline config
```

Root `package.json`:

```json
{
  "name": "my-monorepo",
  "private": true,
  "workspaces": ["apps/*", "packages/*"],
  "scripts": {
    "build": "turbo build",
    "dev":   "turbo dev",
    "lint":  "turbo lint",
    "test":  "turbo test"
  },
  "devDependencies": {
    "turbo": "^2.0.0"
  }
}
```

## Consuming a shared package

```json
// apps/web/package.json
{
  "name": "web",
  "dependencies": {
    "@repo/ui":       "*",
    "@repo/types":    "*",
    "@repo/database": "*"
  }
}
```

```tsx
// apps/web/app/page.tsx
import { Button } from '@repo/ui';
import type { User } from '@repo/types';
import { db } from '@repo/database';
```

The `*` version means "whatever is in the workspace" — no registry, no versioning needed for internal packages.

## turbo.json: defining the pipeline

```json
{
  "$schema": "https://turbo.build/schema.json",
  "pipeline": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": [".next/**", "dist/**"]
    },
    "dev": {
      "cache": false,
      "persistent": true
    },
    "lint": {
      "outputs": []
    },
    "test": {
      "dependsOn": ["build"],
      "outputs": ["coverage/**"]
    }
  }
}
```

`"dependsOn": ["^build"]` means: before building this package, build all its dependencies first. The `^` means "dependencies of this package in the workspace graph." Turborepo builds the dependency graph automatically from `package.json` dependencies.

`"outputs"`: files to cache. Turborepo hashes your inputs (source files, env vars), and if the hash matches a previous run, it restores from cache instead of running the command. This is the build acceleration.

## The shared UI package

```tsx
// packages/ui/src/Button.tsx
export interface ButtonProps extends React.ButtonHTMLAttributes<HTMLButtonElement> {
  variant?: 'primary' | 'secondary' | 'ghost';
  size?:    'sm' | 'md' | 'lg';
}

export function Button({ variant = 'primary', size = 'md', children, ...props }: ButtonProps) {
  return (
    <button className={`btn btn-${variant} btn-${size}`} {...props}>
      {children}
    </button>
  );
}
```

```json
// packages/ui/package.json
{
  "name": "@repo/ui",
  "main":    "./src/index.ts",
  "exports": {
    ".": "./src/index.ts"
  }
}
```

For TypeScript monorepos, pointing `main` directly at `.ts` files works if consuming apps run TypeScript. This avoids a build step in the shared package — consuming apps compile the TypeScript themselves as part of their own build.

## Shared database package

```ts
// packages/database/src/index.ts
import { PrismaClient } from '@prisma/client';

const globalForPrisma = global as unknown as { prisma: PrismaClient };

export const prisma = globalForPrisma.prisma ??= new PrismaClient();

if (process.env.NODE_ENV !== 'production') {
  globalForPrisma.prisma = prisma;
}

export * from '@prisma/client';
```

The Prisma schema lives in `packages/database/prisma/schema.prisma`. All apps import from `@repo/database` — one schema, one client instance.

## Remote caching

Turborepo's local cache is already valuable: if you run `turbo build` twice without changes, the second run restores from local cache in seconds. The remote cache extends this to CI and teammates.

Vercel hosts the remote cache. After `npx turbo login` and `npx turbo link`:

```bash
turbo build  # First run: builds, uploads artifacts to remote cache
turbo build  # Second run (CI machine): downloads from cache, zero rebuild
```

CI builds that hit cache complete in under 30 seconds even for large monorepos. The hash is computed from source files, so the cache is invalidated precisely when source changes.

## When a monorepo isn't the answer

**Separate deployment cycles**: if your apps deploy on completely independent schedules with different teams, monorepo coupling can be friction rather than a benefit.

**Language diversity**: monorepos work best when all packages share a language (TypeScript) and toolchain. Mixing TypeScript, Python, and Go in one repo is possible but the shared tooling benefits disappear.

**Small projects**: a monorepo is overhead you pay upfront. For two apps with minimal shared code, the setup cost isn't worth it. Start with a polyrepo and migrate when the shared code becomes painful to synchronise.

The signal that you need a monorepo: you're copying types between repositories, or a change in a shared library requires coordinated PRs across multiple repos.
