The first version of Scoutr was built for individual product lookups. A user pastes a product URL or barcode, we fetch the eBay data, run the AI analysis, and return the result. Response time: 3-6 seconds. Good enough for initial validation.

Then we watched how professional users actually work.

## The professional workflow

Professional eBay arbitrage isn't one product at a time. It's a systematic sweep: identify a retailer's clearance section, scan through 50-200 products, identify the 5-10 worth pursuing, and act on those. The "scan" phase is rapid — a few seconds per product, but dozens of products in succession.

The single-product lookup architecture doesn't support this workflow. Each lookup blocks the UI while the AI analysis runs. A professional scanning 100 products at 5 seconds each is waiting 8 minutes to see their results, without the ability to keep scanning while earlier results process.

The batch feature needed to be genuinely async: submit products, get notified as results come in, keep submitting more while early submissions process.

## The architecture change

The original architecture was synchronous: HTTP request → fetch eBay data → call Claude API → return result.

The batch architecture is job-based:

```
Submit batch → create JobBatch record → enqueue individual ProductJob records → return batch ID
↓
Worker pool processes ProductJob queue → updates results as they complete
↓
Client polls batch endpoint → receives completed results incrementally
```

**The job table schema:**

```sql
CREATE TABLE product_jobs (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  batch_id    uuid REFERENCES job_batches(id) ON DELETE CASCADE,
  user_id     uuid NOT NULL,
  input_url   text NOT NULL,
  status      text NOT NULL DEFAULT 'queued', -- queued | processing | done | error
  result      jsonb,
  error_msg   text,
  queued_at   timestamptz DEFAULT now(),
  started_at  timestamptz,
  completed_at timestamptz
);

CREATE TABLE job_batches (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id     uuid NOT NULL,
  total       int NOT NULL DEFAULT 0,
  completed   int NOT NULL DEFAULT 0,
  status      text NOT NULL DEFAULT 'processing', -- processing | done | partial_error
  created_at  timestamptz DEFAULT now()
);
```

**The worker:**

```ts
async function processProductJob(jobId: string) {
  await db
    .update(productJobs)
    .set({ status: 'processing', startedAt: new Date() })
    .where(eq(productJobs.id, jobId));

  try {
    const job = await db.query.productJobs.findFirst({ where: eq(productJobs.id, jobId) });
    const ebayData = await fetchEbayListings(job!.inputUrl);
    const analysis = await analyseWithClaude(ebayData);

    await db.update(productJobs).set({
      status: 'done',
      result: analysis,
      completedAt: new Date(),
    }).where(eq(productJobs.id, jobId));

    await incrementBatchCompleted(job!.batchId);
  } catch (err) {
    await db.update(productJobs).set({
      status: 'error',
      errorMsg: String(err),
      completedAt: new Date(),
    }).where(eq(productJobs.id, jobId));
  }
}
```

## Concurrency control

Running all batch jobs in parallel is tempting but dangerous. Twenty simultaneous Claude API calls would hit rate limits; twenty simultaneous eBay requests would trigger rate limiting from eBay's side.

We use a simple concurrency limiter with a configurable max-in-flight:

```ts
async function processBatch(batchId: string, maxConcurrent = 3) {
  const jobs = await getQueuedJobs(batchId);
  const semaphore = new Semaphore(maxConcurrent);
  
  await Promise.all(
    jobs.map(job => semaphore.run(() => processProductJob(job.id)))
  );
}
```

`maxConcurrent: 3` means at most 3 jobs are in the processing state at any time. New jobs start immediately when a processing slot frees up.

The semaphore implementation is a simple counter with a promise queue — no external library needed:

```ts
class Semaphore {
  private count: number;
  private queue: (() => void)[] = [];

  constructor(max: number) { this.count = max; }

  async run<T>(fn: () => Promise<T>): Promise<T> {
    await this.acquire();
    try { return await fn(); }
    finally { this.release(); }
  }

  private acquire(): Promise<void> {
    if (this.count > 0) {
      this.count--;
      return Promise.resolve();
    }
    return new Promise(resolve => this.queue.push(resolve));
  }

  private release() {
    const next = this.queue.shift();
    if (next) { next(); }
    else { this.count++; }
  }
}
```

## The polling endpoint

Clients poll the batch status endpoint every 2 seconds:

```ts
// GET /api/batches/[batchId]
export async function GET(req: Request, { params }: { params: { batchId: string } }) {
  const batch = await getBatchWithResults(params.batchId);
  
  return Response.json({
    batchId: batch.id,
    total: batch.total,
    completed: batch.completed,
    status: batch.status,
    results: batch.jobs
      .filter(j => j.status === 'done')
      .map(j => ({ id: j.id, url: j.inputUrl, analysis: j.result })),
    errors: batch.jobs
      .filter(j => j.status === 'error')
      .map(j => ({ id: j.id, url: j.inputUrl, error: j.errorMsg })),
  });
}
```

The UI shows results as they arrive, in the order they complete (not necessarily submission order). A professional scanning 100 products sees the first results within ~10 seconds and the last results within 2-3 minutes, with the UI updating incrementally throughout.

## What this changed

Three things improved measurably after the batch launch:

**Session length.** Average session length for professional-tier users increased from 8 minutes to 34 minutes. They were now scanning complete clearance sections in a single session rather than doing spot checks.

**Products analysed per session.** Increased from 4.2 to 31.7 for users who adopted batch mode. These users are now using Scoutr the way professional arbitrage workflows actually work.

**Churn in the professional tier.** Reduced from 22% monthly to 9% monthly in the two months following the launch. The batch feature unlocked the core professional use case.

The architectural investment — perhaps 4 days of total work including the UI changes — produced the most significant product metrics shift we've had. Building for how professional users actually work, rather than how we assumed they'd work, was the lesson.
