Postgres has a hard limit on concurrent connections — typically 100 on small instances. Each serverless function invocation creates a new connection; with 100 concurrent requests, you're at the limit. Unlike a long-running Node.js server, serverless functions can't share a connection pool across invocations. The solution is middleware pooling.

## The problem

```ts
// This looks fine in development — one function, one connection
import { drizzle } from 'drizzle-orm/postgres-js';
import postgres from 'postgres';

const client = postgres(process.env.DATABASE_URL!);
export const db = drizzle(client);
```

In production with Amplify (or any serverless environment), each cold start creates a new `postgres` client with its own TCP connection. Under load, you hit `FATAL: sorry, too many clients already`.

## Option 1: PgBouncer

PgBouncer sits between your application and Postgres, maintaining a fixed pool of connections and queueing requests:

```
App instances → PgBouncer (20 connections) → Postgres (max 100 connections)
```

Transaction pooling mode (recommended for serverless):
- Each transaction borrows a connection from the pool
- Connection is returned immediately after `COMMIT` or `ROLLBACK`
- No connection held between queries

Neon, Supabase, and Railway all provide PgBouncer out of the box. Use their pooled connection URL (usually on port 6543 instead of 5432):

```ts
// Use the pooled URL — provided by your Postgres host
const client = postgres(process.env.DATABASE_POOLER_URL!, {
  max: 1,  // Serverless: don't try to maintain more than 1 connection per invocation
  idle_timeout: 20,
  connect_timeout: 10,
  prepare: false,  // Required in transaction mode — no named prepared statements
});
```

The `prepare: false` flag is essential. Transaction pooling mode doesn't support named prepared statements — prepared statements are tied to a specific connection, which PgBouncer doesn't guarantee.

## Option 2: Neon HTTP driver

Neon provides an HTTP-based Postgres driver that doesn't maintain persistent TCP connections — perfect for serverless:

```bash
npm install @neondatabase/serverless
```

```ts
// lib/db.ts
import { neon } from '@neondatabase/serverless';
import { drizzle } from 'drizzle-orm/neon-http';
import * as schema from './schema';

const sql = neon(process.env.DATABASE_URL!);
export const db = drizzle(sql, { schema });
```

Each query goes over HTTP — no connection limit concerns, no pooling needed. The trade-off: slightly higher per-query latency than a persistent TCP connection, and no transactions across separate query calls.

For transactions over HTTP:

```ts
import { neon } from '@neondatabase/serverless';

const sql = neon(process.env.DATABASE_URL!);

// Transaction over HTTP
const result = await sql.transaction([
  sql`UPDATE users SET scan_limit = scan_limit - 1 WHERE id = ${userId}`,
  sql`INSERT INTO scans (user_id, product_id) VALUES (${userId}, ${productId})`,
]);
```

## Option 3: Drizzle with serverless-safe config

If you're using a traditional pooler (PgBouncer or Supabase Pooler):

```ts
// lib/db.ts
import { drizzle } from 'drizzle-orm/postgres-js';
import postgres from 'postgres';
import * as schema from './schema';

function getClient() {
  return postgres(process.env.DATABASE_URL!, {
    max: 1,          // One connection per function instance — pooler handles sharing
    idle_timeout: 5, // Release idle connections quickly
    connect_timeout: 10,
    prepare: false,  // Transaction pooling mode compatibility
    ssl: process.env.NODE_ENV === 'production' ? 'require' : false,
    connection: {
      application_name: 'construx-web',
    },
  });
}

// Module-level singleton — shared within one Lambda/Amplify instance
// Across invocations: pooler manages the actual Postgres connections
const client = getClient();
export const db = drizzle(client, { schema });
```

## Monitoring connection usage

```sql
-- Check current connections by state and user
SELECT
  state,
  count(*) as count,
  application_name
FROM pg_stat_activity
WHERE datname = current_database()
GROUP BY state, application_name
ORDER BY count DESC;

-- Check if you're near the limit
SELECT
  count(*) AS active,
  max_conn,
  max_conn - count(*) AS available
FROM pg_stat_activity, (SELECT setting::int AS max_conn FROM pg_settings WHERE name = 'max_connections') s
WHERE datname = current_database()
GROUP BY max_conn;
```

## Connection string anatomy

```
postgresql://user:password@host:5432/dbname?sslmode=require
                           ↑
                        5432 = direct (no pooler)
                        6543 = pooler port (Neon, Supabase)

# Supabase adds the mode parameter:
postgresql://user:password@host:6543/dbname?pgbouncer=true
```

## The right setup for Amplify

```ts
// lib/db.ts — for Next.js on AWS Amplify (serverless)
import { neon } from '@neondatabase/serverless';
import { drizzle } from 'drizzle-orm/neon-http';
import * as schema from './schema';

// HTTP driver — no connections to manage
const sql = neon(process.env.DATABASE_URL!);
export const db = drizzle(sql, { schema, logger: process.env.NODE_ENV === 'development' });
```

Neon's HTTP driver is the lowest-friction option for serverless — no pooler configuration, no `prepare: false` flag, no connection limit concerns. The per-query HTTP overhead (5-10ms) is negligible compared to a cold-start connection (50-200ms).
