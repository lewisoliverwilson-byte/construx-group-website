The Next.js Image component wraps a standard `<img>` tag with automatic resizing, format conversion, and lazy loading. The performance difference is real — a 1.2MB PNG becomes a 180KB AVIF served from the CDN. But the API has enough footguns to make it confusing.

## The fundamentals

```tsx
import Image from 'next/image';

// Local image — Next.js knows the dimensions from the import
import heroImg from '@/public/hero.jpg';

<Image
  src={heroImg}
  alt="Hero image"
  priority           // LCP image: don't lazy load, fetch immediately
/>
```

For a local import, you don't need `width` and `height` — Next.js reads them from the file. For remote images, you must provide them (or use `fill`).

## Remote images: allowlist required

Next.js won't optimize images from domains it doesn't know about. Configure them in `next.config.ts`:

```ts
// next.config.ts
import type { NextConfig } from 'next';

const config: NextConfig = {
  images: {
    remotePatterns: [
      {
        protocol: 'https',
        hostname:  'images.construxgroup.io',
        pathname:  '/uploads/**',
      },
      {
        protocol: 'https',
        hostname:  '**.amazonaws.com',  // wildcard for S3 buckets
      },
    ],
  },
};

export default config;
```

If you use `src` from an unlisted domain, Next.js throws a configuration error at runtime. Add the domain before you need it.

## fill vs fixed size

Use `fill` when the image should fill its container, and you don't know the dimensions ahead of time:

```tsx
// Container must have position: relative and explicit dimensions
<div className="relative w-full h-64">
  <Image
    src="/banner.jpg"
    alt="Banner"
    fill
    className="object-cover"  // or object-contain
    sizes="100vw"
  />
</div>
```

Without `sizes`, Next.js generates a srcset with images up to 3840px wide and serves the wrong size to mobile. `sizes` tells the browser how wide the image will actually be:

```tsx
// Full width on mobile, half width on desktop
<Image
  src="/product.jpg"
  alt="Product"
  fill
  sizes="(max-width: 768px) 100vw, 50vw"
/>

// Always 300px wide
<Image
  src="/avatar.jpg"
  alt="Avatar"
  width={300}
  height={300}
  sizes="300px"
/>
```

The `sizes` attribute is the most commonly missed config. Without it, you're serving 3x the bytes you need.

## The priority prop and LCP

The Largest Contentful Paint (LCP) image — typically the hero or above-the-fold image — should be loaded immediately, not lazily:

```tsx
// Hero image — add priority to disable lazy loading
<Image
  src="/hero.jpg"
  alt="Hero"
  width={1200}
  height={630}
  priority
/>
```

Without `priority`, Next.js lazy-loads by default. The browser won't fetch the hero image until it's near the viewport — which delays LCP and drops your Core Web Vitals score.

Add `priority` to the first visible image on each page. Never add it to images below the fold.

## Blur placeholder

For large images with a slow connection, a blurred placeholder reduces the perceived loading time:

```tsx
// Local image — Next.js generates the blurDataURL automatically
<Image
  src={heroImg}
  alt="Hero"
  placeholder="blur"
/>

// Remote image — provide the blurDataURL manually (or generate it at build time)
<Image
  src="https://example.com/photo.jpg"
  alt="Photo"
  width={800}
  height={600}
  placeholder="blur"
  blurDataURL="data:image/jpeg;base64,/9j/4AAQ..."
/>
```

For remote images, generate the blur data URL at build time using `plaiceholder`:

```ts
import { getPlaiceholder } from 'plaiceholder';

const { base64 } = await getPlaiceholder('https://example.com/photo.jpg');
// Use base64 as blurDataURL
```

## Format configuration

By default, Next.js serves AVIF for browsers that support it, WebP otherwise, and the original format as fallback. AVIF is 50% smaller than WebP; WebP is 25-35% smaller than JPEG.

```ts
const config: NextConfig = {
  images: {
    formats: ['image/avif', 'image/webp'],
  },
};
```

AVIF encoding is slower than WebP. If your server is CPU-constrained or your images change frequently, consider `['image/webp']` only.

## Quality

Default quality is 75. This is usually good. For product photography where detail matters, use 85-90. For background images, 60 is often unnoticeable at half the size:

```tsx
<Image
  src="/product.jpg"
  alt="Product detail"
  quality={85}
  width={800}
  height={800}
/>
```

## unoptimized for images you control

If your images are already optimized (you're running Sharp on upload, or using a CDN with its own optimization):

```tsx
<Image
  src="https://cdn.construxgroup.io/images/banner.jpg"
  alt="Banner"
  width={1200}
  height={630}
  unoptimized  // bypass Next.js optimization, serve as-is
/>
```

This avoids double-compression artifacts and reduces server CPU.

## What we run

For the Construx website: all marketing images are local imports with automatic WebP/AVIF conversion. The blog post covers are remote (stored in S3), served via a CDN with `remotePatterns` configured. Hero images have `priority`. Content images use `sizes="(max-width: 640px) 100vw, 672px"` matching the post content width.

Before this setup: median image payload 1.4MB per page. After: 210KB. The work was one afternoon of configuration.
