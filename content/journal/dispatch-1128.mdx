date: "2034-03-21"
excerpt: "KEDA (Kubernetes Event Driven Autoscaling) extends the standard HPA with external event sources as scaling metrics. The KEDA HTTP Add-on addresses one of the most common scaling patterns: scale a deployment based on HTTP request queue depth, and scale to zero when there are no requests. Standard HPA cannot scale to zero — it requires at least one replica to measure CPU/memory. KEDA's ScaledObject with external scalers can drive replicas to zero during off-peak hours, with an activator proxy holding requests while the deployment scales from zero to one replica (cold start). ScaledJob is for batch-style workloads: instead of scaling a long-running Deployment, each event creates a new Job — a queue message creates a processing Job, which runs to completion and terminates. This is the right model for per-item processing (resizing an image, running an ML inference, processing a webhook) where each unit of work should be isolated in its own container. KEDA ships with 60+ scalers covering event sources: Kafka consumer lag, NATS JetStream messages pending, AWS SQS queue depth, Redis list length, PostgreSQL query result count, Prometheus metrics, Cron expressions. For Construx, KEDA drives the worker tier: the image processing workers scale from 0 to 50 based on S3 upload event queue depth, and scale back to 0 within 5 minutes of the queue draining."

## KEDA ScaledObjects and ScaledJob config

```yaml
# KEDA ScaledObject: scale deployment based on Kafka consumer lag
# The orders-api consumer group should scale out when lag exceeds 1000 messages

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: orders-consumer
  namespace: construx-prod
spec:
  scaleTargetRef:
    name: orders-consumer

  minReplicaCount: 1      # minimum replicas (set to 0 to enable scale-to-zero)
  maxReplicaCount: 50     # maximum replicas

  pollingInterval: 15     # check event source every 15 seconds
  cooldownPeriod:  300    # wait 5 minutes after last event before scaling down

  triggers:
    - type: kafka
      metadata:
        bootstrapServers: kafka.construx-prod.svc.cluster.local:9092
        consumerGroup: orders-consumer
        topic: orders.created
        lagThreshold: "1000"    # scale up when consumer lag > 1000
        offsetResetPolicy: latest

  advanced:
    horizontalPodAutoscalerConfig:
      behavior:
        scaleDown:
          stabilizationWindowSeconds: 300   # prevent rapid scale-down
          policies:
            - type: Percent
              value: 25
              periodSeconds: 60

---
# KEDA ScaledObject: scale-to-zero HTTP deployment
# The KEDA HTTP Add-on intercepts HTTP requests and holds them during cold start

apiVersion: http.keda.sh/v1alpha1
kind: HTTPScaledObject
metadata:
  name: webhook-processor
  namespace: construx-prod
spec:
  hosts:
    - webhooks.construx.io
  scaleTargetRef:
    name: webhook-processor
    port: 8080
  replicas:
    min: 0              # scale to zero when no traffic
    max: 20
  scaledownPeriod: 300  # 5 minutes of no traffic before scaling to 0

---
# KEDA ScaledObject: cron-based scaling (pre-warm before business hours)
# Scale to 3 replicas at 08:45 UTC, back to 1 at 18:00 UTC

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: orders-api-schedule
  namespace: construx-prod
spec:
  scaleTargetRef:
    name: orders-api
  triggers:
    - type: cron
      metadata:
        timezone: Europe/London
        start: "45 8 * * 1-5"   # Monday-Friday 08:45
        end:   "0 18 * * 1-5"   # Monday-Friday 18:00
        desiredReplicas: "5"
    - type: cron
      metadata:
        timezone: Europe/London
        start: "0 18 * * 1-5"
        end:   "45 8 * * 1-5"
        desiredReplicas: "1"
```

```yaml
# KEDA ScaledJob: per-message image processing job
# Each SQS message creates one processing Job — isolated, parallelisable

apiVersion: keda.sh/v1alpha1
kind: ScaledJob
metadata:
  name: image-resize-worker
  namespace: construx-prod
spec:
  jobTargetRef:
    template:
      spec:
        containers:
          - name: image-resizer
            image: ghcr.io/construx/image-resizer:latest
            env:
              - name: SQS_QUEUE_URL
                value: "https://sqs.eu-west-2.amazonaws.com/123456789/image-resize"
              - name: AWS_REGION
                value: eu-west-2
            resources:
              requests:
                cpu: "500m"
                memory: "512Mi"
              limits:
                cpu: "2"
                memory: "2Gi"
        restartPolicy: Never
    backoffLimit: 3

  maxReplicaCount: 50         # max concurrent jobs
  rollout:
    strategy: gradual         # don't kill running jobs when ScaledJob changes

  triggers:
    - type: aws-sqs-queue
      authenticationRef:
        name: keda-aws-secrets   # TriggerAuthentication with IRSA
      metadata:
        queueURL: https://sqs.eu-west-2.amazonaws.com/123456789/image-resize
        queueLength: "1"        # 1 job per message
        awsRegion: eu-west-2
        identityOwner: operator

---
# TriggerAuthentication: reference to credentials for the SQS scaler
apiVersion: keda.sh/v1alpha1
kind: TriggerAuthentication
metadata:
  name: keda-aws-secrets
  namespace: construx-prod
spec:
  podIdentity:
    provider: aws   # use IRSA (pod identity → IAM role)
```

KEDA vs HPA vs custom controller vs AWS Lambda: Standard HPA scales on CPU and memory only — it cannot scale based on queue depth, message lag, or custom business metrics without writing a custom metrics adapter. KEDA removes this complexity: it ships scalers for every common event source, handles the metrics adapter boilerplate, and works with the existing HPA machinery. AWS Lambda is the scale-to-zero gold standard for stateless, event-driven compute — but it's limited to AWS, has its own deployment model (ZIP/container), and has cold start latency. KEDA brings Lambda-style event-driven scaling to any Kubernetes workload without changing the deployment model. Custom controllers are appropriate when KEDA's scaling semantics don't match the use case — for example, when the scaling decision requires complex logic that spans multiple event sources. KEDA's ScaledJob pattern is the Kubernetes-native alternative to Lambda for containerised batch processing: each event gets its own isolated Job with full container resource limits, the scheduling system distributes work across nodes, and there's no platform lock-in. The trade-off vs Lambda is cold start: KEDA's scale-from-zero takes 10-30 seconds (container pull + pod start), while Lambda cold starts are typically under 1 second for interpreted languages.
