Database access is one of those architectural decisions that's invisible when it works and visible when it doesn't. We started with raw SQL queries via the `postgres` npm package, migrated to Drizzle ORM after six months, and have been using it across all three products since.

Here's the honest assessment.

## Why we switched from raw SQL

Raw SQL has obvious advantages: you know exactly what's being executed, there's no abstraction to reason about, and SQL is a universal skill.

The problems at our scale:

**Type safety.** Raw SQL queries return `any` or untyped results by default. You can add TypeScript assertions, but they're not verified against the schema. Drizzle's query builder infers return types from the schema — a wrong column name is a compile-time error.

**Migration management.** We were writing SQL migration files by hand. Drizzle generates migration files from schema changes — you define the schema in TypeScript, Drizzle diffs it against the current state, and generates the SQL.

**Query complexity.** Joins and filters composed from runtime values require careful string interpolation with raw SQL. With Drizzle, queries are composable TypeScript:

```ts
// Raw SQL — string interpolation risk
const query = `SELECT * FROM listings WHERE status = 'active'${
  category ? ` AND category = '${category}'` : ''
}`;

// Drizzle — composable, type-safe
const conditions = [eq(listings.status, 'active')];
if (category) conditions.push(eq(listings.category, category));
const result = await db.select().from(listings).where(and(...conditions));
```

The string interpolation approach in raw SQL is a SQL injection risk if you're not careful. The Drizzle approach can't produce SQL injection by construction.

## The schema definition pattern

Drizzle schemas are TypeScript files:

```ts
// db/schema.ts
import { pgTable, uuid, text, integer, boolean, timestamptz, vector } from 'drizzle-orm/pg-core';

export const listings = pgTable('listings', {
  id:          uuid('id').primaryKey().defaultRandom(),
  sellerId:    uuid('seller_id').notNull().references(() => users.id),
  title:       text('title').notNull(),
  description: text('description').notNull(),
  category:    text('category').notNull(),
  pricePence:  integer('price_pence').notNull(),
  status:      text('status').notNull().default('draft'),
  embedding:   vector('embedding', { dimensions: 1536 }),
  deletedAt:   timestamptz('deleted_at'),
  createdAt:   timestamptz('created_at').defaultNow(),
  updatedAt:   timestamptz('updated_at').defaultNow(),
});

export type Listing = typeof listings.$inferSelect;
export type NewListing = typeof listings.$inferInsert;
```

The `$inferSelect` and `$inferInsert` types are inferred from the schema. When you add a non-nullable column, `$inferInsert` requires that column — compile-time enforcement of data integrity constraints.

## The query patterns we use most

**Filtered query with optional conditions:**

```ts
async function getListings(filters: {
  category?: string;
  status?: string;
  sellerId?: string;
}) {
  const conditions = [isNull(listings.deletedAt)];
  if (filters.category) conditions.push(eq(listings.category, filters.category));
  if (filters.status) conditions.push(eq(listings.status, filters.status));
  if (filters.sellerId) conditions.push(eq(listings.sellerId, filters.sellerId));

  return db.select().from(listings).where(and(...conditions)).orderBy(desc(listings.createdAt));
}
```

**Relational query (with join):**

```ts
const ordersWithListings = await db
  .select({
    order: orders,
    listing: { title: listings.title, category: listings.category },
    seller: { name: users.name },
  })
  .from(orders)
  .innerJoin(listings, eq(orders.listingVersionId, listingVersions.listingId))
  .innerJoin(users, eq(listings.sellerId, users.id))
  .where(eq(orders.buyerId, userId))
  .orderBy(desc(orders.createdAt));
```

**Upsert:**

```ts
await db.insert(userSettings)
  .values({ userId, ...settings })
  .onConflictDoUpdate({
    target: userSettings.userId,
    set: { ...settings, updatedAt: new Date() },
  });
```

## Where Drizzle's abstractions leak

**Custom functions and extensions.** The pgvector `<=>` cosine distance operator isn't in Drizzle's built-in set. We use `sql` template tag to escape back to raw SQL:

```ts
const similar = await db
  .select({ listing: listings, distance: sql<number>`embedding <=> ${pgvector.toSql(queryEmbedding)}` })
  .from(listings)
  .where(isNull(listings.deletedAt))
  .orderBy(sql`embedding <=> ${pgvector.toSql(queryEmbedding)}`)
  .limit(20);
```

The `sql` escape hatch is necessary here, and it's a sign that you're doing something Drizzle doesn't natively support. This is fine — it's expected — but it means you lose type inference for the custom expressions.

**Complex CTEs.** Common Table Expressions (WITH clauses) are supported in Drizzle but the API is less intuitive than the SQL. For complex analytics queries with multiple CTEs, we sometimes write raw SQL via the `sql` escape hatch and parse the result manually.

**Trigger inspection.** Drizzle doesn't model database triggers. Triggers we've added (for audit logging) are managed as raw SQL migrations outside the Drizzle schema.

## The migration workflow

```bash
# 1. Modify schema.ts
# 2. Generate migration
npx drizzle-kit generate
# 3. Review the generated SQL migration
# 4. Apply in development
npx drizzle-kit migrate
# 5. Apply in production (with backup first)
npx drizzle-kit migrate --url $PROD_DATABASE_URL
```

The generated migrations are SQL files that we commit to version control alongside the schema change. Before applying in production, we:
1. Read the generated SQL carefully.
2. Test in a staging environment.
3. Take a database backup.
4. Apply with a transaction where possible (not all DDL is transactional).

The Drizzle migration workflow removed our hand-written SQL migrations and the errors that came with them. Schema changes are now mechanical — change the TypeScript, generate the migration, review, apply.

Overall: Drizzle is the right ORM for TypeScript products at our scale. It provides type safety and migration management without obscuring the SQL. The abstractions leak in predictable places, and the `sql` escape hatch is a well-designed safety valve.
