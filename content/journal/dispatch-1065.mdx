excerpt: "cert-manager is a Kubernetes controller that automates X.509 certificate issuance and renewal. You declare a Certificate resource specifying the desired common name, SANs, duration, and an Issuer or ClusterIssuer that knows how to obtain certificates (ACME/Let's Encrypt via HTTP-01 or DNS-01 challenge, Vault PKI, a private CA, or self-signed). cert-manager handles the full certificate lifecycle: it generates the private key, constructs the CSR, completes the challenge, stores the signed certificate and key in a Kubernetes Secret, and automatically renews the certificate before it expires (by default at 2/3 of the certificate's lifetime). cert-manager integrates with ingress controllers (annotate an Ingress with cert-manager.io/cluster-issuer and TLS is provisioned automatically), with Istio and SPIFFE for workload identity certificates, and with AWS ACM PCA or Vault for internal PKI. The net effect: TLS certificates on Kubernetes are fully automated — no manual renewal, no expired certificate incidents."

## ClusterIssuer and Certificate configuration

```yaml
# ClusterIssuer: ACME / Let's Encrypt via DNS-01 (Route53)
# DNS-01 is required for wildcard certificates

apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email:  certs@construx.io
    privateKeySecretRef:
      name: letsencrypt-prod-account-key
    solvers:
      - dns01:
          route53:
            region:            eu-west-2
            hostedZoneID:      Z0284551ABCDEFGHIJKL
            # IAM role via IRSA — no static credentials
            role:              arn:aws:iam::123456789012:role/cert-manager-route53
        selector:
          dnsZones:
            - construx.io
            - construx.internal
---
# ClusterIssuer: internal Vault PKI for service-to-service mTLS
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: vault-pki-internal
spec:
  vault:
    server:   https://vault.construx.internal
    path:     pki/sign/construx-intermediate   # Vault PKI secrets engine mount
    caBundle: LS0tLS1CRUdJTi...                # Base64 Vault CA bundle
    auth:
      kubernetes:
        mountPath:       /v1/auth/kubernetes
        role:            cert-manager
        secretRef:
          name: vault-token
          key:  token
---
# Certificate: wildcard cert for *.construx.io via ACME DNS-01
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: construx-io-wildcard
  namespace: ingress-nginx
spec:
  secretName:  construx-io-wildcard-tls   # Kubernetes Secret created/updated by cert-manager
  issuerRef:
    name: letsencrypt-prod
    kind: ClusterIssuer
  commonName:  "*.construx.io"
  dnsNames:
    - "*.construx.io"
    - construx.io
  duration:    2160h   # 90 days (Let's Encrypt max)
  renewBefore: 720h    # renew 30 days before expiry
  privateKey:
    rotationPolicy: Always   # generate new key on each renewal
    algorithm:      ECDSA
    size:           256
```

```yaml
# Certificate: internal service cert from Vault PKI — short-lived
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: construx-api-tls
  namespace: construx-prod
spec:
  secretName: construx-api-tls
  issuerRef:
    name: vault-pki-internal
    kind: ClusterIssuer
  commonName:  construx-api.construx-prod.svc.cluster.local
  dnsNames:
    - construx-api.construx-prod.svc.cluster.local
    - construx-api.construx-prod.svc
    - construx-api
  duration:    24h      # 24-hour certs — Vault PKI, not ACME
  renewBefore: 8h       # renew 8h before expiry
  usages:
    - server auth
    - client auth    # mTLS: this cert is used as both server and client identity
---
# Ingress: cert-manager provisions TLS automatically via annotation
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: construx-api
  namespace: construx-prod
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod   # cert-manager watches this annotation
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  tls:
    - hosts:
        - api.construx.io
      secretName: api-construx-io-tls   # cert-manager creates this Secret
  rules:
    - host: api.construx.io
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: construx-api
                port: { number: 80 }
```

## Monitoring and debugging certificate state

kubectl get certificate -A

# ingress-nginx   construx-io-wildcard   True   construx-io-wildcard   62d

# Detailed certificate info: expiry, renewal window, issuer
kubectl describe certificate construx-io-wildcard -n ingress-nginx

#   Conditions:
#     Message:  Certificate is up to date and has not expired

cert-manager vs manual certificate management vs AWS ACM vs Vault PKI alone: Manual certificate management — tracking expiry in a spreadsheet, renewing via Let's Encrypt CLI or your CA portal, and updating Kubernetes Secrets by hand — produces certificate incidents. The failure mode is predictable: something expires during a holiday because the renewal reminder was buried in email. AWS ACM handles TLS termination at the load balancer layer automatically, but doesn't give you certificates inside the cluster (for pod-to-pod mTLS, internal services, or non-AWS infrastructure). Vault PKI is excellent for internal certificate issuance but requires glue code to wire into Kubernetes. cert-manager is that glue: it integrates all certificate sources (ACME, Vault, private CA, self-signed) through a single Kubernetes-native API, and the auto-renewal loop means the only way a certificate expires is if cert-manager itself goes down — which your alerting covers. For teams running Kubernetes, cert-manager is the standard answer to certificate management. The investment is the initial ClusterIssuer configuration; the return is never manually renewing a certificate again.
