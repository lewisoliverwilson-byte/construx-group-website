There is a specific gap between "I think this works" and "this is live in front of users." Most teams underinvest in this gap. The assumption is that if the code runs locally and the tests pass, it's ready. It usually isn't.

We have a checklist. Not a safety net — a systematic process for catching the things that are easy to miss when you're moving fast and the deadline is today.

## What "done" means before the checklist starts

The checklist isn't a substitute for finishing the work. "Done" means the feature does what it's supposed to do, the code is committed, and you've tested the core path yourself. The checklist is everything that happens after that.

If you're using the checklist to find out whether the feature works, you're using it wrong.

## TypeScript and build checks

First item: `npx tsc --noEmit`. No output means clean. Any output means something is wrong that will either break at runtime or silently degrade. We do not ship with TypeScript errors. Not even "it still runs" TypeScript errors — a type error is a signal that the code isn't doing what you think it's doing.

Second: `npm run build`. The local dev server hides a class of errors that the production build surface — missing environment variables that are only checked at build time, import paths that work in development but break under Next.js's strict module resolution, server/client component boundary violations. Running the production build locally catches these before Amplify does.

If the build breaks, fix it. The deployment pipeline is not a debugging tool.

## Visual review on the specific path that changed

Open the browser. Go to the page. Do the thing the change was supposed to enable. Look at it. Not "does it technically work" — "does it look right, does it feel right, is there anything visually broken?"

This sounds obvious. It is skipped more than any other step.

For a UI change: check it at three widths — mobile (375px), tablet (768px), and desktop (1280px). Most bugs live at the boundaries between these. Padding that looks fine at desktop will collapse on mobile. A flex layout that works at 1280px will wrap awkwardly at 768px. You will not find these by reading the code.

For a content change: read it out loud. Copy that sounded good while writing it often sounds wrong when you hear it. An extra word. An awkward phrase. A heading that doesn't match the body below it. Reading out loud catches these; scanning doesn't.

## The environment variable audit

Every deployment to a new environment requires a check: are all the environment variables that the code depends on set correctly in that environment?

We maintain a list of every environment variable the application uses. Before pushing to production, we verify:

1. Every required variable is set in the Amplify console
2. Variables are set in the correct environment (build-time vs. runtime, per-branch vs. global)
3. No variable is referencing a staging or development value in the production config

The third point is the one that bites teams. A build that connected to the test database in staging will continue connecting to the test database in production if the variable wasn't updated. Environment variables are infrastructure — they get the same attention as code.

## Link and navigation audit

For any change that adds, removes, or modifies links: manually click every changed link. Verify the destination. Check that internal links resolve to real pages, not 404s. Check that external links open in new tabs where expected.

For nav changes: test every nav link in the mobile menu. Mobile menus are a separate code path and break separately from desktop navigation.

For page removals: check that nothing in the codebase still links to the removed page. Search for the slug. A 404 in production is worse than a 404 in development — it's a user's dead end, and it's a crawl error in Google's index.

## The post-deploy check

Push. Wait for Amplify to complete the build. Open the production URL.

The post-deploy check is not a repeat of the pre-deploy check — it's a specific set of things to verify that can only be verified on the live deployment:

**Does it load?** Network tab, check for 4xx or 5xx responses on critical assets. A build that completes successfully can still produce a site that errors on load if a server-side import fails at runtime.

**Does the contact form work?** If the deployment touched environment variables, the email sending may have broken. Send a test submission and verify it arrives.

**Does the correct content appear?** SSG pages are pre-rendered at build time. A content change requires a rebuild to show up. If the new content isn't appearing, the page may have been cached at the previous version.

**Are there console errors?** Open the browser devtools. Unexpected console errors after a clean build are a signal something is wrong at runtime — a failed API call, a missing resource, a client-side exception.

## What we don't check

We don't do automated end-to-end testing. For a two-person team running three ventures, the overhead of maintaining a Playwright or Cypress suite against a rapidly changing interface is higher than the value it provides. Manual visual review and the pre-ship checklist catch the same class of errors, faster, for products at our current scale.

This is a deliberate tradeoff. If scale increases to the point where manual review is no longer tractable, automated testing becomes worth the investment. At current scale, the human review loop is faster and more reliable than a brittle test suite.

We also don't maintain staging environments. Amplify's branch previews provide a staging-equivalent for specific changes when needed. A permanent staging environment that needs to stay in sync with production is overhead we've decided not to carry.

## Why checklists work

Checklists work because the failure mode they prevent is not incompetence — it's distraction. You know all the things on the checklist. You've done them all before. The checklist exists because when you're in the middle of shipping something, the specific things that need checking are easy to not think about.

A checklist externalises the memory of what needs to happen. The cognitive overhead of running through a list is near zero. The cost of skipping something that was on the list — a broken link, a missing environment variable, a layout that collapses on mobile — is much higher.

The checklist is not a sign that you don't trust yourself. It's a sign that you understand how memory and attention work under pressure.
