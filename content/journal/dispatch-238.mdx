Three products, each with 15-25 environment variables, deployed to AWS Amplify. The naive approach is to add variables to the Amplify console when they're needed and figure out the rest later. We did this. It created problems.

Here's the system we use now.

## The naming convention

Every environment variable follows a predictable pattern:

```
[PRODUCT_]PROVIDER_PURPOSE
```

Examples:
- `ANTHROPIC_API_KEY` — Anthropic API key (shared pattern across products)
- `UPSTASH_REDIS_REST_URL` — Upstash Redis connection URL
- `UPSTASH_REDIS_REST_TOKEN` — Upstash Redis auth token
- `NEXT_PUBLIC_POSTHOG_KEY` — PostHog public key (client-visible)
- `NEXT_PUBLIC_SITE_URL` — canonical site URL (client-visible)
- `DATABASE_URL` — database connection string (pooled, for serverless)
- `DATABASE_URL_DIRECT` — database connection string (direct, for migrations)
- `CLERK_SECRET_KEY` — Clerk private key
- `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` — Clerk public key

The `NEXT_PUBLIC_` prefix is a Next.js convention: variables prefixed this way are bundled into the client-side JavaScript. Everything else is server-only.

Consistently following this convention means you can look at a variable name and know:
1. Which product/scope it belongs to (if prefixed)
2. Which provider/service it connects to
3. Its purpose
4. Whether it's exposed to the client (`NEXT_PUBLIC_`)

## The local `.env.local` pattern

Each product has a `.env.local` file for local development. This file is in `.gitignore` — it never gets committed. We have a separate `.env.example` that lists all required variables with placeholder values:

```bash
# .env.example — copy to .env.local and fill in values
ANTHROPIC_API_KEY=sk-ant-...
UPSTASH_REDIS_REST_URL=https://your-endpoint.upstash.io
UPSTASH_REDIS_REST_TOKEN=...
DATABASE_URL=postgresql://...
DATABASE_URL_DIRECT=postgresql://...
CLERK_SECRET_KEY=sk_...
NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=pk_...
NEXT_PUBLIC_POSTHOG_KEY=phc_...
NEXT_PUBLIC_SITE_URL=http://localhost:3000
```

`.env.example` is committed to the repo. A new environment setup consists of: copy `.env.example` to `.env.local`, fill in values. No documentation needed beyond the example file itself.

## The secret vs non-secret distinction

Not all environment variables are equally sensitive:

**Secrets** — must never be exposed to the client, must be rotated if leaked:
- API keys for paid services (`ANTHROPIC_API_KEY`, `RESEND_API_KEY`)
- Database credentials (`DATABASE_URL`)
- Signing secrets (`WEBHOOK_SECRET`, `CLERK_SECRET_KEY`)

**Non-secrets** — can be committed to the repo (but we don't, for consistency):
- Public-facing keys designed to be in the browser (`NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, `NEXT_PUBLIC_POSTHOG_KEY`)
- Configuration values (`NEXT_PUBLIC_SITE_URL`)

In Amplify, secrets are set as "Secret" variables (encrypted at rest); non-secrets are set as regular environment variables. This distinction matters: if you accidentally expose a secret in a build log, it's a problem. If you expose `NEXT_PUBLIC_SITE_URL`, it isn't.

## The runtime vs build-time distinction

Next.js has two contexts where environment variables are read:

**Build time** — when `next build` runs. Static pages are generated; any `process.env.*` access in a page or component that runs at build time uses the build-time environment. In Amplify, this is the environment configured in the Amplify console.

**Runtime** — when API routes handle requests. Server components and API routes access `process.env.*` at the time a request is handled.

The subtle issue: if a variable is only set at runtime (dynamically injected), it won't be available for static generation. `NEXT_PUBLIC_SITE_URL` must be set at build time if it's used in static OG image generation.

We set all variables in Amplify for both build and runtime. The only distinction we make is the secret/non-secret flag.

## The mistake we made

For the first two months, we'd add environment variables to Amplify as we discovered we needed them, with no record elsewhere. When we needed to set up a new developer environment or debug a configuration issue, we had to:
1. Open the Amplify console
2. Look at the current variable list
3. Cross-reference with what was actually needed
4. Guess at what the current values should be

We solved this by:
1. Keeping `.env.example` updated every time we add a variable — before the pull request is merged, not after
2. Adding a comment to each `.env.example` line explaining what service provides it
3. Keeping a local 1Password vault entry for each product with the current production values

The 1Password step sounds like overhead. It costs 2 minutes when you add a variable. It saves 30 minutes when you need to rebuild a lost environment.

## The Amplify-specific gotcha

AWS Amplify caches environment variables during the build. If you change a variable in the Amplify console and trigger a redeploy, the new value is used. But if you're relying on a variable that changed and you don't trigger a new build, you'll get stale values.

For The Hyve's Railway services (which use environment variables from the Railway dashboard), changes take effect on the next service restart, not on the next deploy of the Next.js frontend. This caused an hour of confusion when we changed `DATABASE_URL` in Railway — the Railway API workers picked it up; the Next.js frontend (on Amplify) still had the old value until the next Amplify deploy.

The fix: whenever changing a database or API endpoint URL, trigger deploys of all services that use it, not just the one where you made the change.

## The missing variable problem

The most common cause of production issues post-deploy: a required environment variable isn't set in the target environment.

We catch this with a startup check in each product:

```ts
// lib/env.ts
const required = [
  'ANTHROPIC_API_KEY',
  'DATABASE_URL',
  'CLERK_SECRET_KEY',
  'NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY',
];

for (const key of required) {
  if (!process.env[key]) {
    throw new Error(`Missing required environment variable: ${key}`);
  }
}
```

This runs at build time via `next build`. A missing variable causes the build to fail with a clear error message, rather than causing a cryptic runtime failure when the first request tries to use the missing value.

The check doesn't run in the browser (it's a server-only module). For `NEXT_PUBLIC_` variables, we do a belt-and-suspenders check in the component that uses them, but missing public variables are caught by the TypeScript definitions rather than runtime errors.

## Current state

We're on the third iteration of the env management approach. The current system — example file, 1Password vault, Amplify with secret/non-secret distinction, startup check — handles everything we've encountered. The RESEND_API_KEY is still missing from the Amplify configuration for this site, which is an example of how the system works: the missing variable doesn't cause a crash (the contact form gracefully fails), but it means the feature is silently non-functional. Fixed in January, week one.
