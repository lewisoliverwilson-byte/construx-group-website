title: "Kafka consumer groups: partition assignment and rebalancing"
date: "2031-12-28"
excerpt: "Kafka partitions are the unit of parallelism. A consumer group distributes partitions across its members — each partition is owned by exactly one consumer at a time. When a consumer joins or leaves, the group coordinator triggers a rebalance: partitions are reassigned. The CooperativeStickyAssignor minimises rebalance disruption by only moving partitions that need to move, leaving others running. Committed offsets track per-partition progress; a consumer restarts from its last commit."

Partitions distributed across consumers. Rebalance on membership change. Commit offsets, not acknowledgements.

## CooperativeStickyAssignor — incremental rebalance

```ts
// consumer.ts
import { Kafka } from 'kafkajs';

const kafka = new Kafka({ brokers: ['kafka:9092'] });

const consumer = kafka.consumer({
  groupId:       'order-fulfillment-workers',
  // Default: EagerAssignor (stop-the-world rebalance)
  // CooperativeSticky: only reassign partitions that need to move
  partitionAssigners: [PartitionAssigners.roundRobin],
  // OR use KafkaJS cooperative sticky (check your version)
});

await consumer.connect();
await consumer.subscribe({ topic: 'orders', fromBeginning: false });

await consumer.run({
  // autoCommit: true (default) — commits every 5s
  // autoCommit: false — manual control
  eachMessage: async ({ topic, partition, message }) => {
    const order = JSON.parse(message.value!.toString());
    await processOrder(order);
    // With autoCommit: true, offset is committed automatically
  },
});
```

## Manual offset management

```ts
// Manual commit — only commit after successful processing
await consumer.run({
  autoCommit: false,
  eachBatch: async ({ batch, resolveOffset, heartbeat, commitOffsetsIfNecessary }) => {
    for (const message of batch.messages) {
      const order = JSON.parse(message.value!.toString());

      try {
        await processOrder(order);
        // Mark this offset as processed (doesn't commit yet)
        resolveOffset(message.offset);
        await heartbeat();  // Keep the session alive during slow processing
      } catch (err) {
        // Don't resolve — this offset will be reprocessed on restart
        logger.error({ err, offset: message.offset }, 'processing failed');
        break;  // Stop processing this batch
      }
    }

    // Commit all resolved offsets
    await commitOffsetsIfNecessary();
  },
});
```

## Reset offsets — reprocess from a point in time

```bash
# Reset to earliest — reprocess all messages from the beginning
kafka-consumer-groups.sh \
  --bootstrap-server kafka:9092 \
  --group order-fulfillment-workers \
  --reset-offsets \
  --to-earliest \
  --topic orders \
  --execute

# Reset to a specific datetime
kafka-consumer-groups.sh \
  --bootstrap-server kafka:9092 \
  --group order-fulfillment-workers \
  --reset-offsets \
  --to-datetime 2031-12-01T00:00:00.000 \
  --topic orders \
  --execute

# Reset to offset N on partition 2
kafka-consumer-groups.sh \
  --bootstrap-server kafka:9092 \
  --group order-fulfillment-workers \
  --reset-offsets \
  --to-offset 18241 \
  --topic orders:2 \
  --execute
```

## Dead letter queue — handle poison messages

```ts
const DLQ_TOPIC = 'orders-dlq';

await consumer.run({
  eachMessage: async ({ topic, partition, message }) => {
    try {
      const order = JSON.parse(message.value!.toString());
      await processOrder(order);
    } catch (err) {
      // Send to DLQ instead of blocking the partition
      const producer = kafka.producer();
      await producer.connect();
      await producer.send({
        topic:    DLQ_TOPIC,
        messages: [{
          key:   message.key,
          value: message.value,
          headers: {
            'x-dlq-original-topic':  topic,
            'x-dlq-original-partition': String(partition),
            'x-dlq-original-offset':    message.offset,
            'x-dlq-error':              String(err),
            'x-dlq-timestamp':          String(Date.now()),
          },
        }],
      });
      await producer.disconnect();
    }
  },
});
```

At-least-once vs exactly-once: with manual offset commits, if a consumer processes a message and then crashes before committing the offset, the message is reprocessed on restart — at-least-once delivery. Exactly-once requires transactional producers and the Kafka Streams exactly-once guarantee (EOS). EOS is supported but adds latency (~20% throughput reduction) because each batch requires a two-phase transaction. For most business events (orders, payments, emails), idempotent processing (deduplicate by order ID) gives you exactly-once semantics at the application layer without the Kafka EOS overhead.
