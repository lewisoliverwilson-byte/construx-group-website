TypeScript's type system is compile-time only. By the time your code runs, all the type annotations are gone. That means `response.data as User` is a lie — you're asserting a shape without checking it. Zod validates the actual runtime data and gives you a type that matches. One source of truth.

## Defining schemas

```ts
import { z } from 'zod';

const UserSchema = z.object({
  id:        z.string().uuid(),
  name:      z.string().min(1).max(100),
  email:     z.string().email(),
  role:      z.enum(['admin', 'member', 'viewer']),
  createdAt: z.string().datetime(),
  plan:      z.object({
    tier:       z.enum(['free', 'pro', 'enterprise']),
    expiresAt:  z.string().datetime().nullable(),
  }),
});

// Infer the TypeScript type from the schema
type User = z.infer<typeof UserSchema>;
// {
//   id: string;
//   name: string;
//   email: string;
//   role: 'admin' | 'member' | 'viewer';
//   createdAt: string;
//   plan: { tier: 'free' | 'pro' | 'enterprise'; expiresAt: string | null };
// }
```

Define the schema, get the type for free. No duplication.

## Validating API responses

```ts
async function getUser(id: string): Promise<User> {
  const res = await fetch(`/api/users/${id}`);
  if (!res.ok) throw new Error(`HTTP ${res.status}`);

  const data = await res.json();

  // parse() throws ZodError if shape doesn't match
  return UserSchema.parse(data);
}
```

If the API returns unexpected data, you get a detailed error immediately at the boundary — not a silent `undefined` access six function calls later.

## Safe parse for error handling

```ts
const result = UserSchema.safeParse(data);

if (!result.success) {
  console.error(result.error.issues);
  // [{ code: 'invalid_type', expected: 'string', received: 'number', path: ['id'] }]
  return null;
}

// result.data is typed as User here
return result.data;
```

`safeParse` returns `{ success: true, data }` or `{ success: false, error }` instead of throwing. Better for user-facing validation where you want to surface specific field errors.

## Validating environment variables

```ts
// lib/env.ts
const EnvSchema = z.object({
  DATABASE_URL:                   z.string().url(),
  NEXT_PUBLIC_SITE_URL:           z.string().url(),
  CLERK_SECRET_KEY:               z.string().min(1),
  NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY: z.string().min(1),
  RESEND_API_KEY:                 z.string().min(1),
  UPSTASH_REDIS_REST_URL:         z.string().url(),
  UPSTASH_REDIS_REST_TOKEN:       z.string().min(1),
  NODE_ENV:                       z.enum(['development', 'test', 'production']).default('development'),
});

export const env = EnvSchema.parse(process.env);
```

If any required env var is missing at startup, the process throws a clear error listing exactly what's missing — before any requests are handled. Import `env` throughout the app instead of `process.env` to get full autocomplete.

## Validating Server Action inputs

```ts
// app/actions/posts.ts
'use server';

import { z } from 'zod';
import { auth } from '@clerk/nextjs/server';

const CreatePostSchema = z.object({
  title:   z.string().min(1, 'Title required').max(200),
  body:    z.string().min(1, 'Body required'),
  tag:     z.string().optional(),
});

export async function createPost(input: z.infer<typeof CreatePostSchema>) {
  const { userId } = await auth();
  if (!userId) throw new Error('Unauthenticated');

  const parsed = CreatePostSchema.parse(input);

  await db.insert(posts).values({
    ...parsed,
    authorId: userId,
  });
}
```

Calling `parse` at the top of a Server Action ensures data from the client — which can be manipulated — is validated before touching the database.

## Transformations

```ts
const DateRangeSchema = z.object({
  from: z.string().transform((s) => new Date(s)),
  to:   z.string().transform((s) => new Date(s)),
}).refine(
  (data) => data.from <= data.to,
  { message: 'from must be before to', path: ['from'] },
);

type DateRange = z.infer<typeof DateRangeSchema>;
// { from: Date; to: Date }
```

`transform` converts the input type. `refine` adds cross-field validation with a custom error message.

## Partial and pick

```ts
// All fields optional (for PATCH endpoints)
const UpdateUserSchema = UserSchema.partial();

// Only specific fields
const PublicUserSchema = UserSchema.pick({
  id:   true,
  name: true,
});

// Extend with additional fields
const CreateUserSchema = UserSchema.omit({ id: true, createdAt: true }).extend({
  password: z.string().min(8),
});
```

Zod schemas compose well — pick, omit, extend, merge, and partial all work on existing schemas. No need to redefine shapes.

## The rule

Validate at every boundary where data enters your application: external API responses, form submissions, URL params, environment variables, Server Action inputs, and webhook payloads. Everywhere else — internal function calls, database reads through your own ORM — trust the types. Zod at the boundary, TypeScript everywhere else.
