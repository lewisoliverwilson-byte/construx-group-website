title: "Iceberg: open table format — time travel, schema evolution, partition evolution, compaction"
date: "2034-04-11"
excerpt: "Apache Iceberg is an open table format for large analytic datasets stored in object storage (S3, GCS, ADLS). It solves the problems that arise when you store petabyte-scale data in Parquet files on S3: no ACID transactions (concurrent writers corrupt data), no schema evolution (adding a column requires rewriting all files), no efficient time travel (previous versions are gone), no partition pruning beyond the directory structure, and no row-level deletes without full partition rewrite. Iceberg adds a metadata layer on top of object storage: a snapshot manifest records exactly which data files belong to which table version; a schema is tracked with full evolution history; partition specifications can change without rewriting data; row-level deletes and updates use positional delete files or merge-on-read semantics. The Iceberg REST catalog serves as a central registry for table metadata — any query engine (Spark, Trino, Flink, DuckDB, Snowflake) connects to the catalog and gets a consistent view of the table. Compaction (either scheduled or streaming) merges small data files and delete files into optimally sized Parquet files, maintaining query performance as data accumulates. At Construx, Iceberg is the table format for the data lake on S3 — Flink writes streaming data, Trino queries it, dbt transforms it, and time travel provides point-in-time snapshots for reproducible ML training sets."

## Iceberg table operations and catalog config

```python
# PyIceberg: Python SDK for Iceberg table operations

from pyiceberg.catalog import load_catalog
from pyiceberg.schema import Schema
from pyiceberg.types import (
    NestedField, StringType, LongType, TimestampType, DoubleType
)
from pyiceberg.partitioning import PartitionSpec, PartitionField
from pyiceberg.transforms import DayTransform, IdentityTransform

# Connect to REST catalog (used by Spark, Trino, Flink, DuckDB)
catalog = load_catalog(
    "construx",
    **{
        "type": "rest",
        "uri": "https://iceberg-catalog.construx.internal",
        "credential": "construx:${CATALOG_SECRET}",
        "warehouse": "s3://construx-data-lake/iceberg/",
        "s3.region": "eu-west-2",
    }
)

# Create namespace (database)
catalog.create_namespace("construx_prod")

# Define schema: orders table
schema = Schema(
    NestedField(1,  "order_id",     StringType(),    required=True),
    NestedField(2,  "tenant_id",    StringType(),    required=True),
    NestedField(3,  "status",       StringType(),    required=True),
    NestedField(4,  "total_pence",  LongType(),      required=True),
    NestedField(5,  "created_at",   TimestampType(), required=True),
    NestedField(6,  "updated_at",   TimestampType(), required=False),
)

# Partition by day(created_at) and identity(tenant_id)
# Efficient for time-range queries and per-tenant analysis
partition_spec = PartitionSpec(
    PartitionField(source_id=5, field_id=1000, transform=DayTransform(),      name="created_day"),
    PartitionField(source_id=2, field_id=1001, transform=IdentityTransform(),  name="tenant_id"),
)

table = catalog.create_table(
    identifier="construx_prod.orders",
    schema=schema,
    partition_spec=partition_spec,
    properties={
        "write.target-file-size-bytes": str(128 * 1024 * 1024),  # 128MB target file size
        "write.format.default": "parquet",
        "write.parquet.compression-codec": "zstd",
        "history.expire.max-snapshot-age-ms": str(7 * 24 * 60 * 60 * 1000),  # keep 7 days
    }
)
```

```sql
-- Trino SQL: query Iceberg tables with time travel and schema evolution

-- Current snapshot
SELECT tenant_id, COUNT(*), SUM(total_pence) / 100.0 as revenue
FROM iceberg.construx_prod.orders
WHERE created_at >= TIMESTAMP '2034-04-01 00:00:00'
GROUP BY tenant_id
ORDER BY revenue DESC
LIMIT 20;

-- Time travel: query a specific snapshot (before a bad migration)
SELECT COUNT(*) FROM iceberg.construx_prod.orders
FOR VERSION AS OF 8473629182736481920;   -- snapshot ID

-- Time travel by timestamp (reproduce ML training data at a point in time)
SELECT * FROM iceberg.construx_prod.orders
FOR TIMESTAMP AS OF TIMESTAMP '2034-04-01 00:00:00 UTC';

-- Show all snapshots (history)
SELECT snapshot_id, committed_at, operation, summary
FROM iceberg.construx_prod."orders$snapshots"
ORDER BY committed_at DESC
LIMIT 10;

-- Schema evolution: add a column without rewriting data
ALTER TABLE iceberg.construx_prod.orders
ADD COLUMN discount_pence BIGINT;
-- New files include the column; existing files return NULL for it — no rewrite

-- Partition evolution: change partitioning without rewriting historical data
ALTER TABLE iceberg.construx_prod.orders
SET PARTITIONING (day(created_at), bucket(16, tenant_id));
-- Old data retains original partition spec; new data uses new spec
-- Trino handles both transparently

-- Row-level delete (merge-on-read: efficient for low delete rates)
DELETE FROM iceberg.construx_prod.orders
WHERE tenant_id = 'churned-customer' AND created_at < TIMESTAMP '2034-01-01 00:00:00';

-- Compaction: merge delete files and small data files (run via Spark or Trino)
ALTER TABLE iceberg.construx_prod.orders EXECUTE optimize
WHERE created_at >= TIMESTAMP '2034-03-01 00:00:00';
-- Merges small files and applies deletes — improves subsequent query performance
```

Iceberg vs Delta Lake vs Hudi vs Parquet on S3 vs BigQuery: Delta Lake (from Databricks) is the closest competitor — it has the same ACID guarantees and time travel, with a simpler transaction log format and tighter Spark integration. Its Rust-based Delta Kernel makes it increasingly multi-engine. Apache Hudi (originated at Uber) focuses on record-level upserts with excellent streaming write performance — ideal for CDC pipelines that need to update individual records. Raw Parquet on S3 is what most teams start with: no catalog overhead, works with any tool, but no ACID (concurrent writes corrupt), no schema evolution, and no efficient row-level operations. BigQuery and Snowflake store data in proprietary formats — you pay for the managed metadata, query engine, and storage together, with no freedom to use external query engines. Iceberg's advantage over Delta Lake and Hudi is vendor-neutrality: the spec is open, the REST catalog has multiple open-source implementations (Nessie, Project Polaris, Apache Gravitino), and every major query engine (Spark, Trino, Flink, Snowflake, BigQuery via BigLake, DuckDB) supports it natively. At Construx, Iceberg is the neutral lingua franca: Flink writes streaming data, Trino queries it for analytics, Spark runs batch transforms, dbt models run via Trino, and Snowflake can query the same S3 data via external tables — all without data movement.
