excerpt: "Firecracker is an open-source virtual machine monitor (VMM) developed by AWS that boots a minimal Linux VM in under 125ms using fewer than 5MB of memory overhead per VM. It powers AWS Lambda and AWS Fargate. The key design choice: Firecracker exposes a minimal device model — no USB, no PCI bus, no BIOS, no legacy hardware emulation. The guest kernel boots directly via a custom boot protocol, skipping the firmware and BIOS initialization that traditional VMs run. Each micro-VM gets an isolated kernel, network namespace, and filesystem, providing security boundaries stronger than containers (kernel-level isolation) with startup times approaching containers. Firecracker is controlled via a REST API and is the foundation for serverless container runtimes like Kata Containers."

125ms boot. 5MB overhead. REST API control. AWS Lambda's actual runtime.

## Starting a micro-VM

```bash
# Firecracker: run a micro-VM from the command line
# Requires a kernel image and a rootfs

# Download the Firecracker binary
curl -Lo /usr/local/bin/firecracker \
  https://github.com/firecracker-microvm/firecracker/releases/latest/download/firecracker-v1.8.0-x86_64
chmod +x /usr/local/bin/firecracker

# Firecracker is controlled via a Unix socket (REST API)
# Start the process listening on a socket:
rm -f /tmp/fc.sock
firecracker --api-sock /tmp/fc.sock &

# Configure via the REST API (curl against the socket):

# 1. Set the kernel (must be compiled with Firecracker-specific config)
curl -X PUT --unix-socket /tmp/fc.sock \
  -H 'Accept: application/json' \
  -H 'Content-Type: application/json' \
  -d '{
    "kernel_image_path": "/opt/fc/vmlinux",
    "boot_args": "console=ttyS0 reboot=k panic=1 pci=off"
  }' http://localhost/boot-source

# 2. Set the root filesystem (ext4 image)
curl -X PUT --unix-socket /tmp/fc.sock \
  -H 'Content-Type: application/json' \
  -d '{
    "drive_id": "rootfs",
    "path_on_host": "/opt/fc/rootfs.ext4",
    "is_root_device": true,
    "is_read_only": false
  }' http://localhost/drives/rootfs

# 3. Configure the machine (vCPUs and memory)
curl -X PUT --unix-socket /tmp/fc.sock \
  -H 'Content-Type: application/json' \
  -d '{
    "vcpu_count": 2,
    "mem_size_mib": 512
  }' http://localhost/machine-config

# 4. Start the VM
curl -X PUT --unix-socket /tmp/fc.sock \
  -H 'Content-Type: application/json' \
  -d '{"action_type": "InstanceStart"}' \
  http://localhost/actions

# The VM boots in ~125ms — faster than Docker image pull
```

## Network configuration

```bash
# Firecracker uses virtio network devices and TAP interfaces
# Each VM gets its own network namespace

# Create a TAP interface on the host
ip tuntap add dev tap0 mode tap
ip addr add 172.16.0.1/24 dev tap0
ip link set tap0 up

# Enable NAT (host → VM traffic)
sysctl -w net.ipv4.ip_forward=1
iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
iptables -A FORWARD -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT
iptables -A FORWARD -i tap0 -o eth0 -j ACCEPT

# Configure the network interface in the VM
curl -X PUT --unix-socket /tmp/fc.sock \
  -H 'Content-Type: application/json' \
  -d '{
    "iface_id": "eth0",
    "host_dev_name": "tap0"
  }' http://localhost/network-interfaces/eth0

# Guest VM: configure from inside the VM after boot
ip addr add 172.16.0.2/24 dev eth0
ip link set eth0 up
ip route add default via 172.16.0.1

# Result: VM can reach the internet via NAT through the host
```

## Snapshots and live migration

```bash
# Firecracker supports VM snapshots — pause, save state, resume
# Used for: fast function warm-starts, migration, fork-on-demand

# Pause the VM
curl -X PATCH --unix-socket /tmp/fc.sock \
  -H 'Content-Type: application/json' \
  -d '{"state": "Paused"}' \
  http://localhost/vm

# Create a snapshot (memory + VM state)
curl -X PUT --unix-socket /tmp/fc.sock \
  -H 'Content-Type: application/json' \
  -d '{
    "snapshot_type": "Full",
    "snapshot_path": "/tmp/fc-snapshot.snap",
    "mem_file_path": "/tmp/fc-memory.mem"
  }' http://localhost/snapshot/create

# Resume the VM
curl -X PATCH --unix-socket /tmp/fc.sock \
  -H 'Content-Type: application/json' \
  -d '{"state": "Resumed"}' \
  http://localhost/vm

# Restore from snapshot (new Firecracker process)
firecracker --api-sock /tmp/fc2.sock &
curl -X PUT --unix-socket /tmp/fc2.sock \
  -H 'Content-Type: application/json' \
  -d '{
    "snapshot_path": "/tmp/fc-snapshot.snap",
    "mem_backend": {
      "backend_path": "/tmp/fc-memory.mem",
      "backend_type": "File"
    },
    "enable_diff_snapshots": false
  }' http://localhost/snapshot/load

# Snapshot enables the "pre-warmed" Lambda model:
# Start a VM, load the function runtime (Node.js, Python, Go)
# Snapshot at this point
# On each invocation: fork from snapshot (50ms) instead of cold start (125ms+)
```

## Firecracker in production (AWS Lambda model)

```bash
# The Firecracker execution model for Lambda:
# 1. VM is created per concurrent invocation slot (not per request)
# 2. VM stays warm between invocations (paused, not stopped)
# 3. Each invocation: unpause VM → run handler → pause VM
# 4. After timeout: snapshot → terminate → restore on next request
#
# Security model:
# - Each customer's function runs in a dedicated VM (kernel-level isolation)
# - No shared process namespace between customers
# - Jailer process further restricts Firecracker's own capabilities
#   (seccomp, namespace isolation, dropped capabilities)

# Jailer: runs Firecracker in a restricted environment
jailer --id fc-vm-001 \
       --exec-file /usr/local/bin/firecracker \
       --uid 10000 \
       --gid 10000 \
       --chroot-base-dir /srv/firecracker \
       -- --api-sock /run/firecracker.sock

# Kata Containers: uses Firecracker as the runtime for Kubernetes pods
# Each pod gets a Firecracker micro-VM instead of a container namespace
# Provides VM-level isolation with near-container overhead

# containerd + kata-runtime configuration:
cat /etc/containerd/config.toml
# [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.kata-fc]
#   runtime_type = "io.containerd.kata-fc.v2"
#   sandbox_mode = "vm"

# Run a Kubernetes pod with Kata + Firecracker:
kubectl apply -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: construx-secure-job
  annotations:
    io.containerd.cri.runtime-handler: kata-fc
spec:
  runtimeClassName: kata-fc
  containers:
    - name: worker
      image: construx/worker:1.4.2
EOF
```

Firecracker vs gVisor vs Kata Containers: gVisor (also from Google) intercepts syscalls in user space — no full VM, but better isolation than containers. It's slower for syscall-heavy workloads because every syscall is intercepted and handled in user space. Kata Containers wraps OCI containers in a lightweight VM — Firecracker is one of its VM backends, QEMU another. The isolation hierarchy: container namespace (weakest, fastest) → gVisor (better isolation, user-space syscall filter) → Kata/Firecracker (VM-level isolation, stronger, ~5% overhead) → traditional VM (strongest, highest overhead). Firecracker is the right choice when you need VM-level isolation at near-container density: multi-tenant SaaS, untrusted code execution, or when running code from different customers on the same hardware.
