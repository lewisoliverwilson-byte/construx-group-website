date: "2033-07-21"
excerpt: "MinIO is a high-performance, S3-compatible object storage system that runs on your own infrastructure — bare metal, VMs, or Kubernetes. It implements the full AWS S3 API, so any SDK or tool that works with S3 works with MinIO without code changes (just point at a different endpoint). MinIO uses erasure coding instead of replication: data is split into data shards and parity shards across drives/nodes, so the cluster can tolerate multiple simultaneous drive failures with less storage overhead than 3x replication. For example, a 16-drive cluster with EC:8:8 (8 data, 8 parity) can lose any 8 drives simultaneously and still serve reads and writes. MinIO supports multi-tenancy via separate namespaces, bucket policies, IAM-style access keys, and server-side encryption (SSE-S3 with AES-256, SSE-KMS with Vault). The distributed mode (MinIO distributed) scales horizontally: add more nodes and drives, data is rebalanced automatically."

S3-compatible API. Erasure coding. Multi-tenant. KMS encryption. Kubernetes operator.

## Deployment and bucket operations

```bash
# MinIO Kubernetes operator installation
helm install minio-operator \
  minio/operator \
  --namespace minio-operator \
  --create-namespace \
  --set operator.replicaCount=2

# Deploy a MinIO Tenant (distributed cluster)
cat <<'EOF' | kubectl apply -f -
apiVersion: minio.min.io/v2
kind: Tenant
metadata:
  name: construx-storage
  namespace: minio-tenant
spec:
  image: minio/minio:RELEASE.2033-07-01T00-00-00Z
  pools:
    - servers: 4
      volumesPerServer: 4
      volumeClaimTemplate:
        spec:
          storageClassName: gp3-encrypted
          resources:
            requests:
              storage: 2Ti       # 4 servers × 4 drives × 2TB = 32TB raw, ~16TB usable (EC:8:8)
  mountPath: /data
  requestAutoCert: true           # TLS via cert-manager
  certConfig: {}
  env:
    - name: MINIO_BROWSER_REDIRECT_URL
      value: "https://console.minio.construx.internal"
  externalCertSecret:
    - name: minio-tls
      type: cert-manager.io/v1
  prometheusOperator: true        # ServiceMonitor for Prometheus scraping
  kes:                            # Key Encryption Service — KMS integration
    image: minio/kes:2033-07-01
    configuration:
      name: minio-kes-config
      key: config.yaml
EOF

# mc: MinIO Client (S3-compatible CLI)
mc alias set construx \
  https://minio.construx.internal \
  $MINIO_ACCESS_KEY \
  $MINIO_SECRET_KEY \
  --api S3v4

# Create buckets with versioning and lifecycle rules
mc mb construx/construx-artifacts
mc mb construx/construx-backups
mc mb construx/construx-ml-data

# Enable versioning
mc version enable construx/construx-artifacts

# Lifecycle rule: transition to cold storage after 30 days, delete after 365
mc ilm rule add construx/construx-backups \
  --prefix "daily/" \
  --transition-days 30 \
  --transition-storage-class "GLACIER" \
  --expiry-days 365

# Bucket policy: public read for assets, private for everything else
mc anonymous set download construx/construx-public-assets

# Server-side encryption: all objects encrypted with AES-256
mc encrypt set SSE-S3 construx/construx-artifacts
mc encrypt set SSE-KMS construx/construx-backups --kms-key-id construx-backup-key
```

## S3-compatible access from application code

```typescript
// TypeScript: use AWS SDK v3 — no MinIO SDK needed, just set endpoint

import { S3Client, PutObjectCommand, GetObjectCommand, ListObjectsV2Command } from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";

const s3 = new S3Client({
    endpoint:        "https://minio.construx.internal",
    region:          "us-east-1",          // MinIO ignores region but SDK requires it
    credentials: {
        accessKeyId:     process.env.MINIO_ACCESS_KEY!,
        secretAccessKey: process.env.MINIO_SECRET_KEY!,
    },
    forcePathStyle: true,   // required for MinIO: bucket/key instead of bucket.endpoint/key
});

// Upload a file
async function uploadArtifact(tenantId: string, filename: string, data: Buffer): Promise<string> {
    const key = `tenants/${tenantId}/artifacts/${filename}`;
    await s3.send(new PutObjectCommand({
        Bucket:               "construx-artifacts",
        Key:                  key,
        Body:                 data,
        ContentType:          "application/octet-stream",
        ServerSideEncryption: "AES256",
        Metadata: {
            "tenant-id":  tenantId,
            "uploaded-at": new Date().toISOString(),
        },
    }));
    return key;
}

// Generate pre-signed URL (7 days)
async function getDownloadUrl(key: string): Promise<string> {
    return getSignedUrl(
        s3,
        new GetObjectCommand({ Bucket: "construx-artifacts", Key: key }),
        { expiresIn: 604800 },
    );
}

// List objects with prefix
async function listTenantArtifacts(tenantId: string): Promise<string[]> {
    const response = await s3.send(new ListObjectsV2Command({
        Bucket: "construx-artifacts",
        Prefix: `tenants/${tenantId}/artifacts/`,
    }));
    return (response.Contents ?? []).map((obj) => obj.Key!);
}
```

MinIO vs AWS S3 vs Ceph vs Longhorn vs Rook: AWS S3 is the reference and the default for teams on AWS — no operations burden, infinite scale, 11 nines durability. MinIO is for teams that need S3 on their own infrastructure: data residency requirements, air-gapped environments, egress cost reduction, or running their own cloud. Ceph is a mature distributed storage system (RADOS) that supports object (S3-compatible via RGW), block (RBD), and file (CephFS) storage — more complex to operate than MinIO but more capable for mixed workloads. Longhorn and Rook are Kubernetes-native block storage systems — suited for PersistentVolumeClaims, not object storage. MinIO's advantage over Ceph for pure object storage is operational simplicity: a single binary, a simpler deployment model, and consistently higher throughput benchmarks for sequential PUT/GET. For teams running Kubernetes and needing S3-compatible storage without AWS dependencies, MinIO with the operator is the standard choice.
