`EXPLAIN ANALYZE` runs a query and shows you the execution plan with actual timing and row counts. It's the primary tool for diagnosing slow Postgres queries. Once you can read the output, slow query debugging becomes systematic rather than speculative.

## Basic usage

```sql
EXPLAIN ANALYZE
SELECT u.name, p.title
FROM users u
JOIN posts p ON p.author_id = u.id
WHERE u.created_at > '2029-01-01'
ORDER BY p.created_at DESC
LIMIT 20;
```

```

  ->  Sort  (cost=841.23..843.73 rows=1000 width=64) (actual time=12.439..12.442 rows=20 loops=1)
        Sort Key: p.created_at DESC
        Sort Method: top-N heapsort  Memory: 27kB
```

## Reading the output

**Cost**: `(cost=start_cost..total_cost rows=estimated_rows width=estimated_row_size)`. The cost is in arbitrary units — relative, not seconds. `start_cost` is the cost before the first row is returned (relevant for `LIMIT` queries).

**Actual**: `(actual time=first_row_ms..last_row_ms rows=actual_rows loops=n)`. This is real. The gap between estimated and actual rows is where you look for problems.

**Indentation**: nodes are indented under their parent. Execution flows from the innermost (most indented) nodes upward.

**Seq Scan**: a sequential scan reads every row in the table. For small tables it's fine. For large tables it's usually a missing index.

**Index Scan**: uses an index to find specific rows. Usually faster for selective predicates.

**Hash Join**: builds a hash table from one side, probes with the other. Good for large joins. If you see `Batches: N` greater than 1, the hash spilled to disk — `work_mem` is too low.

## Identifying problems

**Large row count discrepancy**:
```
Seq Scan on posts  (cost=0.00..481.00 rows=100 width=48)
                   (actual time=0.012..6.211 rows=18000 loops=1)
```
Postgres estimated 100 rows but found 18,000. The statistics are stale. Run `ANALYZE posts` to refresh them.

**Sequential scan on a large table**:
```
Seq Scan on events  (cost=0.00..48210.00 rows=1200000 width=72)
                    (actual time=0.011..845.221 rows=1200000 loops=1)
```
1.2 million rows scanned. If this has a WHERE clause, you need an index on the filter column.

**High loop count**:
```
Index Scan using idx_posts_author_id on posts
  (actual time=0.021..0.024 rows=3 loops=280)
```
`loops=280` means this node ran 280 times — once per user in an outer loop. Total time is `0.024 * 280 ≈ 6.7ms`. Often visible as a nested loop join over an unindexed foreign key.

## Common fixes

**Missing index**: add an index on the filter column.
```sql
CREATE INDEX CONCURRENTLY idx_users_created_at ON users (created_at);
```

**Stale statistics**: update planner statistics.
```sql
ANALYZE users;
ANALYZE posts;
```

**work_mem too low** (hash spilled to disk):
```sql
SET work_mem = '64MB'; -- per-session, not global
```
Or in `postgresql.conf` for persistent change. Spill is visible in the plan as `Batches: N` > 1.

**N+1 via nested loop**: the outer query returns N rows, and the inner query runs N times. Fix by restructuring as a JOIN or using a subquery.

## EXPLAIN options

```sql
-- Default: estimated costs only (no actual execution)
EXPLAIN SELECT ...;

-- Run the query, show actual timing
EXPLAIN ANALYZE SELECT ...;

-- Show buffers hit/read (useful for cache analysis)
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;

-- JSON output for programmatic parsing
EXPLAIN (ANALYZE, FORMAT JSON) SELECT ...;
```

`BUFFERS` output shows how many pages were read from disk versus from the shared buffer cache. `Shared hit=N` means N pages from cache; `Shared read=N` means N pages from disk. High read counts with low hit counts indicate a cold cache or missing index.

## A systematic approach

1. Run `EXPLAIN ANALYZE` on the slow query
2. Find the node with the highest actual time (usually the most indented)
3. Check: is it a Seq Scan on a large table? Is the row estimate wildly off? Is there a high loop count?
4. Apply the fix (index, ANALYZE, JOIN restructure)
5. Run `EXPLAIN ANALYZE` again to confirm improvement

Most slow queries have a single obvious bottleneck once you look at the plan. The query itself rarely needs to be rewritten — the fix is almost always an index or stale statistics.
