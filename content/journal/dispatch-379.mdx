A CI/CD pipeline for a Next.js app needs to do five things: lint, type-check, test, build, and deploy. The question is what order, what runs in parallel, and where preview deployments live. Here's the setup that works at production scale.

## The pipeline design

```
PR opened / pushed:
  ┌─────────────────────────────────────────┐
  │  lint + typecheck (parallel)            │
  │  test (after lint passes)               │
  │  build (after tests pass)               │
  │  preview deploy (after build)           │
  └─────────────────────────────────────────┘

Merged to main:
  ┌─────────────────────────────────────────┐
  │  all checks (same as PR)                │
  │  database migrations                    │
  │  production deploy                      │
  └─────────────────────────────────────────┘
```

## GitHub Actions: the full workflow

```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

env:
  NODE_VERSION: '22'
  NEXT_PUBLIC_SITE_URL: ${{ secrets.NEXT_PUBLIC_SITE_URL }}

jobs:
  lint:
    name: Lint + Typecheck
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: 'npm'
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck

  test:
    name: Tests
    runs-on: ubuntu-latest
    needs: lint
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: 'npm'
      - run: npm ci
      - run: npm test -- --reporter=verbose
      - name: Upload coverage
        uses: codecov/codecov-action@v4
        if: always()

  build:
    name: Build
    runs-on: ubuntu-latest
    needs: test
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: 'npm'
      - run: npm ci
      - run: npm run build
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
          NEXT_PUBLIC_SITE_URL: ${{ secrets.NEXT_PUBLIC_SITE_URL }}
      - name: Cache build output
        uses: actions/cache/save@v4
        with:
          path: .next
          key: ${{ runner.os }}-next-${{ github.sha }}
```

## Preview deploys on every PR

Vercel handles preview deploys automatically when you connect the repo. For non-Vercel deployments, use GitHub Environments:

```yaml
  deploy-preview:
    name: Deploy Preview
    runs-on: ubuntu-latest
    needs: build
    if: github.event_name == 'pull_request'
    environment:
      name: preview
      url: ${{ steps.deploy.outputs.url }}
    steps:
      - name: Restore build
        uses: actions/cache/restore@v4
        with:
          path: .next
          key: ${{ runner.os }}-next-${{ github.sha }}

      - name: Deploy to Fly.io (preview)
        id: deploy
        run: |
          fly deploy --app my-app-pr-${{ github.event.pull_request.number }} \
            --region lhr --image-label preview-${{ github.sha }}
          echo "url=https://my-app-pr-${{ github.event.pull_request.number }}.fly.dev" >> $GITHUB_OUTPUT
        env:
          FLY_API_TOKEN: ${{ secrets.FLY_API_TOKEN }}

      - name: Comment preview URL on PR
        uses: actions/github-script@v7
        with:
          script: |
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: `Preview deployed: ${{ steps.deploy.outputs.url }}`
            })
```

## Production deploy

```yaml
  deploy-production:
    name: Deploy Production
    runs-on: ubuntu-latest
    needs: build
    if: github.ref == 'refs/heads/main'
    environment:
      name: production
      url: https://construxgroup.io
    steps:
      - uses: actions/checkout@v4

      - name: Run migrations
        run: npx drizzle-kit migrate
        env:
          DATABASE_URL: ${{ secrets.PRODUCTION_DATABASE_URL }}

      - name: Deploy to production
        run: |
          fly deploy --app my-app-prod \
            --region lhr \
            --strategy rolling  # zero-downtime rolling deploy
        env:
          FLY_API_TOKEN: ${{ secrets.FLY_API_TOKEN }}
```

## Environment variables strategy

```
.env.local          ← local dev only, gitignored
.env.example        ← committed, shows what vars are needed
.env.test           ← committed, test environment values
GitHub Secrets      ← staging and production secrets
```

Never commit real secrets. In CI, inject via GitHub Secrets. The `.env.example` documents what's needed:

```bash
# .env.example
DATABASE_URL=postgresql://localhost:5432/myapp_dev
NEXT_PUBLIC_SITE_URL=http://localhost:3000
STRIPE_SECRET_KEY=sk_test_...  # get from Stripe dashboard
RESEND_API_KEY=re_...          # get from resend.com
```

## Build performance optimizations

Builds are slow. Speed them up:

```yaml
      - name: Cache Next.js build
        uses: actions/cache@v4
        with:
          path: |
            ~/.npm
            ${{ github.workspace }}/.next/cache
          key: ${{ runner.os }}-nextjs-${{ hashFiles('**/package-lock.json') }}-${{ hashFiles('**.[jt]s', '**.[jt]sx') }}
          restore-keys: |
            ${{ runner.os }}-nextjs-${{ hashFiles('**/package-lock.json') }}-
```

Next.js's persistent cache (`/.next/cache`) stores compiled pages and modules. Caching it in CI can cut build times by 50–70% on a warm run.

## Branch protection rules

Required for any serious project:

```
main branch protection:
  ✓ Require pull request before merging
  ✓ Require status checks before merging:
      lint, test, build
  ✓ Dismiss stale pull request approvals when new commits pushed
  ✓ Include administrators
```

No one — not even the repo owner — should be able to push directly to `main` without CI passing.

## The rule

The pipeline isn't done until a failed test prevents a production deploy. A CI system that warns but doesn't block is decoration.
