We build AI products. This doesn't mean every feature should use AI. One of the recurring questions in product development at Construx is: does this feature benefit from AI, or are we reaching for AI because it's available?

Here's the framework we've developed.

## The three questions

Before adding AI to a feature, we ask three questions:

**1. Does this feature require intelligence that can't be expressed as rules?**

Some decisions are straightforwardly rule-based. "Is this price above £50?" doesn't need AI. "Calculate the eBay fees for this category and price point" doesn't need AI — there's a formula. If you can write the logic as an explicit rule or calculation, write the rule.

AI is appropriate when the decision requires understanding that's too complex to encode explicitly — interpreting natural language, recognising patterns across many variables, making judgements that humans would make intuitively.

**2. What's the error cost?**

AI outputs are probabilistic, not deterministic. An AI feature will be wrong some percentage of the time. What happens when it's wrong?

For Scoutr's confidence score: when it's wrong (overestimates confidence), the user might pursue a less-profitable product than they expected. This is unfortunate but recoverable. We've accepted this.

For a financial calculation: if the fee calculation is wrong, the user's margin estimate is wrong. In a payment-critical context, an incorrect calculation could lead to a loss. We do not use AI for the fee calculation — we use a precise formula and verify it against eBay's actual fee schedule.

High error cost → prefer rules. Low error cost → AI is acceptable.

**3. Does the AI's output improve over time with more data?**

Some AI features benefit from a feedback loop: the more data you have, the better the model performs. For Scoutr's product classification, we could fine-tune a model as we accumulate more classified products. The quality improves with scale.

Other AI uses don't benefit from data accumulation — the quality ceiling is determined by the foundation model, not by your data. For a feature that hits that ceiling quickly, the benefit of AI may not justify the complexity.

## Where we use AI and why

**Scoutr — product profitability analysis.** The classification of whether a product is a good arbitrage opportunity involves interpreting category, brand, historical price trends, and market conditions. This can't be reduced to a rule. AI is appropriate.

**The Marqet — listing classification and quality scoring.** Determining whether a listing description matches a category, and whether it's well-written, requires natural language understanding. AI is appropriate. Error cost is low — a mislabelled listing is flagged for review.

**The Marqet — semantic search.** Matching buyer intent to listing content across terminology differences requires semantic understanding. AI (vector embeddings) is appropriate.

**The Hyve — AI agent in workspace channels.** The agent assists with summarising decisions, drafting strategy documents, and answering questions about past channel history. These tasks require generative understanding. AI is the core feature.

## Where we don't use AI

**Fee calculations.** eBay fees are calculated from a published formula. We implement the formula exactly. An AI approximation would be less accurate than the formula for no benefit.

**Authentication and access control.** Security decisions must be deterministic. AI has no role in deciding whether a user is authenticated.

**Payment processing.** Stripe's API is the authority on whether a payment succeeded. We don't use AI to interpret payment outcomes.

**Schema validation.** If a request body doesn't conform to the expected schema, it's rejected. This is a rule, not a judgment.

**Routing and navigation.** The application navigates based on explicit logic. There's no benefit to AI involvement in deciding which page to render.

## The "AI everywhere" failure mode

The most common mistake in early-stage AI products is adding AI to features that don't need it. The symptoms:

- The feature is slow because it requires an API call that could be avoided.
- The feature occasionally produces wrong outputs that are hard to explain.
- The codebase has unnecessary AI dependencies that complicate testing.
- The product is harder to debug because AI outputs are non-deterministic.

Every AI feature is a cost: API calls, latency, probabilistic outputs, debugging complexity. The cost needs to be justified by a genuine quality improvement that couldn't be achieved with deterministic logic.

If a feature can be done well with rules, use rules. AI is appropriate when rules are insufficient, not when rules are merely less convenient.

## The validation test

Before building an AI feature, we validate it manually first. Before Scoutr's profitability analysis was AI-powered, we manually scored a sample of 50 products and compared the results to eBay sold data. The manual scoring was accurate enough to validate the approach — then we built the AI feature to automate it.

If you can't validate the feature manually (because you can't define what "good" looks like), you can't validate the AI version either. Start with a manual version, validate the concept, then automate.
