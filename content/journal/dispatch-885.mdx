date: "2032-03-22"
excerpt: "DNSSEC (DNS Security Extensions) adds cryptographic signatures to DNS records, allowing resolvers to verify that responses haven't been tampered with in transit. The signing chain works root-down: the DNS root zone signs TLD zone keys, TLD zones sign domain zone keys, and domain zones sign their own records. Each level uses DNSKEY records (public keys) and DS records (digests of child zone keys) to build an unbroken delegation chain. DNSSEC protects against cache poisoning (Kaminsky attack) and DNS hijacking — it doesn't encrypt DNS traffic (that's DoT/DoH), it authenticates it."
author: "Lewis Wilson"
tag: "Build Log"
---

Root signs TLDs. TLDs sign domains. Domains sign records. Every step verifiable.

## DNSSEC record types and signing chain

```bash
# DNSSEC adds 4 new record types to DNS:
# DNSKEY  — the zone's public signing key
# RRSIG   — signature over a set of records (RRset)
# DS      — digest of a child zone's DNSKEY, published in the parent zone
# NSEC/NSEC3 — authenticated denial of existence (proves a record doesn't exist)

# Signing chain for construx.io:
# . (root) → DS for .io → .io DNSKEY signs DS for construx.io →
# construx.io DNSKEY signs A records

# Query DNSKEY records — the zone's public keys
dig DNSKEY construx.io +short
# 256 3 13 mdsswUyr3DPW132mOi8V9xESWE8jTo0dxCjjnopKl+GqJxpVXckHAeF8 ...
# 257 3 13 mdsswUyr3DPW132mOi8V9xESWE8jTo0dxCjjnopKl+GqJxpVXckHAeF8 ...
# ^^ Flag 257 = KSK (Key Signing Key): signs other DNSKEYs, published in parent as DS
# ^^ Flag 256 = ZSK (Zone Signing Key): signs all other records, rotated more often

# Query DS record in parent zone (.io)
dig DS construx.io +short
# 12345 13 2 E06D44B80B8F1D39A95C0B0D7C65D08458E880409BBC683457104237C7F8EC8D

# Inspect signatures on A records
dig A construx.io +dnssec +short
# 203.0.113.42
# A 13 2 300 20320419000000 20320320000000 56789 construx.io. P1+...
# RRSIG: algorithm=13 (ECDSA P-256), inception=2032-03-20, expiry=2032-04-19
```

## Signing a zone with BIND

```bash
# Generate Key Signing Key (KSK) — algorithm 13 = ECDSA P-256
dnssec-keygen -a ECDSAP256SHA256 -f KSK -n ZONE construx.io
# Kconstrux.io.+013+12345.key   (public)
# Kconstrux.io.+013+12345.private

# Generate Zone Signing Key (ZSK)
dnssec-keygen -a ECDSAP256SHA256 -n ZONE construx.io
# Kconstrux.io.+013+56789.key
# Kconstrux.io.+013+56789.private

# Sign the zone (produces construx.io.signed)
dnssec-signzone \
  -A \                          # Include NSEC3 for authenticated denial
  -3 $(openssl rand -hex 8) \   # NSEC3 salt (random)
  -o construx.io \              # Zone origin
  -t \                          # Print statistics
  -k Kconstrux.io.+013+12345 \ # KSK
  construx.io.zone \            # Unsigned zone file
  Kconstrux.io.+013+56789      # ZSK

# Output:
# Verifying the zone using the following algorithms: ECDSAP256SHA256
# Zone signing complete:
#   Total records signed:    48
#   Signatures generated:    48
#   Signatures retained:      0
#   Signatures dropped:       0
#   Input zone had 12 records
# The zone is signed and ready to load.

# Publish DS record to parent registrar (copy from dsset-construx.io.)
cat dsset-construx.io.
# construx.io.  IN DS 12345 13 2 E06D44B80B8F1D39A95C0B0D7C65D08458E880409BBC...
# Submit this to your registrar's DS management interface
```

## DNSSEC validation — checking the chain

```bash
# delv: DNS lookup and validation tool (replacement for dig +dnssec for validation)
delv @8.8.8.8 construx.io A +rtrace
# ;; fetch: construx.io/A
# ;; fetch: construx.io/DNSKEY
# ;; fetch: io/DS
# ;; fetch: io/DNSKEY
# ;; fetch: ./DS
# ;; validating construx.io/A: starting
# ;; validating construx.io/A: looking for DS record
# ;; validating construx.io/DNSKEY: starting
# ;; validating construx.io/DNSKEY: DS record found
# ;; validating construx.io/DNSKEY: verified DNSKEY
# ;; validating construx.io/A: verified A RRset
# ; fully validated
# construx.io.  300  IN  A  203.0.113.42

# Check DNSSEC chain with dnssec-verify
dnssec-verify -o construx.io construx.io.signed
# Verifying the zone using the following algorithms: ECDSAP256SHA256.
# Zone fully verified.

# Check expiry on signatures (RRSIG records expire — must re-sign before then)
dig RRSIG A construx.io +short | awk '{print $5}' | \
  xargs -I{} date -d "$(echo {} | sed 's/\(....\)\(..\)\(..\)\(..\)\(..\)\(..\)/\1-\2-\3 \4:\5:\6/')" +%s | \
  xargs -I{} bash -c 'echo "Expires in $(( ({} - $(date +%s)) / 86400 )) days"'
# Expires in 27 days
```

## Automated key rotation with OpenDNSSEC

```bash
# OpenDNSSEC automates ZSK rotation (every 30 days) and KSK rollover (annually)
# Configuration: /etc/opendnssec/kasp.xml (Key And Signing Policy)

# Key policy for construx.io:
# ZSK: ECDSA P-256, rotate every 30 days, resign every 7 days
# KSK: ECDSA P-256, rotate every 365 days (requires registrar DS update)

# Check key states
ods-ksmutil key list
# Zone: construx.io
# Key role: KSK
#   ID: 12345, state: OMNIPRESENT (active), publish: 2032-01-01
# Key role: ZSK
#   ID: 56789, state: OMNIPRESENT (active), publish: 2032-03-01
#   ID: 67890, state: RUMOURED (next key), publish: 2032-03-25 ← pre-published

# Force re-sign after zone changes
ods-signer sign construx.io

# Monitor signing via syslog
journalctl -u opendnssec -f
# ods-signerd[1234]: zone construx.io: signing complete, 48 RRSIGs
```

DNSSEC vs DoT/DoH: DNSSEC and DNS-over-TLS/HTTPS solve different problems. DoT/DoH encrypts the DNS query in transit — your ISP can't see what you're resolving. DNSSEC authenticates the answer — even if you receive an unencrypted response, you can verify it wasn't tampered with. They're complementary: a recursive resolver can validate DNSSEC (authenticate) while using DoT to its upstream (encrypt). The gap DNSSEC doesn't fill: the last-mile stub resolver to recursive resolver path. That's where DoT/DoH matters most.
