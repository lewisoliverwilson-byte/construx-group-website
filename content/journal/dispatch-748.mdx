Background job infrastructure is solved. Trigger.dev v3 runs jobs without managing queues or workers.

## Install

```bash
npm install @trigger.dev/sdk@v3
npx trigger.dev@latest init
```

This adds a `trigger.config.ts` and creates `src/trigger/` for your job definitions.

## Define a job

```ts
// src/trigger/email-sequence.ts
import { task, wait, logger } from '@trigger.dev/sdk/v3';
import { resend }             from '@/lib/resend';
import { db }                 from '@/lib/db';

export const emailSequenceTask = task({
  id:       'email-sequence',
  maxDuration: 60 * 60 * 24 * 7,  // 7 days max

  run: async (payload: { userId: string; email: string; sequenceId: string }) => {
    const { userId, email, sequenceId } = payload;

    logger.info('Starting email sequence', { userId, sequenceId });

    // Step 1: welcome email
    await resend.emails.send({
      to:      email,
      subject: 'Welcome',
      html:    '<p>Welcome!</p>',
    });
    logger.info('Sent welcome email');

    // Wait 3 days — the task is paused, not polling
    await wait.for({ days: 3 });

    // Check if user has completed onboarding
    const user = await db.users.findUnique({ where: { id: userId } });
    if (user?.onboardedAt) {
      logger.info('User already onboarded, skipping reminder');
      return { skipped: true };
    }

    // Step 2: onboarding reminder
    await resend.emails.send({
      to:      email,
      subject: 'Finish setting up your workspace',
      html:    '<p>You started signing up…</p>',
    });

    await wait.for({ days: 4 });

    // Step 3: final check-in
    const updated = await db.users.findUnique({ where: { id: userId } });
    if (!updated?.onboardedAt) {
      await resend.emails.send({
        to:      email,
        subject: 'Can we help?',
        html:    '<p>We noticed you haven't set up your workspace…</p>',
      });
    }

    return { completed: true };
  },
});
```

## Trigger a job from your API

```ts
// src/app/api/signup/route.ts
import { tasks } from '@trigger.dev/sdk/v3';
import { emailSequenceTask } from '@/trigger/email-sequence';

export async function POST(request: Request) {
  const { email } = await request.json();
  const user = await createUser(email);

  // Trigger the job — non-blocking
  const handle = await tasks.trigger<typeof emailSequenceTask>(
    'email-sequence',
    { userId: user.id, email, sequenceId: 'onboarding-v2' },
  );

  return Response.json({ userId: user.id, jobId: handle.id }, { status: 201 });
}
```

## Batch triggering

```ts
// Send 1000 emails in parallel — Trigger.dev manages concurrency
await tasks.batchTrigger<typeof emailSequenceTask>(
  'email-sequence',
  users.map((u) => ({ payload: { userId: u.id, email: u.email, sequenceId: 'weekly-digest' } })),
);
```

## Scheduled jobs

```ts
// src/trigger/weekly-report.ts
import { schedules } from '@trigger.dev/sdk/v3';

export const weeklyReport = schedules.task({
  id:       'weekly-report',
  cron:     '0 8 * * 1',  // Every Monday at 8am UTC

  run: async (payload) => {
    const report = await generateWeeklyReport(payload.timestamp);
    await sendReportEmail(report);
    return { generated: report.id };
  },
});
```

## Trigger.dev vs BullMQ vs Temporal vs Inngest

Trigger.dev: managed infrastructure, real-time observability, no Redis or cluster to maintain, best DX for new projects. BullMQ: self-hosted Redis, high throughput (100k+ jobs/s), good for existing Redis infrastructure. Temporal: complex workflows, human-in-the-loop, enterprise durability requirements. Inngest: similar to Trigger.dev, slightly different API, strong event-driven model. The Construx default: BullMQ for high-frequency simple jobs, Trigger.dev for user-facing sequences and workflows where observability matters.
