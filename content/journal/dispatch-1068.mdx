excerpt: "etcd is a distributed, strongly consistent key-value store built on the Raft consensus algorithm. It is the source of truth for the Kubernetes control plane: every Kubernetes object (Pod, Deployment, Service, ConfigMap, Secret) is stored as a key-value entry in etcd. The Kubernetes API server is the only component that reads and writes etcd directly — all other components (scheduler, controller manager, kubelet) get state through the API server. etcd's watch API is the mechanism by which Kubernetes is reactive: a component watching a key prefix receives an event stream of every change to that prefix, which is how the scheduler detects unscheduled pods and how controllers reconcile desired state with actual state. etcd uses a WAL (write-ahead log) and periodic snapshots for durability. A production etcd cluster runs 3 or 5 members (odd numbers to maintain quorum). etcd is intentionally kept simple — it is not a general-purpose database, and Kubernetes best practice is to run a dedicated etcd cluster for the Kubernetes control plane rather than sharing it with application state."

## etcd cluster setup and operations

```bash
# Production etcd: 3-member cluster for Kubernetes control plane
# Each member runs on a dedicated control plane node

# etcd member on node-01 (similar config on node-02, node-03)
etcd \
  --name                        node-01 \
  --data-dir                    /var/lib/etcd \
  --listen-client-urls          https://10.0.1.10:2379 \
  --advertise-client-urls       https://10.0.1.10:2379 \
  --listen-peer-urls            https://10.0.1.10:2380 \
  --initial-advertise-peer-urls https://10.0.1.10:2380 \
  --initial-cluster             node-01=https://10.0.1.10:2380,node-02=https://10.0.1.11:2380,node-03=https://10.0.1.12:2380 \
  --initial-cluster-token       etcd-prod-cluster \
  --initial-cluster-state       new \
  # TLS: client-to-server and peer-to-peer
  --cert-file                   /etc/etcd/tls/server.crt \
  --key-file                    /etc/etcd/tls/server.key \
  --trusted-ca-file             /etc/etcd/tls/ca.crt \
  --client-cert-auth            true \
  --peer-cert-file              /etc/etcd/tls/peer.crt \
  --peer-key-file               /etc/etcd/tls/peer.key \
  --peer-trusted-ca-file        /etc/etcd/tls/ca.crt \
  --peer-client-cert-auth       true \
  # Performance tuning for Kubernetes workloads
  --quota-backend-bytes         8589934592 \  # 8GiB max DB size
  --auto-compaction-mode        periodic \
  --auto-compaction-retention   1h \          # compact every 1h to reclaim space
  --snapshot-count              10000          # snapshot every 10k commits
```

## Kubernetes data in etcd and watch API

```bash
# Kubernetes stores everything under /registry/ prefix

# List all keys for pods in the default namespace
etcdctl get /registry/pods/default --prefix --keys-only | head -5
# /registry/pods/default/construx-api-7d8f9b-4k2p9
# /registry/pods/default/construx-api-7d8f9b-8m1x3
# /registry/pods/default/construx-worker-6c9f2d-5n7q2

# Read a pod object (stored as protobuf, decode with hex)
etcdctl get /registry/pods/default/construx-api-7d8f9b-4k2p9 | xxd | head -5
# 0000: 2f72 6567 6973 7472 792f 706f 6473 2f64  /registry/pods/d

# Watch API: stream changes to a key prefix in real time
# This is what the Kubernetes scheduler and controllers do internally
etcdctl watch /registry/pods/ --prefix | while read line; do echo "EVENT: $line"; done
# EVENT: PUT /registry/pods/default/construx-api-7d8f9b-9x4k1
# (output: protobuf bytes of the new pod object)
# EVENT: DELETE /registry/pods/default/construx-api-7d8f9b-4k2p9

# Snapshot: manual backup of the etcd database
etcdctl snapshot save /var/backup/etcd/snapshot-$(date +%Y%m%d-%H%M%S).db
# {"level":"info","ts":"2033-09-22","msg":"saved","path":"/var/backup/etcd/snapshot-20330922-020001.db"}
# Snapshot DB size: 185 MB

# Compaction: release disk space from old revisions
etcdctl compact $(etcdctl endpoint status --write-out="json" | \
  jq -r '.[] | .Status.header.revision' | sort -n | head -1)
etcdctl defrag --cluster

# Performance: 99th percentile commit latency should be < 25ms
etcdctl check perf
# 60 / 60 passed, 0 failed
# PASS: Throughput is 150 writes/s
# PASS: Slowest request took 18.4ms
# PASS: Stddev is 2.1ms
```

etcd vs ZooKeeper vs Consul vs CockroachDB for distributed coordination: ZooKeeper is the predecessor — also Paxos-based, also used for distributed coordination, but with a JVM dependency, a more complex client API, and a harder operational model. etcd replaced ZooKeeper as the standard Kubernetes backing store precisely because it is simpler, written in Go, and exposes a clean gRPC/HTTP API. Consul (HashiCorp) is a service mesh and key-value store — its KV store uses Raft but it's designed for service discovery and configuration, not as a control plane database. CockroachDB is a distributed SQL database using Raft per-range — it can model etcd-like use cases but brings far more complexity. etcd's design philosophy is deliberate narrowness: it is a strongly consistent, watch-capable key-value store for small data (< 8GB), not a general-purpose database. For teams operating Kubernetes, etcd operations knowledge — compaction, defrag, snapshot restore, leader election, Raft troubleshooting — is critical infrastructure knowledge. An etcd failure at the wrong moment can make an entire Kubernetes cluster unresponsive, since the API server cannot process writes without quorum.
