Most applications don't need Elasticsearch. PostgreSQL's full-text search handles millions of documents with sub-100ms queries, supports ranking, stemming, phrase matching, and weighted fields. The only thing it doesn't do well is fuzzy matching — for that, `pg_trgm` fills the gap.

## Core concepts

PostgreSQL full-text search converts text into `tsvector` (a list of lexemes) and queries into `tsquery`. The match operator is `@@`:

```sql
-- Does this document match this query?
SELECT 'the quick brown fox'::tsvector @@ 'fox'::tsquery; -- true

-- More practical: convert text using a language dictionary
SELECT to_tsvector('english', 'The quick brown fox jumps') 
  @@ to_tsquery('english', 'jump'); -- true (stemming: jump → jump*)
```

`to_tsvector` strips stop words and applies stemming. `to_tsquery` does the same for the query terms.

## Schema design

Store the `tsvector` in a generated column — it stays in sync automatically:

```sql
CREATE TABLE articles (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  title       TEXT NOT NULL,
  content     TEXT NOT NULL,
  author      TEXT NOT NULL,
  published   BOOLEAN NOT NULL DEFAULT false,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),

  -- Weighted tsvector: title gets weight A (highest), content gets weight C
  search_vector TSVECTOR GENERATED ALWAYS AS (
    setweight(to_tsvector('english', coalesce(title, '')), 'A') ||
    setweight(to_tsvector('english', coalesce(content, '')), 'C')
  ) STORED
);

-- GIN index on the vector for fast searches
CREATE INDEX articles_search_idx ON articles USING gin(search_vector);
```

Weights: A > B > C > D. Title matches rank higher than content matches because title has weight A.

## Querying

```sql
-- Basic search
SELECT id, title, ts_rank(search_vector, query) AS rank
FROM articles, to_tsquery('english', 'redis & cache') query
WHERE search_vector @@ query
  AND published = true
ORDER BY rank DESC
LIMIT 20;

-- Phrase search
SELECT id, title
FROM articles
WHERE search_vector @@ phraseto_tsquery('english', 'cache invalidation');

-- Partial/prefix matching (useful for search-as-you-type)
SELECT id, title
FROM articles
WHERE search_vector @@ to_tsquery('english', 'redis:*');
-- redis:* matches redis, redisearch, redistribution etc.
```

## Highlighting snippets

```sql
SELECT 
  id, 
  title,
  ts_headline(
    'english',
    content,
    query,
    'MaxWords=35, MinWords=15, ShortWord=3, HighlightAll=false, MaxFragments=2'
  ) AS snippet
FROM articles, to_tsquery('english', 'cache invalidation') query
WHERE search_vector @@ query;
```

`ts_headline` wraps matching terms in `<b>` tags by default. The result is a contextual snippet showing where the matches appear in the document.

## In application code (Drizzle)

```ts
// lib/search.ts
import { db } from '@/db';
import { sql } from 'drizzle-orm';

export async function searchArticles(query: string, limit = 20) {
  // Sanitize: split on whitespace, join with &, append :* for prefix matching
  const tsQuery = query
    .trim()
    .split(/\s+/)
    .filter(Boolean)
    .map((term) => `${term}:*`)
    .join(' & ');

  if (!tsQuery) return [];

  return db.execute(sql`
    SELECT
      id,
      title,
      excerpt,
      slug,
      ts_rank(search_vector, to_tsquery('english', ${tsQuery})) AS rank,
      ts_headline(
        'english',
        content,
        to_tsquery('english', ${tsQuery}),
        'MaxWords=25, MinWords=10, MaxFragments=1'
      ) AS snippet
    FROM articles
    WHERE search_vector @@ to_tsquery('english', ${tsQuery})
      AND published = true
    ORDER BY rank DESC
    LIMIT ${limit}
  `);
}
```

## Fuzzy matching with pg_trgm

For typo-tolerance and fuzzy search, combine with `pg_trgm`:

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

-- Trigram index for similarity search
CREATE INDEX articles_trgm_idx ON articles USING gin(title gin_trgm_ops);

-- Find articles where title is similar to the query (typos allowed)
SELECT id, title, similarity(title, 'redis cacheing') AS sim
FROM articles
WHERE title % 'redis cacheing'  -- % operator: similarity > threshold (default 0.3)
ORDER BY sim DESC
LIMIT 10;
```

In practice: run full-text search first (fast, precise), fall back to trigram search if full-text returns no results (slower, fuzzy).

## Performance at scale

For 1M+ documents, partition by a date column and run `VACUUM ANALYZE` regularly to keep the GIN index healthy. The index size grows approximately linearly with document count — expect ~500MB per million mid-length documents. That's significantly cheaper than running Elasticsearch.

The practical ceiling before Elasticsearch becomes necessary is around 10M documents with complex search requirements (multi-language, faceted filtering, ML ranking). Below that, Postgres full-text search is the right choice.
