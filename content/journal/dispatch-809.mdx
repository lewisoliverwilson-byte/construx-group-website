date: "2031-08-06"
excerpt: "Turborepo is a build system for JavaScript/TypeScript monorepos. Its core feature is content-addressable task caching — if the inputs to a task (source files, env vars, dependencies) haven't changed, the output is replayed from cache in milliseconds. Combined with parallel task execution and a dependency graph that understands which packages need rebuilding, Turborepo turns a multi-package monorepo into something that builds as fast as a single package."

Same inputs, same output. Cache the output, skip the build.

## Workspace layout

```
construx-workspace/
├── apps/
│   ├── web/           # Next.js app
│   └── api/           # Hono API
├── packages/
│   ├── ui/            # Shared components
│   ├── db/            # Drizzle schema + client
│   ├── auth/          # Auth utilities
│   └── tsconfig/      # Shared TypeScript config
├── turbo.json
└── package.json       # Root workspace
```

## turbo.json — pipeline definition

```json
{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "inputs":    ["src/**", "package.json", "tsconfig.json"],
      "outputs":   [".next/**", "dist/**", "!.next/cache/**"]
    },
    "lint": {
      "dependsOn": ["^lint"],
      "inputs":    ["src/**", ".eslintrc*", "biome.json"]
    },
    "typecheck": {
      "dependsOn": ["^typecheck"],
      "inputs":    ["src/**", "tsconfig.json", "*.ts"]
    },
    "test": {
      "dependsOn": ["^build"],
      "inputs":    ["src/**", "test/**", "vitest.config.ts"],
      "outputs":   ["coverage/**"]
    },
    "dev": {
      "cache":     false,
      "persistent": true
    }
  }
}
```

The `^` prefix in `dependsOn` means "all workspace dependencies must complete this task first." `build: dependsOn: ["^build"]` ensures `packages/db` builds before `apps/api`.

## Running tasks

```bash
# Build everything (parallel, dependency-aware)
turbo run build

# Build only affected packages (since last git commit)
turbo run build --filter=...[HEAD^1]

# Build a specific app and its dependencies
turbo run build --filter=apps/web...

# Run dev servers for the whole workspace
turbo run dev

# Lint + typecheck in parallel
turbo run lint typecheck
```

## Cache mechanics

```bash
# First run — cache MISS, tasks execute
turbo run build
# >>> FULL TURBO (cache hit rate: 0%)

# Change a file in packages/ui
# Second run — only ui and its dependents rebuild
turbo run build
# packages/tsconfig  >>> CACHED in 12ms
# packages/db        >>> CACHED in 8ms
# packages/auth      >>> CACHED in 11ms
# packages/ui              RUN   1.2s
# apps/web                 RUN   8.7s
# apps/api           >>> CACHED in 9ms
# >>> FULL TURBO (cache hit rate: 66%)
```

## Remote caching — share cache across CI and team

```bash
# Authenticate with Vercel remote cache
turbo login
turbo link

# Or self-host with Turborepo remote cache server
# turbo.json
{
  "remoteCache": {
    "enabled":   true,
    "apiUrl":    "https://turbo-cache.construx.internal"
  }
}
```

With remote caching, a CI run that was already built locally gets 100% cache hits — the CI pipeline takes seconds instead of minutes.

## package.json workspace config

```json
{
  "name":       "construx-workspace",
  "private":    true,
  "workspaces": ["apps/*", "packages/*"],
  "scripts": {
    "build":     "turbo run build",
    "dev":       "turbo run dev",
    "lint":      "turbo run lint",
    "typecheck": "turbo run typecheck",
    "test":      "turbo run test"
  }
}
```

Turborepo vs Nx: both do build caching and task orchestration. Nx has more built-in generators, code scaffolding, and plugin ecosystem. Turborepo is simpler — one config file, no plugin system, no concept of "project graph" beyond what package.json workspaces already define. The Construx default: Turborepo for JavaScript monorepos where simplicity matters; Nx only when the generator/plugin ecosystem is genuinely needed.
