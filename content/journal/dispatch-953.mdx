title: "act: run GitHub Actions workflows locally with Docker — no CI push needed"
date: "2032-10-12"
excerpt: "act is a tool that reads your .github/workflows/*.yaml files and executes them locally inside Docker containers — the same Docker images that GitHub-hosted runners use. It eliminates the feedback loop of pushing a commit to CI just to see if a workflow step works: you get the full step output, environment variables, and action execution in your terminal. act maps events (push, pull_request, workflow_dispatch) to local execution. Secrets from .secrets or environment variables are passed to the workflow. The platform flag lets you use community-maintained runner images (catthehacker/ubuntu:act-*) that pre-install common tools. act is particularly useful for linting workflow files, testing matrix builds, and debugging action failures without a CI round-trip."

Run the workflow locally. Debug action failures in seconds. No push, no wait, no credits burned.

## Basic usage and event simulation

```bash
# act: run the default push event (reads .github/workflows/ in current directory)
act push

# Run a specific workflow
act push -W .github/workflows/ci.yaml

# Run a specific job (by job ID in the workflow file)
act push --job test
act push --job lint

# Simulate other events
act pull_request
act workflow_dispatch
act schedule   # cron-triggered workflows

# --list: show all workflows and jobs without running
act push --list
# Stage  Job ID   Job name         Workflow name   Workflow file
#   0    test     Unit tests       CI              .github/workflows/ci.yml
#   0    lint     golangci-lint    CI              .github/workflows/ci.yml
#   1    release  GoReleaser       Release         .github/workflows/release.yml

# --dryrun: show what would run without executing
act push --dryrun
```

## Runner images and platform configuration

```bash
# GitHub Actions uses ubuntu-latest, ubuntu-22.04, etc.
# act maps these to Docker images — default is nektos/act-environments-ubuntu:18.04
# For a closer match to GitHub's actual environment, use catthehacker images

# ~/.actrc: default flags applied to every act run
cat ~/.actrc
# --platform ubuntu-latest=catthehacker/ubuntu:act-22.04
# --platform ubuntu-22.04=catthehacker/ubuntu:act-22.04
# --platform ubuntu-20.04=catthehacker/ubuntu:act-20.04
# -P ubuntu-24.04=catthehacker/ubuntu:act-24.04
# --container-architecture linux/amd64   # force amd64 on Apple Silicon

# Run with a custom runner image
act push \
  --platform ubuntu-latest=catthehacker/ubuntu:act-22.04 \
  --job test

# Available catthehacker images (pre-installed tools: node, go, python, docker):
# catthehacker/ubuntu:act-22.04   — most GitHub workflows work here
# catthehacker/ubuntu:act-20.04   — older workflows
# catthehacker/ubuntu:full-22.04  — includes browser drivers (Cypress, Playwright)

# Use a smaller image for fast startup (no pre-installed tools, install in steps)
act push --platform ubuntu-latest=node:18-bullseye-slim --job node-test
```

## Secrets and environment variables

```bash
# .secrets file (never commit this — add to .gitignore)
cat .secrets
# GITHUB_TOKEN=ghp_...
# AWS_ACCESS_KEY_ID=AKIA...
# AWS_SECRET_ACCESS_KEY=...
# DOCKERHUB_TOKEN=dckr_pat_...

# act reads .secrets by default in the current directory
act push --job release

# Pass secrets individually
act push --secret GITHUB_TOKEN="$GITHUB_TOKEN" --job release

# Pass env file
cat .env.act
# NODE_ENV=test
# DATABASE_URL=postgres://construx:pass@localhost:5432/construx_test

act push --env-file .env.act

# GitHub context: act injects GITHUB_* variables automatically
# $GITHUB_SHA, $GITHUB_REF, $GITHUB_ACTOR, etc.
# Override them for testing:
act push --env GITHUB_REF=refs/heads/feature/my-branch

# Pass inputs for workflow_dispatch
cat <<'EOF' | act workflow_dispatch --eventpath /dev/stdin
{
  "action": "workflow_dispatch",
  "inputs": {
    "environment": "staging",
    "version": "v1.4.2"
  }
}
EOF
```

## Docker-in-Docker and services

```bash
# Many workflows use Docker (docker build, docker push)
# act supports Docker-in-Docker via the host Docker socket

# Allow act to bind the Docker socket into the runner container:
act push --job build --bind

# .github/workflows/ci.yml — a workflow that builds a Docker image
# steps:
#   - uses: actions/checkout@v4
#   - name: Build Docker image
#     run: docker build -t construx/api:test .
#   - name: Run container tests
#     run: |
#       docker run --rm construx/api:test go test ./...

# Service containers (postgres, redis) in act:
# act starts service containers before the job, same as GitHub does
# services:
#   postgres:
#     image: postgres:16
#     env:
#       POSTGRES_PASSWORD: test
#     ports:
#       - 5432:5432

act push --job integration-test

# Reuse containers between runs (faster for local iteration)
act push --reuse   # keeps containers alive after the run
act push --reuse --job test   # reuse and run test job

# Rebuild containers even if they exist
act push --rebuild
```

## Matrix builds

```bash
# GitHub Actions matrix: run jobs in parallel across combinations
# .github/workflows/ci.yml
# strategy:
#   matrix:
#     go-version: ['1.21', '1.22']
#     os: [ubuntu-latest, macos-latest]

# act runs matrix builds locally (sequentially, not in parallel)
act push --job test --matrix go-version:1.22
act push --job test --matrix go-version:1.21,os:ubuntu-latest

# Run all matrix combinations
act push --job test

# Verbose output to debug step failures
act push --job test --verbose

# Watch step-level output in real time
act push --job test 2>&1 | grep -E "(✅|❌|⭐|🚀|🐳)"
```

act vs GitHub Actions directly vs CircleCI local: CircleCI has a local CLI that runs jobs, but it's limited to CircleCI-specific config. act is GitHub Actions native — the same YAML, the same action versions, the same step IDs. The main limitation: act doesn't perfectly replicate every GitHub service (GitHub Packages, Dependabot, OIDC tokens for cloud providers). For OIDC-dependent workflows (AWS role assumption, GCP Workload Identity), you'll still need the real CI. The practical use case: use act to iterate on workflow YAML without burning CI minutes or waiting for the CI queue. A failed act run in 30 seconds is faster and cheaper than a failed GitHub Actions run in 4 minutes.
