Prisma Migrate is a tool for evolving your Postgres schema over time without losing data. It generates SQL migration files from your Prisma schema, maintains a history of applied migrations, and provides a development workflow that separates schema authoring from schema application.

## The workflow

**1. Edit the schema**:

```prisma
// prisma/schema.prisma
model Post {
  id        String   @id @default(cuid())
  title     String
  content   String?
  published Boolean  @default(false)
  authorId  String
  author    User     @relation(fields: [authorId], references: [id])
  tags      String[] // new field
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}
```

**2. Generate the migration**:

```bash
npx prisma migrate dev --name add_post_tags
```

This command:
- Creates a shadow database
- Computes the diff between the current schema and the shadow
- Generates a SQL migration file in `prisma/migrations/`
- Applies the migration to your development database

**3. Review the generated SQL**:

```sql
-- prisma/migrations/20290930120000_add_post_tags/migration.sql
ALTER TABLE "Post" ADD COLUMN "tags" TEXT[] NOT NULL DEFAULT '{}';
```

Always review the generated SQL before committing. Prisma handles the common cases correctly; complex cases (renaming a column, splitting a table) may need manual adjustment.

**4. Commit the migration file**:

```bash
git add prisma/migrations/20290930120000_add_post_tags/
git commit -m "migration: add tags to Post"
```

Migration files are immutable once committed. Never edit an applied migration.

## Applying migrations in production

```bash
# Apply all pending migrations (CI/CD)
npx prisma migrate deploy
```

`migrate deploy` applies pending migrations and fails if any previously applied migration has been modified. It's designed for CI/CD pipelines — non-interactive, errors clearly, exits with non-zero on failure.

**The critical rule**: run `migrate deploy` before deploying new code. Code that expects the new schema must only run after the schema has been updated. In a blue/green deployment, apply migrations as part of the pre-deploy step, not during the deploy.

## Unsafe operations

Some migrations are inherently dangerous:

**Adding NOT NULL column without a default**:

```sql
ALTER TABLE "User" ADD COLUMN "phoneNumber" TEXT NOT NULL;
-- Fails if existing rows don't have a value
```

The fix: add with a default, backfill, then remove the default if needed.

```prisma
// Step 1: add with default
phoneNumber String @default("")

// Step 2: after backfilling real data, make it required
phoneNumber String // NOT NULL, no default
```

**Dropping a column**: any code still running that reads the old column will fail. Deploy code that doesn't read the column first, then drop it in a subsequent migration.

**Renaming a column**: Prisma treats this as a drop + add. Use `@map` to rename in the schema without changing the database column name:

```prisma
email String @map("emailAddress")  // Prisma field is "email", DB column is "emailAddress"
```

Or do a two-step migration: add the new column, backfill, remove the old one.

## Baseline migrations for existing databases

If you're adding Prisma to an existing database, generate a baseline migration that reflects the current state:

```bash
npx prisma migrate diff \
  --from-empty \
  --to-schema-datamodel prisma/schema.prisma \
  --script > prisma/migrations/0_init/migration.sql

npx prisma migrate resolve --applied 0_init
```

The `--applied` flag marks the migration as already applied without running it. Prisma's migration history starts from here.

## Squashing migrations

Over time, the migration directory grows. For a fresh database setup, Prisma replays every migration from the beginning — slow for many migrations.

Squashing combines all migrations into one. It's safe to do periodically, but requires that all environments have the latest migration applied first.

```bash
# After ensuring all environments are up to date:
npx prisma migrate squash
```

## Shadow database in CI

For CI environments, Prisma needs a shadow database to validate migrations. Configure it in `.env`:

```env
DATABASE_URL="postgresql://user:pass@db:5432/myapp"
SHADOW_DATABASE_URL="postgresql://user:pass@db:5432/myapp_shadow"
```

Or use a separate CI database. Without a shadow database, `migrate dev` fails.

## The discipline

Prisma Migrate is safe when you follow the constraints:
- One direction: never roll back migrations in production, fix forward
- Immutable history: never modify committed migration files
- Review the SQL: generated migrations are usually correct, but verify
- Deploy order: migrations before code
- Test migrations in CI against a real database, not a mock

Schema evolution is one of the highest-risk operations in web development. The tooling handles the mechanics; the discipline handles the risk.
