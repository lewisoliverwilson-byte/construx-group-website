Designing a messaging tool means deciding what to support. Slack supports threads, reactions, mentions, workflows, bots, DMs, group DMs, channels, channel sections, and integration apps. This flexibility comes at a cost: Slack is complicated.

The Hyve targets small, focused teams — 2-20 people who are building things together and want an AI agent that knows what they're building. For this use case, Slack's complexity is mostly overhead.

Here's what we built instead.

## The data model

The core entities are simple:

```sql
CREATE TABLE channels (
  id          TEXT PRIMARY KEY DEFAULT ('ch_' || generate_uid()),
  workspace_id TEXT NOT NULL REFERENCES workspaces(id),
  name        TEXT NOT NULL,
  description TEXT,
  archived    BOOLEAN NOT NULL DEFAULT false,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE messages (
  id          TEXT PRIMARY KEY DEFAULT ('msg_' || generate_uid()),
  channel_id  TEXT NOT NULL REFERENCES channels(id),
  user_id     TEXT NOT NULL REFERENCES users(id),
  content     TEXT NOT NULL,
  content_type TEXT NOT NULL DEFAULT 'text',  -- text | ai_response | file
  parent_id   TEXT REFERENCES messages(id),   -- for simple replies only
  reactions   JSONB NOT NULL DEFAULT '{}',    -- {emoji: [userId, ...]}
  edited_at   TIMESTAMPTZ,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

No nested threads. One level of replies via `parent_id`. Reactions stored as a JSONB map of emoji→userIds.

## The anti-thread decision

Threads — Slack's feature for keeping conversations organised — solve a real problem when a channel has high traffic. But they create a new problem: important conversations disappear into collapsed threads, and the context becomes fragmented across the main channel and many threads.

For small teams (The Hyve's target), threads are rarely the right tool. When 5 people work on the same project, a side conversation goes in a separate channel, not a thread. The thread pattern is a workaround for high-volume channels — if your channel is so busy that conversations get lost without threading, the solution is more channel organisation, not threading.

We support one level of reply (a simple in-line reply indicator, not a full thread) for cases where someone needs to directly respond to a specific message without creating ambient noise. This handles the use case without the full threading complexity.

## Reactions

Reactions (emoji responses to messages) serve a specific purpose: acknowledgement without creating a new message. "I saw this." "Approved." "Good idea." These reduce noise in channels where a text reply would just be "+1" or "thanks."

Implementation is simple: JSONB map per message, updated via a small API endpoint:

```ts
// PUT /api/messages/:id/react
async function toggleReaction(messageId: string, emoji: string, userId: string) {
  const message = await getMessage(messageId);
  const reactions = message.reactions as Record<string, string[]>;
  
  const current = reactions[emoji] ?? [];
  const hasReacted = current.includes(userId);
  
  const updated = hasReacted
    ? { ...reactions, [emoji]: current.filter((id) => id !== userId) }
    : { ...reactions, [emoji]: [...current, userId] };
  
  // Clean up empty emoji keys
  if (updated[emoji]?.length === 0) delete updated[emoji];
  
  await db.update(messages)
    .set({ reactions: updated })
    .where(eq(messages.id, messageId));
    
  // Broadcast to channel subscribers
  channelBus.emit(message.channelId, { type: 'reaction_updated', messageId, reactions: updated });
}
```

The broadcast ensures all connected clients update their reaction display without a page refresh.

## The @mention system

@mentions work in two modes:

**@user:** Notifies the mentioned user. They see an unread indicator for the channel and the message highlights in their view. No email notification (too noisy for real-time tools); push notification if the user has the web app open in another tab.

**@hyve:** Triggers the AI agent. The message gets passed to the AI pipeline with full channel context. The response appears as a message from the AI user in the channel.

Detection is client-side (the editor highlights mentions as you type) and stored as part of the message content as a markdown-style syntax: `@[Lewis Wilson](user_01...)`. The server parses mentions on message creation to trigger notifications.

## Kanban boards within channels

Each channel can have an associated kanban board — columns (To Do, In Progress, Done), cards with titles and descriptions, and assignments. Cards link back to messages when they're created from a message.

This serves The Hyve's core use case: a team building a product, managing tasks, and using the AI agent — all in the same context. The AI agent has read access to the board state, so it can answer questions like "what's still in progress?" with accurate answers.

```ts
const boardContext = await generateBoardContext(workspaceId, channelId);
// Returns:
// "Board state: In Progress: 3 items (Database migration, API rate limiting, Mobile design)
//  Done: 12 items. Blocked: 0 items."
```

This context is injected into the AI's system prompt for board-aware channels.

## What we deliberately left out

**File attachments.** Complex to implement well (storage, preview generation, access control). We reference files by URL and integrate with storage tools people already use (Notion, Google Docs, GitHub). The Hyve handles communication; file storage is someone else's problem.

**Video calls.** Out of scope. We integrate with the tools people use for calls (Google Meet, Zoom), not replace them.

**Workflows and automations.** Slack's workflow builder is powerful. It's also used primarily by power users and rarely by most team members. The Hyve has the AI agent as the automation layer — you ask it to do things, it does them.

**Permissions and roles beyond workspace admin.** Small teams don't need complex permission hierarchies. Every member of a workspace can read all channels and write to all non-archived channels. Simplicity beats flexibility at small team sizes.

## The feedback pattern

Three months in, the dominant feedback: the AI agent is more useful than we expected, and the simplicity of the messaging model is a feature, not a limitation. Teams that have used Slack describe The Hyve as "Slack without the noise." That's exactly the right comparison.
