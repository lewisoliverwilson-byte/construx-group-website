The Marqet launched with 63 listings. Each one was hand-written. That took longer than it should have, and the output varied in a way that bothered us — some listings were crisper than others, some categories were better represented, and the whole catalogue felt patchy in ways you'd only notice if you'd written all of it yourself.

We needed to get to 167. We weren't going to get there by writing each one by hand.

## The constraint

The Marqet sells professional Claude configurations — system prompts, prompt packs, workflow templates. Each listing is a real, deployable configuration for a specific job. A recruiting coordinator. A financial analyst. A real estate negotiator. The product's core promise is that each listing behaves like a trained specialist when pasted into a Claude Project.

That's a harder content brief than it sounds. You can't just generate generic configurations and call them professional. The failure mode is obvious: a user buys a "financial analyst" prompt pack, pastes it into Claude, asks it to model a discounted cash flow, and gets something a second-year intern would be embarrassed to send. That kills trust faster than no product at all.

So the constraint was: scale the catalogue, but don't lower the quality bar. Every listing that ships needs to actually do the job it claims to do.

## Stage one: category architecture

Before generating anything, we needed to be rigorous about what categories existed and which ones were worth filling. The marketplace was already organised into four verticals:

- **System prompts** — role-based personas, domain specialists
- **Prompt packs** — multi-step workflow templates
- **MCP servers** — Claude tool-use configurations
- **Workflow templates** — structured task sequences

Within each vertical, we had 15–20 role categories at launch. The first stage of the pipeline was mapping out the full space. We used Claude to enumerate every professional role that would plausibly benefit from a specialist Claude configuration, scored each one by market size and prompt complexity, and ended up with a structured taxonomy of ~120 viable target roles.

That taxonomy became the pipeline's input. Not a list of job titles — a structured brief for each role: what decisions they make daily, what information they need to make them, what outputs they produce, and what a general LLM fails at when asked to do their job.

## Stage two: automated generation

With a structured brief per role, generation became a templated process. The prompt for each listing was:

1. **Role brief** — generated in stage one
2. **Vertical specification** — what type of product this needs to be (system prompt, workflow template, etc.)
3. **Output schema** — structured format for the listing metadata plus the actual configuration
4. **Examples** — 3 high-quality listings from the existing catalogue as few-shot examples
5. **Quality rubric** — explicit instructions for what makes a good listing vs a generic one

Claude generated a first draft of each listing: configuration, title, description, category tags, use case examples, and a brief assessment of what the configuration does well and where it might fail.

The generation ran in parallel — we batched 20 roles at a time — and took around 4 hours for the full expansion.

## Stage three: automated validation

Generation at scale always produces some garbage. The validation stage was designed to catch it before it reached the catalogue.

We built a validation pipeline that checked each generated listing against three criteria:

**Specificity.** Does the configuration do something specific that a general Claude prompt wouldn't? We prompted Claude as a reviewer: "If a user asked Claude to do this job without any system prompt, what would be different about the output?" Listings where the answer was "nothing much" got flagged.

**Completeness.** Does the configuration handle the full scope of the role? A financial analyst configuration that works for DCF modelling but has nothing to say about risk assessment is incomplete. We checked for obvious gaps in the role's core workflow.

**Hallucination risk.** Some configurations encourage Claude to produce outputs that look authoritative but aren't grounded. A legal configuration that produces confident legal opinions without caveats is dangerous. The validator flagged any configuration that scored high on confidence without explicit grounding instructions.

About 20% of generated listings failed validation on first pass. Most of those were improved by regenerating with the specific validation failure as additional context. A small number — maybe 8% of total — required manual revision.

## Stage four: human review

The pipeline got us to near-final listings, but the final pass was human. Not line-by-line — we reviewed at the level of "would a professional in this role trust this configuration to handle their actual work?"

The reviews that led to the most rewrites were the highly specialised roles. Generalist configurations for "marketing manager" or "project manager" held up well. Specialist configurations for roles like "algorithmic trading desk analyst" or "pharmaceutical regulatory affairs specialist" often needed domain-specific adjustments that were hard to catch without domain knowledge.

We read a lot of industry forums in two weeks.

## The output

Starting from 63 listings, the pipeline produced 104 new listings that met the quality bar. That took the catalogue to 167 across 4 verticals, with 22 role categories represented at multiple product types.

The quality distribution is better than the hand-written catalogue. The pipeline's structured brief and explicit quality rubric produced more consistent listings than the hand-written originals, which varied based on how much we knew about the role going in.

## What this means for future catalogues

The pipeline is now The Marqet's content infrastructure. Adding a new vertical is a matter of:

1. Defining the role taxonomy for that vertical
2. Running generation with vertical-specific few-shot examples
3. Validation passes
4. Human review for specialist roles

We've already run it for a partial expansion into two new verticals. The constraint on catalogue size isn't generation speed or cost — it's the human review capacity for specialist domains.

The longer-term version of this pipeline has domain experts in the loop during generation, not just review. A configuration for a derivatives trader written with a derivatives trader reading over each draft is a different product than one written by a generalist pipeline. That's the direction we're building toward.
