Every database schema encodes assumptions about how the product will be used. Some assumptions hold; some don't. The ones that don't require migrations — and migrations on live data are one of the riskiest operations in production engineering.

Here's the schema decisions that defined our products, and what we'd do differently.

## Scoutr: the scan history model

Scoutr's initial scan table:

```sql
CREATE TABLE scans (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id     uuid NOT NULL,
  url         text NOT NULL,
  result      jsonb NOT NULL,
  created_at  timestamptz DEFAULT now()
);
```

The `result` column stores the full AI analysis as a JSON blob. This was pragmatic — we didn't know exactly what fields the analysis would have when we were building the schema. JSON gave us flexibility to evolve the analysis structure without schema migrations.

**What held up:** The JSON approach for the result is genuinely flexible. We've added, renamed, and restructured fields in the analysis output without touching the database schema.

**What cost us:** Querying scan history by specific result fields is slow and syntax-heavy with JSONB. "Find all scans where the confidence score was above 80" requires:

```sql
SELECT * FROM scans WHERE (result->>'confidenceScore')::int > 80;
```

Instead of the cleaner:

```sql
SELECT * FROM scans WHERE confidence_score > 80;
```

We added an index on the extracted field and a partial index on high-confidence scans, which improved query performance. But the underlying schema design made common queries more complex than they needed to be.

**The lesson:** Separate structured fields from flexible JSON. The core analysis fields (confidence score, estimated margin, category) belong as proper columns. Supplementary metadata that might change can stay in JSONB.

## The Marqet: the listing versioning problem

The Marqet's initial listing table had no versioning. When a seller edited a listing, we overwrote the existing record:

```sql
UPDATE listings SET 
  title = $1, 
  description = $2, 
  price_pence = $3 
WHERE id = $4;
```

This produced an immediate problem: when a buyer viewed a listing, purchased it, and then the seller edited the listing post-purchase, the order record referenced a listing that no longer matched what the buyer had agreed to buy.

**The migration:** We added a `listing_versions` table and moved to immutable versioning:

```sql
CREATE TABLE listing_versions (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  listing_id      uuid REFERENCES listings(id),
  version_number  int NOT NULL,
  title           text NOT NULL,
  description     text NOT NULL,
  price_pence     int NOT NULL,
  created_at      timestamptz DEFAULT now()
);

-- Orders reference the specific version, not the listing
ALTER TABLE orders ADD COLUMN listing_version_id uuid REFERENCES listing_versions(id);
```

The migration ran on a live database with active listings and orders. We:
1. Created the `listing_versions` table.
2. Populated it from the current `listings` data (each existing listing became version 1).
3. Deployed application code that wrote to both tables on edit.
4. Migrated existing orders to reference `listing_version_id`.
5. Removed the deprecated columns.

This migration took three weeks and required careful rollback planning at each step.

**The lesson:** If you're building a marketplace, assume at schema design time that listings will need versioning. "Immutable records with version chains" should be the default for content that can be referenced by transactions.

## The Hyve: the channel permission model

The Hyve launched with a simple permission model: every workspace member had access to every channel. Straightforward to build; straightforward to understand.

Three months in, workspace admins started asking for private channels — channels visible only to a subset of members. A reasonable request that our schema didn't support.

The initial channel model:

```sql
CREATE TABLE channels (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  workspace_id uuid NOT NULL REFERENCES workspaces(id),
  name         text NOT NULL,
  created_by   uuid NOT NULL REFERENCES users(id),
  created_at   timestamptz DEFAULT now()
);
```

No permission columns — because we assumed every member could access every channel.

**The migration:** We added a `channel_type` column and a `channel_members` junction table:

```sql
ALTER TABLE channels ADD COLUMN channel_type text NOT NULL DEFAULT 'public';

CREATE TABLE channel_members (
  channel_id  uuid REFERENCES channels(id) ON DELETE CASCADE,
  user_id     uuid REFERENCES users(id) ON DELETE CASCADE,
  role        text NOT NULL DEFAULT 'member', -- member | admin
  joined_at   timestamptz DEFAULT now(),
  PRIMARY KEY (channel_id, user_id)
);
```

For `public` channels, we don't populate `channel_members` — membership is implicit for all workspace members. For `private` channels, only users in `channel_members` have access.

The application layer checks:

```ts
async function canAccessChannel(userId: string, channelId: string): Promise<boolean> {
  const channel = await getChannel(channelId);
  if (channel.type === 'public') {
    return isWorkspaceMember(userId, channel.workspaceId);
  }
  return isChannelMember(userId, channelId);
}
```

**The lesson:** Permission models are significantly easier to build at schema design time than to retrofit. The question to ask: "will this content ever need access control?" For almost any collaborative product, the answer is yes. Design the permission model from the start, even if you launch without using it.

## Cross-product: the soft delete pattern

All three products use soft deletes for most entities:

```sql
ALTER TABLE listings ADD COLUMN deleted_at timestamptz;
ALTER TABLE scans ADD COLUMN deleted_at timestamptz;
ALTER TABLE channels ADD COLUMN deleted_at timestamptz;
```

A soft delete sets `deleted_at` to the current timestamp rather than removing the row. The application filters all queries by `WHERE deleted_at IS NULL`.

**Why:** Hard deletes lose data permanently. With soft deletes, deleted records are recoverable, and foreign key references remain valid. For a marketplace where a deleted listing might have open orders, soft deletion is critical.

**The cost:** Every query needs `AND deleted_at IS NULL`. We addressed this with a partial index:

```sql
CREATE INDEX idx_listings_active ON listings(workspace_id, created_at)
WHERE deleted_at IS NULL;
```

And by using a database view for the "active" filter:

```sql
CREATE VIEW active_listings AS
SELECT * FROM listings WHERE deleted_at IS NULL;
```

Application queries use the view rather than the base table, keeping the soft-delete filter in one place.

The pattern has paid for itself twice already — we've had to restore "accidentally deleted" listings and channels that users deleted and immediately regretted.
