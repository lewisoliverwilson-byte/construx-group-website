excerpt: "Strimzi is a Kubernetes operator for running Apache Kafka on Kubernetes. It manages the full Kafka lifecycle: broker deployment, ZooKeeper (or KRaft in modern deployments), topic creation, user authentication (mTLS, SCRAM-SHA-512, OAuth2), Kafka Connect, Kafka Mirror Maker 2 (cross-cluster replication), and Cruise Control (automated partition rebalancing). KRaft mode (Kafka's built-in metadata consensus, replacing ZooKeeper) eliminates the ZooKeeper dependency — in Strimzi, this means deploying only Kafka brokers without a separate ZooKeeper StatefulSet, reducing operational complexity. Strimzi's CRDs model every Kafka concept: Kafka (the cluster), KafkaTopic (topic configuration), KafkaUser (authentication principal with ACL policies), KafkaConnect (connector cluster), and KafkaMirrorMaker2 (cross-datacenter replication). mTLS is the recommended authentication mode: each producer and consumer has a certificate issued by the cluster CA, and Strimzi provisions the certificates automatically via cert-manager. Cruise Control integrates with Strimzi to provide automated partition rebalancing — when brokers have uneven load (new brokers added, partitions skewed), Cruise Control computes a rebalancing plan that minimises data movement and applies it without downtime. At Construx, Strimzi manages a 3-broker KRaft cluster handling 84k messages/second across 8 topics, with mTLS for all clients and Cruise Control for automated rebalancing after broker additions."

## Strimzi Kafka cluster and topic configuration

```yaml
# Kafka cluster: 3-broker KRaft (no ZooKeeper) with mTLS and Cruise Control

apiVersion: kafka.strimzi.io/v1beta2
kind: Kafka
metadata:
  name: construx-kafka
  namespace: kafka
spec:
  kafka:
    version: 3.8.0
    metadataVersion: 3.8-IV0

    replicas: 3
    listeners:
      - name: plain
        port: 9092
        type: internal
        tls: false   # within-cluster, plain (CNI encryption via Cilium)
      - name: tls
        port: 9093
        type: internal
        tls: true
        authentication:
          type: tls          # mTLS: client certificates required

    authorization:
      type: simple           # Kafka ACL-based authorization

    config:
      default.replication.factor: 3
      min.insync.replicas: 2
      num.partitions: 12
      log.message.format.version: "3.8"
      offsets.topic.replication.factor: 3
      transaction.state.log.replication.factor: 3
      transaction.state.log.min.isr: 2
      log.retention.hours: 168    # 7 days default retention
      log.segment.bytes: 134217728  # 128MB segment size
      compression.type: lz4

    storage:
      type: jbod
      volumes:
        - id: 0
          type: persistent-claim
          size: 500Gi
          class: gp3
          deleteClaim: false

    resources:
      requests:
        cpu: "2"
        memory: 8Gi
      limits:
        cpu: "4"
        memory: 16Gi

    # JVM tuning for Kafka brokers
    jvmOptions:
      -Xms: 4096m
      -Xmx: 4096m
      gcLoggingEnabled: false

  # ZooKeeper: omitted in KRaft mode (Strimzi >= 0.39 supports KRaft)
  # zookeeper: omitted

  entityOperator:
    topicOperator: {}   # manages KafkaTopic CRDs
    userOperator:  {}   # manages KafkaUser CRDs

  cruiseControl: {}     # enable Cruise Control for automated rebalancing

---
# KafkaTopic: declarative topic configuration
apiVersion: kafka.strimzi.io/v1beta2
kind: KafkaTopic
metadata:
  name: orders-created
  namespace: kafka
  labels:
    strimzi.io/cluster: construx-kafka
spec:
  partitions: 24
  replicas: 3
  config:
    retention.ms: 604800000       # 7 days
    cleanup.policy: delete
    min.insync.replicas: "2"
    compression.type: lz4
    max.message.bytes: "1048576"  # 1MB max message size

---
# KafkaUser: mTLS user with ACL policy
apiVersion: kafka.strimzi.io/v1beta2
kind: KafkaUser
metadata:
  name: orders-consumer
  namespace: kafka
  labels:
    strimzi.io/cluster: construx-kafka
spec:
  authentication:
    type: tls    # Strimzi provisions a TLS certificate for this user

  authorization:
    type: simple
    acls:
      # Consumer: read from topics, commit offsets to consumer group
      - resource:
          type: topic
          name: orders
          patternType: prefix
        operations: [Read, Describe]
        host: "*"
      - resource:
          type: group
          name: orders-consumer
        operations: [Read]
        host: "*"
```

```yaml
# Kafka Mirror Maker 2: cross-cluster replication (disaster recovery)
# Replicates orders.created from eu-west-2 to us-east-1

apiVersion: kafka.strimzi.io/v1beta2
kind: KafkaMirrorMaker2
metadata:
  name: construx-mirror
  namespace: kafka
spec:
  version: 3.8.0
  replicas: 3
  connectCluster: target

  clusters:
    - alias: source
      bootstrapServers: construx-kafka-kafka-bootstrap.kafka.svc.cluster.local:9093
      tls:
        trustedCertificates:
          - secretName: construx-kafka-cluster-ca-cert
            certificate: ca.crt
      authentication:
        type: tls
        certificateAndKey:
          secretName: mirror-maker-source-user
          certificate: user.crt
          key: user.key

    - alias: target
      bootstrapServers: construx-kafka-us.kafka-us.svc.cluster.local:9093
      tls:
        trustedCertificates:
          - secretName: construx-kafka-us-cluster-ca-cert
            certificate: ca.crt
      authentication:
        type: tls
        certificateAndKey:
          secretName: mirror-maker-target-user
          certificate: user.crt
          key: user.key

  mirrors:
    - sourceCluster: source
      targetCluster: target
      sourceConnector:
        config:
          replication.factor: 3
          offset-syncs.topic.replication.factor: 3
          sync.topic.acls.enabled: "false"
      topicsPattern: "orders.*|payments.*"   # only replicate critical topics
      groupsPattern: ".*"
```

Strimzi vs MSK (AWS) vs Confluent Cloud vs Redpanda vs self-managed Kafka: AWS MSK is the managed Kafka option on AWS — no operational overhead for broker management, automatic patching, storage scaling, and multi-AZ replication. The trade-off is cost (MSK is more expensive per GB of storage than self-managed) and less control over broker configuration. Confluent Cloud is the fully managed Kafka SaaS with the richest feature set (Schema Registry, ksqlDB, Flink SQL, Tableau connectors), but the highest cost. Redpanda (dispatch-1026) is a Kafka-compatible broker implemented in C++ — dramatically simpler to operate (single binary, no JVM, no ZooKeeper even before KRaft) and with lower latency at the tail. Self-managed Kafka on VMs is what teams run before discovering operators — difficult to scale, upgrade, and manage certificates. Strimzi's value is the operator model: it makes Kubernetes-native Kafka operations (topic creation, user cert issuance, broker upgrade, partition rebalancing via Cruise Control) declarative and GitOps-compatible. For teams that prefer self-hosted Kafka for control and cost, Strimzi is the production-grade solution; for teams that want Kafka semantics with simpler operations, Redpanda is compelling; for teams that want zero operational overhead, MSK or Confluent Cloud are the right choices.
