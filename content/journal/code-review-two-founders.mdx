Most code review advice is written for teams. Review culture, async vs synchronous review, review metrics, LGTM culture — all of this assumes multiple reviewers, defined roles, and enough pull requests to create a system around.

Two founders running three products have one reviewer: each other. The dynamic is different and requires a different approach.

## What code review is actually for

Before describing how we do it, it's worth being clear about what we're trying to catch.

Code review at a two-person team is not about style consistency (that's what linters and formatters are for), not about catching obvious bugs (that's what TypeScript and tests are for), and not about teaching each other the codebase (we both live in the codebase).

What we're trying to catch:
- **Logic errors** that TypeScript and tests don't cover — wrong assumptions about how data is structured, incorrect business logic, edge cases in the user journey
- **Security issues** — unvalidated inputs, exposed secrets, missing auth checks
- **Regressions** — a change that fixes one thing by breaking another
- **Design decisions made in isolation** — where a second set of eyes would have produced a better design

This narrows the scope significantly. The review doesn't need to be comprehensive — it needs to be targeted at the things the author is likely to have missed.

## Our process

**We don't review everything.** Low-risk changes — adding content to a static page, updating a comment, changing a CSS value — don't get formal review. We use judgment about what needs eyes.

**We do review anything that touches business logic.** Fee calculations, API integrations, auth flows, data mutations, payment handling. Anything where a bug has a user-visible consequence gets reviewed.

**Review happens asynchronously via GitHub pull requests.** The author opens a PR, writes a description of what the change does and why, and tags the other person. The description includes the main decisions made, any alternatives considered, and anything the reviewer should pay specific attention to.

**The reviewer looks at the diff, not the whole codebase.** The PR description provides context. The diff shows the change. If the reviewer needs more context, they look at surrounding code.

**We use comments for questions, approval for confidence.** "Why did you handle this case this way?" is a comment. "This looks correct to me" is an approval. We don't use review as a forum for design discussions — those happen in the decision log or a quick call.

**TypeScript does the first pass.** We run `npx tsc --noEmit` before opening a PR. If there are TypeScript errors, they get fixed first. A TypeScript-clean PR means the reviewer doesn't have to think about type errors.

## What Claude Code's role is

Claude Code writes a significant proportion of the code we ship. Does that change how we review?

Somewhat. Claude Code is very good at implementing well-specified requirements but sometimes misses:
- **Context that wasn't in the prompt** — behaviour that's implied by the surrounding codebase but wasn't explicitly specified
- **Edge cases in the specified behavior** — the spec said "X" but there's a case where X produces Y, which wasn't intended
- **Over-engineering** — solving the stated problem correctly but adding more abstraction than the problem requires

We review Claude Code output with the same process but with slightly more attention to the above. The reviewer asks: does this do what we needed, does it handle edge cases, and is it as simple as it could be?

The most common catch in Claude Code output: code that's more complex than necessary. Claude tends toward complete implementations; we sometimes need simpler ones.

## The constraint: velocity

Two founders, three live products, and no dedicated engineering team means velocity has to be high enough to actually ship improvements. Code review can't be a bottleneck.

Our constraint: if a reviewer hasn't reviewed a PR within 24 hours, the author can merge it. This is a forcing function on the reviewer and a safety valve for the author. It means low-velocity review doesn't block shipping.

In practice, most PRs are reviewed within a few hours. We're both active in the codebase. When something is urgent, we say so and the review happens faster.

The 24-hour rule has only been triggered a handful of times. When it has, it's been for low-risk changes where the reviewer's absence wouldn't have caught anything anyway.

## What we don't do

**We don't do pair programming.** We tried it. The synchronous overhead was too high for the benefit at our scale. For complex features, we might talk through the design before implementation, but the implementation itself is done by one person.

**We don't block on review for hotfixes.** If something is broken in production, it gets fixed and deployed. The PR gets reviewed after the fact. Speed matters more than process in production incidents.

**We don't track review metrics.** Review time, comment volume, review coverage — none of these are tracked. The goal is shipping good code, not optimising review statistics.

## The honest take

Code review with two people works less well than code review with a team. The reviewer is also the author on half the PRs. Blind spots are shared blind spots. An architectural mistake both of us made won't be caught by review.

What makes it work despite this:
- TypeScript catches a class of errors that would otherwise require human review
- Claude Code assists with implementation, which means fewer bugs from typos and off-by-one errors
- We're both senior enough to recognise common failure modes
- The products are not safety-critical — a bug that reaches production will be caught and fixed quickly

Two-person code review isn't the ideal process. It's an adequate process for a two-person team that needs to move fast. We'll iterate on it as we grow.
