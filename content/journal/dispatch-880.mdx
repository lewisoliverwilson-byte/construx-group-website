excerpt: "etcd is the distributed key-value store at the heart of every Kubernetes cluster. It stores all cluster state: pod definitions, service endpoints, secrets, config maps, RBAC rules. etcd achieves consistency through Raft — a consensus algorithm where a cluster of N nodes tolerates (N-1)/2 failures. Writes go through a leader; the leader replicates to a quorum before acknowledging. Reads can be linearizable (go through the leader) or serializable (from any follower, possibly stale). etcd's watch API enables Kubernetes controllers to react to state changes in microseconds."

One leader. Quorum writes. Every Kubernetes watch event starts here.

## Raft consensus — the algorithm in etcd

```
Cluster of 5 etcd nodes. Tolerates 2 failures (quorum = 3).

Leader election:
  1. All nodes start as Followers with a random election timeout (150-300ms)
  2. First node to time out → becomes Candidate, increments term, requests votes
  3. Candidate wins if it gets votes from a quorum (3/5)
  4. Winner becomes Leader, sends heartbeats to prevent new elections

Write path (linearizable):
  1. Client → Leader: PUT /k8s/pods/prod/api-7b9f4
  2. Leader appends to its own log
  3. Leader sends AppendEntries RPC to all 4 followers simultaneously
  4. Leader waits for 2 followers to ACK (quorum = 3 including leader)
  5. Leader commits the entry, applies to state machine
  6. Leader sends "committed" to followers in next heartbeat
  7. Leader responds OK to client

Failure scenarios:
  - Leader crashes mid-write: uncommitted entry is rolled back by new leader
  - Follower crashes: rejoins, leader sends missing log entries (catchup)
  - Network partition: minority partition (< quorum) stops accepting writes
    → prevents split-brain: only the majority partition can commit
```

## etcdctl — the etcd CLI

```bash
# Set up environment
export ETCDCTL_API=3
export ETCDCTL_ENDPOINTS=https://etcd-0:2379,https://etcd-1:2379,https://etcd-2:2379
export ETCDCTL_CACERT=/etc/etcd/ca.crt
export ETCDCTL_CERT=/etc/etcd/client.crt
export ETCDCTL_KEY=/etc/etcd/client.key

# Cluster health
etcdctl endpoint health
# https://etcd-0:2379 is healthy: successfully committed proposal
# https://etcd-1:2379 is healthy: successfully committed proposal
# https://etcd-2:2379 is healthy: successfully committed proposal

# Cluster status — who's the leader?
etcdctl endpoint status --write-out=table
# ENDPOINT            ID              STATUS   VERSION  DB SIZE  LEADER
# https://etcd-0:2379  8e9e05c52164694d  leader  3.5.17  42 MB    8e9e05c52164694d
# https://etcd-1:2379  91bc3c398fb3eb0  follower 3.5.17  42 MB    8e9e05c52164694d
# https://etcd-2:2379  fd422379fda50e48  follower 3.5.17  42 MB    8e9e05c52164694d

# CRUD operations
etcdctl put /construx/config/feature-flags '{"dark_mode": true, "beta": false}'
etcdctl get /construx/config/feature-flags
etcdctl del /construx/config/feature-flags

# Prefix scan — get all keys under a path
etcdctl get /construx/config/ --prefix --keys-only
# /construx/config/feature-flags
# /construx/config/rate-limits
# /construx/config/version
```

## etcd watch — real-time event streaming

```bash
# Watch a single key for changes
etcdctl watch /construx/config/feature-flags

# Watch a prefix — all keys under /k8s/pods/production/
etcdctl watch /k8s/pods/production/ --prefix

# Kubernetes controllers use this: kube-apiserver watches etcd for pod changes
# The controller manager's pod controller reacts in microseconds to pod events

# Watch from a specific revision (replay missed events)
etcdctl watch /construx/config/ --prefix --rev=1024

# Example: watch Kubernetes deployments for rolling update progress
kubectl proxy &  # Forward the Kubernetes API
# Then watch the etcd key for a specific deployment
etcdctl watch /registry/deployments/production/construx-api

# Output when a deployment updates:
# PUT
# /registry/deployments/production/construx-api
# <protobuf-encoded Deployment object>
```

## etcd backup and disaster recovery

```bash
# Snapshot: consistent point-in-time backup
etcdctl snapshot save /backup/etcd-$(date +%Y%m%d-%H%M%S).db

# Verify the snapshot
etcdctl snapshot status /backup/etcd-20320307-140000.db --write-out=table
# HASH        REVISION  TOTAL KEYS  TOTAL SIZE
# a3f9b2c1    18241     12,847      42 MB

# Restore from snapshot (all etcd members must be stopped first)
# Each member gets a different initial-cluster-token to prevent cross-cluster join
etcdctl snapshot restore /backup/etcd-20320307-140000.db \
  --name etcd-0 \
  --initial-cluster "etcd-0=https://etcd-0:2380,etcd-1=https://etcd-1:2380,etcd-2=https://etcd-2:2380" \
  --initial-cluster-token etcd-cluster-restored \
  --initial-advertise-peer-urls https://etcd-0:2380 \
  --data-dir /var/lib/etcd

# Defragmentation — reclaim disk space after many deletes
# Only run on one member at a time to avoid unavailability
etcdctl defrag --endpoint https://etcd-0:2379
etcdctl defrag --endpoint https://etcd-1:2379
etcdctl defrag --endpoint https://etcd-2:2379
```

## etcd in Kubernetes — what's actually stored

```bash
# Kubernetes uses etcd's /registry/ prefix for all cluster state
# You can read Kubernetes objects directly from etcd (protobuf-encoded)

# List all Kubernetes namespaces stored in etcd
etcdctl get /registry/namespaces/ --prefix --keys-only
# /registry/namespaces/default
# /registry/namespaces/kube-system
# /registry/namespaces/production

# Read a Kubernetes secret (stored encrypted in etcd if --encryption-provider-config is set)
etcdctl get /registry/secrets/production/construx-api-secret
# <encrypted or protobuf blob — not human-readable>

# Check etcd revision — monotonically increasing version counter
# Every write increments the revision; watches use it as a cursor
etcdctl get "" --prefix --keys-only --limit 1 -w json | jq '.header.revision'
# 18241

# etcd compaction — remove old revisions to reclaim space
# Kubernetes runs this automatically via kube-apiserver --etcd-compaction-interval
etcdctl compact 18000    # Remove all history before revision 18000
```

etcd sizing: etcd is not a general-purpose database. Its recommended maximum database size is 8GB (default quota: 2GB, warn at 8GB). Beyond that, writes start failing. The database grows with the number of objects stored and the watch history retained. For a 1,000-node Kubernetes cluster with thousands of pods, 2-4GB is typical. The key operational rule: run `etcdctl defrag` regularly and monitor `etcd_server_quota_backend_bytes` and `etcd_mvcc_db_total_size_in_bytes` in Prometheus.
