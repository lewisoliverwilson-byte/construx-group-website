title: "Velero: Kubernetes backup and restore — cluster snapshots, S3, disaster recovery"
date: "2033-10-19"
excerpt: "Velero is a backup and disaster recovery tool for Kubernetes. It backs up both the Kubernetes object state (all API resources — Deployments, ConfigMaps, Secrets, PVCs) and the persistent volume data (via CSI volume snapshots or file-level backup using Restic/Kopia). Backups are stored in an object storage bucket (S3, GCS, Azure Blob). Velero supports scheduled backups (via cron expressions), backup hooks (pre/post commands to quiesce a database before snapshotting), and selective backup (by namespace, label selector, or resource type). Restore is namespace-to-namespace (restore a production backup into a staging namespace for debugging) or cluster-to-cluster (migrate workloads from one cluster to another). Velero's disaster recovery story is: if the entire cluster is lost, you provision a new empty cluster, install Velero pointing at the same S3 bucket, and run velero restore — the cluster is rebuilt from the last backup including all Kubernetes objects and persistent volume data. Velero does not protect against etcd data corruption; for that, etcd snapshots are the correct tool."

## Velero installation and backup configuration

```bash
# Install Velero with AWS plugin (S3 backend + EBS CSI snapshots)
velero install \
  --provider           aws \
  --plugins            velero/velero-plugin-for-aws:v1.10.0 \
  --bucket             construx-velero-backups \
  --backup-location-config region=eu-west-2 \
  --snapshot-location-config region=eu-west-2 \
  --use-node-agent       # enables file-level backup (Kopia) for volumes without CSI snapshots

# Verify installation
kubectl get pods -n velero
# NAME                     READY   STATUS    RESTARTS  AGE
# velero-7d8c9b-4k2p9      1/1     Running   0         2m
# node-agent-zk8j9         1/1     Running   0         2m   (DaemonSet — one per node)
# node-agent-p2x4m         1/1     Running   0         2m
```

```yaml
# Schedule: daily backup of all namespaces, 30-day retention
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: daily-full-backup
  namespace: velero
spec:
  schedule: "0 2 * * *"   # 02:00 UTC daily
  template:
    includedNamespaces:
      - construx-prod
      - construx-staging
      - monitoring
    excludedResources:
      - events          # events are ephemeral — not worth backing up
      - events.events.k8s.io
    storageLocation: default   # points to S3 bucket
    volumeSnapshotLocations:
      - default
    ttl:  720h   # 30 days
    hooks:
      resources:
        - name: postgres-pre-backup
          includedNamespaces: [construx-prod]
          labelSelector:
            matchLabels:
              app: postgres
          pre:
            - exec:
                container: postgres
                command:   ["/bin/bash", "-c", "pg_dump -U construx_app construx > /tmp/backup.sql"]
                timeout:   120s
          post:
            - exec:
                container: postgres
                command:   ["/bin/bash", "-c", "rm /tmp/backup.sql"]
                timeout:   30s
---
# Schedule: hourly backup of just the Secrets and ConfigMaps (cheap, fast)
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: hourly-config-backup
  namespace: velero
spec:
  schedule: "0 * * * *"
  template:
    includedNamespaces: [construx-prod]
    includedResources:
      - secrets
      - configmaps
      - serviceaccounts
    labelSelector:
      matchLabels:
        backup.velero.io/include: "true"
    ttl: 168h   # 7 days
    snapshotVolumes: false   # no PV snapshot for config-only backup
```

Velero vs etcd snapshots vs cloud-native PV snapshots vs application-level backups: etcd snapshots capture the raw Kubernetes control plane state but not persistent volume data — after etcd restore, pods can be recreated but the data inside PVCs is gone unless you also restore PV snapshots. Cloud-native PV snapshots (EBS snapshot via CSI, GCP disk snapshot) protect the data in persistent volumes but not the Kubernetes API objects (Deployments, Services, ConfigMaps) — restoring a PV snapshot to a fresh cluster requires recreating all the API objects manually. Velero bridges both: it backs up API objects and takes PV snapshots in a single coordinated operation. Application-level backups (pg_dump for Postgres, mysqldump for MySQL) protect the data with known-good consistency but require custom tooling per application type and don't capture Kubernetes configuration. Velero's backup hooks integrate application-level quiescing (running pg_dump before snapshotting) with the Velero backup cycle. For teams operating Kubernetes in production, Velero + scheduled backups to S3 + regular restore drills is the standard disaster recovery practice. The restore drill is non-negotiable — a backup you've never restored is not a backup.
