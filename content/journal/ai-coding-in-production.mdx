AI coding tools are part of our standard development workflow across all three products. Not occasionally, as a supplement — continuously, as a primary tool.

This is an honest account of what that looks like in practice.

## What we actually use

The primary tool is Claude Code — the CLI interface to Claude that can read your codebase, edit files, run commands, and work through multi-step problems. We use it for:

- Initial feature implementation when the spec is clear
- Debugging when the error is in unfamiliar territory
- Writing boilerplate (form components, API route handlers, utility functions)
- Refactoring when the pattern is well-defined
- Writing journal posts
- Generating TypeScript types from schemas
- Reviewing code before committing

For the Construx Group website specifically — the one this journal runs on — almost every component was built with AI coding assistance. The Three.js solar system, the terminal log component, the activity histogram, the founders page ID panels. AI generated the initial implementation; we reviewed, adjusted, and iterated.

## Where it genuinely accelerates

**New ground in unfamiliar libraries.** When we integrated Three.js for the homepage solar system, we had minimal Three.js experience. AI provided working code that we could understand, modify, and extend rather than starting from the documentation and building up from primitives. Time to first working prototype: 90 minutes instead of a full day.

**Boilerplate that's correct but tedious.** TypeScript API route handlers, form validation logic, utility functions that transform data shapes — correct but uninteresting to write. AI writes these accurately without the cognitive overhead of building them manually. We review and merge.

**Debugging errors outside our immediate expertise.** A PostgreSQL query planner issue in The Marqet, a CSS animation timing problem on the website, a Next.js build error from a library version mismatch. AI narrows the search space significantly. We don't always accept the diagnosis — sometimes it's wrong — but having a well-informed first hypothesis is valuable.

**Scale of content.** 73 journal posts and counting. At that scale, the discipline of writing every dispatch manually would create pressure to write shorter or less frequently. AI assistance removes that pressure. The posts are still ours — we specify the topic, the stance, the examples — but the actual prose generation is collaborative.

## Where it adds friction

**AI is confident when it should be uncertain.** The biggest practical problem: AI coding tools generate code that looks correct and compiles, but has subtle bugs. TypeScript types that are technically correct but don't model the domain accurately. API calls that handle the success case but miss error states. Logic that works for the happy path and fails silently on edge cases.

This requires a review posture that's different from reviewing human-written code. Human developers signal uncertainty through comments, questions, or obviously incomplete implementations. AI generates complete-looking code regardless of confidence. You have to interrogate it.

**Context drift in long sessions.** Over a long session, the AI's understanding of the codebase can drift from the actual state. It may remember a function's type signature incorrectly, refer to a component that was refactored, or suggest an approach that contradicts a decision made 20 turns ago. We've learned to provide explicit context at the start of complex tasks rather than assuming the AI has retained earlier context.

**Abstraction creep.** Left unconstrained, AI tends toward abstractions and generalisations. It'll suggest a utility function, a config object, a helper that "might be useful later." We have a strong bias against this in our actual codebases — three similar lines is better than a premature abstraction. We've gotten better at specifying "don't abstract this, just do the specific thing" in prompts.

## The review discipline

AI-assisted development requires a specific review discipline. The review goal is not "does this code look reasonable" — it's "does this code do what I intended, handle all the cases I care about, and integrate correctly with the rest of the system."

Concrete things we check on every AI-generated piece:

- Do the TypeScript types actually model the data shape correctly (not just "does it compile")?
- Are error cases handled — what happens when this API call fails, when this array is empty, when this value is null?
- Is there anything in here that the AI invented rather than implementing what I asked for?
- Does this interact with other parts of the codebase in ways I haven't accounted for?

This review discipline adds time, but it's the right cost. AI-generated code that passes a thorough review is at least as good as code written manually — and frequently better, because AI has broader knowledge of library APIs and pattern libraries than any individual developer.

## The honest productivity verdict

Across three products, our best estimate is that AI coding tools have increased our effective development velocity by 40-60%. This is rough — it's impossible to run a controlled experiment on your own development process — but it feels directionally right.

The acceleration is unevenly distributed. Some tasks are 3-4x faster (boilerplate, documentation, content generation). Some are barely faster (complex domain logic that requires careful design, debugging state management issues where context is everything). A few are slightly slower (tasks where the AI's confident-but-wrong behavior sends us down wrong paths).

Net: substantial acceleration, with specific weaknesses that require active management. The correct posture is to trust it as a highly capable first-pass generator and apply rigorous review as the quality gate. Not to trust it blindly, and not to be so skeptical of it that you lose the acceleration.
