Error boundaries are one of those things you set up once and then barely think about — until you hit a production error and realise your boundary isn't where you thought it was.

Here's how the App Router error system actually works.

## What error.tsx is

`error.tsx` is a React Error Boundary implemented as a file convention. Place it inside a route segment and it catches unhandled errors from:

- The `page.tsx` in the same directory
- Any layouts or components the page renders
- Server Component errors (thrown during rendering)

```tsx
// app/journal/error.tsx
'use client'; // Error boundaries must be Client Components

interface Props {
  error: Error & { digest?: string };
  reset: () => void;
}

export default function JournalError({ error, reset }: Props) {
  return (
    <div>
      <h2>Something went wrong loading the journal.</h2>
      <p>{error.message}</p>
      <button onClick={reset}>Try again</button>
    </div>
  );
}
```

The `reset` function retries the render — useful for transient errors like a flaky API call.

The `digest` property is a unique identifier for server-side errors. It's logged to your server logs; you can show it to users ("Error ID: abc123") so they can report it and you can find the relevant log entry.

## What error.tsx doesn't catch

**Root layout errors.** `app/error.tsx` does not catch errors thrown in `app/layout.tsx`. The root layout wraps everything, so there's no boundary above it. For this you need `app/global-error.tsx`:

```tsx
// app/global-error.tsx
'use client';

export default function GlobalError({ error, reset }: Props) {
  return (
    <html>
      <body>
        <div>Critical error. We're looking into it.</div>
        <button onClick={reset}>Try again</button>
      </body>
    </html>
  );
}
```

`global-error.tsx` must include `<html>` and `<body>` tags because it replaces the root layout entirely.

**Event handler errors.** If an error is thrown inside a `onClick` handler or similar, error boundaries don't catch it. Those are not rendering errors. Use `try/catch` in your event handlers and manage error state manually.

**Async component errors without Suspense.** In React 19, async Server Components that throw are caught by the nearest error boundary. But if you're awaiting something inside a component that's not wrapped in Suspense, the error propagates as expected.

## Nested error boundaries

You can have multiple `error.tsx` files at different levels of the route hierarchy. The error is caught by the nearest boundary above the throwing component:

```
app/
  layout.tsx         ← global-error.tsx catches errors here
  error.tsx          ← catches errors in page.tsx at this level
  journal/
    layout.tsx
    error.tsx        ← catches errors in journal/**
    page.tsx
    [slug]/
      error.tsx      ← catches errors only in [slug]/**
      page.tsx
```

This lets you show a narrowly-scoped error state ("This post failed to load") instead of blowing up the whole page.

## The loading.tsx sibling

`error.tsx` and `loading.tsx` are siblings. Both are file conventions for handling the same route segment. `loading.tsx` wraps the segment in a `<Suspense>` boundary; `error.tsx` wraps it in an Error Boundary.

The pattern for a route with both:

```
app/journal/
  loading.tsx    ← Suspense: shows skeleton while page loads
  error.tsx      ← Error Boundary: shows error if page throws
  page.tsx       ← The actual page
```

This gives you three states: loading (skeleton), error (recovery UI), and success (the page).

## What we show on error

Our error pages follow a consistent pattern: explain what failed, give the user an action, and show the error ID if there is one.

```tsx
// app/journal/error.tsx
'use client';

import Link from 'next/link';
import { AlertTriangle, RefreshCw } from 'lucide-react';

export default function JournalError({
  error,
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  return (
    <div
      className="flex flex-col items-center justify-center min-h-96 gap-5 px-5 text-center"
    >
      <AlertTriangle size={28} className="text-orange-400 opacity-70" />
      <div>
        <h2 className="text-lg font-bold text-text-base mb-2">
          Failed to load
        </h2>
        <p className="text-sm text-text-muted">
          Something went wrong. This has been logged.
        </p>
        {error.digest && (
          <p className="font-mono text-[10px] text-text-dim mt-2">
            ID: {error.digest}
          </p>
        )}
      </div>
      <div className="flex gap-3">
        <button
          onClick={reset}
          className="flex items-center gap-2 font-mono text-xs text-construx hover:text-orange-400 transition-colors"
        >
          <RefreshCw size={12} /> Try again
        </button>
        <Link
          href="/journal"
          className="font-mono text-xs text-text-dim hover:text-text-muted transition-colors"
        >
          Back to journal
        </Link>
      </div>
    </div>
  );
}
```

The "Try again" button calls `reset` which retries the render. The back link gives users an escape hatch if the error is persistent.

## Server Component errors and logging

When a Server Component throws, Next.js logs the error server-side with a digest. In production, you want to capture this in your logging service (PostHog events, Sentry, or your own logger):

```ts
// lib/error.ts
export function logServerError(error: Error, context: Record<string, unknown> = {}) {
  if (process.env.NODE_ENV === 'production') {
    // PostHog server-side event
    posthog.capture({
      distinctId: 'server',
      event: 'server_error',
      properties: {
        message: error.message,
        stack: error.stack,
        ...context,
      },
    });
  } else {
    console.error('[server error]', error, context);
  }
}
```

Call this in `try/catch` blocks in your data-fetching Server Components. The digest in the error boundary matches the server log entry — when a user reports an error with their ID, you can find the full stack trace.

## The production difference

In development, Next.js shows you the full error overlay — stack trace, source location, everything. In production, that overlay is replaced by your `error.tsx`. This means you need to test your error states deliberately: throw an error in a page, build for production, check what users see.

We add a route like `/api/test-error` (behind admin auth) specifically for triggering errors in production-like conditions during staging review.
