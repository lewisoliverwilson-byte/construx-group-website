---
title: "Sealed Secrets: encrypted Kubernetes secrets safe to commit to git"
date: "2033-10-07"
excerpt: "Sealed Secrets (Bitnami/VMware) solves the problem of storing Kubernetes secrets in git. A plain Kubernetes Secret is just base64-encoded — committing it to git exposes credentials to anyone who can read the repository. Sealed Secrets introduces a SealedSecret CRD: you encrypt a Secret using the cluster's public key (via the kubeseal CLI), producing a SealedSecret YAML that is safe to commit. Only the Sealed Secrets controller running in the cluster can decrypt it, using the cluster-private key stored in a Kubernetes Secret in the kube-system namespace. When you apply a SealedSecret, the controller decrypts it and creates the corresponding plain Kubernetes Secret in the target namespace. The encryption is asymmetric and scoped: by default a SealedSecret is bound to a specific namespace and Secret name — the same encrypted blob cannot be used to create a Secret in a different namespace or with a different name, even with the correct private key. Sealed Secrets is the standard choice for teams using GitOps (Flux, ArgoCD) who want secrets to live in the same git repository as their application manifests without compromising credentials."
author: "Lewis Wilson"
tag: "Build Log"

SealedSecret CRD. kubeseal CLI. Namespace-scoped encryption. Key rotation. GitOps.

## Sealing and applying secrets

```bash
# Install Sealed Secrets controller
helm repo add sealed-secrets https://bitnami-labs.github.io/sealed-secrets
helm install sealed-secrets sealed-secrets/sealed-secrets \
  --namespace kube-system \
  --version 2.16.1

# Install kubeseal CLI (macOS/Linux)
brew install kubeseal   # or download binary from GitHub releases

# Fetch the cluster's public key (cached locally for offline sealing)
kubeseal --fetch-cert \
  --controller-name=sealed-secrets \
  --controller-namespace=kube-system \
  > /tmp/construx-sealed-secrets-cert.pem

# Seal a secret: create a Secret manifest and pipe it through kubeseal
kubectl create secret generic construx-db-credentials \
  --namespace construx-prod \
  --from-literal=DB_PASSWORD=s3cr3t-p4ssw0rd \
  --from-literal=DB_USERNAME=construx_app \
  --dry-run=client \
  -o yaml | \
  kubeseal \
    --cert /tmp/construx-sealed-secrets-cert.pem \
    --format yaml \
  > k8s/construx-prod/construx-db-credentials-sealed.yaml

# The resulting file is safe to commit to git:
cat k8s/construx-prod/construx-db-credentials-sealed.yaml
# apiVersion: bitnami.com/v1alpha1
# kind: SealedSecret
# metadata:
#   name:      construx-db-credentials
#   namespace: construx-prod
# spec:
#   encryptedData:
#     DB_PASSWORD: AgBy3i4OJSWK+PiTySYZZA9rO...   # RSA-OAEP encrypted
#     DB_USERNAME: AgCH3sFAaFJJEOS9P8k7YJIV...
#   template:
#     metadata:
#       name:      construx-db-credentials
#       namespace: construx-prod   # scoped: only decryptable in construx-prod

# Apply the SealedSecret (controller decrypts it and creates the plain Secret)
kubectl apply -f k8s/construx-prod/construx-db-credentials-sealed.yaml

# The plain Secret now exists (created by the controller, not by us)
kubectl get secret construx-db-credentials -n construx-prod
# NAME                      TYPE    DATA  AGE
# construx-db-credentials   Opaque  2     3s
```

## Scope modes and key rotation

```bash
# Scope options control who can decrypt a SealedSecret

# Default: namespace-scoped (bound to namespace + name)
kubeseal --scope namespace-wide --cert cert.pem -o yaml < secret.yaml

# Cluster-scoped: can be decrypted in any namespace with any name
# (useful for cluster-wide secrets like TLS certificates)
kubeseal --scope cluster-wide --cert cert.pem -o yaml < secret.yaml

# Strict (default): bound to exact namespace AND name
# Cannot be moved to another namespace or renamed
kubeseal --scope strict --cert cert.pem -o yaml < secret.yaml

# Key rotation: controller generates a new sealing key every 30 days by default
# Old keys are retained to decrypt existing SealedSecrets
kubectl get secret -n kube-system -l sealedsecrets.bitnami.com/sealed-secrets-key
# NAME                  TYPE                  DATA  AGE
# sealed-secrets-key    kubernetes.io/tls     2     280d   ← original key
# sealed-secrets-keyhv  kubernetes.io/tls     2     250d   ← new key (auto-generated)
# sealed-secrets-key82  kubernetes.io/tls     2     220d   ← newer key
# ...

# Re-seal with the latest key after rotation (old SealedSecrets still work with old keys)
# To force re-sealing: generate Secret, pipe through kubeseal again with fresh cert

# Controller logs: watch for decrypt failures
kubectl logs -n kube-system deploy/sealed-secrets -f | grep -E "Unsealed|error|failed"
# I1007 construx-prod/construx-db-credentials:Unsealed (via key sealed-secrets-key82)
```

```yaml
# GitOps workflow with ArgoCD: SealedSecrets live in git alongside manifests

# Repository structure:
# k8s/
#   construx-prod/
#     deployment.yaml
#     service.yaml
#     construx-db-credentials-sealed.yaml   ← committed to git
#     construx-api-secrets-sealed.yaml      ← committed to git
#   construx-staging/
#     ...

# ArgoCD Application: syncs the entire directory including SealedSecrets
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: construx-prod
  namespace: argocd
spec:
  project: default
  source:
    repoURL:        https://github.com/construx/k8s-manifests
    targetRevision: main
    path:           k8s/construx-prod
  destination:
    server:    https://kubernetes.default.svc
    namespace: construx-prod
  syncPolicy:
    automated:
      prune:    true
      selfHeal: true
```

Sealed Secrets vs External Secrets Operator vs SOPS vs Vault Agent Injector vs base64-in-git: Base64 encoding is not encryption — anyone with repo access can decode it instantly. SOPS (covered briefly in dispatch-1069) encrypts the entire secret file using KMS keys — requires KMS access to decrypt during CI/CD pipelines. External Secrets Operator (dispatch-1069) is the strongest approach: secrets never enter the repo, they stay in the external store (AWS Secrets Manager, Vault) and are pulled into the cluster at runtime. Sealed Secrets sits between these extremes: the secret value (DB password, API key) is stored encrypted in git, but the encryption is asymmetric — the private key never leaves the cluster. The trade-off vs ESO: with Sealed Secrets you must re-seal secrets when they rotate (or when a dev manually updates a credential), whereas ESO picks up rotations automatically on the next refresh cycle. Sealed Secrets is easier to set up and requires no external secret management system — good for small teams or projects where AWS Secrets Manager or Vault is overkill. For teams already running Vault or AWS Secrets Manager, ESO is the better long-term answer.
