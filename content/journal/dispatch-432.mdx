WebAssembly (WASM) is a binary instruction format that runs in the browser and in server runtimes. It's compiled from languages like Rust, C, or Go. It runs at predictable speed without JIT warmup. It doesn't replace JavaScript — it extends it by handling the CPU-intensive parts.

## When WASM makes sense

**Good fit:**
- Image processing (resize, compress, convert formats)
- Cryptography (AES, RSA, SHA — beyond what Web Crypto covers)
- Video/audio processing
- Compression/decompression (Zstandard, Brotli)
- Complex parsers (Markdown, SQL, WASM itself)
- Scientific computing
- Porting existing native libraries

**Bad fit:**
- Network I/O (JavaScript is fine)
- DOM manipulation (JavaScript is fine)
- Simple data processing (JavaScript is fine)
- Anything not CPU-bound

## Consuming WASM from TypeScript

Most WASM libraries ship an npm package that handles the binary loading and bindings:

```bash
npm install @dqbd/tiktoken  # OpenAI's tokenizer as WASM
```

```ts
import { get_encoding } from '@dqbd/tiktoken';

const encoding = get_encoding('cl100k_base');  // GPT-4's tokenizer

function countTokens(text: string): number {
  const tokens = encoding.encode(text);
  return tokens.length;
}

// Works in Node.js and the browser
console.log(countTokens('Hello, world!'));  // 4
```

The npm package handles loading the WASM binary — you just call the TypeScript API.

## Sharp for image processing

Sharp is a Node.js image processing library backed by libvips (compiled to native, not WASM, but the concept is similar):

```ts
import sharp from 'sharp';

// Resize and convert to WebP
async function optimizeImage(inputBuffer: Buffer): Promise<Buffer> {
  return sharp(inputBuffer)
    .resize(800, 600, {
      fit: 'inside',       // maintain aspect ratio
      withoutEnlargement: true,
    })
    .webp({ quality: 80 })
    .toBuffer();
}

// In a Route Handler
export async function POST(req: Request) {
  const formData = await req.formData();
  const file = formData.get('image') as File;

  const buffer = Buffer.from(await file.arrayBuffer());
  const optimized = await optimizeImage(buffer);

  return new Response(optimized, {
    headers: { 'Content-Type': 'image/webp' },
  });
}
```

## Building your own WASM module (Rust)

For custom high-performance code, compile Rust to WASM with `wasm-pack`:

```toml
# Cargo.toml
[package]
name = "construx-wasm"
version = "0.1.0"
edition = "2021"

[lib]
crate-type = ["cdylib"]

[dependencies]
wasm-bindgen = "0.2"
```

```rust
// src/lib.rs
use wasm_bindgen::prelude::*;

#[wasm_bindgen]
pub fn levenshtein_distance(a: &str, b: &str) -> usize {
    let len_a = a.chars().count();
    let len_b = b.chars().count();

    if len_a == 0 { return len_b; }
    if len_b == 0 { return len_a; }

    let mut matrix = vec![vec![0usize; len_b + 1]; len_a + 1];

    for i in 0..=len_a { matrix[i][0] = i; }
    for j in 0..=len_b { matrix[0][j] = j; }

    let a_chars: Vec<char> = a.chars().collect();
    let b_chars: Vec<char> = b.chars().collect();

    for i in 1..=len_a {
        for j in 1..=len_b {
            let cost = if a_chars[i-1] == b_chars[j-1] { 0 } else { 1 };
            matrix[i][j] = *[
                matrix[i-1][j] + 1,
                matrix[i][j-1] + 1,
                matrix[i-1][j-1] + cost,
            ].iter().min().unwrap();
        }
    }

    matrix[len_a][len_b]
}
```

```bash
# Build and package
wasm-pack build --target bundler

# Output: pkg/ directory with .wasm file and TypeScript bindings
```

```ts
// Use in TypeScript
import init, { levenshtein_distance } from './pkg/construx_wasm';

await init();  // load the WASM binary

const distance = levenshtein_distance('kitten', 'sitting');  // 3
```

## Loading WASM in Next.js

Next.js supports WASM imports with a config option:

```ts
// next.config.ts
import type { NextConfig } from 'next';

const config: NextConfig = {
  experimental: {
    serverComponentsExternalPackages: ['sharp'],
  },
  webpack(config) {
    config.experiments = {
      ...config.experiments,
      asyncWebAssembly: true,  // enable async WASM imports
    };
    return config;
  },
};

export default config;
```

```ts
// Async WASM import (loads the binary lazily)
const { default: init, levenshtein_distance } = await import('./pkg/construx_wasm');
await init();
```

## Off-main-thread with Web Workers

Long-running WASM computations should not run on the main thread — they'll block UI interactions:

```ts
// worker.ts
import init, { process_image } from './image-processor.wasm';

self.onmessage = async (event: MessageEvent<ArrayBuffer>) => {
  await init();
  const result = process_image(new Uint8Array(event.data));
  self.postMessage(result.buffer, [result.buffer]);
};
```

```ts
// Main thread
const worker = new Worker(new URL('./worker.ts', import.meta.url));

worker.onmessage = (event) => {
  const processedImage = new Uint8Array(event.data);
  displayImage(processedImage);
};

worker.postMessage(imageBuffer, [imageBuffer]);  // transfer, don't copy
```

The pattern: reach for WASM when you have a specific CPU-intensive task that's slow in JavaScript, not as a general optimization. The right candidates are almost always: image/video processing, cryptographic operations, or porting an existing native library.
