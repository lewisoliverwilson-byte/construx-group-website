TypeScript's error handling has a gap: `try/catch` catches `unknown`, which means you have to cast or narrow before using the error value — and the type system can't tell you which functions can throw. A function that might throw looks identical to one that can't. The result is implicit error paths that break silently.

## The problem with throw

```ts
// This looks like it returns a User — it doesn't say it can throw
async function getUser(id: string): Promise<User> {
  return db.query.users.findFirst({ where: eq(users.id, id) });
  // Can throw: DB connection error, timeout, invalid query
}

// Caller has no type-level hint that this can fail
const user = await getUser(id);
// If getUser throws, this crashes and the error propagates up
```

## The Result type pattern

Encode success and failure in the return type:

```ts
// lib/result.ts
export type Result<T, E = Error> =
  | { ok: true; value: T }
  | { ok: false; error: E };

export function ok<T>(value: T): Result<T, never> {
  return { ok: true, value };
}

export function err<E>(error: E): Result<never, E> {
  return { ok: false, error };
}

export async function tryAsync<T>(fn: () => Promise<T>): Promise<Result<T>> {
  try {
    return ok(await fn());
  } catch (e) {
    return err(e instanceof Error ? e : new Error(String(e)));
  }
}
```

```ts
// Callers know they get a Result
async function getUser(id: string): Promise<Result<User, 'NOT_FOUND' | 'DB_ERROR'>> {
  const result = await tryAsync(() =>
    db.query.users.findFirst({ where: eq(users.id, id) })
  );

  if (!result.ok) return err('DB_ERROR');
  if (!result.value) return err('NOT_FOUND');
  return ok(result.value);
}

// Caller handles both cases explicitly
const result = await getUser(id);

if (!result.ok) {
  switch (result.error) {
    case 'NOT_FOUND': return Response.json({ error: 'User not found' }, { status: 404 });
    case 'DB_ERROR':  return Response.json({ error: 'Internal error' }, { status: 500 });
  }
}

// TypeScript now knows result.value is User
const user = result.value;
```

## Domain errors as types

For application logic errors (not infrastructure failures), use typed error classes:

```ts
// lib/errors.ts
export class AppError extends Error {
  constructor(
    message: string,
    public readonly code: string,
    public readonly status: number = 500,
  ) {
    super(message);
    this.name = 'AppError';
  }
}

export class NotFoundError extends AppError {
  constructor(resource: string) {
    super(`${resource} not found`, 'NOT_FOUND', 404);
  }
}

export class ValidationError extends AppError {
  constructor(
    message: string,
    public readonly fields: Record<string, string[]>,
  ) {
    super(message, 'VALIDATION_ERROR', 400);
  }
}

export class UnauthorizedError extends AppError {
  constructor() {
    super('Unauthorized', 'UNAUTHORIZED', 401);
  }
}

export class RateLimitError extends AppError {
  constructor(public readonly retryAfter: number) {
    super('Rate limit exceeded', 'RATE_LIMIT_EXCEEDED', 429);
  }
}
```

```ts
// Error handler middleware
export function handleError(error: unknown): Response {
  if (error instanceof ValidationError) {
    return Response.json({
      error: error.message,
      code: error.code,
      fields: error.fields,
    }, { status: error.status });
  }

  if (error instanceof AppError) {
    return Response.json({
      error: error.message,
      code: error.code,
    }, { status: error.status });
  }

  console.error('Unhandled error:', error);
  return Response.json({ error: 'Internal server error' }, { status: 500 });
}
```

## Exhaustive checking with never

```ts
type AlertLevel = 'high' | 'medium' | 'low';

function assertNever(value: never, message: string): never {
  throw new Error(`${message}: ${JSON.stringify(value)}`);
}

function getAlertColor(level: AlertLevel): string {
  switch (level) {
    case 'high':   return '#ef4444';
    case 'medium': return '#f59e0b';
    case 'low':    return '#22c55e';
    default:
      // TypeScript error if you add a new AlertLevel and forget to handle it here
      return assertNever(level, 'Unhandled alert level');
  }
}
```

`assertNever` takes a `never` — TypeScript's bottom type. If you add `'critical'` to `AlertLevel` and don't add a case for it, TypeScript errors at the `default` branch because `level` would be `'critical'`, not `never`.

## Zod for boundary validation

At external boundaries (API inputs, environment variables, external API responses), parse and validate before the value enters your type-safe core:

```ts
import { z } from 'zod';

const ScanRequestSchema = z.object({
  url: z.string().url(),
  marketplace: z.enum(['UK', 'US', 'DE']).default('UK'),
  limit: z.number().int().min(1).max(100).default(20),
});

export async function POST(req: Request) {
  const body = await req.json().catch(() => null);

  const parsed = ScanRequestSchema.safeParse(body);

  if (!parsed.success) {
    const fields = parsed.error.flatten().fieldErrors;
    throw new ValidationError('Invalid request', fields);
  }

  const { url, marketplace, limit } = parsed.data;
  // url, marketplace, limit are all typed and validated
  return runScan(url, marketplace, limit);
}
```

## The boundary rule

The goal is explicit error handling at system boundaries, not everywhere. Trust internal code that can't fail. Validate at external boundaries and convert to typed errors. Handle errors at the layer that can meaningfully respond — not in the middle of a call stack where there's nothing useful to do with a failure.

The discipline: functions that can fail say so in their return type. Functions that can't fail return `T`, not `Result<T>`. The difference is visible without reading the implementation.
