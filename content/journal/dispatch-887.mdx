excerpt: "Go ships with built-in profiling via the `net/http/pprof` package — attach it to your HTTP server and you get live CPU, heap, goroutine, and block profiles accessible over HTTP. The `go tool pprof` command downloads and analyses these profiles interactively: `top` shows hotspot functions, `list` shows annotated source code, `web` renders a flame graph in the browser. Profiling in production with pprof is safe — the CPU profiler samples at 100Hz by default (1% overhead), and heap profiles are snapshots of the current allocation state."

## Enabling the pprof HTTP endpoint

```go
// cmd/api/main.go
package main

import (
    "net/http"
    _ "net/http/pprof"  // Side-effect import registers /debug/pprof handlers
    "log"
)

func main() {
    // Serve pprof on a separate port — never expose this publicly
    go func() {
        log.Println(http.ListenAndServe("localhost:6060", nil))
    }()

    // ... start your main server
}

// Registered endpoints (all at localhost:6060):
// /debug/pprof/                — index page
// /debug/pprof/profile?seconds=30  — 30s CPU profile
// /debug/pprof/heap            — heap snapshot
// /debug/pprof/goroutine       — all goroutine stacks
// /debug/pprof/block           — goroutine blocking events
// /debug/pprof/mutex           — mutex contention
// /debug/pprof/trace?seconds=5 — execution trace (different from pprof)
```

## CPU profiling — finding hot functions

```bash
# Download and analyse a 30-second CPU profile
go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30

# Interactive pprof shell starts after the profile is fetched
(pprof) top10
#       flat  flat%   sum%        cum   cum%
#     420ms  21.0%  21.0%     1980ms  99.0%  construx-api/internal/order.(*Server).CreateOrder
#     380ms  19.0%  40.0%      780ms  39.0%  github.com/jackc/pgx/v5.(*Conn).sendBatchExtendedMode
#     260ms  13.0%  53.0%      420ms  21.0%  encoding/json.Marshal

# flat = time spent in the function itself
# cum  = time spent in the function AND all functions it calls

# Zoom in on a specific function — see annotated source
(pprof) list construx-api/internal/order.CreateOrder
# Total: 2s
# ROUTINE ======================== construx-api/internal/order.(*Server).CreateOrder
#     420ms      1.98s (flat, cum) 99.0% of Total
#      .          .     48:func (s *Server) CreateOrder(ctx context.Context, req *pb.CreateOrderRequest) (*pb.Order, error) {
#   10ms         10ms   52:    if req.CustomerId == "" {
#   410ms        410ms  56:    payload, _ := json.Marshal(req)   ← hot: 20% of time in json.Marshal
#      .        1.57s   57:    order, err := s.db.Insert(ctx, req)  ← 79% in DB

# Render flame graph in browser (requires graphviz)
(pprof) web

# Save profile for later analysis
go tool pprof -pdf http://localhost:6060/debug/pprof/profile?seconds=30 > cpu.pdf
```

## Heap profiling — memory allocations

```bash
# Heap profile: snapshot of current live allocations
go tool pprof http://localhost:6060/debug/pprof/heap

(pprof) top10 -inuse_space    # Memory currently in use (live objects)
#       flat  flat%   sum%        cum   cum%
#    18.2MB  34.2%  34.2%     18.2MB  34.2%  construx-api/internal/cache.(*OrderCache).Set
#    12.4MB  23.3%  57.5%     12.4MB  23.3%  github.com/jackc/pgx/v5/pgproto3.(*Backend).Receive

(pprof) top10 -alloc_space    # Total memory allocated (includes GC'd objects)
# Much higher numbers — shows allocation rate, not just live memory

# Find allocation hotspots
(pprof) list cache.Set
# 18.2MB allocated in OrderCache.Set:
#    all from make([]byte, estimatedSize)  ← pre-allocating slices per request
# Fix: sync.Pool to reuse buffers

# Allocation profile over time (useful for finding leaks)
# Take two snapshots, diff them
go tool pprof -base heap1.pb.gz heap2.pb.gz
(pprof) top  # Shows net allocations between the two snapshots
```

## Goroutine profiling and execution traces

```bash
# Goroutine dump — stack traces for every goroutine
go tool pprof http://localhost:6060/debug/pprof/goroutine

(pprof) top5
#       946   goroutines total
#       384   net/http.(*connReader).readLoop     ← one per HTTP connection
#       128   grpc.(*Server).handleRawConn
#        48   construx-api/internal/order.consumeBillingEvents

# Execution trace — microsecond-resolution timeline of goroutine scheduling
# Much more detailed than pprof; used for latency investigations
go tool trace http://localhost:6060/debug/pprof/trace?seconds=5 -http=:8080
# Opens a web UI showing:
# - Goroutine scheduling timelines per CPU core
# - GC pause events
# - Network wait times
# - Heap growth over time

# Block profile — where goroutines block waiting
go tool pprof http://localhost:6060/debug/pprof/block
(pprof) top5
# Shows functions where goroutines spent time blocked on:
# - channel ops (chan send/recv)
# - sync.Mutex.Lock
# - time.Sleep / select
# - syscall (disk I/O, network)

# Enable block profiling (off by default, has overhead)
runtime.SetBlockProfileRate(1)  // Sample every block event (1ns resolution)
```

The most common pprof finding: JSON marshaling in hot paths. `encoding/json` uses reflection and allocates heavily — switch to `github.com/bytedance/sonic` (SIMD-accelerated) or generated code from `github.com/mailru/easyjson`. Second most common: per-request allocations that could be pooled via `sync.Pool`. Third: goroutine leaks — a goroutine profile that grows over time reveals goroutines that start but never exit, typically because a context cancellation wasn't propagated through a channel or select.
