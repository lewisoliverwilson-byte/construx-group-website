Technical debt is the accumulated cost of shortcuts: decisions made to ship faster that create ongoing maintenance burden. The framing as "debt" is useful — it has a principal (the shortcut taken) and interest (the ongoing maintenance cost).

Not all debt is bad. Some debt is the right choice. Here's how we think about it.

## The good debt / bad debt distinction

**Good technical debt** is debt you took on consciously, in exchange for a clear, time-bounded benefit. Shipping a scrappy authentication system to get to market faster, with a plan to replace it after validating the product — that's good debt. You know you have it, you know why you have it, and you have a plan to pay it.

**Bad technical debt** is debt you accumulated accidentally. Code that grew without a clear architecture, that nobody fully understands, that breaks in unexpected ways when touched. This debt has no upside — it just costs.

The goal isn't to eliminate all debt. It's to have only the good kind.

## Our current debt inventory

**Scoutr:** The category classification system is a hardcoded mapping file. When eBay adds new categories, we manually update it. This was fast to build and has worked without incident, but it's a manual maintenance cost that will grow as we expand the category coverage. Eventually this should be a database-driven configuration with an admin UI. We know this; we haven't built it because the manual maintenance cost is currently low.

**The Marqet:** The notification system was built as a quick implementation with no persistence — notifications are emitted to the client via server-sent events and lost if the client isn't connected. This works for most users but means users who check the app infrequently miss notifications. The correct solution is a persisted notification queue. This is legitimate debt — we know the failure mode, we have a plan to fix it, and we've accepted it temporarily while we prioritise other work.

**The Hyve:** The AI job processing is synchronous within the request lifecycle. A slow AI response (p99: 5.8s) blocks the request thread for the duration. This limits concurrency and will become a problem at higher request volumes. The fix — an async job queue — is documented and understood but not yet built. This is the most consequential debt item we have; it's not causing problems today, but it's a risk that grows with user count.

**The website (this site):** Minimal debt. Static site, simple architecture, content in MDX files. The most significant decision is future-dated content (posts dated in advance for consistency); this is intentional and documented.

## When to pay debt

**Pay debt when it's blocking new work.** If a debt item prevents you from building something you want to build, the debt cost has crossed the threshold where it's cheaper to fix than to live with.

**Pay debt when it's creating incidents.** Debt that's causing production problems is costing you more than the fix would. We paid the connection pool debt immediately after the October incident.

**Pay debt during slow periods.** When there's no pressing feature work, debt reduction is the right use of time. It's the moment when the opportunity cost of fixing vs. building is lowest.

**Don't pay debt preemptively.** Fixing debt before it's causing problems consumes time that could be used to build things users want. The Hyve's async job queue is the right fix, but the synchronous implementation hasn't caused a production problem yet. We'll build it before it does, but not today.

## The refactor anti-pattern

The most common mistake with technical debt: the refactor that doesn't ship anything. A team decides to "clean up the codebase" and spends three weeks refactoring without shipping features. Users see nothing; the team loses momentum.

Debt reduction should be incremental and continuous, not a batch operation. Fix the specific thing that's blocking you. Improve the system in the part you're already touching. Don't declare a refactor quarter.

## The documentation rule

Every debt item should be documented. Not in a debt backlog that nobody reads — in the code, in a comment that explains why the shortcut was taken and what the correct solution looks like.

```ts
// NOTE: Category classifications are hardcoded here. This was the fastest
// approach to ship. The correct solution is a database-driven config with
// an admin UI. Revisit when category count exceeds 200 or when manual
// updates become a meaningful maintenance burden.
const CATEGORY_MAP: Record<string, string> = {
  // ...
};
```

A future reader who touches this code immediately understands: this is known, this is intentional, and here's the plan. The comment prevents both "we should fix this someday" inaction and "I'll fix this right now" premature refactoring.

## The honest position

Technical debt is a management problem, not an engineering problem. Engineers make trade-offs; whether those trade-offs accumulate into debt that slows the team is a function of how well the trade-offs are tracked, communicated, and repaid.

The Hyve's synchronous job queue is the most significant debt we're carrying right now. We'll fix it when the evidence says we need to — either from user growth making it a performance issue, or from an incident that makes it a reliability issue. Until then, we know it's there, we know what the fix looks like, and we're not pretending it isn't a problem.

That's the right relationship with technical debt: honest, documented, and resolved when the cost of carrying it exceeds the cost of fixing it.
