CloudFormation is powerful but painful: hundreds of lines of YAML, no type checking, limited reuse, and verbose syntax for common patterns. CDK solves this by letting you write infrastructure in TypeScript and generating the CloudFormation for you.

## Setup

```bash
npm install -g aws-cdk
cdk init app --language=typescript
```

```ts
// bin/construx-infra.ts — entry point
import 'source-map-support/register';
import * as cdk from 'aws-cdk-lib';
import { ConstruxApiStack } from '../lib/api-stack';

const app = new cdk.App();

new ConstruxApiStack(app, 'ConstruxApi', {
  env: { account: process.env.CDK_DEFAULT_ACCOUNT, region: 'eu-west-1' },
});
```

## Stacks and constructs

CDK organises infrastructure into stacks (a CloudFormation stack) and constructs (reusable infrastructure units).

```ts
// lib/api-stack.ts
import * as cdk   from 'aws-cdk-lib';
import * as ec2   from 'aws-cdk-lib/aws-ec2';
import * as ecs   from 'aws-cdk-lib/aws-ecs';
import * as rds   from 'aws-cdk-lib/aws-rds';
import * as ecr   from 'aws-cdk-lib/aws-ecr';
import { Construct } from 'constructs';

export class ConstruxApiStack extends cdk.Stack {
  constructor(scope: Construct, id: string, props?: cdk.StackProps) {
    super(scope, id, props);

    // VPC with 2 AZs
    const vpc = new ec2.Vpc(this, 'Vpc', {
      maxAzs:      2,
      natGateways: 1,
    });

    // ECR repository for the API container
    const repo = new ecr.Repository(this, 'ApiRepo', {
      repositoryName: 'construx-api',
    });

    // ECS Fargate cluster
    const cluster = new ecs.Cluster(this, 'Cluster', { vpc });

    // RDS Postgres
    const db = new rds.DatabaseInstance(this, 'Db', {
      engine:              rds.DatabaseInstanceEngine.postgres({ version: rds.PostgresEngineVersion.VER_16 }),
      instanceType:        ec2.InstanceType.of(ec2.InstanceClass.T4G, ec2.InstanceSize.MICRO),
      vpc,
      vpcSubnets:          { subnetType: ec2.SubnetType.PRIVATE_WITH_EGRESS },
      multiAz:             false,
      allocatedStorage:    20,
      storageEncrypted:    true,
      deletionProtection:  true,
      databaseName:        'construx',
    });
  }
}
```

## Fargate service with load balancer

```ts
import * as ecs_patterns from 'aws-cdk-lib/aws-ecs-patterns';

// ApplicationLoadBalancedFargateService = ALB + ECS Fargate in one construct
const service = new ecs_patterns.ApplicationLoadBalancedFargateService(this, 'Api', {
  cluster,
  cpu:            512,
  memoryLimitMiB: 1024,
  desiredCount:   2,
  taskImageOptions: {
    image:           ecs.ContainerImage.fromEcrRepository(repo, 'latest'),
    containerPort:   3001,
    environment: {
      NODE_ENV:     'production',
      DATABASE_URL: db.instanceEndpoint.socketAddress,
    },
    secrets: {
      JWT_SECRET: ecs.Secret.fromSecretsManager(
        secretsmanager.Secret.fromSecretNameV2(this, 'JwtSecret', 'construx/jwt-secret')
      ),
    },
  },
  publicLoadBalancer: true,
});

// Allow ECS to connect to RDS
db.connections.allowFrom(service.service, ec2.Port.tcp(5432));

// Auto-scaling
const scaling = service.service.autoScaleTaskCount({ maxCapacity: 10 });
scaling.scaleOnCpuUtilization('CpuScaling', {
  targetUtilizationPercent: 70,
});
```

## CloudFront + S3 for static assets

```ts
import * as s3          from 'aws-cdk-lib/aws-s3';
import * as cloudfront  from 'aws-cdk-lib/aws-cloudfront';
import * as origins     from 'aws-cdk-lib/aws-cloudfront-origins';

const assetsBucket = new s3.Bucket(this, 'Assets', {
  blockPublicAccess: s3.BlockPublicAccess.BLOCK_ALL,
  encryption:        s3.BucketEncryption.S3_MANAGED,
});

const distribution = new cloudfront.Distribution(this, 'Cdn', {
  defaultBehavior: {
    origin: new origins.S3Origin(assetsBucket),
    viewerProtocolPolicy: cloudfront.ViewerProtocolPolicy.REDIRECT_TO_HTTPS,
    cachePolicy: cloudfront.CachePolicy.CACHING_OPTIMIZED,
  },
  additionalBehaviors: {
    '/api/*': {
      origin: new origins.HttpOrigin(service.loadBalancer.loadBalancerDnsName),
      cachePolicy: cloudfront.CachePolicy.CACHING_DISABLED,
      allowedMethods: cloudfront.AllowedMethods.ALLOW_ALL,
    },
  },
});

// Output the CloudFront URL
new cdk.CfnOutput(this, 'CdnUrl', {
  value: `https://${distribution.distributionDomainName}`,
});
```

## Deploying

```bash
cdk synth          # generate CloudFormation template (dry run)
cdk diff           # show what will change
cdk deploy         # deploy to AWS
cdk destroy        # tear down all resources
```

`cdk diff` shows a human-readable diff between your current code and deployed state — like `terraform plan` for CDK.

## L1, L2, L3 constructs

CDK has three abstraction levels:

- **L1** (`Cfn*` classes): 1:1 CloudFormation resources, fully explicit, verbose
- **L2** (`ec2.Vpc`, `ecs.Cluster`): opinionated wrappers with sane defaults
- **L3** (patterns like `ApplicationLoadBalancedFargateService`): high-level patterns that wire multiple resources together

Start with L2. Drop to L1 only when you need CloudFormation features not exposed by L2. Use L3 patterns for common architectures.

## Tradeoffs vs Terraform

**CDK wins**: TypeScript types catch errors at write time, code reuse is natural (just make a class), abstractions are easy, no HCL to learn.

**Terraform wins**: provider ecosystem is broader (GCP, Azure, not just AWS), state management is cleaner, the plan/apply cycle is more explicit, and Terraform state is portable across team members without needing AWS account access.

For AWS-only infrastructure on a TypeScript team: CDK. For multi-cloud or mixed teams: Terraform.
