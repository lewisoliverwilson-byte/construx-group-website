excerpt: "OpenFGA is Auth0/Okta's open-source implementation of Google Zanzibar — the global authorization system that powers Google Drive, Docs, and Calendar sharing. The model is relationship-based: you define types (user, document, folder, organization) and relationships between them (owner, editor, viewer, member), then ask authorization questions ('can user:alice view document:2025-q4-report?'). The FGA engine evaluates the question by traversing the relationship graph — if alice is editor of the folder that contains the document, and editors can view documents, she's authorized. OpenFGA separates authorization from your application code: the authorization model is a config file, not if-statements scattered through handlers."

Relationship graph. Zanzibar model. Tuple store. Check/expand/list operations. Authorization separated from code.

## Authorization model definition

```bash
# OpenFGA uses a DSL to define types and relations

cat > construx.fga <<'EOF'
model
  schema 1.1

# The workspace is the top-level container
type workspace
  relations
    define owner: [user]
    define admin: [user] or owner
    define member: [user] or admin

# A project belongs to a workspace
type project
  relations
    define workspace: [workspace]
    define owner: [user] or owner from workspace
    define editor: [user] or owner or admin from workspace
    define viewer: [user] or editor or member from workspace

    # Can create issues if you can edit the project
    define can_create_issue: editor

# An issue belongs to a project
type issue
  relations
    define project: [project]
    define owner: [user] or owner from project
    define editor: [user] or owner or editor from project
    define viewer: [user] or editor or viewer from project
    define assignee: [user]

    # Direct permission grants
    define can_view:   viewer
    define can_edit:   editor
    define can_delete: owner

# A user is just an identifier
type user

EOF

# Install and run OpenFGA
docker run -d \
  --name openfga \
  -p 8080:8080 \
  -p 8081:8081 \
  -p 3000:3000 \
  openfga/openfga run

# Create a store
curl -s -X POST http://localhost:8080/stores \
  -d '{"name":"construx"}' | jq .id
# "01HXYZ1234567890ABCDEF"
export STORE_ID="01HXYZ1234567890ABCDEF"

# Write the authorization model
fga model write \
  --store-id=$STORE_ID \
  --file=construx.fga
# Authorization model written: 01HXYZ...MODEL_ID
export MODEL_ID="01HXYZ...MODEL_ID"
```

## Writing relationship tuples

```bash
# Tuples are the data: (user, relation, object)
# "user:alice is owner of workspace:construx-prod"
# "user:bob is member of workspace:construx-prod"
# "project:api has workspace:construx-prod"

# Write tuples (batch operation)
curl -s -X POST http://localhost:8080/stores/$STORE_ID/write \
  -d '{
    "writes": {
      "tuple_keys": [
        {"user": "user:alice",          "relation": "owner",     "object": "workspace:construx-prod"},
        {"user": "user:bob",            "relation": "member",    "object": "workspace:construx-prod"},
        {"user": "user:carol",          "relation": "member",    "object": "workspace:construx-prod"},
        {"user": "workspace:construx-prod", "relation": "workspace", "object": "project:api"},
        {"user": "workspace:construx-prod", "relation": "workspace", "object": "project:infra"},
        {"user": "project:api",         "relation": "project",   "object": "issue:ISSUE-42"},
        {"user": "user:carol",          "relation": "editor",    "object": "project:api"}
      ]
    }
  }'

# Using the FGA CLI
fga tuple write \
  --store-id=$STORE_ID \
  user:alice owner workspace:construx-prod

fga tuple write \
  --store-id=$STORE_ID \
  user:bob member workspace:construx-prod

fga tuple write \
  --store-id=$STORE_ID \
  user:carol editor project:api

# Read tuples for an object
fga tuple read \
  --store-id=$STORE_ID \
  --object workspace:construx-prod
# user:alice owner  workspace:construx-prod
# user:bob   member workspace:construx-prod
# user:carol member workspace:construx-prod  ← inherited via member relation
```

## Authorization checks

```bash
# Check: can user:bob view issue:ISSUE-42?
# Evaluation path:
# bob is member of workspace:construx-prod
# construx-prod is workspace of project:api
# api is project of issue:ISSUE-42
# member → viewer via project → viewer of issue → can_view

curl -s -X POST http://localhost:8080/stores/$STORE_ID/check \
  -d '{
    "tuple_key": {
      "user":     "user:bob",
      "relation": "can_view",
      "object":   "issue:ISSUE-42"
    },
    "authorization_model_id": "'$MODEL_ID'"
  }' | jq .allowed
# true

# Can bob delete the issue? (only owners can delete)
fga query check \
  --store-id=$STORE_ID \
  user:bob can_delete issue:ISSUE-42
# false  (bob is only a member, not an editor or owner)

# Can carol edit the issue? (she has direct editor on project:api)
fga query check \
  --store-id=$STORE_ID \
  user:carol can_edit issue:ISSUE-42
# true

# Expand: explain WHY a check passes (debug the graph traversal)
fga query expand \
  --store-id=$STORE_ID \
  viewer issue:ISSUE-42
# {
#   "tree": {
#     "root": {
#       "union": {
#         "nodes": [
#           { "leaf": { "users": { "users": ["user:alice", "user:carol"] } } },
#           { "leaf": { "computed": {"userset": "editor"} } },
#           { "computed": {"userset": "viewer from project"} }
#         ]
#       }
#     }
#   }
# }

# List: what objects can user:bob view?
fga query list-objects \
  --store-id=$STORE_ID \
  --user=user:bob \
  --relation=can_view \
  --type=issue
# issue:ISSUE-42
# (would return all issues bob can view — paginated)
```

## SDK integration (Go)

```go
package auth

import (
  "context"
  openfga "github.com/openfga/go-sdk"
  "github.com/openfga/go-sdk/client"
)

type Authorizer struct {
  client  *client.OpenFgaClient
  storeID string
  modelID string
}

func NewAuthorizer(apiURL, storeID, modelID string) (*Authorizer, error) {
  fgaClient, err := client.NewSdkClient(&client.ClientConfiguration{
    ApiUrl:  apiURL,
    StoreId: storeID,
  })
  if err != nil {
    return nil, err
  }
  return &Authorizer{client: fgaClient, storeID: storeID, modelID: modelID}, nil
}

// CanDo checks if a user has a specific permission on an object
func (a *Authorizer) CanDo(ctx context.Context, user, relation, object string) (bool, error) {
  resp, err := a.client.Check(ctx).Body(client.ClientCheckRequest{
    User:     user,
    Relation: relation,
    Object:   object,
    AuthorizationModelId: &a.modelID,
  }).Execute()
  if err != nil {
    return false, err
  }
  return resp.GetAllowed(), nil
}

// HTTP middleware: enforce authorization on every request
func (a *Authorizer) RequirePermission(relation, objectFromRequest func(*http.Request) string) func(http.Handler) http.Handler {
  return func(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
      user := "user:" + UserFromContext(r.Context())
      object := objectFromRequest(r)

      allowed, err := a.CanDo(r.Context(), user, relation, object)
      if err != nil || !allowed {
        http.Error(w, "Forbidden", http.StatusForbidden)
        return
      }
      next.ServeHTTP(w, r)
    })
  }
}

```

OpenFGA vs Casbin vs OPA: Casbin is a general-purpose RBAC/ABAC library for embedding authorization logic directly in an application — it's fast and simple but stores policy in your app and doesn't scale to distributed authorization across multiple services. OPA (Open Policy Agent) is a general-purpose policy engine using Rego — it's excellent for infrastructure policy (Kubernetes admission, Terraform plan validation) but Rego is hard to read for relational authorization ("can alice share this document with bob?"). OpenFGA/Zanzibar is specifically designed for relational authorization at scale — the tuple store is the right data model for "sharing" semantics where users can delegate permissions to other users. For multi-tenant SaaS with resource sharing, OpenFGA is the right abstraction.
