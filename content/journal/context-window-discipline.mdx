Every AI-assisted workflow has an invisible constraint that shapes everything: the context window. How much of the relevant information fits into what the model can see at once determines the quality of what it produces.

Most teams don't think about context management explicitly. They paste code, paste error messages, paste documentation, and wonder why the output gets less useful as the conversation gets longer. The answer is usually that the signal-to-noise ratio in the context has degraded past the point where the model can produce good work.

Managing context well is a discipline. Here's how we think about it.

## What goes in the context and why it matters

The model works with what's in its context window. If the relevant code isn't there, it invents code that might not exist. If the error message isn't there, it guesses at the cause. If the spec isn't there, it interpolates from general knowledge.

The failure mode is subtle. The model will produce confident, syntactically correct output even when that output is based on incorrect assumptions about what the codebase actually looks like. The context window is the difference between the model reasoning about your system and the model reasoning about a plausible system that resembles yours.

The flip side is that stuffing everything into the context doesn't work either. Long contexts degrade attention. The model is less likely to correctly apply a constraint mentioned on page one of a 50-page document than one it encountered recently. Relevant information competes with irrelevant information for attention, and the competition is lossy.

## The files that should always be in context

For any non-trivial coding task, certain files should always be in context before the model does anything:

**The file being modified.** Not a snippet — the full file. Partial context leads to edits that are locally correct but break something three functions away.

**Directly imported modules.** If the file being edited imports a type, interface, or function from another file, the model needs to see the definition. The alternative is the model inventing an interface that matches what it expects rather than what actually exists.

**The test file, if one exists.** The tests are a spec. They tell the model what the correct behavior looks like, which is more useful than an English description of what you want.

**CLAUDE.md, if it exists.** Project-specific constraints don't get re-stated every time — they live in a file that goes into context automatically. Build constraints, naming conventions, deployment notes.

## What to keep out of context

Everything else. The instinct to provide more context is usually wrong. Context is not "more info the model might find useful." It's "the minimum information required to do this task correctly."

Long documents should be excerpted down to the relevant section. If you need the model to understand a 200-page API spec, give it the 10-page section about the specific endpoint you're working with. If it needs 20 pages, you're probably working on a task that should be broken into smaller tasks.

Old conversation turns should be periodically cleared. A conversation that started as "help me design the data model" and has evolved into "now fix this specific bug in the fee calculation" probably has several thousand tokens of data model discussion that's no longer relevant. Clearing the conversation and starting fresh with only the current context is almost always better than continuing in a degraded context.

## Fresh context for each task

We treat major context resets as a feature, not a failure. When a task shifts significantly — from architecture to implementation, from one module to another, from debugging to writing — we reset.

The cost of a reset is the time to re-establish context. The cost of not resetting is accumulated context noise that degrades output quality progressively. The cost calculation almost always favours the reset.

In practice: one conversation per coherent task. "Build the fee calculator" is one task, one conversation. "Fix the bug in the fee calculator where dimensions aren't parsed correctly" is a different task — new conversation, with just the fee calculator file, the test file, and the error output in context.

## Context contamination

One failure mode worth naming: context contamination from a previous, related task.

You build feature A. In that conversation, you explored several approaches before settling on one. The model understands that the first approach was rejected. You then start a new conversation about feature B, which is adjacent to feature A, and include the conversation history from feature A.

The history now contains a lot of reasoning about rejected approaches. The model will sometimes anchor to those rejected approaches when working on feature B, even though they were explicitly rejected for feature A. The information in context shapes the model's output in ways that are not always transparent.

The solution is the same: fresh context. Include the implemented feature A code (the settled approach), not the conversation about how you got there.

## System prompts as persistent context

Some information should always be in context — not because it's task-specific, but because it constrains all outputs regardless of task. This is what system prompts are for.

We maintain a system prompt for coding sessions that includes:
- Stack and version constraints (Next.js 15, React 19, Tailwind v3 — not v4)
- Naming conventions and file structure conventions
- Things the model should never do autonomously (push to main, modify CI config, delete files)
- Code style preferences (no comments unless WHY is non-obvious, no error handling for impossible cases)

This is a small, stable document. It doesn't grow — adding to it has diminishing returns as each new rule competes with existing rules for attention.

## Measuring context quality

The best proxy for context quality is how many follow-up corrections you need to make after an output. If you're frequently saying "that's not how X works in this codebase" or "that function doesn't exist", your context is missing something important. If you're frequently saying "yes, that's exactly right", your context is well-calibrated.

A high correction rate early in a task usually means the files aren't in context. A high correction rate late in a task usually means accumulated context noise is degrading attention. Both problems have the same solution: reset and reconstruct with the right information for the current step.

Context discipline is the work that makes the model useful. The output quality ceiling is set by how well you manage what goes into the window. Most teams leave significant capability on the table by not managing it deliberately.
