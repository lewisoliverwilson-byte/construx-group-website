Optimistic UI means immediately reflecting the user's action in the UI before the server responds. A like button that fills instantly, a list item that appears before the POST completes, a todo that's crossed out before the DELETE returns — these interactions feel snappy because there's no waiting.

The tradeoff: you're optimistic the server will agree. When it doesn't, you need to roll back.

## The basic pattern with `useOptimistic`

React 19 ships `useOptimistic` for this. It holds optimistic state that auto-reverts when the server response arrives:

```tsx
'use client';

import { useOptimistic, useTransition } from 'react';
import { toggleLike } from '@/lib/actions';

interface Props {
  postId: string;
  initialLiked: boolean;
  initialCount: number;
}

export function LikeButton({ postId, initialLiked, initialCount }: Props) {
  const [isPending, startTransition] = useTransition();
  const [optimistic, setOptimistic] = useOptimistic(
    { liked: initialLiked, count: initialCount },
    (current, newLiked: boolean) => ({
      liked: newLiked,
      count: newLiked ? current.count + 1 : current.count - 1,
    }),
  );

  const handleClick = () => {
    const newLiked = !optimistic.liked;
    startTransition(async () => {
      setOptimistic(newLiked); // immediate UI update
      await toggleLike(postId, newLiked); // actual server call
    });
  };

  return (
    <button
      onClick={handleClick}
      disabled={isPending}
      className={optimistic.liked ? 'liked' : ''}
    >
      ♥ {optimistic.count}
    </button>
  );
}
```

`useOptimistic` takes the real state and a reducer. While the server call is pending, it uses the optimistic value. When the call completes (or fails), it reverts to the real state. If the server agrees, the real state matches — so there's no visible change. If the server fails, the revert is the rollback.

## Manual optimistic updates with useState

For more control, manage the optimistic state manually:

```tsx
function TodoList({ initialItems }: { initialItems: Todo[] }) {
  const [items, setItems] = useState(initialItems);
  const [error, setError] = useState<string | null>(null);

  const addTodo = async (text: string) => {
    const tempId = `temp-${Date.now()}`;
    const optimisticItem: Todo = { id: tempId, text, done: false };

    // Optimistic add
    setItems((current) => [...current, optimisticItem]);
    setError(null);

    try {
      const saved = await createTodo(text);
      // Replace temp item with real item from server
      setItems((current) =>
        current.map((item) => (item.id === tempId ? saved : item)),
      );
    } catch {
      // Roll back
      setItems((current) => current.filter((item) => item.id !== tempId));
      setError('Failed to add todo. Try again.');
    }
  };

  const deleteTodo = async (id: string) => {
    const removed = items.find((item) => item.id === id)!;

    // Optimistic remove
    setItems((current) => current.filter((item) => item.id !== id));

    try {
      await deleteTodoById(id);
    } catch {
      // Roll back the removal
      setItems((current) =>
        [...current, removed].sort((a, b) => a.text.localeCompare(b.text)),
      );
      setError('Failed to delete. Try again.');
    }
  };

  return (
    <>
      {error && <p className="text-red-400">{error}</p>}
      {items.map((item) => (
        <TodoItem key={item.id} item={item} onDelete={deleteTodo} />
      ))}
    </>
  );
}
```

The temp ID approach is critical: you need something to identify the optimistic item before the server returns the real ID. The `temp-${Date.now()}` pattern works; UUID is cleaner.

## What makes a good rollback

A rollback that's visible is a broken promise. Users notice when something disappears or a count resets. Make rollbacks smooth:

```tsx
// Show a dismissible error instead of a jarring state change
setError('Couldn\'t save. Your change has been reversed.');
setTimeout(() => setError(null), 4000);
```

Or better, show a "retry" option alongside the rollback notification. The user's intent was clear — give them a path to retry without re-entering the data.

## When not to use optimistic UI

Optimistic updates are inappropriate when:

- **The outcome is uncertain**: payment processing, file uploads with validation, anything where server refusal is common. Don't optimistically confirm a payment.
- **The cost of rollback is high**: if the user sees a success state and acts on it (navigates away, sends a follow-up message), reversing it after the fact is confusing.
- **Ordering matters**: if two users are adding items to the same list simultaneously, optimistic updates can produce inconsistent state that's hard to reconcile.

For reads that are cheap to re-fetch — toggle states, counters, soft deletes — optimistic updates are the right default. For anything with real consequences, wait for server confirmation.
