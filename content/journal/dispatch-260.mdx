The Hyve has real-time channels where team members can send messages, mention the AI agent, and share files. It works like Slack, but runs on a single Next.js codebase deployed to AWS Amplify.

The architecture isn't obvious. Here's what we chose and why.

## WebSockets vs Server-Sent Events

The canonical choice for real-time messaging is WebSockets: persistent bidirectional connections that allow both client-to-server and server-to-client messages.

We chose Server-Sent Events (SSE) instead.

**Why SSE works for this use case:**

Message channels are fundamentally asymmetric. Clients send messages via HTTP POST. The server needs to push new messages to clients. SSE supports exactly this: unidirectional server-to-client streaming over a standard HTTP connection.

SSE advantages:
- Works over HTTP/1.1 (no protocol upgrade)
- Automatic reconnection built into the EventSource API
- No separate WebSocket server needed — just a streaming HTTP endpoint
- Works with Next.js API routes on AWS Amplify without a separate infrastructure layer

**The trade-off:**

SSE max concurrent connections per browser: 6 per domain (HTTP/1.1). With multiple open channels, this becomes an issue. We handle this by multiplexing — one SSE connection per workspace, with client-side routing of messages to the correct channel view.

WebSockets are the right choice if you need:
- Sub-50ms latency (SSE has slightly higher overhead)
- Bidirectional communication at scale
- Very high connection counts

For The Hyve's current scale and deployment model, SSE is sufficient.

## The message data model

```sql
CREATE TABLE messages (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  channel_id  UUID NOT NULL REFERENCES channels(id),
  sender_id   TEXT NOT NULL,           -- Clerk user ID
  content     TEXT NOT NULL,
  type        TEXT NOT NULL DEFAULT 'text', -- 'text' | 'file' | 'agent'
  metadata    JSONB DEFAULT '{}',
  -- e.g. { "attachments": [{ "url": "...", "name": "..." }] }
  edited_at   TIMESTAMPTZ,
  created_at  TIMESTAMPTZ DEFAULT now()
);

CREATE INDEX messages_channel_created_idx ON messages (channel_id, created_at DESC);
```

The composite index on `(channel_id, created_at DESC)` is the query pattern: "get the last N messages in this channel." The `DESC` ordering means Postgres can satisfy this without a sort.

## The SSE delivery path

When a message is sent:

1. `POST /api/channels/[channelId]/messages` — receives the message, validates, persists to Postgres
2. On success, the API route calls `broadcastToChannel(channelId, message)` — delivers to all active SSE connections for that channel
3. Clients receive the message via SSE and append it to the channel view

```ts
// lib/channel-broadcast.ts
const channelConnections = new Map<string, Set<WritableStreamDefaultWriter>>();

export function broadcastToChannel(channelId: string, message: Message) {
  const writers = channelConnections.get(channelId);
  if (!writers) return;

  const payload = `data: ${JSON.stringify({ type: 'message', message })}\n\n`;
  const encoded = new TextEncoder().encode(payload);

  for (const writer of writers) {
    writer.write(encoded).catch(() => {
      // Client disconnected — remove stale writer
      writers.delete(writer);
    });
  }
}

export function addConnection(channelId: string, writer: WritableStreamDefaultWriter) {
  if (!channelConnections.has(channelId)) {
    channelConnections.set(channelId, new Set());
  }
  channelConnections.get(channelId)!.add(writer);
}

export function removeConnection(channelId: string, writer: WritableStreamDefaultWriter) {
  channelConnections.get(channelId)?.delete(writer);
}
```

The `channelConnections` map is in-process memory. This is the critical architectural constraint: **broadcast only works within a single process.** If the app scales to multiple instances (multiple Amplify instances handling requests), a message sent to instance A won't be delivered to users connected to instance B.

This is acceptable at current scale — a single Amplify instance handles all traffic. At scale, the solution is a pub/sub layer (Redis Pub/Sub or a dedicated message broker) that bridges instances.

## The SSE endpoint

```ts
// app/api/channels/[channelId]/stream/route.ts
export async function GET(
  req: Request,
  { params }: { params: Promise<{ channelId: string }> }
) {
  const { userId } = await auth();
  if (!userId) return new Response('Unauthorized', { status: 401 });

  const { channelId } = await params;
  // Verify user is member of the channel's workspace
  const isMember = await verifyChannelAccess(userId, channelId);
  if (!isMember) return new Response('Forbidden', { status: 403 });

  // Send recent messages on connect (backfill)
  const recentMessages = await getRecentMessages(channelId, 50);

  const { readable, writable } = new TransformStream();
  const writer = writable.getWriter();
  const encoder = new TextEncoder();

  // Send backfill immediately
  const backfill = `data: ${JSON.stringify({ type: 'backfill', messages: recentMessages })}\n\n`;
  await writer.write(encoder.encode(backfill));

  // Register in active connections
  addConnection(channelId, writer);

  // Clean up on close
  req.signal.addEventListener('abort', () => {
    removeConnection(channelId, writer);
    writer.close().catch(() => {});
  });

  return new Response(readable, {
    headers: {
      'Content-Type': 'text/event-stream',
      'Cache-Control': 'no-cache',
      'Connection': 'keep-alive',
    },
  });
}
```

The backfill on connect is important for users who reconnect after a brief disconnect. Instead of missing messages, they get the last 50 messages on reconnection. The client deduplicates by message ID.

## Client-side deduplication

Messages can arrive via:
- The SSE stream (another user's message, or your own message if sent from another tab)
- The optimistic update (your own message, immediately on send)

Without deduplication, a user would see their own messages twice (optimistic + SSE delivery). The client deduplicates by message ID:

```tsx
const [messages, setMessages] = useState<Message[]>(initialMessages);

// When SSE delivers a message
const handleMessage = (incoming: Message) => {
  setMessages((prev) => {
    if (prev.some((m) => m.id === incoming.id)) {
      return prev; // Already present (from optimistic update)
    }
    return [...prev, incoming].sort((a, b) =>
      new Date(a.createdAt).getTime() - new Date(b.createdAt).getTime()
    );
  });
};
```

Optimistic messages use a temporary UUID that doesn't match the server-generated UUID. When the SSE delivers the server message, the client replaces the temporary message:

```tsx
const sendMessage = async (content: string) => {
  const tempId = `temp-${crypto.randomUUID()}`;

  // Optimistic: add with temp ID
  setMessages((prev) => [...prev, {
    id: tempId, content, senderId: userId, createdAt: new Date().toISOString(),
  }]);

  const response = await fetch(`/api/channels/${channelId}/messages`, {
    method: 'POST',
    body: JSON.stringify({ content }),
  });

  const { message } = await response.json();

  // Replace temp message with server message
  setMessages((prev) => prev.map((m) =>
    m.id === tempId ? message : m
  ));
};
```

## What's still missing

**Read receipts.** Channels don't show who's seen a message. This requires tracking per-user read position per channel — a join table and another SSE event type.

**Typing indicators.** No "Lewis is typing…" display. This requires a separate SSE event type and a debounced indicator that clears after N seconds of inactivity.

**Message threading.** All messages are flat. Threads would require parent message references and a different rendering model.

**Offline support.** When the SSE connection drops and reconnects, the backfill catches up missed messages. But if the device is offline for hours and then reconnects, the 50-message backfill may not cover all missed messages. The fix is sending a `lastSeenMessageId` on reconnect so the server can send exactly what was missed.

Each of these is a known gap, not an oversight. The channel system serves the current use case. We add features when teams using The Hyve ask for them.
