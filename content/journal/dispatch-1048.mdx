title: "Apache Flink: stateful stream processing — exactly-once, low latency, high throughput"
date: "2033-07-24"
excerpt: "Apache Flink is a distributed stream processing engine designed for stateful computations over unbounded data streams. The core abstraction is a DataStream — a potentially infinite sequence of records — that you transform with operators (map, filter, keyBy, window, join). State is first-class: operators can store arbitrary state (per-key counters, aggregations, session windows) that survives failures via checkpointing to object storage. Flink's exactly-once processing guarantee means every record affects the state and output exactly once, even when the job restarts after a failure — achieved through distributed snapshots (Chandy-Lamport algorithm) that checkpoint consistent state across all operators simultaneously. Flink is suitable for real-time fraud detection (stateful per-user aggregations over a sliding window), real-time analytics (aggregating events as they arrive, no batch delay), CDC processing (consume Debezium events and materialise views), and complex event processing (detect patterns across sequences of events)."

## DataStream API and stateful operators

```java
// Java: Flink DataStream API — real-time order fraud detection
// Detects: >5 orders from same tenant in 60-second tumbling window (rate spike)

import org.apache.flink.api.common.eventtime.*;
import org.apache.flink.api.common.functions.AggregateFunction;
import org.apache.flink.api.common.state.*;
import org.apache.flink.streaming.api.datastream.DataStream;
import org.apache.flink.streaming.api.environment.StreamExecutionEnvironment;
import org.apache.flink.streaming.api.windowing.assigners.TumblingEventTimeWindows;
import org.apache.flink.streaming.api.windowing.time.Time;
import org.apache.flink.streaming.connectors.kafka.*;

StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();
env.setParallelism(8);

// Checkpointing: snapshot state every 30 seconds, store on S3
env.enableCheckpointing(30_000);
env.getCheckpointConfig().setCheckpointStorage("s3://construx-flink/checkpoints/");
env.getCheckpointConfig().setCheckpointingMode(CheckpointingMode.EXACTLY_ONCE);
env.getCheckpointConfig().setMinPauseBetweenCheckpoints(10_000);
env.getCheckpointConfig().setTolerableCheckpointFailureNumber(3);

// Kafka source: consume orders from Debezium CDC topic
KafkaSource<OrderEvent> source = KafkaSource.<OrderEvent>builder()
    .setBootstrapServers("kafka.construx.internal:9092")
    .setTopics("construx.cdc.public.orders")
    .setGroupId("flink-fraud-detector")
    .setStartingOffsets(OffsetsInitializer.committedOffsets(OffsetResetStrategy.LATEST))
    .setValueOnlyDeserializer(new OrderEventDeserialiser())
    .build();

DataStream<OrderEvent> orders = env.fromSource(
    source,
    WatermarkStrategy
        .<OrderEvent>forBoundedOutOfOrderness(Duration.ofSeconds(5))
        .withTimestampAssigner((event, ts) -> event.createdAtMs()),
    "Kafka Orders Source"
);

// Fraud detection: tumbling 60s window, alert if count > 5
DataStream<FraudAlert> alerts = orders
    .filter(e -> e.op().equals("c"))                   // inserts only
    .keyBy(OrderEvent::tenantId)                       // partition by tenant
    .window(TumblingEventTimeWindows.of(Time.seconds(60)))
    .aggregate(new OrderCountAggregate(), new FraudDetector())
    .filter(alert -> alert != null);                   // only emit when fraud detected

// Kafka sink: publish alerts
KafkaSink<FraudAlert> sink = KafkaSink.<FraudAlert>builder()
    .setBootstrapServers("kafka.construx.internal:9092")
    .setRecordSerializer(KafkaRecordSerializationSchema.builder()
        .setTopic("construx.alerts.fraud")
        .setValueSerializationSchema(new FraudAlertSerializer())
        .build())
    .setDeliveryGuarantee(DeliveryGuarantee.EXACTLY_ONCE)
    .setTransactionalIdPrefix("flink-fraud-")
    .build();

alerts.sinkTo(sink);
env.execute("Construx Fraud Detector");
```

## Table API and Flink SQL

```sql
-- Flink SQL: declarative stream processing
-- Flink SQL compiles to the same DataStream runtime underneath

-- Create Kafka source table (dynamic table = unbounded stream)
CREATE TABLE orders (
    order_id     STRING,
    tenant_id    STRING,
    status       STRING,
    total_pence  BIGINT,
    created_at   TIMESTAMP(3),
    WATERMARK FOR created_at AS created_at - INTERVAL '5' SECOND
) WITH (
    'connector'                     = 'kafka',
    'topic'                         = 'construx.cdc.public.orders',
    'properties.bootstrap.servers'  = 'kafka.construx.internal:9092',
    'properties.group.id'           = 'flink-sql-analytics',
    'format'                        = 'avro-confluent',
    'avro-confluent.url'            = 'http://schema-registry.construx.internal:8081',
    'scan.startup.mode'             = 'latest-offset'
);

-- Create sink: write aggregated results to PostgreSQL
CREATE TABLE tenant_realtime_stats (
    tenant_id       STRING,
    window_start    TIMESTAMP(3),
    window_end      TIMESTAMP(3),
    order_count     BIGINT,
    revenue_gbp     DOUBLE,
    PRIMARY KEY (tenant_id, window_start) NOT ENFORCED
) WITH (
    'connector'  = 'jdbc',
    'url'        = 'jdbc:postgresql://postgres.construx.internal/construx_prod',
    'table-name' = 'tenant_realtime_stats',
    'username'   = 'flink',
    'password'   = '${FLINK_DB_PASSWORD}'
);

-- Tumbling window aggregation: revenue per tenant per 5 minutes (real-time)
INSERT INTO tenant_realtime_stats
SELECT
    tenant_id,
    TUMBLE_START(created_at, INTERVAL '5' MINUTE)  AS window_start,
    TUMBLE_END(created_at, INTERVAL '5' MINUTE)    AS window_end,
    COUNT(*)                                        AS order_count,
    SUM(total_pence) / 100.0                       AS revenue_gbp
FROM orders
WHERE status = 'completed'
GROUP BY
    tenant_id,
    TUMBLE(created_at, INTERVAL '5' MINUTE);

-- Session window: group events by user activity (session ends after 30-min inactivity)
SELECT
    tenant_id,
    SESSION_START(created_at, INTERVAL '30' MINUTE)  AS session_start,
    SESSION_END(created_at, INTERVAL '30' MINUTE)    AS session_end,
    COUNT(*)                                          AS orders_in_session,
    SUM(total_pence)                                  AS session_value_pence
FROM orders
GROUP BY
    tenant_id,
    SESSION(created_at, INTERVAL '30' MINUTE);
```

Apache Flink vs Kafka Streams vs Spark Streaming vs RisingWave vs Materialize: Kafka Streams runs inside your application process (no separate cluster) and is ideal for per-service stream processing at moderate scale — but has no SQL API, limited windowing, and no independent scaling of processing. Spark Structured Streaming has a micro-batch model (tunable from 100ms to minutes) — simpler than Flink, good for teams already on Spark, but higher latency than Flink's true streaming. RisingWave and Materialize are SQL-first streaming databases — easier to use than Flink for analytics queries but less flexible for custom stateful logic. Flink's advantages are exactly-once semantics with a proven track record at billions of events per day, the richest windowing model (tumbling, sliding, session, custom), support for both Java/Scala DataStream API and SQL, and independent operator scaling. The cost: Flink has significant operational complexity — JobManager, TaskManagers, checkpointing configuration, state backend tuning, and watermark strategy selection all require expertise. For teams needing production-grade stateful stream processing at scale, Flink is the battle-tested choice.
