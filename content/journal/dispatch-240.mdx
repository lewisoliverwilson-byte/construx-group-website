Clerk manages authentication for both The Marqet and The Hyve. When a user creates an account, resets their password, or updates their profile, Clerk has the authoritative record. But both products also maintain their own user records in Postgres — for workspace memberships, seller profiles, transaction history, and preference data.

These need to stay in sync. The mechanism is Clerk webhooks.

## What Clerk webhooks send

Clerk fires webhook events for lifecycle events in the auth system:

- `user.created` — a new user signed up
- `user.updated` — a user changed their profile (name, email, avatar)
- `user.deleted` — a user deleted their account
- `session.created` — a user signed in (less commonly used for database sync)

For our use case, `user.created` and `user.updated` are the critical events. When a new user signs up on The Hyve, we need to:
1. Create a record in our `users` table
2. Create a personal workspace for them
3. Seed that workspace with an onboarding channel

All of this happens in the webhook handler for `user.created`.

## The webhook endpoint

```ts
// app/api/webhooks/clerk/route.ts
import { Webhook } from 'svix';
import { headers } from 'next/headers';
import { WebhookEvent } from '@clerk/nextjs/server';
import { db } from '@/lib/db';
import { users, workspaces, channels } from '@/schema';

export async function POST(req: Request) {
  const headersList = await headers();
  const svixId = headersList.get('svix-id');
  const svixTimestamp = headersList.get('svix-timestamp');
  const svixSignature = headersList.get('svix-signature');

  if (!svixId || !svixTimestamp || !svixSignature) {
    return new Response('Missing svix headers', { status: 400 });
  }

  const body = await req.text();
  const wh = new Webhook(process.env.CLERK_WEBHOOK_SECRET!);
  
  let event: WebhookEvent;
  try {
    event = wh.verify(body, {
      'svix-id': svixId,
      'svix-timestamp': svixTimestamp,
      'svix-signature': svixSignature,
    }) as WebhookEvent;
  } catch {
    return new Response('Invalid signature', { status: 400 });
  }

  switch (event.type) {
    case 'user.created':
      await handleUserCreated(event.data);
      break;
    case 'user.updated':
      await handleUserUpdated(event.data);
      break;
    case 'user.deleted':
      await handleUserDeleted(event.data);
      break;
  }

  return new Response('OK', { status: 200 });
}
```

The `svix` library handles webhook signature verification. Clerk uses Svix under the hood for webhook delivery; the `CLERK_WEBHOOK_SECRET` comes from the Clerk dashboard.

## The user.created handler

```ts
async function handleUserCreated(data: {
  id: string;
  email_addresses: Array<{ email_address: string; id: string }>;
  first_name: string | null;
  last_name: string | null;
  image_url: string;
}) {
  const primaryEmail = data.email_addresses[0]?.email_address;
  if (!primaryEmail) return;

  // Use a transaction: all three inserts succeed or all fail
  await db.transaction(async (tx) => {
    // 1. Create user record
    const [user] = await tx.insert(users).values({
      id: data.id, // Use Clerk's user ID as our primary key
      email: primaryEmail,
      name: [data.first_name, data.last_name].filter(Boolean).join(' ') || primaryEmail,
      avatarUrl: data.image_url,
    }).returning();

    // 2. Create personal workspace
    const [workspace] = await tx.insert(workspaces).values({
      name: `${user.name}'s Workspace`,
      ownerId: user.id,
      slug: generateSlug(user.name),
    }).returning();

    // 3. Seed with onboarding channel
    await tx.insert(channels).values({
      workspaceId: workspace.id,
      name: 'general',
      description: 'Welcome to your workspace',
      createdBy: user.id,
    });
  });
}
```

Using Clerk's user ID (`data.id`) as the primary key in our `users` table means every JOIN between our data and auth state is by the same ID without any translation layer.

## The failure case: idempotency

Clerk's webhook delivery is at-least-once. If the endpoint returns a non-2xx status or times out, Clerk will retry the webhook. This means a `user.created` event could be processed twice.

Without idempotency handling, two calls to `handleUserCreated` would attempt to insert a duplicate user — and fail with a primary key conflict, which is actually fine in this case. But the workspace and channel inserts would fail silently after the user insert succeeded, leaving the user without a workspace.

The correct handling:

```ts
async function handleUserCreated(data: ...) {
  // Use ON CONFLICT DO NOTHING — idempotent insert
  const [user] = await db.insert(users)
    .values({ id: data.id, ... })
    .onConflictDoNothing()
    .returning();

  // If user already existed (returned nothing), their workspace was already created
  if (!user) return;

  // Only create workspace if user was freshly inserted
  await db.transaction(async (tx) => {
    const [workspace] = await tx.insert(workspaces).values({ ... }).returning();
    await tx.insert(channels).values({ workspaceId: workspace.id, ... });
  });
}
```

`ON CONFLICT DO NOTHING` makes the insert idempotent. If the user already exists, the insert returns nothing and we skip the workspace creation.

## The user.updated handler

```ts
async function handleUserUpdated(data: {
  id: string;
  email_addresses: Array<{ email_address: string; id: string }>;
  first_name: string | null;
  last_name: string | null;
  image_url: string;
}) {
  const primaryEmail = data.email_addresses[0]?.email_address;
  if (!primaryEmail) return;

  await db.update(users)
    .set({
      email: primaryEmail,
      name: [data.first_name, data.last_name].filter(Boolean).join(' ') || primaryEmail,
      avatarUrl: data.image_url,
      updatedAt: new Date(),
    })
    .where(eq(users.id, data.id));
}
```

## The timing gap problem

There's a small window between when Clerk creates a user and when the webhook fires. If a user signs up, completes Clerk's flow, and is immediately redirected to The Hyve before the webhook has been processed, they'll arrive at the app without a user record or workspace.

The solution: when a user first accesses The Hyve after sign-up, the app checks for the existence of their record and creates it if it doesn't exist yet (a fallback creation path). The webhook is the primary path; the app's first-access check is the safety net.

```ts
// In the authenticated layout
const user = await db.query.users.findFirst({
  where: eq(users.id, currentUserId),
});

if (!user) {
  // Webhook hasn't fired yet — create user record now
  await createUserAndWorkspace(currentUserId, clerkUser);
}
```

This pattern — webhook as primary, fallback on first access — is more robust than relying on the webhook alone for user provisioning.
