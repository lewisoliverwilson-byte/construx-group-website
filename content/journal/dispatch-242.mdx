Analytics events are easy to capture and hard to make useful. You can send thousands of events to PostHog and still not know why users are churning. The quality of the data depends on event design before the first event is sent.

Here's the event taxonomy we use across Scoutr, The Marqet, and The Hyve.

## The naming convention

Events use `noun_verb` naming with snake_case:

```
scan_started
scan_completed
scan_failed
product_added_to_watchlist
subscription_upgraded
listing_viewed
application_submitted
message_sent
channel_created
agent_invoked
```

The pattern is `object_action`:
- Object: the thing that was acted on (`scan`, `listing`, `channel`, `agent`)
- Action: what happened to it (`started`, `completed`, `viewed`, `invoked`)

This makes the event taxonomy browsable: you can filter PostHog by `scan_` and see all scan-related events. It also reads naturally as prose: "a scan was started", "a listing was viewed".

What we avoid:
- `click_scan_button` — captures implementation, not intent (the button could be renamed)
- `scanned` — ambiguous past tense
- `ScanEvent.Started` — unnecessary casing ceremony

## The required properties

Every event includes a minimal set of properties:

```ts
interface BaseEventProperties {
  product: 'scoutr' | 'marqet' | 'hyve' | 'website';
  environment: 'production' | 'development';
  timestamp: string; // ISO 8601
}
```

The `product` property is essential because all three products share a PostHog project. Without it, you can't filter "show me only Scoutr events." The `environment` property keeps development noise out of production dashboards.

These are set once at the PostHog client initialisation level:

```ts
posthog.register({
  product: 'scoutr',
  environment: process.env.NODE_ENV === 'production' ? 'production' : 'development',
});
```

`posthog.register()` adds these as super properties — they're included on every event automatically.

## Event-specific properties

Beyond the base properties, each event has properties specific to its context.

**Scoutr scan events:**
```ts
posthog.capture('scan_started', {
  url_domain: new URL(url).hostname, // amazon.co.uk, ebay.co.uk
  source: 'manual' | 'batch', // how the scan was initiated
});

posthog.capture('scan_completed', {
  url_domain: new URL(url).hostname,
  duration_ms: endTime - startTime,
  margin_pct: result.marginPct,
  confidence: result.confidenceScore,
  platform: result.platform, // 'amazon' | 'ebay' | 'other'
  has_listing_match: result.hasListingMatch,
});

posthog.capture('scan_failed', {
  url_domain: new URL(url).hostname,
  error_type: 'timeout' | 'unsupported_domain' | 'extraction_failed' | 'api_error',
  duration_ms: endTime - startTime,
});
```

The margin and confidence data on `scan_completed` lets us understand whether users are finding the tool useful (high margins discovered → likely retention) and how the confidence score distribution looks across real usage.

**The Marqet listing events:**
```ts
posthog.capture('listing_viewed', {
  listing_id: listing.id,
  category: listing.category,
  seller_id: listing.sellerId, // anonymised in PostHog
  search_query: searchQuery, // if the user came via search
  referral_source: 'search' | 'browse' | 'direct' | 'share',
});

posthog.capture('application_submitted', {
  listing_id: listing.id,
  category: listing.category,
  buyer_has_previous_transactions: hasPreviousTransactions,
});
```

**The Hyve workspace events:**
```ts
posthog.capture('agent_invoked', {
  workspace_id: workspaceId, // anonymised
  channel_type: 'public' | 'private' | 'dm',
  message_length: message.length,
  context_messages: contextCount, // how many messages in context window
  used_historical_context: usedHistoricalContext, // once pgvector is live
});

posthog.capture('channel_created', {
  workspace_id: workspaceId,
  channel_type: 'public' | 'private',
  triggered_by: 'manual' | 'onboarding_flow',
});
```

## What we deliberately don't track

**Individual message content.** We capture `message_sent` with metadata (length, channel type, whether it triggered an agent response), but not the message content itself. Content is private to the workspace.

**Precise user paths.** We capture key feature events, not every page view or click. PostHog's session recordings cover the click-level detail when we need it; our events database doesn't need to.

**Events we'll never act on.** "User viewed their profile" is an event we could capture and never use. Events cost nothing to send but add noise to every dashboard and funnel. If you can't describe the decision the event would inform, don't capture it.

## The funnel that matters most

The most valuable funnel for each product:

**Scoutr:** `scan_started` → `scan_completed` → `product_added_to_watchlist`
The completion rate tells us whether scans are succeeding; the watchlist rate tells us whether the data is useful enough to act on.

**The Marqet:** `listing_viewed` → `application_submitted` → `transaction_funded`
Listing-to-application measures discovery quality; application-to-transaction measures trust and friction.

**The Hyve:** `workspace_created` → `first_message_sent` → `agent_invoked` → `active_7_days`
The activation funnel: does the user get to a moment of value quickly enough to return?

These funnels are configured in PostHog as saved insights, reviewed weekly.

## The PostHog configuration

All three products share a PostHog project, distinguishable by the `product` super property. Separate projects would mean separate dashboards, separate API keys, and no cross-product insights.

The downside of a shared project: distinct IDs (anonymous user IDs before login) aren't automatically unified with identified users across products. If a user tries Scoutr and The Hyve and uses the same email to sign up for both, PostHog doesn't automatically merge those profiles. We handle this with `posthog.identify()` using the Clerk user ID on login for all three products.

## The event we added after shipping

After three months of the `scan_completed` event, we noticed something in the data: `confidence` was clustered in two groups — above 0.8 and below 0.4. The middle range was almost empty.

This wasn't visible until we had real usage data. The bimodal distribution told us the confidence algorithm was working more like a binary signal than a continuous score. We redesigned the confidence score calculation to produce a more useful distribution.

This is the kind of insight that justifies the instrumentation investment. A feature you can measure is a feature you can improve.
