title: "Grafana Tempo: distributed tracing storage with TraceQL"
date: "2033-02-21"
excerpt: "Tempo is Grafana's distributed tracing backend. It stores traces (OpenTelemetry, Jaeger, Zipkin, or Zipkin-compatible formats) in object storage (S3, GCS) using a columnar format called Parquet for the trace index. Unlike Jaeger's Elasticsearch backend or Zipkin's Cassandra, Tempo has no indexing by default — it stores every trace by trace ID and retrieves by ID in O(1). This makes it cheap to operate: Tempo on S3 costs a fraction of running Elasticsearch for Jaeger. The trade-off is you need a trace ID to look up a trace. TraceQL (released in Tempo 2.0) adds server-side search: span attribute filtering, duration constraints, and structural queries (find a root span with a specific error that has a child span calling the database). Combined with exemplars in Prometheus and trace ID injection in Loki, you get correlation: click a spike in Grafana, jump to the exact trace."
author: "Lewis Wilson"

Object storage backend. Trace by ID. TraceQL span search. OTLP ingest. Exemplar correlation.

## Deployment and ingest

```bash
# Install Tempo
helm upgrade --install tempo grafana/tempo-distributed \
  --namespace monitoring \
  -f tempo-values.yaml

cat > tempo-values.yaml <<'EOF'
storage:
  trace:
    backend: s3
    s3:
      bucket: construx-tempo-traces
      endpoint: s3.eu-west-1.amazonaws.com
      region: eu-west-1

# Tempo components (distributed mode):
# - Distributor:  receives traces, validates, and shards to ingesters
# - Ingester:     holds recent traces in memory for fast lookup
# - Querier:      handles trace lookups (by ID) and TraceQL searches
# - Compactor:    merges, indexes, and applies retention to S3 blocks
# - Query-frontend: query sharding and caching

distributor:
  replicaCount: 2
ingester:
  replicaCount: 3
  config:
    max_block_duration: 30m  # flush memory to S3 every 30 min
querier:
  replicaCount: 2
compactor:
  replicaCount: 1  # singleton — runs retention and compaction

tempo:
  retention: 336h  # 14 days trace retention
  global:
    max_bytes_per_trace: 5000000  # 5MB max per trace
EOF

# Ingest endpoint accepts OTLP (gRPC or HTTP)
# Configure OpenTelemetry Collector to export to Tempo:

# otelcol-config.yaml
exporters:
  otlp:
    endpoint: tempo-distributor.monitoring.svc:4317
    tls:
      insecure: true

service:
  pipelines:
    traces:
      exporters: [otlp]

# Or configure the OTel SDK directly in the application:
# OTEL_EXPORTER_OTLP_ENDPOINT=http://tempo-distributor.monitoring.svc:4317
# OTEL_SERVICE_NAME=construx-api
# OTEL_TRACES_SAMPLER=parentbased_traceidratio
# OTEL_TRACES_SAMPLER_ARG=0.1  # 10% sample rate

# Grafana data source (use the Tempo type, not generic HTTP)
# URL: http://tempo-query-frontend.monitoring.svc:3200
```

## TraceQL: searching spans

```bash
# TraceQL: query language for spans across traces
# Two parts:
# 1. Span selector: filter spans by attribute, duration, status, kind
# 2. Pipeline: structural operations on the matching trace (count, avg, etc.)

# Find all traces with an error span in construx-api
{resource.service.name="construx-api" && status=error}

# Find traces with a span longer than 500ms
{resource.service.name="construx-api" && duration>500ms}

# Find traces with a specific attribute
{span.http.url =~ "/api/v1/orders.*" && span.http.status_code=500}

# Structural: find traces where construx-api calls postgres AND the DB span > 100ms
{resource.service.name="construx-api"} >> {resource.service.name="postgres" && duration>100ms}
# >> means "traces containing this span downstream of the parent match"

# Find slow traces with a specific root route
{name="POST /api/v1/orders" && duration>1s}

# Count errors per service (metric over traces)
{status=error} | rate()
# (Returns error span rate over time as a time series)

# Average duration by route (span metrics)
{name=~"/api/v1/.*"} | avg_over_time(duration)

# Search via CLI
curl 'http://tempo:3200/api/search' \
  --data-urlencode 'q={resource.service.name="construx-api" && status=error && duration>500ms}' \
  --data-urlencode 'start=1706524800' \
  --data-urlencode 'end=1706528400' \
  --data-urlencode 'limit=20' \
  | jq '.traces[] | {traceID: .traceID, rootName: .rootName, duration: .durationMs}'

# Fetch a specific trace by ID
curl http://tempo:3200/api/traces/4bff3f9a7e2c1d08b3a9f4e7c2d18305
# Returns all spans for the trace in JSON
```

## Exemplars: linking Prometheus metrics to Tempo traces

```bash
# Exemplars: Prometheus samples with an attached trace ID
# When you click a spike on a Grafana panel, jump to the exact trace

# Instrument the application to emit exemplars
# Go example (using prometheus/client_golang):

import (
  "github.com/prometheus/client_golang/prometheus"
  "go.opentelemetry.io/otel/trace"
)

var requestDuration = prometheus.NewHistogramVec(
  prometheus.HistogramOpts{
    Name:    "http_request_duration_seconds",
    Buckets: prometheus.DefBuckets,
  },
  []string{"method", "route", "status"},
)

func handler(w http.ResponseWriter, r *http.Request) {
  start := time.Now()
  // ... handle request ...
  duration := time.Since(start)

  // Attach trace ID as an exemplar
  spanCtx := trace.SpanFromContext(r.Context()).SpanContext()
  requestDuration.With(prometheus.Labels{
    "method": r.Method,
    "route":  "/api/v1/orders",
    "status": "200",
  }).(prometheus.ExemplarObserver).ObserveWithExemplar(
    duration.Seconds(),
    prometheus.Labels{
      "traceID": spanCtx.TraceID().String(),
    },
  )
}

# Prometheus scrapes exemplars automatically when the metric format is OpenMetrics
# /metrics with Accept: application/openmetrics-text

# Grafana: configure Tempo as the trace backend for Prometheus data source
# In the Prometheus data source settings:
# - Enable "Exemplars"
# - Link to Tempo data source: http://tempo:3200
# - URL label: traceID

# Now in Grafana, spikes on histograms show "star" markers
# Click a star → view the exact trace in Tempo
# Grafana pulls the trace ID from the exemplar label
```

## Loki → Tempo trace correlation

```bash
# Trace correlation: jump from a Loki log line to the Tempo trace
# Requirements:
# 1. Application injects trace ID into log lines
# 2. Loki data source in Grafana is configured with Tempo as the trace backend

# Application: inject trace ID into structured logs
# Go example with slog + OTel:
func LogWithTrace(ctx context.Context, msg string, args ...any) {
  span := trace.SpanFromContext(ctx)
  slog.InfoContext(ctx, msg,
    append(args,
      "traceID", span.SpanContext().TraceID().String(),
      "spanID",  span.SpanContext().SpanID().String(),
    )...,
  )
}
# Output: {"level":"INFO","msg":"order created","traceID":"4bff3f9a...","spanID":"a1b2c3d4...","orderID":"ORD-123"}

# Loki data source in Grafana:
# Settings → Derived Fields:
# - Name: TraceID
# - Regex: "traceID":"([a-f0-9]{32})"
# - Query: ${__value.raw}
# - Internal link: Tempo data source

# Now in Grafana Loki Explore:
# 1. Search logs: {app="construx-api", level="error"}
# 2. See an error log line
# 3. Click the trace ID → opens Tempo waterfall for that exact trace

# Full correlation loop:
# Prometheus spike → exemplar → Tempo trace
# Loki error log → derived field → Tempo trace
# Tempo trace → K8s pod labels → Loki logs for that pod
# All from within Grafana, no context switching
```

## Sampling strategies

```bash
# Head-based sampling (at the SDK, before the trace is complete)
# Probabilistic: sample 10% of all traces
OTEL_TRACES_SAMPLER=parentbased_traceidratio
OTEL_TRACES_SAMPLER_ARG=0.1

# Tail-based sampling (at the Collector, after the trace is complete)
# Advantage: you can keep all error traces even with low sample rate
# Requires OpenTelemetry Collector with tail_sampling processor

# otelcol tail sampling config:
processors:
  tail_sampling:
    decision_wait: 10s       # wait 10s for all spans before deciding
    num_traces: 100000       # hold up to 100k pending traces in memory
    policies:
      # Always keep error traces
      - name: errors
        type: status_code
        status_code: { status_codes: [ERROR] }

      # Always keep slow traces (> 1s)
      - name: slow_traces
        type: latency
        latency: { threshold_ms: 1000 }

      # Sample 1% of everything else
      - name: random_sample
        type: probabilistic
        probabilistic: { sampling_percentage: 1 }

    # Policy evaluation: if ANY policy matches, keep the trace
    # So: errors=always, slow=always, everything else=1%
    # Effective: ~1% of fast successful traces + 100% of errors + 100% of slow

# Cost implication:
# At 1000 req/s, 10% head sampling = 100 traces/s
# Tail sampling: ~1% normal + 100% error (assume 0.1% error rate)
# = 10.1 traces/s normal + 1 error/s = ~11 traces/s stored
# ~98% reduction in trace volume vs head sampling at 10%
```

The LGTM stack (Loki, Grafana, Tempo, Mimir) positions itself as the open-source alternative to Datadog or Honeycomb for observability. The correlation features — exemplars linking Prometheus to Tempo, Loki derived fields linking logs to traces — work well when the stack is deployed together. The operational cost is real: you're running four systems instead of one SaaS. But the economics at scale flip: Datadog pricing scales with hosts and data volume in ways that become painful at growth; LGTM on S3 does not. The decision point is usually around 50-100 hosts where self-hosted LGTM becomes significantly cheaper than Datadog, and you have the engineering capacity to operate it.
