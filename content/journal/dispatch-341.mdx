The Edge Runtime is a restricted JavaScript environment that runs on Cloudflare Workers or Vercel's edge network rather than in a Node.js process. Cold starts are near-zero because there's no Node.js to spin up. The trade-off: you can't use most of the Node.js standard library, no native binaries, and CPU time is capped.

## What the Edge Runtime actually is

At the edge, your code runs in a V8 isolate — the same engine as Chrome, but without Node.js APIs. What's available:

- `fetch`, `Request`, `Response`, `Headers` (Web APIs)
- `crypto` (Web Crypto, not Node's `crypto`)
- `TextEncoder` / `TextDecoder`
- `URL`, `URLSearchParams`
- `setTimeout` / `setInterval` (limited)

What's not available:

- `fs`, `path`, `os`, `net`, `stream` — no Node.js built-ins
- `Buffer` (or polyfill only)
- Native addons (`.node` files) — nothing compiled to native code
- Most npm packages that use Node APIs internally

## Declaring edge runtime

```ts
// In a route handler, middleware, or page:
export const runtime = 'edge';
```

Middleware runs on the Edge Runtime by default. Route handlers and pages default to Node.js unless you opt in.

## What to put at the edge

**Middleware** — already runs at edge. Authentication redirects, locale detection, A/B test assignment, bot detection. These are read-and-redirect operations that don't need Node APIs.

**Geolocation** — Vercel and Cloudflare inject geo headers. Use them in middleware without a database call:

```ts
// middleware.ts (runs at edge automatically)
import { NextRequest, NextResponse } from 'next/server';

export function middleware(req: NextRequest) {
  const country = req.geo?.country ?? 'US';
  const city = req.geo?.city;

  // Redirect UK users to /gb route
  if (country === 'GB' && !req.nextUrl.pathname.startsWith('/gb')) {
    const url = req.nextUrl.clone();
    url.pathname = `/gb${url.pathname}`;
    return NextResponse.redirect(url);
  }

  return NextResponse.next();
}
```

**JWT validation** — decoding and verifying a JWT requires only `crypto`, which is available:

```ts
export const runtime = 'edge';

import { jwtVerify } from 'jose'; // jose uses Web Crypto, works at edge

export async function GET(req: Request) {
  const token = req.headers.get('authorization')?.replace('Bearer ', '');
  if (!token) return Response.json({ error: 'Unauthorized' }, { status: 401 });

  try {
    const secret = new TextEncoder().encode(process.env.JWT_SECRET!);
    const { payload } = await jwtVerify(token, secret);
    return Response.json({ user: payload });
  } catch {
    return Response.json({ error: 'Invalid token' }, { status: 401 });
  }
}
```

**Rate limiting checks** — if your rate limiter uses HTTP (like Upstash Redis), it works at edge. Native Redis connections don't.

**Personalised headers** — injecting `Vary` headers, setting cookies, modifying responses before they hit the cache.

## What to keep in Node.js

**Database queries** — Prisma, Drizzle, Sequelize all require Node.js. Neon and PlanetScale have HTTP-based clients that technically work at edge, but connection overhead matters more for DB queries than for simple middleware — measure before optimising.

**Image processing** — `sharp` is a native module. Won't work at edge. Use Next.js Image component's built-in pipeline or an image CDN.

**File system access** — reading config files, writing temp files, anything using `fs`. Not available.

**Email sending** — Nodemailer uses Node's `net` module. Use an HTTP-based sender (Resend, Postmark) if you need edge email, but there's usually no reason to send email at the edge.

**Complex computation** — the 25ms CPU limit kills anything that does real work. Cryptographic operations beyond JWT verification, PDF generation, video processing — all stay in Node.js.

## Edge-compatible packages

Before adding a dependency in an edge route, check if it uses Node APIs:

```bash
# Check what a package imports
npx @vercel/nft --entrypoint ./app/api/edge-route/route.ts
```

Known edge-compatible libraries: `jose`, `zod`, `date-fns`, `nanoid`, `@upstash/redis`, `@upstash/ratelimit`, `ai` (Vercel AI SDK's edge export).

Known incompatible: `prisma`, `sharp`, `nodemailer`, `bcrypt` (use `bcryptjs` which is pure JS), `jsonwebtoken` (use `jose`).

## Streaming at the edge

Streaming works well at edge — no Node.js required:

```ts
export const runtime = 'edge';

export async function GET() {
  const stream = new ReadableStream({
    async start(controller) {
      const encoder = new TextEncoder();

      for (let i = 0; i < 5; i++) {
        await new Promise((r) => setTimeout(r, 500));
        controller.enqueue(encoder.encode(`data: ${JSON.stringify({ tick: i })}\n\n`));
      }

      controller.close();
    },
  });

  return new Response(stream, {
    headers: {
      'Content-Type': 'text/event-stream',
      'Cache-Control': 'no-cache',
    },
  });
}
```

This is why the Vercel AI SDK's `streamText` defaults to edge — streaming AI responses benefits from zero cold start and global distribution.

## The practical rule

Put something at the edge when: it runs on every request, it doesn't need a database, and latency is the bottleneck. Keep it in Node.js when: it needs libraries, accesses data, or does real computation. Most API routes belong in Node.js. Most middleware belongs at the edge.
