A design system is a library of components, guidelines, and design decisions that teams use to build consistent UIs. Large companies invest significantly in them — Shopify's Polaris, GitHub's Primer, Stripe's design system. They enable teams to build consistently without constant coordination.

We don't have a design system. Here's what we have instead, and why it's enough.

## What we use instead

**Tailwind CSS with a custom theme.** Tailwind's utility-first approach means there's no component library to maintain — just a config file that sets the design tokens. Our `tailwind.config.ts` defines:

```ts
theme: {
  extend: {
    colors: {
      construx: '#F97316',
      'construx-dim': 'rgba(249,115,22,0.1)',
      'text-base': 'rgba(240,239,255,0.92)',
      'text-muted': 'rgba(240,239,255,0.55)',
      'text-dim': 'rgba(240,239,255,0.3)',
      'text-primary': 'rgba(240,239,255,0.85)',
      'border': 'rgba(255,255,255,0.08)',
      'border-bright': 'rgba(255,255,255,0.14)',
      'subtle': 'rgba(255,255,255,0.03)',
    },
    fontFamily: {
      sans: ['Space Grotesk', 'var(--font-space-grotesk)', 'sans-serif'],
      mono: ['JetBrains Mono', 'var(--font-jetbrains-mono)', 'monospace'],
    },
    fontSize: {
      'display': ['4.5rem', { lineHeight: '1', letterSpacing: '-0.03em' }],
      'display-sm': ['3rem', { lineHeight: '1.05', letterSpacing: '-0.02em' }],
      'heading-xl': ['1.75rem', { lineHeight: '1.2' }],
    },
  },
},
```

These tokens establish the vocabulary. Consistency comes from using the token (e.g., `text-text-muted`) rather than a raw colour value (e.g., `text-[rgba(240,239,255,0.55)]`). If we want to change the muted text colour globally, we change one token value.

**Shared component conventions.** Our components follow patterns that are documented but not in a design system — in code review comments, in the journal (like this post), and in the components themselves. For example:

- Every terminal-style panel gets macOS traffic lights: red (#FF5F57), yellow (#FFBD2E), green (#28C840)
- Every dark card uses `background: rgba(5,5,18,0.88)` and `border: 1px solid rgba(255,255,255,0.07)`
- Every monospace metadata label uses `font-mono text-[9px] uppercase tracking-widest`
- Every interactive element gets `transition-all duration-150` or similar

These aren't documented in a Storybook or Notion page. They're encoded in existing components — a new component is built by reading an existing one that does something similar.

**A prose style guide for the journal.** MDX posts follow consistent conventions:
- H2 for main sections, H3 for subsections
- Code blocks always have a language tag (```ts, ```sql, etc.)
- Lists for enumerations, paragraphs for prose
- Bold for the first occurrence of a technical term
- Example code reflects the actual codebase patterns, not simplified pseudocode

The journal is the only place where content consistency matters enough to document explicitly.

## Why a full design system isn't worth it

**Maintenance cost.** A component library needs maintenance — when you change the design of a button, you update the component and every consumer needs to be tested. For two people shipping three products, this overhead eats into building time.

**Premature abstraction.** Design systems abstract patterns before those patterns are stable. In a product that's still finding its form, the right abstraction isn't obvious until you've built enough instances to see the pattern. Building a component library before the patterns are stable means you're abstracting the wrong things.

**Storybook overhead.** Storybook is the standard tool for documenting design systems. It's excellent. It's also a separate build system to maintain, a documentation site to keep updated, and an environment that diverges from the real app context over time. The overhead isn't worth it for our team size.

**Figma duplication.** Design systems that work well typically have Figma components that mirror the code components. Keeping these in sync is overhead. We design in code — the Figma equivalent is just reading the source.

## When we'll revisit

A design system makes sense when:
1. Multiple developers build UI independently and inconsistency becomes a problem
2. The design patterns are stable enough to abstract confidently
3. The overhead of maintaining a design system is less than the overhead of inconsistency

We're not at any of those points. Two people who review each other's code and read each other's components before building can maintain consistency without formal systems.

The right design infrastructure for a two-person team: semantic Tailwind tokens, good component naming, consistent patterns established by example, and regular visual review. That's what we have. It works.

## The future

As Construx grows (in team size or in product surface area), the pressures above will change. The token system we have now is the foundation a design system would build on — it's already more systematic than most teams start with. The jump from "well-configured Tailwind" to "shared component library" is smaller than the jump from "ad-hoc styling" to "design system."

We've kept the path to a design system open. We just haven't walked it yet.
