Sentry closes the gap between a user experiencing an error and you knowing about it. Without it, errors are invisible until a user reports them. With it, every unhandled exception lands in your inbox within seconds, with enough context to reproduce and fix it.

## Next.js setup

```bash
npm install @sentry/nextjs
npx @sentry/wizard@latest -i nextjs
```

The wizard creates `sentry.client.config.ts`, `sentry.server.config.ts`, `sentry.edge.config.ts`, and instruments `next.config.js` automatically.

```ts
// sentry.client.config.ts
import * as Sentry from '@sentry/nextjs';

Sentry.init({
  dsn:              process.env.NEXT_PUBLIC_SENTRY_DSN,
  environment:      process.env.NODE_ENV,
  tracesSampleRate: 0.2,   // 20% of requests traced for performance
  replaysOnErrorSampleRate: 1.0,  // 100% of error sessions replayed
  replaysSessionSampleRate: 0.1,  // 10% of all sessions replayed

  integrations: [
    Sentry.replayIntegration({
      maskAllText:   false,
      blockAllMedia: false,
    }),
  ],
});
```

```ts
// sentry.server.config.ts
import * as Sentry from '@sentry/nextjs';

Sentry.init({
  dsn:              process.env.SENTRY_DSN,
  environment:      process.env.NODE_ENV,
  tracesSampleRate: 0.2,
});
```

## Capturing errors manually

```ts
import * as Sentry from '@sentry/nextjs';

// Capture an exception
try {
  await riskyOperation();
} catch (err) {
  Sentry.captureException(err, {
    tags:  { operation: 'payment', userId },
    extra: { orderId, amount },
  });
  throw err;
}

// Capture a message (non-exception)
Sentry.captureMessage('Unusual payment flow triggered', {
  level: 'warning',
  tags:  { userId },
});

// Add breadcrumbs (user actions leading to the error)
Sentry.addBreadcrumb({
  category: 'auth',
  message:  'User clicked login',
  level:    'info',
});
```

## User context

```ts
// Set user context on every session
Sentry.setUser({
  id:    userId,
  email: user.email,
});

// Clear on logout
Sentry.setUser(null);
```

When an error occurs, Sentry shows which user was affected — useful for reaching out directly or understanding blast radius.

## Custom spans for performance tracing

```ts
import * as Sentry from '@sentry/nextjs';

async function processOrder(orderId: string) {
  return Sentry.startSpan({ name: 'processOrder', op: 'function' }, async (span) => {
    span.setAttribute('orderId', orderId);

    const payment = await Sentry.startSpan({ name: 'chargeCard', op: 'payment' }, () =>
      chargeCustomer(orderId),
    );

    await Sentry.startSpan({ name: 'fulfillOrder', op: 'db' }, () =>
      fulfillOrder(orderId, payment.id),
    );

    return { success: true };
  });
}
```

Spans appear in the Sentry performance waterfall — you can see exactly where time is spent across the request lifecycle.

## Error boundaries in React

```tsx
import * as Sentry from '@sentry/nextjs';

// Sentry's ErrorBoundary component
export function AppWithErrorBoundary({ children }: { children: React.ReactNode }) {
  return (
    <Sentry.ErrorBoundary
      fallback={({ error, resetError }) => (
        <div>
          <h2>Something went wrong</h2>
          <pre>{String(error)}</pre>
          <button onClick={resetError}>Try again</button>
        </div>
      )}
      onError={(error, info) => {
        console.error('Error boundary caught:', error, info);
      }}
    >
      {children}
    </Sentry.ErrorBoundary>
  );
}
```

## Source maps

```ts
// next.config.ts
import { withSentryConfig } from '@sentry/nextjs';

const nextConfig = { /* your config */ };

export default withSentryConfig(nextConfig, {
  org:     'construx-group',
  project: 'construx-website',

  // Upload source maps during build — Sentry shows exact source line in errors
  sourcemaps: {
    deleteSourcemapsAfterUpload: true,  // don't ship source maps to users
  },

  // Silence Sentry CLI output during build
  silent: !process.env.CI,
});
```

Source maps are uploaded during `next build`. In the Sentry dashboard, stack traces show the original TypeScript source line, not the minified bundle output.

## Alerts

```yaml
# Alert: more than 10 new errors in 10 minutes
# (configured in Sentry dashboard, not YAML — shown here for documentation)
trigger: new_error_count > 10 in 10 minutes
channels: [slack:#errors, email:lewis@construxgroup.io]
filters:
  - environment: production
  - level: error
```

Set alert thresholds per project — too many alerts becomes noise. Start with: alert on new error types (first occurrence), and weekly digest for ongoing errors.

## Rate limiting what Sentry captures

```ts
Sentry.init({
  beforeSend: (event, hint) => {
    // Drop errors from browser extensions
    if (event.exception?.values?.[0]?.stacktrace?.frames?.some(
      (f) => f.filename?.includes('chrome-extension'),
    )) {
      return null;
    }

    // Drop cancelled fetch requests
    const error = hint.originalException;
    if (error instanceof Error && error.name === 'AbortError') {
      return null;
    }

    return event;
  },

  // Only capture a fraction of performance data
  tracesSampler: (ctx) => {
    if (ctx.transactionContext.name.includes('/api/health')) return 0;
    return 0.1;
  },
});
```
