Async JavaScript is pervasive and async bugs are subtle. A promise that resolves after a component unmounts, a background fetch that continues after a user navigates away, a concurrent operation where a partial failure leaves state inconsistent — these are the failure modes that structured concurrency patterns prevent.

Here's how we handle concurrent async operations in production TypeScript.

## The problem with Promise.all

`Promise.all` is the standard tool for concurrent async operations:

```ts
const [users, listings, stats] = await Promise.all([
  getUsers(),
  getListings(),
  getStats(),
]);
```

The failure mode: if any of the three operations fails, `Promise.all` rejects with the first failure, and the other operations continue running in the background. You have no way to cancel them, and they may resolve or reject later, potentially modifying state you've already abandoned.

For read-only operations this is usually fine — the background operations complete harmlessly. For write operations, it's a problem.

## AbortController for cancellable operations

Every fetch operation in the products uses `AbortSignal.timeout()` or an explicit `AbortController`:

```ts
// Timeout-based cancellation
const result = await fetch(url, {
  signal: AbortSignal.timeout(10_000), // 10 second timeout
});

// Manual cancellation
const controller = new AbortController();
const { signal } = controller;

// Cancel after navigation (useEffect cleanup)
useEffect(() => {
  let cancelled = false;
  
  fetchData(signal).then((data) => {
    if (!cancelled) setState(data);
  });
  
  return () => {
    cancelled = true;
    controller.abort();
  };
}, []);
```

The `cancelled` flag guards against the case where the component unmounts between the fetch completing and the state update — a common race condition in React effects.

## Promise.allSettled for independent operations

When operations are independent and you need all results regardless of individual failures, use `Promise.allSettled`:

```ts
const results = await Promise.allSettled([
  sendEnquiryEmail(enquiry),
  notifySellerSlack(enquiry),
  recordAnalyticsEvent('enquiry_sent', enquiry),
]);

// Process results individually
results.forEach((result, i) => {
  if (result.status === 'rejected') {
    logger.error('Background operation failed', {
      operation: ['email', 'slack', 'analytics'][i],
      error: result.reason,
    });
  }
});
```

The core operation (saving the enquiry to the database) happens before this block. These three operations are best-effort side effects — a failure in one shouldn't affect the others.

## Semaphore for controlled concurrency

Processing a batch of items concurrently without overwhelming downstream services:

```ts
class Semaphore {
  private queue: (() => void)[] = [];
  private active = 0;

  constructor(private maxConcurrent: number) {}

  async acquire(): Promise<void> {
    if (this.active < this.maxConcurrent) {
      this.active++;
      return;
    }
    return new Promise((resolve) => {
      this.queue.push(() => {
        this.active++;
        resolve();
      });
    });
  }

  release(): void {
    this.active--;
    const next = this.queue.shift();
    if (next) next();
  }

  async run<T>(fn: () => Promise<T>): Promise<T> {
    await this.acquire();
    try {
      return await fn();
    } finally {
      this.release();
    }
  }
}

// Use in Scoutr's batch scan processing
const sem = new Semaphore(3); // max 3 concurrent eBay API calls

const results = await Promise.allSettled(
  productUrls.map((url) => sem.run(() => analyseProduct(url)))
);
```

The Semaphore ensures that at most 3 concurrent eBay API calls are in flight, regardless of how many products are in the batch.

## The cleanup pattern for useEffect

Any async operation started in a `useEffect` that reads component state or calls component setState needs cleanup:

```ts
useEffect(() => {
  // Create a stable reference to avoid closures over stale state
  const abortController = new AbortController();
  
  async function fetchData() {
    try {
      const data = await fetch('/api/data', {
        signal: abortController.signal,
      }).then((r) => r.json());
      
      // Guard against unmount
      if (!abortController.signal.aborted) {
        setData(data);
      }
    } catch (err) {
      if (err instanceof Error && err.name === 'AbortError') {
        return; // Expected — component unmounted
      }
      setError(err);
    }
  }
  
  fetchData();
  
  return () => {
    abortController.abort();
  };
}, []);
```

The `AbortController` pattern is cleaner than a `cancelled` boolean flag because it works for nested operations — a fetch started by `fetchData` will also be cancelled when the signal is aborted.

## Concurrent mutation safety

For write operations where concurrent execution could produce inconsistent state, we use a lock pattern:

```ts
class AsyncLock {
  private locked = false;
  private queue: (() => void)[] = [];

  async acquire(): Promise<() => void> {
    if (!this.locked) {
      this.locked = true;
      return () => this.release();
    }
    return new Promise((resolve) => {
      this.queue.push(() => {
        this.locked = true;
        resolve(() => this.release());
      });
    });
  }

  private release() {
    this.locked = false;
    const next = this.queue.shift();
    if (next) next();
  }
}

const paymentLock = new AsyncLock();

// Ensure payment capture is not run concurrently for the same order
async function capturePayment(orderId: string) {
  const release = await paymentLock.acquire();
  try {
    await stripe.paymentIntents.capture(orderId);
    await db.update(orders).set({ status: 'paid' }).where(eq(orders.id, orderId));
  } finally {
    release();
  }
}
```

In practice, we use PostgreSQL's `FOR UPDATE` locking at the database level for critical mutual exclusion — database-level locks survive process restarts, application-level locks don't. The `AsyncLock` above is used for in-process resource contention, not for distributed state.

## The principle

Structured concurrency is about making async lifecycle explicit: when does an operation start, when does it end, what happens if it's cancelled, what happens if it fails. JavaScript's `async/await` is powerful but doesn't enforce structure — that's the developer's responsibility.

The patterns above aren't complex, but they're consistently applied. A codebase where every async operation has explicit cancellation and cleanup is a codebase where "async bug" is a rare incident rather than a regular occurrence.
