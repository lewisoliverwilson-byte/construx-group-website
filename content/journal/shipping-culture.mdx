The most common question we get about the Construx model is some variation of: how do two people maintain three production products and still ship new features?

The answer is a combination of tooling, culture, and deliberate choices about what we don't do.

## The tooling leverage

Modern AI-assisted development compresses the time between "I have an idea" and "it's live." A feature that would have taken a week to spec, design, implement, test, and ship in 2022 takes 1-2 days in 2026. The tool is Claude Code, but the principle applies to any capable AI coding assistant.

The leverage is not uniform. AI assistance compresses the implementation phase dramatically. The design and product thinking phases are not compressed — deciding what to build, why, and for whom still takes the same human judgment as always. The ratio of thinking-to-typing has shifted dramatically in favour of thinking.

We spend a larger fraction of our time on product decisions and a smaller fraction on writing code than most teams. This is the right direction.

## The definition of done

A feature is done when:
1. It's live in production.
2. It works for real users.
3. We've confirmed it doesn't break any existing functionality.

It is not done when:
- It passes tests locally.
- It's been reviewed.
- It's merged to main.

The production environment is the truth. Everything before that is preparation.

This focus on production as the measure of done creates an urgency around shipping. Features that sit in staging or review for more than 24 hours are features we're failing to deliver value with.

## Small batches

We ship in the smallest possible increments. Not "let's build the full batch processing feature" but "let's ship the job submission API, then the status polling endpoint, then the UI."

Small batches have three advantages:

**Faster feedback.** Users are using the feature within days of the first piece being live. Their feedback shapes the subsequent pieces.

**Easier debugging.** When something breaks, there's a smaller set of recent changes to investigate.

**Reduced risk.** Each individual deployment is low-risk. The accumulated risk of a large batch deployment is higher than the sum of several small ones.

The discipline is resisting the urge to "finish the whole thing before shipping." Partial features are fine if the part that's live is genuinely useful.

## Async by default

We operate asynchronously. Not because we're in different time zones — we're not — but because synchronous work creates dependencies that slow both people down.

The practice: everything is written down. A feature decision isn't made in conversation; it's written as a brief (a few paragraphs in Linear) and reviewed. A bug report goes into Linear with reproduction steps before anyone looks at the code.

This feels inefficient when you could just have a five-minute conversation. It's not. Writing the decision down forces the thinking to be complete. Talking about it can leave ambiguities that manifest later. The five-minute conversation often saves 20 minutes but costs 40 in rework.

## No meeting culture

We have no standing meetings. Zero recurring calendar items. If we need to talk, we talk; we don't have a scheduled time to do it.

The time savings are real — estimates vary, but eliminating meetings typically frees 2-4 hours per week per person. At two people, that's 4-8 hours per week of additional productive time.

The practices that replace meetings:
- Async written updates in Linear on each significant decision or progress point.
- A shared Notion workspace where longer-form thinking lives.
- Signal (instant messaging) for quick questions and blockers.

None of these require scheduling.

## The things we don't do

The other half of the output equation is what we don't do.

**We don't design things that don't need design.** Internal admin screens, error pages, and developer tools get functional implementation, not design time. Users of those surfaces care about function; we give them function.

**We don't write documentation that doesn't exist yet.** We document as we ship, not in advance. A document about a feature that doesn't exist yet is speculative and usually wrong by the time the feature ships.

**We don't refactor without cause.** Code that works and is understood doesn't get refactored because it could theoretically be cleaner. We refactor when the code is actively slowing us down or making bugs harder to prevent.

**We don't have quarterly planning.** Planning in three-month increments is too coarse for a two-person team building AI products. Our planning horizon is 2-4 weeks. What are we shipping in the next two weeks? That question is answerable.

## The cultural foundation

None of this works without a shared understanding of what success looks like. For us, it's: users using the products and finding them valuable, measured by retention. Everything else — code quality, feature count, shipping velocity — is instrumental.

This sounds obvious. Most teams don't actually operate with this clarity. Features get built because they're interesting, not because they serve users. Metrics get optimised because they're measurable, not because they correlate with user value. Processes get added because they feel professional, not because they make the product better.

The discipline of asking "does this serve users?" before any significant investment of time is what keeps a two-person team focused on the things that matter.
