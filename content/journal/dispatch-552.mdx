Search in Postgres comes in two flavours: full-text search and vector search. Most documentation treats them as alternatives. They're not. FTS and pgvector answer different questions.

## Full-text search: keyword matching

FTS answers: "which documents contain these words?"

```sql
-- Create a tsvector column
ALTER TABLE posts ADD COLUMN search_vec tsvector;

-- Populate it
UPDATE posts
SET search_vec = to_tsvector('english', coalesce(title, '') || ' ' || coalesce(body, ''));

-- Keep it updated on insert/update
CREATE TRIGGER posts_search_update
BEFORE INSERT OR UPDATE ON posts
FOR EACH ROW EXECUTE FUNCTION tsvector_update_trigger(
  search_vec, 'pg_catalog.english', title, body
);

-- Create GIN index for fast FTS
CREATE INDEX posts_search_idx ON posts USING GIN(search_vec);
```

```sql
-- Search: find posts matching "rate limiting"
SELECT title, ts_rank(search_vec, query) AS rank
FROM posts, to_tsquery('english', 'rate & limiting') query
WHERE search_vec @@ query
ORDER BY rank DESC
LIMIT 10;
```

FTS handles: typos (via stemming — "rates" matches "rate"), stopwords (ignores "the", "and"), and ranking (how many times a term appears, in title vs body).

FTS doesn't handle: semantic similarity. "connection pooling" won't match a document about "database proxies" unless those exact words appear.

## pgvector: semantic similarity

pgvector answers: "which documents are semantically similar to this query?"

```sql
-- Enable the extension
CREATE EXTENSION IF NOT EXISTS vector;

-- Add an embedding column (1536 dimensions for OpenAI text-embedding-3-small)
ALTER TABLE posts ADD COLUMN embedding vector(1536);

-- Create an IVFFlat index for approximate nearest neighbor
CREATE INDEX posts_embedding_idx ON posts
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);
```

```ts
// Generate embedding for the query (application side)
const response = await openai.embeddings.create({
  model: 'text-embedding-3-small',
  input: query,
});
const embedding = response.data[0].embedding;

// Find similar posts
const results = await db.execute(sql`
  SELECT title, 1 - (embedding <=> ${JSON.stringify(embedding)}::vector) AS similarity
  FROM posts
  WHERE embedding IS NOT NULL
  ORDER BY embedding <=> ${JSON.stringify(embedding)}::vector
  LIMIT 10
`);
```

The `<=>` operator is cosine distance. `1 - distance` is similarity. Documents with semantically similar meaning to your query score high even if they don't share keywords.

## When to use each

**Use FTS when:**
- Users are searching for specific terms, product names, error messages, or exact phrases
- You need fast, deterministic results with no external API dependency
- Your corpus is in a supported language and benefits from stemming

**Use pgvector when:**
- You want semantic search: "how do I prevent SQL injection" should match a document about "parameterised queries"
- Building a recommendation system ("posts similar to this one")
- AI-driven features: RAG (retrieval-augmented generation) for finding relevant context to give to Claude

**Use both:**
Hybrid search combines keyword precision with semantic recall:

```sql
-- Hybrid: FTS + vector similarity, re-ranked by weighted score
SELECT
  title,
  (ts_rank(search_vec, to_tsquery('english', $1)) * 0.3 +
   (1 - (embedding <=> $2::vector)) * 0.7) AS score
FROM posts
WHERE
  search_vec @@ to_tsquery('english', $1)
  OR (1 - (embedding <=> $2::vector)) > 0.7
ORDER BY score DESC
LIMIT 10;
```

FTS filters to keyword matches and semantically similar documents; the combined score re-ranks them. This gives better recall than FTS alone and better precision than vector alone.

## Embedding cost and latency

pgvector requires embedding your documents and your queries. Each embedding API call costs time and money.

**Embedding documents**: do this at insert/update time. Store the embedding in the database. One API call per document, amortised over all searches.

**Embedding queries**: happens at search time. OpenAI's text-embedding-3-small is 20ms at the p50. That's acceptable. Cache common query embeddings in Redis if you have high search volume.

**Cost**: `text-embedding-3-small` is $0.02 per million tokens. A Scoutr-sized corpus (10,000 documents, average 500 tokens each) costs $0.10 to embed completely. Re-embedding on content updates is marginal.

## Backfill strategy

If you're adding embeddings to an existing table:

```ts
// scripts/backfill-embeddings.ts
const posts = await db.select().from(posts).where(isNull(posts.embedding));

for (const post of posts) {
  const text = `${post.title} ${post.body}`;
  const response = await openai.embeddings.create({
    model: 'text-embedding-3-small',
    input: text.slice(0, 8191), // token limit
  });
  await db.update(posts)
    .set({ embedding: response.data[0].embedding })
    .where(eq(posts.id, post.id));

  await new Promise(r => setTimeout(r, 50)); // rate limit
}
```

Run this as a one-time migration. Keep the embedding updated with a trigger or application logic on each post update.

## What we use

Scoutr's journal search uses FTS — users are looking for specific topics, terms, and tool names. Exact keyword matching is what they want.

The Scoutr product catalog uses hybrid search — a user searching "tools for tracking inventory" should find products tagged "stock management" even if they don't overlap on keywords. pgvector finds the semantic match; FTS finds exact matches; the hybrid score combines both.
