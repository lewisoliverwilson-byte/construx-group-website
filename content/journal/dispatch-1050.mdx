title: "Rook-Ceph: cloud-native distributed storage — block, object, and file on Kubernetes"
date: "2033-07-30"
excerpt: "Rook is a Kubernetes operator that deploys and manages Ceph — a mature distributed storage system — inside a Kubernetes cluster. Ceph provides three storage primitives: block storage (RBD — RADOS Block Device, used as Kubernetes PersistentVolumes for databases and stateful workloads), object storage (RGW — RADOS Gateway, S3-compatible API), and file storage (CephFS — POSIX-compatible shared filesystem). Rook automates the lifecycle: cluster deployment, disk discovery and OSD provisioning, failure detection and recovery, pool resizing, and upgrades. Instead of running Ceph on separate storage nodes and managing it with cephadm, Rook makes Ceph a first-class Kubernetes workload — the cluster state is declared in CRDs, backups use Velero, and capacity is added by joining new nodes with available disks. The replication model is configurable per pool: 3x replication for critical data, erasure coding (EC:4:2 — 4 data chunks, 2 parity) for bulk storage with 50% overhead instead of 200%."

Ceph on Kubernetes. RBD block volumes. S3-compatible RGW. CephFS shared filesystem. OSD pools.

## CephCluster and pool configuration

```yaml
# CephCluster: declare the storage cluster via Rook CRD
apiVersion: ceph.rook.io/v1
kind: CephCluster
metadata:
  name: construx-storage
  namespace: rook-ceph
spec:
  cephVersion:
    image: quay.io/ceph/ceph:v18.2.0
    allowUnsupported: false
  dataDirHostPath: /var/lib/rook
  mon:
    count: 3
    allowMultiplePerNode: false
  mgr:
    count: 2
    modules:
      - name: pg_autoscaler
        enabled: true
      - name: dashboard
        enabled: true
  dashboard:
    enabled: true
    ssl: true
  network:
    provider: host   # use host networking for storage traffic — avoids CNI overhead
  storage:
    useAllNodes: false
    nodes:
      - name: storage-node-01
        devices:
          - name: nvme0n1
          - name: nvme1n1
      - name: storage-node-02
        devices:
          - name: nvme0n1
          - name: nvme1n1
      - name: storage-node-03
        devices:
          - name: nvme0n1
          - name: nvme1n1
  resources:
    osd:
      requests:
        cpu: 2
        memory: 4Gi
      limits:
        memory: 8Gi
---
# CephBlockPool: replicated pool for PersistentVolumes
apiVersion: ceph.rook.io/v1
kind: CephBlockPool
metadata:
  name: construx-block
  namespace: rook-ceph
spec:
  replicated:
    size: 3             # 3x replication — survive 2 OSD failures
    requireSafeReplicaSize: true
---
# Erasure-coded pool: bulk storage with 50% overhead (vs 200% for 3x replication)
apiVersion: ceph.rook.io/v1
kind: CephBlockPool
metadata:
  name: construx-bulk
  namespace: rook-ceph
spec:
  erasureCoded:
    dataChunks: 4
    codingChunks: 2     # EC:4:2 — tolerate 2 OSD failures, 1.5x overhead
---
# StorageClass: expose block pool as Kubernetes PersistentVolumes
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: rook-ceph-block
provisioner: rook-ceph.rbd.csi.ceph.com
parameters:
  clusterID: rook-ceph
  pool: construx-block
  imageFormat: "2"
  imageFeatures: layering,fast-diff,object-map,deep-flatten,exclusive-lock
  csi.storage.k8s.io/provisioner-secret-name: rook-csi-rbd-provisioner
  csi.storage.k8s.io/provisioner-secret-namespace: rook-ceph
  csi.storage.k8s.io/node-stage-secret-name: rook-csi-rbd-node
  csi.storage.k8s.io/node-stage-secret-namespace: rook-ceph
  csi.storage.k8s.io/fstype: ext4
reclaimPolicy: Retain
allowVolumeExpansion: true
```

## Object storage and CephFS

```yaml
# CephObjectStore: S3-compatible object storage (RGW)
apiVersion: ceph.rook.io/v1
kind: CephObjectStore
metadata:
  name: construx-object
  namespace: rook-ceph
spec:
  metadataPool:
    replicated:
      size: 3
  dataPool:
    erasureCoded:
      dataChunks: 4
      codingChunks: 2
  preservePoolsOnDelete: true
  gateway:
    port: 80
    securePort: 443
    instances: 2
    resources:
      requests:
        cpu: 500m
        memory: 1Gi
---
# StorageClass for object bucket claims (OBC)
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: rook-ceph-bucket
provisioner: rook-ceph.ceph.rook.io/bucket
reclaimPolicy: Delete
parameters:
  objectStoreName: construx-object
  objectStoreNamespace: rook-ceph
---
# ObjectBucketClaim: provision a bucket — like a PVC but for object storage
apiVersion: objectbucket.io/v1alpha1
kind: ObjectBucketClaim
metadata:
  name: construx-ml-data
  namespace: ml-workloads
spec:
  generateBucketName: construx-ml-data
  storageClassName: rook-ceph-bucket
  additionalConfig:
    maxSize: 500Gi
    maxObjects: "1000000"
---
# CephFilesystem: shared POSIX filesystem (ReadWriteMany PVs)
apiVersion: ceph.rook.io/v1
kind: CephFilesystem
metadata:
  name: construx-fs
  namespace: rook-ceph
spec:
  metadataPool:
    replicated:
      size: 3
  dataPools:
    - name: replicated
      replicated:
        size: 3
  preserveFilesystemOnDelete: true
  metadataServer:
    activeCount: 1
    activeStandby: true   # hot standby MDS for fast failover
```

Rook-Ceph vs MinIO vs Longhorn vs OpenEBS vs cloud storage: MinIO is object-only — no block volumes for PersistentVolumeClaims. Longhorn is block-only (replicates volumes at the block level across nodes) — simpler than Ceph but no object or file storage and lower throughput. OpenEBS has multiple engines (Jiva, cStor, LocalPV, Mayastor) — LocalPV is simple but no replication; Mayastor uses NVMe-oF for high-performance block storage. Rook-Ceph is the most capable self-hosted option: block (RBD), object (RGW/S3), and file (CephFS) from one system. The tradeoff is complexity: Ceph has a steep learning curve, CRUSH map tuning matters for performance, and PG (placement group) counts need to be sized correctly. For teams running Kubernetes on bare metal that need all three storage primitives without cloud vendor dependencies, Rook-Ceph is the production-proven choice. For teams on cloud, use managed services (EBS, S3, EFS) and save the operational complexity.
