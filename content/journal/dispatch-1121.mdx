date: "2034-02-28"
excerpt: "OPA Gatekeeper is the Kubernetes admission controller for Open Policy Agent — it enforces custom policies at admission time, before resources are persisted in etcd. Where Kyverno uses YAML-based rules, Gatekeeper uses Rego (OPA's policy language) defined in ConstraintTemplates, which are CRDs that compile Rego into a webhook policy. The constraint model separates the policy schema (ConstraintTemplate) from its configuration (Constraint): the K8sRequireResourceLimits template defines a policy that checks for CPU and memory limits; the K8sRequireResourceLimits constraint instantiates that template for the construx-prod namespace with specific parameters. Gatekeeper's audit controller continuously re-evaluates existing resources against constraints, surfacing violations that slipped in before a constraint was enforced — making it possible to enable enforcement on existing clusters without breaking them, by auditing first and remedying violations before switching to deny mode. Gatekeeper ships a library of pre-built ConstraintTemplates (the Gatekeeper Policy Library) covering common security policies: no privileged containers, no host path mounts, required labels, allowed container registries, no latest image tags. For Construx, Gatekeeper provides the preventative layer alongside Falco's detective layer: Gatekeeper blocks non-compliant resources at admission; Falco detects unexpected runtime behaviour after admission."

## Gatekeeper ConstraintTemplates and constraints

```yaml
# ConstraintTemplate: defines the policy schema and Rego logic
# This template enforces that all containers have resource limits set

apiVersion: templates.gatekeeper.sh/v1
kind: ConstraintTemplate
metadata:
  name: k8srequireresourcelimits
spec:
  crd:
    spec:
      names:
        kind: K8sRequireResourceLimits
      validation:
        openAPIV3Schema:
          type: object
          properties:
            allowedResources:
              type: array
              items:
                type: string

  targets:
    - target: admission.k8s.gatekeeper.sh
      rego: |
        package k8srequireresourcelimits

        violation[{"msg": msg}] {
          container := input.review.object.spec.containers[_]
          not container.resources.limits.cpu
          msg := sprintf("Container '%v' must have resources.limits.cpu set", [container.name])
        }

        violation[{"msg": msg}] {
          container := input.review.object.spec.containers[_]
          not container.resources.limits.memory
          msg := sprintf("Container '%v' must have resources.limits.memory set", [container.name])
        }

        # Also check initContainers
        violation[{"msg": msg}] {
          container := input.review.object.spec.initContainers[_]
          not container.resources.limits.cpu
          msg := sprintf("InitContainer '%v' must have resources.limits.cpu set", [container.name])
        }

---
# Constraint: instantiates the template for specific namespaces
# enforcementAction: deny (blocks admission), warn (warns but allows), dryrun (audit only)

apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sRequireResourceLimits
metadata:
  name: require-resource-limits
spec:
  enforcementAction: deny
  match:
    kinds:
      - apiGroups: [""]
        kinds: ["Pod"]
    namespaces:
      - construx-prod
      - construx-staging
    excludedNamespaces:
      - kube-system
      - gatekeeper-system
      - cert-manager
```

```yaml
# ConstraintTemplate: block privileged containers and hostPath mounts
# Combines multiple security checks in one template

apiVersion: templates.gatekeeper.sh/v1
kind: ConstraintTemplate
metadata:
  name: k8sdisallowprivileged
spec:
  crd:
    spec:
      names:
        kind: K8sDisallowPrivileged

  targets:
    - target: admission.k8s.gatekeeper.sh
      rego: |
        package k8sdisallowprivileged

        violation[{"msg": msg}] {
          container := input.review.object.spec.containers[_]
          container.securityContext.privileged == true
          msg := sprintf("Privileged container '%v' not allowed", [container.name])
        }

        violation[{"msg": msg}] {
          input.review.object.spec.hostNetwork == true
          msg := "hostNetwork: true is not allowed in this namespace"
        }

        violation[{"msg": msg}] {
          volume := input.review.object.spec.volumes[_]
          volume.hostPath
          msg := sprintf("hostPath volume '%v' not allowed", [volume.name])
        }

---
# ConstraintTemplate: allowed container registries
# Only images from ghcr.io/construx and gcr.io/distroless are permitted

apiVersion: templates.gatekeeper.sh/v1
kind: ConstraintTemplate
metadata:
  name: k8sallowedregistries
spec:
  crd:
    spec:
      names:
        kind: K8sAllowedRegistries
      validation:
        openAPIV3Schema:
          type: object
          properties:
            registries:
              type: array
              items:
                type: string

  targets:
    - target: admission.k8s.gatekeeper.sh
      rego: |
        package k8sallowedregistries

        violation[{"msg": msg}] {
          container := input.review.object.spec.containers[_]
          not any_allowed(container.image)
          msg := sprintf("Image '%v' not from an allowed registry", [container.image])
        }

        any_allowed(image) {
          allowed := input.parameters.registries[_]
          startswith(image, allowed)
        }

---
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sAllowedRegistries
metadata:
  name: allowed-registries
spec:
  enforcementAction: deny
  match:
    kinds: [{apiGroups: [""], kinds: ["Pod"]}]
    namespaces: [construx-prod, construx-staging]
  parameters:
    registries:
      - ghcr.io/construx/
      - gcr.io/distroless/
      - registry.k8s.io/
      - quay.io/prometheus/
```

```bash
# Gatekeeper audit: review existing violations

# List all constraints with violation counts
kubectl get constraints -A -o json | \
  jq '.items[] | {name: .metadata.name, violations: (.status.totalViolations // 0)}'

# Show detailed violations for a specific constraint
kubectl describe k8srequireresourcelimits require-resource-limits

# Output:
# Status:
#   Total Violations: 0
#   Violations:       (none)

# Audit report: all violations across all constraints
kubectl get k8srequireresourcelimits,k8sdisallowprivileged,k8sallowedregistries \
  -A -o json | \
  jq '.items[].status.violations[]? |
    {constraint: .resource, namespace: .namespace, message: .message}'

# Test a constraint with conftest (before applying to cluster)
conftest test deployment.yaml \
  --policy gatekeeper-policies/ \
  --namespace gatekeeper

# Mutation: Gatekeeper can also mutate objects (add labels, set defaults)
# AssignMetadata mutator: add required labels to all pods missing them
kubectl apply -f - <<EOF
apiVersion: mutations.gatekeeper.sh/v1
kind: AssignMetadata
metadata:
  name: add-construx-labels
spec:
  match:
    scope: Namespaced
    kinds: [{apiGroups: ["*"], kinds: ["Pod"]}]
    namespaces: [construx-prod]
  location: "metadata.labels.managed-by"
  parameters:
    assign:
      value: "construx-platform"
EOF
```

Gatekeeper vs Kyverno vs Pod Security Admission vs custom webhooks: Kyverno (dispatch-1097) uses YAML-based rules rather than Rego — it is significantly more approachable for platform engineers without a policy-as-code background, and its generate and mutate capabilities are more ergonomic. Gatekeeper's Rego is more expressive for complex conditions (multi-resource joins, mathematical constraints, external data via OPA's data document), but harder to write and test. Pod Security Admission (PSA) is Kubernetes' built-in alternative — it enforces three hardcoded profiles (privileged, baseline, restricted) with no customisation. PSA covers the most common security requirements (no privileged containers, no hostPath, seccomp defaults) but cannot enforce custom policies like required labels or allowed registries. Custom admission webhooks give you complete control but require building and maintaining a webhook server. The practical choice: Kyverno for teams that prioritise ergonomics and want policy-as-code without learning Rego; Gatekeeper for teams with existing OPA investment or that need Rego's expressiveness for complex multi-resource policies. At Construx, both run together: Kyverno handles image signing verification and network policy generation; Gatekeeper handles security baseline enforcement where its audit capabilities and Rego precision are valuable.
