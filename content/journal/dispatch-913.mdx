title: "WireGuard: modern VPN with minimal attack surface and kernel integration"
date: "2032-06-14"
excerpt: "WireGuard is a VPN protocol and Linux kernel module that uses Curve25519 for key exchange, ChaCha20-Poly1305 for encryption, and BLAKE2s for hashing — a cryptographic stack with no legacy algorithm options, no negotiation surface, and no configuration knobs that could be set insecurely. WireGuard is 4,000 lines of code (versus OpenVPN's 100,000+), integrated into the Linux kernel since 5.6, and achieves better throughput than both OpenVPN and IPsec while being simpler to configure. The peer model — every peer is just a public key with allowed IPs — scales from two-machine tunnels to hub-and-spoke mesh networks."

Generate keys. Exchange public keys out-of-band. Add peers. Done.

## Key generation and basic tunnel

```bash
# Install WireGuard
apt install wireguard          # Debian/Ubuntu
brew install wireguard-tools   # macOS (userspace only)

# Generate a keypair (each peer needs one)
wg genkey | tee server-private.key | wg pubkey > server-public.key
wg genkey | tee client-private.key | wg pubkey > client-public.key

cat server-public.key
# uRk4JCH4a3K2oKn7XbHxG5RQZA2SJ8mLPt3YvHdE9Wc=

cat client-public.key
# 7Xv8Qw4mN1bKzJ6L3oR0pT5hY2aF9eD8cS4uM7nB1k0=

# Optional: preshared key for an additional symmetric layer (post-quantum defence)
wg genpsk > shared.psk

# Server configuration (/etc/wireguard/wg0.conf)
cat > /etc/wireguard/wg0.conf << 'EOF'
[Interface]
Address = 10.10.0.1/24
ListenPort = 51820
PrivateKey = <server-private-key>
PostUp = iptables -A FORWARD -i wg0 -j ACCEPT; iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
PostDown = iptables -D FORWARD -i wg0 -j ACCEPT; iptables -t nat -D POSTROUTING -o eth0 -j MASQUERADE

[Peer]
# construx-dev — Lewis's laptop
PublicKey = 7Xv8Qw4mN1bKzJ6L3oR0pT5hY2aF9eD8cS4uM7nB1k0=
PresharedKey = <preshared-key>
AllowedIPs = 10.10.0.2/32
EOF

# Client configuration
cat > /etc/wireguard/wg0.conf << 'EOF'
[Interface]
Address = 10.10.0.2/24
PrivateKey = <client-private-key>
DNS = 1.1.1.1

[Peer]
# construx-vpn-gateway
PublicKey = uRk4JCH4a3K2oKn7XbHxG5RQZA2SJ8mLPt3YvHdE9Wc=
PresharedKey = <preshared-key>
Endpoint = vpn.construx.io:51820
AllowedIPs = 10.10.0.0/24, 10.0.0.0/8   # Route private RFC1918 through VPN
PersistentKeepalive = 25                  # Keep NAT mapping alive for mobile clients
EOF

# Bring up the interface
wg-quick up wg0

# Verify
wg show
# interface: wg0
#   public key: uRk4JCH4a3K2oKn7XbHxG5RQZA2SJ8mLPt3YvHdE9Wc=
#   private key: (hidden)
#   listening port: 51820
#
# peer: 7Xv8Qw4mN1bKzJ6L3oR0pT5hY2aF9eD8cS4uM7nB1k0=
#   endpoint: 93.184.216.34:41827
#   allowed ips: 10.10.0.2/32
#   latest handshake: 14 seconds ago
#   transfer: 14.82 MiB received, 2.14 MiB sent
```

## Hub-and-spoke mesh for Kubernetes nodes

```bash
# Scenario: private Kubernetes cluster across 3 availability zones
# Each node needs a WireGuard tunnel to every other node (mesh)
# OR: use a hub-and-spoke model with one gateway node

# Hub node (runs in eu-west-1a, routes between AZs)
cat > /etc/wireguard/wg0.conf << 'EOF'
[Interface]
Address = 10.20.0.1/24
ListenPort = 51820
PrivateKey = <hub-private-key>

# Node in eu-west-1b
[Peer]
PublicKey = <node-b-public-key>
AllowedIPs = 10.20.0.2/32, 10.0.1.0/24   # Node B's WireGuard IP + its pod CIDR

# Node in eu-west-1c
[Peer]
PublicKey = <node-c-public-key>
AllowedIPs = 10.20.0.3/32, 10.0.2.0/24   # Node C's WireGuard IP + its pod CIDR
EOF

# Spoke node (eu-west-1b) — only talks to hub, hub routes to other spokes
cat > /etc/wireguard/wg0.conf << 'EOF'
[Interface]
Address = 10.20.0.2/24
ListenPort = 51820
PrivateKey = <node-b-private-key>

[Peer]
# Hub
PublicKey = <hub-public-key>
Endpoint = 10.0.0.1:51820   # Hub's real IP (within VPC)
AllowedIPs = 10.20.0.0/24, 10.0.0.0/24   # All WireGuard IPs + hub's pod CIDR
PersistentKeepalive = 25
EOF

# Kubernetes: use wg-quick via systemd for auto-start
systemctl enable wg-quick@wg0
systemctl start wg-quick@wg0

# Verify cross-node connectivity
ping 10.20.0.3    # Ping node C through the hub
wg show wg0 transfer
```

## Dynamic peer management and monitoring

```bash
# Add a peer without restarting (zero-downtime peer addition)
wg set wg0 peer <new-public-key> \
  preshared-key /etc/wireguard/new-peer.psk \
  allowed-ips 10.10.0.10/32 \
  endpoint new-peer.construx.io:51820

# Remove a peer
wg set wg0 peer <public-key> remove

# Save the current running config (useful after dynamic changes)
wg-quick save wg0
# Overwrites /etc/wireguard/wg0.conf with current state

# Monitor: watch handshake freshness (>180s = peer may be unreachable)
watch -n 5 'wg show all dump'
# wg0  <public-key>  <endpoint>  10.10.0.2/32  1748592007  38241  2847192  25

# Alert if any peer handshake is stale (>3 minutes)
wg show wg0 dump | awk '$5 > 0 && (systime() - $5) > 180 {
  printf "STALE PEER: %s last handshake %ds ago\n", $1, systime()-$5
}'

# Bandwidth stats per peer
wg show wg0 transfer
# <public-key>   1234567 bytes received, 7654321 bytes sent

# Prometheus exporter for WireGuard (prometheus-wireguard-exporter)
wireguard_exporter --verbose
# Exposes: wireguard_peer_last_handshake_seconds, wireguard_peer_received_bytes_total
```

WireGuard vs OpenVPN vs IPsec: OpenVPN is TLS-based and runs in userspace — flexible, audited, but slower (kernel/userspace context switches on every packet) and configuration-heavy. IPsec is kernel-native and fast but notoriously complex to configure: IKEv2, XFRM policies, connection tracking exceptions for encapsulated traffic. WireGuard is kernel-native (kernel module, no userspace overhead), simpler than either (a WireGuard config is 15 lines vs hundreds for IPsec), and faster in benchmarks (~3.5 Gbps on a 4-core VM vs ~1.5 Gbps for IPsec). The limitation: WireGuard is transport-only — no built-in user authentication, no certificate revocation, no access control beyond allowed IPs. For enterprise VPN with user auth, layer WireGuard with a control plane (Tailscale, Headscale, or Netbird) that handles key distribution, user identity, and device management.
