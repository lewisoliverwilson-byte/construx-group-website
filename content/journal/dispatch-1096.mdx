excerpt: "Prometheus recording rules pre-compute expensive PromQL expressions into new time series, making dashboards and alert evaluations fast even over long query ranges. Alerting rules define conditions that trigger Prometheus to fire an alert to Alertmanager, which routes it to PagerDuty, Slack, or on-call systems. The production alerting pattern for SLOs is the multi-window burn rate alert: instead of alerting on raw error rate (which generates too many false positives for transient spikes), you alert when the error budget consumption rate is high enough to exhaust the 30-day budget within a meaningful window. Google's SRE Workbook defines two canonical burn rate windows for SLO alerts: a fast burn (2% of budget consumed in 1 hour, which projects to full exhaustion in ~2 days) and a slow burn (5% of budget consumed in 6 hours, which catches sustained lower-rate degradation). The alert fires only when both a short window and a long window agree — the short window gives sensitivity, the long window prevents alerting on brief transient spikes. Recording rules pre-compute the error rate at each window so the multi-window alert expression is a simple numeric comparison rather than a complex nested PromQL expression evaluated at every scrape interval."

## Recording rules and SLO alert configuration

```yaml
# Prometheus rules file: SLO recording rules + burn rate alerts
# Applied via kube-prometheus-stack PrometheusRule CRD

apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: construx-slo-rules
  namespace: monitoring
  labels:
    prometheus: kube-prometheus
    role: alert-rules
spec:
  groups:

    # --- Recording rules: pre-compute error ratios at multiple windows ---
    - name: construx_slo_recording
      interval: 30s
      rules:
        # Total request rate (success + error)
        - record: job:http_requests_total:rate5m
          expr: |
            sum by (job, namespace) (
              rate(http_requests_total{namespace="construx-prod"}[5m])
            )

        - record: job:http_requests_total:rate1h
          expr: |
            sum by (job, namespace) (
              rate(http_requests_total{namespace="construx-prod"}[1h])
            )

        - record: job:http_requests_total:rate6h
          expr: |
            sum by (job, namespace) (
              rate(http_requests_total{namespace="construx-prod"}[6h])
            )

        # Error rate (5xx responses)
        - record: job:http_errors_total:rate5m
          expr: |
            sum by (job, namespace) (
              rate(http_requests_total{namespace="construx-prod", status=~"5.."}[5m])
            )

        - record: job:http_errors_total:rate1h
          expr: |
            sum by (job, namespace) (
              rate(http_requests_total{namespace="construx-prod", status=~"5.."}[1h])
            )

        - record: job:http_errors_total:rate6h
          expr: |
            sum by (job, namespace) (
              rate(http_requests_total{namespace="construx-prod", status=~"5.."}[6h])
            )

        # Error ratio at each window
        - record: job:http_error_ratio:rate5m
          expr: |
            job:http_errors_total:rate5m
            /
            job:http_requests_total:rate5m

        - record: job:http_error_ratio:rate1h
          expr: |
            job:http_errors_total:rate1h
            /
            job:http_requests_total:rate1h

        - record: job:http_error_ratio:rate6h
          expr: |
            job:http_errors_total:rate6h
            /
            job:http_requests_total:rate6h

    # --- Alerting rules: multi-window SLO burn rate ---
    # SLO target: 99.9% availability (0.1% error budget, ~43 min/month)
    - name: construx_slo_alerts
      rules:

        # Fast burn: 14.4× burn rate in 1h and 5m windows
        # At 14.4× rate: 100% of budget consumed in ~2 days
        # 1 - 0.999 = 0.001 budget; 14.4 × 0.001 = 0.0144 error ratio
        - alert: SLOFastBurn
          expr: |
            (
              job:http_error_ratio:rate1h > (14.4 * 0.001)
              and
              job:http_error_ratio:rate5m > (14.4 * 0.001)
            )
          for: 2m
          labels:
            severity: critical
            slo: availability
          annotations:
            summary: "Fast SLO burn: {{ $labels.job }} error rate {{ $value | humanizePercentage }}"
            description: "Error rate exceeds 14.4× burn rate in both 1h and 5m windows. Budget exhaustion in ~2 days at this rate."
            runbook_url: "https://runbooks.construx.internal/slo-fast-burn"

        # Slow burn: 6× burn rate in 6h and 30m windows
        # 6 × 0.001 = 0.006 error ratio, sustained over 6h
        - alert: SLOSlowBurn
          expr: |
            (
              job:http_error_ratio:rate6h > (6 * 0.001)
              and
              job:http_error_ratio:rate1h > (6 * 0.001)
            )
          for: 15m
          labels:
            severity: warning
            slo: availability
          annotations:
            summary: "Slow SLO burn: {{ $labels.job }} sustained elevated error rate"
            description: "Error rate exceeds 6× burn rate sustained over 6h window. Budget will exhaust before end of month."

        # Latency SLO: 95th percentile < 200ms
        - alert: SLOLatencyBudgetBurn
          expr: |
            histogram_quantile(0.95,
              sum by (job, le) (
                rate(http_request_duration_seconds_bucket{namespace="construx-prod"}[5m])
              )
            ) > 0.200
          for: 5m
          labels:
            severity: warning
            slo: latency
          annotations:
            summary: "Latency SLO breach: {{ $labels.job }} p95={{ $value | humanizeDuration }}"
```

Multi-window burn rate vs simple threshold alerting vs error budget step function: Simple threshold alerting ("alert if error rate > 1% for 5 minutes") has two failure modes: it is too sensitive (a 10-second spike fires an alert) and too insensitive (a sustained 0.5% error rate slowly burns the budget without alerting). The multi-window burn rate alert fixes both: the short window (5m or 1h) provides sensitivity to detect real incidents fast; the AND with a longer window (1h or 6h) eliminates false positives from transient spikes. The burn rate multiplier ties the alert directly to the SLO budget: a 14.4× burn rate at a 0.1% error budget means you will exhaust the 30-day budget in 2 days, which is clearly page-worthy. A 6× burn rate will exhaust the budget in ~5 days — worth a warning-level alert to investigate. Error budget step functions (alert once 10% of budget is consumed, again at 50%) are an alternative approach that works well for low-traffic services where rate-based windows are noisy. For high-traffic APIs where Prometheus has enough data points for meaningful rate calculations, multi-window burn rate alerts are the standard.
