The pattern appears in all three products:

- Scoutr: a user scans a product URL; the scan takes 2-4 seconds (eBay API calls, sold data fetching, confidence score calculation). The user is staring at a loading spinner.
- The Hyve: a user @mentions the AI agent; the response takes 3-8 seconds (embedding the query, RAG retrieval, Claude API call). The user is waiting.
- The Marqet: a seller submits a listing; the submission triggers content moderation, embedding generation, and category enrichment. The page hangs for 2+ seconds.

These are all background work masquerading as synchronous API calls. The fix is a job queue: accept the work, return immediately, process in the background, deliver the result when ready.

## The job queue options

At our scale, three serious choices:

**1. Database-backed queue (DIY):** Use a `jobs` table in PostgreSQL. Workers poll for new jobs with `SELECT ... FOR UPDATE SKIP LOCKED`. Simple, no new infrastructure, uses the database you already have.

**2. Redis-backed queue:** BullMQ (Node.js) uses Redis as the queue backend. More sophisticated than database polling — supports priorities, delays, retries with backoff, concurrency limits, and a dashboard (Bull Board).

**3. Cloud queue:** AWS SQS, Google Cloud Tasks. Fully managed, high durability, scales to any volume. More complex to operate, more expensive at low volume.

We chose BullMQ with Redis. We already run Redis for rate limiting and caching. BullMQ's feature set is sufficient, and the operational complexity of adding SQS isn't justified at our scale.

## The implementation

Queue definition and producer:

```ts
import { Queue, QueueEvents } from 'bullmq';

const connection = { host: process.env.REDIS_HOST, port: 6379 };

export const scanQueue = new Queue('product-scans', { connection });
export const aiQueue = new Queue('ai-requests', { connection });
export const moderationQueue = new Queue('content-moderation', { connection });

// Producer: add job when user submits a scan
export async function enqueueScan(scanId: string, sourceUrl: string, userId: string) {
  const job = await scanQueue.add(
    'scan-product',
    { scanId, sourceUrl, userId },
    {
      attempts: 3,
      backoff: { type: 'exponential', delay: 2000 },
      removeOnComplete: { age: 3600 },   // Keep completed jobs for 1h
      removeOnFail: { age: 86400 },      // Keep failed jobs for 24h
    }
  );
  return job.id;
}
```

Worker:

```ts
import { Worker } from 'bullmq';

const scanWorker = new Worker(
  'product-scans',
  async (job) => {
    const { scanId, sourceUrl, userId } = job.data as {
      scanId: string;
      sourceUrl: string;
      userId: string;
    };

    // Update progress so the client can poll it
    await job.updateProgress(10);
    const listingData = await fetchEbayListing(sourceUrl);

    await job.updateProgress(40);
    const soldData = await fetchSoldListings(listingData.title);

    await job.updateProgress(70);
    const margin = calculateMargin(listingData, soldData);
    const confidence = computeConfidenceScore(listingData, soldData, margin);

    await job.updateProgress(90);
    await db.update(scans).set({
      status: 'complete',
      margin,
      confidence,
      result: { listingData, soldData, margin, confidence },
      completedAt: new Date(),
    }).where(eq(scans.id, scanId));

    await job.updateProgress(100);
    return { scanId, margin, confidence };
  },
  { connection, concurrency: 5 }
);

scanWorker.on('failed', async (job, err) => {
  if (!job) return;
  const { scanId } = job.data as { scanId: string };
  await db.update(scans).set({ status: 'failed', error: err.message })
    .where(eq(scans.id, scanId));
});
```

## The API route pattern

The route that accepts scan submissions now returns immediately:

```ts
// Before: synchronous (hangs for 2-4 seconds)
export async function POST(req: Request) {
  const { sourceUrl } = await req.json();
  const result = await runFullScan(sourceUrl);  // BLOCKS
  return Response.json(result);
}

// After: async (returns in <50ms)
export async function POST(req: Request) {
  const { sourceUrl } = await req.json();
  const scanId = crypto.randomUUID();
  
  await db.insert(scans).values({ id: scanId, sourceUrl, status: 'queued' });
  await enqueueScan(scanId, sourceUrl, session.userId);
  
  return Response.json({ scanId, status: 'queued' });
}

// New: poll for status
export async function GET(req: Request) {
  const scanId = new URL(req.url).searchParams.get('id');
  const scan = await db.query.scans.findFirst({ where: eq(scans.id, scanId!) });
  return Response.json(scan);
}
```

The client polls `/api/scans?id=${scanId}` every 500ms until status is `complete` or `failed`. Polling is simple and works — for Scoutr's scan workflow (2-4 seconds), the UX is: immediate feedback ("scan queued"), then progressive updates as the scan runs.

## The progress update pattern

BullMQ's `job.updateProgress(n)` allows the client to track scan progress. We combine polling with the progress field:

```ts
// Client
async function pollScanStatus(scanId: string): Promise<ScanResult> {
  while (true) {
    const res = await fetch(`/api/scans?id=${scanId}`);
    const scan = await res.json();
    
    // Update progress bar
    setScanProgress(scan.progress ?? 0);
    
    if (scan.status === 'complete') return scan.result;
    if (scan.status === 'failed') throw new Error(scan.error);
    
    await new Promise((r) => setTimeout(r, 500));
  }
}
```

The progress bar moves from 0% to 100% as the worker advances through stages. This is meaningfully better UX than an indeterminate spinner — the user can see that work is happening.

## Retries and dead letter queues

BullMQ retries failed jobs with exponential backoff by default. After `attempts` are exhausted, the job moves to the `failed` state. We have a daily job that reviews failed jobs and alerts us if more than 5% of scans are failing (indicating a systemic problem with an external API).

Dead letter handling:

```ts
scanWorker.on('failed', async (job, err) => {
  if (!job) return;
  const isExhausted = job.attemptsMade >= (job.opts.attempts ?? 1);
  if (isExhausted) {
    await alerting.notify({
      level: 'warning',
      message: `Scan job ${job.id} exhausted retries: ${err.message}`,
    });
  }
});
```

## The operational complexity

Adding BullMQ means:
- Redis must be highly available (we use Redis managed on Railway, same as our rate limit Redis)
- Workers must be running (we deploy them as separate processes alongside the Next.js server)
- Failed jobs must be monitored (the alert above covers this)
- The job queue state should be observable (Bull Board provides a UI dashboard)

For the simplest alternative (database-backed queue), the operational overhead is lower — no extra infrastructure. The trade-off: polling-based database queues have higher latency (workers poll on a schedule rather than reacting to events) and less feature richness (no built-in priorities, delay scheduling).

We'd use a database queue for low-volume, non-latency-sensitive work. For Scoutr's scans (real-time, user-facing) and The Hyve's AI responses (streaming, time-sensitive), BullMQ's reaction time and feature set justify the operational complexity.
