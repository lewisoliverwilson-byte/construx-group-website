date: "2033-08-11"
excerpt: "Dagger is a programmable CI/CD engine that runs pipelines as code in a containerised execution environment. Instead of writing YAML pipeline definitions tied to a specific CI system (GitHub Actions, CircleCI, GitLab CI), you write a Dagger function in Go, TypeScript, or Python — and that function runs identically on your laptop, in GitHub Actions, in a Kubernetes Job, or on any machine with Docker. The key property is cache correctness: Dagger computes a content-addressed cache key for every function input (source files, environment variables, base images), so steps are only re-executed when their inputs change. If your test step passes locally with the same source hash, it passes in CI — no 'works locally but fails in CI' divergence. Dagger functions are composed: a function can call other functions (build → test → push → deploy), and each step gets its own cache layer. The Dagger Cloud dashboard shows a visual DAG of your pipeline with cache hit/miss rates and timing per step."

Containerised functions. Content-addressed cache. SDK in Go/TS/Python. Portable execution.

## Dagger functions in TypeScript

```typescript
// dagger.ts: Dagger pipeline for the construx-api service
// Runs identically locally and in CI

import { dag, Container, Directory, Secret, object, func } from "@dagger.io/dagger";

@object()
class ConstruxApi {
    // Build: compile the Go binary in a containerised environment
    @func()
    async build(source: Directory): Promise<Container> {
        return dag
            .container()
            .from("golang:1.23-alpine")
            .withDirectory("/src", source, { exclude: ["**/.git"] })
            .withWorkdir("/src")
            .withMountedCache("/go/pkg/mod", dag.cacheVolume("go-mod"))   // cached module download
            .withMountedCache("/root/.cache/go-build", dag.cacheVolume("go-build"))
            .withExec(["go", "build", "-o", "/app/construx-api", "./cmd/api"])
            .withWorkdir("/app");
    }

    // Test: run tests with race detector
    @func()
    async test(source: Directory): Promise<string> {
        return dag
            .container()
            .from("golang:1.23-alpine")
            .withDirectory("/src", source, { exclude: ["**/.git"] })
            .withWorkdir("/src")
            .withMountedCache("/go/pkg/mod", dag.cacheVolume("go-mod"))
            .withServiceBinding("postgres", this.testDatabase())   // spin up a real Postgres
            .withEnvVariable("DATABASE_URL", "postgresql://test:test@postgres:5432/test")
            .withExec(["go", "test", "-race", "-count=1", "./..."])
            .stdout();
    }

    // Lint: run golangci-lint
    @func()
    async lint(source: Directory): Promise<string> {
        return dag
            .container()
            .from("golangci/golangci-lint:v1.61-alpine")
            .withDirectory("/src", source, { exclude: ["**/.git"] })
            .withWorkdir("/src")
            .withMountedCache("/root/.cache", dag.cacheVolume("golangci-lint"))
            .withExec(["golangci-lint", "run", "--timeout", "5m"])
            .stdout();
    }

    // Publish: build Docker image and push to registry
    @func()
    async publish(
        source:         Directory,
        registryUser:   string,
        registryPass:   Secret,
        imageTag:       string,
    ): Promise<string> {
        const built = await this.build(source);
        return dag
            .container()
            .from("gcr.io/distroless/static-debian12")
            .withFile("/app/construx-api", built.file("/app/construx-api"))
            .withEntrypoint(["/app/construx-api"])
            .withRegistryAuth("registry.construx.internal", registryUser, registryPass)
            .publish(`registry.construx.internal/construx/api:${imageTag}`);
    }

    // Pipeline: lint → test → build → publish (sequential, cached per step)
    @func()
    async pipeline(source: Directory, registryUser: string, registryPass: Secret): Promise<string> {
        await this.lint(source);
        await this.test(source);
        return this.publish(source, registryUser, registryPass, await source.digest());
    }

    // Test database service: runs as a sidecar during tests
    private testDatabase(): Container {
        return dag
            .container()
            .from("postgres:16-alpine")
            .withEnvVariable("POSTGRES_USER", "test")
            .withEnvVariable("POSTGRES_PASSWORD", "test")
            .withEnvVariable("POSTGRES_DB", "test")
            .withExposedPort(5432);
    }
}
```

## Running locally and in CI

```bash
# Dagger CLI

# Install Dagger
curl -L https://dl.dagger.io/dagger/install.sh | sh

# Run a specific function (downloads and caches module dependencies, runs in Docker)
dagger call lint --source .

# Run tests
dagger call test --source .
# [0.72s] go: downloading dependencies
# [12.4s] Test run complete: 148 tests passed, 0 failed

# Full pipeline with registry push
dagger call pipeline \
  --source . \
  --registry-user construx-ci \
  --registry-pass env:REGISTRY_PASSWORD

# Dagger Cloud: upload traces for visibility
DAGGER_CLOUD_TOKEN=dctk_xxx dagger call pipeline \
  --source . \
  --registry-user construx-ci \
  --registry-pass env:REGISTRY_PASSWORD
# Dashboard: https://dagger.cloud/org/construx/traces/run_abc123

# Pipeline trace output:
# ✔  lint (2.1s, cache hit for go-mod)
# ✔  test (18.4s, real postgres sidecar)
#    ✔  go test ./...  → 148 passed
# ✔  build (0.3s, cache hit — source unchanged)
# ✔  publish (4.2s) → registry.construx.internal/construx/api:sha256:abc123

# GitHub Actions integration: just call dagger
# .github/workflows/ci.yaml
# - name: Run Dagger pipeline
#   uses: dagger/dagger-for-github@v6
#   with:
#     verb: call
#     args: pipeline --source . --registry-user $REGISTRY_USER --registry-pass env:REGISTRY_PASSWORD
#   env:
#     REGISTRY_PASSWORD: ${{ secrets.REGISTRY_PASSWORD }}
#     DAGGER_CLOUD_TOKEN: ${{ secrets.DAGGER_CLOUD_TOKEN }}

# Same command in CircleCI, GitLab CI, Jenkins — the pipeline is in code, not YAML
```

## Module composition and reuse

```typescript
// Compose Dagger modules: reuse across services
// construx-shared/main.go published as a Dagger module

// In any service: import the shared construx module
// dagger.json:
// {
//   "dependencies": [
//     {"source": "github.com/construx/dagger-modules/go-service@v1.2.0"}
//   ]
// }

// Then call functions from the shared module
// dagger call go-service lint --source .
// dagger call go-service test --source . --db-image postgres:16
// dagger call go-service publish --source . --image construx/api:latest
```

Dagger vs GitHub Actions YAML vs Makefile + Docker vs Earthly: GitHub Actions YAML pipelines run only in GitHub Actions — you can't run them locally to debug CI failures, and the YAML syntax limits expressiveness. Makefile + Docker is portable and simple but has no cache layer management, no service composition API, and no DAG of dependencies. Earthly is similar to Dagger (container-native builds, local/CI parity) but uses an Earthfile syntax similar to Makefile with FROM/RUN — less flexible than a full programming language. Dagger's advantage is that the pipeline is real code: you get type checking, unit-testable functions, IDE support, and the ability to import third-party Dagger modules. The cache is content-addressed and shared across runs (locally and in CI if you use Dagger Cloud). The tradeoff: Dagger adds a binary dependency and the execution model (everything in containers) means initial runs are slower than native CI steps. For teams that want portable, testable, composable CI pipelines that work identically on developer laptops and in CI, Dagger is the right abstraction.
