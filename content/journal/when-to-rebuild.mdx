Every product eventually reaches a point where the original architecture is fighting you. The features you want to add require working around decisions that made sense at the start but constrain you now. The question becomes: iterate on what exists, or rebuild?

Rebuilds are seductive. None of the old constraints. None of the decisions you regret. A clean start where you know everything you didn't know when you started.

They're also expensive, disruptive, and often produce a new product with different problems rather than better solutions to the old ones. We've made both calls across our products and developed a framework for thinking about it.

## The case for iteration

Iteration preserves what's working. If users are engaged, if the core value proposition is validated, if the existing code is at least partially sound — rebuilding discards real value to fix problems that might be solved more cheaply.

The case for iteration is strongest when:

**The core architecture is sound but a specific component is problematic.** You can replace a database, refactor a data model, or rewrite a module without rewriting the whole system. Surgical replacement is almost always cheaper than total rebuild.

**Users are active and dependent on the product.** A rebuild introduces a migration cost for existing users. If you have users who are getting value, you owe them continuity. You can rebuild incrementally without breaking what they depend on.

**The problems are well understood.** You know specifically what needs to change. A rebuild is most efficient when you're translating clear requirements into clean implementation. If the requirements are still evolving, a rebuild produces a new version of the same uncertainty.

## The case for rebuild

Rebuilds are the right call when the architecture itself is the constraint on the value you can deliver.

We rebuilt parts of The Hyve's document collaboration system. The original implementation stored documents as single markdown strings with a simple locking mechanism. When we needed to support concurrent editing — multiple users editing the same document — the single-string model couldn't accommodate it without substantial workaround.

The question we asked: can we evolve the existing model to support concurrent editing, or does concurrent editing require a fundamentally different data structure? The answer was the latter. Block-based document storage requires a different schema, different APIs, and different client-side rendering. These changes weren't additive — they required replacing the existing system.

The case for rebuild is strongest when:

**The data model is wrong.** Data model changes are the most expensive to make incrementally. If the fundamental shape of your data is wrong for the product you need to build, changing it incrementally is usually more expensive than a clean rebuild.

**You're accumulating workarounds faster than you're shipping features.** Every workaround adds complexity. When workarounds start requiring their own workarounds, the cost of each new feature is growing faster than the features themselves. The compounding complexity is a signal.

**The user experience requires a fundamentally different flow.** UX changes that require rethinking the main workflow are hard to do incrementally — you're asking users to adjust to a changing product while you evolve it. Sometimes a clean launch is better than a gradual transition.

## The decision test

Before committing to a rebuild, we ask three questions:

**What specifically can't we build in the current architecture?** This needs to be concrete. "The code is messy" is not an answer. "We can't support real-time collaborative editing because documents are stored as single strings" is an answer.

**Can we achieve the same outcome by replacing a component rather than rebuilding the whole?** Scoped rebuilds are almost always available as an alternative to total rebuilds. Identify the minimum scope that solves the problem.

**What do we lose by rebuilding?** User state, integrations, established workflows, existing code that works well. Rebuilds destroy more than just the bad decisions — they destroy the good ones too.

## The iteration trap

There's an iteration failure mode as well. Products that accumulate technical debt fast enough eventually reach a state where iterating is slower than rebuilding. You spend more time maintaining workarounds than shipping features. Each new feature requires understanding a web of constraints that shouldn't exist.

The signal: the time from decision to shipped feature is growing, even for simple changes. If adding a new field to a form takes days because of the layers of state management, something is wrong.

When the iteration trap closes, the rebuild decision becomes obvious — not because rebuilding is appealing, but because the alternative is no longer viable.

## What we'd tell ourselves

The mistake we've made most often is rebuilding too early. Early product code is often messy in ways that don't actually constrain the next stage of development. Rewriting it before knowing what the next stage requires produces clean code for the wrong product.

The second-most-common mistake: iterating too long after the architecture had become the binding constraint. The decision to rebuild Scoutr's output rendering system should have come earlier — we spent two months adding features that worked against the grain of the original design before acknowledging the rebuild was necessary.

The honest test: are the problems you're solving with the rebuild problems that the current users are experiencing, or problems that make development harder? If the rebuild benefits developers more than users, iterate.
