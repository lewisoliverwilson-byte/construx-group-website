This website, Scoutr, The Marqet, and The Hyve were all built primarily with Claude Code. We're not using it for autocomplete or to fill in boilerplate. We're using it for architecture decisions, complex implementations, debugging, and refactoring.

Here's what's actually different about this way of working.

## The context advantage

The most significant shift is in how you carry context across sessions. With conventional development, everything lives in your head or in documentation: why you made a decision, what alternatives you considered, what constraints shaped the implementation. When you come back to code six weeks later, you're reconstructing.

With Claude Code, you can describe the context explicitly — the history of the problem, what you've tried, what the constraints are — and the model has that context during the session. The quality of the model's output scales with the quality of the context you provide.

This changes how you think about working. Writing good context at the start of a session — "we're building X, the relevant constraint is Y, we previously tried Z which didn't work because..." — is now a productive investment rather than documentation overhead.

## Design before implementation

The temptation with a capable coding assistant is to jump to implementation: "write me a component that does X." The resulting code is often correct but not necessarily the right abstraction.

The workflow that produces better results: design before implementation. Describe what you need to build, ask for the design to be reasoned through, agree on the approach, then implement.

"I need a command palette that searches journal posts. Help me think through the right data flow for this given that the post data is server-side and the component needs to be client-side." → design discussion → "Now implement it based on that design."

This produces implementations that fit the surrounding architecture better than prompting directly for code. The design step takes five minutes and saves debugging time.

## Specificity in requests

"Improve this component" produces marginal results. "Refactor this component to extract the filtering logic into a custom hook, keep the JSX in the main component, and maintain the existing prop interface" produces a concrete change you can review.

The specificity requirement feels restrictive at first — with a human colleague, you could say "improve this" and have a discussion. With a coding assistant, the discussion needs to happen in the prompt. You have to be clear about what "improve" means before the work starts.

The benefit: writing precise requests forces you to think precisely about what you want. Imprecise requests are often imprecise requirements. The discipline of specifying concretely produces better specifications, which produces better implementations.

## Reviewing AI-generated code

Code produced by Claude Code should be reviewed like code produced by a human developer: with appropriate skepticism, focused on correctness and fit rather than style.

The failure mode we've encountered: reviewing AI output too quickly because it looks correct. AI-generated code often looks more authoritative than it is. The syntax is right, the style is consistent, the implementation is plausible — but the logic might be wrong at the edge cases, or the design might be solving the stated problem while missing the actual one.

The review checklist we run:
1. Does it do what I asked? (Not "does it look like it does" — actually trace through the logic)
2. Does it handle edge cases? (What happens with empty arrays, null values, network failures)
3. Is it simpler than it needs to be? (Claude tends toward completeness; sometimes simpler is better)
4. Does it fit with how the rest of the codebase works? (Patterns, naming, conventions)

Point 3 is the most common catch. Claude will implement a complete solution to the stated problem, sometimes with abstraction layers that aren't needed. "You've implemented this correctly, but the hook isn't necessary for this case — inline the logic in the component."

## When not to use it

Claude Code is not always the right tool.

**Exploration is sometimes better than implementation.** If you're figuring out the right abstraction — not sure yet whether something should be a hook, a component, a utility function — thinking it through yourself first often produces a clearer result than starting with AI output that locks you into one approach.

**Debugging is sometimes slower with AI.** Giving Claude a bug to fix can produce a correct fix without an understanding of why the bug existed. If the bug reveals something systematic about how the codebase works, understanding it yourself is valuable. Not every bug should be delegated.

**Novel problem domains require your judgment.** For well-understood problems (a form component, a data fetching hook, a utility function), Claude has strong priors. For novel problems specific to your codebase or domain, Claude's output reflects general patterns rather than specific knowledge. Your judgment about what's right for this specific context is more reliable than the model's.

## The compounding effect

The most significant thing about AI-assisted development is how it compounds. Early sessions require more context-setting and correction. As you develop patterns for how to work with the model — what to specify, what to verify, when to design before implementing — velocity increases.

Six months in, a session that would have taken an hour at the start takes 20 minutes. Not because the model improved (though it did), but because the working patterns improved.

This is the part that doesn't show up in benchmarks or capability comparisons: the meta-skill of working effectively with an AI coding assistant. It takes time to develop and the investment pays compound returns.
