Pagination is one of those problems that looks solved until you have real data. Offset-based pagination works fine up to a few thousand rows. After that, the database is doing work proportional to the offset size, and users see duplicated or skipped items as the data changes between pages.

Here's what we use and why.

## Offset pagination: the familiar pattern

```ts
// Page 3, 20 items per page
const items = await db
  .select()
  .from(listings)
  .where(eq(listings.workspaceId, workspaceId))
  .orderBy(desc(listings.createdAt))
  .limit(20)
  .offset(40);  // skip first 2 pages = 2 × 20 = 40 rows

const total = await db
  .select({ count: count() })
  .from(listings)
  .where(eq(listings.workspaceId, workspaceId));
```

The UI gets a `total` count and can calculate total pages. This is the familiar "Page 1 of 47" pattern.

**Why this breaks at scale:**

1. `OFFSET 40000` requires the database to read and discard 40,000 rows before returning 20. At large offsets, this is expensive.

2. If a new item is inserted between page loads, every subsequent page shifts by one. A user browsing page 3 might see the last item from page 2 again (or miss an item entirely).

3. The `COUNT(*)` query on large tables takes time proportional to the table size.

For The Marqet's listing browser (167+ listings per category, growing), offset pagination was noticeably slow past page 10. We replaced it with cursor pagination.

## Cursor pagination: the production pattern

Cursor pagination uses a value from the last seen item as the starting point for the next page, rather than a numeric offset:

```ts
interface CursorParams {
  cursor?: string;  // encoded cursor from previous page
  limit?: number;
}

interface ListingsPage {
  items: typeof listings.$inferSelect[];
  nextCursor: string | null;
  hasMore: boolean;
}

async function getListingsPage(
  workspaceId: string,
  { cursor, limit = 20 }: CursorParams,
): Promise<ListingsPage> {
  let createdAtCursor: Date | undefined;
  let idCursor: string | undefined;

  if (cursor) {
    // Decode the cursor: base64-encoded JSON with {createdAt, id}
    const decoded = JSON.parse(Buffer.from(cursor, 'base64url').toString());
    createdAtCursor = new Date(decoded.createdAt);
    idCursor = decoded.id;
  }

  const items = await db
    .select()
    .from(listings)
    .where(
      and(
        eq(listings.workspaceId, workspaceId),
        cursor
          ? or(
              lt(listings.createdAt, createdAtCursor!),
              and(
                eq(listings.createdAt, createdAtCursor!),
                lt(listings.id, idCursor!),  // tie-break by ID
              ),
            )
          : undefined,
      )
    )
    .orderBy(desc(listings.createdAt), desc(listings.id))
    .limit(limit + 1);  // fetch one extra to detect hasMore

  const hasMore = items.length > limit;
  const page = hasMore ? items.slice(0, limit) : items;

  const lastItem = page[page.length - 1];
  const nextCursor = lastItem
    ? Buffer.from(JSON.stringify({
        createdAt: lastItem.createdAt.toISOString(),
        id: lastItem.id,
      })).toString('base64url')
    : null;

  return { items: page, nextCursor, hasMore };
}
```

Key design decisions:

**Composite cursor (createdAt + id):** Using `createdAt` alone fails when multiple rows have the same timestamp. The tie-break on `id` ensures a stable sort even with identical timestamps.

**Fetch limit + 1:** Requesting one more item than needed tells us whether there's a next page without a separate COUNT query.

**base64url encoding:** Opaque to the client — they treat it as a black box and pass it back unchanged. URL-safe encoding avoids issues in query strings.

**Stable sort:** The sort order must be consistent between requests. If the query sorts by `createdAt DESC`, new items inserted at the top of the table are invisible to paginated clients until they start a new session — which is usually the right behavior for feed-style pagination.

## The index matters

Cursor pagination relies on the database using an index for the cursor condition:

```sql
-- Index that makes cursor pagination fast
CREATE INDEX ON listings (workspace_id, created_at DESC, id DESC);
```

Without this index, the cursor condition (`WHERE created_at < ? OR (created_at = ? AND id < ?)`) requires a full table scan. With it, PostgreSQL jumps directly to the cursor position.

The `EXPLAIN ANALYZE` output before adding the index shows `Seq Scan` — after, it shows `Index Scan` with very low cost.

## When to use which

**Offset pagination:**
- When total counts are essential UI (admin tables with "243 results, page 12 of 25")
- Small tables (under a few thousand rows) where offset cost is negligible
- When the dataset doesn't change between pages (static exports, historical data)

**Cursor pagination:**
- Feed-style UI where "load more" replaces page numbers
- Live data that changes between requests
- Large or growing tables where offset cost becomes significant
- Any case where skipped/duplicated items are unacceptable

The Marqet's public listing browser uses cursor pagination with an infinite scroll trigger. The admin panels use offset pagination with explicit page numbers — the data is small and counts matter for the admin interface.

## The API response shape

For cursor pagination, we return a consistent envelope:

```ts
interface PaginatedResponse<T> {
  data: T[];
  pagination: {
    hasMore: boolean;
    nextCursor: string | null;
    count: number;  // count of items in this response, not total
  };
}
```

No total count — that requires a separate expensive query. If the UI needs to show "X items returned so far," the client accumulates the count across pages. If it genuinely needs a total, add a separate count endpoint that the UI calls once.
